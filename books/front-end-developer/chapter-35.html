Chapter 35 — Performance: Loading and Rendering

Section 1 — What performance means

Performance is how quickly a page becomes usable and how smoothly it responds afterwards, as experienced by a real user on a real device and connection. It is not a single number, but a set of experiences: loading, responding, and staying smooth. In plain terms, what the user sees should follow from a value you can point to and name, rather than from a hidden side effect in several places at once. When you first meet what performance means, it can look like a small detail, but it shapes how the rest of the work behaves, so it is worth understanding before the code around it grows.

Why does this matter in real work? Because front-end code is judged by what users experience. If what performance means is handled carelessly, the symptoms are familiar: stale information, a button that works once and then stops, or a form that loses what was typed. Users rarely report the underlying cause; they report that the site feels broken, and they leave. Getting this idea right saves the user's time and your own time when you return to the code later.

How do you apply it in practice? Start by naming the thing you are working with, then state what should happen in a single sentence before you write code. Next, make the smallest change that produces that behaviour, and look at the result in the browser rather than assuming it worked. Then try the awkward cases: an empty value, a very long value, and a rapid repeated action. Those cases are where most front-end ideas fail, not in the happy path where everything is typed correctly and the network is fast.

Here is a short example to make the idea concrete:

import('./HeavyChart.js');

Read the example slowly and notice what each part contributes. The point is not to memorise the snippet, but to see the pattern: a named value, an action that changes it, and a visible result that follows from it. Try changing one part in your head and predicting the result before you run anything, because a wrong prediction tells you exactly which part of your mental model needs correcting.

A common mistake is to rush past this idea and treat it as obvious, then to improvise a different approach in each part of a project. That is how inconsistency creeps in, and nobody can say which approach is correct. Another common mistake is to add complexity before the simple version has been tried. To check your own work, explain the idea aloud, demonstrate it with a tiny example, and try one case that should fail gracefully.

A useful habit is to measure before and after a change on the same device and connection, because a change that feels faster in development may not help real visitors.

When a page feels slow, find the largest cost first instead of tuning small details, because one heavy image or one large script often outweighs many tiny savings.
