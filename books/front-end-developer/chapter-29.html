Chapter 29 — Introduction to React (concepts)

Section 1 — What React is, at concept level

React is a JavaScript library for building user interfaces from components. Instead of writing a page as a single document that you edit directly whenever something changes, you describe components, small pieces of interface such as a button, a card, or a list, and React assembles them into the page and keeps the display in sync with your data. When the data changes, React updates only the parts of the page that need to change.

React is a library, not a complete framework, which means it focuses on the interface layer: how components are defined, how they receive data, and how they update. Other concerns, such as fetching data, routing between pages, and form handling, are handled by additional libraries or by code you write, chosen to fit the project. That focus is deliberate: React does one job, the interface, and it does it through components. In practice, start small and observe the result before adding more. Build one component or one page section, apply the idea there, open the page in a browser, and resize the window to see how it behaves. Small, observable steps make it obvious which change caused which effect, and that feedback loop is how good front-end judgement is formed.

For example, a React application might consist of a header component, a list component, and a card component, composed together like building blocks. Each component is a JavaScript function that describes what it should display, and React turns those descriptions into the page the user sees. A common mistake is to copy a solution without understanding what each part does, then to be stuck when it needs adjusting. Avoid that by reading the example line by line and asking what would happen if each part were removed. The lines you cannot explain are the lines most likely to cause trouble later.

A common mistake is thinking of React as a different language. It is JavaScript, using JavaScript functions, values, and logic, plus a few ideas and a special syntax that this chapter explains at concept level. To check your own work, open the page, inspect the relevant element in developer tools, and confirm that the styles you expect are actually applied rather than overridden or ignored. Then change the browser width, reload, and confirm nothing has broken. Write down anything surprising; those notes become your personal checklist for the next project.

Try it now: make a tiny page with two or three elements, apply this idea to them, and compare the result with a version that does not use it. Notice what got easier, what got harder, and what you would want to change next time. That comparison is the real lesson, and it will guide your choices on larger pages.

Section 2 — Why React was created

React was created to solve a problem that grows with interactive pages: keeping the display consistent with the data behind it. In a page built by directly editing elements, every user action may require several separate edits to different parts of the page, and it is easy to update one part and forget another, leaving the screen in a contradictory state. As pages grew more interactive, with lists that filter, forms that validate live, and dashboards that update constantly, that manual updating became the main source of bugs. Think of this as a working habit rather than a piece of trivia. You will use it on almost every page you build, and the benefit appears gradually: files stay shorter, decisions become easier to explain to a teammate, and fixing a visual bug takes minutes instead of an afternoon of hunting through unrelated rules.

React's answer is to change the direction of the work. Instead of writing instructions for how to update the page step by step, you describe what the page should look like for a given set of data, and React works out the updates when the data changes. That description, called declarative programming, is easier to reason about, because the code states the intended result, not a sequence of edits. When you apply this idea, keep the surrounding code in mind. A front-end page is a system: markup, styles, and behaviour interact, and a choice that looks good in isolation can create a problem elsewhere, such as overflowing content on a narrow screen or a colour that fails a contrast check. Test the whole page, not just the fragment you edited.

For example, a list that should show only matching items can be described as the items that match the search, and React will add or remove list entries as the search changes. You do not write separate code for adding and removing; you describe the result, and React handles the transition. Another frequent mistake is to mix approaches in the same file without a reason: part of the page follows one convention and part follows another. That inconsistency makes the code harder to scan and harder to maintain, because a reader cannot predict which convention applies where. Pick one approach for a given job and use it consistently.

A common mistake is trying to use React as if it were direct page editing, reaching in to change elements by hand. That fights the library's model and reintroduces the inconsistency it was designed to prevent. A good self-check is to explain the idea aloud in one or two sentences without looking at this section. If you can do that and give a correct example, you understand it well enough to use it. If you cannot, re-read the example and try building a tiny version from scratch before moving on.

For practice, take an existing practice page and rework one section using this idea, keeping the visible result the same. If the page looks identical but the code is clearer or shorter, the rework was worthwhile. If the result changed unexpectedly, you have found a gap in your understanding worth closing before you rely on the idea in a bigger project.

Section 3 — Declarative versus imperative UI

Declarative user interface code describes what the interface should be, while imperative code describes how to change it step by step. An imperative approach to showing a message might say: find the message element, change its text, remove a hidden class, and add a visible class. A declarative approach says: when this condition is true, show this message, and leaves the steps to the library. The difference matters most as interfaces grow, because declarative code stays readable while imperative code accumulates steps. The reason this matters for a beginner is that early choices compound. If you adopt a messy approach on a small practice page, the same approach will feel natural on a larger project, where its cost is much higher. Learning the disciplined version now saves you from having to unlearn a habit later, when a real deadline is involved.

Declarative code is easier to debug because the display is a function of the data: if the screen is wrong, the data or the description is wrong, and there are only two places to look. Imperative code can be wrong in any of its steps, and the steps may have run in an order that is hard to reconstruct. That is why modern interface libraries, including React, favour the declarative style, even though it requires a shift in thinking for developers used to direct editing. A practical test is to change one thing deliberately. Alter a value, remove a class, or rename something, then refresh and watch what breaks. That experiment teaches you what actually depends on the idea, which is far more useful than memorising a definition. Undo the change afterwards and confirm the page returns to normal.

For example, a declarative description of a button might be: show a loading label while saving, and the normal label otherwise. The condition is visible in the code, and the two states are both designed, rather than one being the result of a sequence of edits. Watch out for overuse. A technique that helps in moderation can hurt when applied everywhere: too many classes, too many wrappers, or too many overrides all add weight and confusion. If a page feels complicated, look for the simplest version that still meets the design, and prefer that version.

A common mistake is mixing the two styles, describing most of the interface declaratively but patching one element imperatively when it misbehaves. That patch will be overwritten on the next update, producing a bug that appears and disappears mysteriously. Keep a small practice file where you try each idea in isolation. A tiny page with a single component is a better laboratory than a large project, because there is nothing else to confuse the result. Once the idea works there, carry it into a real page with confidence.

A helpful exercise is to build the same small component twice: once with this approach and once without it. Put the two versions side by side and judge them on readability, ease of change, and behaviour on a narrow screen. There is rarely one winner for every situation, and learning when each approach wins is the skill that matters.

Section 4 — Components in React

In React, a component is a JavaScript function that returns a description of what should appear on the page. That description is written in a syntax that looks like HTML, which you will meet shortly as JSX, but it is produced by a function, which means it can use JavaScript logic: variables, conditions, and lists. A component can be as small as a button or as large as a whole page section, and components compose by using other components inside their descriptions. A useful way to judge this idea is to ask what happens when the design changes. Clients and designers change colours, spacing, and layouts often. An approach that survives those changes without a rewrite is a good one; an approach that forces you to edit dozens of files for one small change is a warning sign.

The function idea is important, because it means a component is reusable logic, not a copied block of markup. Calling the same component function with different inputs produces different outputs, and the component's internal logic is written once. It also means components can be tested like functions: give them inputs, check their outputs, and confirm they behave correctly in each case. Do not adopt this idea blindly on every element. Ask whether it earns its place in this particular case: does it make the code clearer, the page faster, or the design more consistent? If the answer is no, plain hand-written code may be the better choice. Good developers choose tools for a reason they can state.

For example, a greeting component might be a function that accepts a name and returns a heading containing that name. Using it with different names produces different headings, all from one definition, and the logic for formatting the greeting lives in exactly one place. A subtler mistake is to optimise for the first screen you test and forget the rest. Check a narrow phone width, a large desktop width, and a zoomed-in view. Many front-end bugs only appear at an extreme, and catching them early is much cheaper than explaining them to a user who has already encountered them.

A common mistake is writing a component as a single large function that does everything on a page, instead of breaking it into smaller components. Small components are easier to understand, test, and reuse, just as small functions are. Section 5 — JSX: the idea, not the syntax rules

JSX is a syntax extension for JavaScript that lets you write markup-like code inside JavaScript, so that a component's output looks like the HTML it will produce. Instead of building page elements with long function calls, you write something resembling <h1>Hello</h1> inside your component, and a build tool converts it into the JavaScript calls that create those elements. JSX is not HTML, and it is not a string of HTML: it is JavaScript syntax that describes elements, and it can contain JavaScript expressions inside curly braces. This idea also affects how other people read your work. A teammate, a future version of yourself, or a reviewer judging a portfolio project should be able to open your code and understand the intention quickly. Clear, consistent choices communicate professionalism even before anyone runs the page.

The reason JSX exists is readability. A component's output is easier to understand when it looks like the structure it produces, with nesting visible as nesting, than when it is a nest of function calls. The curly-brace expressions are the bridge: they let you insert a variable, a calculation, or a conditional result into the markup, so the description can vary with data while remaining readable as structure. Remember accessibility while you work. Visual changes are not only about appearance; they affect whether text remains readable, whether interactive elements remain reachable by keyboard, and whether a screen reader still announces content in a sensible order. Check those things as you go, not as an afterthought at the end.

For example, a component might return <p>Welcome, {name}</p>, where the braces insert the value of the name variable into the paragraph. The markup shows the structure; the braces show where data enters it. That combination is the essence of JSX. Finally, do not confuse looking finished with being finished. A page can look correct in one browser and fail in another, or look correct with short sample text and break with a long real heading. Test with realistic content, realistic text lengths, and at least one other browser before you call the work done.

A common mistake is treating JSX as HTML and being confused when an HTML attribute or habit does not work the same way. JSX follows JavaScript rules in places, such as its handling of certain attribute names, so learn it as its own syntax, not as HTML pasted into JavaScript. A good self-check is to explain the idea aloud in one or two sentences without looking at this section. If you can do that and give a correct example, you understand it well enough to use it. If you cannot, re-read the example and try building a tiny version from scratch before moving on.

Practice deliberately: create a small test page, apply the idea, break it on purpose by changing one value, and then fix it. The break-and-fix cycle teaches you the boundaries of the idea far faster than reading alone, and it builds the calm debugging habit that professional work depends on.

Section 6 — The virtual DOM idea

The virtual DOM is React's way of updating the page efficiently. Instead of changing the real page directly on every data change, React keeps a lightweight, in-memory representation of what the page should look like, called the virtual DOM. When data changes, React builds a new virtual representation, compares it with the previous one to find exactly what changed, and then updates only those parts of the real page. That comparison step is called diffing, and the update step is called reconciliation. In plain terms, this idea exists because real projects grow. A page that starts with a handful of styles can end up with hundreds, and without a clear approach the stylesheet becomes hard to read, hard to change, and easy to break by accident. The idea in this section gives you a rule you can apply consistently, so that a change in one place does not produce a surprise somewhere else on the site.

The benefit is not that the virtual DOM is faster than a direct edit in every single case; a single direct edit can be faster. The benefit is that developers no longer need to work out, by hand, the minimal set of edits for a complex change. React does that work, reliably, for every change, which removes a whole class of inconsistency bugs. It also means the developer's job is to describe the desired result, not to optimise the update steps. In practice, start small and observe the result before adding more. Build one component or one page section, apply the idea there, open the page in a browser, and resize the window to see how it behaves. Small, observable steps make it obvious which change caused which effect, and that feedback loop is how good front-end judgement is formed.

For example, when one item in a list of fifty changes, React's comparison finds that single item and updates only it, rather than rebuilding the whole list. The developer described the new list; React worked out the minimal update. A common mistake is to copy a solution without understanding what each part does, then to be stuck when it needs adjusting. Avoid that by reading the example line by line and asking what would happen if each part were removed. The lines you cannot explain are the lines most likely to cause trouble later.

Section 7 — Props in React

Props in React are the inputs passed to a component, supplied as attributes in JSX and received by the component function as an object. A parent component passes data down to a child by writing attributes on the child's element, and the child reads those values to decide what to display. Props flow in one direction, from parent to child, which makes data flow predictable: to understand what a component displays, you look at what its parent passed it. Think of this as a working habit rather than a piece of trivia. You will use it on almost every page you build, and the benefit appears gradually: files stay shorter, decisions become easier to explain to a teammate, and fixing a visual bug takes minutes instead of an afternoon of hunting through unrelated rules.

One-way data flow is a deliberate design choice. Because data does not flow back up through props, a child cannot silently change its parent's data; it can only announce events, which the parent may handle by changing its own state and passing new props down. That cycle, props down and events up, is the same pattern you met in component thinking, now made concrete by React's mechanism. When you apply this idea, keep the surrounding code in mind. A front-end page is a system: markup, styles, and behaviour interact, and a choice that looks good in isolation can create a problem elsewhere, such as overflowing content on a narrow screen or a colour that fails a contrast check. Test the whole page, not just the fragment you edited.

For example, a card component might receive a title and a summary as props, written as <Card title="Hello" summary="A short text" />, and render them in its markup. The same card component, given different props, renders a different card, without any change to its definition. Another frequent mistake is to mix approaches in the same file without a reason: part of the page follows one convention and part follows another. That inconsistency makes the code harder to scan and harder to maintain, because a reader cannot predict which convention applies where. Pick one approach for a given job and use it consistently.

A common mistake is mutating props inside a component, trying to change the values it received. Props should be treated as read-only; if a value needs to change, the owner of that data should change it and pass new props down. Section 8 — State in React

State in React is data that a component owns and can change over time, such as whether a menu is open, what a user has typed, or which item is selected. When state changes, React re-renders the component, producing a new description of its output, and updates the page to match. That automatic re-render is the core of React's interactivity: you change the state, and the display follows, without you writing update steps. The reason this matters for a beginner is that early choices compound. If you adopt a messy approach on a small practice page, the same approach will feel natural on a larger project, where its cost is much higher. Learning the disciplined version now saves you from having to unlearn a habit later, when a real deadline is involved.

State differs from props in ownership: props come from a parent, state lives inside the component. A component's state should hold the smallest set of facts that describe its situation, and everything else should be derived from it when rendering, for the same reasons you met in component thinking. Keeping state minimal prevents contradictions, because there is only one copy of each fact, and the display is always computed from it. A practical test is to change one thing deliberately. Alter a value, remove a class, or rename something, then refresh and watch what breaks. That experiment teaches you what actually depends on the idea, which is far more useful than memorising a definition. Undo the change afterwards and confirm the page returns to normal.

For example, a toggle component might hold a single boolean state, open or closed, and render its content only when open. Clicking the toggle flips the state, React re-renders, and the content appears or disappears. The developer never writes code to show or hide the element directly. Watch out for overuse. A technique that helps in moderation can hurt when applied everywhere: too many classes, too many wrappers, or too many overrides all add weight and confusion. If a page feels complicated, look for the simplest version that still meets the design, and prefer that version.

A common mistake is storing data in state that could be derived from props or from other state, creating two copies that can disagree. Store the facts, derive the rest. Section 9 — Rendering: from description to page

Rendering in React means turning a component's description into actual page elements, and re-rendering means doing it again when props or state change. The first render builds the page; later renders update it. React does not rebuild the whole real page on every render; it compares the new description with the previous one, as described in the virtual DOM section, and applies only the necessary changes to the real page. The word rendering therefore refers to producing the description and reconciling it, not to repainting everything. A useful way to judge this idea is to ask what happens when the design changes. Clients and designers change colours, spacing, and layouts often. An approach that survives those changes without a rewrite is a good one; an approach that forces you to edit dozens of files for one small change is a warning sign.

Understanding rendering helps you reason about performance and bugs. A component re-renders when its own state changes or when its parent passes new props, and its children may re-render as a result. That cascade is normal, but it means a component should render quickly and without side effects, such as fetching data or changing other state during rendering. Side effects belong in separate, controlled places that React provides for that purpose. Do not adopt this idea blindly on every element. Ask whether it earns its place in this particular case: does it make the code clearer, the page faster, or the design more consistent? If the answer is no, plain hand-written code may be the better choice. Good developers choose tools for a reason they can state.

For example, typing in a search box changes the box component's state, which triggers a re-render, which produces a new description of the results list, which React reconciles into the page. The chain from keystroke to updated list is a series of renders, not a series of direct page edits. A subtler mistake is to optimise for the first screen you test and forget the rest. Section 10 — One-way data flow

One-way data flow means data moves in a single, predictable direction through a React application: from parent components down to children through props, and from children back to parents through event announcements, not through direct data changes. The application's state lives in specific components, and changes to it flow down as new props, causing re-renders that update the display. There is no hidden channel by which a distant component can change another's data. This idea also affects how other people read your work. A teammate, a future version of yourself, or a reviewer judging a portfolio project should be able to open your code and understand the intention quickly. Clear, consistent choices communicate professionalism even before anyone runs the page.

Predictability is the payoff. When the screen shows something unexpected, you can trace the data backwards: which component rendered this, what props did it receive, and which component owns the state those props came from? That chain is always visible in the component tree, because data flow follows the tree. In a system where any component could change any other's data, tracing a bug would require searching the whole application. Remember accessibility while you work. Visual changes are not only about appearance; they affect whether text remains readable, whether interactive elements remain reachable by keyboard, and whether a screen reader still announces content in a sensible order. Check those things as you go, not as an afterthought at the end.

For example, a shopping basket total is computed from the basket state held by a parent, passed down to a summary component as a prop, and displayed there. The summary cannot change the total; only the parent, responding to add or remove events, can change the basket state, which then flows down again as a new total. Finally, do not confuse looking finished with being finished. A page can look correct in one browser and fail in another, or look correct with short sample text and break with a long real heading. Section 11 — Lists and keys in React

Rendering a list in React means turning a collection of data into a collection of components, usually by transforming each data item into a component element. Each item in such a list needs a key, a stable identifier that tells React which component corresponds to which data item when the list changes. Keys let React match old and new lists correctly, so that adding, removing, or reordering items updates the right components instead of confusing them. In plain terms, this idea exists because real projects grow. A page that starts with a handful of styles can end up with hundreds, and without a clear approach the stylesheet becomes hard to read, hard to change, and easy to break by accident. The idea in this section gives you a rule you can apply consistently, so that a change in one place does not produce a surprise somewhere else on the site.

Keys matter most when a list changes. Without a stable key, React may reuse a component for a different item, carrying over its state incorrectly, such as showing one item's expanded state on another item after a sort. With a stable key, usually an identifier from the data, React tracks each item correctly across changes. The key is not displayed; it is bookkeeping for React's reconciliation, and it should be stable, unique among siblings, and derived from the data, not from position.

For example, a list of articles might render each article as a card with a key set to the article's identifier. When a new article is added at the top, React uses the keys to recognise the existing articles and adds only the new card, leaving the others untouched. A common mistake is to copy a solution without understanding what each part does, then to be stuck when it needs adjusting. Avoid that by reading the example line by line and asking what would happen if each part were removed. The lines you cannot explain are the lines most likely to cause trouble later.

A common mistake is using the item's index in the list as its key. Indices change when the list is sorted or filtered, which defeats the purpose of the key and can produce exactly the confusion keys exist to prevent. Section 12 — Conditional rendering in React

Conditional rendering in React means that a component's output varies with its props or state, using ordinary JavaScript logic: conditions, variables, and short-circuit expressions inside the component function. Because a component is a function returning a description, it can return one description in one case and a different description in another, and React will update the page accordingly when the condition changes. There is no separate template language for conditions; JavaScript itself is the mechanism. Think of this as a working habit rather than a piece of trivia. You will use it on almost every page you build, and the benefit appears gradually: files stay shorter, decisions become easier to explain to a teammate, and fixing a visual bug takes minutes instead of an afternoon of hunting through unrelated rules.

This approach unifies the states you met in component thinking: loading, empty, error, and success are simply different return values of the same component, chosen by its current state. Writing them as branches of one function keeps the states together and makes it obvious when a state is missing, because the function's logic shows every case it handles and, by omission, every case it does not. Section 13 — Events in React

Events in React are handled by passing functions as props, usually written as attributes on elements in JSX, such as an on-click handler. When the user interacts with the element, React calls the handler function, which typically changes state or announces an event to a parent component. The handler is ordinary JavaScript, so it can read state, compute values, and decide what to do, but it should not directly edit the page's elements, because React owns the display and will overwrite direct edits on the next render. Each small project should exercise one new idea, and each should be finished and tested before the next begins. A useful way to judge this idea is to ask what happens when the design changes. Clients and designers change colours, spacing, and layouts often. An approach that survives those changes without a rewrite is a good one; an approach that forces you to edit dozens of files for one small change is a warning sign.

A good first sequence is: a component that renders fixed content, then the same component with props, then a counter with state, then a list with keys, then a form with a controlled input, then a small application composing several components. That sequence covers React's core in the order this chapter introduced it, and each step is small enough to debug when it fails. Resist the temptation to start with a large tutorial application; its size will hide the concepts this chapter worked to make clear. Do not adopt this idea blindly on every element. Ask whether it earns its place in this particular case: does it make the code clearer, the page faster, or the design more consistent? If the answer is no, plain hand-written code may be the better choice. Good developers choose tools for a reason they can state.

For example, a todo list is an ideal first application because it uses state for the items, props for each item, keys for the list, events for adding and toggling, and conditional rendering for the empty state. It is small, but it is complete. A subtler mistake is to optimise for the first screen you test and forget the rest. Check a narrow phone width, a large desktop width, and a zoomed-in view. Many front-end bugs only appear at an extreme, and catching them early is much cheaper than explaining them to a user who has already encountered them.

A common mistake is building a first React project that is too large, and then attributing its difficulties to React rather than to its size. Small and finished beats large and abandoned. To check your own work, open the page, inspect the relevant element in developer tools, and confirm that the styles you expect are actually applied rather than overridden or ignored. Then change the browser width, reload, and confirm nothing has broken. Write down anything surprising; those notes become your personal checklist for the next project.

To make this stick, add the idea to your next practice project in exactly one place, and keep a short note about why you chose it there. Later, when you review the project, that note will tell you whether the choice paid off. Over several projects, those notes become a reliable personal guide to what works for you.

Section 50 — Chapter 29 in one paragraph, revisited

This final section returns to the chapter's central claim, because it is worth restating after the details: React is a way of describing interfaces as components, where data flows down through props, events flow up through handlers, state lives in the component that owns it, and the screen is always a function of props and state. JSX lets those descriptions look like the structure they produce, the virtual DOM lets React update the real page efficiently, and hooks, effects, and context are mechanisms that extend the same model to state, side effects, and shared data. This idea also affects how other people read your work. A teammate, a future version of yourself, or a reviewer judging a portfolio project should be able to open your code and understand the intention quickly. Clear, consistent choices communicate professionalism even before anyone runs the page.

If you remember nothing else from this chapter, remember that cycle: an event changes state, state triggers a re-render, and the re-render updates the page. Every other idea in the chapter, from keys to fragments to controlled components, is a refinement of that cycle for a particular situation. Later chapters will make the cycle concrete in code, but the cycle itself, understood now, will make that code intelligible rather than mysterious. Remember accessibility while you work. Visual changes are not only about appearance; they affect whether text remains readable, whether interactive elements remain reachable by keyboard, and whether a screen reader still announces content in a sensible order. Check those things as you go, not as an afterthought at the end.

For example, explain the cycle to a friend using a todo list, a search box, or any interface you know well, without mentioning any syntax. If the explanation is clear, the concepts are yours; syntax is then a matter of learning how to write down what you already understand. Finally, do not confuse looking finished with being finished. A page can look correct in one browser and fail in another, or look correct with short sample text and break with a long real heading. Test with realistic content, realistic text lengths, and at least one other browser before you call the work done.

A common mistake is finishing a concepts chapter without testing the concepts against a real design. Sketch one interface, name its components, and trace one event through its cycle before you move on. A good self-check is to explain the idea aloud in one or two sentences without looking at this section. If you can do that and give a correct example, you understand it well enough to use it. If you cannot, re-read the example and try building a tiny version from scratch before moving on.

Practice deliberately: create a small test page, apply the idea, break it on purpose by changing one value, and then fix it. The break-and-fix cycle teaches you the boundaries of the idea far faster than reading alone, and it builds the calm debugging habit that professional work depends on.
