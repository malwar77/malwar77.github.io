Chapter 38 — Working with APIs and Data Display

Section 1 — What an API is

An API, or application programming interface, is an agreed way for one piece of software to ask another piece of software for data or for an action, without needing to know how the other piece works inside. For a front-end developer, an API is usually a server address that your page can request data from, such as a list of articles, a product catalogue or a weather forecast, and that returns that data in a structured form your page can display. The front end does not own the data; it asks for it, receives it, and presents it. Users rarely notice this when it works, which is exactly the point; they only notice it when it is missing, broken or inconsistent. That matters because the people using the page judge it by what they can see, understand and do, not by how clever the code behind it looks.

Using an API starts with knowing its address, what it returns, and what it expects in return, such as parameters or a method. You request a resource, you receive a response, you check whether the response succeeded, and you display its contents, or a clear error if it failed. You do not need to know how the server stores its data or how it calculates its answers; you only need the agreed contract, which is usually documented by the API provider, and you must handle the cases where the contract is not met, such as missing data or a failed request. When something goes wrong, trace the same steps in reverse, asking at each point what you expected and what actually happened. Work through it slowly, one step at a time, and check what changes at each step instead of trying to fix everything at once.

Section 2 — JSON in plain words

JSON, short for JavaScript Object Notation, is a text format for structured data that is easy for both people and machines to read. It represents data as objects, which are collections of named values, arrays, which are ordered lists, and simple values such as text, numbers and true or false. Because it is plain text, it can travel over the web in a response, be read by a developer, and be turned into JavaScript values that a page can display, which is why it is the most common format for web APIs. That matters because the people using the page judge it by what they can see, understand and do, not by how clever the code behind it looks. It also matters for trust: when this part behaves predictably, visitors are more willing to stay, return and complete the task they came for.

Reading JSON means following its structure: an object is wrapped in curly braces, an array in square brackets, and each name is quoted, followed by a colon and a value. A front-end developer reads JSON to understand what fields are available, such as a title, an author and a date, and then uses those fields to build the page, for example by putting the title in a heading and the author in a paragraph. If a field is missing, the page must handle that gracefully, rather than breaking or showing an empty or broken element. Work through it slowly, one step at a time, and check what changes at each step instead of trying to fix everything at once. If you can describe the flow in plain words before you write code, the code itself becomes much easier to write and to debug.

Section 3 — GET requests

A GET request is a request to retrieve data, without changing anything on the server, such as asking for a list of guides, a single article, or a product's details. It is the most common kind of API request in front-end work, because most pages begin by getting data to display, and it is considered safe in the technical sense that repeating it should not change the server's state, even if it is repeated many times. That safety is a promise the front end should respect: a GET request should never be used to delete, create or change something. In real projects this idea shows up again and again, in small pages and in large applications alike, so learning it well now saves repeated confusion later. It is worth learning properly rather than copying a snippet and hoping, because a copied snippet hides the choices you will need to make when the real content differs.

To make a GET request, you name the resource's address, add any parameters that narrow the request, such as a search term or a page number, and send it, usually with the browser's fetch function, which is covered later. The server answers with a status code and, on success, the requested data, which the front end then displays. If the resource does not exist, the server answers with a not-found status, and the front end should show a clear message, rather than an empty page or a broken layout, because a missing resource is a normal outcome, not an exception to hide. Notice the order of the steps: each one depends on the one before it, and skipping a step usually creates a fault that looks mysterious later. A useful habit is to test with realistic content, not only with a perfect example, because long titles, empty lists and slow networks reveal the real behaviour.

Section 4 — Other request methods

Beyond GET, APIs use other methods to describe the kind of action being requested. POST is used to create something new, such as submitting a comment, PUT or PATCH are used to update something that already exists, with PUT usually replacing it and PATCH usually changing part of it, and DELETE is used to remove something. Each method has a meaning, and using the right method matters, because the server, caches and other tools all rely on that meaning to handle the request correctly. Users rarely notice this when it works, which is exactly the point; they only notice it when it is missing, broken or inconsistent. That matters because the people using the page judge it by what they can see, understand and do, not by how clever the code behind it looks.

In the front end, you choose the method by asking what the action does: are you creating, reading, updating or deleting. A form that creates a new item should use POST, a form that edits an existing item should use PUT or PATCH as the API specifies, and a delete button should use DELETE, with a confirmation step, rather than a simple link, because a link can be triggered accidentally. After a change, the front end should check the server's response, show a clear result, and refresh the displayed data from the server, rather than assuming the change worked. When something goes wrong, trace the same steps in reverse, asking at each point what you expected and what actually happened. Work through it slowly, one step at a time, and check what changes at each step instead of trying to fix everything at once.

Section 5 — Endpoints and resources

An endpoint is an address that represents a resource, such as a collection of guides, a single guide, or a guide's comments, and a well-designed API organises its endpoints around resources rather than around actions. A collection address, such as the guides address, returns the whole collection or a page of it, while an item address, which adds an identifier, returns one specific guide. That pattern is predictable: once you understand one resource, you can guess the shape of others, which makes an API easier to learn and a front end easier to build. In real projects this idea shows up again and again, in small pages and in large applications alike, so learning it well now saves repeated confusion later. It is worth learning properly rather than copying a snippet and hoping, because a copied snippet hides the choices you will need to make when the real content differs.

When building a front end, start by listing the resources the page needs, then the endpoints that provide them, and then the data each endpoint returns. For a guide site, the resources might be guides, authors and comments, and the endpoints might be a guides collection, a single guide, and that guide's comments. Keep the front-end code organised around those resources too, so the code that fetches guides, the code that displays them, and the code that handles their errors are easy to find and to change when the API changes. Notice the order of the steps: each one depends on the one before it, and skipping a step usually creates a fault that looks mysterious later. Section 6 — Query parameters

Query parameters are extra pieces of information added to an address after a question mark, used to narrow, sort or page a request, without changing which resource is being asked for. A request for guides might add a search term, a category, a sort order or a page number, each as a name and a value, joined by ampersands, and the server uses those values to filter or order its answer. Query parameters are therefore the front end's way of asking a more precise question, rather than asking for everything and filtering it all in the browser. The benefit is practical, not theoretical: a page that gets this right is easier to maintain, easier to test and easier to explain to another developer. Users rarely notice this when it works, which is exactly the point; they only notice it when it is missing, broken or inconsistent.

Build query parameters carefully, because values that contain spaces, ampersands or other special characters must be encoded, or the address will break, as covered in the chapter on sharing. Use parameters the API documents, and do not invent parameters in the hope the server will understand them, because an ignored parameter silently returns the wrong data. After receiving a filtered response, display the filter that was applied, so the visitor understands why they see those results and not others, and offer a clear way to clear the filter. Keep the responsibility clear: the front end presents and requests, and it should not pretend to decide things that belong elsewhere in the system. When something goes wrong, trace the same steps in reverse, asking at each point what you expected and what actually happened.

Section 7 — Headers in plain words

Headers are extra pieces of information sent with a request or a response, beyond the main data, that describe how the data should be handled. A request header might say what format the front end accepts, such as JSON, or what language it prefers, while a response header might say what format the data actually is, or how long it may be cached. Headers are not usually visible to visitors, but they affect whether a request succeeds, whether a response can be understood, and whether a cached copy may be reused. In real projects this idea shows up again and again, in small pages and in large applications alike, so learning it well now saves repeated confusion later. It is worth learning properly rather than copying a snippet and hoping, because a copied snippet hides the choices you will need to make when the real content differs.

For most front-end work, you need only a few headers, and you should set them as the API documents. The content-type header says what format a request body is in, such as JSON, when you send data to the server, and the accept header says what format you would like in return. Do not put secrets in headers from front-end code, and do not invent headers, because an unexpected header can cause a request to be rejected or to trigger extra security checks. When a request fails unexpectedly, checking the response headers and status, in the browser's developer tools, often explains why. Notice the order of the steps: each one depends on the one before it, and skipping a step usually creates a fault that looks mysterious later. A useful habit is to test with realistic content, not only with a perfect example, because long titles, empty lists and slow networks reveal the real behaviour.

Section 8 — Status codes

A status code is a three-digit number in a response that summarises the outcome of a request, and learning its broad families is more useful than memorising every code. Codes in the 200s mean success, codes in the 300s mean redirection, codes in the 400s mean the request itself was faulty, such as a missing resource or invalid data, and codes in the 500s mean something went wrong on the server's side. A front-end developer uses the code to decide what to show: success data, a not-found message, a validation error, or a server-error message, each of which is different. In real projects this idea shows up again and again, in small pages and in large applications alike, so learning it well now saves repeated confusion later. It is worth learning properly rather than copying a snippet and hoping, because a copied snippet hides the choices you will need to make when the real content differs.

Check the status before you try to display data, because a failed response may contain an error message rather than the data you expected, and displaying it as if it were data produces a confusing page. For a 404, show a clear not-found message with a way forward, as in the search chapter. For a 400, show the validation problem next to the field it concerns. For a 500, show a general server-error message and a retry option, without blaming the visitor. Log the code and the request that caused it, in development, so the cause can be found, but do not display technical details to visitors that would confuse them. Notice the order of the steps: each one depends on the one before it, and skipping a step usually creates a fault that looks mysterious later. A useful habit is to test with realistic content, not only with a perfect example, because long titles, empty lists and slow networks reveal the real behaviour.

Section 9 — Fetch in plain words

Fetch is the browser's built-in way for JavaScript to make a request to an API and receive a response, without reloading the page. It takes an address and, optionally, details such as the method and headers, and it returns a promise, covered in a later section, that resolves with the response when it arrives. Fetch is the foundation of most dynamic front-end data work: a page loads, it fetches data, it displays the data, and later it fetches again when the visitor searches, filters or changes page. In real projects this idea shows up again and again, in small pages and in large applications alike, so learning it well now saves repeated confusion later. It is worth learning properly rather than copying a snippet and hoping, because a copied snippet hides the choices you will need to make when the real content differs.

Using fetch well means handling its whole lifecycle, not only the successful case. Start by showing a loading state, then call fetch, then check the response status, then read the data, then display it, and if any step fails, show a clear error and a retry option. Remember that fetch only rejects its promise for a network failure, not for a 404 or a 500, so a failed status must be checked explicitly, which is a common source of bugs for beginners who assume a response always means success. Notice the order of the steps: each one depends on the one before it, and skipping a step usually creates a fault that looks mysterious later. A useful habit is to test with realistic content, not only with a perfect example, because long titles, empty lists and slow networks reveal the real behaviour.

Section 10 — Async and await

Async and await are JavaScript features that let you write code that waits for a slow operation, such as a fetch request, in a way that reads like ordinary, step-by-step code. A function marked async can pause at an await expression, letting the browser do other work, such as responding to clicks, while it waits, and then resume when the awaited operation finishes. The result is code that is easier to read than a long chain of callbacks, because the steps appear in the order they happen, even though the waiting happens in the background. Users rarely notice this when it works, which is exactly the point; they only notice it when it is missing, broken or inconsistent. That matters because the people using the page judge it by what they can see, understand and do, not by how clever the code behind it looks.

Use async and await by marking the function that fetches data as async, awaiting the fetch call, awaiting the reading of its data, and wrapping those steps in error handling, so a failed request is caught and shown as an error rather than crashing the page. Keep the waiting visible to the visitor with a loading state, because await does not make the network faster; it only makes the waiting code clearer. Avoid awaiting many independent requests one after another when they could run together, because sequential waiting adds up, but prefer clarity over cleverness when you are learning, and optimise only when a real delay is measured. When something goes wrong, trace the same steps in reverse, asking at each point what you expected and what actually happened. Work through it slowly, one step at a time, and check what changes at each step instead of trying to fix everything at once.

Section 11 — Promises in plain words

A promise is JavaScript's way of representing a value that is not available yet, such as the result of a fetch request that is still travelling over the network. A promise can be pending, meaning it is still waiting, fulfilled, meaning it succeeded and has a value, or rejected, meaning it failed and has a reason. Code can attach handlers to a promise, to run when it fulfils or rejects, which is how a page can say, when the data arrives, display it, and when the request fails, show an error, without freezing the page while it waits. In real projects this idea shows up again and again, in small pages and in large applications alike, so learning it well now saves repeated confusion later. It is worth learning properly rather than copying a snippet and hoping, because a copied snippet hides the choices you will need to make when the real content differs.

Understanding promises helps you understand fetch, because fetch returns a promise, and it helps you understand async and await, because await simply waits for a promise to settle. When you chain promises, each step receives the previous step's result, and an error at any step can be caught by a single error handler at the end, which is why chaining is often cleaner than nesting handlers inside each other. Avoid the common fault of forgetting to return a value from a step in a chain, which breaks the chain and produces an undefined result in the next step, and always handle rejection, because an unhandled rejection is a silent failure that is hard to debug. Notice the order of the steps: each one depends on the one before it, and skipping a step usually creates a fault that looks mysterious later. A useful habit is to test with realistic content, not only with a perfect example, because long titles, empty lists and slow networks reveal the real behaviour.

Section 12 — Loading states

A loading state is what a page shows while it waits for data, and it matters because a page that shows nothing while waiting looks broken, even when it is working correctly. A good loading state tells the visitor that their request was received, that work is happening, and roughly what is coming, without promising a result before it arrives. It can be a simple message, a spinner, or a skeleton, meaning a grey outline of the layout that will appear, and the choice depends on how long the wait is likely to be and how much of the page is waiting. In real projects this idea shows up again and again, in small pages and in large applications alike, so learning it well now saves repeated confusion later. It is worth learning properly rather than copying a snippet and hoping, because a copied snippet hides the choices you will need to make when the real content differs.

Show a loading state as soon as a request starts, keep it visible until the request settles, and replace it promptly with data, an empty state or an error, rather than leaving it on screen after the request has finished. Section 13 — Error states

An error state is what a page shows when a request fails, and it is as important as the success state, because requests fail in real life for many reasons, including lost connections, server faults and missing resources. A good error state explains, in plain words, what went wrong, what the visitor can do next, and whether their work is safe, without blaming the visitor and without displaying technical details that would confuse them. Section 22 — Caching in plain words

Section 23 — Debouncing search input

Debouncing means waiting until a visitor has paused typing before acting on their input, rather than acting on every single keystroke. Without debouncing, a search input that fetches on every keystroke can send many unnecessary requests, re-render the list repeatedly, and feel jittery, especially on slow connections. With debouncing, the page waits a short pause, such as a few hundred milliseconds, after the last keystroke, and then acts once, which feels smoother and uses far fewer requests. In real projects this idea shows up again and again, in small pages and in large applications alike, so learning it well now saves repeated confusion later. It is worth learning properly rather than copying a snippet and hoping, because a copied snippet hides the choices you will need to make when the real content differs.

Implement debouncing by starting a short timer on each keystroke, cancelling the previous timer if another keystroke arrives, and acting only when the timer completes without interruption. Choose a delay that feels responsive but not frantic, and always act immediately on a clear action, such as pressing Enter or clicking Search, rather than making the visitor wait for the timer. Debouncing is for input handling, not for delaying feedback: the input itself should respond instantly, and only the expensive action, such as a request or a re-render of a large list, should wait for the pause. Notice the order of the steps: each one depends on the one before it, and skipping a step usually creates a fault that looks mysterious later. Section 38 — API keys and the front end

Section 39 — Rate limits and polite clients

Rate limits are therefore a form of traffic management, not a punishment, and a polite client works within them rather than trying to evade them. The benefit is practical, not theoretical: a page that gets this right is easier to maintain, easier to test and easier to explain to another developer. Users rarely notice this when it works, which is exactly the point; they only notice it when it is missing, broken or inconsistent.

Do not try to evade a limit by using many keys, many addresses or many accounts, because evasion violates the provider's terms and can lead to loss of access. If a feature genuinely needs more requests than the limit allows, the correct path is to ask the provider, to redesign the feature to need fewer requests, or to accept a slower pace, not to bypass the limit. Section 49 — Returning to a list after a detail view

Returning to a list after viewing a detail item is a common journey, and it should feel like returning, not like starting again. A visitor who searched, filtered, sorted and paged to a particular item, opened it, and then goes back, expects to find the same list, in the same state, with the same item visible, rather than a reset list at its first page with all filters cleared. Losing that state forces the visitor to repeat their work, and for a long or carefully filtered list, that repetition can be enough to make them give up. Users rarely notice this when it works, which is exactly the point; they only notice it when it is missing, broken or inconsistent. That matters because the people using the page judge it by what they can see, understand and do, not by how clever the code behind it looks.

Preserve list state by keeping the search, filters, sort and page in the address, or in a state that survives navigation, so that returning, whether by a back button or by a link, restores the same view. When the visitor returns, restore their scroll position sensibly, highlight or indicate the item they just viewed where helpful, and refresh the list's data only if it is likely to have changed, without resetting the visitor's choices. Test the journey end to end: search, filter, open a detail, go back, and check that the list, its filters and its place are all as the visitor left them. When something goes wrong, trace the same steps in reverse, asking at each point what you expected and what actually happened. Section 50 — Putting it together: a data display checklist

A data display checklist turns this chapter into a habit, so no data page goes live with a missing loading state, a silent error, an unsafe display, or a secret in code. The checklist is not a guarantee that data will always be correct, because APIs change, networks fail and data is imperfect, but it catches the ordinary faults that are most common and most costly, before visitors meet them. Teams that use a checklist consistently publish data pages that fail gracefully, display honestly, and stay usable when the network or the API does not cooperate. It also matters for trust: when this part behaves predictably, visitors are more willing to stay, return and complete the task they came for. In real projects this idea shows up again and again, in small pages and in large applications alike, so learning it well now saves repeated confusion later.

Before publishing a data page, confirm that loading, error, empty and success states are all designed, that status codes are checked, that untrusted data is displayed as text, that no API key or credential appears in front-end code, that lists, sorting, filtering and pagination or scrolling are clear, that dates, numbers and money are formatted correctly, that updates are announced accessibly, and that the page works on a slow connection and offline, with clear messages. After publishing, test the page with real data, with imperfect data, and with a failed request, and fix anything the tests reveal. Keep the checklist short enough to use every time, and update it when you learn a new lesson. If you can describe the flow in plain words before you write code, the code itself becomes much easier to write and to debug. Notice the order of the steps: each one depends on the one before it, and skipping a step usually creates a fault that looks mysterious later.
