Chapter 9: Functions: Writing Reusable Code

Section 1: What a Function Is

What a Function Is is the focus of this section, and it belongs to the wider topic of functions in Go. Functions also change how you think about a problem. Instead of holding an entire program in your head at once, you split it into steps, give each step a function, and then think about one step at a time. That isolation makes bugs easier to find, because a problem inside a function can usually be understood by looking at that function alone, and it makes testing easier, because a small function can be tried on its own with known inputs.

Every function has its own scope. Variables declared inside a function are local: they are created when the function starts, they are invisible outside it, and they disappear when it returns. Two functions can each have a variable with the same name without any conflict, because each name belongs to its own function. Parameters, which the next chapter covers in full, are the function's inputs, and return values are its outputs, but even before those details, a function with no inputs that simply prints a message or performs a step already earns its place by giving that step a name.

To study a function, read its name first and guess what it does, then read its body and check your guess. Call it from a tiny test program with a simple case and watch what happens, then call it again with a different case. If a function does two unrelated jobs, try splitting it and notice how much easier each half is to describe. When you refactor a long main function, extract one step at a time, run the program after each extraction, and keep the program working at every step rather than rewriting it all at once.

Another pitfall is writing a function that is never called, or calling a function in the wrong place so its work happens at the wrong time, such as printing a welcome message after the main work has already finished. Also watch for shadowing, where a local variable with the same name as an outer variable hides the outer one inside a small block, and a reader assumes the outer value is being changed when it is not. Short, single-purpose functions with honest names prevent most of these problems before they start.
