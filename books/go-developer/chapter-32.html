Watch for the quieter mistakes around a secure defaults review routine as well, not just the ones the compiler catches. A program can compile cleanly and still be wrong if it records the wrong information, trusts an unchecked value, hides an error, or succeeds on a test input while failing on a realistic one. That is why testing a secure defaults review routine with several different inputs matters: a normal case, an empty case, a boundary case, and one deliberately awkward case will reveal far more than a single happy-path run.
