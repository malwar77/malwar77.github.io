Chapter 29: Defending AI Systems: Output Checks

Section 1: What an Output Check Is

An output check is a test that a program runs on something it produced, before that something reaches a user or triggers an action. Just as an input check inspects what enters a tool, an output check inspects what leaves it, asking whether the output matches the task, whether it contains anything it should not, whether it is well-formed, and whether it is safe to share. If the answers are satisfactory, the output is delivered. If they are not, the output is blocked, corrected, flagged for human review, or replaced with a safe alternative. That inspection, at the exit of the system, is an output check, and it is the second half of the gate that input checks began.

Output checks matter because models are unpredictable. A clean input can still lead to a strange, wrong, or harmful output, because the model may misunderstand the task, wander off topic, repeat private data from its input, or follow an instruction hidden in data that input checks missed. Input checks reduce the chance of a bad output, but they cannot eliminate it, because the model itself adds a layer of uncertainty that no input inspection can remove. Output checks address that uncertainty directly, by looking at the result rather than trusting the process that produced it. A tool that checks its outputs is a tool that verifies its work, rather than assuming it, and verification is a mark of careful engineering.

It helps to think of output checks as a proofreader, not a censor. A proofreader reads a draft before publication, checking for errors, inconsistencies, and content that should not be there, and returns the draft for correction when something is wrong. The proofreader does not prevent the author from writing. They catch problems before readers see them, which protects both the author and the readers. An output checker does the same for a model: it reads the model's draft, checks it against the task and the rules, and catches problems before users see them. That framing matters, because it shows output checking as a quality practice as well as a safety practice, improving answers for honest users while also blocking harmful ones.

This chapter teaches you to build that proofreader, stage by stage. You will learn to check output length, format, consistency with the task, factual grounding, private data, and signs of steering, to combine those checks into a pipeline, to decide when to block, correct, or escalate, and to measure whether your checks help or hurt. All practical work is on your own machine, with your own invented test outputs, using only Python's standard library. By the end of the chapter, you will have a complete output-checking pipeline for a toy tool, and you will understand why output checks, together with input checks and human review, form the layered defence that this book has built toward.

Section 2: Why Outputs Cannot Be Trusted

An output from a language model cannot be trusted blindly, for reasons that follow directly from how models work. A model produces text by predicting what comes next, based on patterns in its training, and that prediction can go wrong in many ways. It can invent facts that sound plausible but are false, a problem you met as hallucination in earlier chapters. It can drift from the task, answering a different question from the one asked, or adding content the user never requested. It can repeat material from its input that should stay private, because it does not reliably distinguish between what may be shared and what must be kept back. It can adopt a tone, a role, or a set of rules that the user never asked for, because wording in the conversation steered it. Each of these failures produces an output that looks reasonable on the surface but is wrong, unsafe, or inappropriate underneath, and only a check that reads the output can catch them.

There is another reason outputs cannot be trusted: they may reflect problems in the input that input checks missed. An injection hidden in a document, a jailbreak attempt dressed as an innocent question, or a malformed input that passed the format check can all steer the model, and their effects appear in the output, not in the input. An output check that looks for signs of steering, such as unexpected topics, actions, or private material, can catch those effects even when the input check missed their cause. Output checks are therefore a safety net for input checks, catching the failures that slip through the first layer, and that net is essential in a layered defence, where each layer covers the gaps of the others.

Outputs also cannot be trusted because they may be used in ways the builder did not intend. A summary may be forwarded to others, a generated message may be sent as if the user wrote it, or a piece of code may be run without review, and in each case, an error in the output becomes an error in the world, larger than the original mistake. Checking outputs before they are shared, forwarded, or acted on prevents those amplifications, by catching problems while they are still drafts, before they become messages, actions, or published content. That timing, checking before sharing, is the key insight of output checking: a problem caught as a draft costs little to fix, while the same problem caught after sharing costs far more.

For your own projects, the habit to build is simple: never deliver a model's output directly to a user or to an action without at least a basic check. Start with length and format, add consistency and private-data checks, and escalate the hard cases to a human. That habit, applied consistently, will prevent a large fraction of the problems that beginners encounter with model outputs, and it will make your tools more reliable and more trustworthy, even before you add any advanced defences.

Section 3: Checking Output Length and Format

Length and format are the simplest output checks, and they are usually the first to run, for the same reasons as on the input side: they are cheap, they catch a common class of problems, and they protect later, more expensive checks from being overwhelmed. An output length check asks whether the result is within the size the task requires. An output that is empty, when the user asked for a summary, indicates a failure, and the tool should retry, report an error, or ask for clarification, rather than delivering a blank answer. An output that is far longer than requested, such as a ten-page answer to a request for three sentences, indicates that the model lost track of the task, and the tool should trim it, flag it, or ask the model to try again with a clearer instruction. Length is a simple signal, but it reveals a great deal about whether the model understood the task.

A format check asks whether the output is shaped the way the user or the next stage expects. If the tool promised a list, is the output a list? If it promised a short paragraph, is the output a paragraph rather than a jumble of fragments? If the output will be fed to another program, does it match the format that program requires, such as a set of fields or a structured layout? Format mismatches cause confusion downstream, because the next stage, whether it is a human reader or another program, must guess what the output means, and guessing leads to errors. Catching a format problem at the exit is far cheaper than catching it after the output has been shared, forwarded, or acted on, when its meaning has already been misinterpreted.

Length and format checks also serve as a first signal of steering. An output that suddenly changes format, or that grows far beyond the requested length, may indicate that the model followed an instruction from the data rather than from the user, or that it wandered into a topic it was not asked about. Those signals are weak on their own, but they are cheap to check, and they can trigger deeper checks or human review for the outputs that deserve it. A length or format anomaly is therefore not only a quality problem. It is a reason to look closer, and looking closer is what the later stages of the pipeline do.

In Python, length and format checks for outputs use the same techniques as for inputs: comparisons for length, and simple pattern tests for format, all with only the standard library. Test it with a normal output, an empty output, an overlong output, and a wrongly formatted output, and confirm that each case is handled correctly. Those four cases are the foundation of output testing, and they will recur in every stage you add.

Section 4: Checking Consistency with the Task

A more demanding output check asks whether the output actually does what the task asked for. This is called consistency checking, and it compares the output with the task, rather than checking the output in isolation. A summary should cover the document's main points, not invent new ones. An answer should address the question asked, not a different question. A list should contain items of the requested kind, not items of another kind. A piece of code should do what it was asked to do, not something else. Consistency is harder to check automatically than length or format, because it requires understanding the relationship between the task and the output, but even simple consistency checks catch many problems that simpler checks miss.

Simple consistency checks work by looking for signals, rather than by understanding deeply. One signal is topic overlap: do the important words in the task also appear in the output, or has the output wandered to entirely different words? A summary of a gardening document that never mentions plants is suspicious, whatever its length or format. Another signal is structure: if the task asked for three points, does the output contain roughly three points, or does it contain one, or twenty? A third signal is the absence of contradictions: does the output claim something that directly contradicts the task, such as saying it cannot help when the task was straightforward, or offering an action the task never requested? Each of these signals is weak on its own, but together they form a picture of whether the output is on task, and that picture is enough to flag the worst cases for review.

Consistency checks also need to handle the case where the task itself was vague. If the user asked for something good, without specifying what good means, then almost any output could be called consistent, and the check cannot do much. That limitation points back to input checking: a vague task should have been clarified before generation, as you learned in Chapter 28, so that consistency can be judged afterwards. Input and output checks therefore reinforce each other: clear inputs make outputs checkable, and output failures reveal inputs that were too vague. A builder who improves both ends together will get better results than one who improves either end alone.

In a toy, you can practise consistency checking by writing a function that takes a task description and an output, extracts the important words from each, and reports how many task words appear in the output. Test it with an on-task output, an off-task output, and a partially on-task output, and see whether the scores separate them. That simple overlap score is not a perfect consistency measure, but it teaches you the pattern: compare output with task, score the match, and flag low scores for review. That pattern, refined and combined with other signals, is the basis of real consistency checking.

Section 5: Checking for Private Data in Outputs

Outputs can leak private data in ways that are easy to overlook, and checking for leaks is one of the most important output checks. A model may include private material from its input in its output, because it does not reliably distinguish between what may be shared and what must be kept back. A summary of a document that contains a password, an address, or a personal detail may repeat that detail in the summary, even though the user only wanted the document's main ideas. An answer to a question about one person may include details about another person that appeared in the source material. A generated message may quote private content that the user never intended to share. Each of these is a leak, and each is preventable by an output check that looks for private-data shapes before delivery.

Private-data output checks use the same pattern-matching approach as input private-data checks, with the same limits: they look for shapes that suggest private data, such as long digit sequences, labels followed by values, or patterns that resemble addresses or account numbers, and they flag outputs containing those shapes. The flag should trigger a response proportionate to the risk: for a summary that will only be seen by the user who supplied the input, a warning may be enough, because the user already knows the data. For an output that will be shared, forwarded, or published, a block or a redaction, replacing the sensitive value with a placeholder, is more appropriate, because the audience does not already know the data and should not learn it from the output. The audience determines the response, and a builder who thinks about audience will choose correctly.

Redaction deserves special care. Replacing a sensitive value with a placeholder, such as writing [removed] in its place, preserves the output's structure while removing the leak, which is better than blocking the whole output when only one value is problematic. But redaction must be complete: if the same value appears in several forms, such as a full number and a shortened version, all forms must be redacted, or the leak remains through the unredacted form. A redaction checker should therefore search for all occurrences and variants, not just the first one it finds, and it should log the category of the redaction without storing the value itself, following the same privacy rule as for input logs.

Test it with a clean output, an output containing a private-data shape, and an output containing the same value in two forms, and confirm that the redaction catches both forms. That exercise teaches you both the technique and its limits, because you will see how easily a variant can slip past a simple pattern, and why redaction must be thorough and why human review remains necessary for high-stakes outputs.

Section 6: A Length, Format, and Private-Data Output Checker

Now you will build a small output checker that combines length, format, and private-data stages, using only Python's standard library. The checker takes a toy output and a task description, and returns a decision with a reason, following the pattern you have used for input checkers. The length stage rejects empty outputs and outputs beyond a maximum you choose. The format stage checks that the output contains only expected characters and that it has the basic shape the task requires, such as containing at least one sentence. The private-data stage flags outputs containing your own invented private-data shapes, such as a label followed by a value, without storing the value itself. Each stage is a small function, and the checker runs them in order, stopping at the first block, or collecting a flag and continuing, depending on the stage.

Here is a version you can type and run. Its test outputs are invented by you, for your toy, so that your practice stays safe and local. The test list includes a normal output, an empty output, an overlong output, and an output containing a private-data shape, so that you can see each stage fire. You can extend the checker by changing the maximum length, by adding a new format rule, or by adding a new private-data pattern, and by watching how the decisions change. That experimentation is the point: a checker you have adjusted and re-tested is a checker you understand.

def stage_length(output, maximum=500):
    if len(output) == 0:
        return "block", "empty output"
    if len(output) > maximum:
        return "block", "output too long"
    return "pass", ""

def stage_format(output):
    if "." not in output:
        return "block", "output has no sentence"
    return "pass", ""

def stage_private(output):
    if "password:" in output.lower():
        return "flag", "possible private data"
    return "pass", ""

def check_output(output):
    flags = []
    for stage in (stage_length, stage_format, stage_private):
        decision, reason = stage(output)
        if decision == "block":
            return "block", reason, flags
        if decision == "flag":
            flags.append(reason)
    if flags:
        return "flag", "; ".join(flags), flags
    return "allow", "all checks passed", flags

tests = [
    "Tomatoes need full sun and regular water.",
    "",
    "x" * 600,
    "The shed code is password: hunter2 for the garden.",
]
for item in tests:
    print(check_output(item))

Notice the order: length first, then format, then private data, from cheap to expensive, as you learned for inputs. Notice also that the private-data stage flags rather than blocks, because the output's audience determines the right response, and a flag lets a later stage or a human decide. That design, cheap stages first and flagging for audience-dependent cases, is the same pattern you used for inputs, applied to outputs, and it shows how much of your input-checking knowledge transfers directly. Output checking is not a new subject. It is the same discipline, applied to the other end of the system.

One more extension will make this checker more useful in practice: add a reporting step that prints a short summary of what each stage did, including which stage made the final decision and how many flags were collected. That summary is useful for logging, because it contains categories and counts rather than full content, and it is useful for debugging, because it shows which stage caught a problem or missed it. A checker that reports on itself is easier to trust than one that works silently, because its work can be inspected and verified. When you extend the code, add that reporting step first, before adding more patterns, because visibility makes every later improvement easier to judge. A visible pipeline is a maintainable pipeline, and maintainability is what keeps a checker useful as it grows.

Section 7: Checking for Hallucination Signals

Hallucination, where a model invents plausible-sounding facts that are false, is one of the hardest output problems to check automatically, because a false statement can look exactly like a true one. No simple checker can verify every fact in an output, but several signals can raise suspicion and trigger review or a disclaimer. One signal is specificity without grounding: an output that gives precise numbers, dates, or names, when the input contained no such details, may have invented them, because precise details must come from somewhere, and if they did not come from the input, they came from the model's pattern-matching, which is unreliable for facts. A checker that compares the specific details in the output with those in the input, and flags details that appear from nowhere, catches a useful fraction of hallucinations.

Another signal is internal inconsistency: an output that contradicts itself, such as giving two different values for the same quantity, or stating a fact and then denying it, is likely to contain at least one error, because a true account is usually consistent with itself. A checker that looks for repeated quantities with different values, or for direct contradictions in simple forms, can flag those outputs for review. A third signal is overconfidence: an output that states uncertain matters as absolute facts, without any hedging or qualification, is more likely to contain errors than one that acknowledges uncertainty, because real knowledge about many topics is partial. A checker cannot judge truth, but it can notice the absence of hedging language and flag outputs that are suspiciously certain about topics the input did not settle.

None of these signals proves hallucination, and a checker that blocks on any of them would block many legitimate outputs, because legitimate outputs can also be specific, can contain apparent contradictions that resolve on closer reading, and can be confidently stated when the facts are clear. The right response to a hallucination signal is therefore usually a flag, not a block, together with a disclaimer or a request for verification. A flag that says this output contains details not found in the input, please verify them, helps the user without preventing them from using the output, and it teaches the user to verify, which is the most reliable defence against hallucination in practice.

In a toy, you can build a grounding checker that extracts numbers from an input and from an output, and flags numbers in the output that do not appear in the input. Test it with an output that only uses input numbers, an output that invents a new number, and an output that uses a number in a different but legitimate way, such as a total calculated from input numbers, and see how the checker handles each case. That exercise teaches you both the power and the limits of grounding checks, and why they flag for review rather than block outright.

Section 8: Checking for Signs of Steering

An output check can also look for signs that the model was steered by an injection or a jailbreak, even when the input checks missed the cause. Steering signals are patterns in the output that do not match the task, the user's request, or the model's expected behaviour. One signal is an unexpected action: the output proposes, or claims to have taken, an action the user never requested, such as sending a message, changing a file, or contacting someone. Another signal is an unexpected role: the output adopts a persona, a set of rules, or a style that the user never asked for, or that contradicts the system's instructions. A third signal is an unexpected topic: the output discusses a subject far from the task, or includes content that has no connection to the input, suggesting that something other than the task influenced it.

These signals are valuable because they catch the effect of an attack even when the attack itself was invisible to input checks. An injected instruction hidden in a document may have passed the input scanner, but its effect, a steered output, is visible to an output checker that compares the output with the task. That comparison is the output checker's strength: it does not need to find the hidden instruction. It needs to notice that the output does not match what was asked, and that mismatch is often easier to spot than the hidden cause. A builder who checks outputs for steering therefore has a second chance to catch every injection and jailbreak that slipped past the input layer.

The response to a steering signal should usually be to block or to escalate, rather than to deliver the output with a warning, because a steered output is not merely inaccurate. It is an output whose behaviour has been influenced by someone other than the user, and delivering it, even with a warning, risks acting on that influence. Blocking the output, logging the category, and informing the user that the output did not match the task, without reproducing any suspicious content, is the safer response. For high-stakes tools, escalation to a human reviewer is even better, because a human can judge whether the mismatch is a steering attempt or an innocent misunderstanding, with context that the checker lacks.

Test it with an on-task output, an output with an unexpected action, and an output with an unexpected topic, and confirm that it distinguishes them. That exercise teaches you to think about outputs as evidence of what influenced the model, not just as text to be delivered, and that way of thinking is central to output checking.

Section 9: Correcting Outputs Versus Blocking Them

When an output check finds a problem, the tool has several responses, and choosing among them is a design decision that depends on the problem and the stakes. Blocking means withholding the output entirely, with a message explaining why. Correcting means fixing the problem and delivering a cleaned version, such as trimming an overlong output, redacting a private value, or reformatting a malformed answer. Flagging means delivering the output with a warning, or sending it to a human for review before delivery. Each response suits a different kind of problem, and a good output pipeline uses all three, choosing the gentlest response that still protects the user.

Blocking is appropriate when the problem is serious and cannot be fixed by editing, such as a steered output, a heavily hallucinated answer, or an output that is fundamentally off-task. In those cases, editing would produce a misleading impression that the output was sound, when it was not, and delivering a cleaned version would hide the fact that the model failed. Blocking, with a clear message and an offer to try again, is more honest, because it acknowledges the failure and gives the user a chance to rephrase or to seek help elsewhere. Blocking is also appropriate when the output's audience is broad, such as a published post, where even a small error can spread widely.

Correcting is appropriate when the problem is local and fixable, such as a single private value that can be redacted, an overlong output that can be trimmed to the requested length, or a format error that can be repaired without changing meaning. Correcting preserves the useful parts of the output while removing the problematic parts, which is better for the user than losing the whole answer. But correcting must be done transparently: the user should be told that the output was corrected, and ideally what kind of correction was made, so that they do not mistake the cleaned version for the model's original. Silent correction hides the model's failure and the checker's intervention, which undermines trust in both.

Flagging is appropriate when the problem is uncertain, such as a possible hallucination, a weak consistency signal, or a private-data shape that may be harmless. In those cases, neither blocking nor correcting is clearly right, because the output may be fine, and the checker is unsure. Flagging, with a warning that names the concern in general terms, lets the user decide, with more information than they would have had without the check. That decision respects the user's judgement, and it turns the user into a participant in the defence, which is valuable when the checker itself cannot decide. The three responses together, blocking, correcting, and flagging, give the pipeline a graded set of tools, rather than a single blunt instrument.

Section 10: Failing Closed on the Output Side

The principle of failing closed, which you learned for inputs, applies equally to outputs: when an output check cannot decide whether an output is safe, it should treat the output as unsafe. Failing closed on the output side means withholding, flagging, or escalating an uncertain output, rather than delivering it in the hope that it is harmless. The reasoning is the same as for inputs: uncertainty is common, because outputs are complex and checkers are imperfect, and the cost of delivering a harmful output is usually higher than the cost of withholding a harmless one. A user who receives a withheld output with a clear message can try again. A user who receives a harmful output may act on it, share it, or be harmed by it before anyone notices.

Failing closed for outputs needs the same three-way design as for inputs: allow, flag, and block. An output that is clearly sound is allowed. An output that is clearly problematic is blocked. An output that is uncertain is flagged, either with a warning to the user or by escalation to a human reviewer, depending on the stakes. That middle outcome is what makes failing closed practical, because without it, failing closed would block too many legitimate outputs and frustrate users into working around the checks. With it, failing closed becomes a way of asking for help when the program is unsure, which is exactly what a careful program should do at the exit as well as at the entrance.

The principle also applies to checker failures. If an output check itself fails, because of a bug, a missing file, or an unexpected output shape, the safe response is to treat the output as unchecked and therefore unsafe, rather than to skip the check and deliver the output. A program that skips a failed output check is failing open by accident, and that accident can become a gap through which harmful outputs pass. A program that withholds the output when a check fails, with a message explaining that the check could not run, is failing closed, and it alerts the builder to a problem that needs fixing. That alert is valuable, because a failing check is a bug, and bugs should be visible, not silently bypassed.

In your own output checkers, practise failing closed by writing the uncertain case explicitly. When you write a rule, ask what happens if the output does not match any of your patterns, or if a value is missing, or if a check raises an error. If the answer is allow, change it to flag or block, and write a test for that case. That habit, applied to every output rule, will make your checkers safer by default, and it will teach you to think about uncertainty as a normal condition to handle, not as an edge case to ignore, at both ends of the system.

Section 11: Output Checks for Code

When a model generates code, output checks take on special importance, because code is not just text to be read. It is text that may be run, and running it has effects. A code output check therefore asks different questions from a prose check. First, is the code well-formed, meaning does it follow the syntax of its language, without errors that would prevent it from running? A syntax check, using a parser from the standard library, can catch malformed code before it reaches the user, which saves the user from debugging output that was never valid. Second, does the code do what was asked, in general terms, without doing extra things the user never requested, such as accessing files, sending network requests, or changing system settings? A code checker that scans for operations outside the task's scope can flag code that does more than it should, which is a sign of steering or of a model misunderstanding the task.

Third, does the code contain anything dangerous, such as a command that deletes files, or a value that looks like a credential? Those patterns deserve flagging or blocking, depending on the audience and the stakes, because code that deletes or exposes is code whose effects are hard to undo. Fourth, is the code understandable, with clear structure and, where appropriate, comments explaining what it does? Understandability is a quality check, but it is also a safety check, because code the user cannot understand is code the user cannot review, and unreviewed code should not be run. A code output that is a dense, uncommented block is harder to trust than one that is clear and explained, even if both do the same thing.

The response to a code problem depends on its kind. A syntax error can be reported to the user with a suggestion to try again, because the code cannot run as it is. A scope problem, where the code does extra things, should be flagged, with the extra operations named in general terms, so that the user can decide whether they are acceptable. A dangerous pattern should be blocked or escalated, because running it could cause harm. In all cases, the user should review code before running it, and the tool should encourage that review, by showing the code clearly and by warning when it contains anything unusual. That review step is the human layer that no automated code check can replace, because understanding code requires judgement that patterns alone cannot supply.

Test it with valid code, code with a syntax error, and code that includes an out-of-scope operation from your own test list, and confirm that each case is handled correctly. That exercise teaches you to treat generated code as an action, not just as text, and that shift in thinking is essential for any tool that generates code for users to run.

Section 12: Output Checks for Summaries

Summaries are one of the most common model outputs, and they have their own checking needs. A summary check starts with coverage: does the summary mention the main points of the source, or does it miss them, or invent new ones? Coverage can be approximated by comparing the important words or ideas in the source with those in the summary, and flagging summaries that cover too little or that introduce too much that was not in the source. A summary that covers nothing is useless, and a summary that invents is misleading, and both failures are worth catching, even with a simple overlap measure. The measure does not need to be perfect. It needs to catch the worst cases, and to flag the borderline ones for human judgement.

A second summary check concerns length relative to the source. A summary should be shorter than its source, by a margin that fits the task: a short summary of a long document should be much shorter, while a detailed summary may be closer in length. A summary that is longer than its source has failed at its basic purpose, and a summary that is only a sentence long, when the source is long and complex, has probably missed most of the content. Length relative to source is therefore a useful signal, cheap to compute, and easy to explain to users: this summary is longer than the document it summarises, which suggests something went wrong. That explanation is understandable without any technical knowledge, which makes it a good user-facing check.

A third summary check looks for private data carried over from the source, as you learned in Section 5, with the audience determining the response. A summary for the user who supplied the source may safely include details the user already knows, while a summary that will be shared needs redaction of those details. A fourth check looks for steering signals, such as the summary introducing a topic, an action, or a recommendation that the source never mentioned, which may indicate that the model was influenced by something other than the source. Those four checks, coverage, relative length, private data, and steering, together form a solid summary pipeline, and they illustrate how output checks combine several simple signals into a judgement about quality and safety.

In a toy, you can build a summary checker that takes a source and a summary, both invented by you, computes word overlap, compares lengths, scans for a private-data shape, and flags steering words from your own test list. Section 13: Output Checks for Messages and Emails

When a model drafts a message or an email, output checks must consider that the draft may be sent as if the user wrote it, which raises the stakes considerably. A draft check starts with the basics: does the draft address the right person, does it concern the right topic, and does it say what the user intended, in general terms? A draft addressed to the wrong person, or about the wrong topic, is a sign that the model misunderstood the task or was steered, and it should be flagged before the user sees it, let alone sends it. Address and topic checks are simple to implement as comparisons between the draft and the task, but they catch errors that would be embarrassing or harmful if sent.

A second draft check looks for tone and claims. Does the draft's tone match what the user would use, or is it inappropriately formal, casual, or aggressive? Does it make claims, promises, or commitments that the user never authorised, such as offering a discount, agreeing to a deadline, or stating a fact the user did not verify? Unauthorised claims are a serious problem in drafted messages, because once sent, they bind the user to something they never agreed to. A checker that flags drafts containing commitment language, such as promises or offers, from a list you define for your toy, gives the user a chance to remove those claims before sending. That flag is a safety net for the user's reputation and obligations, not just for the message's wording.

A third draft check looks for private data, with the same audience logic as before, but with higher stakes, because a sent message reaches another person, who should not receive the user's private details. A draft that includes a password, an address, or another person's private information should be blocked or redacted, not merely flagged, when its destination is outside the user's own circle. The distinction between a draft for the user to review and a message ready to send matters here: a draft can carry a flag, because the user will review it, while a message about to be sent needs a block, because there will be no further review. That distinction, between draft and send, is a design decision that every messaging tool must make explicitly.

Finally, a messaging tool should never send a draft automatically, without the user reviewing it, no matter how clean the checks say it is. Human review before sending is the last layer, and it is non-negotiable for messages, because the cost of a wrong send is high and the cost of a review is low. Output checks make review easier, by flagging problems for the user to fix, but they do not replace review. A tool that checks drafts well and still requires review is a tool that respects both automation and human judgement, and that balance is the hallmark of safe messaging design.

Section 14: A Consistency Checker in Python

Now you will build a consistency checker, which compares a toy output with its task and scores how well they match, using only Python's standard library. The checker extracts the important words from the task and from the output, by lowercasing, splitting into words, and removing a small list of common words, such as the, and, and of, which carry little meaning. It then computes the overlap: what fraction of the task's important words appear in the output. A high overlap suggests the output is on task. A low overlap suggests it has wandered. The checker returns the score, together with a decision: allow if the score is high, flag if it is medium, and block if it is very low, with thresholds you choose and can explain. Those thresholds are design decisions, and you should test them with your own examples to see whether they separate on-task outputs from off-task ones.

Here is a version you can type and run. Its task and outputs are invented by you, for your toy, so that your practice stays safe and local. The test list includes an on-task output, an off-task output, and a partially on-task output, so that you can see how the scores differ. You can extend the checker by changing the common-word list, by adjusting the thresholds, or by adding a second signal, such as checking whether the output's length is appropriate for the task, and by watching how the decisions change. That experimentation teaches you how consistency scoring works in practice, and how sensitive it is to the choices you make.

COMMON = {"the", "and", "of", "a", "to", "in", "is", "for", "on", "with"}

def important_words(text):
    words = text.lower().split()
    cleaned = []
    for word in words:
        word = word.strip(".,!?")
        if word and word not in COMMON:
            cleaned.append(word)
    return set(cleaned)

def consistency(task, output):
    task_words = important_words(task)
    output_words = important_words(output)
    if not task_words:
        return 0.0
    return len(task_words & output_words) / len(task_words)

def check_consistency(task, output):
    score = consistency(task, output)
    if score >= 0.6:
        return "allow", score
    if score >= 0.3:
        return "flag", score
    return "block", score

task = "Summarise garden notes about tomatoes and watering."
tests = [
    "Tomatoes need sun and regular watering.",
    "The history of trains is long and fascinating.",
    "Tomatoes are plants.",
]
for item in tests:
    print(check_consistency(task, item))

Notice how simple this checker is, and how much it already teaches. It shows that consistency can be approximated with word overlap, that thresholds turn a score into a decision, and that the decision needs a middle outcome, flag, for the uncertain cases. It also shows the limits: a partially on-task output scores in the middle, and a clever off-task output that reuses task words could score highly, which is why consistency is one signal among many, not a complete solution. A checker that you understand, including its limits, is a checker you can improve, and improvement starts with honest measurement of what it catches and what it misses.

A further refinement is to weight the words, giving more importance to rare or distinctive words and less to common ones, because a match on a distinctive word, such as a proper name or a technical term, is stronger evidence of consistency than a match on an ordinary word. Weighting improves the checker's ability to separate on-task outputs from off-task ones that merely reuse ordinary vocabulary, but it adds complexity, and the weights themselves need to be chosen and tested. For a toy, simple unweighted overlap is a good start, and weighting is a natural next improvement once the simple version works and its limits are understood. That progression, from simple to refined, is how checkers grow without becoming unmanageable.

Section 15: Output Checks for Factual Claims

Outputs that make factual claims deserve a special kind of check, because a false claim, delivered confidently, can mislead users who trust the tool. Factual checking is hard to automate fully, because verifying a claim requires knowledge of the world, but several partial checks help. One is grounding: does the claim appear in, or follow from, the input the model was given, or does it introduce new facts from nowhere? A claim grounded in the input is more likely to be correct than one invented from pattern-matching, because the input is a source the user supplied and can verify. A grounding checker, like the one you met for hallucination signals, compares the specific details in the output with those in the input, and flags details that appear from nowhere.

A second partial check is source attribution: does the output say where its claims come from, or does it present them without any source? An output that cites its sources, even in general terms, such as naming the document it summarised, is more checkable than one that states facts baldly, because the user can follow the citation and verify. A checker can flag outputs that make specific claims without any attribution, and can suggest adding a source note, which improves both accuracy and trust. Attribution does not prove truth, but it makes truth checkable, and checkability is a practical step toward accuracy.

A third partial check is uncertainty marking: does the output distinguish between what is certain and what is uncertain, or does it present everything with equal confidence? An output that says this is likely, or according to the source, for uncertain points, is more honest than one that states everything absolutely, and a checker can flag outputs that lack any hedging language on topics where the input was uncertain. That flag does not prove an error, but it prompts the user to verify, which is the most reliable defence against false claims in practice: a user who verifies is a user who catches errors that no automated check could.

For high-stakes claims, such as medical, legal, or financial advice, automated checks are not enough, and the output should carry a disclaimer and be escalated to a human expert, or should be refused with a suggestion to consult a professional. That escalation is not a failure of the checker. It is a recognition of its limits, and of the stakes, which together demand human judgement. A builder who knows when to escalate, rather than trying to automate everything, is a builder who understands both the power and the limits of output checking.

A fourth partial check for factual claims is freshness: is the claim about something that changes over time, such as a price, a date, or a current event, and if so, is the output's information recent enough to be trusted? A claim that was true last year may be false today, and a checker that flags time-sensitive claims for verification helps users avoid acting on outdated information. Freshness checking does not require knowing the current truth. It requires recognising that a claim is time-sensitive, and prompting the user to verify it against a current source. That prompt is a small step with a large benefit, because outdated facts are a common and costly kind of error.

Section 16: Handling Outputs That Are Partially Wrong

Many outputs are not wholly good or wholly bad. They are partially wrong: mostly correct, with a section that is off-topic, a fact that is invented, or a value that is private. Handling partially wrong outputs requires a nuanced response, because blocking the whole output wastes the correct parts, while delivering it as if it were fully correct misleads the user about the wrong parts. The best response is usually to identify the problematic part, and to deal with that part specifically, while preserving the rest. That targeted response requires the checker to locate problems, not just to detect their presence, which is a harder task, but one that is worth attempting for common, local problems.

For local problems, such as a single private value, a single invented number, or a single off-topic paragraph, the checker can redact, correct, or remove that part, and deliver the rest with a note explaining what was changed. That note is important, because it tells the user that the output was modified, and why, so that they do not mistake the cleaned version for the model's original. For problems that are spread throughout the output, such as a general drift from the task, or widespread hallucination, targeted correction is not feasible, because there is no clean part to preserve, and blocking the whole output, with an offer to try again, is more honest. The choice between targeted correction and whole-output blocking depends on whether the problem is local or global, and a checker that can distinguish those cases is a checker that serves users well.

There is also a middle response for partially wrong outputs: delivering the output with annotations that mark the uncertain or problematic parts, so that the user can see which parts to trust and which to verify. Annotations, such as a note that a particular figure was not found in the input, or that a section seems off-topic, give the user the information to judge the output for themselves, without the checker having to decide definitively. That approach respects the user's judgement and the checker's uncertainty at the same time, and it is especially useful for outputs where the checker is unsure, because it shares the uncertainty rather than hiding it.

Test it with a fully clean output, an output with one bad sentence, and an output where every sentence is problematic, and confirm that the responses differ appropriately. That exercise teaches you to think about outputs as collections of parts, not as single blocks, and that granularity is what makes nuanced responses possible.

Section 17: Output Checks for Different Audiences

The same output may need different checks depending on who will see it, because different audiences have different needs, different knowledge, and different vulnerabilities. An output for the user who supplied the input can include details that user already knows, while an output for a wider audience, or for publication, must be checked more strictly for private data, for accuracy, and for tone, because its readers do not share the original user's context. An output for a child or a beginner needs simpler language, stricter safety, and clearer explanations than one for an expert, who can judge technical content for themselves. Audience-aware checking is therefore a design skill, and it starts with asking who will see this output, and what they need from it.

One practical way to handle audiences is to define output profiles: a set of check settings for each audience, such as private, team, and public, with stricter checks for wider audiences. A private profile might allow private-data shapes, because the audience already knows them, while a public profile would redact them. A beginner profile might require simpler language and more disclaimers, while an expert profile might allow technical detail. The tool chooses a profile based on the output's destination, which the user specifies or which the tool infers from the task, and runs the checks for that profile. That explicit choice makes the tool's behaviour predictable and explainable: the same output checked for publication is stricter than the same output checked for personal use, and the user can understand why.

Audience checks also concern tone and appropriateness. An output that is suitable for an adult expert may not be suitable for a child, not because it is harmful in itself, but because its language, its assumptions, or its topics are beyond the child's understanding or appropriate range. A checker that flags complex language, sensitive topics, or unexplained jargon for a young audience helps the tool serve that audience well, by prompting simpler, clearer output. That kind of check is not censorship. It is adaptation, matching the output to the reader, which is a basic principle of good communication as well as of safety.

In a toy, you can implement audience profiles as a dictionary mapping an audience label to a set of thresholds and flags, and a function that runs the appropriate checks for the chosen audience. Test it with the same output checked for two audiences, and confirm that the decisions differ in the expected way. That exercise teaches you to think about outputs in relation to their readers, not in isolation, and that relational thinking is essential for any tool whose outputs reach more than one kind of person.

Audience profiles also need a default, for cases where the audience is unknown. The safe default is the stricter profile, because an output checked strictly can still be used by a narrower audience, while an output checked loosely may be unsafe for a wider one. That default follows the failing-closed principle you have met before: when unsure about the audience, choose the safer treatment. A tool that defaults to the strictest profile protects the widest range of readers, and users who need a looser check can request it explicitly, with the audience specified, which makes the choice deliberate rather than accidental.

Section 18: Logging Output Check Decisions

Logging output check decisions follows the same rules as logging input decisions: record categories and decisions, not full content, and review the logs regularly for patterns. A useful output log entry includes the time, the task type, the stage that made the decision, the category of the problem, such as off-task, private data, or hallucination signal, the decision, such as allow, correct, flag, or block, and whether the output was corrected, and if so, in what general way, such as redaction or trimming. It does not include the full output, because the output may contain private data or harmful content that should not be stored, and it does not include values that would let someone reconstruct the output. Category-level logging gives you everything needed for analysis, without creating a second copy of potentially sensitive material.

Log analysis for outputs reveals patterns that single decisions do not. If one stage blocks far more outputs than the others, it may be too strict, or it may be catching a real problem that other stages miss. If hallucination flags rise for a particular kind of task, it may mean that the task is too vague, or that the model struggles with that topic, and that the task needs clearer instructions or a different approach. If corrections cluster around private data, it may mean that inputs for that task routinely contain private details, and that the input checks should be tightened to catch them earlier. Those insights come from counting log entries by stage, by category, and by task, over time, and they guide improvements to both input and output checks, because the two ends of the pipeline learn from each other.

Logging also serves accountability for outputs. If a user complains that an answer was wrong, or that a message was sent with an error, the log lets you find the decision, identify the stage and the category, and explain what happened, or fix the rule if it was wrong. If an incident occurs, the log lets you trace which outputs were delivered, which were corrected, and which were blocked, which is the after-the-fact investigation you learned for injections, applied to outputs. A tool without output logs cannot explain its answers or investigate its failures, and that inability undermines trust, both from users who want explanations and from builders who want to improve.

Finally, output logs need the same retention policy as input logs: stored with sensible permissions, reviewed on a schedule, and deleted after a period, so that they do not become a liability. A log that grows forever, without review or deletion, is a store of information about user interactions that could leak or be misused. Set a simple policy, even for a toy: keep logs for a short period, review them regularly, and delete old entries. That policy, written down and followed, completes the habit of responsible logging at both ends of the system.

Section 19: Measuring Output Check Quality

Measuring an output checker uses the same four counts and two rates as for inputs, with a small extension for corrections. You need legitimate outputs that should be allowed, and problematic outputs that should be blocked, flagged, or corrected, and you count how many of each were handled correctly. From those counts you calculate the catch rate, the fraction of problematic outputs caught, and the false block rate, the fraction of legitimate outputs wrongly blocked or flagged. A good output checker has a high catch rate and a low false block rate, but improving one often worsens the other, and measuring both lets you see the trade-off and choose a balance that fits the tool's purpose and audience. A tool for publication needs a higher catch rate, even at the cost of more false blocks, than a tool for personal use, where false blocks are more annoying than a missed problem.

The extension for outputs is to measure correction quality separately. When a checker corrects an output, by redacting, trimming, or reformatting, you need to know whether the correction preserved the output's useful content, or whether it damaged it. A correction that removes a private value while keeping the rest intact is good. A correction that mangles the output, removing so much that it becomes useless, is bad, even though it technically removed the problem. Measuring correction quality requires human judgement, or at least a check that the corrected output still passes basic length, format, and consistency checks, which is a way of verifying that the correction did not break the output it was meant to save. That verification step is easy to add, and it prevents corrections from becoming a new source of problems.

Measurement should also cover cost and timing, as for inputs. An output checker that is accurate but slow may delay delivery unacceptably, especially for interactive tools where users expect quick answers. Measure how long the pipeline takes for a normal output and for a problematic one, and notice whether problematic outputs are caught quickly, after cheap checks, or slowly, after running the whole pipeline. A pipeline that catches problems slowly has an ordering problem, and fixing the order improves both speed and cost. Cost measurement is part of quality measurement, because a checker that is too slow will be disabled or bypassed, and a disabled checker protects no one.

Finally, measure over time, running your test set regularly and recording the rates, so that you can see whether the checker is improving or degrading. A single measurement tells you where you are. A series tells you where you are going, and whether your changes are helping. That trend is the most valuable measurement, because it shows learning, and learning is what turns a beginner's checker into a reliable defence. It also shows the feedback loop with input checks: when output catches fall, it may mean input checks improved, and when they rise, it may mean input checks need attention. Measuring both ends together gives you the whole picture.

Section 20: Output Checks and User Trust

Output checks affect user trust in a direct and powerful way, because users judge a tool by its outputs, not by its internal checks. A tool whose outputs are consistently accurate, well-formed, and appropriate earns trust, and users rely on it more, share its outputs more, and recommend it to others. A tool whose outputs are erratic, contain errors, or leak private data loses trust quickly, and users who lose trust rarely return, even after the problems are fixed. Output checks are therefore not only a safety measure. They are a trust measure, and investing in them is investing in the tool's reputation and its future use.

Trust is built by consistency and by honesty. Consistency means that outputs are checked the same way every time, so that users can predict the tool's behaviour and rely on it. A tool that sometimes delivers a flawed output and sometimes blocks a good one, for no clear reason, feels arbitrary, and arbitrary tools are not trusted. Honesty means that when an output is corrected or flagged, the tool says so, in plain words, rather than silently altering it or delivering it as if it were perfect. A user who is told that an output was corrected, and why, trusts the tool more than one who discovers the correction later, because the tool was transparent about its own limitations. Transparency about checking builds trust, while silent checking, even when it works, leaves users guessing about what happened.

Trust is also built by giving users a way to respond. If a user believes an output was wrongly blocked, or wrongly corrected, they should be able to say so, and the tool should have a path for that feedback to reach the builder, who can review the decision and improve the check. That feedback loop turns users into partners in improving the tool, rather than passive recipients of its decisions, and it gives the builder real data about where checks are too strict or too loose. A tool without a feedback path tells users that their judgement does not matter, which undermines trust, while a tool with a clear feedback path tells them that it does, which strengthens it.

For your own tools, the lesson is to design output checks with trust in mind, not only with safety. Check consistently, explain corrections and blocks plainly, and provide a way for users to report problems. Those three practices, consistency, honesty, and feedback, are the foundation of trust, and they cost little to implement, while their absence costs a great deal in lost users and lost reputation. A tool that is trusted is a tool that is used, and a tool that is used is a tool whose checks matter, because they protect real people doing real work.

Section 21: Output Checks for Lists and Structured Answers

When a model is asked for a list or a structured answer, output checks can be precise, because the expected shape is clear. A list check asks whether the output actually contains a list, whether it has roughly the number of items requested, whether each item is of the requested kind, and whether any item is duplicated, contradictory, or off-topic. A structured answer check asks whether the expected fields are present, whether each field has the expected type, and whether required fields are missing. These checks are the output versions of the schema checks you learned for inputs, and they are powerful, because structure is easier to verify than meaning, and a structural failure often indicates a deeper failure in the model's understanding of the task.

Duplicates deserve special attention in lists, because a model that repeats the same item several times, perhaps in slightly different words, is a model that has run out of genuine items and is filling space. A duplicate checker that normalises items, by lowercasing and trimming them, and then counts distinct items, can flag lists where the distinct count is far below the requested count. That flag does not prove the list is wrong, because some tasks legitimately produce similar items, but it prompts the user to look closely, which is the right response to a suspicious pattern. Duplication is a hallucination signal in list form, and it is one of the easiest output signals to check automatically.

Structured answers also need a check for invented fields. A model asked for a name and a date may invent an extra field, such as a location, that was never requested, or may fill a required field with a plausible-sounding value when the true value is unknown. An invented field is a sign that the model is guessing rather than reporting, and a checker that compares the output's fields with the requested fields, flagging extras and checking required fields for grounding, can catch it. That comparison is simple to implement for toy outputs, where fields are labelled, and it teaches you to think about outputs as structures to be validated, not just as text to be read.

Section 22: Output Checks for Tone and Style

Tone and style are part of an output's quality, and in some tools they are part of its safety as well. A tone check asks whether the output's tone matches what the task and the audience require: is it polite when it should be polite, neutral when it should be neutral, and simple when the audience is a beginner? An output that is rude, aggressive, or mocking, when the task called for a helpful answer, is a failure, even if its facts are correct, because tone affects how the output is received and whether it harms the reader. A style check asks similar questions about clarity: is the output readable, are its sentences a reasonable length, and does it avoid jargon the audience would not understand? Those checks improve usability as well as safety, because a clear, appropriately toned output is more likely to be understood and less likely to be misinterpreted.

Tone checking automatically is difficult, because tone is subtle and context-dependent, but simple signals help. A checker can look for words associated with rudeness or hostility, from a list you define for your toy, and flag outputs containing them. It can measure average sentence length, and flag outputs whose sentences are so long that they become hard to follow. It can check for jargon, by comparing the output's words with a list of simple words, and flagging outputs that use many words outside that list when the audience is a beginner. None of these signals proves a tone or style problem on its own, but together they identify outputs worth a second look, which is the right role for an automated tone check: flagging, not deciding.

The response to a tone or style flag should usually be a suggestion, not a block, because tone is subjective, and a checker that blocks outputs for tone will block many legitimate ones, frustrating users who disagree with its judgement. A better response is to deliver the output with a note, or to offer a rewritten version in a more appropriate tone, letting the user choose. That gentleness reflects the uncertainty of tone judgement, and it respects the user's ability to judge tone for themselves, once the concern is pointed out. For high-stakes contexts, such as messages to customers, a tone flag should escalate to a human reviewer, who can judge tone with context that the checker lacks.

That exercise teaches you to treat tone as checkable, in a limited but useful way, and to respond to tone flags with suggestions rather than blocks, which is the proportionate response to an uncertain judgement.

Section 23: Combining Output Stages into a Pipeline

You have now met length, format, consistency, private-data, hallucination, steering, and tone checks, and it is time to combine them into a single output pipeline, so that you can see how they work together. The pipeline runs stages in order, from cheap to expensive: length and format first, then private-data and structure, then consistency and grounding, then steering and tone, with the most expensive and uncertain checks last, so that they only run on outputs that have passed the earlier stages. Each stage returns a decision, allow, flag, correct, or block, and the pipeline combines them: a block from any stage blocks the output, a correction from a stage is applied and noted, and flags are collected for the final decision, which may be delivery with warnings, or escalation to a human, depending on the number and severity of flags.

The pipeline's combination rule needs to be written down, because different builders may combine stages differently, and the rule determines the pipeline's overall behaviour. A simple rule is: block beats everything, correction applies when no block exists, and flags accumulate, with delivery allowed only when the number of flags is below a threshold you choose, and escalation when it is above. That rule is easy to explain, easy to test, and easy to adjust, by changing the threshold or by changing which stages can block versus flag. A pipeline whose combination rule is explicit is a pipeline whose behaviour can be predicted and improved, while one whose rule is implicit, buried in code, will surprise its builder when stages interact unexpectedly.

Testing the combined pipeline requires cases that exercise each stage and their combinations: an output that fails length, one that fails format, one that is flagged for private data, one that is flagged for consistency, one that is blocked for steering, and one that passes everything. It also requires cases that fail multiple stages, to confirm that the combination rule handles them correctly, such as an output that is both overlong and off-task, which should be blocked, not merely flagged. Those combination cases reveal ordering bugs and rule errors that single-stage tests miss, and they are the cases that give you confidence in the pipeline as a whole, rather than in each stage alone.

In a toy, you can implement the pipeline as a list of stage functions, like your input pipeline, with a combination function that applies the rule above. Run your test cases through it, record which stage made each decision, and confirm that the final decisions match your expectations. That exercise shows you the pipeline as a system, not as a collection of checks, and that systems view is what makes a builder effective, because real outputs fail in combinations, and only a pipeline tested in combinations can handle them.

def stage_consistency(task, output):
    task_words = important_words(task)
    output_words = important_words(output)
    if not task_words:
        return "pass", ""
    score = len(task_words & output_words) / len(task_words)
    if score < 0.3:
        return "block", "output off task"
    if score < 0.6:
        return "flag", "output partly off task"
    return "pass", ""

def check_output(task, output):
    flags = []
    for stage in (stage_length, stage_format, stage_private):
        decision, reason = stage(output)
        if decision == "block":
            return "block", reason, flags
        if decision == "flag":
            flags.append(reason)
    decision, reason = stage_consistency(task, output)
    if decision == "block":
        return "block", reason, flags
    if decision == "flag":
        flags.append(reason)
    if flags:
        return "flag", "; ".join(flags), flags
    return "allow", "all checks passed", flags

Section 25: Output Checks for Actions Proposed by Models

When a model proposes an action, rather than merely producing text, output checks must consider the action itself, not just the words describing it. A proposed action check starts with scope: is the action within what the user asked for, and within what the tool is allowed to do? An action outside the task's scope, such as a message to someone the user never mentioned, or a file change the user never requested, is a sign of steering or misunderstanding, and it should be blocked or escalated, not merely flagged. Scope is the most important action check, because an out-of-scope action is an action the user did not authorise, and unauthorised actions are the core harm that action defences exist to prevent.

A second action check concerns reversibility: can the action be undone if it turns out to be wrong? An action that can be undone, such as saving a draft, is lower risk than one that cannot, such as sending a message or deleting a file, and the check should treat them differently. Reversible actions may proceed with a flag, while irreversible actions should require confirmation, even when they pass all other checks, because confirmation is the human layer that no automated check can replace. That distinction, between reversible and irreversible, is a practical way to allocate checking effort: spend the most care on the actions that cannot be taken back.

A third action check concerns details: does the proposed action specify its target, its content, and its parameters clearly, or is it vague, incomplete, or ambiguous? A vague action, such as sending a message without saying to whom, or changing a file without saying how, should not proceed, because its effects cannot be predicted, and an unpredictable action is an unsafe action. The checker should require actions to be fully specified before they are approved, and should flag any action with missing details for clarification. That requirement forces the model, or the user, to state the action plainly, which makes it checkable and confirmable, and checkability is a precondition for safety.

In a toy, you can model proposed actions as small dictionaries, with fields for the action type, the target, and the details, and write a checker that validates scope against the task, checks reversibility against a list you define, and requires all fields to be present. Test it with a valid action, an out-of-scope action, an irreversible action without confirmation, and an action with a missing field, and confirm that each case is handled. That exercise teaches you to treat proposed actions as outputs to be checked, not as instructions to be obeyed, which is the mindset that makes action tools safe.

A fourth action check concerns timing: is this the right moment for the action, or should it wait? An action proposed too early, before the user has reviewed earlier steps, or too late, after the context has changed, may be wrong even if its scope, reversibility, and details are all correct. Timing checks ask whether the action fits the current stage of the task, and whether any precondition, such as a prior approval or a completed step, has been met. That check prevents premature or stale actions, a common error source in multi-step tools.

Section 26: When Output Checks Disagree

In a pipeline with several stages, stages will sometimes disagree: one stage flags an output while another passes it, or one stage suggests correction while another suggests blocking. Disagreement is normal, because stages look at different aspects, and it is not a sign that the pipeline is broken. It is a sign that the output is complex, and that different aspects point in different directions. Handling disagreement well requires a combination rule that is explicit, as you learned in Section 23, and a habit of logging disagreements, so that they can be studied and the rule can be improved. A pipeline that hides disagreement, by reporting only the final decision, loses information that could improve it.

The most common disagreement is between a strict stage and a lenient one: a length check may pass an output while a consistency check flags it, or a format check may block an output that a tone check would have passed. The combination rule resolves these by priority: blocks beat flags, and flags accumulate, so that a single block is enough to stop an output, while multiple flags together may escalate it, even if no single flag would. That priority reflects the stakes: a block indicates a serious problem that should not be overridden by a pass elsewhere, while a pass indicates only that one aspect is fine, not that the whole output is fine. A stage that passes is not voting for delivery. It is simply not objecting, and the absence of an objection is not an endorsement.

Disagreements also reveal which stages are most and least reliable. If one stage frequently flags outputs that other stages and human reviewers judge to be fine, that stage may be too strict, or its patterns may be poorly chosen, and it deserves adjustment. If a stage rarely flags anything, while other stages catch problems it should have caught, it may be too lenient, or its patterns may be outdated. Logging disagreements, by recording each stage's decision for each output, lets you see these patterns and adjust the stages, rather than guessing about them. That adjustment, based on disagreement data, is how pipelines improve over time, from a set of independent checks into a tuned system.

For your own pipelines, log each stage's decision separately, not just the final decision, and review the logs for disagreements. When you find a frequent disagreement, ask which stage is right, and why, and adjust the wrong one, or adjust the combination rule if the rule itself is the problem. That review habit turns disagreement from a nuisance into a diagnostic, and diagnostics are how builders learn. A pipeline whose disagreements are studied is a pipeline that gets better, while one whose disagreements are ignored stays stuck at its initial, imperfect settings.

Section 27: Output Checks for Safety-Critical Topics

Some topics deserve stricter output checks than others, because errors in those topics have higher stakes. Medical, legal, financial, and safety advice are the clearest examples: a wrong answer about a medicine, a law, a financial decision, or a safety procedure can cause real harm, while a wrong answer about a hobby or a story is merely disappointing. Output checks for safety-critical topics should therefore be stricter, with lower thresholds for flagging, mandatory disclaimers, and escalation to human experts or to professional sources, rather than delivery as if the model were an authority. That strictness is not a judgement about the model's general ability. It is a judgement about the stakes, and stakes should drive strictness, as you learned for risk ratings in Chapter 26.

A practical approach is to define topic profiles, similar to audience profiles, with stricter settings for safety-critical topics. A medical output, for example, might require a disclaimer that it is not medical advice and that the user should consult a professional, and it might be blocked if it contains specific dosage or treatment recommendations, because those are decisions for a professional, not for a model. A legal output might require a similar disclaimer and a suggestion to consult a lawyer. A financial output might require a disclaimer that it is not financial advice. Those disclaimers do not make the output safe on their own, but they set the user's expectations correctly, which reduces the chance that the user will act on the output as if it were professional advice. Expectation-setting is a safety measure in its own right.

Topic profiles also need a list of topics that trigger them, and that list should be based on the tool's purpose and its users, not on a universal catalogue. A tool for gardeners needs a profile for advice about chemicals, because a wrong answer there could harm plants, people, or pets, while a tool for writers may not need that profile at all. The builder's job is to identify the high-stakes topics for their tool, define profiles for them, and test those profiles with examples, including borderline cases where a topic is partly safety-critical and partly not. That identification is a design task, and it requires thinking about the tool's real use, not just about abstract categories.

In a toy, you can implement topic profiles as a dictionary mapping a topic keyword to a stricter set of checks, and a function that chooses the profile based on the task. Test it with a general output and a safety-critical output, and confirm that the latter receives a disclaimer and a stricter decision. That exercise teaches you to think about stakes as an input to checking, not as an afterthought, and that stakes-driven checking is the mark of a builder who understands that not all outputs are equal.

Section 28: Output Checks and the Feedback Loop

Output checks do more than protect users. They also teach the builder, through a feedback loop that connects output failures back to improvements in inputs, instructions, and the model itself. When an output check blocks or flags an output, that event is data: it tells you what went wrong, which stage caught it, and what kind of input or task led to it. Collecting those events, by category and by task, reveals patterns: a particular kind of task may produce many hallucination flags, suggesting that its instructions are vague; a particular source may produce many steering flags, suggesting that its content needs stronger input cleaning; a particular output format may produce many format blocks, suggesting that the task's format requirements are unclear. Each pattern points to a fix upstream, not just at the output stage, and fixing upstream prevents the problem from recurring, rather than catching it every time.

The feedback loop also works in the other direction: when output checks pass an output that later turns out to be wrong, because a user reports it or a reviewer catches it, that miss is data too. It tells you which stage failed, what signal it missed, and how the check should be improved. A builder who studies misses as carefully as catches will improve their checks faster than one who only celebrates catches, because misses reveal blind spots, while catches merely confirm that known patterns work. Keeping a record of misses, with their categories and causes, is therefore as important as keeping a record of catches, and it is a habit that distinguishes a learning builder from one who merely operates a pipeline.

Closing the feedback loop requires a routine, not just a record. On a schedule, review the output log, note the patterns, and decide on one or two upstream improvements, such as clarifying an instruction, tightening an input check, or adding a new output pattern. Then implement those improvements, test them, and watch the next period's logs to see whether the pattern improves. That cycle, review, improve, measure, is the same improvement cycle you have practised for input checks, and it is what turns a static pipeline into a learning system. A pipeline that learns is a pipeline that gets better with use, while one that does not learn stays at its initial quality, no matter how long it runs.

For your own projects, set a simple feedback routine: once a month, look at your output log, pick the most frequent problem category, and make one upstream fix for it. That single habit, repeated, will improve your tools more than any single clever check, because it compounds: each fix prevents a class of future problems, freeing attention for the next class. Compounding improvement is the most powerful force in defence, and it starts with the humble act of reading your own logs and acting on what they say.

Section 29: Output Check Myths, Corrected

Several myths about output checking circulate among beginners, and correcting them will save you from common mistakes. The first myth is that output checks are unnecessary if input checks are good, because clean inputs guarantee clean outputs. In reality, models are unpredictable, and clean inputs can still lead to wrong, hallucinated, or steered outputs, as you learned in Section 2. Input checks reduce the chance of a bad output, but they cannot eliminate it, because the model itself is a source of uncertainty. A builder who relies only on inputs is trusting the model completely, and that trust is misplaced. Output checks are the verification that the model earned, not the assumption that it did.

The second myth is that output checks slow a tool down so much that they are not worth it. In reality, most output checks are cheap, like their input counterparts, and ordering them from cheap to expensive keeps costs low. A length check, a format check, and a pattern scan take a tiny fraction of the time that generation itself takes, and they catch many problems before delivery. The cost of a missed problem, a harmful output shared or acted on, is far higher than the cost of checking, and it includes investigation, correction, and lost trust, which are expensive in time and reputation. Performance is not a reason to skip output checks. It is a reason to order them well, as you learned for inputs.

The third myth is that a single, clever output check can replace a pipeline. A beginner may find a consistency score or a pattern that catches many bad outputs, and conclude that the pipeline is unnecessary. But a single check, however clever, has a single blind spot, and outputs fail in many ways: length, format, consistency, privacy, steering, tone, and more. No single check covers all of them, and a problem that slips past the one check has no other layer to catch it. A pipeline's strength comes from diversity, with different stages catching different failures, and that diversity is not redundancy. It is layered design, and it is why this chapter teaches a pipeline rather than a single rule.

The fourth myth is that output checks, once written, never need updating. In reality, models change, tasks change, users change, and new patterns of failure appear, all of which require the checks to be reviewed and updated. A check written for last year's outputs may miss this year's problems, or may block this year's legitimate outputs, because the tool's purpose has grown. Regular review, which you learned for pipelines in earlier chapters, applies to output checks too, and it is what keeps them alive. A check that is never reviewed is a check that is slowly going stale, and stale checks are a common source of both missed problems and frustrated users.

Section 30: From Output Checks to Human Review

This chapter has taught you to inspect everything that leaves a tool, before it reaches a user, and the next chapter teaches you the final layer: human review. Human review exists because automated checks, for all their speed and consistency, cannot judge context, intent, or nuance as well as a person can. An output that passes every automated check may still be wrong in a subtle way that only a human, with knowledge of the task and the audience, would notice. An output that is flagged by an automated check may be perfectly fine, and only a human can tell the difference. Human review is therefore not a replacement for automated checks. It is their complement, handling the hard, ambiguous cases that automation cannot decide, while automation handles the clear, high-volume cases that would overwhelm a human.

The relationship between automated checks and human review is one of triage. Automated checks sort outputs into three groups: clearly sound, which are delivered; clearly problematic, which are blocked; and uncertain, which are sent to a human. That triage makes human review feasible, because humans only see the uncertain fraction, not every output, and it makes automated checks more effective, because they do not have to decide every case, only to sort the clear ones from the uncertain ones. A builder who designs that triage well, with thresholds that send the right fraction to humans, gets the best of both worlds: the speed of automation and the judgement of people. A builder who designs it poorly, sending too much or too little to humans, gets the worst of both: overwhelmed reviewers or unchecked outputs.

Human review also feeds back into automated checks, because reviewers' decisions are data. When a reviewer approves a flagged output, that approval suggests the flag was too strict, and the check can be softened. When a reviewer blocks an output that automation passed, that block suggests a gap, and a new check can be added. That feedback loop, which you met in Section 28, is how the combination of automation and human review improves over time, with each side teaching the other. The next chapter will teach you to design that loop deliberately, with queues, priorities, and escalation paths, so that human review is not an afterthought but a designed part of the system.

Those tools and habits are the foundation of human review, because a review queue is fed by the flags and blocks of the automated pipeline, and a reviewer needs the pipeline's reasons and categories to judge efficiently. The next chapter completes the layered defence you have built across this book, adding the human layer that makes all the automated layers trustworthy.

Section 31: Output Checks for Translated or Rewritten Content

When a model translates or rewrites content, output checks face a special challenge: the output is supposed to differ from the input in language or style, while preserving its meaning. A translation check therefore cannot compare words directly, because the words will be different by design. Instead, it checks for signals of meaning preservation: does the output have roughly the expected length relative to the input, does it cover the same main points in general terms, and does it avoid adding new claims that were not in the original? Length is a weak but useful signal: a translation that is far shorter than its source has probably dropped content, while one that is far longer has probably added content. Both extremes deserve flagging, even though length alone cannot prove a translation error.

A second check for rewritten content concerns tone and register. A rewrite asked to simplify a text for beginners should use simpler words and shorter sentences than the original, and a checker can measure that simplification, by comparing average sentence length and word complexity, and flag rewrites that are no simpler than the original. A rewrite asked to make a text more formal should show the opposite pattern. Those measurements are approximate, but they catch the clear failures, such as a simplification that changed nothing, or a formalisation that made the text more casual, which are the cases where the model misunderstood the rewrite task. Approximate checks that catch clear failures are valuable, even when they cannot judge subtle quality.

A third check concerns preservation of important details. A translation or rewrite should preserve names, numbers, and dates from the original, because those details carry meaning that must survive the transformation. A checker that extracts numbers and proper names from the input and checks whether they appear, in some form, in the output, can flag cases where a crucial detail was dropped or changed. That check is imperfect across languages, because names and numbers may be written differently, but for same-language rewrites it is straightforward, and for translations it can be adapted to check numbers at least, which are often written similarly. Detail preservation is a concrete, testable aspect of translation quality, and it deserves a check even when full meaning comparison is beyond automation.

In a toy, you can build a rewrite checker that takes an original and a rewritten version, both invented by you, compares their lengths, measures average sentence length, and checks that numbers from the original appear in the rewrite. Test it with a good rewrite, a rewrite that drops a number, and a rewrite that is no simpler than the original, and confirm that each case is handled. That exercise teaches you to check transformations by their invariants, the things that should not change, rather than by their surface, which is supposed to change, and that way of thinking applies to every kind of transformation a model performs.

Section 32: Output Checks for Long Answers

Long outputs present special checking challenges, because their length makes them harder to review, more likely to contain an error somewhere, and more costly to check thoroughly. A long-answer check starts with structure: does the output have a clear organisation, with sections, headings, or a logical flow, rather than being an unstructured wall of text? Structure can be checked simply, by looking for headings, paragraph breaks, or list markers, and a long output without any structure is a sign that the model lost track of its organisation, which makes errors more likely and review harder. Structure is therefore both a quality signal and a safety signal, because a well-structured output is easier for a human to verify, section by section, than an unstructured one.

A second long-answer check samples the output rather than reading it all. Because checking every sentence of a very long output may be expensive, a checker can sample sections, such as the beginning, the middle, and the end, and check those for consistency, private data, and steering signals. Sampling does not guarantee that the unsampled parts are clean, but it catches problems that appear throughout the output, which are the most common kind, and it does so at a fraction of the cost of full checking. Sampling should be combined with a full check of the most sensitive parts, such as any section that contains numbers, names, or claims, so that the highest-risk content is always checked, even when the rest is sampled. That combination, sampling plus targeted full checks, balances cost and coverage sensibly.

A third long-answer check concerns repetition and drift over length. Models generating long outputs tend to repeat themselves, to drift from the original topic, or to contradict earlier sections as the output grows, because maintaining consistency over many paragraphs is hard. A checker that compares later sections with earlier ones, looking for repeated phrases, topic changes, or contradictions in simple forms, can flag long outputs where drift or repetition has set in. That flag does not prove the output is wrong, but it prompts the user or reviewer to read the later sections carefully, which is where errors are most likely to hide. Drift over length is a predictable failure mode of long generation, and checking for it explicitly is a sign of a builder who understands their model.

In a toy, you can simulate a long output by joining several short paragraphs you invent, including one that repeats an earlier paragraph and one that drifts to an unrelated topic, and build a checker that splits the output into sections and compares them for repetition and topic overlap. That exercise teaches you to think about long outputs as sequences to be checked section by section, not as single blocks, and that sectional thinking is essential for any tool that produces long answers, reports, or documents.

Section 33: Disclaimers and Warnings in Outputs

Disclaimers and warnings are a form of output check response, distinct from blocking, correcting, or flagging, because they do not change the output itself. They add information alongside it, telling the user how to interpret it, what its limits are, and what to verify before acting on it. A disclaimer that says this summary was generated automatically and may contain errors sets the user's expectations correctly, which reduces the chance that they will act on an error as if it were fact. A warning that says this output contains details not found in the input, please verify them, directs the user's attention to the specific parts that need checking. Those additions do not make the output more accurate, but they make the user more careful, and careful users catch errors that checkers miss.

Disclaimers work best when they are specific and brief. A generic disclaimer on every output, such as a long legal paragraph, becomes background noise that users ignore, because it appears whether or not it is relevant. A specific disclaimer, attached only when a check raises a concern, and naming that concern in general terms, is more likely to be read and acted on, because it is relevant to the output in front of the user. The principle is the same as for warnings in earlier chapters: warn when it matters, stay quiet when it does not, so that warnings retain their power to attract attention. A tool that warns constantly trains users to ignore warnings, which defeats their purpose.

Warnings also need to be placed well. A warning at the beginning of an output prepares the user to read carefully, while a warning at the end may be missed if the user stops reading early. A warning attached to a specific section, such as a note beside a paragraph containing an unverified figure, is more useful than a warning at the document level, because it tells the user exactly where to look. Placement is therefore a design decision, and it should be made with the user's reading habits in mind: put the warning where the user will see it before acting on the uncertain part, not after. That timing, warning before action, is what makes warnings protective rather than merely decorative.

Test it with a clean output, a flagged output, and a heavily flagged output, and confirm that the disclaimers differ appropriately. That exercise teaches you to treat disclaimers as a graded response, not as a blanket addition, and that grading is what keeps them meaningful.

Section 34: Output Checks for Accessibility

Output checks should ensure that outputs are accessible to all users, including those who use screen readers, who have limited vision, or who read in a second language. An accessibility check for outputs asks whether the output is structured so that assistive technologies can navigate it, whether its language is clear enough for its audience, and whether any visual information is also conveyed in text. A long output without headings is hard for a screen reader user to navigate, because they cannot skim it visually, and a checker that flags unstructured long outputs therefore serves accessibility as well as quality. An output that relies on colour alone to convey meaning, such as saying the red items are important without naming them, is inaccessible to users who cannot see colour, and a checker that flags colour-only references helps the builder fix that.

Language clarity is another accessibility concern. An output written in dense, jargon-heavy language excludes users who are beginners, who read in a second language, or who have cognitive difficulties, even when its content is accurate. A checker that measures sentence length, word complexity, and the presence of unexplained terms, and that flags outputs that exceed the audience's reading level, helps the builder adapt the output to its readers. That adaptation is not dumbing down. It is matching communication to audience, which is a basic principle of good writing as well as of accessibility, and it benefits all readers, not only those with accessibility needs, because clear language is easier for everyone.

A third accessibility check concerns alternatives for non-text content. If an output includes a chart, an image, or a diagram, it should also include a text description of what that content shows, so that users who cannot see it can still understand it. A checker that flags outputs containing images without descriptions, or charts without data summaries, prompts the builder to add those alternatives, which makes the output usable by more people. That check is easy to implement in a toy, where images are represented by placeholders, and it teaches the habit of always providing a text alternative, which is one of the most important accessibility practices.

For your own tools, include accessibility in your output pipeline from the start, rather than adding it later, because retrofitting accessibility is harder than building it in. Check structure, clarity, and alternatives for every output, and test with the perspective of a user who cannot see the output, who reads slowly, or who is new to the topic. That perspective will improve your outputs for everyone, because the qualities that make an output accessible, structure, clarity, and completeness, are the qualities that make it good.

A fourth accessibility check concerns colour and contrast in any visual part of an output. If an output uses colour to distinguish items, it should also use labels, patterns, or text, so that the distinction survives for users who cannot perceive colour, and its contrast should be strong enough for users with limited vision. A checker that flags colour-only distinctions prompts the builder to add redundant cues, which is a simple form of inclusion that also helps users in bright light, on small screens, or with ageing eyes. Redundant cues are good design for everyone.

Section 35: Output Checks in Multi-Step Tools

In a multi-step tool, where the output of one step becomes the input of the next, output checks serve a double purpose: they protect the user from a bad final output, and they protect later steps from bad intermediate outputs. An intermediate output that contains an error, a private value, or a steered instruction can poison every later step, because each step builds on the previous one's result. Checking intermediate outputs, with the same stages as final outputs, prevents that poisoning, by catching problems early, when they are cheapest to fix and before they spread. A tool that only checks its final output, and not its intermediates, is a tool that lets errors compound through its steps, which makes the final output harder to trust and harder to debug.

Intermediate checks can be lighter than final checks, because their audience is the next step, not a human user, and their purpose is to catch gross errors rather than subtle ones. A length check, a format check, and a private-data scan may be enough for intermediates, while final outputs deserve the full pipeline, including consistency, grounding, and tone. That tiered approach balances cost and coverage: intermediates are checked cheaply and frequently, finals are checked thoroughly and once. The tiering should be explicit, so that the builder knows which checks run where, and can adjust the balance if intermediates prove to be a source of problems.

Intermediate checks also need to handle the case where a step's output is intentionally different from its input, such as a summarisation step that shortens, or a translation step that changes language. A checker that compares an intermediate output directly with the original input may flag legitimate transformations as errors, because transformation is the step's purpose. Intermediate checks should therefore compare each step's output with that step's task, not with the original task, so that legitimate transformations pass and only genuine errors are flagged. That per-step comparison requires the pipeline to know each step's task, which is a design requirement: multi-step tools should record each step's task alongside its output, so that checks can be task-aware.

In a toy multi-step tool, you can simulate two steps, such as extracting key points and then summarising them, and build a checker that runs light checks on the first step's output and full checks on the second's, comparing each with its own task. Test it with a good intermediate, a bad intermediate, and a good final built from a bad intermediate, and see whether the intermediate check catches the problem before it reaches the final. That exercise teaches you to think about outputs as a chain, where each link needs checking, not just the last one.

Intermediate checks also protect against a subtle failure: a step that succeeds technically but produces an output in a format the next step cannot handle. A format mismatch between steps causes the next step to fail, or worse, to misinterpret the intermediate and produce a plausible-looking but wrong final output. Checking each intermediate's format against what the next step expects catches those mismatches at the boundary where they occur, rather than letting them propagate as silent errors. Boundary checks between steps are therefore as important as checks at the system's entrance and exit, because every boundary is a place where assumptions can break.

Section 36: Testing Output Checkers

Testing an output checker requires test outputs that cover the full range of cases, from clean to problematic, and the test set should be organised by category, so that each stage can be measured separately. A good test set includes clean outputs that should pass, outputs that fail length, outputs that fail format, outputs that contain private-data shapes, outputs that are off-task, outputs that contain hallucination signals, outputs that show steering signals, and outputs that are partially wrong. Each category tests a different stage, and running the checker against all categories shows which stages work and which need improvement. A test set that only includes clean outputs and obviously bad ones will miss the borderline cases, which are the ones where checkers most often fail.

Test outputs should be invented by you, for your toy, and should be clearly labelled as tests, kept in a separate folder from real outputs, and deleted when no longer needed, following the same safe-testing habits as for inputs. The labels matter, because a test output containing a private-data shape or a steering signal could be mistaken for a real problem if it leaks into a real log or report. Keeping test material separate and labelled prevents that confusion, and it makes the test set itself a document of what the checker is supposed to catch, which is useful for collaborators and for future you.

Testing should also measure the checker's behaviour on corrected outputs. When a checker corrects an output, by redacting or trimming, the corrected output should be re-checked, to confirm that the correction removed the problem without introducing a new one. A redaction that leaves a partial value, or a trim that cuts a sentence in half, creates a new problem while fixing the old one, and only a re-check catches that. That re-check step is easy to add: after correction, run the pipeline again on the corrected output, and confirm that it passes or is flagged at a lower severity. A checker that re-checks its own corrections is a checker that verifies its work, which is the same principle as output checking itself, applied to the checker.

Finally, test the checker with outputs from different tasks and audiences, because a checker tuned for one task may fail on another. A summary checker may work well for gardening notes but poorly for technical documents, if its patterns and thresholds were chosen for the first task only. Testing across tasks reveals that overfitting, and it prompts the builder to make the checker more general, or to define task-specific profiles, as you learned for audiences and topics. Generality is not automatic. It must be tested for, and the test set is where that testing happens.

Section 37: Output Check Myths Revisited

Earlier in this chapter you corrected four myths about output checking. Now, with more knowledge, you can revisit those myths and see them more deeply, which is a useful way to consolidate learning. The first myth was that output checks are unnecessary if input checks are good. You now know that models are unpredictable, and that clean inputs can still lead to wrong, hallucinated, or steered outputs, because the model adds uncertainty that inputs cannot remove. The deeper correction is that input and output checks are partners, not alternatives, and that each covers the other's gaps: inputs catch problems before generation, outputs catch problems after it, and together they catch far more than either alone. That partnership is the core of layered defence, and it applies at every level of the system.

The second myth was that output checks slow a tool down too much to be worth it. You now know that most checks are cheap, that ordering them from cheap to expensive keeps costs low, and that the cost of a missed problem far exceeds the cost of checking. The deeper correction is that cost should be measured, not assumed, and that a checker whose cost is measured can be optimised, by ordering, by sampling long outputs, or by reserving expensive checks for flagged cases, while a checker whose cost is merely feared will be skipped entirely, without evidence. Measurement replaces fear with fact, and fact is a better basis for design.

The third myth was that a single clever check can replace a pipeline. You now know that outputs fail in many ways, and that no single check covers them all. The deeper correction is that pipeline stages are diverse, not redundant: each looks at a different aspect, length, format, consistency, privacy, steering, tone, and together they form a judgement that no single stage could. Understanding diversity versus redundancy helps you design pipelines that are efficient as well as layered, because you can remove a truly redundant stage without weakening the pipeline, while keeping the diverse stages that each contribute something unique. That efficiency matters, because a lean pipeline is more likely to be kept and maintained than a bloated one.

The fourth myth was that output checks, once written, never need updating. You now know that models, tasks, users, and failure patterns all change, and that checks must be reviewed and updated to stay in step. The deeper correction is that maintenance is part of building, and that a checker's changelog, review schedule, and test set are as much a part of the checker as its rules. A builder who maintains their checks is a builder whose tools stay safe as they grow, while one who writes checks once and forgets them watches those checks go stale. Maintenance is the difference between a defence that lasts and one that merely looked good on the day it was built.

Section 38: Output Checks for Your Own Projects

When you build tools for yourself, output checks are easy to skip, because you are the only user, and you can review your own outputs as you go. But skipping them is a mistake, for two reasons. First, you will not always review carefully: when you are busy, tired, or in a hurry, you will skim outputs and miss errors that a checker would have caught. A checker works consistently, even when you do not, and that consistency is valuable even for personal tools. Second, the habits you build on personal tools transfer to shared tools, and a builder who checks outputs on personal projects will check them on shared ones too, while one who skips them personally will likely skip them professionally as well. Personal practice is professional preparation, and output checking is a habit worth building early.

For a personal tool, the output pipeline can be simple: length, format, private-data, and consistency checks, with flags printed alongside the output, rather than blocks, so that you can see the checker's judgement and decide for yourself. That light-touch design suits personal use, because you are the reviewer, and the checker is your assistant, not your gatekeeper. It still catches problems you would miss when skimming, and it teaches you the pipeline pattern without the overhead of a full shared-system design. As your personal tools grow, or as you share them, you can tighten the pipeline, adding blocks, corrections, and escalation, with the foundation already in place.

A personal output checker also helps you learn about your model and your tasks. When it flags outputs repeatedly for a particular task, that pattern tells you something: the task may be vague, the input may be problematic, or the model may struggle with that topic. That learning, gained from your own checker's flags, improves your prompting, your input checks, and your task design, in a feedback loop that benefits all your future projects. A checker that only protects is useful. A checker that also teaches is invaluable, and personal tools are the ideal place to experience that teaching, because the feedback is immediate and the stakes are low.

Finally, keep your personal output checker visible. Print its decisions and flags alongside outputs, rather than hiding them, so that you learn to read its judgements and to trust or question them appropriately. A checker whose work is visible is a checker you understand, and understanding is what turns a tool into a skill. When you later build shared tools, that understanding will let you design checkers that users trust, because you will have experienced, first-hand, what good checking feels like from the user's side.

A personal output checker can also serve as a diary of your tool's behaviour. When you look back over its flags, you can see which tasks you struggled with, which topics produced the most errors, and how your prompting improved over time. That diary is a record of learning, and it is satisfying to review, because it shows progress that would otherwise be invisible. A builder who keeps such a diary learns faster, because they can see their own patterns, and they can share the lessons with others, turning personal practice into community knowledge. The diary is a small side effect of checking, but it is a valuable one.

Section 39: Output Check Checklist

By now you have met many kinds of output checks, and a checklist will help you apply them consistently to any tool. The checklist has ten items, and you can run through it for each output your tool produces. First, length and format: is the output within the expected size and shape for its task? Second, consistency: does the output address the task, covering its main points without wandering or inventing? Third, grounding: do the specific details in the output come from the input, or do they appear from nowhere? Fourth, private data: does the output contain private details that its audience should not see, and are they redacted or flagged? Fifth, steering: does the output show signs of being influenced by something other than the task, such as unexpected actions, roles, or topics?

Sixth, tone and style: is the output's tone appropriate for its audience, and is its language clear enough to be understood? Seventh, structure: for long or structured outputs, is the organisation clear, with headings, lists, or fields as expected, without duplication or drift? Eighth, audience and topic: is the output checked with the profile for its audience and its topic, with stricter checks and disclaimers for safety-critical topics and wider audiences? Ninth, decision and message: does the check produce a clear decision, allow, correct, flag, or block, with a general message for the user and a detailed entry for the log? Tenth, logging and review: is the decision logged by category, without full content, and is there a schedule for reviewing the logs, studying misses, and updating the checks?

Run through this checklist for a toy you have built, and write down the answer to each item for each output type. Where an answer is missing, you have found a gap, and the gap is your next improvement. Where every answer is present, you have a tool whose output checks are complete at a basic level, not because each check is perfect, but because every kind of problem has at least one check looking for it. That completeness is the goal of the checklist: coverage across all kinds of output problems, so that no kind is left entirely undefended.

Keep the checklist with your project, and revisit it when the tool changes. A new output type, a new audience, a new topic, or a new ability should trigger a fresh run through the checklist, because each change can open a new gap. A checklist that is used once and forgotten is a snapshot. A checklist that is revisited regularly is a habit, and habits are what keep defences alive as tools grow and change over time.

An eleventh item is worth adding for tools that will be used by others: communication. Does the tool explain its output checks to users, in plain words, so that they understand why an output was corrected, flagged, or blocked, and what they can do next? A tool that explains its checks helps users trust them, because transparency turns an opaque block into an understandable decision. Communication is not strictly a check, but it belongs on the checklist because it helps users cooperate rather than work around the system. A checklist that includes communication is a checklist that thinks about people, not only about rules.

Section 40: Looking Ahead to Human Review

This chapter has taught you to guard the exit of your tools, and the next chapter teaches you the final layer: human review. Human review exists because automated checks, for all their speed and consistency, cannot judge context, intent, or nuance as well as a person can. An output that passes every automated check may still be wrong in a subtle way that only a human, with knowledge of the task and the audience, would notice. An output that is flagged by an automated check may be perfectly fine, and only a human can tell the difference. Human review is therefore not a replacement for automated checks. It is their complement, handling the hard, ambiguous cases that automation cannot decide, while automation handles the clear, high-volume cases that would overwhelm a human.

The relationship between automated checks and human review is one of triage, which you met in Section 30, and the next chapter will develop it in full: how to build a review queue, how to prioritise its items, how to give reviewers the context they need to judge efficiently, and how to use their decisions to improve the automated checks. Those topics are the practical heart of human review, and they turn a vague idea, have a human look at it, into a designed system that works at scale, with limited reviewer time and many outputs to judge. Designing that system well is a skill in its own right, and it is the final skill this book's safety chapters will teach you.

What changes in the next chapter is the perspective. Input and output checks are programs judging programs, with rules, patterns, and scores. Human review is people judging programs, with context, judgement, and responsibility, and designing for people requires different thinking: about workload, about fairness, about training, and about the wellbeing of reviewers who see difficult content. Those human considerations are as much a part of defence design as any technical check, because a review system that burns out its reviewers, or that treats them unfairly, will fail, no matter how well its queue is engineered. The next chapter therefore broadens the view from code to people, and that broadening is the final step in building a complete defence.

Section 41: A Complete Output Pipeline in One Script

You have now met every stage of output checking, and it is time to assemble them into a single script that you can run, test, and adapt. The script has six stages, in order: length, format, private-data flagging, consistency scoring, steering signals, and tone signals. Each stage is a small function that returns a decision, and a combination function applies the rule: block beats everything, corrections are noted, flags accumulate, and delivery is allowed only when no block exists and the flag count is below a threshold you choose. The task and outputs are invented by you, for your toy, so that your practice stays safe and local. The script prints the decision, the flags, and the stage that made the decision for each test output, so that you can see which stage contributed to each outcome.

The value of assembling the pipeline is that you can see the stages interact and can measure their combined behaviour. A test output that fails length will be rejected before any other stage runs, which shows the cheap-first ordering working. A test output that passes length and format but scores low on consistency will be blocked at the consistency stage, which shows that later stages catch what earlier ones miss. A test output that passes everything but contains a private-data shape will be flagged, which shows the flag outcome working as a middle path. Those interactions are the heart of pipeline design, and they are best learned by running the pipeline and watching its decisions, rather than by reading about them.

Build the script in stages, testing after each addition, as you have learned. Start with length and format, and test them. Add private-data flagging, and test it with your private-data cases. Add consistency scoring, and test it with on-task and off-task outputs. Add steering and tone signals, and test them with your signal cases. At each step, run your full test set and record the results, so that you can see whether the new stage helped or hurt. That staged building, with measurement at each step, is the professional way to grow a pipeline, and it produces a pipeline you understand deeply, because you watched it grow.

When the script works, write a short paragraph describing what it does, what it catches, what it misses, and what you would improve next. That paragraph is your pipeline's documentation, and it is the honest summary that future you, or a collaborator, needs to maintain the pipeline. Keep it with the code, update it when the code changes, and you will have a record of your thinking that makes maintenance possible. Documentation is not separate from building. It is part of building, and it is part of defence, because a pipeline no one understands cannot be kept safe.

Section 42: Reading Model Outputs Like a Builder

When you use an AI tool yourself and receive an output, that output is a learning opportunity, if you read it like a builder. A good output, in response to a clear task, will stick to the task, cover its main points, avoid inventing details, and present itself in a clear, appropriate tone. Reading outputs with those criteria in mind trains your eye for quality, and it shows you what good output checking feels like from the user's side. An output that wanders, invents, or adopts an odd tone is a signal worth noticing, even if you cannot prove it is wrong, because noticing is the first step toward verifying, and verifying is the habit that protects users from hallucination and steering.

It is also useful to notice how a tool handles its own uncertain outputs. Does it add a disclaimer when it is unsure? Does it show its sources, so that you can verify its claims? Does it flag parts that need checking, or does it present everything with equal confidence, as if all parts were equally certain? A tool that shows its uncertainty honestly is a tool you can trust more, because it helps you judge where to verify, while a tool that hides uncertainty forces you to verify everything or to trust blindly, neither of which is practical. Noticing that difference trains your judgement about tools, and it will shape the tools you build, because you will remember the value of honest uncertainty and will design for it.

Section 43: Output Checks for Your Own Summariser

If you build a summariser for your own notes, output checks are easy to add and valuable to have, because summaries are the outputs you will rely on most, and errors in them propagate into your later work. A personal summariser's output pipeline can be light: length relative to the source, coverage of the source's main points, a private-data scan, and a steering check for unexpected topics or actions. Those four stages catch the most common summary failures, and they run quickly, so that they do not slow down a tool you use every day. The pipeline's decisions can be shown as flags alongside the summary, rather than as blocks, because you are the reviewer, and the checker is your assistant, not your gatekeeper.

A personal summariser also benefits from a habit that is specific to summaries: comparing the summary with the source before trusting it. When you read a summary, skim the source for the main points and check whether the summary covers them, without inventing new ones. That skim takes little time, and it catches errors that automated checks miss, especially subtle hallucinations that look plausible. The checker and the skim together, automation plus human attention, are stronger than either alone, and that combination is the same partnership you will design formally in the next chapter, practised here in its simplest, personal form.

Another habit for personal summarisers is to keep the source alongside the summary, so that you can verify any part of the summary that looks doubtful, without searching for the original. A summary stored without its source is harder to verify, and a doubtful claim in it may go unchecked because the effort of finding the source is too high. Storing source and summary together, with a link or a reference, makes verification cheap, and cheap verification is verification that actually happens. That design choice, keeping provenance with output, is a small habit with a large effect on trust, and it applies to every tool that produces summaries, reports, or answers based on sources.

Finally, review your summariser's flags regularly. When it flags summaries repeatedly for a particular kind of note, that pattern tells you something: the notes may be vague, the task may be unclear, or the model may struggle with that topic. That learning improves your notes, your tasks, and your prompting, in a feedback loop that benefits all your future work. A personal checker that teaches you about your own material is a tool that pays for itself, and it is the kind of tool worth building and keeping.

One more habit for personal summarisers is to keep a short note of any summary you corrected or discarded, with the reason in general terms, so that you can see whether the same problem recurs. A recurring problem points to a systematic issue, such as a vague task or a problematic source, while a one-off problem is usually just noise. That distinction helps you spend your improvement effort where it matters most, on the systematic issues, rather than chasing every single error. A small log of corrections is therefore a learning tool as well as a record, and it costs almost nothing to keep.

Section 44: Talking About Output Checks Without Jargon

Explaining output checks to someone who has never heard of them is a useful skill, because it spreads defensive awareness in plain language. The explanation should be short and concrete, using an everyday comparison. You might say that an output check is like a proofreader who reads a draft before it is published, checking for errors, for content that should not be there, and for parts that do not match the assignment, and returning the draft for correction when something is wrong. That comparison gives the listener the core idea, without any technical detail they do not need, and it connects to experience they already have with proofreading, editing, and publication. Plain comparisons are more persuasive than technical definitions, because they anchor a new idea in a familiar one.

When you explain output checks, focus on the benefit, not on the mechanism. Tell the listener that checks keep answers accurate, prevent private details from leaking into shared outputs, and catch mistakes before they spread, rather than listing the stages of a pipeline. Benefits are what listeners care about, and they are what motivate people to accept checks, rather than seeing them as obstacles. A listener who understands that checks prevent their own mistakes from reaching others will cooperate with them, while a listener who hears only about attacks and threats may see checks as someone else's problem. Framing checks as help, not as hindrance, is a communication skill that makes defences more effective in practice.

Be careful about the examples you use when explaining. Use general descriptions, such as a summary that invents a detail, or a message that includes something private, rather than realistic harmful examples, because general examples teach the principle without giving anyone material to misuse or without alarming the listener unnecessarily. If a listener asks for a specific harmful example, explain why you are keeping it general: the principle is what matters, and the specific wording is not needed to understand why checks exist or how they help. That refusal to share specifics is itself a teaching moment, because it models the boundary between sharing principles and sharing harmful detail, which is one of the most important habits in security work.

Finally, tailor your explanation to the listener. A colleague who builds tools needs more detail than a friend who merely uses them, and a teacher needs different examples from a student. The core idea stays the same, but the depth and the examples change with the audience. That tailoring is a communication skill, and it is worth practising, because the best defence knowledge is useless if it cannot be explained to the people who need it. A builder who can explain output checks clearly is a builder who can build a team, a user base, and a culture that takes checking seriously.

Section 45: The Builder's Responsibility for Outputs

When your tool produces outputs, you take on a responsibility for what those outputs do in the world, and that responsibility goes beyond merely generating them. You are responsible for checking them before they reach users, for correcting or blocking them when they are problematic, for warning users when they are uncertain, and for not sharing them in ways that could harm. That responsibility exists even when the output was generated by a model, because you chose the model, you designed the pipeline, and you decided to deliver the output. Blaming the model does not remove the builder's responsibility, any more than blaming a tool removes a craftsperson's responsibility for what they make with it. Responsibility for outputs is therefore a core part of building AI tools.

This responsibility has visible signs, similar to those you met for inputs. One sign is a pipeline: every output passes through the same stages, in the same order, with no shortcuts. Another sign is helpful messages: corrections, flags, and blocks explain what was wrong and what to do next, in plain words, without leaking internal rules. A third sign is logging: decisions are recorded by category, without full content, and logs are reviewed on a schedule. A fourth sign is testing: the checker is tested in both directions, with clean and problematic outputs, and the results are recorded. Those four signs, taken together, show that a builder took output handling seriously, and they are achievable even in a small project.

Responsibility for outputs also means being honest about what your tool's outputs are. If they are generated automatically and may contain errors, say so, with a disclaimer that sets expectations correctly. If they are not professional advice, say so, and suggest consulting a professional for high-stakes decisions. That honesty lets users make informed decisions about whether to trust and act on an output, and it protects you, because users who were informed cannot fairly claim they were misled. A tool that presents its outputs as perfect, when they are not, may gain trust quickly, but it will lose that trust just as quickly when errors are discovered, and the loss will be harder to repair than any short-term gain was worth.

Finally, responsibility for outputs extends to what you teach others about them. If you share your checker, your test outputs, or your explanations, share them with their limits attached, so that others do not mistake a basic checker for a complete solution. The defensive community grows stronger when each contribution is honest about what it does and what it does not do, and that honesty is a form of care for the next builder. Output responsibility is not a burden. It is a mark of a builder who understands that tools exist to serve people, and that serving people well includes checking what you share with them.

Section 46: Reviewing Your Output Pipeline Regularly

An output pipeline that is never reviewed will slowly go stale, because the outputs it checks change, the patterns it looks for become outdated, and the tool itself gains new output types and audiences. Regular review is therefore part of output checking, not an optional extra. A review does not have to be long or formal. For a small project, it can be a short session, once a month, in which you run your test set, look at your log counts, and ask three questions: which checks are blocking legitimate outputs, which checks are missing problematic ones, and what has changed about the tool or its users since the last review? Those three questions, answered honestly, will usually reveal the next improvement, whether it is a new pattern, a softer threshold, or a clearer message.

Review should also cover the pipeline's assumptions. When you built the pipeline, you assumed certain things about your outputs, your users, and your audiences. Those assumptions may no longer hold. An output type that was once rare may now be common. A user base that was once just you may now include friends or colleagues. A tool that only produced summaries may now produce messages as well. Each change in assumptions is a reason to adjust the pipeline, because a pipeline designed for old assumptions will miss new risks or block new legitimate outputs. Writing your assumptions down when you build the pipeline makes review easier, because you can check each assumption against reality, rather than trying to remember what you assumed months ago.

Review is also a good time to clean up. Delete old logs that are no longer needed, remove test outputs that have served their purpose, and update your documentation to match the current pipeline. That housekeeping keeps the project tidy and reduces the risk of old material leaking or confusing future work. It also gives you a sense of progress, because you can see how the pipeline has improved since the last review, and that sense of progress is motivating. Defence work can feel thankless, because its successes are invisible: nothing bad happened. A review session makes the successes visible, by showing what was caught and what was improved, and that visibility helps sustain the habit.

Make review a routine, not a reaction. Do not wait for an incident to review your pipeline. Review it on a schedule, even when nothing seems wrong, because the point of review is to find problems before they become incidents. A builder who reviews regularly is a builder who learns steadily, and steady learning is the most reliable form of defence. The pipeline you review today is the pipeline that will protect you tomorrow, and the habit of reviewing is what keeps it alive.

Section 48: Output Check Myths Revisited Again

You have now revisited the output myths once, in Section 37, and revisiting them again, with the full chapter behind you, is a useful way to consolidate learning at a deeper level. The first myth was that output checks are unnecessary if input checks are good. You now know, from building pipelines at both ends, that inputs and outputs fail differently: inputs fail by being malformed, hostile, or oversized, while outputs fail by being wrong, hallucinated, steered, or leaked, and no input check can catch an output failure that arises in the model itself. The deeper correction is that defence must guard both ends, because the model sits between them and adds its own uncertainty, which neither end alone can control. Guarding both ends is not duplication. It is the recognition that a system has two boundaries, and both need gates.

The second myth was that output checks slow a tool down too much. You now know, from measuring and ordering, that most checks are cheap, that sampling can handle long outputs, and that expensive checks can be reserved for flagged cases. The deeper correction is that speed and safety are not opposites to be traded, but qualities to be designed together, by ordering, by tiering, and by measuring, so that the pipeline is fast for clean outputs and thorough for suspicious ones. A pipeline designed that way is both fast and safe, while one designed without measurement is likely to be neither, because its builder guessed about both. Design with measurement is the habit that resolves the apparent trade-off.

The third myth was that a single clever check can replace a pipeline. You now know, from building combined pipelines, that stages interact, that disagreements reveal tuning opportunities, and that diversity across stages is what makes a pipeline resilient. The deeper correction is that a pipeline is a system, not a collection, and its behaviour emerges from the interaction of its stages, their order, and their combination rule, not from any single stage's cleverness. Thinking in systems, rather than in single checks, is the shift that separates a beginner from a practised builder, and it is a shift you have now made, by building and testing pipelines at both ends.

The fourth myth was that output checks never need updating. You now know, from review habits and feedback loops, that outputs, tasks, users, and failure patterns all change, and that checks must change with them. The deeper correction is that a checker is a living system, with a changelog, a review schedule, and a test set, and that maintaining it is part of building it, not an afterthought. A builder who maintains their checkers is a builder whose tools stay safe as they grow, while one who writes checkers once and forgets them watches those checkers go stale. Maintenance is the difference between a defence that lasts and one that merely looked good on the day it was built, and you now have the habits to maintain yours.

Section 49: Your Output Check Habits, Summarised

It is time to gather the habits of this chapter into a summary you can carry forward. The first habit is to treat every output as untrusted until it has passed its checks, regardless of how clean its input was, because the model adds uncertainty that inputs cannot remove. The second habit is to check length and format first, then private data and structure, then consistency and grounding, then steering and tone, ordering stages from cheap to expensive, so that bad outputs are caught quickly and good outputs pass smoothly. The third habit is to compare outputs with their tasks, using overlap, grounding, and structure signals, and to flag low scores for review rather than pretending that a score proves truth. The fourth habit is to fail closed, treating uncertain outputs as unsafe, with a flag outcome for cases that need human judgement.

The fifth habit is to choose the response proportionately: block serious, unfixable problems; correct local, fixable ones transparently; flag uncertain ones with a specific warning or disclaimer; and escalate high-stakes cases to humans. The sixth habit is to write helpful messages, general for users and detailed for logs, that explain what was wrong and what to do next, without leaking internal rules. The seventh habit is to log decisions by category, without full content, and to review those logs regularly for patterns, trends, misses, and disagreements between stages. The eighth habit is to test in both directions, with clean and problematic outputs, including boundaries, partial errors, and combinations, and to re-check corrected outputs and re-run tests after every change. The ninth habit is to review and update the pipeline on a schedule, retiring outdated checks and adding new ones as outputs, tasks, and audiences change. The tenth habit is to keep the boundary clear: practise only on your own systems, share principles rather than harmful detail, and never carry test material to a real system.

These ten habits, practised steadily, will make your tools' outputs safer than most, not because of any single clever technique, but because of a consistent, careful approach to everything that leaves a tool. Start with the first three on your next project, add the rest as you grow comfortable, and revisit the list from time to time to see which habit needs attention. A builder who practises these habits steadily will build tools that are reliable, predictable, and trustworthy, and that trust is the real product of output checking, beyond any single prevented error.

One more thought belongs in this summary. Output checking is not only about preventing harm. It is about building tools that work well, because a tool that checks its outputs delivers answers that are accurate, clear, and appropriate, which are the qualities users value most. By building output checks, you are not adding obstacles to your tools. You are making them better tools, for honest users as well as for security, and that improvement is the real reward of this chapter's habits.
