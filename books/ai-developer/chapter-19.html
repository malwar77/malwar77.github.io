Chapter 19: Tools, Actions and Safe Agent Design

Section 1: Tools: What Agents Can Do

This section is about tools: what agents can do. A tool is a named ability given to an agent, such as reading a file or searching notes, and tools are what turn an agent from words into actions. You already meet this idea in everyday life. like giving a worker a set of tools instead of only a description of the job. The goal here is not speed but clarity. When you can say each part of a job out loud, in order, you can spot mistakes early, explain your thinking to another person, and fix one part without throwing the whole job away. Keep this picture in mind as you read: small pieces, in order, each one checked, leading to an answer you can trust.

An agent's actions should always be logged with the tool's name, the inputs it received, and the result it returned. The log is what lets you answer the question of what the agent actually did, as opposed to what it meant to do. When something goes wrong, the log shows which tool was called, with what, and what came back. Without that record, you are left guessing, and guessing is a poor way to run a system that changes things.

Testing tools is straightforward, because each tool is small. Test it with a normal input, with an empty input, with a missing file, and with an input that tries to reach outside the allowed area. Each test should produce either a correct result or a clear error, never a silent wrong answer and never access to something forbidden. A tool that passes these four tests is a tool you can hand to an agent with reasonable confidence.

One danger in agent design is a tool that is too powerful for its name. A tool called read_note should never also be able to write, and a tool called add_numbers should never be able to open files. Power hidden behind an innocent name is how small mistakes become large ones, because nobody reviewing the log expects the danger. Name tools honestly, keep their power narrow, and review the list of tools as carefully as you review the agent itself.

The safest agents in this book are small, local, and approval-first. They work on your own files, they use a handful of boring tools, they log every action, and they ask before changing anything. That design is not a limitation to escape as you grow more skilled; it is the pattern that scales. Larger systems need the same habits, only enforced more strictly: fewer privileges, clearer logs, and stronger approval for anything that cannot be undone.
