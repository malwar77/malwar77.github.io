Chapter 14: Inheritance and Composition

Section 1

Inheritance is a way for a new class to reuse the attributes and methods of an existing class, by declaring that the new class is a kind of the existing one. If Book is a class with a title and an author, then Ebook might inherit from Book, gaining its title and author handling automatically, while adding a file size and a download method of its own. That reuse saves code, because the child class does not need to repeat the parent's implementation, and it creates a relationship that Python understands: an ebook is a book, so anywhere a book is expected, an ebook can be used, because it provides everything a book provides, plus more. That substitutability, where a child can stand in for a parent, is the core idea behind inheritance, and it is what makes inheritance more than mere code reuse.

Inheritance also creates a hierarchy, where classes are arranged from general to specific, with each level adding detail. A hierarchy might start with a general Publication, then a Book that adds an author, then an Ebook that adds a file size, each level refining the previous one. That hierarchy can be a useful way to organise a domain, because it reflects how general concepts specialise into specific ones, and it allows code written for a general level to work with any specific level below it, which is a powerful form of reuse. Hierarchies can also become a liability, however, when they grow deep or tangled, because a change to a general class can affect many specific classes in ways that are hard to predict, and because a specific class may inherit behaviour it does not need, simply because it sits below a general class in the hierarchy. That liability is why inheritance should be used thoughtfully, with hierarchies kept shallow and meaningful, rather than deep and speculative.

For beginners, the practical lesson is to use inheritance when the kind-of relationship is clear and stable, such as an ebook being a kind of book, or a savings account being a kind of bank account, and when the child genuinely needs most of the parent's behaviour, not just a small part of it. If the relationship is unclear, or if the child needs only a little of the parent, composition, covered later in this chapter, is often a better choice, because it allows reuse without the commitment of a hierarchy. Learning to distinguish a genuine kind-of relationship from a mere similarity, or from a has-a relationship, is a key design skill, and this chapter will help you develop it, through examples, guidelines, and warnings about common pitfalls.

class Book:
    def __init__(self, title):
        self.title = title
class Ebook(Book):
    def __init__(self, title, size):
        super().__init__(title)
        self.size = size
print(Ebook("Dune", 1200).title)

Section 2

super() also works for other methods, not just __init__, allowing a child to extend a parent method, rather than replacing it entirely. An ebook's describe method, for example, might call super().describe() to get the parent's description, and then add its file size to it, reusing the parent's formatting while adding its own detail. That extension pattern, call the parent, then add to the result, is common and clear, because it shows that the child's behaviour builds on the parent's, rather than duplicating it, and it ensures that a change to the parent's description, such as a new format, automatically appears in the child's description, without needing to update the child separately. That automatic propagation of parent changes is a benefit of inheritance, provided the parent's changes are compatible with the child's expectations, which is why parent classes should be designed with extension in mind, documenting which methods are meant to be overridden and which are meant to be called as-is.

Understanding super() also requires understanding the method resolution order, or MRO, which is the order in which Python searches classes in a hierarchy for a method, when a method is called on an object. For a simple hierarchy, with one parent, the order is intuitive: the child's class first, then the parent, then the parent's parent, and so on, until the method is found or the search fails. For multiple inheritance, where a class inherits from several parents, the order is more complex, and Python uses a specific algorithm, called C3 linearisation, to produce a consistent order that respects the hierarchy, which will be discussed later in this chapter. For now, the key point is that super() does not simply mean the immediate parent; it means the next class in the MRO, which, in a simple hierarchy, is the parent, but in a complex hierarchy, may be a different class, and understanding that distinction is important for advanced inheritance, though it rarely matters for simple, single-parent hierarchies.

A common mistake with super() is to call the parent method directly, by name, such as Book.__init__(self, title), rather than through super(), which works for a simple hierarchy, but breaks in more complex hierarchies, where the next class in the MRO is not the named parent, and it also makes refactoring harder, because renaming the parent requires changing every direct call. Using super() consistently, therefore, is a best practice, even in simple cases, because it prepares the code for future complexity, and because it expresses the intent, call the next method in the hierarchy, rather than call this specific parent, which is more accurate and more maintainable. That habit, like other best practices in this book, costs little in simple cases and saves a great deal in complex ones.

    def speak(self):

class Dog(Animal):

print(Dog("Bingo").speak())

Section 3

Overriding should respect the parent method's contract, meaning that the child's method should accept the same arguments, return the same kind of value, and maintain the same invariants, as the parent's method, even if its implementation differs, because callers who use a child through a parent reference, expecting parent behaviour, should not be surprised by a child that behaves incompatibly. That principle, sometimes called the Liskov substitution principle, states that a child should be substitutable for its parent, not just in the sense of providing the same methods, but in the sense of behaving in a way that is consistent with the parent's promises, so that code written for the parent works correctly with any child, without needing to know which child it is dealing with. Violating that principle, by overriding a method to do something completely different, or to raise an exception where the parent would succeed, or to require different arguments, breaks substitutability, and it causes bugs in code that treats children as parents, which is a common pattern in polymorphic programs.

A related guideline is to override only when the child's behaviour genuinely differs, and to call the parent method when the child's behaviour extends, rather than replaces, the parent's, as discussed for super(). Overriding a method merely to duplicate the parent's implementation, with a small change, is a sign that the method should be refactored, perhaps by extracting the varying part into a separate method that children override, while the common part remains in the parent, a pattern that keeps the parent's logic in one place, while allowing children to vary only the part that needs to vary. That refactoring, from duplication to extension, is a common improvement in hierarchies, and it is driven by noticing that several children override the same method in similar ways, with only a small difference, which suggests that the difference should be isolated, rather than repeated.

Finally, overriding should be documented, by noting in the child's method docstring that it overrides a parent method, and by explaining how its behaviour differs, so that readers who know the parent's method can understand the child's specialisation without comparing implementations line by line. That documentation, like other documentation, helps maintainers, who need to know whether a change to the parent method will affect children, and whether a change to a child method will break substitutability, which are questions that arise whenever a hierarchy evolves. A hierarchy whose overriding is documented is easier to maintain than one where overriding is implicit and must be discovered by searching for method names, because documentation makes the hierarchy's structure visible, rather than hidden in code.

class Shape:
    def area(self):
        return 0
class Square(Shape):
    def __init__(self, side):
        self.side = side
    def area(self):
        return self.side * self.side
print(Square(4).area())

Section 4

Composition is often preferred by experienced programmers, by default, with inheritance used only when the is-a relationship is clear, stable, and genuinely requires substitutability, because composition is more modular: each part can be developed, tested, and changed independently, and the containing class can use different parts in different situations, without needing a new subclass for each combination. For example, a car that composes an engine can use a petrol engine, a diesel engine, or an electric motor, by containing a different engine object, while a car that inherits from an engine would need a separate subclass for each engine type, and would be locked into that engine type by its place in the hierarchy, which is less flexible and harder to maintain as new engine types are added. That flexibility, through composition, is why many design guidelines recommend favouring composition over inheritance, not as a ban on inheritance, but as a default that should be departed from only when inheritance's specific benefits, substitutability and shared interface, are genuinely needed.

Composition also makes testing easier, because a containing class can be tested with mock or simple contained objects, that simulate the real ones, without needing to create the full hierarchy, whereas a child class in an inheritance hierarchy cannot easily be tested without its parent, because its behaviour depends on the parent's implementation, which must be understood and set up for the test. That testability, like modularity, is a practical benefit that matters in real programs, where tests must be fast, focused, and independent, and where a class that can be tested in isolation, with simple collaborators, is easier to verify than one that is entangled in a hierarchy. Composition, therefore, is not just a design preference; it is a testing strategy, that keeps classes independent and testable.

For beginners, the practical lesson is to ask, for each relationship between classes, whether it is is-a or has-a, and to choose inheritance for is-a, composition for has-a, and to be suspicious of a relationship that is neither, or that is both, because such a relationship may indicate a modelling error, where two concepts have been conflated, or where a class is trying to do too much. That question, is-a or has-a, asked consistently, will guide you to the right choice in most cases, and it will prevent the most common inheritance mistakes, such as inheriting to reuse code when composition would be clearer, or composing when inheritance would provide a needed substitutability, because the question forces you to think about the relationship's meaning, not just about code reuse, which is a secondary benefit, not the primary criterion for choosing between inheritance and composition.

class Engine:
    def start(self):
        return "engine started"
class Car:
    def __init__(self):
        self.engine = Engine()
    def start(self):
        return self.engine.start()
print(Car().start())

Section 5

Polymorphism through inheritance is explicit: children inherit a parent's interface, and they override methods to provide their own implementations, with the guarantee, if the Liskov principle is respected, that they will behave consistently with the parent, so that code written for the parent will work with any child. Polymorphism through duck typing is implicit: classes that happen to provide the same methods can be used interchangeably, without a common parent, because Python checks for methods at call time, rather than requiring a declared relationship, which is more flexible, because it allows unrelated classes to be used together, but also riskier, because there is no guarantee that a class providing a method with the right name will behave consistently with other classes that provide the same method, unless that consistency is documented and tested. Both forms are used in Python, and understanding their trade-offs, explicit guarantee versus flexible coincidence, helps you choose the right form for a given situation, and helps you write code that is robust to new classes, whether they arrive through inheritance or through duck typing.

A common use of polymorphism is in collections of heterogeneous objects, such as a list containing dogs, cats, and birds, all of which provide speak, where a loop can call speak on each, without checking its type, and each will respond appropriately, which is far cleaner than a loop that checks types and calls different methods for each type, with a growing chain of conditions that must be updated for every new type added. That loop, written polymorphically, is open to extension, because adding a new animal type requires only defining its class, with its speak method, and adding it to the list, without changing the loop, which is a practical benefit that grows as the number of types grows, and which is a reason why polymorphism is considered a core principle of object-oriented design, not just a theoretical idea.

For beginners, the lesson is to write code that relies on interfaces, not on types, where possible, by calling methods that objects provide, rather than checking their class and branching, because that code will be more flexible, more concise, and easier to extend, and it will work with both inherited and duck-typed polymorphism, without needing to know which form is being used. That interface-based style, sometimes called programming to an interface, is a habit that develops with practice, and it is reinforced by designing classes with clear, consistent interfaces, as discussed in the previous chapter, because a clear interface is what makes polymorphic code possible, by giving different classes a common set of methods that callers can rely on, regardless of the specific class involved.

Section 6

Abstract base classes are useful when a hierarchy has a common interface, but no meaningful default implementation for some methods, such as a Shape class with an abstract area method, where each specific shape, such as a square or a circle, must compute its area differently, and where a generic Shape has no area to compute, because it is not a specific shape, but a concept that groups specific shapes. Defining area as abstract, therefore, expresses that every shape must have an area, without pretending that a generic shape has one, and it forces each subclass author to think about area for their specific shape, rather than inheriting a meaningless default, such as returning zero, which might be mistaken for a correct area, or might hide a forgotten implementation. That forcing, through abstraction, is a form of design by contract, where the base class specifies what subclasses must do, without specifying how, leaving the how to each subclass, which is appropriate when the how varies by subclass, but the what is common to all.

Abstract base classes should be used sparingly, for interfaces that are genuinely shared and that have required methods, rather than for every parent class, because they add complexity, by requiring subclasses to implement methods, and because they can make a hierarchy rigid, where a subclass that wants to reuse most of a parent's behaviour, but not all of it, is forced to implement a method it does not need, or to provide a stub that raises an error, which is awkward. A parent class with concrete methods, that subclasses can override when needed, is more flexible, and it is the right choice when a default implementation is meaningful, or when subclasses may not need to override every method. Abstract methods are for the case where a default would be meaningless or misleading, and where forcing implementation is better than allowing a meaningless default to be inherited silently.

For beginners, abstract base classes are a concept to recognise, rather than a tool to use frequently, because most learning hierarchies can be expressed with concrete parent classes, where methods have defaults or where subclasses override as needed, without needing the enforcement of abstraction. Knowing that abstraction exists, and recognising it in libraries, where interfaces are often defined as abstract base classes, will help you read those libraries, by showing you which methods you must implement when you subclass, and which methods you may inherit, which is information that is essential for using a library correctly, even if you do not define abstract classes yourself in your own programs yet. As your programs grow, and your hierarchies become more formal, abstraction will become a natural tool, for defining interfaces that must be implemented, rather than merely suggested.

from abc import ABC, abstractmethod
class Shape(ABC):
    @abstractmethod
    def area(self):
        pass
class Square(Shape):
    def __init__(self, side):
        self.side = side
    def area(self):
        return self.side * self.side
print(Square(3).area())

Section 7

Multiple inheritance should therefore be used sparingly, and only when the parents are truly independent, with little overlap in their methods, and when the child's relationship to each parent is a genuine is-a relationship, not merely a desire to reuse code from two places, because code reuse through multiple inheritance creates a tangled hierarchy that is hard to understand, hard to test, and hard to maintain, as changes to either parent can affect the child in ways that are not obvious from the child's definition alone. A common alternative, for combining independent aspects, is composition, where a class contains objects for each aspect, rather than inheriting from both, which is clearer, because the contained objects are explicit attributes, with their own interfaces, rather than implicit parents whose methods are merged into the child's namespace, where they can conflict or be shadowed without warning. Composition, in the multiple-inheritance case, is often the clearer choice, because it makes the combination explicit, rather than hiding it in a hierarchy.

When multiple inheritance is used, it is often in the form of mixins, which are small classes that provide a specific, focused set of methods, such as a Loggable mixin that adds logging, or a Serializable mixin that adds conversion to a dictionary, and that are designed to be combined with other classes, rather than to stand alone as a complete entity. Mixins are typically placed after the main parent in the inheritance list, and they are designed to be cooperative, using super() to chain their methods with other mixins and with the main parent, so that several mixins can be combined in a predictable way, each adding its behaviour without conflicting with the others. That cooperative design, through super(), is what makes mixins workable, despite the complexity of multiple inheritance, because it ensures that each mixin's method is called in turn, in MRO order, rather than one mixin shadowing another entirely, which would lose behaviour.

For beginners, the lesson is to avoid multiple inheritance in your own programs, except for simple, well-understood cases, such as combining a main class with a small, focused mixin, and to prefer composition for combining independent aspects, because composition is easier to understand and to debug, and because multiple inheritance's complexity, through MRO and method conflicts, is a common source of bugs that are hard to diagnose, especially for programmers who are still learning single inheritance. Recognising multiple inheritance in libraries, where it is sometimes used for mixins, will help you read those libraries, but you do not need to use it yourself to write good programs, and many good programs use only single inheritance, or no inheritance at all, relying on composition for reuse, which is a perfectly valid and often superior design.

Section 8

You can inspect a class's MRO by accessing its __mro__ attribute, or by calling its mro() method, which returns a tuple or a list of classes in search order, and that inspection is a useful debugging tool, when a method call does not behave as expected, because it shows exactly which classes will be searched, in which order, and therefore which method definition will be found first. A common debugging step, when a method from an unexpected parent is called, is to print the MRO and to check whether the parent order is as intended, or whether a mixin or a parent has been listed in the wrong order, causing its method to shadow another's, which is a mistake that is easy to make and hard to spot without inspecting the MRO, because the class definition alone does not make the search order obvious, especially in a deep hierarchy with several parents at each level.

The MRO also explains how super() works, because super() does not call the immediate parent directly, but calls the next method in the MRO, after the current class, which, in a cooperative multiple inheritance hierarchy, allows each class in the chain to contribute its behaviour, in turn, rather than only the immediate parent contributing, and the chain ending there. That cooperative chaining, through super(), is what makes mixins work, as discussed earlier, because each mixin's method calls super() to invoke the next mixin's method, and so on, until the main parent's method is reached, with each layer adding its behaviour, in a predictable order, determined by the MRO. Without understanding the MRO, super() in a multiple inheritance hierarchy can seem mysterious, because it does not always call the class you think of as the parent, but with the MRO in mind, its behaviour becomes predictable, as the next class in a well-defined order.

For beginners, the practical lesson is to keep hierarchies simple, so that the MRO is intuitive, to inspect the MRO when behaviour is surprising, and to use super() consistently, so that cooperative chaining works, even in simple hierarchies, where it may seem unnecessary, because that consistency prepares the code for future complexity, and because it expresses the intent to call the next method in the hierarchy, rather than a specific parent, which is more accurate and more maintainable, as discussed earlier. A simple hierarchy, with a clear MRO, is a hierarchy that is easy to understand, easy to test, and easy to maintain, which is the goal of good inheritance design, whether single or multiple, and keeping hierarchies simple is the best way to ensure that the MRO remains a helpful tool, rather than a source of confusion.

Section 9

Inheritance can lead to a problem known as the fragile base class problem, where a change to a parent class, even a seemingly harmless one, such as adding a new method, changing a method's implementation, or renaming an internal attribute, breaks a child class that depended on the parent's old behaviour, in a way that the parent author did not anticipate, because the child relied on details that were not part of the parent's documented interface, but that happened to work with the old implementation. That fragility arises because inheritance creates a tight coupling between parent and child, where the child depends not just on the parent's public interface, but also, in practice, on its implementation details, such as the order in which methods are called, the attributes it sets, or the methods it uses internally, which the parent author may change without realising that a child depends on them, because those dependencies are not visible in the parent's code, but in the child's code, which the parent author may not have seen.

Composition, by contrast, is less vulnerable to the fragile base class problem, because a containing class depends only on the contained object's public interface, not on its implementation, and because the contained object can be replaced with another object that provides the same interface, without affecting the containing class, as long as the interface remains stable, which is a weaker coupling than inheritance, where the child depends on the parent's implementation in many subtle ways. That weaker coupling is a major reason why composition is often preferred, as discussed earlier, because it allows parts to evolve independently, without the risk that a change to one part will break another in an unexpected way, which is a property that becomes more important as a program grows, and as more classes depend on each other, because the cost of a fragile change grows with the number of dependents.

For beginners, the lesson is to be aware of the fragile base class problem, to design parent classes with stable, documented interfaces, to avoid relying on parent implementation details in child classes, and to prefer composition when the relationship does not genuinely require inheritance's substitutability, because those practices reduce fragility, even if they do not eliminate it entirely, and they make hierarchies more maintainable over time. Awareness of fragility, like awareness of other inheritance pitfalls, does not mean avoiding inheritance altogether, but means using it with eyes open, understanding its costs as well as its benefits, and choosing it only when its benefits, reuse and substitutability, outweigh its costs, tight coupling and fragility, for the specific relationship in question.

Section 10

Designing a hierarchy starts with identifying the general concept, the parent, and the specific concepts, the children, and with deciding what behaviour belongs at each level, so that common behaviour is in the parent, and specific behaviour is in the children, with no duplication and no behaviour in a level where it does not belong. That decision, about placement, is the core of hierarchy design, and it should be guided by asking, for each method, whether it applies to all children, in which case it belongs in the parent, or only to some children, in which case it belongs in those children, or to a intermediate parent that groups those children, if such a grouping is meaningful.

Hierarchy design also involves deciding how deep the hierarchy should be, with a general guideline to keep it shallow, typically no more than two or three levels, because deeper hierarchies become hard to understand, hard to test, and hard to maintain, as each level adds a layer of indirection, and as a method call may traverse many levels before finding its implementation, making it hard to predict which method will be called, and hard to debug when the wrong method is called. A shallow hierarchy, with a parent and its immediate children, is easy to understand, because the relationship between parent and child is direct, and the method resolution is simple, while a deep hierarchy, with many intermediate levels, each adding a small refinement, may be more precise in modelling a domain, but it pays for that precision with complexity, which often outweighs the benefit, especially when the intermediate levels do not correspond to meaningful domain concepts, but are merely organisational conveniences.

A third hierarchy design consideration is whether to use inheritance at all, versus composition, for a given relationship, as discussed throughout this chapter, and that decision should be revisited as a hierarchy evolves, because a relationship that started as inheritance, when it seemed like a kind-of relationship, may turn out, as the program grows, to be better modelled as composition, when the child needs to change its parent-like behaviour dynamically, or when it needs to combine behaviours from several sources, which inheritance cannot do cleanly, without multiple inheritance's complexity.

Finally, hierarchy design, like other design, is iterative, and your first hierarchy will rarely be perfect, so you should expect to refactor it, by moving methods between levels, by splitting a parent, by merging children, or by replacing inheritance with composition, as you learn more about the domain and about how the hierarchy is actually used, rather than how you imagined it would be used. That iteration, driven by real use and by testing, is how good hierarchies emerge, not through perfect initial design, but through continuous improvement, guided by principles such as shallow depth, clear placement, and genuine kind-of relationships, which you can apply at each iteration, to judge whether the hierarchy is improving or becoming more complex without benefit. Embracing iteration, as with other design, is what allows a hierarchy to remain useful as a program grows, rather than becoming a liability that constrains it.

Section 11

Dependency injection also makes testing easier, because a containing class can be tested with a simple, fake part, that records calls or returns known values, without needing the real part, which may be complex, slow, or dependent on external resources. A library class tested with a fake book, for example, can be checked for its collection logic, without needing real books with full data, and a car class tested with a fake engine can be checked for its start logic, without needing a real engine. That testability, through injection, is a major benefit of composition, and it is a reason why many experienced programmers design classes to receive their collaborators as arguments, rather than creating them internally, even when the collaborators are not variable in production, because the testability benefit alone justifies the extra argument, and because it makes the class's dependencies explicit, visible in its constructor signature, rather than hidden inside its implementation.

A containing class should delegate to its parts, rather than duplicating their logic, by calling their methods and using their results, so that each part remains responsible for its own behaviour, and the containing class remains responsible for coordination, such as deciding which part to call, in what order, and how to combine their results. That delegation, where a library's list_available method calls each book's is_available method, rather than checking book attributes directly, preserves encapsulation, because the library does not need to know how availability is determined, only that each book can answer whether it is available, and it allows the book's availability logic to change, without changing the library, as long as its method interface remains stable. Delegation, therefore, is not just a coding pattern; it is a way of respecting boundaries between classes, so that each class can evolve independently, as long as its interface is preserved.

Finally, composition can be nested, with a class containing objects that themselves contain objects, forming a tree of parts, such as a library containing shelves, each containing books, or a car containing an engine, which contains pistons, and that nesting can continue to any depth, as the domain requires, without the complexity of a deep inheritance hierarchy, because each level is a simple has-a relationship, with a clear owner and a clear part, rather than a kind-of relationship that must satisfy substitutability at every level. That nesting, through composition, is how complex systems are built from simple parts, in programming as in engineering, by combining parts into larger assemblies, which can themselves be parts of even larger assemblies, with each assembly tested and understood in isolation, before being combined, which is a scalable way to build complexity without losing clarity.

Section 12

A more subtle issue is method shadowing, where a child defines a method with the same name as a parent method, but with a different signature, such as different arguments, which breaks substitutability, because code that calls the method through a parent reference, with parent arguments, will fail when given a child, or will behave unexpectedly, because the child's method expects different arguments. That signature change is a common inheritance mistake, often made when a child needs extra information that the parent method did not require, and the remedy is usually to add the extra information as an optional argument, with a default, so that the child's method remains compatible with the parent's signature, while also accepting the extra argument when it is provided, or to add a new method for the child's specific behaviour, rather than changing the parent method's signature. That compatibility, in signatures as in behaviour, is part of the Liskov principle, and it should be checked whenever a method is overridden, by comparing its signature with the parent's, and ensuring that it accepts at least the parent's arguments, and returns a compatible kind of value.

Another subtlety is that a child class inherits not just public methods, but also private-by-convention attributes and methods, those with a leading underscore, which are intended for internal use by the parent, and which a child should generally not rely on, or override, unless it is designed to do so, because those internals may change in a future version of the parent, breaking the child in the fragile base class way discussed earlier. A child that accesses a parent's underscore attribute directly, or that overrides an underscore method, is depending on an implementation detail, not on a public interface, and that dependency should be avoided, unless the parent explicitly documents that attribute or method as intended for subclass use, in which case it is effectively part of the subclass interface, even if it is marked private for external callers. That distinction, between public interface, subclass interface, and internal implementation, is a refinement of encapsulation for hierarchies, and it helps both parent and child authors know what is safe to rely on, and what may change.

For beginners, the practical lesson is to treat parent attributes and methods as a contract, to shadow only intentionally, with documentation, to keep overridden method signatures compatible, and to avoid relying on underscore internals, unless they are documented for subclass use, because those habits will make your hierarchies more robust, even if they seem like extra care in simple cases, where the parent and child are written by the same person, and where the risks seem low. That care pays off when the parent is later changed, or when the child is used by someone else, who expects the contract to hold, and who will be surprised if it does not, which is the same reason why all interface contracts, not just inheritance contracts, deserve careful attention in program design.

Extracting a parent should be done carefully, by first identifying exactly what is shared, and what differs, and by ensuring that the extracted parent represents a genuine general concept, not merely a container for shared code, because a parent that is not a meaningful concept, but only a code-sharing device, will create a confusing hierarchy, where children inherit from a parent that does not make sense as a kind-of relationship, and where future readers will struggle to understand why the hierarchy exists, or what the parent means in domain terms. A parent method sometimes calls another method that a child overrides. Wrapping is a form of composition in which one object holds another object and adds behaviour around it, so callers talk to the outer wrapper while the wrapper passes the real work on to the inner object. Logging is a clear example, because a logging wrapper can print a message before a save, call the storage object to do the actual saving, and then report that the save has finished, all without changing the storage class itself. This separation keeps each class focused on one job, since the storage class stays concerned only with storage and the logging class stays concerned only with logging, and each class can therefore be tested and changed on its own.

Wrapping also differs from inheritance in a way that matters for runtime flexibility. Inheritance fixes behaviour when a class is defined, so every instance of a subclass receives the same added behaviour whether it needs it or not. Wrapping can instead be applied to a single object after that object has been created, leaving other objects of the same class unwrapped. That choice can depend on configuration or on data that is only known while the program runs. Consider a program that saves files where most saves need no log entry but a few sensitive saves need a full audit trail. With inheritance you would need a separate subclass for logged saves, while with wrapping you can start with a plain storage object and wrap it only when a sensitive save is required.

Wrapping does have a cost that should be weighed before it is used. The wrapper must offer the same interface as the wrapped object. If the wrapped object gains a new method then the wrapper may need a matching method, or callers will be unable to reach the new method through the wrapper. This maintenance work is the price of the extra layer, and it is worth paying only when the added behaviour is genuinely useful for selected objects rather than for every object of a class.

The example below shows a logging wrapper around a simple storage class. The wrapper prints a message, delegates the save to the wrapped object, and returns whatever the wrapped object returns, so the caller sees the same result as before with a log message added as a side benefit.

class Storage:
    def save(self, item):
        return f"saved {item}"

class Logger:
    def __init__(self, wrapped):
        self.wrapped = wrapped
    def save(self, item):
        print("saving", item)
        return self.wrapped.save(item)

plain = Storage()
logged = Logger(plain)
print(logged.save("task"))
print(plain.save("task"))

Notice the contrast between the two calls at the end of the example. The wrapped call prints a log message first, while the plain call does not, yet both calls save the item in exactly the same way. That contrast is the whole point of wrapping, because behaviour is added to one object without changing its class and without affecting other objects of the same class. Used with care, this pattern keeps classes small and focused, and it makes added behaviour easy to add, easy to remove, and easy to test in isolation.

Section 36

A parent class designed for extension serves three different audiences, and each audience needs a different level of access to the class. The first audience is external callers, who use the public interface to get work done and who should not need to know how the parent works inside. The second audience is subclass authors, who extend the parent to create new behaviour and who need hooks they can override plus helpers they can call from their own methods. The third audience is the parent class itself, which uses internal details to implement its own methods and which must be free to change those details when its implementation improves.

If these three levels are not kept distinct then problems follow, because a subclass author may rely on an internal method by accident and that method may later change or disappear. The subclass then breaks even though the public interface stayed the same, and the parent author may not even know that the subclass existed, so the breakage feels unfair to both sides. A distinct subclass interface prevents that confusion by naming the methods that subclasses may override, naming the methods that subclasses may call, and stating what each hook is for and what value it must return.

Naming helps with this distinction but it is not enough on its own. A leading underscore often marks a method as private, yet in a parent class that mark can be ambiguous, because it might mean internal only or it might mean intended for subclass use. A reader cannot tell which meaning applies from the underscore alone, so documentation must resolve the ambiguity by stating plainly whether a method is for subclasses or is internal only. Without that note a subclass author might avoid a useful hook and duplicate its logic, or might use a purely internal method and break when it changes.

A common design that makes the subclass interface concrete is the template method pattern. In this pattern a public method defines the overall steps of an operation and calls a hook at the point where behaviour may vary, while subclasses override only the hook rather than copying the whole template method. This keeps the overall flow in one place, limits what a subclass can change, and protects the invariants of the parent, and that limit is a feature rather than a flaw because it channels extension through defined points.

class Base:
    def _hook(self):
        return "hook"
    def run(self):
        return self._hook()

class Child(Base):
    def _hook(self):
        return "child hook"

print(Base().run())
print(Child().run())

In this example the hook is marked with an underscore, yet its role still needs documentation in a real project, because the docstring should state that subclasses may override it and what value it must return. Without that note a reader might treat it as purely internal, while with that note the subclass interface becomes explicit and safe to use. For beginners this distinction may look like an advanced detail, but it is really a natural extension of public versus private, since hierarchies add a third audience that needs its own interface. Clear documentation for that interface makes both extension and change safer, because both sides benefit from a boundary that is written down rather than guessed.

Section 37

A parent class can define a plugin interface: the methods every plugin must implement, plus any common behaviour plugins can reuse. The main program then discovers plugin subclasses and uses them polymorphically through the parent interface, without knowing each plugin's specific class in advance. New plugins can be added simply by defining a new subclass, without changing the main program, as long as they implement the interface correctly. That extensibility is the main benefit of a plugin system, and it grows as more plugins are added by different authors at different times.

For that to work, the plugin interface must be stable, documented, and tested. If the interface is unclear, new plugin authors will guess at what they must implement and may write plugins that fail in subtle ways. A good test is to write a sample plugin using only the parent's documentation, without reading the main program's code. If that sample is straightforward, the interface is clear; if it requires guesswork or workarounds, the interface should be simplified before real plugins are built on it.

The parent should also keep its helper behaviour minimal. A plugin parent that provides too much shared behaviour, or behaviour that conflicts with a plugin's specific needs, will discourage new plugins rather than encourage them. The parent is both a contract, stating what plugins must do, and a helper, providing what they can reuse, and those two roles should be balanced so the contract stays simple while the helper stays genuinely useful.

Plugin systems show inheritance used for extensibility rather than mere code reuse. The purpose is not just to share implementation, but to allow third parties to extend a program without modifying its core. That purpose should guide the design: keep the interface small, document it well, and test it with a sample plugin before relying on it.

class Plugin:
    def run(self):
        raise NotImplementedError
class MyPlugin(Plugin):
    def run(self):
        return "plugin ran"
print(MyPlugin().run())

A plugin interface should also provide a way to discover plugins and to report failures when a plugin does not implement the interface correctly. Discovery might be by scanning a folder, by importing named modules, or by registering subclasses explicitly, and each method has trade-offs in explicitness and in ease of use. Failure reporting matters just as much: a plugin that fails to implement a required method should produce a clear error at load time, naming the plugin and the missing method, rather than failing later, in the middle of a run, when the missing method is finally called, because early, clear failure saves debugging time and prevents a faulty plugin from corrupting a run. Clear discovery and clear failure reporting together make a plugin system welcoming to new authors, rather than frustrating.

Section 38

Composition can forward many methods from a container to a contained object. Writing each forwarding method by hand is tedious when the contained interface is large, but it has a major advantage: the container's interface is explicit. A reader can see, in the container's code, exactly which methods it provides, what arguments they take, and what added behaviour, such as logging or validation, each one performs. That explicitness makes the container easier to understand, document, and test.

Python offers an automatic alternative through __getattr__, which is called when an attribute lookup fails. A container can use it to delegate unknown attributes to the contained object dynamically, without defining each method. That creates a transparent wrapper whose interface appears to match the contained object's, plus the container's own methods. It is convenient, especially when the contained interface is large or changes often, because the wrapper need not be updated for each new method.

The cost is clarity. With automatic forwarding, the container's interface is implicit: it cannot be seen in its definition, and must be inferred from the contained object's interface and the __getattr__ implementation. Readers will wonder where a method comes from when they see it called on the container but cannot find it in its code. Documentation generators and type checkers also struggle with dynamic interfaces, which makes the wrapper harder to work with in larger projects.

For most programs, explicit forwarding is the better choice, even though it requires writing a few extra methods. Those methods make the interface visible and therefore understandable. Reserve __getattr__ forwarding for cases where the contained interface is large or dynamic and explicit forwarding would be impractical, and document the forwarding clearly when you do use it.

class Wrapper:
    def __init__(self, wrapped):
        self._wrapped = wrapped
    def __getattr__(self, name):
        return getattr(self._wrapped, name)

Automatic forwarding also interacts with special methods, which Python looks up on the class, not on the instance, and therefore does not route through __getattr__ in the same way as ordinary methods. A wrapper that relies on __getattr__ may therefore fail to forward special methods such as iteration or length, even though it forwards ordinary methods correctly, which is a surprising inconsistency that can cause bugs when a wrapped object is used in a context that expects those protocols. Explicit forwarding, or explicitly defining the special methods on the wrapper, avoids that inconsistency, because each protocol method is visible in the wrapper's definition and can be tested directly. That special-method gap is a good reason to test a wrapper thoroughly with the same operations, including iteration and length, that you expect callers to use, rather than only with ordinary method calls. Explicit forwarding also makes it easier to add logging or validation to a single method without affecting others, because each method is a separate place where that added behaviour can be inserted.

Section 39

Serialisation, converting an object to bytes for storage or transmission and reconstructing it later, adds complications for hierarchies and shared objects. An object's class, its attributes, and its relationships must all survive the round trip, so that the reconstructed object behaves like the original. Inheritance complicates this because a child's attributes include those inherited from its parent, and all of them must be captured in the correct form. Composition complicates it because a contained object may be shared between several containers, and pickling must preserve that sharing rather than creating a separate copy for each container, which would break the sharing that the program relied on.

Those issues are easy to overlook in programs tested only in memory. A class design that works perfectly while objects are alive may fail, or behave incorrectly, when its objects are saved and loaded, because a shared object becomes duplicated or a hierarchy attribute is lost. The remedy is to test persistence explicitly: round-trip objects through pickling or another format and check that reconstructed objects have the same attributes, the same relationships, and the same sharing where sharing matters.

For most learning programs, the standard library's pickling will handle ordinary classes correctly, and you do not need custom serialisation code. The lesson is simply to be aware that persistence is part of a class's lifecycle, not an afterthought. When you design classes that will be saved, think about which attributes must be preserved, whether shared objects must stay shared, and whether a version marker is needed so old saved data can still be loaded after the class changes.

That awareness, tested with a round trip, prevents a class of bugs that only appear after a program restarts and reloads its data, which is often the worst time to discover them.

import pickle
class Book:
    def __init__(self, title):
        self.title = title
data = pickle.dumps(Book("Dune"))
print(pickle.loads(data).title)

Versioning is another serialisation concern: a class that gains a new attribute in a later version must still be able to load data saved by the earlier version, by filling in a sensible default for the missing attribute, and it must handle data that contains an attribute it no longer uses, by ignoring it rather than failing. That tolerance, like tolerance in file loading, makes persistence robust across program updates, which is essential for user data that should not be lost when a program is upgraded. Without it, every class change risks breaking every saved file, which is a cost users should not have to pay for an improvement they did not ask to lose data over. Testing a round trip after every class change that affects saved data is a small habit that protects users from silent data loss.

Section 40

When you must choose between inheritance and composition the most important question is simple, and it should be asked before any code is written. Is the new class a kind of the old class, or does it merely use one? That question is more useful than asking which pattern saves more code, because code reuse alone is a weak reason to choose either pattern and meaning should come first, with structure following meaning. A true is-a relationship means the new class can stand in for the old class everywhere. A savings account is a kind of bank account and an ebook is a kind of book, and code written for the general class should work with the specific class without special cases or type checks.

A has-a relationship means the new class contains or uses another object, so a car has an engine and a library has books, yet neither pair is an is-a relationship. A car is not a kind of engine and a library is not a kind of book, so modelling a has-a relationship with inheritance creates a false claim that one thing is another thing when it is not. That false claim will cause trouble later, because methods will be inherited that make no sense for the child and callers will be misled about what the object can actually do.

The practical way to apply the question is to test substitution with a concrete example. Imagine a real use of the parent class, then try the child in its place, and watch for surprises in behaviour, in meaning, or in the methods that become available. If the result is correct and unsurprising then inheritance is worth considering, but if the result is confusing or wrong then composition is the better choice. This test also helps when a class needs most of a parent behaviour but not all of it. Needing most of the behaviour is not enough, and if it needs only part of the behaviour then it probably uses the parent rather than being one.

Composition also keeps future change easier in doubtful cases, because a composed part can be swapped for a different part, tested on its own, and reused by other classes without a hierarchy. Inheritance locks the child into the parent family, which is fine when the family is stable and the meaning is clear, but becomes a burden when the family grows or changes direction.

class Animal:
    def speak(self):
        return "..."

class Dog(Animal):
    def speak(self):
        return "Woof"

class Library:
    def __init__(self, books):
        self.books = books

print(Dog().speak())
print(len(Library(["Dune"]).books))

The example above shows both patterns side by side in a compact form. A dog inherits from an animal because a dog is an animal, while a library contains books rather than inheriting from them, because a library is not a book. Return to this question whenever a design feels awkward, because awkwardness often signals a mismatch between meaning and structure. A class that inherits methods it never uses, a class that fights its parent, or a class that needs a different parent at runtime are all warning signs. In each case asking again whether the relationship is is-a or has-a can guide the refactor.

When a hierarchy is used with type hints, which are covered in a later chapter, a child type is considered compatible with a parent type. A function annotated to accept a parent can also accept a child, mirroring runtime substitutability. A function annotated to accept a child cannot accept a general parent, because the parent may not provide the child's specific methods. That static compatibility mirrors the runtime rule, and a well-designed hierarchy will usually type-check cleanly as well as run correctly.

Type checking, however, only verifies interface compatibility, not behavioural compatibility. A child may keep the same method signatures while changing a method's meaning, and a type checker will not detect that. Behavioural compatibility, the deeper requirement of the Liskov principle, must still be verified through tests that check results, not just types. Type hints are therefore a useful complement to testing, not a replacement for it.

Type hints also interact with composition. A containing class that receives a part as an argument can annotate that argument with the part's type, or better, with a protocol describing only the methods it needs. That is more flexible, because it allows any object providing those methods, including simple test doubles, to be used as the part, without requiring it to inherit from a specific parent. Annotating with the most general type that still provides the needed methods keeps the class reusable.

The guideline is the same as for runtime design: describe only what you need, and no more. A specific type annotation that is unnecessarily restrictive can force callers to inherit from an arbitrary parent merely to satisfy the annotation, which is a form of coupling that composition is meant to avoid. General, protocol-based annotations preserve flexibility while still giving readers and checkers useful information.

class Book:
    def __init__(self, title):
        self.title = title
class Library:
    def __init__(self, books):
        self.books = books
print(len(Library([Book("Dune")]).books))

Type annotations for hierarchies also help readers, because they make the expected relationship explicit in a signature, rather than leaving it to be inferred from method calls or from documentation alone. A reader who sees a parameter annotated with a parent type knows immediately that any child is acceptable, while a reader who sees a child type knows that only that specific kind, or its own children, will do. That explicitness in signatures is a powerful form of documentation that is checked automatically, which makes it more reliable than prose alone, even though it does not replace behavioural tests, which remain necessary to verify that a child actually behaves like its parent in practice, not just in type, and not just in theory, in real programs, every day. Type annotations also make refactoring safer, because a checker will flag places where a changed parent type no longer matches its children.

A hierarchy's evolution can be managed by versioning its interface. A new version of a parent class, with new methods or changed behaviour, can be introduced alongside the old version, or with a deprecation period during which old methods continue to work but warn that they will be removed. That gives child authors and callers time to update, rather than breaking them immediately with a sudden change. That courtesy is especially important for a parent used by many children or by external code, where a sudden break would affect many programs at once.

A gradual transition, with warnings and documentation of what has changed and how to update, is far more helpful than a sudden break that forces immediate updates under pressure. Some users cannot update immediately, due to time, resources, or dependencies on other code that has not yet updated. Deprecation gives them a timeline and a plan, which reduces fear of updating and encourages adoption of new versions, because updates become predictable rather than disruptive.

Versioning also requires deciding, for each change, whether it is breaking or not. A breaking change requires callers or child authors to update their code, such as removing a method, changing a signature, or changing behaviour in a way that affects results. A non-breaking change adds a new method, or adds an optional argument with a default that preserves old behaviour, while providing new capabilities for new callers. That distinction should be made deliberately for each change, by asking whether old code will still work without modification.

That discipline requires thinking about compatibility from users' perspectives, not just from the author's. A change that seems small, or that does not affect the parent's own tests, may still break child uses that the author did not anticipate. Testing with representative children and callers, and documenting each change as breaking or non-breaking in release notes, helps users judge whether they need to update and how urgently, which maintains trust in a shared hierarchy over time.

        self.title = title
print(Book("Dune").title)

Deprecation warnings should also be visible in a way that users cannot easily miss, such as through warnings that appear when deprecated code is used, rather than only through release notes that users may not read. A warning at runtime, naming the deprecated method clearly and suggesting its replacement explicitly, reaches users at the moment they are affected, which is far more effective than a note in documentation that they may never open. That visibility, combined with a clear timeline and clear replacement guidance, turns deprecation from a passive note into an active guide, helping users update before removal actually breaks their code. A deprecation period should be long enough for users to plan, test, and deploy their updates without rushing.

When a hierarchy is used in a team, communication becomes as important as code. Different team members may work on different classes in the hierarchy at the same time, and may make changes that affect each other without realising it, unless they communicate through documentation, code reviews, and discussions about the hierarchy's design, its invariants, and its intended evolution. A change by one person, without communication, can break another person's work in a way that is hard to diagnose, because the breakage may not appear until the other person's code is run with the changed parent, and the cause may not be obvious from code that appears unchanged and correct in isolation.

That social aspect is often overlooked in technical discussions that focus on syntax and patterns, but it is essential in practice. A hierarchy is a shared structure that many people depend on and may change, and a change to it should be reviewed by child authors before it is merged, and discussed before it is implemented, so its impact can be assessed by those who will be affected. That process takes time, but it saves far more time than it costs, by preventing breakages that would otherwise require debugging and fixing after the fact, under pressure and with less information about the change that caused them.

Team communication also needs a shared vocabulary for discussing relationships, such as is-a, has-a, parent, child, override, and delegate, so team members can discuss a hierarchy without ambiguity about what they mean. Without agreed terms, a discussion about whether a relationship is is-a or has-a becomes a discussion about terminology, which wastes time and causes confusion. Agreeing on terms in advance, and using them consistently in code, documentation, and discussion, helps a team think clearly about design, because clear language leads to clear thinking.

That discipline applies to all technical communication, but it is especially important for hierarchies, where relationships are central and where ambiguous language about relationships can lead to ambiguous designs that are hard to understand and maintain. Clear, shared vocabulary is therefore part of good hierarchy design, not an optional extra.

Communication about hierarchies should also happen in code reviews, where a proposed parent change can be examined by child authors before it is merged, rather than after it has already broken their code. A review that includes the hierarchy's stakeholders, not just its author, is more likely to catch impacts that the author overlooked, because each stakeholder brings knowledge of how they use the hierarchy, which the author may not share. That collaborative review is therefore a practical safeguard, not just a social nicety, and it should be part of the workflow for any shared hierarchy.

A hierarchy can be visualised through diagrams that show classes as boxes and relationships as arrows, with inheritance arrows pointing from child to parent and composition arrows pointing from container to contained. That visibility is a benefit beyond mere presentation: it can actually improve design by making problems apparent that were previously hidden in code. When you finish designing a hierarchy, it is useful to review it against a checklist, by asking, for each class, whether its responsibility is clear and focused, whether its interface is small and consistent, whether its methods respect parent contracts, whether its relationships are genuinely is-a or has-a as modelled, whether its hierarchy is shallow, whether its documentation explains its place in the hierarchy, and whether its tests cover both individual behaviour and polymorphic use. That systematic review can catch design problems that a casual review might miss, where attention is drawn to the most salient aspect while other equally important aspects are ignored until they cause problems later, when they are harder to fix because the design has already been used in many places.

A checklist is especially valuable for hierarchies, where a problem in one class can affect many others through inheritance or composition, and where early detection is far cheaper than late detection after the problem has propagated to clients. A problem that is caught at its source, before it spreads, can be fixed once; a problem that spreads must be fixed in many places, and its symptoms may appear in client code far from the hierarchy itself, making diagnosis harder. Systematic review therefore prevents a diagnostic difficulty that is specific to hierarchies, where source and symptom can be far apart due to polymorphism hiding the source behind a general interface.

An author may be blind to problems in their own design due to familiarity with their intentions, which may not be clear to others who must use or maintain the hierarchy without sharing those intentions. A reviewer, reading the hierarchy as a new user would, can note where understanding breaks down or where documentation does not answer questions that arise. Those gaps should be filled before the hierarchy is released for shared use, rather than after users have already formed incorrect understandings that are hard to correct.

That peer review, combined with a checklist, turns review from a casual glance into a structured check that improves both clarity and correctness, which is essential for a hierarchy that will be used by others.

Section 46

A hierarchy's test suite should include tests for the parent class, for each child class, for polymorphic use, and for structural properties where structure is contractual. Those tests should be organised by class and by relationship, so that a failing test points clearly to the class or relationship that broke, rather than to the hierarchy as a whole. That organisation is especially valuable for hierarchies, where a failure in one class can cause failures in many others through inheritance. Without organisation, a single root cause can produce many failures, making it hard to tell which failure is the root and which are merely consequences.

A useful diagnostic strategy is to check parent tests before child tests. If parent tests fail and child tests fail in the same way, the pattern indicates a parent problem rather than many independent child problems. Fixing the parent first, then re-running child tests, will often clear the cascade. That pattern recognition is supported by organised tests and hindered by disorganised ones, which obscure the pattern among failures and can lead to wasted effort chasing consequences as if they were causes.

Test organisation should also include edge cases at each level, such as empty collections in a container class, invalid transitions in a stateful child, or missing methods in a plugin subclass. Edge cases at one level can affect other levels through inheritance or composition, and a hierarchy that passes happy-path tests at each level may still fail on edge cases that reveal inconsistencies between levels, such as a parent assuming a non-empty collection while a child allows an empty one. Edge-case tests surface those differing assumptions explicitly, so they can be made consistent or documented as intentional differences, rather than being discovered by accident in production where they are harder to diagnose and more costly to fix.

Planning test organisation alongside hierarchy design, rather than as an afterthought, keeps the suite useful for diagnosis as the hierarchy grows.

When a hierarchy is documented, its documentation should include a changelog, or history, of changes to its classes, methods, and relationships, so readers familiar with an older version can understand what has changed and how to update their code, without comparing old and new code line by line to find differences. Deprecation warnings in code, together with changelog entries stating clearly what is deprecated, why, and when it will be removed, give users fair warning and time to update, which is a reasonable approach to evolving shared code.

Section 48

A hierarchy can be used with data classes, which simplify class definition by generating methods such as __init__, __repr__, and __eq__ automatically from attribute declarations. That convenience can reduce boilerplate in simple classes, but it interacts with inheritance in ways that should be understood before using data classes in a hierarchy. A data class inheriting from another data class will generate methods based on its own attributes plus those inherited from its parent, in an order determined by the hierarchy and by the data class machinery, which can be surprising if the order is not as expected. If a parent is not a data class but a regular class, the child's generated methods may not include parent attributes correctly, or may fail to initialise them correctly through super().

That complexity arises from combining automatic generation with inheritance, and it should be considered when deciding whether to use data classes in a hierarchy or regular classes with manually written methods. Manual methods, while more verbose, are more explicit and easier to understand in a hierarchy, where the order of initialisation and the inclusion of attributes must be clear and predictable without relying on generation rules that may not be obvious to a reader unfamiliar with data class machinery. That clarity benefit should be weighed against the convenience of automatic generation, especially in hierarchies where clarity is already challenged by inheritance itself, and where adding generation on top can make a hierarchy even harder to understand.

That does not mean data classes should never be used in hierarchies. In a simple hierarchy of value objects, where each class adds a few attributes and where generation works predictably, data classes can be a clear and concise way to define the hierarchy without boilerplate. In a complex hierarchy with custom initialisation or non-trivial equality, manual methods may be clearer and safer than generation that would need to be overridden or customised in ways that negate its convenience.

The key is consistency: choose one approach for a hierarchy, document it, and follow it as the hierarchy grows, rather than mixing generated and manual styles ad hoc, which makes the system harder to predict and maintain.

Consistency in class definition style also helps tooling, because documentation generators, type checkers, and linters can work more reliably with a uniform style than with a mixture, where each class must be handled differently. A tool that understands data classes may not understand manual classes in the same way, and vice versa, leading to incomplete documentation or missed type errors for some classes in a hierarchy. Uniform style therefore improves not just human readability, but also the reliability of automated tools that support development.

Section 49

When you design a hierarchy, you should also consider its future, by asking how it might need to change as requirements evolve, as new kinds are added, as old kinds are removed, or as the domain itself changes. You cannot predict every future change in detail, but you can design for changeability, through shallow hierarchies, clear interfaces, documented invariants, and tests that make change safer and easier when it comes. That future-proofing does not require predicting the future; it requires making the present design easy to change in the future, which is a more achievable goal than prediction and one that should guide hierarchy design from the start.

Favouring simplicity over cleverness, clarity over conciseness, and flexibility through composition where appropriate over rigidity through deep inheritance are choices that make future change easier. A simple, clear, flexible hierarchy can be refactored to accommodate new requirements with less effort and less risk than a complex, clever, rigid hierarchy optimised for its current requirements at the expense of future changeability. That is a common design mistake: over-fitting to current needs, so the hierarchy becomes brittle when needs change, as they inevitably will in any real program that lives beyond its initial release.

Future-proofing also means avoiding premature optimisation for future kinds that may never be needed, such as creating intermediate parent classes for kinds that do not yet exist in the domain. That speculative design adds complexity without benefit and makes the hierarchy harder to understand for its current kinds, because readers must navigate through levels that serve no current purpose and may never serve a future one. A just-in-time approach is better: add structure only when a new kind actually arises and actually requires a new class or level, while keeping the current design easy to change when that happens.

That distinction, between designing for changeability and designing for predicted changes, is central to good design: the former is prudent and sustainable over time, the latter is speculative and wasteful in practice, and the former should be pursued while the latter is avoided.

class Book:
    def __init__(self, title):
        self.title = title
print(Book("Dune").title)

Changeability also depends on keeping a hierarchy's public interface stable, even as its internals evolve, because clients depend on the interface, not on internals, and a stable interface allows internals to change without breaking clients. That stability is achieved by distinguishing public methods, which should change rarely and only through deprecation, from internal methods, which can change freely, and by documenting that distinction clearly. A hierarchy with a stable public interface and flexible internals is changeable in the ways that matter, without being unstable for its users. Changeable designs also tend to be simpler designs, because simplicity leaves room for future adaptation without tangled dependencies.

Section 50

The final message of this chapter returns to the simple idea with which it began: inheritance is about is-a, and composition is about has-a, and choosing between them correctly for each relationship is the most important design skill in this chapter. That choice matters more than knowing the syntax of super(), the details of the method resolution order, or the specifics of abstract base classes or mixins, because those features are tools that serve the basic choice. Without that basic choice made correctly, the tools will be misapplied to relationships that do not fit them, leading to hierarchies that are confusing, fragile, and hard to maintain, regardless of how skilfully the tools themselves are used in isolation.

Design begins with understanding relationships in the domain and modelling them accurately in code, and tools and patterns are secondary to that understanding. That understanding should be developed first, through thinking about the domain in plain language, as discussed in the previous chapter for classes in general and here for relationships specifically. Asking, in words, whether one thing is a kind of another or has another as a part is the most reliable guide to choosing between inheritance and composition, and it should be applied before writing any code for a hierarchy, by discussing the relationship with colleagues or in a design note, and by checking whether the plain-language description matches the code you are about to write.

That cycle, of design, discussion, implementation, and review, should be repeated for each important relationship until its modelling is clear and its code is clear as a consequence. A mismatch between plain language and code will reveal itself as awkward client code, or as a hierarchy that is hard to extend or test, which are symptoms of a mis-modelled relationship that should prompt re-examination in plain language and refactoring to match the corrected understanding. Catching mis-modelling early, before more code depends on it, avoids a cost that only grows as dependents accumulate.

That thoughtful approach, practised through building programs that use inheritance and composition well and through reviewing and refactoring them when relationships become unclear, is what will make you a thoughtful programmer, not just a competent one, and it is the approach this chapter hopes to encourage as you move on to later topics.

Plain-language thinking also helps when a hierarchy is presented to non-programmers, such as domain experts or users, because they can validate the relationships in terms they understand, without needing to read code. A domain expert who hears that an ebook is a kind of book, or that a library has books, can confirm or correct that description based on their knowledge of the domain, catching modelling errors that a programmer working alone might miss. That validation by domain experts is a powerful check on design accuracy.
