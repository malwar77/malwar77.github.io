Section 4

A comment that merely restates the code beside it adds nothing. If the code says total = price * quantity, a comment saying "multiply price by quantity" only repeats what any reader can already see. Worse, it creates a second place that must be kept correct. When the code changes and the comment does not, the comment becomes a lie that a future reader may trust. That is why the useful question to ask before writing a comment is not "what does this line do?" but "what would a reader misunderstand, or get wrong, without this note?"

The answer to that question is usually about why a decision was made. Code can show the choice that was taken, but it cannot easily show the choices that were rejected, or the constraint that forced the choice. Perhaps an apparently odd order of operations is required by an external system. Perhaps a simpler approach was tried and failed for a reason that is not obvious from the code alone. Perhaps a value that looks arbitrary comes from a specification, a legal requirement or a quirk of the data being handled. In each case a short comment recording the reason protects the code. Without it, a well-meaning maintainer may "tidy" the code into a form that looks cleaner but breaks the hidden requirement.

Consider a concrete example. Suppose a list must be sorted in a particular way before it is passed on:

# The receiver expects names sorted by surname, then first name.
# Sorting by full name would put "Mary Ann" before "Mary Beth" wrongly
# when surnames differ, so sort on the two fields separately.
names.sort(key=lambda person: (person.surname, person.first_name))

The code alone shows a sort key. The comment explains why that key was chosen and what mistake it prevents. A reader who understands the reason is far less likely to simplify the sort into something that looks equivalent but is not.

Good why-comments are brief and focused. A long essay beside a short function is a warning sign: either the code is unclear and should be rewritten with better names or a clearer structure, or the comment is explaining things the code already makes plain. Prefer the clearer code first. Rename a variable so its purpose is obvious. Extract a step into a small function whose name states its purpose. Only then add a comment for the part that clarity alone cannot convey, namely the reasoning behind a decision.

There is one more habit worth building. When you write a why-comment, write it for the person who will change the code next, not for the person who wrote it. State the reason plainly, name the constraint if there is one, and say what would go wrong if the code were changed in the obvious way.

Finally, treat comments as code that needs maintenance. When you change the behaviour a comment describes, update the comment in the same change. A stale comment is not harmless clutter. It actively misleads, because readers tend to trust prose over code when the two disagree, and they may then "fix" correct code to match an outdated explanation. Short, accurate, why-focused comments, kept in step with the code they describe, are one of the cheapest ways to make a program easier to maintain.

Section 5

Readers understand code visually before they understand it logically. Indentation shows nesting. Blank lines show where one idea ends and another begins. Spaces around operators show which parts of an expression belong together. When those visual cues are consistent, a reader can grasp the shape of a program at a glance and then read the details with confidence. When they are inconsistent, the reader must spend attention on layout instead of meaning, working out whether an odd indent is significant or merely careless. That extra work slows reading and, worse, it can hide real errors behind visual noise.

Consistency across a whole program matters more than any single formatting choice because readers learn a pattern once and then apply it everywhere without thinking. It does not matter very much whether a team indents with four spaces or some other width, or exactly where it breaks a long line, provided the choice is the same in every file. A reader who opens an unfamiliar file written in the team's usual style already knows how to read it. A reader who finds a different style in every file must relearn the visual language each time, and that friction accumulates across a working day.

This is why automated formatters are so valuable. A formatter applies the team's conventions uniformly, without requiring anyone to remember every rule while writing code. It also removes formatting from code review. Reviewers no longer need to argue about spacing or line breaks, and can spend their attention on logic, naming and design, which are the things that actually affect correctness. Running a formatter before review, or as part of a project's standard tooling, turns consistency from a matter of discipline into a matter of habit.

Long lines deserve particular attention. A line that forces horizontal scrolling breaks concentration, because the reader cannot see the whole statement at once. Breaking such a line at a natural point, for example between arguments in a call or between parts of a long expression, makes each part visible separately:

result = process_order(
    customer, items, discount_code, shipping_address
)

Here the call is easy to scan, and adding or removing an argument later is a small, clear change. Blank lines serve a similar purpose between logical sections of a function or module. They mark boundaries without needing a comment for every section, and they let the eye rest at a natural pause.

None of this means formatting is more important than logic. It means formatting is the surface through which logic is read, and a rough surface makes the logic harder to reach. Small visual practices, applied consistently, accumulate into a program that feels pleasant to open and invites careful review. A program whose formatting is chaotic, by contrast, feels like a chore before a single line has been read, and reviewers are less likely to give it the careful attention it needs. Choose conventions as a team, automate them where you can, and then leave them alone so that readers can focus on what the code does.

Section 6

Duplicated code is a maintenance problem because every copy must be kept correct. When a rule changes, a developer must find every place that implements it and change each one. If one copy is missed, the program becomes inconsistent: it behaves one way in one place and another way elsewhere, for what should be the same operation. Bugs of this kind are hard to spot because each copy looks correct on its own. They often appear only for some inputs or some uses, long after the change was made, when the forgotten copy is finally exercised.

The principle often called "do not repeat yourself" captures the remedy. Every piece of knowledge in a program should have a single authoritative representation, so that a change is made once and is reflected everywhere automatically. In practice this usually means extracting shared logic into a function that all the duplicated places call, with parameters for the values that genuinely vary between uses:

def discounted_price(price, rate):
    return price * (1 - rate)

total_a = discounted_price(100, 0.10)
total_b = discounted_price(250, 0.10)

Now the discount rule lives in one place. If the rule changes, it changes once, and both uses follow.

Extraction must be done carefully, however, because two pieces of code that look similar may not represent the same knowledge. They may coincide for now while representing different ideas that will diverge as requirements change. Forcing such code into a single function creates false coupling: a future change to one idea will wrongly affect the other, and unravelling that coupling later is often harder than the duplication was. The classic example is two calculations that happen to use the same formula today but mean different things, such as a tax rate and a discount rate that are both ten percent at present but are governed by different rules.

A useful test separates the two cases. Ask whether a change to one copy would necessarily require the same change to the other copy to keep the program correct. If the answer is yes, the copies represent shared knowledge and should be unified. If the answer is no, because a change to one copy might not apply to the other for reasons specific to its context, then the copies represent different knowledge that merely looks alike for now, and they should be left duplicated until their relationship becomes clearer.

This test also explains why duplication is not always a failure. Early in a program's life, it may be unclear whether two similar pieces of code are truly the same idea. Duplicating them, and waiting to see how they evolve, is often wiser than unifying them prematurely and then discovering that they needed to diverge. The goal is not zero duplication at any cost. It is a program in which each genuine piece of knowledge has one home, and in which accidental similarity is not mistaken for shared meaning.

Section 7

Clean error handling means dealing with errors in a predictable way, rather than scattering checks through code so that the reader cannot tell where failures are handled or what happens when they occur. Errors are a normal part of a program's life: files may be missing, networks may fail, and users may supply input the program did not expect. A program that handles those cases in a clear, consistent place is easier to understand than one in which every function quietly guards against every possible failure in its own way.

A common clean practice is to handle an error where it can be dealt with meaningfully. Low-level code often cannot know what to do about a failure, so it should report the error upward, by raising an exception, rather than inventing a fallback. Higher-level code, which knows the context, can then decide whether to retry, use a fallback, show a message to the user, or stop gracefully. Centralising handling in this way makes the flow of a program easier to follow: the main logic describes the successful path, and the error handling describes what happens when that path fails.

Equally important is not hiding errors silently. A program that catches an exception and carries on as if nothing happened may appear to work while its state is inconsistent or its output is incomplete. Silent failures are particularly harmful because they are discovered late. By the time their effects become visible, the original failure is far in the past, and there may be no record of what went wrong. Users cannot report a problem they do not know exists, and developers cannot fix a failure they cannot reproduce or trace.

Every caught error should therefore be handled deliberately. Either handle it meaningfully, for example by retrying with a fallback or by telling the user what happened and what they can do next, or log it with enough detail for later diagnosis, or re-raise it to code that can handle it. An empty handler that swallows an exception should be treated as suspicious in review, and if it is genuinely the right choice, it deserves a comment explaining why ignoring that particular error is safe:

try:
    cache_file.unlink()
except FileNotFoundError:
    # Already gone: nothing to clean up.
    pass

Finally, error messages themselves should be clear and actionable. A message that merely says something went wrong helps nobody. A good message states what operation failed, what input or condition caused the failure, and what the reader can do next. For users, that might be a concrete next step. For developers reading a log, it might be the values involved and where the failure occurred. In both cases, avoid exposing sensitive details such as internal paths or credentials in messages shown to users. Clarity for the reader and safety for the system are both part of clean error handling, and both deserve attention when an error path is written.

Section 8

Refactoring is the practice of restructuring existing code to improve its internal structure without changing its observable behaviour. The code becomes clearer, better organised or easier to change, but for every input the program currently handles correctly, it produces the same result as before. That last condition is the defining feature of refactoring, and it is what separates refactoring from other kinds of change. If behaviour changes, the work is not refactoring alone. It is refactoring combined with a functional change, and the two should be done separately so that each can be verified on its own.

Keeping them separate matters because tests are the main tool for verifying a refactoring. A test suite can only confirm that behaviour has not changed if the only change made is the refactoring itself. If a functional change is mixed in, and a test then fails, the cause is unclear. It could be that the refactoring broke existing behaviour, or that the new behaviour is correct and the test needs updating, or that the new behaviour itself is wrong. Sorting out which of those is true wastes time and risks masking a genuine regression behind a change that was expected to alter test results. When the two kinds of change are separate, a failing test after a refactoring has one clear meaning: the refactoring went wrong.

Separation also makes review easier. A reviewer looking at a pure refactoring can check that the structure improved and that no behaviour changed, without also having to judge whether a new feature is correct. A reviewer looking at a functional change can focus on the new behaviour, knowing the structure it sits in is already understood. Mixing the two forces the reviewer to do both jobs at once, and makes it harder to spot mistakes in either.

Refactoring is not a separate phase that happens only when code becomes unbearably messy. It is a continuous practice that happens alongside ordinary development. A developer who notices a misleading name while reading code for another purpose can rename it immediately, in a small step that does not change behaviour. A developer who notices duplication while adding a feature can extract the shared logic as part of that work, again in a small, tested step. Because each step is small, its cost is low and its safety is easy to verify.

Those small, continuous refactorings accumulate. A codebase that is tidied a little at a time stays clean without needing large, disruptive efforts that compete with feature work and risk introducing bugs through large-scale changes to previously working code. The discipline is simple to state and worth practising: first refactor, verify with tests, and only then change behaviour, or the other way round, but never both in the same change. A team that follows that rule can improve its code steadily while keeping its test suite as a reliable witness that nothing else changed.

Section 9

Refactoring safely depends on tests, because tests are how you verify that behaviour has not changed after restructuring code. Without tests, refactoring is guesswork. A developer may hope that the restructured code behaves exactly as the original did, but cannot verify that hope except by trying cases by hand, and hand trials easily miss the case where behaviour actually changed. A regression introduced by refactoring may then be discovered later by users, who must report it, and by then the change that caused it may be hard to identify among many other changes.

Before refactoring code that lacks adequate tests, therefore, the usual first step is to write tests that capture its current behaviour. These are sometimes called characterisation tests, because they characterise what the code actually does. They do not need to assert that the behaviour is correct. In fact, for legacy or poorly understood code, the behaviour may include quirks that are wrong in principle but relied upon in practice. The point of the test is to record what the code does now, so that the refactoring can be checked against that record. If the refactoring changes behaviour, even in a way that looks like an improvement, the test will catch it, and the developer can decide deliberately whether that change is wanted, rather than discovering it by accident.

Characterisation tests should cover representative inputs, including edge cases that are known to matter. An empty list, a boundary value, an unusual but valid input, and an input that currently causes an error are all worth recording, because those are exactly the cases where a restructuring is most likely to slip. Writing these tests is often the most valuable part of the work, since it forces the developer to understand the code's actual behaviour before touching its structure:

def test_total_with_empty_order():
    assert order_total([]) == 0

def test_total_applies_discount_once():
    assert order_total([100, 50]) == 135

With such tests in place, refactoring can proceed in small steps, with the tests run after each step. A failing test after a small step points directly at that step, and the step can be reverted and tried differently. A failing test after a large, multi-step refactoring, by contrast, could have been caused by any step, and finding the faulty one requires debugging across the whole change. Reverting a single small step is cheap. Reverting a large change that contains some correct steps and some broken ones is not.

That rhythm, small step, run tests, small step, run tests, is what makes refactoring safe rather than merely hopeful. Tests do not make refactoring risk-free, and they cannot prove that behaviour is unchanged for every possible input. But a good set of tests, written before the restructuring begins, turns refactoring from a leap of faith into a checked, repeatable process, and it gives the developer the confidence to improve code that would otherwise be left alone for fear of breaking it.

Section 10

A code smell is a surface indication that something in the code may be wrong, in the same way that a smell in a kitchen may indicate that something needs attention without proving what it is. Code smells are useful triggers for refactoring, but they should prompt investigation first, not automatic refactoring. A long method, a long parameter list, a class with many unrelated methods, duplicated code and feature envy, where a method uses another object's data far more than its own, are all familiar smells. Each one suggests a possible problem, and each one deserves a look. None of them, on its own, proves that a problem exists.

Consider a long method. It may be a sign that the method does several things and should be split into smaller functions, each with a clear purpose. But it may also be a single coherent sequence of steps that belongs together for readability, and splitting it into many tiny functions could make it harder to follow, because the reader would have to jump between fragments whose individual meaning is lost outside the sequence. The length alone cannot decide between those two readings. Only reading the method, and understanding what it does, can.

A long parameter list raises a similar question. It may mean that several values belong together and should be grouped into a structured value, or that the function does too much and should be split. Or it may mean that the function genuinely needs those values, and grouping them would only hide the complexity rather than reduce it. Duplicated code, too, may be genuine shared knowledge that should be extracted, or it may be coincidentally similar code that will diverge, as discussed for duplication. Feature envy may show that a method belongs in another class, or it may show that the method legitimately coordinates several objects and cannot be moved without making the design worse.

Treating smells as prompts for investigation, rather than as automatic triggers, protects against refactoring that makes code worse. A refactoring undertaken without understanding why the smell is present can destroy a deliberate design, introduce coupling where none was needed, or split a coherent sequence into fragments that are harder to maintain. It also wastes effort on code that was never a problem, while real problems elsewhere go unexamined.

The right response, then, is a short investigation followed by a decision. Read the smelly code and ask what it is doing, why it is shaped that way, and whether that shape causes a real difficulty for readers or for future changes. If the investigation confirms a real problem, refactor in small, tested steps, as for any safe refactoring. If it shows a good reason for the current shape, leave the code alone, and consider adding a comment recording the reason, so that the next reader does not repeat the investigation. Used this way, code smells are a valuable guide to where attention is most likely to pay off, without becoming a mechanical rule that overrides judgement.

Section 17

Guard clauses simplify conditionals by handling special cases early and returning immediately, instead of nesting the main logic inside layers of conditions. The idea is simple: check for the cases that should stop the function first, deal with each one, and then let the rest of the function describe the normal path without further indentation. A reader can then read the function from top to bottom, dismissing each early exit as it is handled, and arrive at the main logic knowing exactly which cases have already been excluded.

Without guard clauses, a function often takes the shape of a deep nest. Each condition adds a level of indentation, and the main logic ends up buried at the deepest level, surrounded by conditions that the reader must hold in mind simultaneously. Consider a function that validates its input before processing it. Written with nesting, the reader must track every enclosing condition to understand what is true at the point where the real work happens. Written with guard clauses, each invalid case is rejected at the top, and the real work stands out clearly at the normal indentation level:

def average(numbers):
    if not numbers:
        return 0
    if any(n < 0 for n in numbers):
        raise ValueError("numbers must not be negative")
    return sum(numbers) / len(numbers)

Here the two guard clauses state their conditions plainly and exit at once. By the time the final line runs, the reader knows the list is not empty and contains no negative numbers, without having to trace through nested blocks to establish those facts.

Guard clauses also make each special case easier to test and to change. Because each guard is a separate, early check, a test can target it directly, and a change to one special case does not disturb the others or the main logic. In nested code, by contrast, changing one condition can affect the meaning of everything inside it, and the interaction between conditions becomes a source of bugs. Early returns reduce that interaction by turning a set of overlapping conditions into a sequence of independent decisions.

There are limits to the technique. A function with a very large number of guard clauses may itself become hard to read, and that is a sign that the validation logic should be extracted into its own function, or that the function is doing too much. Guard clauses also need to be used consistently: mixing early returns with deeply nested logic in the same function can confuse readers about which style to expect. But used in moderation, they are one of the simplest ways to flatten a function and make its intent visible.

The habit to build is to look for nesting when you read a function and ask whether the outer conditions are really part of the main logic or merely preconditions. If they are preconditions, moving them to the top as guard clauses will usually make the function shorter, flatter and easier to follow, and the main logic will finally be where the reader can see it.

Encapsulating a collection means controlling how outside code can access and modify a collection that belongs to an object, instead of exposing the collection directly. If a class holds a list of items and hands that list out as it is, any caller can add, remove or reorder items without the class knowing, and without any of the class's rules being applied. The object's state can then become inconsistent in ways that are hard to trace, because the change did not go through any method of the class and left no trace in its own code.

The invariants that justify encapsulation are the rules that must always hold for the collection. Perhaps items must be unique, or must be kept in sorted order, or must satisfy some validity condition, or must be accompanied by a count or total that is kept in step with the collection. Perhaps removing an item must trigger some other update, such as releasing a resource or notifying another part of the system. If no such rule exists, and the collection is simply a bag of items with no constraints, exposing it may be harmless. But as soon as there is a rule that must hold after every change, direct exposure becomes a risk, because nothing stops a caller from breaking the rule.

Encapsulation solves this by making the collection private and providing methods that enforce the rules. Callers add items through a method that checks the rule, removes them through a method that performs the necessary follow-up, and read them through a method that returns a copy or a read-only view, so that they cannot mutate the internal collection by accident:

class Playlist:
    def __init__(self):
        self._songs = []

    def add_song(self, song):
        if song not in self._songs:
            self._songs.append(song)

    def songs(self):
        return list(self._songs)

In this example, uniqueness is enforced by add_song, and songs returns a copy, so a caller who appends to the returned list does not corrupt the playlist. The invariant, that the playlist contains no duplicates, is maintained no matter how the class is used.

This control also makes future change easier. If the internal representation needs to change, for example from a list to a set, or if a new rule needs to be added, the change can be made inside the class, and callers that use the public methods are unaffected. Callers that had direct access to the list would all need to be checked and possibly changed, which is exactly the kind of scattered change that encapsulation prevents.

Encapsulation is therefore not about secrecy for its own sake. It is about giving the class sole responsibility for keeping its own state valid, so that its invariants hold by construction rather than by the goodwill of every caller. When a collection carries rules that matter, that responsibility is worth protecting, and the small cost of writing accessor methods is repaid by the bugs that never happen.

Refactoring and performance interact, because restructuring code for clarity can affect its speed. A refactoring that introduces an extra function call, an extra copy of a collection, or an extra pass over data may be entirely harmless in most code, yet noticeable in a hot path, a section of code that runs very frequently or over very large inputs. The clean-code habit of preferring clarity is still the right default, but it should not be based on assumptions about speed, in either direction. Neither "this refactoring will be too slow" nor "this refactoring cannot matter" is a safe claim without evidence.

The reason measurement matters is that performance is often surprising. Code that looks expensive may run rarely enough that its cost is irrelevant, while code that looks trivial may run millions of times and dominate the total time. A developer who avoids a clear refactoring on performance grounds, without measuring, may preserve a speed problem that does not exist while keeping code that is harder to maintain. A developer who applies a refactoring blindly to a hot path, without measuring, may introduce a slowdown that only appears under real load, when it is expensive to diagnose. In both cases the error is the same: deciding on the basis of a guess instead of a measurement.

Measuring on hot paths means identifying where the program actually spends its time, and then checking the effect of the change there. Profiling tools can show which functions consume the most time for realistic inputs, and that picture should guide where optimisation effort, and performance caution, is spent. Once the hot paths are known, a refactoring can be tested against them directly: run a representative workload before and after the change, and compare. If the difference is negligible, clarity wins. If the difference is significant, the developer can decide deliberately, perhaps by keeping the clearer structure in most places and using a faster form only where it is measured to matter, with a comment explaining why.

It is also worth remembering that clarity itself can help performance work. A well-structured program, with small functions and clear boundaries, is easier to profile and easier to optimise in the one place that matters, because the hot path can be found and changed without disturbing the rest of the system. Tangled code, by contrast, makes it hard to tell where time is spent or to change one part without affecting others.

The practical rule, then, is straightforward. Refactor for clarity by default. When the code involved is on a hot path, or when a refactoring is suspected to be expensive, measure before and after with realistic data, and let the measurement decide. That habit protects both goals: code stays readable where speed does not matter, and it stays fast where speed genuinely does, with the distinction grounded in evidence rather than in habit or fear.

Automated refactoring tools help by performing mechanical refactorings, such as renaming a name everywhere it is used, extracting a block into a method, or moving a method to another class, quickly and consistently. A human performing the same steps by hand might miss a use, introduce a typo, or update callers inconsistently. A good tool, backed by an understanding of the program's structure, does not make those mistakes, and it frees the developer to think about design rather than about search and replace. For that reason, tools should be used whenever they are available, and their results should still be verified with tests.

What tools cannot do is decide whether a refactoring should happen at all. Renaming is safe mechanically, but choosing a better name requires understanding what a thing means and what name will make that meaning clear to future readers. Extracting a method is safe mechanically, but choosing which block to extract, and what to call it, requires judgement about the structure of the problem and the purpose of each step. Moving a method requires judgement about which class the method truly belongs to, and about whether the move improves cohesion or merely shuffles code. A tool can perform the move once the decision is made, but it cannot make the decision, because the decision depends on intent, on the domain, and on the future direction of the program, none of which are visible in the code alone.

Tools also cannot judge trade-offs. A refactoring that improves clarity in one place may introduce coupling elsewhere, or may be unnecessary because the code is stable and rarely changed, or may conflict with a larger change already planned. A human reviewer weighs those factors against the cost of the change and the risk of disturbing working code. A tool, which sees only the current structure, cannot weigh them, and applying every refactoring a tool suggests would produce churn without benefit, and would risk breaking code for no good reason.

There is a further limit. Tools work best on code they can analyse precisely. Code that relies on dynamic behaviour, on names resolved at run time, or on external configuration may not be fully understood by the tool, and a mechanical change may then miss a use or change a meaning the tool did not see. Tests help to catch such mistakes, but the developer must still review the result and ask whether it is what was intended.

The right relationship, then, is a division of labour. Let tools do the mechanical work, because they do it more reliably than people. Keep the judgement with people, because only people can decide what the code should mean, whether a change is worth its cost, and whether the result is genuinely clearer. A developer who uses tools without judgement will refactor busily and learn little. A developer who uses judgement without tools will waste effort on mechanics and make avoidable mistakes. Together, the two produce refactorings that are both safe and worthwhile.

Section 23

Refactoring code that works with a database involves an extra dimension that ordinary code refactoring does not. Code can be changed and redeployed in one step, but stored data persists. Data written by the old version of the code must continue to work with the new version, and data written by the new version must not break anything that still reads the old form. A refactoring that changes only the code, while ignoring the data already stored, risks corrupting that data or making it unreadable, and such damage is often far harder to undo than a code change.

The most common form of this problem is a change to the shape of stored data. Renaming a column, splitting a table, changing the type of a field, or moving information from one place to another all affect existing rows, not just future ones. A code refactoring that assumes the new shape will fail, or worse, silently misread, rows written in the old shape. The safe approach is to treat the data change as a migration: a planned, tested step that transforms existing data from the old shape to the new shape, with a way to verify that the transformation was correct and, where possible, a way to roll back if it was not.

Timing matters as well. In many systems, old and new versions of the code may run at the same time during a deployment, or old data may be read by tools and reports outside the main program. A refactoring that requires all data to change at once, and all readers to change at once, creates a fragile moment in which any part that lags behind will break. Safer patterns expand first and contract later: add the new shape alongside the old one, migrate the data, move readers to the new shape, and only then remove the old shape. Each step is small and reversible, in the same spirit as small, tested code refactorings.

Testing database refactoring therefore needs to cover data, not just code. Tests should exercise the migration against realistic stored data, including old rows, edge cases and rows that may be incomplete or unusual. They should check that data survives the migration unchanged in meaning, even if its shape changes, and that code reading the new shape handles rows that have not yet been migrated, if that situation can occur in production.

Finally, database refactoring deserves the same separation of concerns as code refactoring. A migration that changes the shape of data should be kept separate from a change that changes what the data means, so that each can be verified on its own and rolled back on its own. Treating stored data as part of the system being refactored, rather than as an afterthought, is what makes database refactoring safe. The code may be easy to redeploy, but the data it guards may be irreplaceable, and that asymmetry should shape every decision about how the refactoring is planned and carried out.

Section 24

Refactoring a public interface, one used by code outside your own program or package, requires care, because changing it without notice breaks the code of people who depend on it. A function, method or class that is part of a public interface is a promise. Other developers have written code against that promise, and they cannot all update their code at the moment you change yours. Deprecation provides a safe migration path by keeping that promise for a while, while clearly signalling that it will change, so that users can move to the new interface at their own pace.

The pattern works in stages. First, introduce the new interface alongside the old one, so that both exist and both work. Then mark the old interface as deprecated, with a warning that tells users what to use instead and, if possible, when the old form will be removed. Users who run their code will see the warning and can plan their migration, while their code continues to work in the meantime. Only after a reasonable period, and after the warning has had time to reach users, is the old interface removed. Each stage is small, and each can be verified separately, which is the same discipline that makes ordinary refactoring safe.

A deprecation warning should be specific and helpful. It should name the replacement, not merely say that something is deprecated, and it should be issued in a way that users will actually see, rather than buried in documentation they may not read. In Python, the standard warnings mechanism provides a conventional way to do this:

import warnings

def old_function():
    warnings.warn(
        "old_function is deprecated; use new_function instead.",
        DeprecationWarning,
        stacklevel=2,
    )
    return new_function()

Here the old function still works, by delegating to the new one, so existing callers are not broken. The warning tells them exactly what to change, and the delegation ensures that behaviour stays consistent between the old and new forms.

Deprecation also needs a timetable and a commitment. A deprecated interface that is never removed accumulates forever, and the codebase ends up maintaining two versions of everything. A deprecated interface that is removed without warning, or after too short a period, breaks trust. The right balance depends on how widely the interface is used and how disruptive the change is, and it should be stated plainly, in the warning or in the release notes, so that users can plan.

Used well, deprecation turns a breaking change into a gradual migration. Users are not forced to update everything at once, maintainers are not forced to support old forms forever, and the interface can evolve without breaking the ecosystem that depends on it. That is why deprecation, rather than a sudden rename or removal, is the standard tool for refactoring a public interface safely.

Section 25

Code review for clean code focuses on readability and maintainability in addition to correctness. A reviewer is not only checking whether the code works, but whether a future reader will understand it, whether its names are clear, whether its functions are small enough to follow, and whether its structure will make the next change easy or hard. Comments about those qualities can be genuinely helpful, but only if they are phrased in a way that the author can act on. A comment that merely says "this is messy" or "this is bad style" tells the author nothing useful and is likely to be experienced as obstructive, however well it is meant.

Helpful review comments are specific. Instead of a general judgement, they point to a particular line or decision, explain the problem it creates for a reader or a future change, and suggest a concrete alternative. For example, "this variable name could be misread as a count rather than a list; pending_orders would make its type clear" gives the author something to do, and explains why it matters. A comment that explains the reasoning behind a suggestion also teaches, so that the author is less likely to repeat the same pattern, whereas a bare instruction to change something teaches nothing and may feel arbitrary.

Tone matters as much as content. Review is a conversation between colleagues, and the author has usually invested effort in the code under review. Phrasing a suggestion as a question or a possibility, "would it be clearer to extract this block into a function named validate_order?" invites discussion and leaves room for the author to explain a reason the reviewer missed. Phrasing it as a command, or as a judgement of the author's ability, shuts discussion down and makes the author defensive, which is the opposite of what review is for. The goal is better code, not winning an argument about code.

It is also important to distinguish between issues that must be fixed and suggestions that are a matter of taste. A misleading name that could cause a bug, or a structure that will make the next change dangerous, is worth blocking a change over. A preference for one equally clear naming style over another is not, and insisting on it wastes both people's time and erodes goodwill for the occasions when a strong objection genuinely matters. Reviewers should say plainly which category a comment falls into, so that the author knows what requires action and what is open for discussion.

Finally, good review comments acknowledge what is good as well as what needs work. A clear function, a well-chosen name, or a thoughtful comment is worth noting, not only because encouragement matters, but because it shows the author, and other reviewers, what the team's standard looks like in practice. Review conducted in this spirit, specific, reasoned, kind and proportionate, improves code without obstructing the people who write it, and it builds the shared understanding of clean code that makes future reviews faster and easier.

Section 26

Clean code helps onboarding, because new developers must learn a codebase quickly to become productive, and a codebase that is readable, well named and well structured is far easier to learn than one that is tangled or obscure. But onboarding also works in the other direction. New developers bring fresh questions, and those questions are a valuable diagnostic tool for the clarity of a codebase. A question that a newcomer asks is often a question that the code failed to answer on its own, and that failure is worth fixing, not merely answering in conversation.

When a new developer asks what a function does, or why a particular step exists, or what a variable means, the first response should be to listen carefully, because the question reveals a gap. Perhaps a name is misleading, and the newcomer was led to expect something different from what the code does. Perhaps a step lacks a why-comment, and the reason for it is known only to the original author. Perhaps a structure is more complex than it needs to be, and the newcomer is struggling for a good reason. In each case, the question points to a specific improvement: a rename, a comment, or a simplification that would help the next newcomer as well as this one.

Treating fresh questions this way requires a deliberate habit. It is easy, and often tempting, to answer the question verbally and move on, leaving the code exactly as unclear as it was. The newcomer leaves satisfied, but the next newcomer will ask the same question again, and the knowledge will remain trapped in people's heads rather than recorded in the code. A better habit is to fix the code as part of answering the question, or to record the fix as a small task to be done promptly. If a name was confusing, rename it. If a reason was missing, add the comment. If a structure was obscure, consider whether a small refactoring would make it plain.

This approach also benefits the newcomer. Being invited to point out unclear code, and seeing their questions lead to real improvements, signals that the team values clarity and that asking questions is welcome rather than a sign of weakness. New developers are often reluctant to criticise code written by more experienced colleagues, so the invitation needs to be explicit. A team that says, plainly, that fresh eyes are an asset, and that questions about unclear code are contributions, will hear more of them, and will learn more from them.

There is a limit, of course. Not every question indicates a problem in the code. Some questions arise because the newcomer has not yet learned the domain, and the right response is an explanation, not a change. The judgement lies in asking whether a reasonable reader, with the relevant background, would have understood the code without asking. If the answer is no, the code should change. If the answer is yes, the explanation is enough. Applied with that judgement, new developers' questions become a steady, low-cost source of improvements, and onboarding becomes not just a process of bringing people up to speed, but a process that leaves the codebase clearer than it was before.

Check: How can new developers' fresh questions help improve a codebase's clarity?

Section 27

Measuring code quality helps a team track whether its code is getting cleaner or messier over time. Metrics such as function length, the number of parameters, the depth of nesting, or the amount of duplication can be computed automatically, and they can highlight parts of a codebase that deserve attention. Used well, they are a useful prompt for investigation. Used badly, as absolute thresholds that code must pass, they become a source of distortion, because developers will optimise for the metric rather than for the quality the metric was meant to represent.

The problem with absolute thresholds is that they treat every part of a codebase as if it were the same. A function that is long because it implements a single coherent algorithm, with steps that belong together, is not necessarily worse than a shorter function that hides its complexity elsewhere. A module with more duplication than some threshold allows may contain coincidentally similar code that should not be unified. A strict limit, enforced without judgement, will push developers to split functions that should stay together, to group parameters that should stay separate, or to extract shared code that represents different ideas, all in order to satisfy a number, while making the code harder to read. The metric improves, and the code gets worse.

Metrics are far more useful as trends. If the average function length in a codebase is rising steadily, or if duplication is growing month by month, that trend is a signal worth investigating, even if no single function breaches a limit. It suggests that the codebase is accumulating complexity faster than it is being tidied, and that the team may need to invest more effort in refactoring, or to look at why new code is being written in a tangled way. Conversely, if the trend is improving, the team can be confident that its habits are working, without needing to celebrate any particular number.

Trends also allow for context. A team can look at where a metric is changing, rather than merely at its overall value, and can ask whether the change reflects a genuine problem or a legitimate feature, such as a complex new area of the program that is inherently harder to express simply. That investigation, prompted by the metric but not dictated by it, is where the value lies. The metric tells the team where to look. Human judgement decides what, if anything, to do.

A practical approach, then, is to track a small number of metrics that the team understands, to review their direction regularly, and to treat sudden changes as prompts for conversation rather than as failures to be fixed mechanically. Avoid turning metrics into targets for individuals, since that invites gaming and discourages honest work on genuinely hard code. Used as trend prompts, metrics support the same habit that runs through clean code generally: notice a signal, investigate it with judgement, and act only where investigation confirms a real problem.

Section 28

Refactoring and documentation must be kept in step, because documentation that describes a program's structure becomes misleading after refactoring changes that structure. If a guide says that a particular task is performed by a particular function, or that data flows through a particular set of classes, and a refactoring renames those functions, splits a class, or reorganises the flow, the guide is now wrong, even though the program still works. A reader who follows the outdated guide will be confused, and may make changes based on a picture of the program that no longer exists.

Documentation that focuses on behaviour is far more resilient to this problem. Behaviour, what the program does, what inputs it accepts, what outputs it produces, and what guarantees it offers, changes much less often than structure. A refactoring, by definition, does not change behaviour, so documentation that describes behaviour survives refactoring untouched. A guide that says "the program validates an order before charging the customer, and rejects orders with missing items" remains true whether validation lives in one function or several, and whether charging is performed by one class or another. Structure-focused documentation, by contrast, must be updated after almost every refactoring, and in practice it often is not, which is how it becomes stale.

This does not mean structure should never be documented. For a newcomer learning a codebase, a map of its main parts can be genuinely helpful. But such maps should be kept short, high-level, and clearly marked as an overview, so that they are easy to update and so that readers do not rely on details that may have changed. Detailed structural documentation, naming every function and describing every internal step, is a maintenance burden that refactoring will quickly outgrow, and it is usually better replaced by clear code itself, with good names and small functions that make the structure self-evident.

A useful rule is to document the contract, not the implementation. State what a component promises to do, what it requires from its callers, and what it guarantees about its results, and leave the internal steps to the code. When the implementation is refactored, the contract stays the same, and the documentation stays correct. When the contract itself changes, that is a functional change, not a refactoring, and the documentation should be updated as part of that change, alongside the code.

Finally, treat documentation updates as part of the refactoring checklist. Before finishing a refactoring, ask whether any documentation describes the structure that has just changed, and update it or remove it. Documentation that is known to be outdated is worse than no documentation, because it misleads with confidence. Behaviour-focused documentation, kept in step with the program's promises rather than its internal shape, avoids that trap and remains a reliable guide through many rounds of refactoring.

Check: Why is behaviour-focused documentation more resilient to refactoring than structure-focused documentation?

Section 29

Knowing when not to refactor is as important as knowing how to refactor, because refactoring carries risk and cost, and spending that risk and cost where it brings no benefit is wasteful. Stable, rarely changed code is a clear example. If a piece of code works correctly, is well tested, and is seldom touched, refactoring it will not make future changes easier in any meaningful way, because there are few future changes to make easier. The benefit is hypothetical, while the risk, that the refactoring introduces a bug into working code, and the cost, in time and review effort, are real and immediate.

Code that is about to be replaced is an even clearer case. If a component is scheduled for removal, or for a major rewrite, in the near future, tidying its internal structure now is effort that will be thrown away when the replacement arrives. The time would be better spent on the replacement, or on code that will live longer. Similarly, code that is about to be changed for functional reasons should usually be refactored, if at all, as a separate step before the functional change, not as part of a large combined effort, and if the functional change will reshape the code anyway, a preliminary refactoring may be wasted work.

This is not an argument for leaving messy code alone forever. It is an argument for judging refactoring by its return. Refactoring pays off when code is changed frequently, when it is hard to understand and that difficulty is causing bugs or slowing work, when it blocks a new feature, or when it is about to be extended in a way that its current structure makes dangerous. In those cases, the investment is repaid by safer, faster future changes. When none of those conditions holds, the return is low, and the effort is better spent elsewhere.

A practical test is to ask what will be different after the refactoring, in concrete terms. Will the next change to this code be easier, and is such a change actually expected? Will a bug that is currently likely become less likely? Will a new developer understand this code materially better, and will that understanding matter soon? If the honest answers are vague or negative, the refactoring is probably not worth doing now, however untidy the code looks. Tidiness for its own sake is not a sufficient reason to disturb working code.

None of this means stable code should never be touched. If a bug is found in stable code, fix it, and refactor only the part needed to make the fix safe. If stable code must be extended after a long quiet period, refactor it then, when the benefit is real and immediate. The discipline is to let the need drive the refactoring, rather than refactoring on principle alone. A codebase kept clean by refactoring where it matters, and left alone where it does not, will be both healthier and less risky than one in which every untidy corner is chased regardless of cost.

Check: When is refactoring stable, rarely changed code usually a poor use of effort?

Section 30

A refactoring checklist helps you apply the practices of safe refactoring consistently, without forgetting a step that matters for safety. Refactoring is made of small decisions, and under pressure it is easy to skip one, to mix a functional change into a structural one, or to forget to run the tests. A checklist turns the discipline into a habit, and it gives a reviewer a clear picture of what was done and what was verified. The steps below form a practical checklist that can be adapted to a team's needs, but the order and the principles behind them are worth keeping.

The first step is to understand the code before changing it. Read the function or class to be refactored, and make sure you know what it does, what inputs it handles, and what its callers expect. If the code is unclear, that understanding may itself require investigation, and it may reveal that the refactoring you planned is not the right one. Rushing into restructuring code you do not understand is a common source of refactoring mistakes.

The second step is to ensure tests exist that capture current behaviour. If adequate tests are already in place, run them to confirm they pass before you start. If they are not, write characterisation tests first, covering representative inputs and edge cases, and confirm that they pass against the unchanged code. These tests are your safety net, and without them the rest of the checklist cannot be verified.

The third step is to make one small change at a time. Rename one name, extract one function, or move one method, and nothing else. Do not combine a refactoring with a functional change, and do not bundle several refactorings into a single step. Small steps make failures easy to diagnose, because a failing test after a small step can only have been caused by that step.

The fourth step is to run the tests after each change. If they pass, the step is safe, and you can proceed to the next one. If they fail, stop, diagnose the failure, and either fix the step or revert it and try a different approach. Do not press on in the hope that later steps will fix an earlier failure, because later steps built on a broken foundation are likely to be broken themselves.

The fifth step is to review the result for clarity, not merely for passing tests. A refactoring that passes tests but leaves code no clearer than before has not achieved its purpose. Read the refactored code as a stranger would, and ask whether its names, structure and flow now make its intent plain. If they do not, consider whether a different refactoring, or a further small step, is needed.

The final step is to commit the refactoring separately from any functional change, with a clear description of what was restructured and why, and with the test results noted. A separate, well-described commit makes the change easy to review, easy to understand in the project's history, and easy to revert if a problem is discovered later. Followed in order, these steps, understand, test, change small, verify, review for clarity, and commit separately, turn refactoring from a risky improvisation into a repeatable, safe practice.

Functions should take as few arguments as possible, because each argument is a burden on callers, who must supply it correctly, and on readers, who must understand what each value means and how it affects the function's behaviour. A function with many arguments is harder to call correctly, harder to test, because each combination of arguments may need a test, and harder to understand, because the reader must hold all the arguments in mind at once. A guideline that suggests keeping the number small, often stated as three or fewer, captures that burden in a memorable form, and it is a useful prompt to stop and think.

It is a prompt for thought rather than a rigid rule, however, because the right number of arguments depends on what the function does. Some functions genuinely need several values that do not belong together and cannot sensibly be grouped. Forcing such a function to take fewer arguments by bundling unrelated values into a single object does not reduce complexity. It hides it, because the caller must still supply all the values, and the reader must now unpack the bundle to understand what the function actually needs. In that case, the guideline has been satisfied in form while the underlying problem remains, and the code is arguably worse, because the function's true requirements are now less visible.

Conversely, a function with few arguments is not automatically clean. A function that takes a single large object, and then reaches deep inside it for many values, may be harder to understand and test than a function that takes those values explicitly, because its dependencies are hidden. Counting arguments alone cannot capture that difference. What matters is whether the function's inputs are clear, whether they belong together, and whether the function can be understood and tested without excessive effort.

The guideline is therefore best used as a question, not as a limit. When a function grows beyond a few arguments, ask whether it is doing too much and should be split, whether some arguments belong together as a coherent group that deserves its own type, or whether some arguments are really configuration that could be supplied once rather than on every call. Each of those questions may lead to a genuine improvement. But if none of them leads anywhere, if the function does one thing well and simply needs its inputs, then keeping the arguments is the honest choice, and the guideline has still done its job by making you check.

A related habit is to be suspicious of arguments that change the function's behaviour in a fundamental way, such as a flag that switches between two different tasks. Such a flag often indicates that the function is really two functions, and splitting it will usually be clearer than any argument-count rule could require. Comments in legacy code deserve special care, because a comment that was accurate when written may have become inaccurate since, as the code around it changed without the comment being updated. In legacy code, where many hands have touched the program over a long period, and where the original authors may no longer be available to ask, the chance that a comment has gone stale is high. That makes the situation where code and comment disagree a common one, and it calls for investigation rather than a quick decision to trust one or the other.

Trusting the comment without question is risky. If the comment is stale, following it may mean "fixing" code that is actually correct, introducing a bug into a program that was working, or reverting a deliberate change whose reason was never recorded. The code, after all, is what actually runs, and if it has been tested and used in production, its behaviour, however surprising, may be the behaviour that users rely on. Changing it to match an old comment, without understanding why it differs, is a gamble.

Trusting the code without question is also risky. Code can contain bugs that have gone unnoticed, especially in paths that run rarely, and a comment may preserve the original intent that the code now fails to implement. If the code was changed by mistake, or if an earlier refactoring introduced an error that tests did not catch, the comment may be the only record of what was intended. Dismissing it outright would lose that information and leave the bug in place.

Investigation, therefore, is the right response. Start with the history, if it is available: when was the comment written, when did the code last change, and were those changes described in a way that explains the difference? Then look at the tests. Do they support the code's current behaviour or the comment's description? Then look at the surrounding system. Which behaviour do callers expect, and which behaviour would break them if it changed? In some cases, a small experiment, running the code with a revealing input, can settle the question quickly.

Whatever the investigation finds, record the outcome. If the code is correct and the comment is stale, update the comment so the next reader is not misled. If the comment is correct and the code is wrong, fix the code, and treat that fix as a functional change, not a refactoring, with tests to confirm the new behaviour. If the investigation cannot settle the question, say so in a comment, and note what is unknown, rather than silently choosing one side. Legacy code rewards this caution, because its history is often the only guide to intent, and intent is exactly what is at stake when code and comment disagree.

Version control supports clean refactoring, because it lets you make small changes, commit them separately, and describe each change clearly, so that the history of a program tells the story of how it evolved. That history is valuable for reviewers, for future maintainers, and for anyone who needs to understand why a piece of code looks the way it does. It is also a safety net: a change that turns out to be mistaken can be reverted, but only if it can be identified and separated from other changes. Both benefits depend on commits being small and separately described.

Small refactoring commits matter for the same reason that small refactoring steps matter. A commit that contains only a rename, or only an extraction, can be reviewed quickly, because the reviewer can see exactly what changed and can check that behaviour did not change. A commit that mixes a refactoring with a functional change, or that bundles many refactorings together, forces the reviewer to untangle several kinds of change at once, and makes it harder to spot a mistake in any of them. It also makes reversion harder: if the functional change is good but the refactoring is flawed, the two cannot be separated without manual work.

Separately describing each commit matters just as much. A commit message for a refactoring should say what was restructured and why, not merely that code was cleaned up. For example, "extract order validation into validate_order so that the checkout function reads as a sequence of named steps" tells a future reader what changed and what problem it solved. A vague message, by contrast, leaves the reader to reconstruct the reasoning from the diff alone, which is often impossible long after the change was made. Good messages also help when searching history for the origin of a bug or a design decision.

The discipline extends to the order of commits. Refactoring commits should come before the functional changes that build on them, so that the history reads as a sequence: first the structure was improved, then the new behaviour was added on top of the improved structure. A reviewer following that sequence can verify each step in turn. A history in which refactoring and functionality are interleaved is much harder to follow, and it hides the point at which behaviour actually changed.

There is a practical cost to this discipline, since it requires committing more often and writing more messages. That cost is repaid quickly, in faster reviews, in easier debugging when a regression appears, and in a history that future maintainers can actually use. A useful habit is to commit after each small, tested refactoring step, with a message that states the step and its reason, before moving on to the next step or to new functionality. Over time, that habit produces a history that is itself a form of documentation, showing not just what the code is, but how and why it came to be that way.

Section 36

Module structure affects clean code, because how a program is organised into modules shapes how easily it can be read, understood and changed. A module should have a clear responsibility, and its dependencies, the other modules it uses, should be few and easy to follow. When that structure is sound, a reader can understand one module without needing to understand the whole program, and a change to one module can be made with confidence that its effects are contained. Circular dependencies break that property, and that is why they are a sign of poor structure.

A circular dependency occurs when two modules depend on each other, directly or through a chain of other modules. Module A imports something from module B, and module B imports something from module A, so neither can be understood, loaded or tested without the other. In Python, such a cycle can cause import errors or surprising behaviour, because the order in which modules are loaded determines which definitions are available when. Even when the program happens to work, the cycle makes the structure fragile: a change in either module may require a change in the other, and the two modules can no longer evolve independently.

The deeper problem is what the cycle reveals about the design. If two modules genuinely need each other, it usually means that a shared idea has been split across them, or that a responsibility has been placed in the wrong module. Perhaps a function in A uses data from B, while a function in B uses data from A, because the two functions really belong together, or because a third concept that both depend on has not been identified and given its own module. The cycle is a symptom of that confusion, not merely a technical inconvenience, and fixing it by rearranging imports without addressing the underlying design will usually leave the confusion in place, ready to reappear.

Breaking a cycle therefore starts with understanding it. Identify what each module uses from the other, and ask whether those uses represent a genuine shared concept. If they do, extract that concept into a third module that both can depend on, so that the dependency flows in one direction. If one use is incidental, move the function or value that causes it to the module where it belongs, so that the dependency disappears. In either case, the result should be a structure in which dependencies flow in one direction, from higher-level modules to lower-level ones, without loops.

That one-way flow is sometimes called a layered structure, and it is worth aiming for because it makes the program easier to reason about. A reader can start at the top layer and follow dependencies downward, knowing that no lower module will unexpectedly reach back upward. Testing becomes easier too, because a lower module can be tested without the higher modules that use it. Circular dependencies deny all of those benefits, and removing them, by clarifying responsibilities rather than merely shuffling imports, is one of the more valuable structural refactorings a team can undertake.

Magic numbers and magic strings are literal values buried in code without any explanation of what they mean, such as 0.2 in a calculation, 7 in a loop, or "PENDING" in a comparison. A reader encountering such a value must guess its meaning from context, and may guess wrongly. A future maintainer who needs to change the value must find every place it appears and change each one, risking a missed copy. Replacing a magic value with a named constant solves both problems at once, by giving the value a name that states its meaning and a single home where it can be changed.

Consider a discount calculation written with a literal:

total = price * 0.8

The reader must work out that 0.8 means a twenty percent discount, and must hope that no other meaning of 0.8 is intended. Written with a constant, the same line becomes self-explanatory:

DISCOUNT_RATE = 0.20
total = price * (1 - DISCOUNT_RATE)

Now the purpose is plain, and if the discount rate changes, it changes in one place. The name also documents the value's role for every reader, without needing a comment, and it makes the code easier to search: finding all uses of the discount rate is a matter of searching for one name, rather than searching for a number that may appear for unrelated reasons.

Named constants also help changing code safely in a subtler way. When the same literal appears in several places for the same reason, giving it one name unifies those places, so that a change is made once and applies everywhere. When the same literal appears for different reasons, giving each use its own name keeps them separate, so that changing one does not wrongly change the other. The act of naming forces the developer to decide which case applies, and that decision itself clarifies the code. Two values that happen to be equal today, such as a tax rate and a discount rate that are both twenty percent, should have different names if they are governed by different rules, because they will diverge in future.

There are exceptions. Small, universally understood values, such as 0 or 1 in a simple count, or an index that is clearly explained by its context, do not always need a name, and naming every trivial literal can clutter code with constants that add no understanding. The test is whether a reader would need to stop and ask what the value means, or whether a future change to the value would need to be made in more than one place. If either answer is yes, a named constant is warranted.

Used with that judgement, named constants are a small refactoring with a large payoff. They make code easier to read, because values carry their meaning with them, and easier to change, because each piece of knowledge has a single home. That combination of readability and maintainability is exactly what clean code aims for, and it is why replacing magic values is one of the first refactorings worth learning.

Section 38

Clean code helps debugging, because when a program fails, a developer must find the part of the program responsible for the failure, and clean structure makes that search short. In tangled code, a failure could have been caused by any part of a long, intertwined sequence, and finding it requires reading and reasoning about the whole sequence. In clean code, the failure can usually be localised quickly, because the program is divided into small functions with clear purposes, and the evidence from the failure points to one of them.

Small functions localise a failure in several ways. First, a stack trace, the record of which functions were running when the failure occurred, becomes informative. If the trace shows a failure inside a function named calculate_discount, the developer knows immediately which piece of logic failed, and can focus there, rather than searching through a large function that does many things.

Second, small functions can be tested in isolation. Once a failing case is known, the developer can reproduce it by calling the suspect function directly, with the same inputs, and observe its behaviour without needing to run the whole program or set up a complex scenario. That isolation makes it possible to confirm or rule out a suspect quickly, and to experiment with a fix without disturbing other parts of the system. In a large function, the same experiment would require reproducing the entire sequence that leads to the failure, which is slower and more error-prone.

Third, small functions limit the scope of what can be wrong. A function that does one thing well has a small number of inputs, a clear purpose, and a limited set of ways it can fail. A developer examining it can reason about all of its behaviour in a short time. A large function, with many variables and many steps interacting, has a much larger space of possible faults, and reasoning about it requires holding all of those interactions in mind at once. That difference is often the difference between a bug found in minutes and a bug found in hours.

Consider a concrete example. Suppose an order total is wrong. In a program where the total is computed by a single function that also validates items, applies discounts and adds tax, the developer must examine all of those steps to find the error. In a program where each step is a small function, the developer can check each step's output in turn, perhaps by calling the functions directly or by adding temporary output, and the faulty step will reveal itself as the first one whose output is wrong. The search becomes a short walk down a chain of named steps, rather than a hunt through an undifferentiated block.

Clean code does not prevent bugs, and it does not make every failure trivial to find. But by dividing a program into small, named, testable parts, it ensures that when a failure occurs, the developer has a clear place to start, a short list of suspects, and a practical way to narrow that list down. That is a large part of what makes a codebase maintainable in practice, long after it was first written.

Shotgun surgery is a smell in which a single logical change requires making many small changes scattered across a codebase, because the logic involved is itself scattered rather than held together in one place. Divergent change is a different smell in which a single module or class must be changed in many different ways, for many different reasons, because it contains unrelated responsibilities that happen to live together. Both are cohesion problems, meaning that they arise from code not being grouped according to what belongs together, but they point in opposite directions, and confusing them leads to the wrong fix.

Shotgun surgery appears when a concept is spread too thinly. Suppose a new kind of order status is added, and that change requires edits in validation, in display, in reporting, in storage, and in several other places, each edit small, but together forming a scattered change that is easy to get partly wrong. The problem is that the knowledge about order status lives in many places, so no single place can be changed to effect the whole change. The risk is a missed edit: one place is updated and another is forgotten, leaving the program inconsistent. The remedy is to gather the scattered logic together, so that the concept has a single home, and a change to it can be made in one place.

Divergent change appears when a concept is packed too tightly. Suppose a single class handles user authentication, order processing and report generation, because those features were added to it over time. A change to authentication requires editing that class, a change to order processing requires editing the same class, and a change to reporting requires editing it again, for entirely different reasons. The problem is not that a change is scattered, but that unrelated changes all land in the same place, making the class harder to understand, harder to test, and riskier to change, because an edit for one purpose may disturb code serving another purpose. The remedy is to split the class, giving each responsibility its own home, so that each kind of change touches only the part that owns it.

The two smells can be told apart by asking where a change lands. If one logical change requires edits in many places, that is shotgun surgery, and the fix is to bring the scattered pieces together. If many unrelated changes all require edits in one place, that is divergent change, and the fix is to split that place apart.

Recognising the difference matters because the remedies are opposites, and applying the wrong one makes the problem worse. Splitting a class that suffers from shotgun surgery would scatter its logic further. Gathering the responsibilities of a class that suffers from divergent change would make it even more overloaded. The shared principle behind both fixes is cohesion: code that changes together, for the same reason, should live together, and code that changes for different reasons should live apart. Judged by that principle, each smell points clearly to its own remedy, and a codebase organised by cohesion will suffer from neither.
