Chapter 27: Caching in Plain Words

Section 1: What Caching Means

Caching is one of the simplest ideas in computing, and also one of the most powerful. It means keeping a copy of something you have already computed or fetched, so that the next time you need it, you can use the copy instead of doing the work again. That is all there is to it. You have done this in real life many times. When you write a phone number on a sticky note instead of looking it up in your contacts every time, you are caching. When a teacher writes the day's timetable on the board instead of checking the office list for every lesson, that is caching. The copy is quicker to reach than the original, and as long as the copy is still correct, using it saves time and effort.

In back-end development, caching usually means storing the result of slow work so that later requests can reuse it. A web request might need to query a database, call an outside service, and shape the result into a response. If a thousand users ask for the same popular page, doing all that work a thousand times is wasteful. Instead, the server does the work once, stores the result in a cache, and serves the stored copy to the next nine hundred and ninety-nine users. The response is faster, the database is less busy, and the server can handle more users with the same hardware. That is the basic bargain of caching: a little extra storage and complexity, in exchange for a lot of speed.

It helps to picture a cache as a shelf near your desk. The storeroom, which is the database or the outside service, holds everything, but it is far away and slow to reach. The shelf holds the few things you use most often, close at hand. When you need something, you check the shelf first. If it is there, you are done quickly. If it is not, you walk to the storeroom, fetch it, and put a copy on the shelf for next time. That check-first habit is the heart of every cache, from the smallest dictionary in a Python program to the largest content delivery network in the world.

Caching is not free. A copy can become out of date, so users might see old information. A cache takes up memory or disk space, which is limited. And cache code adds complexity, which can introduce bugs. A developer who caches everything will create a system full of stale data. A developer who never caches will create a slow, wasteful system. The skill is knowing what to cache, for how long, and how to tell when a copy is no longer trustworthy.

One more thing to understand from the start: caching does not change what your application does. It changes how fast it does it, and how much work it repeats. The correct answer to a request should be the same whether it came from the cache or from fresh work. If caching changes the answer, something is wrong: either the cached copy is stale, or the wrong thing was cached. Keep that test in mind as you learn. A cache should be invisible to the user, except that everything feels faster.

# A cache is just a stored copy of work already done.
cache = {}
cache["popular_page"] = "<h1>Welcome</h1>"
print(cache["popular_page"])  # served from the copy, no fresh work

Section 2: Why Fetching Everything Fresh Is Slow

To understand why caching matters, you need to understand why fresh work is slow. When a user asks your server for a page, the server often has to do several slow things before it can answer. It might query a database, and a database query involves reading from disk, searching through rows, and assembling a result. It might call an outside service over the internet, and that call can take hundreds of milliseconds, or longer if the service is busy. It might process the data: sorting, filtering, formatting, and turning it into HTML or JSON. Each step takes time, and the steps add up. A request that does all of this might take half a second, or several seconds, while the user waits.

Half a second does not sound terrible, but it adds up in two ways. First, users notice. Studies of web behaviour consistently show that slower pages lose visitors. A page that takes three seconds feels sluggish. A page that takes ten seconds feels broken, and many users will leave before it loads. Speed is not a luxury feature. It is part of whether your application feels good to use, and whether people come back. Second, slow requests use up server resources for longer. While a request is waiting on a database or an outside service, it holds memory and a connection. A server handling many slow requests at once can run out of capacity, even if its code is correct, simply because each request occupies resources for so long.

There is also a cost angle. Database queries, outside service calls, and processing all cost something: server time, network traffic, and sometimes money per call. An outside service might charge per request, or limit how many requests you can make. A database under heavy load might need a larger, more expensive server. Doing the same work a thousand times, when once would do, wastes all of those resources. Caching is one of the cheapest ways to reduce that waste, because a cached answer costs almost nothing to serve compared to a fresh one.

None of this means fresh data is bad. Fresh data is the most correct data, and some requests genuinely need it. A bank balance, a private message, or a live stock price should not be served from an old copy. The point is that not every request needs the freshest possible data. A list of popular articles, a product catalogue, a help page, or a public profile changes rarely, and serving a copy that is a few minutes old is harmless. The skill is telling the difference: which data must be fresh, and which data can be a little old without anyone minding. That judgement, applied consistently, is what makes caching effective rather than reckless.

Finally, remember that slowness compounds. A page that makes ten database queries, each taking a tenth of a second, takes a second before any other work. A page that calls three outside services in a row waits for all three. Caching attacks this compounding directly: it removes whole steps from the chain for most requests, so the remaining work is small and fast. That is why caching is often the first performance improvement a developer reaches for, and why it appears in every serious back-end system.

import time

# Fresh work takes time; a stored copy is nearly instant.
start = time.time()
time.sleep(0.5)  # pretend this is a slow database query
fresh_time = time.time() - start
print(f"Fresh work: {fresh_time:.2f}s; cached copy: ~0.00s")

Section 3: The Cache as a Notebook

A useful way to think about a cache is as a notebook you keep beside you while you work. The first time you need a fact, you look it up properly, in the big reference book, and you write the answer in your notebook. The next time you need the same fact, you check your notebook first. If it is there, you save yourself the trip to the reference book. If it is not, you look it up, write it down, and carry on. The notebook is small, fast, and personal. The reference book is complete, slow, and shared. Together, they give you the best of both: speed for common facts, completeness for everything else.

This analogy maps neatly onto a real cache. The notebook is the cache store: a dictionary in memory, a table in a database, or a file on disk. The reference book is the original source: the database, the outside service, or the computation itself. The act of checking the notebook first, and only going to the source on a miss, is called the cache lookup pattern, and it is the same in every system, whatever the technology. When you understand the notebook, you understand the shape of caching, and the rest of this chapter is about the details: what to write in the notebook, how long to keep it, and what to do when the reference book changes.

The notebook also shows why a cache is limited. A notebook has a fixed number of pages. You cannot copy the whole reference book into it, and you would not want to, because most of the reference book you will never need. A good notebook holds the facts you use most often, and you replace old entries with new ones as your needs change. A cache works the same way: it has a size limit, and it must decide which entries to keep and which to throw away when it fills up. Those decisions, called eviction, get their own sections later, because they matter more than beginners expect.

Another lesson from the notebook is about trust. A notebook entry is only useful if it is still correct. If the reference book changes and your notebook still holds the old answer, you will give wrong answers confidently, which is worse than giving slow right answers. That is why every cache entry needs a lifetime, or a way to know when it is out of date. A notebook with no dates on its entries is a trap. A cache with no expiry is the same trap, in software form. The habit of asking "how do I know this copy is still good?" should accompany every cache you build.

Finally, the notebook shows why caching is a trade, not a pure win. You gain speed, but you spend storage, you add code that can go wrong, and you accept the risk of stale data. A developer who understands the trade can make good decisions: cache the popular, slow, rarely changing facts, and leave the rest to the reference book. A developer who does not understand the trade will cache everything, and then spend weeks debugging why users see old data. Keep the notebook picture in mind, and the rest of the chapter will feel like common sense.

# The notebook pattern: check the copy first, look it up only on a miss.
notebook = {}

def get_fact(key, lookup):
    if key in notebook:
        return notebook[key], "from notebook"
    value = lookup()
    notebook[key] = value
    return value, "looked up"

print(get_fact("capital of France", lambda: "Paris"))
print(get_fact("capital of France", lambda: "Paris"))

Section 4: Cache Hits and Cache Misses

Every time your code checks a cache, one of two things happens. If the answer is in the cache, that is a cache hit, and the request is served quickly from the copy. If the answer is not in the cache, that is a cache miss, and your code must do the fresh work, then usually store the result in the cache for next time. Hits and misses are the basic vocabulary of caching, and almost every discussion of cache performance comes down to the ratio between them: how often do you hit, and how often do you miss? That ratio is called the hit rate, and it is the single most important number for a cache.

A high hit rate means the cache is doing its job. If ninety out of a hundred requests are hits, then ninety requests were served fast and cheaply, and only ten needed fresh work. A low hit rate means the cache is barely helping. If only ten out of a hundred requests are hits, the cache is adding complexity and storage for little benefit, and it might even be slowing things down, because every request now pays the cost of checking the cache before doing the fresh work anyway. A cache with a low hit rate is a warning: either you are caching the wrong things, or your entries expire too quickly, or your cache is too small to hold the working set, which is the collection of items your users actually ask for.

Misses come in different kinds. A cold miss happens the first time an item is requested, when the cache has never seen it. Cold misses are unavoidable; they are the price of filling the cache. A capacity miss happens when an item was thrown out to make room, because the cache was full, suggesting the cache is too small or its eviction policy is poor. An expiry miss happens when an item's lifetime ran out. Naming the kind of miss helps you fix it, instead of guessing.

Hits also deserve a closer look. A hit is only good if the cached copy is still correct. A hit on stale data is fast but wrong, and wrong answers can be worse than slow ones. That is why hit rate alone is not enough to judge a cache. A cache with a perfect hit rate that serves day-old prices is not a success. It is a bug that happens to be fast.

In practice, you measure hits and misses with counters: two numbers that go up as requests are served. Many cache systems report them automatically. Get into the habit of checking them, especially after you add or change a cache. If the hit rate is high and users are happy, the cache is working. If the hit rate is low, or if users report stale data, something needs adjusting. Caching is not a feature you add once and forget. It is a system you watch, measure, and tune, like any other part of your application.

# Count hits and misses to find the hit rate.
hits, misses = 0, 0
cache = {"home": "page"}

for request in ["home", "home", "about", "home"]:
    if request in cache:
        hits += 1
    else:
        misses += 1
        cache[request] = "page"

print(f"Hits: {hits}, misses: {misses}, hit rate: {hits / (hits + misses):.0%}")

Section 5: Where Caches Live

A cache can live in many places, and where it lives shapes what it is good for. The most familiar place is the user's browser, which caches pages, images, and files so that revisiting a site is fast. A browser cache is private to one user and one device, and it is controlled partly by the server, through headers you will learn about later, and partly by the browser itself. Browser caching is powerful because it avoids network trips entirely: a cached image is not downloaded again at all. But it only helps the user who already visited, and the server cannot easily clear it when something changes.

The next place is the server's own memory. An in-memory cache lives inside your application's process, usually as a dictionary, and it is extremely fast, because there is no network or disk involved. Its weakness is that it is private to one process. If your application runs on several servers, or restarts, each process has its own cache, and a restart wipes it clean. In-memory caches are perfect for small, fast, per-process data, such as configuration or the results of a quick computation, and they are the easiest cache to build, which makes them a great starting point for learning.

A step up is a shared cache service: a separate program, running on its own server or alongside yours, that many application processes can all use. When one process stores something, every other process can read it. Shared caches survive application restarts, and they can hold much more data than a single process's memory. They add a network trip, because your application must ask the shared service, but that trip is usually very fast, much faster than a database query or an outside call. Shared caches are the standard choice for larger applications, and you will meet the pattern, if not a specific product, later in this chapter.

Caches also live in the database itself, and in content delivery networks, which are covered in their own sections. A database can cache query results internally, so that a repeated query is answered from memory instead of disk. A content delivery network, or CDN, is a network of servers around the world that cache your static files close to your users, so a user in Lagos downloads an image from a nearby server instead of one on another continent. Each of these is the same idea, a stored copy for speed, placed at a different point in the journey between your data and your user.

The lesson is that caching is not one thing in one place. It is a layered system, with caches at several points, each catching requests that the layers below it missed. A request might be served by the browser cache, or by the CDN, or by the shared cache, or by the database's internal cache, or finally by fresh work. Each layer that hits saves the layers below it some work. Designing with layers in mind, rather than a single cache, is what makes large systems fast. Start with one layer, measure it, and add another only when the first is not enough.

# Layers of cache: each layer is checked before the slower one below it.
layers = ["browser cache", "CDN cache", "shared cache",
          "database cache", "fresh work"]
for layer in layers:
    print("Try:", layer)

Section 6: Browser Caching in Plain Words

When a user visits your website, their browser downloads files: pages, styles, images, and scripts. Downloading takes time and bandwidth, and on a slow connection it can dominate how long a page takes to appear. Browser caching solves this by letting the browser keep copies of those files, so that the next visit does not download them again. If you have ever revisited a site and found it loading instantly, browser caching is a large part of the reason. It is the cache closest to the user, and therefore the most valuable one for speed, because it avoids the network entirely.

Browser caching is controlled by the server, through response headers, which are extra pieces of information sent alongside a file. The most important header is Cache-Control, which tells the browser how long it may reuse a copy before checking again. A header saying a file may be cached for a year means the browser will not ask for it again for a year, unless the user forces a refresh. That is wonderful for files that never change, such as a logo or a library script. It is dangerous for files that change often, because a browser holding an old copy will not know the file changed, and the user will see the old version.

The standard solution is versioning: giving each version of a file a different name, or a different query string, so that when the file changes, its name changes too, and the browser treats it as a brand new file. For example, a stylesheet called style-v2.css is a different file, to the browser, from style-v1.css, even if they live in the same place. With versioned names, you can safely tell browsers to cache files for a very long time, because a changed file is really a new file, and the old cached copy is simply never asked for again. This pattern, long cache times plus versioned names, is one of the most effective performance techniques on the web, and it costs almost nothing to implement.

There is a subtlety, though. The main HTML page of your site is usually not cached for long, or not cached at all, because it is the file that references all the others. If the HTML page is cached for a year, a user will keep loading the old page, which references the old versioned files, and will never see your updates. The usual pattern is therefore: cache static files, like images and scripts, for a long time with versioned names, and cache the HTML page briefly, or not at all, so that users always get the latest page, which points them to the latest files. That balance gives you both speed and freshness.

Finally, remember that browser caching is partly out of your control. Users can clear their cache, browsers have size limits, and private browsing modes may not cache at all. Your application must work correctly even when the browser cache is empty, because for a first-time visitor, it always is. Browser caching makes repeat visits fast. It does not replace a fast server, a good server-side cache, or fresh data where it matters. It is one layer, and a very good one, in the layered system you are learning to build.

# Versioned file names: a changed file is a new file to the browser.
files = {"style-v1.css": "cached for a year",
         "style-v2.css": "new file, downloaded fresh"}
for name, behaviour in files.items():
    print(name, "->", behaviour)

Section 7: Server-Side Caching

Server-side caching means caching done by your application, on the server, before a response is sent. When a request arrives, your code checks a cache, and if the answer is there, it returns it immediately, without querying the database or calling outside services. If the answer is not there, your code does the work, stores the result, and returns it. This is the cache you have the most control over, because it lives in your code, and it is the cache this chapter focuses on most, because it is the one a back-end developer builds and tunes directly.

The simplest server-side cache is a dictionary in your Python process. You have already seen this pattern: check the dictionary, return on a hit, compute and store on a miss. That is enough for many small applications, and it is an excellent way to learn, because every behaviour is visible in your own code. You can see what is cached, how long it lives, and when it is cleared. The limits are the ones you met earlier: the cache is private to one process, it disappears on restart, and it shares memory with everything else your application does, so an unbounded dictionary can grow until it consumes all available memory. A real server-side cache therefore needs size limits and expiry, which you will learn to add.

Server-side caching can happen at several levels within your application. You can cache the result of a database query, so a repeated query is answered from memory. You can cache the result of a computation, so an expensive calculation is done once. You can cache a whole rendered page, or a whole API response, so that a repeated request skips all work entirely. Each level trades effort against benefit. Caching a whole response saves the most work, but it is the hardest to keep fresh, because any change to the underlying data makes the whole response stale. Caching a single query saves less work, but it is easier to invalidate precisely. Choosing the level is a judgement call, and the right answer often changes as an application grows.

A server-side cache also needs a clear ownership story. Which part of your code fills it, expires entries, and clears it when data changes? If every part of the code manages the cache in its own way, the result is confusion and bugs. A clean approach is a small cache module with three functions, get, set, and delete, used by the rest of the code. That module hides whether the store is a dictionary, a file, or a shared service.

Finally, server-side caching must be measured. Add counters for hits and misses, log slow paths, and check the numbers after every change. A server-side cache that nobody measures will drift: lifetimes will become wrong as data patterns change, the cache will fill with entries nobody needs, and stale data will creep in unnoticed. A measured cache, by contrast, can be tuned with confidence. You will know what to cache, for how long, and when to clear it, because the numbers will tell you.

# A tiny server-side cache module: get, set, delete.
store = {}

def cache_get(key):
    return store.get(key)

def cache_set(key, value):
    store[key] = value

def cache_delete(key):
    store.pop(key, None)

cache_set("homepage", "<h1>Welcome</h1>")
print(cache_get("homepage"))

Section 8: Database Query Caching

Database queries are often the slowest part of answering a request, which makes them a natural target for caching. Database query caching means storing the result of a query, so that the same query, asked again soon after, is answered from the cache instead of the database. If your application shows a list of popular articles on every page, and that list comes from a query that scans thousands of rows, caching the result for a few minutes can save an enormous amount of database work, because the list changes rarely but is requested constantly.

The pattern is the same as any cache: a key, a value, and a lifetime. The key is usually built from the query itself, or from a name that describes what the query returns, such as "popular_articles". The value is the result, usually a list of rows or a ready-shaped piece of data. The lifetime is chosen based on how often the data changes and how bad stale data would be. A list of popular articles might be cached for ten minutes. A user's private messages should probably not be cached this way at all, or only very briefly, because they change often and staleness would be confusing. The key, the value, and the lifetime are the three decisions in every cache, and query caching is a good place to practise making them deliberately.

There is an important choice here: do you cache the raw rows or the finished result? Caching raw rows means your code still shapes them into a response on every request, but shaping is usually cheap compared to the query. Caching the finished response, such as HTML or JSON, saves even the shaping, but it is harder to reuse: the same rows might be displayed differently on different pages. Cache at the level where the work is, and no higher. If the query is slow and shaping is fast, cache the query result.

Invalidation is the hard part of query caching. When the underlying data changes, the cached result becomes stale. If a new article becomes popular, the cached popular list is wrong until it expires. You can accept that, if a few minutes of staleness is harmless, and simply let entries expire. Or you can invalidate actively: when an article is created or updated, delete the cached popular list, so the next request rebuilds it fresh. Active invalidation gives fresher data, but it requires your code to know, at every place data changes, which cached entries are affected. That knowledge is easy to get wrong. Many teams start with expiry only, and add active invalidation only where freshness truly matters.

Finally, databases have their own internal caches, which work without any code from you. A database keeps recently used data in memory, so a repeated query may be answered from memory rather than disk. That internal cache helps, but it does not replace application-level query caching, because it still runs the query, still processes the rows, and still returns them over a connection. Application caching skips all of that. Think of the database's cache as making the storeroom faster to reach, and your application's cache as keeping a copy on your desk. Both help, and they help in different ways.

import sqlite3

# Cache a query result: the database is only asked on a miss.
db = sqlite3.connect(":memory:")
db.execute("CREATE TABLE articles (title TEXT, views INTEGER)")
db.executemany("INSERT INTO articles VALUES (?, ?)",
               [("Intro to Caching", 500), ("Python Basics", 300)])
query_cache = {}

def popular_articles():
    if "popular" in query_cache:
        return query_cache["popular"], "cached"
    rows = db.execute("SELECT title FROM articles ORDER BY views DESC").fetchall()
    query_cache["popular"] = rows
    return rows, "fresh"

print(popular_articles())
print(popular_articles())

Section 9: Caching Computed Results

Not all slow work involves a database or an outside service. Some work is slow because it is computation: sorting a large list, analysing text, generating a report, rendering a complex page, or running a calculation over thousands of records. Caching computed results means storing the answer to a computation, keyed by its inputs, so that the same computation is not repeated. If the inputs have not changed, the answer has not changed either, so the cached answer is exactly right, not approximately right. That makes computed-result caching unusually safe, because staleness is not a matter of judgement: if the inputs are the same, the output is the same.

The classic example is a function that is called repeatedly with the same arguments. Python's standard library even has a built-in tool for this, called functools.lru_cache, which wraps a function and remembers its recent results. The first call with a given set of arguments runs the function and stores the result. Later calls with the same arguments return the stored result immediately, without running the function again. That is memoisation, a grand word for the notebook pattern applied to functions. It is a beautiful tool for learning, because it shows how much caching can be just a wrapper around work you already do, with no other changes to your code.

Computed-result caching works best when three conditions hold. First, the function must be deterministic: the same inputs always give the same output, with no randomness, no dependence on the time of day, and no hidden dependence on outside state. A function that reads the current time or a changing database is not deterministic, and caching its result would be wrong. Second, the function must be slow enough that caching is worth it. Caching a function that takes a microsecond adds overhead for no benefit. Third, the inputs must repeat. A function called with a new set of arguments every time will never hit the cache, and the cache will only waste memory. When all three hold, computed-result caching is almost free performance.

There are limits to watch. A memoised function keeps its results in memory, so a function called with many different arguments can grow the cache without bound. The lru_cache tool handles this with a size limit, throwing away the least recently used results when it fills up, which is a pattern you will learn about in the eviction sections. Also, a memoised function's cache lives in the process, so it does not help across servers or restarts, and it is not suitable for results that must be shared. For those cases, you need a shared cache, with the same key idea: the key is built from the inputs, and the value is the computed result.

A practical tip: start by caching the slowest, most repeated computations in your application, and measure the effect. A report that takes ten seconds to build and is requested a hundred times a day is a perfect candidate. A tiny helper function called twice is not. Caching is most valuable where the work is large, the inputs repeat, and the result is deterministic. Find those places, cache them carefully, and you will get large speedups from small changes, which is the most satisfying kind of optimisation there is.

from functools import lru_cache
import time

@lru_cache(maxsize=128)
def slow_total(numbers):
    time.sleep(0.1)  # pretend this is heavy computation
    return sum(numbers)

print(slow_total((1, 2, 3)))  # computed
print(slow_total((1, 2, 3)))  # cached, instant

Section 10: Caching API Responses

When your back-end serves an API, other programs, not just browsers, consume its responses. Those programs may ask for the same data repeatedly: a dashboard refreshing every minute, a mobile app syncing on launch, a partner system polling for updates. Caching API responses means storing a response, so that a repeated request for the same resource is answered from the cache instead of by doing the work again. The idea is familiar, but APIs add a few twists that are worth understanding, because they affect how you design your cache keys and lifetimes.

The first twist is that API responses are often personalised. A request for "my tasks" returns different data for each user, so a single cached copy cannot serve everyone. The cache key must therefore include the user, or the request must not be cached at all. A common mistake is caching a personalised response under a key that does not include the user, so that one user sees another user's data. That is a serious privacy bug, and it is entirely avoidable: whenever a response depends on who is asking, the key must reflect who is asking. When in doubt, do not cache personalised responses, or cache them only briefly, in a private cache for that user.

The second twist is that API clients can be told about caching through headers, just like browsers. An API response can include Cache-Control headers saying how long the response may be reused, and ETag headers that let a client ask "has this changed?" instead of downloading it again. A well-behaved API client will respect those headers, reducing load on your server without any extra work from you, beyond setting the headers correctly. That is why learning HTTP caching headers, covered later in this chapter, matters for API developers as much as for web page developers. The protocol already has caching built in, and using it is free performance.

The third twist is that API responses change at different rates. A list of public categories might change once a month, and can be cached for a long time. A user's task list changes often, and should be cached briefly, if at all. A live price should not be cached. Choosing lifetimes per endpoint, based on how the underlying data behaves, is the core skill of API caching. A single lifetime for every endpoint is almost certainly wrong for some of them. Review each endpoint, ask how often its data changes and how bad staleness would be, and set its lifetime accordingly. Write those decisions down, so the next developer understands why each endpoint is cached the way it is.

Finally, API caching interacts with pagination, filtering, and sorting, which you learned about in an earlier chapter. A request for page one of a list, sorted by date, is a different request from page two, sorted by name, and they need different cache keys. The key must capture everything that affects the response: the resource, the page, the filter, the sort order, and the user, if relevant. A key that misses one of those will serve the wrong page to the wrong request, which is a confusing bug. Building keys carefully, from all the inputs that matter, is a skill that repays attention many times over.

# An API cache key must capture everything that changes the response.
def cache_key(user, resource, page, sort):
    return f"{user}:{resource}:page={page}:sort={sort}"

print(cache_key("ada", "tasks", 1, "date"))
print(cache_key("ben", "tasks", 1, "date"))  # different user, different key

Section 11: Time to Live: How Long Is Fresh?

Every cache entry needs a lifetime, and the standard name for that lifetime is time to live, usually shortened to TTL. A TTL says how long a cached copy may be used before it must be considered stale and refreshed. A TTL of five minutes means a copy fetched at noon may be served until five past noon, and after that, the next request must fetch fresh data. TTL is the simplest, most widely used freshness mechanism in caching, and understanding how to choose it well is one of the most practical skills in this chapter.

Choosing a TTL is a trade-off between freshness and performance. A short TTL means data is fresher, because copies expire quickly, but it also means more requests miss the cache and do fresh work, so the performance benefit is smaller. A long TTL means fewer fresh fetches and faster responses, but data can be older, and users may notice. There is no universally correct TTL. The right value depends on the data: how often it changes, how bad it would be if a user saw an old copy, and how much load fresh fetches create. A weather forecast might have a TTL of ten minutes. A list of countries might have a TTL of a day. A user's bank balance should have a TTL of zero, which is another way of saying it should not be cached at all.

A useful way to choose is to ask two questions. First, how often does this data actually change? If it changes once a day, a TTL of an hour is comfortably fresh, and a TTL of a minute is wasteful. If it changes every few seconds, even a TTL of a minute might be too stale. Second, what happens if a user sees data that is a few minutes old? For a blog post list, nothing bad happens. For a seat availability display, a user might try to book a seat that is already gone, which is frustrating. For a price display, a user might see a price that no longer applies, which can cause real arguments. The worse the consequence of staleness, the shorter the TTL should be, until you reach data that must never be cached.

TTL also bounds the damage of mistakes. If you cache something you should not have, or if your invalidation logic has a bug, a TTL ensures the stale copy eventually disappears on its own. Without a TTL, a bad entry could live forever, serving wrong data until someone notices and clears it by hand. That is why experienced developers give every cache entry a TTL, even entries they also invalidate actively. TTL is the safety net; invalidation is the precision tool.

Finally, TTLs should be set per item, not globally, and they should be reviewed as data patterns change. A TTL that was right when your application had a hundred users might be wrong when it has a hundred thousand, because the load of fresh fetches grows with traffic. A TTL that was right for a rarely updated blog might be wrong when the blog starts publishing hourly. Revisit your TTLs when behaviour changes, measure the hit rate and the freshness complaints, and adjust. Caching is a living configuration, not a one-time setting.

import time

# A TTL entry: usable until its expiry time, stale after that.
entry = {"value": "popular articles", "expires_at": time.time() + 300}

def is_fresh(entry):
    return time.time() < entry["expires_at"]

print("Fresh now:", is_fresh(entry))

Section 12: Expiry Versus Invalidation

There are two main ways to deal with stale cache entries, and they are often confused, so this section draws the line clearly. Expiry means an entry stops being usable after its TTL runs out, whether or not the underlying data changed. Invalidation means an entry is deliberately removed or marked stale because the underlying data did change, even if its TTL has not run out. Expiry is passive: time does the work. Invalidation is active: your code does the work, at the moment data changes. Both aim at freshness, but they work differently, cost differently, and fail differently.

Expiry is simple and robust. You set a TTL, and the cache handles the rest. You do not need to know, at every place data changes, which cached entries are affected. You do not need to remember to clear anything. The cost is staleness within the TTL window: after data changes, users may see the old copy until it expires. For data where a few minutes of staleness is harmless, that cost is acceptable, and expiry alone is the right choice. It is also the safety net we discussed: even if everything else fails, expiry eventually clears bad entries. Every cache should have expiry, for that reason alone.

Invalidation is precise and demanding. When an article is updated, your code deletes the cached article page, the cached article list, and any other entry that includes that article, so the next request rebuilds them fresh. Users see fresh data immediately, with no waiting for a TTL. The cost is knowledge: your code must know, at each point where data changes, exactly which entries to invalidate. Miss one, and stale data lingers until expiry, which defeats the purpose. As an application grows, the web of dependencies between data and cached entries grows too, and keeping invalidation correct becomes one of the hardest maintenance tasks in the system. There is a famous joke that the two hardest problems in computer science are cache invalidation, naming things, and off-by-one errors. The joke is funny because invalidation really is hard.

In practice, most systems use both. Expiry provides the safety net and handles the common case. Invalidation provides freshness where it matters most, for the few entries where immediate freshness is worth the complexity. For example, a blog might expire its article lists every ten minutes, but invalidate a specific article's page immediately when that article is edited, because the author will check their own article straight away and notice staleness. That combination gives you most of the benefit of invalidation, with a fraction of the complexity of invalidating everything.

A practical rule for beginners: start with expiry only. Choose sensible TTLs, measure, and see whether staleness actually causes problems. Add invalidation only for specific cases where users complain, or where correctness demands it, such as a user seeing their own updated profile. Each invalidation you add is a promise your code must keep at every data change, so add them deliberately, document which entries each change invalidates, and test them. A cache with expiry and a few careful invalidations is a reliable cache. A cache with ambitious invalidation that is half-implemented is a source of confusing bugs.

# Expiry: time removes the entry. Invalidation: code removes it on change.
cache = {"article_12": "old text"}

def invalidate_on_edit(article_id):
    cache.pop(f"article_{article_id}", None)

invalidate_on_edit(12)
print("Cache after edit:", cache)

Section 13: Cache Invalidation: The Hard Problem

Cache invalidation has a reputation as one of the hardest problems in software, and that reputation is earned. The difficulty is not in deleting an entry, which is one line of code. The difficulty is in knowing, reliably and completely, which entries to delete when data changes, across a whole application, as it grows and changes over time. Every new feature that displays data adds new cached entries. Every new way data can change adds new invalidation points. The mapping between data and cached entries grows in both directions, and keeping it correct by hand is a task that quietly becomes impossible.

Consider a simple example. An article appears in many places: its own page, the homepage list, a category list, an author's page, a search result, and a related-articles block on other pages. If the article is edited, all of those cached entries are stale. If your code only invalidates the article's own page, the other five places will show old data until they expire. A user will see the new title on the article page and the old title on the homepage, and will reasonably conclude your application is broken. Fixing that means finding every place the article appears, which requires knowing the whole application, not just the editing code. As features are added by different people over time, that knowledge fragments, and invalidations get missed.

There are strategies that help. One is to use naming that groups related entries, so they can be cleared together. If all entries involving an article share a prefix, or a tag, you can clear the whole group at once. Tag-based invalidation, where clearing a tag removes all entries carrying it, is powerful, though it needs a cache system that supports it. Another strategy is to keep TTLs short for complex, widely displayed data, so that even a missed invalidation only causes brief staleness.

Another strategy is to reduce what you cache. If a piece of data appears in many places and changes often, perhaps it should not be cached at a high level, such as a whole page, but only at a low level, such as a single query, where invalidation is simpler. Or perhaps it should not be cached at all, because the cost of keeping it fresh outweighs the benefit of caching it. Not caching something is a valid, respectable decision, and it is often the right one for data that is complex, personal, or fast-changing. The best invalidation strategy is sometimes to avoid needing invalidation in the first place.

Finally, accept imperfection and design for it. Assume some invalidations will be missed, and make sure the consequences are bounded: short TTLs, visible freshness indicators where they matter, and a way for users to force a refresh. Test invalidation explicitly: change data, then check every place it appears, and confirm the new data shows. Those tests catch missed invalidations before users do. Invalidation is hard, but it is not mysterious. It is a bookkeeping problem, and bookkeeping problems are solved by clear naming, short lifetimes, good tests, and a willingness to not cache what you cannot keep fresh.

# Tag-based invalidation: clear every entry tagged with the changed article.
cache = {("homepage", "article_12"): "old", ("article_12_page", "article_12"): "old",
         ("other_page", "article_99"): "kept"}
cache = {k: v for k, v in cache.items() if "article_12" not in k}
print("Remaining entries:", cache)

Section 14: Cache Keys: Naming What You Store

Every cache entry is stored under a key, a name that identifies it, and the quality of your keys determines the quality of your cache. A good key is unique, descriptive, and built from exactly the inputs that affect the value. A bad key causes collisions, where two different things share a key and one overwrites the other, or misses, where the same thing gets different keys and is never found. Key design sounds trivial, and it is one of the most common sources of caching bugs, because keys are written quickly and rarely reviewed.

The basic rule is: the key must include everything that can change the value, and nothing else. If a page differs by user, the key must include the user. If a list differs by page number and sort order, the key must include both. If a result differs by language, the key must include the language. Miss one input, and users will see each other's data or the wrong page, which are serious bugs. Include an irrelevant input, and you will store duplicate copies of the same value under different keys, wasting space and lowering the hit rate, which is wasteful but not dangerous. When in doubt, include the input. A slightly wasteful key is far better than a dangerously incomplete one.

Keys should also be readable and consistent. A key like "user:42:tasks:page=1:sort=date" tells a developer exactly what it holds, which makes debugging much easier than a key like "x7f9". Use a consistent pattern across your application, such as separating parts with colons, and naming parts clearly. Consistency matters because cache keys are often inspected during debugging, in logs or in a cache browser, and a readable key answers questions immediately. A cryptic key forces you to guess, or to look up documentation, in the middle of an incident.

Another consideration is key length and characters. Keys are often stored and transmitted, so extremely long keys waste space, and keys with special characters can cause problems in some cache systems. A common solution for complex inputs is to hash them: turn the inputs into a short, fixed-length string, such as a hash of the query and its parameters, and use that as part of the key. Hashing keeps keys short and safe, but it makes them unreadable, so it is best used for the variable part, while keeping a readable prefix. For example, a key might be "search:" followed by a hash of the search terms. That gives you readability and safety together.

Finally, version your keys when the format of the value changes. If you change how a cached value is structured, old entries under the same key will have the old structure, and code expecting the new structure will break or behave strangely. The fix is to include a version in the key, such as "tasks:v2:...", so that a format change creates a new set of keys, and old entries simply expire unused. Key versioning is a small habit that prevents a whole class of deployment bugs, and it is worth adopting from the start, before you need it urgently.

import hashlib

# Readable prefix + hash of the variable part = safe, debuggable key.
def search_key(terms):
    digest = hashlib.sha256(terms.encode()).hexdigest()[:12]
    return f"search:v1:{digest}"

print(search_key("caching basics"))
print(search_key("caching basics"))  # same input, same key

Section 15: What to Cache and What Not To Cache

Not everything should be cached, and choosing what to cache is a judgement that improves with experience. The best candidates share a few traits: they are requested often, they are expensive to produce, and they change rarely. A popular homepage, a product catalogue, a list of categories, or a help page all fit that description. Caching them gives a large benefit, because many requests are served from the copy, and a small risk, because the data rarely changes, so staleness is rare and brief. When you find data with all three traits, cache it confidently.

The worst candidates also share traits: they are requested rarely, they are cheap to produce, or they change constantly. Caching a rarely requested item wastes space, because the entry will likely expire before it is ever reused. Caching a cheap computation adds overhead for no benefit, because the cache lookup costs nearly as much as the computation. Caching fast-changing data, like a live price or a chat message, creates staleness problems that outweigh any speed gain. If a candidate has any of these traits, think twice. The cache might still be worthwhile, but the case needs to be made, not assumed.

Personal data deserves special caution. A user's private tasks, messages, or settings should not be cached in a shared cache, because a key mistake could expose one user's data to another. If personal data is cached at all, it should be in a private cache, with the user in the key, and with a short lifetime. Even then, ask whether the benefit justifies the risk. Private data is often not requested as frequently as public data, and it changes more often, so the case for caching it is weaker anyway. When in doubt, do not cache personal data. The performance gain is rarely worth the privacy risk.

Secrets must never be cached. Passwords, tokens, API keys, and other credentials have no place in a cache, because caches are often less protected than the systems that hold secrets, and because cache entries can linger, be logged, or be inspected during debugging. If your code is tempted to cache a secret for convenience, that is a sign the design needs rethinking, not a sign to add a cache entry. The same applies to data that is legally sensitive, such as health or financial records, unless you have a clear, reviewed reason and proper protections. Caching is an optimisation, and optimisations must never compromise security.

A practical approach to choosing is to measure first. Find the slowest, most frequent requests in your application, using logs or simple timing, and cache those. That evidence-based approach beats guessing, because it targets the work that actually matters to users. Start with one or two high-value caches, measure the hit rate and the improvement, and expand from there. Caching everything at once, without measurement, creates a system that is hard to debug and full of stale data. Caching deliberately, one proven candidate at a time, creates a system that is fast and trustworthy.

# Score a caching candidate: frequent + expensive + rarely changing = cache it.
candidates = {"homepage": (1000, "slow", "rarely"),
              "live price": (1000, "slow", "constantly"),
              "rare report": (2, "slow", "rarely")}
for name, (freq, cost, change) in candidates.items():
    good = freq > 100 and cost == "slow" and change == "rarely"
    print(name, "-> cache?" , good)

Section 16: Caching User-Specific Data Safely

User-specific data, such as a person's task list, inbox, or profile, is tempting to cache, because users request it often and it can be slow to build. But it is also the data where caching mistakes cause the most harm, because a mistake can show one person's private information to another person. Caching user-specific data safely is possible, but it requires discipline, and the rules are worth learning explicitly, because the consequences of getting them wrong are serious.

The first rule is that the user must be part of the key, always, without exception. A cache key for a task list must include the user id, so that Ada's tasks and Ben's tasks live under different keys and can never be confused. This sounds obvious, and it is, but it is also the rule most often broken under pressure, when a developer copies a caching pattern from a public page and applies it to a private page without adding the user to the key. Make it a habit to check, for every cache entry, whether the value depends on the user, and if it does, whether the user is in the key. That single check prevents the worst class of caching privacy bugs.

The second rule is to prefer private caches for private data. A private cache is one that is only accessible to that user's requests, such as the user's browser cache, or a per-user section of a server cache that is never shared across users. A shared cache, where all users' entries live together, can be used safely if keys are correct, but it has a larger blast radius if a key is wrong. A private cache limits the damage of a mistake. For highly sensitive data, the safest choice is often not to cache at all on the server, and to rely on the browser cache, which is inherently private to the device, or to accept the cost of fresh fetches.

The third rule is about lifetimes. User-specific data changes more often than public data, because users act on it constantly. A task list cached for an hour will be stale within minutes of the user completing a task, and the user will notice immediately. Short lifetimes, or active invalidation when the user changes their own data, are therefore essential. A common pattern is to invalidate a user's cached data immediately when they change it, so they always see their own latest state.

The fourth rule is about what not to store. Even with correct keys, a cache entry containing private data is a copy of that data in a place that may be less protected, less audited, and longer-lived than the original. Minimise what you store: cache the task list, not the full task histories; cache the profile summary, not the private settings. And never cache secrets or credentials, as established earlier. If a cache entry would embarrass you if it were printed in a log, it should not be in the cache, or it should be encrypted, with access tightly controlled. Private data deserves the same care in a cache as it does in a database.

# Safe: the user is always part of the key for private data.
def tasks_key(user_id, page):
    return f"user:{user_id}:tasks:page={page}"

print(tasks_key(42, 1))
print(tasks_key(43, 1))  # a different user can never collide

Section 17: Shared Caches and Private Caches

Caches can be shared or private, and the distinction matters for both correctness and performance. A shared cache is one used by many users, such as a server-side cache holding public pages, or a CDN holding images. Every user who requests the same item gets the same cached copy, which is efficient, because one copy serves everyone. A private cache is one used by a single user, such as a browser cache, or a per-user section of a server cache. Each user has their own copies, which is safer for personal data, but less efficient, because the same work may be cached separately for each user.

The rule for choosing is based on the data, not on convenience. Public data, which is the same for everyone, belongs in a shared cache, where one copy serves all. Private data, which differs by user, belongs in a private cache, or not in a cache at all. Mixing the two is where bugs happen: private data in a shared cache, under a key that does not distinguish users, will leak. Public data in a private cache is merely wasteful, because each user builds their own copy of something that could have been shared. Getting the distinction right is a matter of asking, for each cached item, "is this the same for everyone?" If yes, shared. If no, private.

HTTP has built-in support for this distinction, through the Cache-Control header, which you will learn in detail later. A response can be marked public, meaning shared caches may store it, or private, meaning only the user's own browser may store it. That header is a promise from the server to the caches in between, and it is important to set it correctly, because shared caches, like CDNs and proxies, will obey it. Marking a private response as public is a serious mistake, because it invites shared caches to store and serve one user's data to others. Marking a public response as private is merely wasteful, because shared caches will skip it, but it is the safe direction to err in when you are unsure.

There is also a middle ground: a shared cache that stores private data under per-user keys. This is common in practice, because it gives the performance of shared infrastructure with the safety of per-user separation, as long as keys are correct. The cache itself is shared, but the entries are private, because each key includes the user. What it must never hold is a private entry under a public key, where any user can retrieve it.

Finally, think about cache size and efficiency. Shared caches are efficient for popular public data, because one entry serves many users. Private caches are less efficient, because each user needs their own entries, and the total storage grows with the number of users. That is another reason to be selective about caching private data: the storage cost is multiplied by users, while the benefit is limited to one user at a time. Cache public data aggressively, cache private data sparingly, and you will get most of the performance benefit with a fraction of the risk and cost.

# Public data: one shared key. Private data: a key per user.
shared_key = "public:homepage"
private_key = "private:user:42:tasks"
print("Shared:", shared_key)
print("Private:", private_key)

Section 18: Stale Data and How Much It Matters

Stale data is cached data that no longer matches the original source. It is the central risk of caching, and the question every developer must answer is not "how do I avoid staleness entirely?" but "how much staleness can this data tolerate?" Because the honest answer is that some staleness is unavoidable in any caching system. Even with active invalidation, there is a moment between a change and its invalidation when the old copy is still served. The goal is not zero staleness, which is impossible, but staleness that is small enough, and harmless enough, that users do not notice or do not mind.

How much staleness matters depends entirely on the data and its use. A blog post list that is five minutes stale is harmless: readers will not notice, and nothing breaks. A product price that is five minutes stale could cause a customer to see one price and be charged another, which causes arguments and refunds. A seat map that is five minutes stale could let two people book the same seat, which is a real operational problem. A security setting, such as whether an account is blocked, that is five minutes stale could let a blocked user act for five more minutes, which could be a security incident. The same five minutes means nothing in one case and a great deal in another, which is why staleness tolerance must be judged per item, not globally.

There are also cases where staleness is not just tolerable but expected. A search index is always a little behind the live data, because indexing takes time. A trending list is a snapshot, not a live count. A cached weather forecast is, by nature, an estimate. Users understand these as approximations, and they do not expect perfection. In those cases, caching is not introducing a problem. It is matching the nature of the data, which is already approximate. Recognising those cases frees you from chasing freshness that nobody needs.

When staleness does matter, there are ways to reduce its harm without abandoning caching. Shorten the TTL, so stale windows are brief. Invalidate actively on change, so stale windows are rare. Show the user when the data was last updated, so they can judge its freshness themselves: a label saying "updated 5 minutes ago" turns a hidden staleness into an honest, visible one. And for critical decisions, such as charging money or booking a seat, do not rely on cached data at all: check the source fresh at the moment of the decision, even if the display was cached. That pattern, cached display plus fresh check at the critical moment, gives you speed where it is safe and correctness where it counts.

Finally, talk to users about staleness when it affects them. If a dashboard is cached for ten minutes, say so on the dashboard. If a report is a snapshot from last night, label it as such. Users are remarkably tolerant of staleness they understand, and remarkably intolerant of staleness that surprises them. Transparency about freshness is a small design choice that prevents a large number of support messages and trust problems.

# Staleness tolerance differs by data: same delay, different impact.
tolerance = {"blog list": "10 minutes is fine",
             "product price": "seconds matter",
             "blocked account check": "must be fresh"}
for item, verdict in tolerance.items():
    print(item, "->", verdict)

Section 19: Stale-While-Revalidate in Plain Words

Stale-while-revalidate is a clever caching pattern with a long name for a simple idea: serve the stale copy immediately, and refresh it in the background, so the next request gets the fresh copy. Normally, when a cache entry expires, the next request must wait for fresh data, which is slow. With stale-while-revalidate, that request gets the old copy instantly, and the system quietly fetches a fresh copy behind the scenes. The user never waits, and the cache is fresh again for the next user. It is a pattern that gives you both speed and reasonable freshness, and it is worth understanding because it appears in HTTP headers, CDNs, and application caches.

Here is how it works in practice. Suppose a popular page is cached with a fresh lifetime of five minutes and a stale-while-revalidate window of a further minute. For the first five minutes, requests get the fresh copy. Between five and six minutes, requests still get the copy, now technically stale, but they also trigger a background refresh. After the refresh completes, later requests get the new copy. If the background refresh fails, the stale copy can keep being served, within limits, rather than failing the request. That graceful behaviour under failure is a major advantage: a failing data source does not immediately break the user experience, because the stale copy covers for it briefly.

The trade-off is that users sometimes see data that is a little older than the nominal lifetime. In the example above, a user at five minutes and thirty seconds sees data that is five and a half minutes old, not five minutes old. For data where that extra staleness is harmless, the trade is excellent: you gain speed and resilience for a small freshness cost. For data where freshness is critical, such as prices or security checks, the trade is not acceptable, and stale-while-revalidate should not be used. As always, the decision depends on the data, and the pattern is a tool, not a universal answer.

Implementing stale-while-revalidate in your own application cache is straightforward in concept. When a request finds an entry that is past its fresh lifetime but within its stale window, return the entry immediately, and queue a background job to refresh it, or refresh it in a way that does not block the response. The details, such as ensuring only one refresh happens at a time, rather than one per request, matter, and they connect to the stampede problem covered next. But the core idea is simple: never make a user wait for a refresh if a slightly old copy will do, and refresh quietly so the next user benefits.

HTTP supports this pattern directly, through a Cache-Control directive with the same name, which browsers and CDNs understand. That means you can get stale-while-revalidate behaviour for web pages and static files simply by setting a header, without writing any code. It is a good example of how learning HTTP caching headers, later in this chapter, gives you powerful behaviour for free. The pattern is the same wherever it appears: serve fast, refresh quietly, and accept a small, bounded staleness in exchange for speed and resilience.

import time

# Serve stale instantly, refresh in the background for the next request.
entry = {"value": "old page", "fresh_until": time.time() - 10,
         "stale_until": time.time() + 60}

def serve(entry):
    now = time.time()
    if now < entry["fresh_until"]:
        return entry["value"], "fresh"
    if now < entry["stale_until"]:
        return entry["value"], "stale, refreshing in background"
    return None, "must fetch fresh"

print(serve(entry))

Section 20: Cache Stampede: When Everyone Asks at Once

A cache stampede, also called a thundering herd, happens when a popular cache entry expires, and many requests arrive at once, all find a miss, and all do the fresh work at the same time. Imagine a homepage cached for five minutes, visited by a thousand users a minute. At the moment it expires, a hundred requests might arrive before the first fresh fetch completes, and each one will query the database, call the services, and build the page, duplicating the same expensive work a hundred times. That sudden burst can overwhelm the database, slow the whole application, and turn a routine expiry into an incident. Stampedes are a classic caching failure, and they are preventable.

The simplest prevention is to ensure only one request rebuilds the entry, while the others wait for it, or use the stale copy. One way to do that is a lock: when a request finds a miss, it claims the right to rebuild, and other requests that arrive during the rebuild either wait briefly for the result, or are served the stale copy if one exists. That stale-copy option connects back to stale-while-revalidate, which is one of the best stampede defences, because it means no request ever waits for a rebuild: they all get the stale copy, and a single background refresh updates it. A system with stale-while-revalidate rarely stampedes, because misses do not trigger simultaneous rebuilds.

Another prevention is to stagger expiry times. If many entries are cached at the same moment with the same TTL, they will all expire at the same moment, causing a burst of rebuilds. Adding a small random variation to TTLs, sometimes called jitter, spreads expiries out over time, so rebuilds happen gradually instead of all at once. For example, instead of every entry expiring after exactly five minutes, each expires after five minutes plus a random few seconds. That small change can dramatically smooth load, and it costs nothing. Jitter is a humble, effective technique, and it applies to retries and scheduled jobs as well as to caches.

A third prevention is cache warming, covered in the next section: rebuilding popular entries before they expire, so that expiry never causes a miss in the first place. If a background job refreshes the homepage every four minutes, and its TTL is five minutes, the entry never expires in practice, and no request ever triggers a rebuild. Warming removes the stampede risk entirely for the entries it covers, at the cost of doing refresh work even when nobody is asking, which is a reasonable trade for very popular pages.

Finally, stampedes teach a general lesson about synchronised behaviour. Whenever many independent parts of a system do the same thing at the same time, whether expiring, retrying, or restarting, the result is a burst that can overwhelm shared resources. The defences are always similar: stagger the timing, let one actor do the work while others wait or use a stale copy, and pre-compute where possible. Keep those defences in mind whenever you design a system with many concurrent users, because stampedes appear in many forms beyond caching, and the same thinking prevents them all.

# Jitter: spread expiry times so entries do not all expire at once.
import random

base_ttl = 300
for i in range(5):
    ttl = base_ttl + random.randint(0, 30)
    print(f"Entry {i}: TTL {ttl}s")

Section 21: Warming a Cache

Cache warming means filling a cache before users ask for anything, so that the first request is already a hit. Normally, a cache starts empty, and the first user to request each item pays the cost of a miss: a slow response while the work is done and the result stored. Warming avoids that cost by doing the work in advance, usually with a background job that requests popular pages, runs common queries, or pre-computes frequent results, and stores them in the cache. When users arrive, the answers are already waiting. Warming turns the cold-start problem into a scheduled chore, handled quietly before anyone notices.

Warming is most valuable for data that is popular and predictable. A homepage, a list of categories, a daily report, or the top ten articles are all things you can predict users will ask for, so you can warm them confidently. Warming unpredictable data is wasteful, because you will fill the cache with entries nobody requests, pushing out entries that matter. The rule is the same as for caching in general: warm what is popular, and leave the rest to be cached on demand. A small set of warmed entries, the top twenty pages rather than the whole site, usually captures most of the benefit.

Warming is usually done on a schedule. A background job runs every few minutes, or after a deployment, or when data changes, and refreshes the warmed entries. That schedule also solves the stampede problem for warmed entries, because they are refreshed before they expire, so requests never trigger a rebuild. The warming job itself must be careful, though: if it refreshes everything at once, it can create its own burst of load on the database. Spreading the refresh across the schedule, or refreshing entries one at a time, keeps the load smooth. Warming should make the system calmer, not create a new peak.

There is a cost to warming, and it should be weighed honestly. Warming does work that might not be needed, uses resources even when traffic is low, and adds a scheduled job that must be monitored. For a small application with light traffic, warming may be unnecessary: the first user pays a slightly slow response, and everyone after benefits. For a large application, or one where the first impression matters, such as a news site at the top of the hour, warming is essential, because a slow first response for thousands of simultaneous users is a visible failure. As with most caching decisions, the right answer depends on scale and on how much a slow first response matters.

Finally, warming interacts with deployments. When you deploy new code, caches are often cleared, or the application restarts with an empty in-memory cache, and suddenly every request is a miss. A warming step as part of deployment, run automatically after the new version is live, restores the cache before real traffic arrives, and prevents a post-deployment slowdown. Teams that have been bitten by a cold cache after a deployment learn to treat warming as part of the release process, not as an optional extra. It is a small habit that makes deployments noticeably smoother.

# Warming: fill the cache with popular pages before users arrive.
popular_pages = ["homepage", "categories", "top-articles"]
cache = {}
for page in popular_pages:
    cache[page] = f"<h1>{page}</h1>"
print("Warmed entries:", list(cache))

Section 22: Cold Starts and Empty Caches

A cold start happens when a cache is empty and must be filled from scratch, usually after a restart, a deployment, or a cache clear. During a cold start, every request is a miss, and the system does full fresh work for each one, which is slow and puts heavy load on the database and outside services. If traffic is high during a cold start, the load can be severe enough to slow the whole application, or even cause failures, as the database struggles under a sudden flood of queries it has not seen in a while. Cold starts are a normal part of running a system, but they need a plan, because an unplanned cold start at peak traffic is a painful experience.

The most common cold start cause is a restart. An in-memory cache lives inside the application process, so restarting the process wipes it. A deployment that restarts the application therefore causes a cold start, unless the cache is shared or persisted. That is one reason shared caches are popular: they survive application restarts, so a deployment does not empty them. Another common cause is a deliberate cache clear, done to fix stale data or after a major data change. Clearing a cache is sometimes necessary, but it should be done thoughtfully, because it trades a stale-data problem for a cold-start problem, and the cold start may be worse.

There are several ways to soften a cold start. Warming, covered in the previous section, is the main one: refill the cache before or soon after the restart, so the cold period is brief. Another is to restart gradually, one server at a time, so that while one server's cache is cold, the others still serve from warm caches. That rolling restart pattern is standard practice for larger systems. A third way is to use a persistent cache, stored on disk or in a database, so that a restart does not empty it at all.

Cold starts also reveal which data truly matters. During a cold start, the items requested first, and most often, are the ones that fill the cache fastest, and they are usually the popular pages and common queries. Watching a cold start, through hit rate and load numbers, tells you what your real working set is, which is useful information for warming and for capacity planning. If a cold start is consistently painful, that is a signal: your working set is large, your fresh work is slow, or your traffic is high enough that warming and shared caches are no longer optional.

Finally, plan for cold starts before they happen. Know how your cache behaves on restart, how long a cold start lasts, and what load it creates. Test it deliberately: restart your application, watch the numbers, and see how long it takes for the hit rate to recover. A cold start you have measured is a known quantity, and you can schedule restarts for quiet times, warm afterwards, and warn your team. A cold start you have never tested is a surprise, and surprises at peak traffic are the worst kind.

# A cold cache: every request misses until entries are rebuilt.
cache = {}
requests = ["homepage", "homepage", "categories"]
for r in requests:
    if r in cache:
        print(r, "hit")
    else:
        print(r, "miss, building and storing")
        cache[r] = "page"

Section 23: Memory Caches with Dictionaries

The simplest cache you can build in Python is a dictionary. A dictionary maps keys to values, looks them up almost instantly, and is built into the language, so there is nothing to install and nothing to configure. For learning, and for many small applications, a dictionary cache is enough, and it teaches the core operations clearly: check for a key, return the value on a hit, compute and store on a miss, and delete when data changes or expires. Every larger cache system offers the same operations, with more features around them, so a dictionary cache is a genuine foundation, not a toy.

A basic dictionary cache needs two additions to be practical: expiry and size limits. Without expiry, entries live forever and become stale. Without size limits, the dictionary grows until it consumes all memory. Expiry can be added by storing, alongside each value, the time it expires, and checking that time on lookup. If the entry has expired, treat it as a miss, delete it, and fetch fresh data. Size limits can be added by checking the dictionary's length before storing, and removing an entry, usually the least recently used one, when the limit is reached. Both additions are small, and writing them yourself teaches you exactly what larger cache systems do internally.

There is a subtlety with expiry checks: expired entries that are never requested again will sit in the dictionary forever, wasting memory, because they are only removed when someone looks them up. That lazy cleanup is fine for small caches, but for larger ones, a periodic cleanup pass, which scans for expired entries and removes them, keeps memory under control. A background job or a timer can run that pass every few minutes. The combination of lazy removal on lookup and periodic cleanup is the standard approach, and it balances simplicity with tidiness.

Thread safety is another consideration, though it is less pressing for a learner. If your application handles requests in multiple threads, two threads could read and write the dictionary at the same time, causing confusion. Python's dictionary operations are mostly safe individually, but a check-then-store sequence can still race: two threads might both miss, both do the fresh work, and both store, duplicating effort. For a learning project, that duplication is harmless. For production, a lock, or a cache system designed for concurrent use, solves it. The lesson is to be aware that shared mutable state, like a cache dictionary, needs care when many threads use it, even if the basic idea is simple.

Finally, remember the limits of a dictionary cache: it lives in one process, it disappears on restart, and it shares memory with your application. Those limits are acceptable for configuration data, small computed results, and per-process data. When you need sharing across processes, persistence across restarts, or larger capacity, you move to a shared cache or a disk-backed cache, which are covered next. Starting with a dictionary, and outgrowing it for clear reasons, is a healthy path. It means you understand what you need, because you have felt the limits yourself.

import time

# A dictionary cache with expiry: value plus an expiry time.
store = {}

def cache_set(key, value, ttl):
    store[key] = (value, time.time() + ttl)

def cache_get(key):
    item = store.get(key)
    if item is None:
        return None
    value, expires = item
    if time.time() > expires:
        del store[key]
        return None
    return value

cache_set("homepage", "<h1>Hi</h1>", 300)
print(cache_get("homepage"))

Section 24: Caching with Files on Disk

Not all caches live in memory. Some live on disk, as files, and disk caches have their own strengths. The main one is persistence: files survive a restart, so a disk cache does not suffer a cold start when the application restarts. The main weakness is speed: reading from disk is slower than reading from memory, though still much faster than a database query or an outside call. Disk caches are a good middle ground when you need persistence, or when the cached data is large, such as rendered pages, images, or generated files, and would use too much memory to hold in RAM.

A simple disk cache works like this: each cache entry is a file, named after its key, containing the value, plus perhaps metadata like an expiry time. To read an entry, your code checks whether the file exists, reads it, and checks whether it has expired. To write an entry, your code writes the file. To delete an entry, it deletes the file. That is the whole system, and it can be built with Python's standard library, using the filesystem and a safe way to turn keys into filenames, such as hashing the key. Hashing matters, because keys can contain characters that are not valid in filenames, and because very long keys would make unwieldy filenames.

Disk caches need the same care as memory caches: expiry, size limits, and cleanup. Expired files that are never requested will accumulate, filling the disk, so a periodic cleanup job should remove them. Size limits matter even more on disk, because disks fill up too, and a full disk can break an application in many ways at once. A simple size policy is to track total cache size, and when it exceeds a limit, delete the oldest or least recently used files until it fits. That policy is easy to implement with file modification times, and it keeps the cache bounded without constant attention.

There is also a question of what kind of data suits a disk cache. Large, rarely changing, expensive-to-produce data is ideal: a generated report file, a rendered page, a processed image. Small, frequently accessed data is better in memory, because disk reads, while fast compared to a database, are still slower than memory, and the overhead of opening a file for a tiny value can outweigh the benefit. A common pattern is two layers: a small memory cache in front of a larger disk cache, so hot items are served from memory and colder items from disk, with the database as the final fallback. Layered caches like that give you the best of both worlds, at the cost of a little extra code.

Finally, disk caches share a lesson with all caches: the cache directory must be managed. It should live in a place with enough space, it should not be backed up as if it were precious data, because it can always be rebuilt, and it should be excluded from deployments, so that old cached files do not ship with new code. A cache is a performance tool, not a data store, and treating it as disposable, rebuildable, and bounded is what keeps it helpful rather than hazardous.

import hashlib, os

# A disk cache: one file per entry, named by a hash of the key.
CACHE_DIR = "/tmp/simple-cache"
os.makedirs(CACHE_DIR, exist_ok=True)

def cache_path(key):
    name = hashlib.sha256(key.encode()).hexdigest()
    return os.path.join(CACHE_DIR, name)

def disk_set(key, value):
    with open(cache_path(key), "w") as f:
        f.write(value)

def disk_get(key):
    path = cache_path(key)
    if os.path.exists(path):
        with open(path) as f:
            return f.read()
    return None

disk_set("homepage", "<h1>Hi</h1>")
print(disk_get("homepage"))

Section 25: SQLite as a Simple Cache Store

SQLite, which you already know as a small database, also makes an excellent simple cache store, and it is worth considering before reaching for a dedicated cache service. A SQLite cache is a table with columns for the key, the value, and an expiry time. Reading an entry is a query by key. Writing an entry is an insert or replace. Deleting expired entries is a delete by time. That is the whole system, and it has several advantages over a dictionary or a file cache: it persists across restarts, it can be queried and inspected with ordinary SQL, it handles concurrent access better than hand-rolled files, and it is already available in Python's standard library.

A SQLite cache also gives you features that are harder to build by hand. You can index the key column, so lookups are fast even with many entries. You can query by expiry time to clean up old entries in one statement. You can count entries, measure total size, and find the oldest entries, all with simple queries. And you can store structured values, such as JSON text, and query parts of them if needed. That inspectability is a real advantage during debugging: when a cache behaves strangely, you can open the database and look at exactly what is stored, which is much harder with a memory cache that vanishes on restart.

There are limits, and they should be stated plainly. SQLite is a file-based database, so it is slower than a memory cache, though still fast for most purposes. It is not designed for very high concurrency across many processes, though it handles moderate use well. And it shares a disk with your application, so a cache that grows without limits can fill the disk, just like a file cache. The same disciplines apply: expiry on every entry, size limits, and periodic cleanup. A SQLite cache that is managed well is a reliable, inspectable, persistent cache. One that is unmanaged will grow and slow down, like any other.

When should you choose SQLite as a cache? When you need persistence, when you want inspectability, when your application is small or medium in size, and when you do not want to add a new service to your infrastructure. A personal project, a small team application, or a learning project all fit that description. When should you move beyond it? When you need very high throughput, when many servers must share one cache, or when cache operations must be extremely fast, in which case a dedicated in-memory cache service is the standard next step. The move is not a failure of SQLite. It is a sign your application has grown, and growth is a good problem to have.

A final practical tip: keep your cache table separate from your application data, ideally in its own database file. That separation makes it clear that cache data is disposable: you can delete the file, and the application will rebuild it. It also prevents cache operations from interfering with your main data, and it makes backups simpler, because you do not need to back up a cache. A cache you can delete without fear is a cache you can manage confidently.

import sqlite3, time

# A SQLite cache table: key, value, expiry time.
db = sqlite3.connect("/tmp/cache.db")
db.execute("CREATE TABLE IF NOT EXISTS cache (key TEXT PRIMARY KEY, value TEXT, expires REAL)")
db.execute("INSERT OR REPLACE INTO cache VALUES (?, ?, ?)",
           ("homepage", "<h1>Hi</h1>", time.time() + 300))
row = db.execute("SELECT value FROM cache WHERE key=? AND expires > ?",
                 ("homepage", time.time())).fetchone()
print(row[0] if row else None)

Section 26: Cache Size Limits and Eviction

Every cache has a limit, because memory and disk are finite, and an unbounded cache will eventually consume all available resources and crash the application it was meant to speed up. Cache size limits are therefore not an optional extra. They are a core part of cache design, and the policy for what happens when the limit is reached is called eviction. Eviction is the decision, made when the cache is full and a new entry arrives, about which old entry to throw away. That decision has a large effect on hit rate, because throwing away an entry that will be requested again soon causes a miss, while throwing away an entry nobody wants costs nothing.

The simplest size limit is a count: the cache holds at most a thousand entries, and when it is full, one must go before a new one is stored. A more precise limit is total size in bytes, which matters when entries vary greatly in size: a cache holding a few large pages and many small fragments needs a byte limit, not a count limit, or the large pages will dominate. Some caches limit both: at most a thousand entries and at most a hundred megabytes, whichever is reached first. The right limit depends on your resources and your data, but the principle is the same: pick a limit your system can afford, enforce it always, and never let the cache grow beyond it.

Eviction policies are the rules for choosing what to throw away, covered in detail in the next sections. The goal is to keep entries most likely to be requested again, and throw away the ones least likely. Predicting future requests is impossible, so policies use proxies: how recently an entry was used, how often it has been used, or how long it has been in the cache. Each proxy is a guess about the future based on the past, and different guesses suit different access patterns.

Eviction also interacts with expiry. An expired entry is already useless, so it should be removed before any live entry is evicted. A cache that evicts live entries while holding expired ones is wasting its space. The cleanup order should therefore be: first remove expired entries, then, if still full, evict according to policy. That order is simple, but it is easy to forget when implementing a cache by hand, and forgetting it causes a cache to perform worse than it should, for no good reason.

Finally, size limits should be monitored. Track how full the cache is, how often evictions happen, and whether evicted entries are soon requested again, which would show up as misses shortly after eviction. A cache that is constantly full and constantly evicting is probably too small for its working set, and increasing its size, if resources allow, will improve the hit rate more than any policy change. A cache that is never full is oversized, and its limit could be reduced to free resources. Monitoring turns size limits from a guess into a tuned setting, adjusted as your application grows.

# Enforce a size limit: when full, evict before storing.
MAX_ENTRIES = 3
cache = {"a": 1, "b": 2, "c": 3}

def store(key, value):
    if len(cache) >= MAX_ENTRIES and key not in cache:
        oldest = next(iter(cache))
        del cache[oldest]
        print(f"Evicted {oldest} to make room")
    cache[key] = value

store("d", 4)
print(cache)

Section 27: LRU: Least Recently Used

LRU, which stands for Least Recently Used, is the most widely used eviction policy, and it is worth understanding thoroughly, because you will meet it in many systems, from Python's lru_cache to dedicated cache services. The rule is simple: when the cache is full and a new entry must be stored, throw away the entry that has not been used for the longest time. The reasoning is that an entry unused for a long time is less likely to be needed again than an entry used recently. Recent use is taken as a predictor of future use, which is a reasonable guess for many workloads, where popular items stay popular for a while.

Implementing LRU is straightforward in concept, though the details require care. The cache must track, for each entry, when it was last used, and using an entry means both reading it and writing it. Every hit updates the entry's position, moving it to the "most recently used" end. Every eviction removes from the "least recently used" end. Python's standard library provides an OrderedDict, which maintains insertion order and can move an entry to the end on access, making a simple LRU cache easy to build. That built-in support is one reason LRU is so popular: it is simple to implement correctly, and its behaviour is easy to reason about.

LRU works well when access patterns have locality, which is a fancy way of saying that recently used items tend to be used again soon. Web traffic often has this property: a popular article is read many times in a short period, a homepage is visited constantly, a common query is repeated. For those patterns, LRU keeps the hot items and discards the cold ones, giving a high hit rate. It works poorly when access patterns are scans, where each item is used once and never again, such as a process that reads through a large list in order. In a scan, LRU will fill the cache with items that will never be reused, evicting genuinely popular items in the process. That failure mode, called cache pollution, is worth knowing, because it explains why LRU is not perfect for every workload.

There are variations that address LRU's weaknesses. One is to split the cache into sections, or to protect entries that have been used more than once, so that a single scan cannot evict popular items. Another is to combine recency with frequency, keeping items that are both recent and frequent. Those variations are more complex, and they are used in larger systems, but the core idea remains LRU: recent use predicts future use. For a learner, and for most small applications, plain LRU is an excellent default, and it is the policy to reach for first.

Finally, remember that LRU is a policy, not a guarantee. It improves the odds of keeping useful entries, but it cannot know the future. A cache with LRU and a good size will perform well. A cache with LRU but too small a size will still miss often, because even the best policy cannot keep a working set larger than the cache itself. Size and policy work together: size determines what is possible, policy determines how close you get to it. Tune both, and measure the result.

from collections import OrderedDict

# LRU with OrderedDict: hits move entries to the end; eviction takes from the front.
cache = OrderedDict()
for key in ["a", "b", "c"]:
    cache[key] = key
cache.move_to_end("a")  # "a" was just used, so it is now most recent
print("Order (least to most recent):", list(cache))
print("Evict first:", next(iter(cache)))

Section 28: FIFO and Other Eviction Rules

LRU is popular, but it is not the only eviction policy, and knowing the alternatives helps you choose wisely and understand cache behaviour when you meet a system that uses a different rule. The simplest policy is FIFO, First In, First Out: when the cache is full, throw away the entry that has been in the cache the longest, regardless of how recently it was used. FIFO is easy to implement, because it only needs insertion order, not access tracking, and it is fair in a simple sense: every entry gets the same maximum lifetime in the cache, unless it expires first. Its weakness is that it can evict a very popular entry simply because it arrived early, even if it was used a second ago.

A close cousin of FIFO is LIFO, Last In, First Out, which evicts the most recently added entry. LIFO is rarely used for caches, because it tends to keep old, possibly stale entries while discarding fresh ones, which is the opposite of what you usually want. It appears here mainly as a contrast: the fact that LIFO is a bad cache policy shows that eviction is not just about picking any rule. The rule must match the goal, which is keeping entries likely to be reused, and LIFO fails that test for most workloads. Knowing a bad policy helps you recognise one when you see it.

Another policy is LFU, Least Frequently Used, which evicts the entry used the fewest times. Its reasoning is that frequency predicts future use better than recency: an entry used a hundred times is likely to be used again, even if it was not used in the last hour, while an entry used once is probably a one-off. LFU works well for stable popularity, such as reference data. Its weakness is slow adaptation: an item popular last year but now forgotten keeps a high count and occupies space, while a newly popular item struggles to build its count.

Random eviction is simpler than it sounds: when full, throw away a random entry. Random eviction is surprisingly reasonable for some workloads, because it avoids the pathological cases of other policies, and it costs almost nothing to implement. It is not as good as LRU or LFU for workloads with clear patterns, but it is far better than no policy, and it is a useful baseline. If a fancy policy does not beat random eviction by a clear margin, the fancy policy is probably not worth its complexity. That test, comparing against random, is a healthy scepticism to apply to any optimisation.

In practice, many systems combine policies, or let you choose per cache. A cache for session data might use LRU. A cache for reference data might use LFU. A small, simple cache might use FIFO, because it is easy and good enough. The lesson is not to memorise every policy, but to understand that eviction is a choice, that different choices suit different data, and that the choice should be deliberate and measured, not accidental. Start with LRU, measure, and change only if the numbers say another policy would serve your data better.

# FIFO eviction: the oldest arrival goes first, however popular it is.
from collections import OrderedDict

cache = OrderedDict([("old-popular", 1), ("mid", 2), ("new", 3)])
evicted, _ = cache.popitem(last=False)
print("FIFO evicted:", evicted)

Section 29: Measuring Cache Performance: Hit Rate

You cannot improve a cache you do not measure, and the primary measurement is the hit rate: the share of cache lookups that find an entry. A hit rate of ninety percent means nine out of ten lookups were served from the cache. A hit rate of fifty percent means half the lookups still did fresh work. Hit rate is simple, easy to compute, and directly related to the benefit of the cache: a higher hit rate means more work saved, more load removed from the source, and faster responses for more users. It is the first number to check whenever you add, change, or debug a cache.

Hit rate alone, however, does not tell the whole story, and a thoughtful developer looks at a few more numbers alongside it. Latency, the time a request takes, is the ultimate measure: a cache that improves hit rate but does not improve latency is not helping users, perhaps because the cached items were already fast, or because cache lookups themselves are slow. Source load, the number of requests reaching the database or outside service, is another key number: a good cache should visibly reduce it. And error rate matters too: a cache that serves stale or wrong data might show a wonderful hit rate while harming users, which is why hit rate must be read alongside freshness checks and user feedback.

Measuring hit rate is straightforward: count hits and misses. Most cache systems expose those counters automatically, and for a hand-built cache, two variables and a division are all you need. Report the rate over a sensible period, such as the last hour or day, rather than since the cache started, because a lifetime average hides recent changes. A cache whose hit rate was ninety percent last month and fifty percent this week has a problem, but a lifetime average might still show eighty percent and look healthy. Recent windows reveal trends, and trends are what you act on.

There are also more detailed measurements that help diagnose problems. Hit rate per key pattern, such as per page type or per endpoint, shows which parts of your cache work well and which do not. A homepage cache with a ninety-five percent hit rate and a search cache with a ten percent hit rate tells you to focus on search, not on the homepage. Miss reasons, whether cold, capacity, or expiry, tell you whether to warm, enlarge, or lengthen lifetimes. Those breakdowns turn a single number into actionable insight, and they are worth building as your system grows.

Finally, set expectations honestly. A hit rate of one hundred percent is impossible, because the first request for each item must miss, and because data changes. A hit rate of ninety percent is excellent for many workloads. A hit rate of fifty percent might be excellent for a workload where each item is requested twice on average, because the theoretical maximum is fifty percent in that case, once to fill and once to hit. Judge a hit rate against what is possible for your data, not against an abstract ideal. Measure, compare against your own history, and improve steadily, rather than chasing a perfect number that your workload cannot reach.

# Hit rate over a recent window, not since the beginning of time.
hits, misses = 900, 100
hit_rate = hits / (hits + misses)
print(f"Hit rate: {hit_rate:.0%} ({hits} hits, {misses} misses)")

Section 30: When Caching Makes Things Slower

Caching is supposed to make things faster, but it can sometimes make them slower, and knowing when that happens prevents a common disappointment: adding a cache and finding performance got worse. The most direct cause is overhead. Every cache lookup costs something: a function call, a dictionary check, a network trip to a shared cache, or a file read. If the work being cached is itself very cheap, such as adding two numbers or formatting a short string, the lookup can cost more than the work, and the cache becomes pure overhead. Caching is only worthwhile when the work saved is clearly larger than the cost of the lookup, with a comfortable margin.

A second cause is a low hit rate. If a cache rarely hits, almost every request pays both the lookup cost and the fresh-work cost, making it slower than fresh work alone. Low hit rates happen when cached items are rarely reused, when lifetimes are too short, when the cache is too small, or when keys are wrong, so the same item is stored under different keys and never found. A cache with a low hit rate is not just useless. It is actively harmful, and the fix is either to improve the hit rate, by caching better candidates with better keys and lifetimes, or to remove the cache entirely. Removing a bad cache is a respectable decision, and it is better than keeping it out of pride.

A third cause is contention and serialisation. A shared cache accessed by many processes can become a bottleneck itself, if every request must wait for the cache, or if storing large values takes significant time to transmit. A cache that stores huge values, such as multi-megabyte pages, can spend more time moving data in and out than the database would have spent generating it. Keeping cached values reasonably sized, and caching at the right level, such as query results rather than giant pages, avoids this. Large values also consume cache capacity quickly, evicting many small, useful entries, which lowers the overall hit rate.

A fourth cause is complexity and bugs. Cache code can introduce subtle errors: stale data, key collisions, invalidation mistakes, and stampede behaviour, all of which can make an application slower in practice, because users retry, support tickets increase, and developers spend time debugging instead of improving. A system that is simple and a little slow is often better than a system that is complex, nominally fast, and frequently wrong. Complexity has a cost, and caching adds complexity, so it should be added where the benefit is clear and measured, not everywhere on principle.

The lesson is to treat caching as an experiment, not as an article of faith. Before adding a cache, measure the current performance. After adding it, measure again, including hit rate, latency, and source load. If the numbers improve, keep it. If they do not, adjust or remove it. That discipline, measure before and after, is what separates effective optimisation from guesswork, and it applies to every performance technique, not just caching. A cache that does not make things measurably better is not a cache. It is decoration.

# Caching only helps when the work saved exceeds the lookup cost.
work_cost_ms = 0.01   # very cheap work
lookup_cost_ms = 0.05  # cache lookup costs more than the work
print("Cache helps:", work_cost_ms > lookup_cost_ms)

Section 31: Caching and Changing Data

Caching and changing data are in tension, and managing that tension is the central challenge of this chapter. Caching wants copies to live long, because long-lived copies give high hit rates and fast responses. Changing data wants copies to die young, because a changed fact should be visible immediately. Every caching decision is a compromise between those two desires, and the right compromise depends on the data, the users, and the consequences of staleness. There is no single answer, but there is a reliable way to think about it, and this section sets it out.

Start by classifying your data by how it changes. Some data never changes after creation, such as a published article's original version, a historical record, or a file that is versioned by name. That data can be cached for a very long time, even forever, because it cannot become stale. Some data changes rarely, such as a category list or a help page, and can be cached for hours with little risk. Some data changes often, such as a task list or a comment thread, and should be cached briefly, if at all. Some data changes constantly and critically, such as a balance or a seat count, and should not be cached. Classifying data this way, before choosing TTLs, prevents most staleness problems, because the lifetime follows the nature of the data.

Next, think about who changes the data and who reads it. When the same user changes their own data and then reads it, they expect to see the change immediately, and staleness is very noticeable. That is why invalidating a user's own cached data on their own change is so important. When one user changes data that many others read, such as an editor updating a public article, a brief delay is usually acceptable, because readers do not know the exact moment of the change. The relationship between writer and reader shapes the tolerance for staleness, and designing for the most sensitive relationship, usually the owner reading their own data, covers the rest.

Next, consider the pattern of changes. Data that changes in bursts, such as a news site during a major event, needs different handling from data that changes steadily. During a burst, short TTLs and active invalidation matter more, because staleness accumulates quickly. Data that changes on a schedule, such as a daily report, can be cached until the next scheduled change, with warming to prepare the new version. Understanding the rhythm of change lets you set lifetimes that match reality, rather than guessing. A cache tuned to the rhythm of its data is a cache that rarely surprises anyone.

Finally, build a habit of reviewing caching decisions when data behaviour changes. A feature that was read-only becomes editable. A page that was updated monthly starts updating hourly. A private page becomes public, or vice versa. Each change alters the caching calculus, and if the cache configuration does not change with it, staleness or leaks will follow. When you change how data behaves, ask: does this affect any cache? Which entries, which lifetimes, which keys? That question, asked consistently, is the cheapest form of cache maintenance there is.

# Classify data by change rate, then choose a lifetime to match.
change_rate = {"historical record": "never", "category list": "rarely",
               "task list": "often", "live balance": "constantly"}
ttl = {"never": "forever", "rarely": "hours", "often": "minutes",
       "constantly": "do not cache"}
for item, rate in change_rate.items():
    print(item, "->", ttl[rate])

Section 32: Write-Through Caching

Write-through caching is a pattern for handling writes, which is the other half of caching that beginners often overlook. So far, this chapter has mostly discussed reads: serving data from a cache. But data also changes, and when it changes, both the cache and the source must be updated, or they will disagree. Write-through is the simplest consistent approach: when your code writes data, it writes to the cache and to the source, in the same operation, before reporting success. After a write-through write, the cache and the source agree, and later reads can use the cache confidently.

The main advantage of write-through is consistency. Because every write updates both places, a reader can never find a stale copy that predates a completed write, as long as reads use the cache correctly. That guarantee is valuable for data where correctness matters more than write speed, such as user settings or account details. The main disadvantage is write latency: every write now does two operations instead of one, so writes are slower. For data that is written rarely and read often, that trade is excellent: you pay a little on rare writes to gain a lot on frequent reads. For data written constantly, the double-write cost adds up, and another pattern may fit better.

Write-through also simplifies invalidation, in a sense, because it replaces invalidation with updating. Instead of deleting a cached entry when data changes and waiting for the next read to rebuild it, write-through updates the entry immediately, so the next read is a hit on fresh data. That is elegant, but it requires care: the cached value must be built correctly at write time, which means the write path must know how the cached value is shaped. If the cached value is a complex page or a computed result, building it on every write may be expensive, and invalidating, letting the next read rebuild it, may be cheaper. Write-through fits best when the cached value is simple, such as a single record or a small object.

There is also a failure question: what happens if the cache write succeeds but the source write fails, or vice versa? A careful implementation must handle partial failure, usually by treating the source as the truth and the cache as disposable: if the source write fails, the cache entry should be removed, not left holding a value the source does not have. If the cache write fails but the source succeeds, the system can continue, because the next read will miss and rebuild from the source, though it should log the cache failure. Designing for partial failure is what makes write-through robust rather than merely tidy.

Finally, write-through is a pattern, not a product. You can implement it with a dictionary, with SQLite, or with a shared cache service, using the same idea: write to both places, treat the source as truth, handle partial failure. Larger systems often use a cache service that supports write-through natively, but the concept is identical. Understanding it at a small scale prepares you for the larger scale, and it gives you a precise tool for the common case where reads are frequent, writes are rare, and correctness matters.

# Write-through: update the source and the cache together.
source = {}
cache = {}

def write(key, value):
    source[key] = value
    cache[key] = value
    return "written to both"

print(write("user:42:name", "Ada"))
print("Cache now agrees with source:", cache == {"user:42:name": "Ada"})

Section 33: Write-Behind Caching

Write-behind caching, also called write-back caching, takes the opposite approach to write-through: when your code writes data, it writes only to the cache, reports success immediately, and lets the cache write to the source later, in the background. That makes writes very fast, because the caller does not wait for the slower source, such as a database on disk. It also batches writes: if the same entry is written several times quickly, only the final value may need to reach the source, saving work. For workloads with many writes, such as logging, counters, or session updates, write-behind can be dramatically faster than writing through every time.

The price of that speed is risk. Between the cache write and the later source write, the data exists only in the cache. If the cache crashes, or the process restarts, before the source is updated, the data is lost. That risk is acceptable for data that can be recreated or that is not critical, such as a view counter or a temporary session value. It is not acceptable for data that must never be lost, such as a payment, an order, or a password change. Choosing write-behind means accepting a window of potential loss, and that window must be understood and bounded. A write-behind cache that flushes to the source every few seconds has a window of a few seconds. One that flushes every hour has a window of an hour, and a much larger risk.

Write-behind also adds complexity around ordering and failure. If writes arrive in a particular order, they must reach the source in that order, or the final state may be wrong. If a source write fails, the cache must retry, and must not discard the data while retrying. If the cache fills up with unflushed writes, it must either flush faster or slow down new writes, or it will run out of space. These are solvable problems, and dedicated cache systems solve them, but they are real engineering, not free behaviour. A hand-built write-behind cache that ignores them will lose data in exactly the situations where reliability matters most.

For a learner, the key lesson is not to implement write-behind from scratch, but to recognise it and judge it. When a system promises very fast writes, ask where the data is actually stored, and what happens if the cache crashes before flushing. If the answer is that data could be lost, ask whether that data can afford to be lost. If it cannot, write-behind is the wrong pattern, however fast it looks. Speed gained by risking data loss is not performance. It is a gamble, and it should be taken only when the stakes are low and the gamble is explicit.

In practice, most applications use write-through, or no cache on writes at all, and reserve write-behind for specific, well-understood cases: counters, analytics, session activity, and other data where approximate or recreatable values are acceptable. That restraint is wise. Write-behind is a powerful tool, but its power comes with a risk that must be respected. Use it where loss is tolerable, flush promptly, monitor the queue of unflushed writes, and never use it for data your users cannot afford to lose.

# Write-behind: fast cache write now, source write later (risk: loss before flush).
cache = {}
pending = []

def write_behind(key, value):
    cache[key] = value
    pending.append((key, value))
    return "written to cache, source update pending"

def flush(source):
    while pending:
        key, value = pending.pop(0)
        source[key] = value

print(write_behind("page_views", 101))
print("Pending source writes:", len(pending))

Section 34: Cache-Aside: The Application Manages It

Cache-aside, also called lazy loading, is the most common caching pattern in application code, and it is the pattern you have been using throughout this chapter, perhaps without knowing its name. In cache-aside, the application itself manages the cache: on a read, it checks the cache, and on a miss, it reads from the source, stores the result in the cache, and returns it. On a write, the application updates the source and deletes, or updates, the affected cache entries. The cache itself is passive: it stores what it is given and returns what it holds. All the intelligence lives in the application code, which decides what to cache, when to invalidate, and how keys are built.

The main advantage of cache-aside is control and simplicity. The application decides everything, so the pattern works with any cache store, from a dictionary to a shared service, without needing special features from the store. It is also easy to understand and debug, because the caching logic is visible in your code, in the same place as the data access logic. For a learner, and for most small to medium applications, cache-aside is the right default, because it is transparent: you can read the code and see exactly when the cache is checked, filled, and cleared. Transparency is a virtue in systems that must be maintained over time.

The main disadvantage is that the application must remember to do everything. Every read path must check the cache. Every write path must invalidate or update the affected entries. Miss one path, and stale data appears, or the cache is bypassed. As an application grows, with many developers and many data paths, that discipline becomes harder to maintain, and missed invalidations become more likely. That is why larger systems sometimes move to patterns where the cache itself handles more of the work, such as read-through or write-through caches provided by a service. But those patterns trade control for convenience, and they are worth adopting only when the discipline of cache-aside becomes a genuine burden.

Cache-aside also has a characteristic failure mode worth knowing: on a miss, every concurrent request for the same item will read from the source and store the result, duplicating work. That is a mild form of the stampede problem, and it is usually harmless for small systems, but it can matter for very popular items. The mitigations are the ones you already know: locks, stale-while-revalidate, and warming. A cache-aside system with those mitigations for its hottest items is a robust system, and it remains simple enough to understand.

Finally, cache-aside teaches a design lesson that goes beyond caching: putting logic in the application, where it is visible, versus putting it in infrastructure, where it is automatic but opaque. Neither is always right. Application logic is flexible and debuggable. Infrastructure logic is consistent and less error-prone across many code paths. The right choice depends on scale, team size, and how much you trust each layer. Starting with cache-aside, and moving to infrastructure-managed patterns when the burden justifies it, is a sensible path that many successful systems have followed.

# Cache-aside: the application checks, fills, and invalidates.
source = {"article_12": "Fresh text"}
cache = {}

def read(key):
    if key in cache:
        return cache[key], "hit"
    value = source[key]
    cache[key] = value
    return value, "miss, now cached"

def write(key, value):
    source[key] = value
    cache.pop(key, None)  # invalidate so the next read is fresh

print(read("article_12"))
print(read("article_12"))

Section 35: Read-Through Caches

A read-through cache is one where the application asks the cache for data, and if the cache does not have it, the cache itself fetches it from the source, stores it, and returns it. From the application's point of view, there is only one step: ask the cache. The miss handling, the source fetch, and the storing are all hidden inside the cache layer. That is the opposite of cache-aside, where the application does all of that work itself. Read-through simplifies application code, because every read looks the same, whether it hits or misses, and the application never talks to the source directly for cached data.

The advantage is consistency and simplicity across many code paths. With cache-aside, every read path must implement the check-fill logic correctly, and a forgotten path bypasses the cache or, worse, serves stale data. With read-through, the logic lives in one place, the cache layer, and every path benefits automatically. That consistency is valuable in larger applications, where many developers write data access code, and where a single missed cache check is a bug waiting to happen. It also makes it easier to change caching behaviour globally, such as adjusting TTLs or switching stores, because the change is in one layer, not scattered across the application.

The disadvantage is that the cache layer must know how to fetch from the source, which means it needs a loader function or a connection to the source, and that coupling can be awkward. The cache is no longer a passive store. It is an active participant that understands your data sources, which makes it more complex and harder to replace. It also means that a cache failure can become a data failure: if the cache layer is down, the application cannot reach the source through it, even though the source itself is healthy. With cache-aside, the application can fall back to the source directly if the cache fails. With read-through, that fallback requires extra design.

Read-through also interacts with writes in a specific way. Typically, a read-through cache is paired with write-through, so that writes update both the cache and the source, keeping them consistent, or with invalidation, so that writes delete cached entries and the next read reloads them through the cache. The pairing matters, because a read-through cache that is never invalidated will serve stale data indefinitely, just like any other cache. The pattern does not solve invalidation. It only moves the read logic into the cache layer. Invalidation remains the application's, or the write path's, responsibility.

For a learner, the practical takeaway is to recognise read-through when you meet it, and to understand its trade: simpler application code and more consistent behaviour, in exchange for a smarter, more coupled cache layer and a new failure mode. Many dedicated cache services and libraries offer read-through as an option, and it is a good choice when many code paths need the same data and consistency matters. For a small application with a few paths, cache-aside is simpler and more transparent. Choose based on how many paths you have and how much you value consistency over simplicity.

# Read-through: the application asks the cache; the cache loads on a miss.
source = {"article_12": "Fresh text"}
cache = {}

def cache_read(key):
    if key not in cache:
        cache[key] = source[key]  # the cache itself loads from the source
    return cache[key]

print(cache_read("article_12"))  # miss, loaded, returned
print(cache_read("article_12"))  # hit

Section 36: HTTP Cache Headers: Cache-Control

HTTP, the protocol of the web, has caching built into it, through headers that servers send with responses. The most important of these is Cache-Control, a header that tells browsers, CDNs, and other shared caches how a response may be cached, for how long, and under what conditions. Learning Cache-Control is one of the highest-value skills in this chapter, because it gives you browser and CDN caching behaviour, which are powerful layers, simply by setting a header correctly, without writing cache code of your own. A single header can make repeat visits dramatically faster.

Cache-Control is made of directives, which are short instructions separated by commas. The most common are max-age, which sets the lifetime in seconds, public, which says shared caches may store the response, private, which says only the user's browser may store it, and no-store, which says the response must not be cached at all. A header like "public, max-age=3600" means any cache may store this response for one hour. A header like "private, max-age=0" means only the browser may store it, and it must revalidate immediately. A header like "no-store" is for sensitive responses, such as a page containing personal data or a security token, which must never be stored anywhere.

Choosing directives follows the same rules as choosing TTLs and shared versus private, because Cache-Control is just those decisions expressed in HTTP. Public data that changes rarely gets a long max-age and public. Private data gets private, with a short max-age or none. Sensitive data gets no-store. Static files with versioned names get a very long max-age and public, because a changed file is a new file. The HTML page that references them gets a short max-age or no-cache, so users always get the latest page. Those patterns, applied consistently, give you a fast, fresh web application with very little code.

Two directives deserve special attention because they are often confused. No-cache does not mean "do not cache". It means "cache, but revalidate with the server before reusing", which is a subtle but important difference. A no-cache response may be stored, but it must be checked with the server, using a validator like an ETag, before it is served again. No-store means "do not store this at all", which is stronger, and is the right choice for truly sensitive data. Mixing them up is a common mistake: using no-cache for sensitive data still stores it, which may be unacceptable, while using no-store for ordinary data throws away a useful optimisation.

Finally, Cache-Control headers are set by your server, which means they are part of your back-end code, even though they control browser behaviour. In Python, using http.server or any framework, you set them as response headers alongside the content. Test them: request a page, inspect its headers, and confirm they say what you intend. Headers are easy to get wrong, and a wrong header can cache private data publicly or prevent caching entirely, both of which are serious. A few minutes checking headers saves hours debugging mysterious browser behaviour later.

# Cache-Control examples: what each header tells caches to do.
headers = {"public file": "public, max-age=31536000",
           "private page": "private, max-age=0",
           "sensitive data": "no-store"}
for name, value in headers.items():
    print(name, "->", value)

Section 37: ETag and Conditional Requests

An ETag, or entity tag, is a short identifier that a server attaches to a response, representing the current version of that resource. Think of it as a fingerprint for the content: if the content changes, the fingerprint changes, and if the content is the same, the fingerprint is the same. ETags enable conditional requests, which are a clever way to avoid downloading data that has not changed. Instead of asking "give me the page", a client that already has a copy asks "give me the page, but only if it has changed since this fingerprint". If it has not changed, the server replies with a short "not modified" response, and the client reuses its copy. That saves bandwidth and time, without risking staleness.

Here is how the conversation works. On the first request, the server sends the resource with an ETag header, such as a hash of the content. The client stores both the content and the ETag. On a later request, the client sends the ETag back in an If-None-Match header, saying "I have the version with this fingerprint". The server compares the fingerprint with the current version. If they match, the resource has not changed, and the server replies with status 304, Not Modified, and no body. The client then uses its stored copy, which it knows is still current, because the server just confirmed it. If the fingerprints differ, the server sends the new content with a new ETag, and the client replaces its copy.

ETags are powerful because they give you freshness without re-downloading. A page that is checked often but changes rarely will mostly produce 304 responses, which are tiny compared to full pages, saving bandwidth and server work. They also solve a problem that TTLs cannot: TTLs guess when data might have changed, while ETags know. A resource with a short TTL but an ETag can be revalidated cheaply and often, giving both freshness and efficiency. That combination, a short max-age plus an ETag, is a common pattern for pages that change unpredictably but not constantly.

Generating ETags is straightforward. A hash of the content is the usual method: if the content is the same, the hash is the same, and if the content changes, the hash changes. For dynamic content, you can hash the rendered output, or use a version number or timestamp from the underlying data, as long as it changes whenever the content changes. A weak ETag, marked with a W/ prefix, means the content is semantically the same even if the bytes differ slightly, which is useful for content where minor differences do not matter. For a learner, a strong ETag based on a content hash is the simplest correct approach.

ETags also have a second use: preventing lost updates. When a client wants to update a resource, it can send the ETag it based its change on, and the server can refuse the update if the resource has changed since, preventing one user from overwriting another's changes unknowingly. That use, called optimistic concurrency, is more advanced, but it shows how versatile a version fingerprint can be. ETags are a small mechanism with large benefits, and they are worth adding to any API or site where clients re-request the same resources.

import hashlib

# An ETag is a fingerprint of the content: same content, same tag.
def etag(content):
    return '"' + hashlib.sha256(content.encode()).hexdigest()[:16] + '"'

print(etag("Hello, world"))
print(etag("Hello, world"))   # unchanged, same tag
print(etag("Hello, again"))   # changed, different tag

Section 38: Last-Modified and Freshness

Before ETags, there was Last-Modified, an older but still useful HTTP mechanism for freshness. When a server sends a resource, it can include a Last-Modified header giving the date and time the resource last changed. On a later request, the client can send that date back in an If-Modified-Since header, saying "only send me the resource if it has changed since this date". If it has not changed, the server replies with 304 Not Modified, just like with ETags, and the client reuses its copy. If it has changed, the server sends the new version. Last-Modified is simpler than ETags, and it works well for resources that have a clear modification time, such as files on disk.

Last-Modified has limitations that ETags do not. Its resolution is one second, so changes within the same second may not be detected, which matters for fast-changing resources. It relies on the server's clock and the resource's timestamp being accurate, which is not always true, especially when files are copied or restored. And it cannot distinguish between a resource that was rewritten with identical content and one that truly changed, because the timestamp changes even if the content does not, causing an unnecessary re-download. ETags, based on content, handle all of these cases better, which is why they are generally preferred for dynamic content.

Despite those limitations, Last-Modified remains useful and widely supported, and it is often sent alongside an ETag, giving clients two ways to validate. For static files, the file's modification time is a natural Last-Modified value, and it costs nothing to send. For dynamic content, a timestamp from the underlying data, such as the last time an article was edited, can serve the same purpose. The key requirement is honesty: the Last-Modified value must reflect when the content actually changed, not when the server happened to generate it, or clients will revalidate incorrectly and either miss changes or re-download unnecessarily.

There is also a related concept worth knowing: the Expires header, an older way to set a lifetime, giving an absolute date after which a response is stale. Cache-Control's max-age has largely replaced Expires, because a relative lifetime in seconds is easier to reason about than an absolute date, which depends on clocks agreeing. If both are present, max-age takes precedence. For a learner, the practical rule is to use Cache-Control for lifetimes, ETags for validation, and Last-Modified as a helpful extra for static or timestamped resources, not as the primary mechanism.

Finally, remember that these headers work together as a system, not in isolation. A typical well-configured response might carry Cache-Control with a max-age, an ETag, and a Last-Modified header. For the max-age period, clients reuse the copy without asking. After that, they revalidate with the ETag or date, getting a cheap 304 if nothing changed. That combination gives speed, freshness, and bandwidth savings together, which is the goal of HTTP caching. Learning to set these headers correctly is one of the most practical skills in web back-end development, because it improves every client that talks to your server.

# Last-Modified validation: send 304 if nothing changed since the client's date.
from datetime import datetime

last_modified = datetime(2026, 10, 30, 12, 0, 0)
client_date = datetime(2026, 10, 30, 12, 0, 0)
if client_date >= last_modified:
    print("304 Not Modified: client copy is still current")
else:
    print("200 OK: sending new version")

Section 39: Caching Static Files

Static files are files that do not change per request: images, stylesheets, scripts, fonts, and documents. They are the easiest and most rewarding things to cache, because they are requested often, they are expensive to download, especially images, and they change rarely, or can be versioned so that a change becomes a new file. A well-cached static file strategy can dramatically improve page load times, reduce server load, and cut bandwidth costs, all with a small amount of configuration. It is one of the first optimisations any web application should implement.

The standard strategy has three parts, which you have already met separately and which come together here. First, serve static files with a long Cache-Control max-age, such as one year, and a public directive, so that browsers and CDNs store them for a long time. Second, version the filenames, so that when a file changes, its URL changes, and cached copies of the old version are simply abandoned, not incorrectly reused. Third, keep the HTML pages that reference those files on a short cache lifetime, so users always get the latest page, which points to the latest files. That trio, long-lived versioned files plus fresh HTML, is the backbone of static file caching on the modern web.

There are practical details that matter. Versioning can be done by including a hash of the file's content in its name, so the name changes automatically when the content changes, or by a version number you manage. Content hashes are more reliable, because they cannot get out of sync with the content, but they require a build step that rewrites references. Version numbers are simpler but rely on a human remembering to bump them, which is error-prone. Whichever you choose, be consistent, and test that a changed file really gets a new URL, and that the old URL is no longer referenced.

Another detail is file size and format. Caching a huge, unoptimised image for a year is less helpful than caching a sensibly sized one, because the first download is still slow and expensive. Optimise images, compress text files, and serve modern formats where supported, before relying on caching to fix performance. Caching multiplies the benefit of optimisation: a small file cached for a year is downloaded once and reused many times, which is the best possible outcome. A large file cached for a year is still downloaded once, slowly, and every new visitor pays that cost.

Finally, static file caching interacts with CDNs, covered next, which cache your files on servers around the world. When you use a CDN, your long cache headers tell the CDN how long to hold files, and versioned names let you update files without purging the CDN, which is a slow and sometimes unreliable operation. That is another reason versioning is preferred over purging: purging asks every cache in the world to forget a file, which takes time and may not complete everywhere, while versioning simply introduces a new file that no cache has seen. Versioning is the cleaner, more reliable update mechanism, and it is worth building into your workflow from the start.

# Content-hash versioning: the filename changes only when the content does.
import hashlib

def versioned_name(filename, content):
    digest = hashlib.sha256(content.encode()).hexdigest()[:8]
    base, ext = filename.rsplit(".", 1)
    return f"{base}.{digest}.{ext}"

print(versioned_name("style.css", "body { color: black; }"))
print(versioned_name("style.css", "body { color: blue; }"))

Section 40: CDN Caching in Plain Words

A CDN, or content delivery network, is a network of servers distributed around the world, each holding cached copies of your files, so that users download from a nearby server instead of from your origin server, which might be on another continent. If your server is in Europe and a user is in Lagos, downloading an image from Europe takes time, because the data travels a long distance through many networks. Downloading the same image from a CDN server in or near Nigeria is much faster, because the distance is shorter and the route is simpler. That geographic closeness is the core benefit of a CDN, and it is why CDNs are standard for popular sites.

A CDN works as a shared cache with a geographic twist. When a user requests a file, the request goes to the nearest CDN server. If that server has a cached copy, it serves it immediately. If it does not, it fetches the file from your origin server, stores a copy, and serves it, so the next user nearby gets the cached copy. Your origin server therefore handles far fewer requests, because the CDN absorbs the repeated ones, and users get faster responses, because they download from nearby. The CDN's caching behaviour is controlled by the same Cache-Control headers you set on your origin, which is why those headers matter beyond the browser: they tell the CDN how long to hold each file.

CDNs are best for static files: images, stylesheets, scripts, videos, and downloads. Those files are the same for everyone, they are large, and they benefit most from geographic closeness. CDNs can also cache dynamic content, but that requires care, because dynamic content differs by user or changes often, and caching it incorrectly causes the same staleness and privacy problems as any other cache, amplified across many servers. Most applications start with a CDN for static files only, and expand to dynamic caching only with clear rules and testing. That restraint is wise, because a CDN mistake affects users worldwide, not just on one server.

There are costs and considerations. CDNs are usually paid services, though many have free tiers for small sites, and the cost grows with traffic and storage. Purging, forcing a CDN to forget a file, takes time to propagate to all servers, and is not instantaneous, which is another reason versioned filenames are preferred: a new file needs no purging. And a CDN is another dependency: if it fails, your files may be unavailable, unless you have a fallback to your origin. For most sites, the benefits, speed, reduced origin load, and resilience, outweigh those costs, especially as traffic grows.

For a learner, the key point is that a CDN is not a different kind of technology. It is a cache, placed close to users, operated at scale, and controlled by the headers you already understand. When you set Cache-Control correctly, version your files, and serve static content, you are already doing most of what a CDN needs. Adding a CDN later is then a matter of pointing your domain at it and letting it cache what you have already prepared. That is a reassuring thought: good caching habits at a small scale prepare you for large-scale caching, because the principles are the same.

# A CDN serves from the nearest cached copy, not from the distant origin.
def serve(user_location, cdn_has_copy):
    if cdn_has_copy:
        return f"Served from nearby CDN server near {user_location}"
    return "Fetched from origin server, copy stored for next user"

print(serve("Lagos", True))
print(serve("Lagos", False))

Section 41: Caching and Personalisation

Personalisation means tailoring content to each user: showing their name, their tasks, their recommendations, or their language. Personalisation and caching are in tension, because caching wants one copy to serve many users, while personalisation wants a different copy for each user. Handling that tension well is essential for modern applications, which are increasingly personalised, because a naive cache will either break personalisation, by serving one user's content to another, or break performance, by refusing to cache anything personalised at all. The solution is to separate what is shared from what is personal, and cache each appropriately.

The most effective technique is to split a page into shared and personal parts. The shared parts, such as the layout, the navigation, the article text, or the product description, are the same for everyone and can be cached aggressively, in shared caches and CDNs. The personal parts, such as the user's name, their unread count, or their recommendations, are small and are fetched fresh, or cached privately per user, and inserted into the page when it is served. That split, sometimes called fragment caching or edge-side includes, gives you most of the benefit of caching, because the bulk of the page is shared, while preserving personalisation, because the personal fragments are handled separately. It requires your application to be structured so that shared and personal parts are distinct, which is a design discipline worth building.

Another technique is to cache personalised data privately, per user, with short lifetimes. A user's recommendation list, for example, might be cached for ten minutes under a per-user key. That still saves work, because the list is not recomputed on every request, but it does not risk leaking data, because the key includes the user. Private caching is less efficient than shared caching, because each user needs their own entries, but it is far better than no caching, and it is safe when keys are correct. For highly personalised pages, private caching with short lifetimes is often the best available compromise.

A third technique is to move personalisation to the client. The server sends a shared, cached page, and the user's browser or app fills in the personal parts by calling a small API for the user's data. That API response may itself be cached privately, or fetched fresh, but it is small, so the cost is low. Client-side personalisation is common in modern web applications, because it lets the main page be cached in CDNs while personal data stays fresh and private. It requires JavaScript on the client, which is outside this book's Python focus, but the architectural idea, shared page plus personal API calls, is worth understanding, because you will meet it often.

Finally, be honest about the limits. A page that is entirely personal, such as a private dashboard with no shared content, cannot benefit much from shared caching, and should not pretend to. Cache its underlying queries privately, keep lifetimes short, and accept that personal pages are slower than public pages. That honesty is better than a broken cache that leaks data in the name of speed. Personalisation is a feature users value, and it is worth paying a performance cost for, as long as the cost is understood and the shared parts are still cached well.

# Split the page: shared parts cached for everyone, personal parts per user.
page = {"shared": "article text (cached, public)",
        "personal": "Hello, Ada (private, per user)"}
print(page["shared"])
print(page["personal"])

Section 42: Caching Lists and Pagination

Lists are everywhere in back-end applications: lists of articles, tasks, products, users, and comments. Lists are also a caching challenge, because they are large, they change often, and they are paginated, which means different requests ask for different slices of the same list. Caching lists well requires thinking about pages, ordering, and change, together, rather than treating a list as a single blob. A list cached as one blob is simple, but it wastes memory and becomes stale in whole, even when only one item changed. A list cached per page is more precise, but it multiplies the number of entries and the invalidation work.

The per-page approach is the most common. Each page of a list, with its filters and sort order, gets its own cache key, such as "articles:page=2:sort=date". When a user requests page two, the cache is checked for that key. When an article is added or changed, the affected pages must be invalidated, which, in the worst case, is every page, because a new article at the top shifts every item down by one, changing every page. That invalidation burden is the main drawback of per-page caching, and it is why many systems accept a short TTL instead of active invalidation for lists: pages expire within minutes, and the shift is absorbed by expiry rather than by tracking every affected page.

An alternative is to cache the underlying data, not the pages, and build pages from it on each request. For example, cache the list of article ids in order, which is small, and fetch the article details for the requested page from their own cache entries or from the database. When an article changes, only its detail entry is invalidated, and the id list is updated or expires. Building pages from cached parts is more work per request than serving a cached page, but it is much more precise about invalidation, and it avoids caching the same article's details many times across many pages. That part-based approach is a form of fragment caching, applied to lists.

Filtering and sorting add complexity, because each combination of filter and sort is a different list, with a different key. A list filtered by category and sorted by date is not the same as the same list sorted by popularity. The number of combinations can explode, especially with free-text search, where each query is unique. For search, caching is often less valuable, because queries rarely repeat exactly. A faster search implementation, or a short-lived cache for the most common queries only, is usually better than caching every query.

A practical rule for lists: cache the first few pages most aggressively, because they are requested most often, and be more relaxed about deeper pages, which are requested rarely. Cache with short TTLs, accept that lists are slightly stale, and invalidate actively only where freshness matters, such as a user's own list after they change it. Lists are a case where perfect freshness is rarely worth the cost, and where a pragmatic, TTL-based approach serves users well. Measure which pages are actually requested, and let that data guide how much effort you spend caching each one.

# Per-page list keys: page, filter, and sort are all part of the key.
def list_key(resource, page, category, sort):
    return f"{resource}:page={page}:cat={category}:sort={sort}"

print(list_key("articles", 1, "tech", "date"))
print(list_key("articles", 2, "tech", "date"))

Section 43: Caching Search Results

Search is a special caching challenge, because search queries are highly variable. Unlike a homepage, which is the same for everyone, a search query is whatever the user typed, and the number of possible queries is effectively infinite. Caching every search result would fill the cache with entries that are rarely, if ever, requested again, pushing out useful entries and wasting space. That does not mean search results should never be cached. It means caching search requires selectivity: cache only what is likely to be repeated, and accept that most searches will not hit the cache.

The most repeated searches are usually the popular ones: common terms, trending topics, and the default or empty search. Those are worth caching, because they are requested often and their results change slowly. A cache of the top hundred search terms, refreshed regularly, can serve a large share of search traffic, even though it covers a tiny fraction of possible queries. That pattern, caching the head of the distribution and letting the long tail go fresh, applies to many problems beyond search, and it is a useful mental model: focus caching effort where requests concentrate, not where they spread thinly.

Search results also change for a subtle reason: relevance. A search result is not just a list of matching items. It is a list ranked by relevance, which can depend on the user's history, location, language, and other personal factors. A cached result for one user may be wrong for another, even for the same query, if ranking is personalised. That means search cache keys must include the factors that affect ranking, or search caching must be limited to non-personalised results. Getting this wrong produces confusing results, where users see results ranked for someone else, which undermines trust in search. When in doubt, cache only the non-personalised parts, such as the matching item ids, and rank or filter them per user at request time.

Another consideration is freshness. Search users expect fresh results, especially for news or recent content. A search result cached for an hour might miss a just-published article that the user is specifically looking for, which is a visible failure. Short TTLs, such as a few minutes, are therefore common for search caches, trading a lower hit rate for fresher results. Some systems also invalidate search caches when new content is published, though that is complex, because a new item could match any query, and invalidating every cached query on every publish is impractical. Short TTLs are the pragmatic answer, and they are usually good enough.

Finally, consider whether caching is the right optimisation for search at all. Search performance often depends more on the search implementation, such as indexes, than on result caching. A well-indexed search that answers in milliseconds does not need a result cache as desperately as a slow search does. Caching can hide a slow search, but it does not fix it, and it adds staleness. The better investment is often to make search itself fast, through proper indexing and efficient queries, and to use result caching only for the most popular queries, where it gives a clear, measurable benefit. Optimise the source first, cache second, is a good order for search and for many other features.

# Cache only popular searches; let rare, unique queries go fresh.
popular = {"python": "cached results", "caching": "cached results"}

def search(query):
    if query in popular:
        return popular[query], "cached"
    return "fresh search results", "fresh"

print(search("python"))
print(search("obscure term nobody repeats"))

Section 44: Cache Poisoning and Safety

Cache poisoning is an attack where an attacker tricks a cache into storing a harmful or incorrect response, which is then served to other users. It is a security problem, not just a performance problem, because the poisoned entry affects everyone who requests that resource, not just the attacker. Understanding cache poisoning matters for defence: you need to know how it happens, so you can design caches that resist it, even if you never implement an attack yourself. This section teaches defence only, describing attacks at a high level so you can recognise and prevent them.

The basic mechanism is that a cache decides what to store based on the request and the response, and an attacker can influence both. For example, if a cache stores responses based only on the URL, and an attacker can cause the server to return a malicious response for a URL that other users will request, the cache will store that malicious response and serve it to victims. A common variant involves headers: if a cache does not include an important header, such as a language or user identifier, in its key, an attacker can request a resource with unusual headers, poison the entry for that URL, and later users, with normal headers, receive the poisoned response. The root cause is almost always the same: a cache key that does not capture everything that affects the response.

Defending against poisoning starts with correct keys, which you have already learned: include every input that affects the response, including headers that change it, and never cache personalised responses under shared keys. It continues with careful decisions about what to cache: do not cache responses that contain user input reflected back, such as error pages that echo a query string, because those are easy to poison with crafted input. And it includes validating responses before caching them: a cache should only store responses that are complete, well-formed, and from a trusted source, not error pages or partial responses that might be attacker-controlled.

Another defence is to separate caches by trust level. Public, static content can live in shared caches with long lifetimes. Dynamic, user-influenced content should live in private caches, or not be cached at all. Error responses should generally not be cached, or only very briefly, because an error caused by an attacker should not be served to legitimate users. And cache purging, the ability to remove a poisoned entry quickly, should be available and tested, so that if poisoning is discovered, the damage can be limited by clearing the affected entries immediately, rather than waiting for expiry.

Finally, monitor for poisoning. Unusual cache entries, unexpected content in cached responses, or a sudden change in hit patterns can indicate an attack. Regular checks, such as fetching key pages through the cache and verifying their content, catch poisoning early. Cache poisoning is a reminder that a cache is not just a performance tool. It is a part of your system's trust boundary, and it must be designed with the same care as any other part that serves data to users. Correct keys, careful selection of what to cache, and monitoring are the defences, and they are all practices you have already learned in this chapter, applied with security in mind.

# Defence: the key must include every input that changes the response.
def safe_key(url, language):
    return f"{url}:lang={language}"

print(safe_key("/welcome", "en"))
print(safe_key("/welcome", "fr"))  # different language, different entry

Section 45: Never Cache Secrets

Secrets, such as passwords, tokens, API keys, session identifiers, and private keys, must never be stored in a cache. This rule is absolute, and it deserves its own section, because the temptation to cache a secret for convenience is real, and the consequences of doing so are severe. A cache is a copy, and every copy of a secret is another place it can leak: through logs, through debugging tools, through a cache inspection page, through a backup, or through a misconfigured shared cache that serves one user's entry to another. Secrets belong in dedicated, protected stores, with strict access control, not in a performance layer designed for speed and sharing.

The risk is not theoretical. Caches are often less protected than databases, because they are seen as disposable performance tools, not as sensitive stores. Cache data may be logged during debugging, may be visible to developers who should not see production secrets, and may persist longer than intended, because cache expiry is about performance, not about secret rotation. A token cached for an hour remains valid for that hour, even if the user changes their password or the token is revoked, unless the cache is also invalidated, which is an extra step that is easy to forget. Caching a secret creates a second source of truth for access, and second sources of truth are a security liability.

There are specific cases to watch for. Session tokens should not be cached as if they were ordinary data, because a cached session token can be replayed. Authentication responses, which confirm a user's identity, should not be cached in shared caches, because they would let another user impersonate the first. Error pages that include debug information, which sometimes includes secrets, should not be cached, because the secret would then be served to anyone requesting that page. And API responses that include keys or tokens, even for the requesting user, should be marked no-store, so that neither browsers nor shared caches keep a copy.

The safe alternative is to check secrets fresh, every time, against their proper store, and to cache only the result of authorisation, not the secret itself, and only where appropriate. For example, after verifying a token, you might cache a short-lived authorisation decision, such as "user 42 may read article 12", in a private, short-lived cache, but you would never cache the token. Even that decision cache needs care: it must expire quickly, and it must be invalidated when permissions change. The principle is to minimise the lifetime and the spread of sensitive data, and to keep secrets in exactly one well-guarded place.

Finally, audit your caches for secrets, as a habit. Review what your caches store, check cache keys and values during development, and search for patterns that look like tokens or passwords in cache dumps. Automated checks can help: a test that inspects cached values for secret-like patterns catches mistakes before they reach production. A developer who audits caches for secrets, and who treats any secret in a cache as a bug to be fixed immediately, is a developer whose users can trust the system with their data. That trust is worth far more than any small performance gain from caching a secret.

# Never do this: a token stored in a cache is a leak waiting to happen.
# Instead, verify tokens fresh against their proper store every time.
def verify_token(token, valid_tokens):
    return token in valid_tokens  # fresh check, nothing cached

print(verify_token("abc123", {"abc123", "def456"}))

Section 46: Testing Cached Code

Cached code needs testing, and it needs tests that specifically target caching behaviour, because ordinary tests, which check that a function returns the right answer, will pass whether the answer came from the cache or from fresh work. A test that only checks the answer cannot tell you whether the cache is working, whether it is stale, or whether it leaks data between users. Testing cached code therefore means testing the cache itself: hits, misses, expiry, invalidation, and key correctness, in addition to testing the underlying logic. Those tests are what give you confidence that caching helps rather than harms.

The first kind of cache test checks hits and misses. Call a cached function twice with the same inputs, and verify that the second call was faster, or that the underlying work was only done once. You can verify that by counting calls to the underlying function, or by using a fake source that records how often it was asked. If the source was asked twice for the same input, the cache did not work. If it was asked once, it did. That simple counting test catches a large class of bugs, including keys that change on every call, caches that are never stored, and caches that are cleared unexpectedly.

The second kind of test checks expiry and invalidation. Store an entry, advance a fake clock past its TTL, and verify that the next call fetches fresh data. Change the underlying data, trigger invalidation, and verify that the next call reflects the change. Those tests catch TTL bugs, such as lifetimes in the wrong unit, and invalidation bugs, such as forgetting to clear an entry. Fake clocks are essential here, because waiting for a real TTL to expire would make tests slow. A cache that accepts a clock or a time function as a parameter is a cache that can be tested properly, which is another reason to design caches with testability in mind.

The third kind of test checks key correctness and privacy. Call a cached function for two different users, or two different pages, and verify that each gets their own correct result, not the other's. That test catches the most dangerous caching bug, key collisions that leak data, and it should be part of every test suite for cached personalised data. Similarly, test that different filters, sorts, and languages produce different entries, and that identical inputs produce the same entry. Key tests are cheap to write and they prevent serious bugs, so there is no excuse for skipping them.

Finally, test failure modes. What happens when the cache is unavailable? A well-designed system falls back to fresh work, perhaps slowly, rather than failing the request. Test that fallback by disabling the cache and verifying requests still succeed. What happens when the cache returns corrupt or unexpected data? The application should handle it gracefully, not crash. Testing failures is less satisfying than testing happy paths, but it is where reliability is built. A cache that is tested for hits, expiry, invalidation, keys, and failures is a cache you can trust in production.

# Test a cache by counting how often the slow source is actually used.
calls = []

def slow_source(key):
    calls.append(key)
    return f"value for {key}"

cache = {}

def cached_get(key):
    if key not in cache:
        cache[key] = slow_source(key)
    return cache[key]

cached_get("a")
cached_get("a")
print("Source calls:", len(calls), "(should be 1, not 2)")

Section 47: Debugging Stale Data

When users report seeing old data, stale cache entries are a prime suspect, and debugging them requires a systematic approach, because stale data can come from several layers: the browser cache, a CDN, a shared cache, or the application's own cache. Jumping to conclusions, such as clearing everything, might fix the symptom but teaches you nothing, and it causes a cold start. A methodical approach finds the actual layer, fixes the actual cause, and prevents a repeat. Debugging stale data is a skill that improves with practice, and this section gives you a checklist to practise with.

Start by reproducing the problem. Ask what the user sees, what they expect to see, and when the underlying data changed. Check whether you see the same stale data, or whether it is specific to that user, that device, or that location. A problem seen by everyone, everywhere, is likely in a shared cache or in the source data itself. A problem seen by one user on one device is likely in that device's browser cache. A problem seen in one region is likely in a CDN node. Those distinctions narrow the search dramatically, and they come from asking simple questions before touching any code.

Next, check each layer in order, from the user inwards. Ask the user to hard-refresh, which bypasses the browser cache, and see if the fresh data appears. If it does, the browser cache was the cause, and the fix is in cache headers or versioning. If not, check the CDN or shared cache, by requesting the same resource with a cache-busting parameter or from a different location, and see if the fresh data appears. If it does, the shared cache was stale, and the fix is in its TTL or invalidation. If not, check the application's cache, by inspecting its entries for that key, and see whether the entry is old. If it is, the application's invalidation or TTL is at fault. If the application's cache is fresh but the user still sees old data, the problem may be in the source data itself, or in a layer you have not considered.

Once you find the layer, find the cause. Was the TTL too long? Was an invalidation missed? Was the key wrong, so the old entry was never cleared? Was the data changed through a path that does not invalidate, such as a direct database edit or a bulk import? Direct edits are a common cause of stale caches, because they bypass the application code that would normally invalidate. The fix might be to invalidate manually after such edits, or to route all changes through the application. Understanding the cause, not just the layer, is what prevents recurrence.

Finally, fix it properly and verify. Clear only the affected entries, not the whole cache, to avoid a cold start. Fix the TTL, the invalidation, or the key, whichever was wrong. Then verify from the user's perspective: ask them to check again, or check yourself with their account and device, if appropriate, and confirm the fresh data appears. Record what happened, so the next developer, or your future self, can recognise the pattern. Stale data bugs are rarely unique. They are variations on a few themes, and a record of past incidents makes future debugging faster and less stressful.

# Debug by layers: browser, CDN, application cache, source.
layers = {"browser cache": "stale?", "CDN cache": "stale?",
          "app cache": "stale?", "source data": "current?"}
for layer, state in layers.items():
    print(f"Check {layer}: {state}")

Section 48: A Small Caching Layer Design

You have now met the pieces of caching. This section puts them together into a small, complete caching layer design that you could actually build with Python's standard library, and that embodies the lessons of this chapter. The design is deliberately modest: a cache module with a clear interface, sensible defaults, and no external dependencies. Modest designs are valuable because they can be built, tested, and understood, and then grown. A grand caching system that never gets built helps nobody, while a small one that works teaches you what you actually need next.

Start with the interface. Your cache module should offer a few functions: get, which returns a value or None on a miss or expiry; set, which stores a value with a TTL; delete, which removes an entry; and clear, which removes entries matching a pattern, for invalidation. It should also offer a helper, get_or_compute, which takes a key, a TTL, and a function, checks the cache, and on a miss, calls the function, stores the result, and returns it. That helper embodies the cache-aside pattern in one place, so the rest of your application does not repeat the check-fill logic everywhere. A small, clear interface is the foundation of a maintainable cache.

Next, the store. For a small application, a SQLite table, as designed earlier, is an excellent store: it persists across restarts, it is inspectable, and it supports expiry queries and size management. For an even smaller application, or for data that need not persist, a dictionary with expiry and LRU eviction, also designed earlier, is enough. Choose based on persistence needs, not on fashion. Either store can sit behind the same interface, so you can switch later without changing the rest of your application. That interchangeability is the benefit of a clean module boundary, and it is worth preserving.

Next, the policies. Set a default TTL that is safe, such as five minutes, and let callers override it per entry, with longer TTLs for public, rarely changing data and shorter TTLs, or no caching, for personal or fast-changing data. Enforce a size limit, with LRU eviction, and a periodic cleanup of expired entries. Add hit and miss counters, so you can measure the cache's effectiveness. And build in safety rules: never cache a response marked private in a shared store, never cache secrets, and always include the user in keys for personal data. Those rules, enforced in the module, protect every caller, even one who forgets them.

Finally, the surrounding practices. Document each cached item's key pattern, TTL, and invalidation points, so the next developer understands the design. Test the module for hits, expiry, invalidation, keys, and failures, as covered earlier. Monitor hit rate and size, and review TTLs when data behaviour changes. And remember that the module is a tool, not a mandate: not everything needs to go through it, and data that is cheap, rare, or critical should bypass it. A caching layer that is used deliberately, measured regularly, and understood by its users is a layer that will serve your application well as it grows.

import time

# A small cache interface: get, set, delete, and get-or-compute.
store = {}

def cache_get(key):
    item = store.get(key)
    if item and item[1] > time.time():
        return item[0]
    store.pop(key, None)
    return None

def cache_set(key, value, ttl=300):
    store[key] = (value, time.time() + ttl)

def get_or_compute(key, compute, ttl=300):
    value = cache_get(key)
    if value is None:
        value = compute()
        cache_set(key, value, ttl)
    return value

print(get_or_compute("homepage", lambda: "<h1>Hi</h1>"))

Section 49: Common Caching Mistakes

Every topic has its classic mistakes, and caching is rich in them, because it is easy to add and hard to get perfectly right. This section collects the most common ones, so you can recognise them in your own designs before users do. Read through them, check your caches against them, and you will avoid a large share of caching trouble, which is a good return on a few minutes of reading.

The first mistake is caching everything, everywhere, without thinking. It fills the cache with useless entries, causes stale data in places where freshness matters, and makes debugging a nightmare, because every response might come from any layer. The fix is selectivity: cache deliberately, one proven candidate at a time, with measured benefit. The second mistake is caching personalised data under a shared key, which leaks one user's data to another. The fix is to always include the user in the key for private data, and to test with multiple users. The third mistake is forgetting TTLs, so entries live forever and become stale permanently. The fix is a TTL on every entry, without exception.

The fourth mistake is caching secrets, which creates a second, less protected copy of sensitive data. The fix is never to cache secrets, and to audit caches for them. The fifth mistake is ignoring invalidation, assuming expiry alone will handle everything, for data where immediate freshness matters, such as a user's own profile after they edit it. The fix is active invalidation where the owner will notice staleness immediately. The sixth mistake is the opposite: building elaborate invalidation that is half-implemented and wrong, causing confusing partial staleness. The fix is to start with expiry, add invalidation only where proven necessary, and test it thoroughly.

The seventh mistake is using the same TTL for everything, so fast-changing data is stale and slow-changing data is refetched wastefully. The fix is per-item TTLs based on change rate and staleness tolerance. The eighth mistake is not measuring: adding a cache and never checking its hit rate, latency, or source load, so a useless or harmful cache persists indefinitely. The fix is counters and regular review. The ninth mistake is clearing the whole cache to fix a stale entry, causing a cold start and a stampede. The fix is targeted invalidation of only the affected entries. The tenth mistake is caching cheap work, where the lookup costs more than the work saved, making requests slower. The fix is to measure before and after, and remove caches that do not help.

None of these mistakes comes from bad intentions. They come from enthusiasm for speed, from copying an example without understanding it, or from adding a cache and moving on before its behaviour is verified. The antidote is the habit this chapter has tried to build: cache deliberately, with keys that capture all inputs, TTLs that match change rates, invalidation where freshness matters, measurement always, and security always. A developer who does that will still make mistakes, but they will be new and interesting ones, not the classics listed here, and that is progress.

Section 50: Caching in Your Back-End Toolkit

This chapter began with a notebook beside a reference book. It ends with a toolkit: a set of ideas, patterns, and habits that belong in every back-end developer's repertoire, alongside databases, APIs, and authentication. Caching is not a single feature to add once and forget. It is a way of thinking about work, time, and copies: work that can be reused should be reused, copies that can go stale must be bounded, and the trade between speed and freshness must be made deliberately, per item, not globally. That way of thinking will serve you in every system you build, because every system repeats work, and every system can benefit from repeating it less.

Let us review the toolkit. You know the basic pattern: check the cache, serve on a hit, compute and store on a miss. You know the vocabulary: hits, misses, hit rate, TTL, expiry, invalidation, eviction, and the policies LRU, FIFO, and LFU. You know the layers: browser, CDN, shared server cache, and database cache, each catching what the layers above missed. You know the HTTP mechanisms: Cache-Control, ETags, Last-Modified, and conditional requests, which give you powerful caching behaviour through headers alone. And you know the patterns for writes: write-through, write-behind, cache-aside, and read-through, each with its trade-offs between speed, consistency, and risk.

You also know the cautions, which matter as much as the techniques. Never cache secrets. Never cache private data under a shared key. Always set a TTL. Measure hit rate and latency, and remove caches that do not help. Expect stampedes, and defend against them with jitter, stale-while-revalidate, and warming. Expect cold starts, and plan for them with shared or persistent caches. And expect invalidation to be hard, so start with expiry and add invalidation only where freshness truly matters.

There are things this chapter did not cover in depth, and you should know their names so you can learn them next. Dedicated cache services, which provide shared, high-performance caching across many servers, are the natural next step when a dictionary or SQLite cache outgrows its limits. Advanced CDN configuration, including dynamic content caching and edge computing, extends the geographic caching you learned here. And cache-aware database design, including materialised views and pre-computed aggregates, applies caching ideas inside the database itself. You do not need those yet. The foundation you have now will make them much easier when you reach them, because they are all variations on the same notebook idea.

Your next step is practice. Take a small application you have built, find its slowest, most repeated request, and add a cache for it, with a deliberate key, a sensible TTL, and hit and miss counters. Measure the improvement. Then break it on purpose: change the data, watch the stale copy, and fix it with invalidation. Then restart the application, watch the cold start, and warm the cache. That cycle, build, measure, break, fix, is how caching skill is really learned, and it is a cycle you will repeat throughout your career, because every new system brings new data, new patterns, and new caching decisions.
