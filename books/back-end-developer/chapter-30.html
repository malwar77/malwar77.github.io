Chapter 30: Security Basics for Back-End Developers

Section 1: Security Is Part of the Job

Security is not a separate feature you add at the end of a project, if time allows. It is part of every feature, from the first line of code, because every feature that handles user data, accepts input, or makes decisions can be misused if it is not designed with misuse in mind. A back-end developer who thinks security is someone else's job, such as a specialist team, or a problem for later, will build features with weaknesses that are expensive to fix after release, and that may harm users in the meantime. Security is part of the job in the same way correctness is: a feature that works for honest users but fails for dishonest ones is not a finished feature.

The reason security must be built in from the start is that it is hard to add afterwards. A system designed without authorisation checks needs those checks added to every endpoint, which is a large, error-prone change. A system that stored passwords insecurely needs every password reset, which disrupts users. A system that logged secrets needs its logs scrubbed and its secrets rotated, which is a serious incident response. By contrast, a system designed with security from the start, with validation, authorisation, safe storage, and careful logging as standard habits, avoids those painful retrofits, because security is part of its normal structure, not an extra layer bolted on afterwards. Building security in is cheaper, easier, and more reliable than adding it later, in every case.

Security also matters because back-end systems are trusted with valuable things: personal data, private messages, financial information, and the ability to act on users' behalf. A breach of that trust harms users directly, through exposed data, stolen accounts, or financial loss, and it harms the service, through lost trust, legal consequences, and repair costs that dwarf the cost of preventing the problem. Users cannot protect themselves from a back-end weakness, because they cannot see or fix your code. They depend on you to protect them, and that dependence is a responsibility that comes with the role. Taking it seriously is not paranoia. It is professionalism.

There is a common misconception that security is about stopping brilliant hackers with exotic techniques. In reality, most security incidents exploit ordinary weaknesses: missing validation, missing authorisation checks, weak passwords, outdated dependencies, or leaked secrets, all of which are covered in this chapter, and all of which are preventable with basic, disciplined practices. You do not need to be a security expert to prevent most incidents. You need to apply the basics consistently, for every feature, and to keep learning as new weaknesses are discovered. The basics in this chapter, applied habitually, will protect your users from the vast majority of real-world attacks, which is a strong claim, but it is supported by incident data: most breaches exploit known, basic weaknesses, not novel techniques.

Finally, security is a mindset as much as a set of techniques. It means asking, for every feature, "how could this be misused, and what would happen if it were?" and assuming input is hostile until proven otherwise. That mindset, applied consistently, turns the techniques in this chapter from a checklist into a habit, and a habit into a trustworthy system.

# Security from the start: validate, authorise, and protect, for every feature.
def handle_request(user, action):
    if not user:
        return "denied: not signed in"
    if action not in ("read", "write"):
        return "denied: unknown action"
    return f"allowed: {action}"

print(handle_request("ada", "read"))
print(handle_request(None, "write"))

Section 2: Thinking Like a Defender

Thinking like a defender means looking at your own system from the perspective of someone who wants to misuse it, and asking what they would try, what they could gain, and what would stop them. It does not mean learning to attack systems you do not control, which this book does not teach and which you should never do without explicit permission. It means, for your own system, in your own test environment, thinking adversarially about your own code, so you can strengthen it before anyone else tests it. That defensive thinking is a skill, and it can be practised safely, on your own projects, with your own data, by asking a few structured questions about every feature.

The first question is: what is valuable here? Data, accounts, money, and the ability to act are all valuable, and attackers target value. A feature that displays public articles has little value to an attacker, beyond defacement, while a feature that changes passwords, transfers money, or exports user data has high value, and deserves stronger protection. Identifying what is valuable in a feature tells you where to focus your defensive effort, because not every feature needs the same level of protection, and spending equal effort everywhere wastes time that should be spent on high-value features. Value assessment is the first step in prioritising security work.

The second question is: who could misuse this, and how would they try? The answer is rarely a single, sophisticated attacker. It is often ordinary users testing boundaries, automated scripts probing for common weaknesses, or a compromised account being used to access more than it should. Thinking about those actors, and their likely attempts, such as entering unexpected input, requesting other users' data, or repeating requests rapidly, helps you design defences that match real threats, rather than imagined ones. A defence designed for a movie-style hacker, but not for a curious user who changes an id in a URL, will fail against the more common threat, which is the curious user.

The third question is: what happens if misuse succeeds? If the worst outcome is a user seeing a slightly wrong page, the risk is low, and a simple fix is enough. If the worst outcome is exposed private data, stolen accounts, or financial loss, the risk is high, and the feature needs strong, layered defences, thorough testing, and careful monitoring. That impact assessment, combined with value and likelihood, gives you a sense of risk, which guides how much effort a feature's security deserves. Risk assessment is not about being afraid of everything. It is about being proportionate: strong protection where harm is high, sensible protection where harm is low, and no wasted effort where there is nothing to protect.

The fourth question is: what defences are already in place, and what gaps remain? A feature might already be protected by authentication, validation, and authorisation, but missing rate limiting or logging. Listing defences and gaps turns vague worry into a concrete list of improvements, which can be prioritised and implemented. That list is also useful for code review, because a reviewer can check it against the code and spot missing defences.

# Defender questions: what is valuable, who might misuse it, what if they do?
feature = {"name": "password change", "value": "account access",
           "risk_if_misused": "account takeover"}
print(feature)
print("Defences needed: authentication, authorisation, rate limiting, logging")

Section 3: The Three Goals: Confidentiality, Integrity, Availability

Security is often summarised as three goals, known as the CIA triad, which stands for confidentiality, integrity, and availability, not to be confused with any agency of the same initials. Those three goals describe what security protects, and they are a useful framework for thinking about any feature's security requirements, because every security problem can be described as a failure of one or more of them. Learning the triad gives you a vocabulary for discussing security, and a checklist for reviewing features: does this feature protect confidentiality, integrity, and availability, as appropriate?

Confidentiality means that information is only accessible to those authorised to see it. A user's private tasks should only be visible to that user. A password should only be known to its owner, and stored in a form that even the service cannot reverse. An API key should only be known to its holder. Confidentiality failures are leaks: data seen by someone who should not see it, whether through a missing authorisation check, a leaked log, or an insecure transmission. Protecting confidentiality involves authentication, authorisation, encryption, and careful handling of data in logs, responses, and caches, all of which you have met in earlier chapters, now seen as confidentiality controls.

Integrity means that information is accurate and unaltered, except by authorised changes. A task's title should only change when its owner edits it, not when someone else tampers with a request. A payment amount should not change in transit between the user and the service. A report should reflect the data it claims to reflect, not a modified version. Integrity failures are tampering: data changed by someone who should not change it, or changed accidentally through a bug, or changed in transit by an intermediary. Protecting integrity involves validation, authorisation checks on writes, signatures for important data, and secure transmission, which prevents alteration in transit.

Availability means that the service is accessible to authorised users when they need it. A task application that is down, or so slow as to be unusable, fails availability, even if its data is confidential and intact. Availability failures are often caused by overload, such as too many requests, or by attacks that exhaust resources, such as flooding a server, or by accidents, such as a full disk. Protecting availability involves capacity planning, rate limiting, monitoring, and resilience, such as handling failures gracefully, so that one failing part does not bring down the whole service. Availability is sometimes overlooked in security discussions, because it feels like a performance problem, but it is a security goal, because denying service to legitimate users is a form of harm, and attackers exploit it deliberately.

The three goals can conflict, and balancing them is part of security design. Strong confidentiality, such as encrypting everything and requiring frequent re-authentication, can harm availability and usability, if users cannot access their own data conveniently. Strong integrity checks, such as verifying every change, can slow a system, affecting availability. The right balance depends on the data and the users: highly sensitive data deserves strong confidentiality, even at some usability cost, while a public blog deserves availability above all, with confidentiality less relevant. Thinking in terms of the triad helps you make those trade-offs explicitly, rather than by accident, and to explain them to others, which is part of professional security work.

# The CIA triad: three goals every security review should check.
goals = {"confidentiality": "only authorised eyes see it",
         "integrity": "only authorised changes alter it",
         "availability": "authorised users can reach it when needed"}
for goal, meaning in goals.items():
    print(goal, "->", meaning)

Section 4: Trust Nothing from the Outside

A foundational rule of secure back-end development is to trust nothing that comes from outside your system, until it has been checked. Outside means any input that originates beyond your code's control: request parameters, headers, cookies, file uploads, data from outside services, and even data from your own database, if it was originally provided by a user, because it could have been malicious when it was stored, and it will be dangerous when it is used, if it is not handled safely. That rule sounds extreme, but it is practical, because outside input is the main way attackers reach your code, and because checking input is cheap compared to the harm of trusting it blindly.

Trusting nothing does not mean rejecting everything. It means validating everything, according to what you expect, before using it. If you expect a number, check that it is a number, within range, before using it in a calculation or a query. If you expect an email address, check its format, before storing or sending to it. If you expect a file upload, check its type, size, and name, before saving it, as covered later. If you expect a user id, check that the requesting user is authorised to access that id, before returning its data. Validation is the mechanism of distrust: it turns untrusted input into trusted data, by verifying it meets your expectations, and rejecting it when it does not.

There is a subtlety here that is worth understanding: validation must happen on the server, not just in the browser or app, because client-side checks can be bypassed. A web form might validate input in JavaScript, giving users helpful immediate feedback, but an attacker can send requests directly to your server, skipping the form and its checks entirely. Server-side validation is therefore the real defence, while client-side validation is a convenience for honest users. A system that only validates on the client is a system with no validation at all, from a security perspective, because its checks are optional for anyone who chooses to skip them. Always validate on the server, even if you also validate on the client for usability.

Another subtlety is that trust should be based on verification, not on origin. A request from your own app, or a familiar address, is not automatically trustworthy, because apps can be modified, addresses can be spoofed, and accounts can be compromised. A request carrying a valid authentication token is trustworthy to the extent that token proves, because the token was verified, not because the request looks familiar. Similarly, data from an outside service should be validated, because that service could be compromised or buggy.

Finally, distrust should be implemented as allow-listing, not block-listing, wherever possible. Allow-listing means defining what is acceptable, and rejecting everything else, which is safe, because unknown inputs are rejected by default. Block-listing means defining what is forbidden, and accepting everything else, which is unsafe, because an attacker can find an input you did not think to forbid. Allowing only letters, numbers, and underscores in a username is safer than forbidding a list of dangerous characters, because the allowed set is finite and known.

# Distrust by default: allow-list what is acceptable, reject everything else.
import re

def is_safe_username(name):
    return re.fullmatch(r"[A-Za-z0-9_]{3,20}", name) is not None

print(is_safe_username("ada_123"))  # True
print(is_safe_username("ada; DROP"))  # False: rejected, not trusted

Section 5: Input Validation as a Security Control

Input validation is often taught as a correctness feature, ensuring data is well-formed, but it is also, fundamentally, a security control, because most attacks begin with input: a request that contains more than expected, or different from expected, designed to make the system misbehave. Validation, done well, stops those attacks at the boundary, before malicious input reaches sensitive code, such as database queries, file operations, or output rendering, where it could cause harm. Thinking of validation as security, not just as tidiness, changes how thoroughly you do it, and how seriously you take its failures.

The security value of validation comes from its position: it is the first line of defence, at the edge of your system, where untrusted input enters. If validation is strong, downstream code can assume its inputs are safe, within the validated bounds, and it does not need to defend itself against every possible input. If validation is weak or missing, every downstream component must defend itself, which is error-prone, because a single missed defence in any component becomes a vulnerability. Strong boundary validation therefore simplifies the rest of the system, by establishing a trusted zone inside the boundary, where code can operate on validated data with confidence. That simplification is a major security benefit, beyond the immediate rejection of bad input.

Validation as security requires completeness. It is not enough to validate the fields you expect, while ignoring extra fields, or to validate one endpoint thoroughly while leaving another unvalidated. Attackers probe for the weakest endpoint, the forgotten parameter, the extra field that is passed through without checking, and they exploit whatever they find. A security review of validation should therefore cover every input to every endpoint, including query parameters, body fields, headers that affect behaviour, and file uploads, asking for each: is it validated, against what rules, and what happens when it fails? That completeness check is tedious, but it is what separates a system that is mostly validated, which is to say, vulnerable somewhere, from one that is actually validated.

Validation as security also requires safe failure. When validation fails, the system should reject the request, with a clear but not revealing error, and without side effects, such as partial writes or sent notifications, as covered in the testing chapter. It should not attempt to clean or fix malicious input and then use it, because cleaning is error-prone: a cleaner that removes known dangerous patterns will miss unknown ones, while a validator that rejects anything outside its allow-list is safe by default. Reject, do not sanitise and proceed, is the safer rule for security-critical input, though sanitisation has a place for display, as covered in the output escaping sections, where it is a different operation with a different purpose.

Finally, validation should be tested as security, with adversarial cases. Test each rule with inputs designed to break it: too long, too short, wrong type, forbidden characters, and boundary values, and assert rejection, with the right error, and no side effects. Those tests should be part of the regular suite, run on every change, because a rule broken by a change will only be caught by a test that checks it.

# Validation as a boundary: reject anything outside the allow-list.
def validate_age(age):
    if not isinstance(age, int) or not 0 <= age <= 120:
        raise ValueError("age must be a whole number between 0 and 120")
    return age

print(validate_age(30))
try:
    validate_age("thirty")
except ValueError as e:
    print("Rejected:", e)

Section 6: Never Trust the Client

The client is the browser, app, or program that talks to your server, and a fundamental rule is to never trust it, because it runs on the user's device, outside your control, and it can be modified, bypassed, or impersonated. A user can edit a web page's code in their browser, modify an app's requests, or send requests directly with a tool, skipping your client entirely. Any check, rule, or secret that lives only on the client can therefore be bypassed by anyone who chooses to, and your server must not rely on it for security. Server-side enforcement is the only enforcement that counts, because the server is the part you control.

The most common client trust mistake is relying on client-side validation alone, as covered earlier, but there are others. Relying on the client to hide data, such as not showing a button for an action a user should not perform, is not security, because the user can still call the action's endpoint directly, even if the button is hidden. Hiding is a usability choice, not a security control. The server must check authorisation for every action, regardless of whether the client showed the option, because the endpoint is the real boundary, not the interface. A hidden button with an unprotected endpoint is an open door with a curtain over it: it looks closed, but anyone can walk through.

Another client trust mistake is relying on client-provided data for security decisions, such as trusting a role, a price, or a user id sent by the client, without verifying it on the server. For example, a shopping app that trusts the price sent by the client, rather than looking up the price on the server, can be exploited by changing the price to a lower value, because the server will charge the client-provided price. Similarly, an app that trusts a client-provided user id, without checking it matches the authenticated user, can be exploited to access other users' data. The server must derive security-critical values from its own trusted state, such as the authenticated session and the database, not from client input, which is untrusted by definition.

Another mistake is storing secrets on the client, such as API keys or tokens with excessive privileges, in client code that anyone can read. Secrets in client code are not secret. Secrets belong on the server, with the client receiving only what it needs, such as a limited token for its own session, not a master key. Similarly, authorisation rules should be enforced on the server, even if also reflected on the client for usability, because the client's reflection is for convenience, not protection.

Finally, never trust the client means designing your API as if every request could be crafted by hand, because it can be. For each endpoint, ask: if an attacker sent this request directly, with any values they choose, what would happen? Would authorisation be checked? Would validation reject bad values? Would prices be looked up, not trusted? That adversarial question, asked during design, review, and testing, is the practical test for client trust mistakes.

# Server-side truth: prices come from the server's catalogue, never from the client.
catalogue = {"book": 20, "pen": 5}

def charge(item, client_price):
    real_price = catalogue[item]  # server looks it up, ignores client_price
    return real_price

print(charge("book", 1))  # charges 20, not the client's claimed 1

Section 7: Least Privilege in Plain Words

Least privilege is the principle that every part of a system, whether a user, a process, or a component, should have only the permissions it needs to do its job, and no more. A user who only needs to read tasks should not be able to delete them. A database account used by a web server should only be able to access the tables it needs, not to drop tables or create users. A background worker that sends emails should not be able to read passwords. Least privilege limits the damage when something goes wrong, because a compromised account, a buggy component, or a mistaken action can only do what its limited permissions allow, not everything the system can do.

Least privilege applies at several levels. For users, it means roles with minimal permissions: readers read, editors edit their own content, administrators administer, and no one gets administrator rights by default, or for convenience, because convenience permissions become permanent vulnerabilities. For application components, it means separate database accounts or API keys per component, each with only the access that component needs, so a compromise of one component does not give access to everything. For processes, it means running servers with a limited operating system user, not as a superuser, so a compromised process cannot take over the whole machine. Each level is a separate application of the same idea: minimise permissions, minimise damage.

Implementing least privilege requires knowing what each part actually needs, which is a useful design exercise in itself. When you create a role, list its actions, and grant only those. When you create a database account for an application, grant only select, insert, update, and delete on the tables it uses, not administrative rights. When you run a service, give it access only to its own files and directories, not to the whole filesystem. That listing, of needs versus grants, often reveals unnecessary permissions that accumulated by default or by copying a broad template, and removing them is a concrete security improvement, with no downside, because the part continues to work with what it needs, and nothing more.

Least privilege also applies to data access within code. A function that only needs a user's name should receive the name, not the whole user record including secrets. An API response should include only the fields the client needs, not every field in the database row, because extra fields may contain sensitive data the client should not see. That data minimisation is least privilege applied to information: give each part only the data it needs. A system built on least privilege contains single failures, rather than letting them become catastrophic.

Finally, least privilege must be maintained, because permissions tend to grow over time, as features are added and temporary grants become permanent. Regular reviews, asking for each role, account, and component whether its permissions are still minimal, and removing what is no longer needed, keep privilege from creeping upwards. That review is a small, periodic task with large security benefits, because it catches the administrator account created for a one-time task and never removed, or the broad database grant copied for convenience, before an attacker finds and uses it. Least privilege is not a one-time setup. It is an ongoing discipline of granting little, and reviewing often.

# Least privilege: a reader role can read, but cannot delete.
roles = {"reader": {"read"}, "editor": {"read", "write"}, "admin": {"read", "write", "delete"}}

def allowed(role, action):
    return action in roles[role]

print(allowed("reader", "read"))    # True
print(allowed("reader", "delete"))  # False: not needed, not granted

Section 8: Defence in Depth

Defence in depth means protecting a system with multiple, layered defences, so that if one defence fails, another still protects it. The idea comes from physical security, where a building might have a fence, a locked door, an alarm, and a safe, each providing protection even if the previous one is bypassed. In software, defence in depth means not relying on a single control, such as validation alone, or authentication alone, but combining several: validation plus authorisation plus safe queries plus output escaping plus logging plus monitoring, so that a bug in any one layer does not automatically become a breach, because the next layer catches what the first missed.

Defence in depth is necessary because no single defence is perfect. Validation can have gaps, because a rule was missed or a new input form was added. Authorisation can have bugs, because a new endpoint forgot a check. A library can have a vulnerability, because it was not updated. If your system relies on only one of those, a single failure is a breach. If it has layers, a single failure is a warning, caught by the next layer, and fixed before it causes harm. That resilience to single failures is the core value of defence in depth, and it is why security-conscious systems are designed with redundancy, even though redundancy costs effort and complexity.

A concrete example helps. Consider a task title displayed on a page. Validation at input ensures titles contain only safe characters, which is one layer. Output escaping at display ensures that even if a title contains special characters, they are shown as text, not treated as code, which is a second layer. A content security policy, covered later, restricts what code can run on the page, which is a third layer. If validation misses a character, escaping still protects the page. If escaping has a bug, the policy still limits harm. No single layer is trusted completely, and together they provide robust protection, even though each alone is imperfect. That layering, applied to every important feature, is defence in depth in practice.

Defence in depth also applies to infrastructure and operations, not just code. A database protected by a password, by network restrictions allowing only the application server to connect, and by backups allowing recovery, has three layers. A secret protected by environment variables, by server access controls, and by rotation has three layers. In each case, the layers are independent, so a failure in one does not defeat the others. Layers must be independent, not all relying on the same assumption, or they will fail together.

Finally, defence in depth should be proportionate. Not every feature needs ten layers, and adding layers indiscriminately creates complexity that can itself cause bugs. The right number depends on the value and risk of the feature: high-value features, such as authentication and payments, deserve many layers, while low-value features, such as public article display, need fewer. Have more than one layer for important things, and ensure layers are independent, so a single bug does not lead directly to harm.

# Defence in depth: validation, escaping, and policy each protect the same output.
import html

title = "<b>Hello</b>"
validated = title  # layer 1: validation would restrict input at entry
escaped = html.escape(title)  # layer 2: escaping makes it safe to display
print("Displayed safely as text:", escaped)

Section 9: Keeping Secrets Safe

Secrets are pieces of information that must not become known to unauthorised people, and in back-end development, they are everywhere: passwords, API keys, database credentials, session tokens, encryption keys, and private certificates. Keeping secrets safe is one of the most important security responsibilities, because a leaked secret can give an attacker direct access to your system, your data, or your users' accounts, often without any other vulnerability needed. A leaked database password is as good as an open door. A leaked API key is as good as a stolen identity. Secrets deserve the highest level of care, and this section covers the principles for that care.

The first principle is to minimise secrets: do not create a secret unless you need one, do not store a secret longer than you need it, and do not copy a secret to more places than necessary. Every copy is another place it can leak, through logs, backups, screenshots, or shared files. A secret that exists only in one well-protected place, used only where needed, is far safer than a secret copied into code, configuration files, documentation, chat messages, and logs, which is a common pattern when secrets are handled casually. Minimising secrets starts with asking, for each secret, "do we need this, where does it live, and who can see it?" and reducing the answers to the minimum.

The second principle is to never put secrets in source code. Source code is copied, shared, stored in repositories, and often made visible to many people, including future team members, contractors, and, if a repository becomes public accidentally, everyone. A secret in code is a secret that will leak, eventually, because code travels farther and lasts longer than its author intends. Instead, secrets should live in a dedicated secrets store, or, for smaller systems, in environment variables set on the server, which are covered in the next section, and which keep secrets out of code and out of repositories. That separation, code in the repository, secrets on the server, is a fundamental security practice, and it should be non-negotiable.

The third principle is to protect secrets in use and in transit. Secrets should be transmitted only over encrypted connections, such as HTTPS, never over plain HTTP, where they can be intercepted. They should be used only where needed, and not logged, not displayed in error messages, and not included in responses, as covered in the logging chapter. When a secret is no longer needed, such as a token that has expired, it should be discarded, not kept in logs or databases indefinitely. And when a secret is suspected of leaking, it should be rotated, meaning replaced with a new secret, and the old one revoked, promptly, because a leaked secret that remains valid is an ongoing vulnerability, not a past incident.

The fourth principle is to limit who and what can access secrets. Only the processes that need a secret should be able to read it, with file permissions or access controls enforcing that limit. Only the people who need to know a secret should know it, and they should be few. Access to secrets should be logged, so unusual access can be noticed. Keeping secrets safe is about minimising, separating, protecting, and limiting, applied consistently, from creation to retirement.

# Secrets live outside code: read them from the environment, never hard-code them.
import os

db_password = os.environ.get("DB_PASSWORD")
print("Password loaded from environment:", "yes" if db_password else "not set")
print("Never write: DB_PASSWORD = 'hunter2'  # in source code")

Section 10: Environment Variables for Secrets

Environment variables are a simple, standard way to provide secrets and configuration to an application without putting them in source code. An environment variable is a named value set in the operating system's environment, where a process runs, which the process can read at startup. For example, a server might have an environment variable called DB_PASSWORD, set to the database password, and the application reads it when it starts, using it to connect, without the password ever appearing in code, in a configuration file committed to a repository, or in a log. That separation is the main benefit, and it is why environment variables are the default recommendation for small and medium applications.

Using environment variables correctly involves a few practices. First, set them on the server, through your hosting platform's settings, or through a secure startup process, not by writing them in a file that is committed to your repository. A file named .env, which holds environment variables for local development, is a common convenience, but it must never be committed, because it contains secrets, and it should be listed in your repository's ignore file, so it cannot be committed accidentally. That ignore rule is a small configuration that prevents a large leak, and it should be set up from the first day a .env file exists.

Second, read environment variables at startup, and fail clearly if a required one is missing, rather than proceeding with a default or an empty value, which could cause confusing errors or insecure behaviour. A clear error at startup, such as "DB_PASSWORD is not set", tells the operator exactly what is wrong, and prevents the application from running in a broken or insecure state. That fail-fast behaviour is better than a silent default, which might be a weak password, or a missing secret that causes failures later, in harder-to-diagnose places. Configuration errors should be loud and early, not silent and late.

Third, understand the limits of environment variables. They are visible to the process and, depending on the system, to other processes or users on the same machine, if permissions are not set correctly, so they are not a perfect secrets store for highly sensitive systems, which use dedicated secrets managers with encryption, access controls, and rotation. For most small and medium applications, however, environment variables, with proper server permissions, are a large improvement over hard-coded secrets, and they are the right starting point. As systems grow and secrets become more numerous and more sensitive, moving to a dedicated secrets manager is a natural next step, and the code change is small, because the application already reads secrets from outside itself, rather than from its own code.

Finally, environment variables are also useful for non-secret configuration, such as whether the application is in development or production, or which database to use. Using them for configuration as well as secrets keeps all environment-specific settings in one place, outside code, so the same code runs in development and production, differing only in configuration. That consistency reduces deployment bugs, because the code tested in development is the code that runs in production.

import os

# Read configuration from the environment; fail clearly if a secret is missing.
def get_secret(name):
    value = os.environ.get(name)
    if not value:
        raise RuntimeError(f"Missing required environment variable: {name}")
    return value

Section 11: Password Storage Done Right

Storing passwords correctly is one of the most critical security tasks in back-end development, because a database breach that exposes passwords can lead to account takeovers, not just on your service, but on other services where users reused the same password, which many users do. The correct approach is well established, and it is not to store passwords at all, in any readable form, but to store a hash, which is a one-way transformation of the password, computed with a slow, salted hashing algorithm designed for passwords, such as bcrypt, scrypt, or Argon2. When a user logs in, you hash the password they provide, with the same method, and compare the result with the stored hash. If they match, the password was correct, without your system ever needing to know, or store, the actual password.

The key concepts are hashing, salting, and slowness, and each matters. Hashing is one-way: given a hash, it should be computationally infeasible to recover the original password, unlike encryption, which is reversible with a key, as covered next. That one-way property means a database breach exposes hashes, not passwords, which is far less harmful, though not harmless, because weak passwords can still be guessed by trying many candidates and hashing them, which is why the other two properties matter. Salting means adding a unique random value, the salt, to each password before hashing, so that two users with the same password get different hashes, and so that precomputed tables of hashes for common passwords, called rainbow tables, are useless, because each password must be attacked individually, with its own salt. A unique salt per user, stored alongside the hash, is essential, and it is handled automatically by good password hashing libraries.

Slowness means the hashing algorithm is deliberately slow, taking a significant fraction of a second per password, rather than microseconds, as general-purpose hashes do. That slowness is a feature, not a bug, because it makes guessing attacks expensive: an attacker trying millions of passwords must pay the slow cost for each one, making large-scale guessing impractical, while a legitimate login, which hashes once, experiences only a small, acceptable delay. General-purpose hashes, such as SHA-256, are designed to be fast, which makes them terrible for passwords, because an attacker can try billions of candidates quickly. Password hashing algorithms are designed to be slow and memory-hard, meaning they also use significant memory, which makes them expensive to attack with specialised hardware. Using the right algorithm, not just any hash, is therefore crucial, and it is why you should use a dedicated password hashing library, not a general hash function, for passwords.

In Python's standard library, hashlib provides pbkdf2_hmac, which applies a hash many times, with a salt, making it slow, and which is reasonable when no dedicated library is available, though bcrypt or Argon2 are preferred in production. Whichever you use, never write your own password hashing, never store passwords in plain text, and never store them encrypted with a reversible key your application holds, because a breach would expose the key and the passwords together. Password storage is a solved problem, and using established tools correctly is non-negotiable.

import hashlib, os

# Password storage: salted, slow hash (pbkdf2). Never store plain passwords.
def hash_password(password):
    salt = os.urandom(16)
    digest = hashlib.pbkdf2_hmac("sha256", password.encode(), salt, 200_000)
    return salt.hex() + ":" + digest.hex()

def check_password(password, stored):
    salt_hex, digest_hex = stored.split(":")
    digest = hashlib.pbkdf2_hmac("sha256", password.encode(),
                                 bytes.fromhex(salt_hex), 200_000)
    return digest.hex() == digest_hex

stored = hash_password("correct horse battery staple")
print(check_password("correct horse battery staple", stored))  # True
print(check_password("wrong password", stored))                # False

Section 12: Hashing Versus Encryption

Hashing and encryption are often confused, because both transform data into an unreadable form, but they serve different purposes, and using the wrong one is a serious security mistake. Hashing is one-way: it turns data into a fixed-size fingerprint, from which the original data cannot be recovered, at least not feasibly. It is used for verifying data without storing it, such as passwords, and for checking integrity, such as verifying a file has not changed, by comparing its hash before and after. Encryption is two-way: it turns data into an unreadable form that can be turned back into the original, using a key. It is used for protecting data that must be read later, such as stored personal data, or data in transit, such as a web request over HTTPS, where the recipient must decrypt it to use it.

The distinction matters most for passwords. Passwords should be hashed, not encrypted, because the system never needs to recover the original password, only to verify that a provided password matches the stored one. If passwords were encrypted, a breach exposing both the encrypted passwords and the key would expose all passwords, defeating the protection. Hashing avoids that, because there is no key that can reverse a hash, so a breach exposes only hashes, which are far less useful, especially when salted and slow. That is why "we encrypt passwords" is a red flag.

Encryption, by contrast, is the right tool when data must be recovered. A user's stored address, which the application must display later, cannot be hashed, because hashing would destroy it. It must be encrypted, if it needs protection at rest, with a key held securely, and decrypted when needed. Data in transit, such as a login request, must be encrypted with HTTPS, so it cannot be read or altered by intermediaries, and then decrypted by the server to be used. Encryption's security depends entirely on key management: who holds the key, how it is stored, how it is rotated, and what happens if it leaks. A key that is hard-coded, logged, or shared widely is a key that will leak, and encryption with a leaked key provides no protection, which is why key management is as important as the encryption algorithm itself.

There is also a third concept worth distinguishing: encoding, which is neither hashing nor encryption, because it is easily reversible and provides no security at all. Base64 encoding transforms data into text form, but anyone can decode it instantly, so it must never be mistaken for protection. A password stored as Base64 is as good as plain text. Beginners sometimes confuse encoding with encryption, because both produce unreadable-looking output, but the difference is crucial: encoding is for format, encryption is for secrecy with a key, and hashing is for verification without recovery.

Finally, use established libraries for all three, never invent your own algorithms, because cryptographic design is extremely difficult, and even experts make mistakes discovered only after years of analysis. Standard libraries provide hashing, encryption, and encoding tested by many eyes, and using them correctly, with safe key management and sensible parameters, is far safer than any custom solution.

import hashlib

# Hashing is one-way: you can verify, but you cannot recover the original.
data = "hello"
digest = hashlib.sha256(data.encode()).hexdigest()
print("Hash:", digest)
print("You cannot turn this hash back into 'hello' without guessing it")

Section 13: Safe Login Flows

A login flow is the sequence by which a user proves their identity and gains access, and it must be designed carefully, because it is the gateway to accounts, and attackers focus on it. A safe login flow has several properties, each of which addresses a specific risk, and together they make login both usable for legitimate users and resistant to misuse. The first property is to verify credentials securely: compare the provided password with the stored hash, using a constant-time comparison, which takes the same time regardless of how much matches, to avoid leaking information through timing, where an attacker could infer how much of a password is correct by measuring response times. Python's hmac.compare_digest provides constant-time comparison, and it should be used for secrets, rather than a simple equality check, which can leak through timing.

The second property is to give generic error messages on failure, as covered in the authentication testing section. Whether the username does not exist, or the password is wrong, the response should be the same, such as "invalid username or password", without revealing which part was wrong, because revealing that a username exists helps attackers enumerate accounts, which they can then target with password guessing or phishing. That generic message is slightly less helpful to a legitimate user who mistyped their username, but it is a necessary trade-off for security, and it is standard practice. Users who forget their username can recover it through a separate, safe flow, rather than through login error messages that leak account existence.

The third property is to protect against brute force, which is covered in detail in the next section, but which starts in the login flow: limit attempts, delay responses after failures, and consider additional verification, such as a CAPTCHA or a second factor, after repeated failures, to slow automated guessing without blocking legitimate users excessively. The fourth property is to create a secure session on success, as covered in the sessions section, with a random, unguessable session identifier, stored safely, and with appropriate cookie flags, so the session cannot be hijacked easily. A login that succeeds but creates an insecure session is a login that hands the account to the next attacker who steals the session.

The fifth property is to log login attempts, both successes and failures, with enough detail to detect attacks, such as the time, the username, and the source, but without logging passwords, which must never appear in logs, even in failed attempts, because a mistyped password in a log is still a password. Login logs should be monitored for patterns, such as many failures from one source, which indicate an attack.

Finally, a safe login flow should support account recovery and second factors, as separate, carefully designed flows, not as afterthoughts. Password reset must use random, expiring tokens, not guessable links. Second factor authentication, such as a code from an app, adds a layer beyond passwords, so a stolen password alone is not enough to access an account. Passwords alone are vulnerable to guessing, phishing, and reuse, and a second layer significantly raises the bar for attackers.

import hmac

# Constant-time comparison: does not leak how much of a secret matched.
stored = "correct-secret"
provided = "correct-secret"
print("Match:", hmac.compare_digest(stored, provided))
print("Login errors must be generic: 'invalid username or password'")

Section 14: Protecting Against Brute Force

Brute force is an attack where an attacker tries many passwords, or many guesses, in rapid succession, hoping to find the correct one by trial and error. It is a simple attack, but it is effective against weak passwords and unprotected login systems, because computers can try thousands of guesses per second, and because many users choose predictable passwords, such as common words, names, or dates. Protecting against brute force means making guessing slow, expensive, and detectable, so that an attacker cannot try enough guesses, fast enough, to succeed, before being blocked or noticed. That protection is essential for any login system, because passwords, however well stored, are only as strong as the system's resistance to guessing.

The most basic protection is rate limiting: restricting how many login attempts can be made, per account, per source, or overall, within a time period. For example, allowing only five failed attempts per account per fifteen minutes, after which further attempts are blocked or delayed, makes brute force impractical, because an attacker who needs thousands of guesses would take days or weeks, during which they are likely to be noticed. Rate limiting must be applied carefully: limiting per account protects that account, but an attacker could try many accounts with few guesses each, which is called password spraying, and which per-source limiting, blocking an address that tries many accounts, helps to prevent. Combining per-account and per-source limits covers both patterns, and is the standard approach.

Another protection is progressive delays: increasing the wait time after each failed attempt, so the first few failures are quick, for legitimate users who mistype, but subsequent failures become increasingly slow, making automated guessing painful. A delay doubling after each failure quickly makes brute force infeasible, while barely affecting a user who mistypes once or twice. Delays must be implemented on the server, not just on the client, because client-side delays can be bypassed.

A third protection is account lockout, where an account is temporarily locked after many failures, requiring a reset or a wait before further attempts. Lockout is effective against brute force on a specific account, but it has a drawback: an attacker can lock out a legitimate user deliberately, by failing many logins for that user, causing a denial of service for that account. That is why temporary lockouts, with automatic unlocking after a period, are preferred over permanent lockouts, and why lockouts should be combined with alerts to the account owner, so they know their account is being targeted. Lockout is a trade-off between security and availability, and it should be tuned to your users: a short lockout, with notification, is usually a good balance.

A fourth protection is to require additional verification after suspicious activity, such as a CAPTCHA, which distinguishes humans from automated scripts, or a second factor, which an attacker guessing passwords does not have. Those steps raise the cost of brute force significantly, because they cannot be automated easily. They also add friction for legitimate users, so they should be triggered by suspicious patterns, such as many failures, rather than on every login. Brute force protection is about raising attacker cost while minimising legitimate user friction.

# Rate limiting: block further attempts after too many failures.
attempts = {}

def login_attempt(user, success):
    if success:
        attempts[user] = 0
        return "logged in"
    attempts[user] = attempts.get(user, 0) + 1
    if attempts[user] >= 5:
        return "blocked: too many failed attempts, try later"
    return f"failed attempt {attempts[user]}"

for _ in range(6):
    print(login_attempt("ada", False))

Section 15: Sessions Done Safely

A session is how a server remembers that a user has logged in, across many requests, without requiring them to log in again for every page. When a user logs in successfully, the server creates a session, usually identified by a random session id, stored in a cookie in the user's browser, and stored on the server, associated with that user. On each subsequent request, the browser sends the session id, the server looks it up, and if it is valid, the user is recognised. Sessions are convenient, but they are also a target: if an attacker steals a session id, they can impersonate the user, without needing the password, until the session expires or is revoked. Session safety is therefore critical, and it involves how ids are generated, stored, transmitted, and expired.

Session ids must be random, long, and unguessable, generated by a secure random generator, not by predictable values such as user ids, timestamps, or sequential numbers, which an attacker could guess. Python's secrets module provides secure random tokens, suitable for session ids, and it should be used, rather than the regular random module, which is predictable and not suitable for security. A session id should also be long enough, such as 32 bytes, to make guessing infeasible, even with many attempts. Predictable session ids are a serious vulnerability, because they allow session hijacking by guessing, without any other exploit needed, and they are entirely preventable by using secure randomness.

Sessions must expire. An absolute expiry, such as 24 hours, limits how long a stolen session can be used, even if never detected. An idle expiry, such as 30 minutes of inactivity, limits how long a session left open on a shared device remains usable. Both should be implemented on the server, by storing expiry times with sessions and checking them on every request, not just by relying on cookie expiry in the browser, which can be ignored. Sessions should also be revoked on password change, logout, or suspicious activity. Logout must invalidate the session on the server, not just delete the browser cookie, because a deleted cookie can be restored from a stolen copy.

Sessions must be transmitted safely, over HTTPS only, with cookie flags that prevent theft, as covered in the next section, and stored safely on the server, with access controls. Session data should be minimal: store only what is needed to recognise the user, such as a user id, not passwords or full profiles, because session storage is another place data can leak. And sessions should be regenerated on privilege changes, such as after login, so that a session id created before login, which might have been fixed by an attacker, is replaced with a fresh one after authentication.

Finally, sessions should be monitored and limited. A user should not have an unlimited number of active sessions, because that makes it hard to notice a stolen one among many legitimate ones. Limiting sessions per user, and letting users see and revoke their active sessions, helps them detect and stop hijacking. Session safety combines secure generation, safe transmission, sensible expiry, proper revocation, and monitoring, and a weakness in any one can undermine the others.

import secrets

# Session ids must be long, random, and unguessable: use secrets, not random.
session_id = secrets.token_urlsafe(32)
print("Session id (safe):", session_id[:12] + "...")
print("Never use: user id, timestamp, or sequential numbers as session ids")

Section 16: Cookies: Secure Flags

Cookies are small pieces of data that a server asks a browser to store and send back with future requests, and they are commonly used for sessions, as covered earlier, and for preferences. Because cookies travel with every request, and because they often contain session ids, their security flags matter enormously: a cookie without the right flags can be stolen through script injection, sent over insecure connections, or leaked to other sites, turning a secure session into a compromised one. Understanding cookie flags is therefore essential for any developer who uses cookies, which is almost every web developer.

The most important flags are HttpOnly, Secure, and SameSite, and each addresses a specific risk. HttpOnly means the cookie cannot be accessed by JavaScript in the browser, only by the browser itself when sending requests. That prevents theft through cross-site scripting, where malicious script tries to read cookies, because the script cannot access HttpOnly cookies, even if it runs on the page. Session cookies should always be HttpOnly, because there is rarely a legitimate reason for JavaScript to read a session id.

Secure means the cookie is only sent over HTTPS, encrypted connections, never over plain HTTP, where it could be intercepted by anyone on the network. Session cookies should always be Secure, in production, because sending a session id over plain HTTP exposes it to interception, especially on shared networks, such as public Wi-Fi, where attackers can listen to traffic. The Secure flag is simple to set, and it provides strong protection against network interception, at no cost to legitimate users, because legitimate traffic should already be over HTTPS, as covered later. A session cookie without Secure, sent over HTTP, is a session waiting to be stolen on an open network.

SameSite controls whether a cookie is sent with requests from other sites, which matters for cross-site request forgery, covered later. SameSite=Lax, the modern default in many browsers, means the cookie is sent with top-level navigation, such as clicking a link, but not with cross-site subrequests, such as images or forms from another site, which blocks many forgery attacks while preserving normal navigation. SameSite=Strict is stronger, blocking even top-level navigation from other sites, but it can break legitimate flows, such as returning from a payment provider. SameSite=None allows cross-site sending, but requires Secure, and should be used only when cross-site cookies are genuinely needed, such as for embedded content. For most session cookies, Lax is a good balance, and it should be set explicitly, rather than relying on browser defaults, which vary and change.

There are also practices around cookie scope and lifetime. A cookie's Path and Domain should be as narrow as possible, so it is only sent to the parts of your site that need it. A cookie's expiry should match the session's expiry. And cookies should never contain sensitive data directly, such as a password or a user role, because cookies are stored in the browser, where they can be inspected, and sent with every request. Store only an opaque session id in a cookie, and keep sensitive data on the server, associated with that id.

# A safe session cookie: HttpOnly, Secure, SameSite=Lax, narrow scope.
cookie = ("session_id=abc123; HttpOnly; Secure; SameSite=Lax; "
          "Path=/; Max-Age=86400")
print(cookie)

Section 17: Tokens: Safe Handling

Tokens are opaque strings that represent authorisation, such as API keys, access tokens, and password reset tokens, and they are widely used in back-end systems, for user sessions, for API access, and for one-time actions. A token is like a key: whoever holds it can act as its owner, within its scope, until it expires or is revoked. Safe token handling is therefore critical, and it involves how tokens are generated, stored, transmitted, expired, and revoked, with the same care as passwords, because a leaked token is as good as a leaked password, for the duration of its validity.

Token generation must use secure randomness, as with session ids, so tokens cannot be guessed. A token should be long, random, and unique, generated with a secrets module, not with predictable values, timestamps, or user data, which an attacker could guess or construct. A reset token that is simply the user's id, or a hash of their email, is not a token, it is a guessable identifier, and it allows anyone to reset any account by constructing the token. That mistake, using predictable values as tokens, is a serious vulnerability, and it is entirely preventable by using secure random generation for every token, without exception.

Token storage must be careful. Tokens that grant long-term access, such as API keys, should be stored hashed, like passwords, so that a database breach does not expose usable tokens, only hashes, which cannot be used directly, though they must still be verified by hashing the presented token and comparing, just as with passwords. One-time tokens, such as password reset tokens, should also be stored hashed, for the same reason, and they should be single-use, expiring quickly, such as within an hour, and invalidated after use, so that a leaked token has a short window and cannot be reused. Storing tokens in plain text in a database is a common mistake, and it turns a database breach into a full account compromise, for every token stored, which is a catastrophic outcome that hashing prevents, or at least mitigates.

Token transmission must be over HTTPS only, never over plain HTTP, and never in URLs for sensitive, long-lived tokens, because URLs are logged in browser history, server logs, and referrer headers, exposing the token to many places beyond the intended recipient. One-time tokens in URLs, such as password reset links, are an exception, because they must be delivered by email, which uses links, but they should be short-lived and single-use, to limit the exposure from URL logging, and they should never be long-lived API keys, which should be transmitted in headers, not URLs, where they are less likely to be logged. That distinction, short-lived tokens in URLs, long-lived tokens in headers, is a practical rule that balances usability with safety.

Token scope and expiry must be minimal. A token should grant only the permissions it needs, for only as long as it needs them, following least privilege. An API token for reading tasks should not also allow deleting users. A reset token should expire in an hour, not a month. And tokens should be revocable, so a compromised token can be invalidated promptly, without waiting for expiry. Revocation requires server-side storage of token validity, which adds complexity, but it is essential for responding to leaks.

import secrets, hashlib

# Store tokens hashed, like passwords, so a breach does not expose usable tokens.
token = secrets.token_urlsafe(32)
stored = hashlib.sha256(token.encode()).hexdigest()
print("Token sent to user:", token[:8] + "...")
print("Stored hash only:", stored[:12] + "...")

Section 18: Authorisation Checks on Every Request

Authorisation, deciding whether a user is allowed to perform an action, must be checked on every request, on the server, for every protected resource and action, without exception. That rule sounds obvious, but it is the most commonly violated security rule in back-end development, because it is easy to forget a check on a new endpoint, to assume a check in one place covers another, or to rely on the client to hide an action, as covered earlier. A single missing authorisation check can expose private data or allow unauthorised actions, and attackers actively probe for such omissions, by trying endpoints with different users, ids, and roles, looking for the one that forgot to check. Every request, every time, is the standard, and it must be enforced by design, not by memory.

The way to enforce it by design is to centralise authorisation, rather than scattering checks throughout code, where they can be forgotten. A common pattern is a helper function, or middleware, that runs before each handler, checks the user's permissions for the requested action and resource, and denies the request if the check fails, before any handler logic runs. That central check ensures no endpoint can accidentally skip authorisation, because the check happens automatically, unless explicitly bypassed, and bypasses should be rare, documented, and reviewed. Centralisation also makes authorisation easier to audit: a reviewer can read the central logic and see all rules in one place, rather than hunting through every handler for its checks.

Authorisation checks must be based on server-side truth, not on client-provided claims, as covered earlier. A check that asks "does the requesting user own this resource?" must look up ownership in the database, using the authenticated user id from the session, and the resource id from the request, and compare them, rather than trusting a client-provided owner field, or a client-provided role. A check that asks "is this user an administrator?" must look up the user's role in the database, not trust a role field sent by the client, which can be forged. Server-side truth is the foundation of authorisation, and any check that relies on client data is not a check at all, it is a suggestion that an attacker will ignore.

Authorisation must also be tested, with a matrix of users, resources, and actions, asserting allowed and denied cases, and asserting that denied requests do not change data. That testing should cover every endpoint, including new ones, as part of development, not as an afterthought, because a new endpoint without an authorisation test has unverified authorisation, a common source of vulnerabilities. A suite covering authorisation for every endpoint, run on every change, catches missing checks before they reach production.

Finally, authorisation failures should be handled safely: return a generic denial, such as 403 Forbidden, without revealing why, or whether the resource exists, because revealing existence helps attackers enumerate resources. A request for another user's private task should return the same response as a request for a non-existent task, so an attacker cannot use error differences to discover which ids exist. Authorisation on every request, without exception, prevents the most common and most serious class of back-end vulnerabilities.

# Authorisation on every request: check ownership from server-side truth.
tasks = {1: "ada", 2: "ben"}  # task id -> owner, from the database

def can_access(user, task_id):
    return tasks.get(task_id) == user

print(can_access("ada", 1))  # True: owner
print(can_access("ben", 1))  # False: not owner, denied

Section 19: Insecure Direct Object References

An insecure direct object reference, often shortened to IDOR, occurs when an application exposes an internal identifier, such as a user id, task id, or file name, in a request, and fails to check that the requesting user is authorised to access the object with that identifier, allowing an attacker to access other users' objects simply by changing the identifier. For example, a URL like /tasks/123 might return task 123 to anyone who requests it, without checking whether the requester owns task 123, so an attacker who changes 123 to 124 can read another user's task. IDOR is one of the most common web vulnerabilities, because it arises from a simple omission, a missing authorisation check, and because identifiers are predictable, often sequential numbers, making guessing easy.

IDOR is a specific form of the missing authorisation problem from the previous section, but it deserves its own section, because it is so common and so easily overlooked, especially when identifiers appear in URLs, which feel like addresses rather than security boundaries. Developers often think of a URL as a location, and assume that if a user knows the URL, they must be allowed to access it, which is false: knowing an identifier is not authorisation, and identifiers are easy to guess, especially sequential ones, or to discover, through other means, such as shared links, or enumeration. Authorisation must be checked for every object reference, regardless of how the identifier was obtained, because obtaining an identifier is not permission to use it.

Preventing IDOR involves two complementary measures. The first is authorisation checks: for every request referencing an object by id, check that the authenticated user owns it, using server-side data, before returning or modifying it. That check must be applied to every endpoint taking an object id, including read, update, and delete. The second measure is using unpredictable identifiers, such as random UUIDs, instead of sequential numbers, which makes guessing harder, though it is not a substitute for authorisation, because an identifier can still be leaked. Unpredictable ids are a helpful additional layer, but they must never replace authorisation checks.

Testing for IDOR is straightforward and should be part of every authorisation test suite: create two users, each with their own objects, and for each endpoint, assert that each user can access their own objects, and cannot access the other's, by trying the other's ids directly. That test simulates exactly what an attacker does: changing an id and seeing if access is granted. It is cheap to implement, because the pattern is the same for every endpoint, varying only in the resource and ids used.

Finally, IDOR teaches a general lesson about identifiers: they are not secrets, and they are not permissions. An id is a reference, not an authorisation, and treating it as either is a mistake. Design your APIs with that in mind: expose ids where needed for functionality, but always check authorisation when an id is used, and never assume that an id's obscurity, or its presence in a URL, implies permission. That mindset, applied consistently, prevents IDOR and the broader class of authorisation failures it represents, which are among the most damaging vulnerabilities in back-end systems, because they expose private data directly, with no sophisticated attack needed, just a changed number in a URL.

# IDOR defence: always check ownership, even when the id is known.
tasks = {123: "ada", 124: "ben"}

def get_task(user, task_id):
    if tasks.get(task_id) != user:
        return "denied"
    return f"task {task_id}"

print(get_task("ada", 123))  # allowed: own task
print(get_task("ada", 124))  # denied: another user's task

Section 20: SQL Injection in Plain Words

SQL injection is a vulnerability where an attacker inserts, or injects, SQL code into a query, through input that the application incorporates into the query without proper handling, causing the database to execute the injected code as part of the query, rather than treating it as data. For example, if an application builds a query by concatenating a user-provided name directly into SQL text, an attacker can provide a name containing SQL syntax that changes the query's meaning, such as returning all rows, bypassing a login check, or modifying data, depending on the query and the database permissions. SQL injection is one of the oldest and most serious web vulnerabilities, because it can lead to complete database compromise, including data theft, modification, and deletion, from a single input field.

The key concept is the distinction between code and data in a query. A SQL query is code, written by the developer, with placeholders for data, such as a username or an id, provided at runtime. When data is incorporated safely, through parameterised queries, covered next, the database treats it strictly as data, never as code, no matter what characters it contains, so even input containing SQL syntax is harmless, because it is compared as a value, not executed as instructions. When data is incorporated unsafely, by building query text through string concatenation, the database cannot distinguish developer code from attacker data, because they are mixed together in one string, and it executes the whole thing as code, including the attacker's part. That mixing of code and data is the root cause, and preventing it is the defence.

SQL injection is entirely preventable, and its prevention is simple and well established, which makes its continued occurrence frustrating to security professionals. The prevention is parameterised queries, also called prepared statements, where the query structure is sent to the database separately from the data, and the data is bound to placeholders, so the database never treats data as code. Every modern database library supports parameterised queries, including Python's sqlite3, which you have used throughout this book with ? placeholders, and using them consistently, for every query that includes user input, eliminates SQL injection for those queries. There is no excuse for string concatenation in queries, even for internal or trusted input, because trusted input can become untrusted, through changes, bugs, or data originally provided by users and stored, and because consistency is what prevents mistakes.

This section describes SQL injection defensively, so you can recognise and prevent it, without providing exploit details for attacking systems. The defensive lesson is clear: never build SQL by concatenating input, always use parameterised queries, and validate input as well, though validation alone is not sufficient, while parameterisation addresses the root cause, the mixing of code and data. Also apply least privilege to database accounts, so that even if an injection occurred, limited permissions would restrict an attacker.

Finally, test for SQL injection defensively, by providing inputs containing SQL-like characters, such as quotes and semicolons, through your own test suite, in your own test environment, and asserting they are treated as data, not altering query behaviour. Those tests verify that parameterisation is working, without attacking a live system. SQL injection is a solved problem, and a developer using parameterised queries consistently, for every query, will never introduce it.

import sqlite3

# Safe: parameterised query. Data is never treated as SQL code.
db = sqlite3.connect(":memory:")
db.execute("CREATE TABLE users (name TEXT)")
db.execute("INSERT INTO users VALUES ('ada')")
user_input = "ada' OR '1'='1"  # SQL-like text, treated as plain data
rows = db.execute("SELECT * FROM users WHERE name = ?", (user_input,)).fetchall()
print("Rows returned for tricky input:", rows)  # []: no injection, just no match

Section 21: Cross-Site Scripting in Plain Words

Cross-site scripting, usually shortened to XSS, is a vulnerability where attacker-controlled text is inserted into a web page and then treated as code by a visitor's browser. Imagine a comment system that stores a user's comment and shows it to other users, without checking what the comment contains. If a comment contains markup or script code, and the page displays it as raw markup, the visitor's browser will run that code, as if the site itself had written it. That code runs in the visitor's context, so it can read the page, steal data shown on it, or perform actions as that visitor. The vulnerability is on the server, for failing to handle user text safely, but the harm happens in victims' browsers.

The root cause is the same mixing problem as SQL injection: data is treated as code. In SQL injection, user input is mixed into a query and treated as SQL. In XSS, user input is mixed into a page and treated as markup or script. The defence is also parallel: keep data as data, by encoding it when it is placed into a page. Encoding means converting characters with special meaning in HTML, such as angle brackets and quotes, into harmless forms that display as text rather than being interpreted. A comment containing an opening angle bracket, when encoded, shows up as a visible bracket character on the page, not as the start of a tag.

Python's standard library provides html.escape, which converts the dangerous characters into safe entities, and that single function is the core defence for text inserted into HTML. Whenever you place user-supplied text into a page, escape it, unless you have a specific, safe reason not to, such as rendering trusted markup through a proper sanitiser. The key word is "trusted": your own fixed templates are trusted, user input is not. Even input from an authenticated user should be escaped, because accounts can be compromised, and a compromised account posting script that runs for every visitor turns one breach into many victims.

A second layer is the HttpOnly cookie flag, covered earlier, which prevents scripts from reading session cookies, so even if an XSS flaw exists, session theft through script is blocked. A third layer is a Content Security Policy, covered in the headers section, which can restrict what scripts a page is allowed to run. Those layers help, but they do not replace escaping: escaping is the primary defence, and it must be applied consistently, everywhere user data appears in a page, including names, comments, search terms reflected in results, and error messages that echo input.

Testing for XSS is straightforward and defensive: submit test input containing markup characters through your own forms, in your own test environment, and check that the displayed page shows them as text, not as rendered markup. Add those checks to your test suite, so a future change that forgets to escape is caught before release. XSS is common, but it is also well understood, and consistent escaping, plus HttpOnly cookies and a sensible content policy, makes it hard to introduce and easy to prevent.

Section 22: Cross-Site Request Forgery in Plain Words

Cross-site request forgery, usually shortened to CSRF, is an attack where a malicious site tricks a visitor's browser into making a request to your site, using the visitor's existing login. Imagine you are logged into a task application, and you visit a different, malicious page in another tab. That page can contain a hidden form that submits to your task application, for example to delete a task, or change a setting. Your browser, when submitting that form, will include your cookies for the task application, because that is how browsers work: cookies are sent automatically with requests to their site. The task application sees a request with a valid session cookie and, if it does not check anything else, performs the action, believing you requested it.

The key insight is that cookies alone cannot prove that a request came from your own site, because browsers send cookies automatically, even for requests initiated by other sites. Authentication proves who the user is, but it does not prove that the user intended the request, or that the request came from your pages. CSRF protection therefore adds a second check: a token that only your own pages can provide. When your server renders a form, it includes a random, secret token, unique to the user's session, as a hidden field. When the form is submitted, the server checks that the token matches the session's token. A malicious site cannot know the token, because it cannot read your pages' content, so its forged form will lack a valid token, and the server will reject it.

Generating a CSRF token is simple: use the secrets module to create a random token, store it in the session, and include it in each form. On submission, compare the submitted token with the session token using a constant-time comparison, as covered later, and reject the request if they do not match. The token must be random and unpredictable, not derived from something an attacker can guess, and it should change with the session, so a leaked token does not stay valid forever. GET requests, which should only read data and never change it, do not need CSRF tokens, but every state-changing request, POST, PUT, and DELETE, should be protected, because those are the requests an attacker wants to forge.

A complementary layer is the SameSite cookie flag, covered earlier, which tells browsers not to send cookies with cross-site requests, blocking most CSRF attempts at the browser level. SameSite is valuable, but it should not be the only defence, because browser behaviour varies, and defence in depth calls for both the flag and tokens. Another helpful practice is to require re-authentication, or a second confirmation, for especially sensitive actions, such as changing a password or deleting an account, so a single forged request cannot cause serious harm.

Testing CSRF protection is simple: in your own test environment, submit a state-changing request without a token, and with a wrong token, and assert that both are rejected, and that no change occurs. Then submit with a valid token and assert success. Those tests, run on every change, ensure that new forms and endpoints do not forget their tokens, which is the most common CSRF mistake: protection added to old forms, but not to new ones.

Section 23: HTTPS Everywhere

HTTPS is HTTP with encryption, provided by TLS, which protects data in transit between the browser and your server. Without it, everything sent between a user and your site, including passwords, session cookies, and personal data, can be read or altered by anyone positioned between them, such as on a public Wi-Fi network, or by a compromised network device. With HTTPS, that traffic is encrypted, so intermediaries see only unreadable data, and the server's identity is verified, so users can be confident they are talking to your site, not an impostor. HTTPS is not an optional extra for sensitive pages. It should be used for your entire site, for every page and every request, because even pages that seem public can leak session cookies or personal data.

A common mistake is to use HTTPS only for login and payment pages, and plain HTTP elsewhere. That leaves session cookies exposed on the plain pages, because a cookie set for the whole site is sent with every request, including plain ones, where it can be stolen and reused. It also leaves users vulnerable to tampering on the plain pages, where an attacker could modify content, or inject scripts that then affect the secure pages. The modern standard is HTTPS everywhere, with all HTTP requests redirected to HTTPS, so no request ever travels unencrypted, and no cookie is ever sent in the clear.

Obtaining a certificate, the credential that proves your site's identity and enables encryption, is now free and automated, through services that issue certificates at no cost, and tools that renew them automatically. There is no longer a cost or complexity excuse for serving a site over plain HTTP, and browsers now warn users about non-HTTPS sites, which also damages trust. When you deploy, configure your server to serve HTTPS, set up automatic renewal, and redirect all HTTP traffic to HTTPS, with a permanent redirect, so bookmarks and old links are updated.

Two supporting measures complete the picture. First, the Secure cookie flag, covered earlier, ensures cookies are only sent over HTTPS, so even if a user somehow makes a plain request, their session cookie is not exposed. Second, a header called Strict-Transport-Security tells browsers to always use HTTPS for your site, even if a user types an HTTP address, preventing downgrade attacks where an attacker tries to force a plain connection. Together, HTTPS everywhere, HTTP redirection, Secure cookies, and Strict-Transport-Security form a complete transport security story, and each piece is simple to implement.

Testing HTTPS is part of deployment checks: request your site over HTTP and confirm it redirects to HTTPS, request it over HTTPS and confirm it works, and check that cookies carry the Secure flag. Those checks should be repeated after any deployment change, because a misconfigured server can silently stop serving HTTPS, or stop redirecting, and users will not notice until harm is done.

Section 24: Security Headers in Plain Words

Security headers are instructions your server sends with every response, telling the browser how to behave safely when displaying your site. They are a cheap, powerful layer of defence, because they are set once, on the server, and then protect every page, without changing your application's logic. Think of them as safety settings for the browser: they restrict what a page can do, where it can load resources from, and how it handles framing and cookies. They do not replace the primary defences, such as escaping output and validating input, but they add depth, so a single mistake elsewhere is less likely to become a serious breach.

The most important headers are a small set, worth knowing by name. Content-Security-Policy, often shortened to CSP, controls which sources a page may load scripts, styles, and other resources from, and can block inline scripts, which significantly limits XSS damage. X-Content-Type-Options, set to nosniff, prevents browsers from guessing a file's type, which stops attackers from uploading a file that the browser then misinterprets as a script. X-Frame-Options, or the frame-ancestors directive in CSP, prevents your pages from being embedded in frames on other sites, which blocks clickjacking, where a malicious page overlays your site invisibly to trick users into clicking something. Strict-Transport-Security, covered in the HTTPS section, forces HTTPS. Referrer-Policy controls how much information is sent in the Referer header when users follow links, protecting privacy.

Setting headers in Python's http.server is straightforward: after creating a response, call send_header for each header before sending the body. For example, you can set Content-Security-Policy to allow resources only from your own site, X-Content-Type-Options to nosniff, and X-Frame-Options to DENY, meaning your pages may never be framed. Those values are a safe starting point for many sites, and they can be adjusted as your site's needs grow, for example to allow specific trusted sources for scripts or images, while still blocking everything else.

A caution about CSP: a policy that is too strict can break your site, blocking legitimate scripts or styles, and a policy that is too loose, such as allowing everything, provides no protection. Start with a restrictive policy, test your site thoroughly, and loosen it only where needed, for specific trusted sources, documenting each exception. Use a reporting directive during testing, so the browser reports violations without blocking, letting you discover what your site actually needs before enforcing the policy. That gradual approach avoids breaking the site while still gaining protection.

Headers should be checked as part of deployment and testing: request your site's pages and confirm the headers are present, with the expected values, and repeat that check after changes, because a server reconfiguration can silently drop headers. A site with good headers is not automatically secure, but a site without them is missing a simple, effective layer that every modern site should have.

Section 25: Safe File Uploads

File uploads are one of the riskiest features a back-end can offer, because they allow outside users to place files on your server, or in your storage, and those files may then be served to other users, or processed by your system. An attacker who uploads a file that your server later treats as code, or that other users' browsers treat as a script, can gain control of your server, or attack your users. Safe file handling is therefore essential, and it follows the same principles as the rest of this chapter: validate, restrict, isolate, and never trust the uploader's claims about the file.

The first rule is to never trust the filename or the content type supplied by the uploader. A filename can contain path characters, such as slashes or double dots, designed to escape your upload directory and overwrite files elsewhere, a flaw called path traversal. Always generate your own safe filename, for example a random identifier plus a verified extension, and store the original name separately, only for display, after escaping it. Similarly, a content type header can claim a file is an image while it is actually something else, so do not rely on it for security decisions.

The second rule is to validate the file's actual content, not just its claimed type. For images, you can check the file's magic bytes, the first bytes that identify its real format, or attempt to open it with a safe image library, rejecting files that fail. For other types, apply allow-listing: accept only the specific formats you need, such as PNG and JPEG for avatars, and reject everything else, rather than trying to block dangerous types, which is a losing game, because there are always types you did not think of. Also enforce size limits, so a huge upload cannot exhaust your disk or memory, as covered in the denial-of-service section.

The third rule is isolation: store uploads outside your application's code directory, and serve them in a way that prevents execution. Files should never be placed where the web server could run them as code, and they should be served with headers that prevent browsers from interpreting them as scripts, such as Content-Type set to the verified type, and Content-Disposition to force download where appropriate, rather than inline display, for untrusted types. Scanning uploads for malware, where feasible, is an additional layer, though it does not replace validation and isolation.

Finally, access to uploads should be controlled like any other resource: a private upload should only be downloadable by its owner, or by authorised users, with the same authorisation checks as other endpoints, not by anyone who guesses the URL. Public uploads, such as avatars, should still use unpredictable filenames, so they cannot be enumerated. File uploads, handled with generated names, content validation, size limits, isolation, and access control, can be offered safely, but each of those measures matters, and skipping one can undo the others.

Section 26: Safe Error Messages

Error messages are helpful to developers, but dangerous when they reveal too much to users or attackers. A detailed error that includes a database query, a file path, a stack trace, or internal configuration tells an attacker how your system works, what technologies it uses, and where its weaknesses might be. That information does not, by itself, break into a system, but it makes an attack much easier, by narrowing the search from guessing to targeting. Safe error handling therefore means giving users enough information to understand what went wrong, and giving developers the full detail, but in separate places: brief messages for users, full details in logs.

The classic example is a login error. A message that says "no such user" for one input and "wrong password" for another tells an attacker which usernames exist, enabling account enumeration, where they build a list of valid accounts to attack further. A safe login error says the same thing in both cases, such as "invalid username or password", revealing nothing about which part was wrong. The same principle applies elsewhere: a "file not found" error that reveals a full path, or a database error that reveals a table name, gives an attacker information they should not have, and should be replaced with a generic message, with the detail logged server-side.

Implementing this split is straightforward. In your code, catch exceptions at the boundary of a request, log the full exception, with a request id, to your server logs, where developers can read it, and return a generic response to the user, such as "something went wrong, please try again", with the request id, so support can look up the log entry. That way, users get a usable message, support can help, developers can debug, and attackers learn nothing. Never return raw exception text, stack traces, or library error messages directly to users, in production, because those are written for developers, not for the public.

Development and production should differ here. In development, detailed errors are useful, and it is fine to show them, because the audience is the developer, on their own machine. In production, detailed errors must be off, replaced by generic messages and logging. That difference should be controlled by configuration, such as an environment variable, so the same code behaves safely in production, without manual changes at deploy time, which are easy to forget. Test the production configuration, not just development, to confirm that errors are generic there.

Error messages also matter for APIs. An API error should include a stable error code, a brief human-readable message, and no internal detail, so clients can handle failures without learning about your internals. Validation errors are an exception in a limited sense: telling a user that an email address is invalid, or a field is too long, is helpful and expected, but even there, avoid revealing internal rules that help attackers, such as exact password requirements beyond what is needed, or database constraints. Safe errors are a small habit with a large payoff: brief for users, detailed in logs, never leaking internals.

Section 27: Rate Limiting as a Security Control

Rate limiting, introduced in the brute-force section, is a security control in its own right, protecting your system against abuse by limiting how many requests a client can make in a given time. Without it, an attacker can hammer your login endpoint with guesses, flood your API with requests, submit huge numbers of forms, or scrape your data at machine speed, all at little cost to themselves, while consuming your resources and degrading service for everyone else. With rate limiting, each client gets a fair share, abuse becomes expensive and slow, and your system stays available for legitimate users.

Rate limits should be applied per client, usually per account or per network address, and per endpoint, with stricter limits for sensitive endpoints, such as login, password reset, and account creation, and looser limits for ordinary reads. A login endpoint might allow five attempts per minute per account, while a public article endpoint might allow hundreds per minute. Those numbers should be chosen to allow normal use comfortably, while blocking abuse, and they should be tested with realistic usage, so legitimate users are not locked out by a limit set too low. Limits that are too strict create their own problem, by frustrating users and generating support requests.

Implementing a basic rate limiter in Python is simple: keep a record of recent request times per client, in memory for a small system, or in a database or cache for a larger one, and reject requests that exceed the limit, with a 429 Too Many Requests response, and a Retry-After header telling the client when to try again. The record should expire old entries, so memory does not grow forever, and the limiter should be applied at the start of request handling, before expensive work, such as database queries or password hashing, so that rejected requests cost your system almost nothing. That ordering matters: a limiter that runs after expensive work does not protect against resource exhaustion.

Rate limiting also needs care around fairness and evasion. Limits per network address can unfairly block many users sharing one address, such as behind a school or office network, so combining address limits with account limits, and allowing higher limits for authenticated users, is often fairer. Attackers can also rotate addresses, so rate limiting alone does not stop a determined attacker, but it raises their cost and slows them down, and combined with other defences, such as CAPTCHAs after repeated failures, and monitoring for abuse patterns, it forms a strong layer. For a system running on more than one server, the limiter's records must be shared, in a database or cache, rather than kept in each server's memory, or an attacker can simply spread requests across servers to bypass per-server limits. That shared state is worth designing early, before scaling makes it harder to add. Rate limiting is not just a performance tool. It is a security control, and every public endpoint should have one.

Section 28: Protecting APIs: Keys and Authentication

An API is a door into your system for other programs, and like any door, it needs a lock. API clients are usually not people typing passwords into a browser, but programs, services, or scripts, and they authenticate with API keys or tokens, rather than with a browser session. An API key is a long, random secret, given to a client, which the client sends with each request, usually in a header, and the server checks it before processing the request. If the key is valid, the request is allowed; if it is missing or wrong, the request is rejected. That simple mechanism, done correctly, is the foundation of API security.

The first rule is that keys must be random, long, and unguessable, generated with the secrets module, not with predictable patterns, and stored safely, hashed on the server where possible, like passwords, so a database leak does not immediately expose usable keys. Keys should be sent only over HTTPS, in headers, not in URLs, because URLs are logged in many places, including server logs and browser history, and a key in a URL will leak into those logs. Keys should also be scoped, following least privilege: a key for reading tasks should not allow deleting users, and a key for one integration should not grant access to everything, so a leaked key causes limited harm.

The second rule is that API authentication must be checked on every request, for every endpoint, just like authorisation for users, with no exceptions for "internal" endpoints, because internal endpoints are often reachable, and attackers probe for them. Unauthenticated endpoints should be the explicit exception, documented and justified, such as a public health check, not the default. API responses for failed authentication should be generic, a 401 Unauthorized, without revealing whether a key exists or is merely expired, to avoid leaking information.

The third rule is lifecycle: keys should be revocable, so a compromised key can be invalidated immediately, and rotatable, so clients can replace keys periodically, or after a suspected leak, without downtime. Provide a way for key owners to see their keys' usage, and to revoke them, and log API key usage, so unusual patterns, such as a sudden surge from a new location, can be detected. Rate limiting, covered earlier, should also apply to API endpoints, per key, to prevent abuse and scraping.

Finally, distinguish API keys from user authentication. A key identifies a client application, not a person, and it should not grant the full powers of a user account, unless that is explicitly intended and scoped. Where an API acts on behalf of a user, use user tokens, such as OAuth-style tokens, with the user's permissions, rather than a master key, so the API's power is limited to what that user can do. API security, done well, is keys that are random, scoped, revocable, sent safely, and checked always, plus logging and rate limits, and it is worth getting right, because APIs are a favourite target for attackers, being machine-accessible and often less carefully protected than web pages.

Section 29: Data Minimisation and Privacy

Data minimisation is the practice of collecting, storing, and sharing only the data you actually need, for a specific purpose, and no more. It is both a privacy principle and a security control, because data you do not hold cannot be leaked, stolen, or misused. Every piece of personal data you collect, a phone number, an address, a date of birth, becomes a responsibility: it must be protected, it must be handled correctly, and its loss can harm the person it belongs to. Collecting data "just in case" creates risk without benefit, and the safest data is the data you never collected.

Applying minimisation starts with questions, for each field you plan to collect: why do we need this, what will we do with it, and what happens if it leaks? If you cannot answer clearly, do not collect it. If you need a user's age group, collect the group, not their exact date of birth. If you need to contact a user, collect an email address, not also a phone number and a home address, unless those are genuinely needed. If you need data temporarily, such as for a one-time verification, delete it when the purpose is complete, rather than keeping it indefinitely, because old data, forgotten in a database, is still at risk.

Minimisation also applies to what your system shares and displays. An API response should include only the fields the client needs, not every field in the database row, as covered in least privilege. A log line should include only what is needed for debugging, never personal data, passwords, or tokens, as covered in logging. An error message should not reveal personal data about other users. A page should not display data to users who do not need to see it. Each of those is minimisation in a different place, and together they reduce the surface area for leaks, because sensitive data appears in fewer places, and each place is easier to protect.

Retention is the other half of minimisation. Data should have a lifetime: kept while it is needed, deleted when it is not, with a clear policy for how long different kinds of data are kept, and automated cleanup where possible, such as deleting old sessions, old logs, and old inactive accounts after a defined period. That policy should be documented, so users know what you keep and for how long, and so your team can follow it consistently. Backups complicate retention, because deleted data may remain in backups, so backup retention should also be considered, with backups expiring on a schedule, rather than kept forever.

Privacy laws in many places require minimisation, purpose limitation, and user rights, such as access and deletion, and the details vary by region, so for a real product, you should check the rules that apply to your users. This section is not legal advice, but the engineering habit is universal: collect less, keep it shorter, share it narrower, and your system will be both more private and more secure, with less to protect and less to lose.

Section 30: Encrypting Sensitive Data at Rest

Encrypting data at rest means protecting data stored on disk, in a database, or in backups, so that it cannot be read if the storage itself is accessed by someone unauthorised, such as through a stolen disk, a leaked backup, or a compromised storage system. It is different from HTTPS, which protects data in transit, while it travels, and it is different from hashing, which is for verification, not recovery, as covered earlier. Encryption at rest is for data that must be read back later, such as personal details, but which should not be readable to anyone who merely gains access to the storage.

The simplest and most effective form of encryption at rest is full-disk or database-level encryption, provided by your operating system, database, or hosting platform, which encrypts everything stored, transparently, with a key managed by the platform. That protects against physical theft and storage leaks, without changing your code, and it is a good baseline for every system. It does not, however, protect against an attacker who compromises your running application, because the application, once running, can decrypt data through the platform, just as it should. That limitation is important: disk encryption protects storage, not a compromised application, and it must be combined with other defences, such as access control and monitoring.

For especially sensitive fields, such as payment details or government identifiers, application-level encryption adds another layer: your code encrypts the field before storing it, and decrypts it only when needed, with a key held separately from the database, such as in an environment variable or a key management service, never in the same database, and never in code. That way, a database leak alone, without the key, does not expose the sensitive fields, which is a meaningful improvement for the most sensitive data. Application-level encryption requires care: keys must be managed, rotated, and backed up safely, because losing a key means losing the data permanently, and encryption must be applied consistently, so sensitive fields are never stored unencrypted by a forgotten code path.

A related practice is tokenisation for the most sensitive data, such as card numbers, where the real value is stored in a specialised, highly protected system, and your database holds only a random token that refers to it, with no way to derive the real value. That is the safest approach for data you rarely need, because your system never holds the sensitive value at all, but it adds complexity and usually involves a third-party service, so it is reserved for the highest-risk data, not for every field.

Encryption at rest should be planned, not added as an afterthought: decide which data is sensitive enough to need it, choose the right level, disk or database encryption for everything, plus application-level encryption for the most sensitive fields, manage keys separately and safely, and test recovery, including what happens if a key is lost or rotated. A system that encrypts its stored data, with keys managed properly, is a system where a storage leak is an incident, not a catastrophe.

Section 31: Safe Redirects and Open Redirects

A redirect is when your server tells a browser to go to a different address, usually after login, or after an action completes, by returning a redirect response with a target address. Redirects are normal and useful: after logging in, a user is often sent back to the page they were trying to reach, with that page's address passed as a parameter, such as "next=/dashboard". An open redirect vulnerability occurs when an attacker can control that target address, and your server redirects to it without checking, so a link that looks like it goes to your trusted site actually sends the victim to a malicious site. The attacker then uses your site's reputation to make the malicious link look trustworthy, for phishing or other deception.

The danger is subtle, because the redirect itself does not steal data directly. It abuses trust: users are trained to trust links to sites they know, and a link starting with your domain looks safe, even if it ends up elsewhere. An attacker can craft such a link, share it in a message or post, and victims who click it are sent to a fake login page, or a page that tricks them into downloading something harmful, believing they are still dealing with your site. The fix is simple, but it must be applied to every redirect that uses user-supplied input: validate the target before redirecting.

Validation should use allow-listing, as covered earlier. The safest approach is to accept only relative paths on your own site, such as "/dashboard" or "/tasks", and reject anything that looks like an absolute address, such as one starting with "http://" or "//", which could point elsewhere. If you genuinely need to redirect to other sites, maintain an explicit allow-list of trusted destinations, and reject everything else, rather than trying to block known bad destinations, which is a losing game, because attackers can always find a destination you did not think to block. Also beware of tricks such as backslashes, encoded characters, or whitespace, which can disguise an absolute address as a relative one, so validation should be done after decoding, and should be strict: if the target does not clearly match the allowed pattern, reject it and redirect to a safe default, such as the homepage.

A second layer is to avoid passing redirect targets in URLs where possible, for example by storing the intended destination in the session, server-side, rather than in a parameter an attacker can craft and share. Where a parameter is necessary, sign it, or validate it as described, and never redirect blindly. Testing is straightforward: in your own test environment, try redirect targets that are absolute addresses, protocol-relative addresses, and encoded variants, and assert that each is rejected or replaced with a safe default, while legitimate relative paths still work. Those tests, run on every change, ensure that new redirect features do not reintroduce the flaw.

Open redirects are often dismissed as low severity, because they do not directly breach a system, but they are a real phishing enabler, and they are trivial to fix, with allow-listing and validation. A site that validates every redirect target is a site that cannot be used as a launchpad for deception, and that protects its users' trust, which is one of its most valuable assets.

Section 32: Keeping Dependencies Up to Date

Modern back-end systems are built on dependencies: libraries and packages written by others, which provide functionality you do not want to write yourself, from web frameworks to database drivers. Those dependencies are a strength, because they are tested by many users, but they are also a risk, because a vulnerability in a dependency is a vulnerability in your system, and attackers actively look for systems running known vulnerable versions. Keeping dependencies up to date, and knowing what you depend on, is therefore a core security practice, not just housekeeping.

The first step is knowing your dependencies. Maintain an explicit list, such as a requirements file, that records every direct dependency and its version, and use tooling to list indirect dependencies, the packages your dependencies themselves depend on, because those can also be vulnerable, even though you did not choose them directly. That inventory should be checked regularly, and it should be part of your codebase, so a new team member, or a future you, can see exactly what the system uses, and a security review can check it for known issues.

The second step is monitoring for vulnerabilities. Many package ecosystems provide advisories, and tools that scan your inventory against known vulnerability databases, reporting which packages have issues and which versions fix them. Running such a scan as part of your regular workflow, and as part of automated testing, means you learn about a vulnerability promptly, rather than discovering it after an attack. When a vulnerability is reported in a dependency you use, prioritise it by severity and by whether your system is actually exposed: a vulnerability in a feature you do not use is less urgent than one in a feature you rely on, but it should still be scheduled, because exposure can change as your system grows.

The third step is updating safely. Updates should be tested before deployment, because a new version can change behaviour and break your system, and that testing is part of your regular test suite, which is why a good suite matters for security as well as correctness. Pin versions in production, so deployments are reproducible, and update deliberately, one package at a time, with tests, rather than blindly updating everything at once, which makes failures hard to diagnose. For critical vulnerabilities, update urgently, even if that means an out-of-cycle release, because the window between disclosure and exploitation is often short, and attackers move quickly.

Finally, minimise dependencies where you can. Every dependency is code you trust, but did not write, and a smaller dependency set means fewer vulnerabilities to track, fewer updates to apply, and a smaller attack surface. Before adding a new package, ask whether the standard library already provides what you need, or whether a small amount of your own code would suffice, as this book's examples demonstrate with the standard library. Dependencies are a powerful tool, but they are also a responsibility, and managing them deliberately is part of building a secure system.

Section 33: Secrets Rotation

Secrets rotation is the practice of regularly replacing secrets, such as passwords, API keys, database credentials, and tokens, with new ones, and invalidating the old ones, so that a secret that has leaked, without your knowledge, stops working after a limited time. It is a containment measure: you may never know that a secret leaked, because leaks are often silent, but if secrets are rotated, a leaked secret's useful life is bounded, and the damage it can cause is limited. Rotation does not replace protecting secrets in the first place, but it limits the harm when protection fails, which, over a long enough time, it will.

Rotation should be planned for every secret, from the start. That means designing systems so secrets can be changed without downtime, and without code changes, for example by reading secrets from environment variables or a configuration store, so a new secret can be deployed by changing configuration and restarting, rather than by editing code. It also means supporting more than one valid secret during a transition, where possible, so old and new secrets overlap briefly, allowing clients to switch over without a hard cutover that breaks service. That overlap, called a grace period, is especially important for API keys used by external clients, who need time to update.

The frequency of rotation depends on the secret's sensitivity and exposure. Highly sensitive secrets, such as database credentials for a production system, or keys with broad permissions, should be rotated more often, perhaps every few months, while less sensitive secrets can rotate less often. More important than a fixed schedule is rotation on events: rotate immediately after a suspected leak, after a team member with access leaves, after a security incident, or after any change in who should have access. Event-driven rotation is often more valuable than scheduled rotation, because it responds to actual risk, rather than to the calendar.

Rotation also requires care about old copies. A rotated secret must be invalidated everywhere, not just in one place: in the application, in backups, in logs, and in any place it may have been copied, because an old copy that still works is not really rotated. That is why secrets should never be logged, and why access to secrets should be limited, as covered earlier, because each copy is another place to clean up. Testing rotation is also important: practice rotating a secret in a test environment, confirm the system continues working with the new secret, and confirm the old secret is rejected, so that when you must rotate urgently, you are not discovering the process for the first time.

Secrets rotation, combined with strong initial protection, limited access, and prompt revocation on suspicion, turns secrets from permanent keys, whose leak is permanent, into temporary credentials, whose leak is bounded. That is a significant improvement in security posture, and it is achievable with planning, not with complex tooling.

Section 34: Security Logging and Alerting

Security logging is the practice of recording events that matter for security, in a way that allows you to detect, investigate, and respond to attacks, and it is different from ordinary application logging, which is about debugging. Ordinary logs record what the system did; security logs record who did what, from where, and whether it succeeded, for events that could indicate an attack or a breach. Without security logs, an attack can succeed and you will never know, or you will discover it too late, without evidence of what happened, which makes response and recovery much harder.

The events worth logging for security include authentication successes and failures, authorisation failures, password changes and resets, account creation and deletion, privilege changes, access to sensitive data, configuration changes, and unusual patterns, such as many requests from one source, or access from an unusual location. Each log entry should include the time, in UTC, the user or account involved, the source, the action, and the outcome, but never sensitive data, such as passwords, tokens, or full personal details, because logs themselves can leak, and they are often stored less securely than the database. That balance, enough detail to investigate, without sensitive data, is the key skill in security logging.

Logging alone is not enough; logs must be monitored, and monitoring means alerting. An alert is a notification triggered by a pattern in logs that suggests an attack, such as many failed logins in a short time, many authorisation failures, or a sudden surge in sensitive data access. Alerts should be tuned to be meaningful: too many alerts, for harmless events, leads to alert fatigue, where real alerts are ignored, as covered in monitoring, while too few alerts means attacks go unnoticed. Start with a small set of high-value alerts, for the most serious patterns, and expand as you learn what normal looks like for your system.

Security logs should also be protected and retained. They should be stored separately from the application, ideally in a central log system, so that an attacker who compromises the application cannot easily delete or alter the logs that would reveal their activity. They should be retained long enough to investigate incidents, which may be discovered weeks after they occur, but not forever, because old logs also contain information, and retention should follow a policy, as covered in minimisation. Access to security logs should be limited to those who need it, because they contain sensitive operational information.

Finally, security logging should be tested and practised. Simulate an attack in a test environment, such as repeated failed logins, and confirm that the expected log entries appear, and that the expected alert fires, so you know detection works before a real attack. An incident response plan, covered later, depends on logs, and logs that have never been tested are a hope, not a capability. Security logging and alerting turn your system from one that is attacked silently, into one that notices, records, and responds, which is a fundamental shift in security posture.

Section 35: Input Size Limits and Denial-of-Service Protection

A denial-of-service attack aims to make your system unavailable to legitimate users, by exhausting its resources, such as CPU, memory, disk, or network, with excessive or expensive requests. Not all denial-of-service is malicious: a bug, a misconfigured client, or a sudden surge of legitimate traffic can also overwhelm a system, and the defences are largely the same. The core idea is to bound what any single request, or any single client, can consume, so that no request and no client can exhaust the system alone, and legitimate traffic can continue even under load.

The simplest and most effective bound is input size limits. Every input your system accepts, a request body, an uploaded file, a form field, a JSON payload, should have a maximum size, enforced before the input is fully processed, so a huge payload cannot consume memory or disk. For example, a JSON endpoint expecting a small task object should reject a body larger than a few kilobytes, rather than parsing a multi-megabyte payload, which could exhaust memory or CPU. Size limits should be chosen based on legitimate needs, with a comfortable margin, but not so large that they are meaningless, and they should be documented, so clients know what to expect.

A second bound is on work per request. Some operations are inherently expensive, such as password hashing, which is deliberately slow, or complex searches, or generating large reports, and an attacker can exploit that by making many expensive requests, each cheap for them, but costly for you. Rate limiting, covered earlier, addresses the many-requests case, while timeouts address the single expensive request: set timeouts for request handling, for database queries, and for calls to outside services, so a slow or hanging operation does not hold resources forever. Timeouts turn a potential hang into a controlled failure, which can be retried or reported, rather than a resource leak.

A third bound is on concurrency and total load. Limit how many requests your system handles at once, queue or reject excess, rather than accepting unlimited work and collapsing under it, and protect shared resources, such as database connections, with pools that have maximum sizes, so one surge does not exhaust the pool for everyone. Those limits should be tested under load, in a test environment, by simulating many concurrent requests, and observing how the system behaves: does it degrade gracefully, with clear errors for excess traffic, or does it crash, or slow to a crawl for everyone? Graceful degradation, where excess traffic is rejected cleanly while normal traffic continues, is the goal.

Finally, denial-of-service protection is layered, like other security: size limits, rate limits, timeouts, concurrency limits, and monitoring for unusual load, together, make your system resilient. No single measure stops a large, distributed attack, which may require help from your hosting provider or a dedicated protection service, but for the common cases, a single abusive client, a buggy client, or a modest surge, these bounds are sufficient, and they are simple to implement. A system that bounds input size, work, and concurrency is a system that stays available, which is, after all, one of the three security goals.

Section 36: Safe Deserialisation

Serialisation is the process of turning data in memory, such as a Python object, into a format that can be stored or transmitted, such as JSON text, and deserialisation is the reverse: turning that format back into data. Deserialisation is risky when the input comes from an untrusted source, because some formats, when deserialised, can do more than restore data: they can execute code, create arbitrary objects, or trigger actions, if the input is crafted maliciously. The rule is simple and absolute: never deserialise untrusted data with a format that can execute code, and prefer safe formats, such as JSON, which can only represent plain data, not code or objects.

Python's pickle module is the classic example of an unsafe format. Pickle can serialise almost any Python object, which makes it convenient, but deserialising pickle data runs code embedded in that data, by design, because pickle restores objects by calling their constructors and methods. That means unpickling data from an untrusted source, such as a user upload, a cookie, or a network request, is equivalent to running that source's code on your server, with your server's privileges. It should never be done, for untrusted data, under any circumstances, no matter how convenient it seems, and no matter how much you trust the immediate source, because that source could itself be compromised, or the data could be tampered with in transit.

The safe alternative is JSON, which Python's json module handles, and which can only represent strings, numbers, booleans, lists, and dictionaries, none of which execute code when parsed. JSON is sufficient for almost all data exchange needs, including API requests, stored settings, and job payloads, and it has the additional benefits of being human-readable, language-independent, and widely supported. When you need to store Python-specific data, convert it to plain JSON-compatible structures first, rather than reaching for pickle, and when you receive JSON, validate it as covered earlier, because safe parsing does not mean safe content: a JSON payload can still contain invalid values, oversized data, or unexpected fields, which must be checked.

Other formats also deserve caution. YAML, XML, and similar formats can have features, such as object construction or external entity references, that are unsafe when parsing untrusted input, unless those features are explicitly disabled, and the safe parser is used. The general principle is to use the safest parser available, disable dangerous features, and treat the parsed result as untrusted data, to be validated, not as trusted objects, to be used directly. If a library offers both a safe loader and a general loader, always choose the safe one, and be suspicious of any code that uses the general loader on outside input.

Testing for deserialisation safety is about review and replacement: search your codebase for pickle loads, and for other unsafe deserialisation, and confirm each use is only for trusted, local data, such as your own cache files, never for user input, and replace unsafe uses with JSON where possible. A codebase with no unsafe deserialisation of untrusted data is a codebase without this entire class of vulnerability, and that is an achievable goal, because JSON covers nearly every real need.

Section 37: Timing Attacks and Constant-Time Comparison

A timing attack is a subtle attack that extracts secret information by measuring how long an operation takes, rather than by breaking its logic directly. The classic example is comparing a secret, such as a password hash, a token, or an API key, with a user-supplied value, character by character, stopping at the first mismatch. If the first character is wrong, the comparison fails quickly; if the first ten characters are right, and the eleventh is wrong, it takes slightly longer, because more characters were compared before failing. An attacker who can measure those tiny time differences, over many attempts, can deduce the secret one character at a time, by trying each possible character and observing which one takes longest, indicating a match. It is a slow attack, but for secrets that can be tried many times, it is real, and it is preventable with a simple technique.

The defence is constant-time comparison, where the comparison always takes the same amount of time, regardless of where the values differ, or whether they differ at all. Python's standard library provides hmac.compare_digest, which compares two values in constant time, for strings and bytes, and it should be used for every comparison involving a secret: password hashes, tokens, API keys, CSRF tokens, and any other value where an attacker could benefit from learning it character by character. The function is easy to use, and replacing a plain equality check with compare_digest, for secrets, is a one-line change with significant security value.

It is important to understand where constant-time comparison matters, and where it does not. It matters for secrets, where the attacker does not know the value, and can make many attempts, measuring timing. It does not matter for public data, such as usernames, where the value is not secret, and timing reveals nothing useful, and using it everywhere, while harmless, is unnecessary. It also does not protect against other information leaks, such as error messages that reveal whether a user exists, which must be handled separately, as covered in safe errors. Constant-time comparison is one specific defence, for one specific leak, and it should be applied where that leak matters.

A related timing concern is that operations should not leak information through other timing differences, such as taking measurably longer for valid users than for invalid ones, due to extra work, such as password hashing, that is only done for valid users. A safe login flow, as covered earlier, does the same work, including hashing, in both cases, so timing does not reveal whether a user exists. That principle, equal work for equal cases, generalises: where timing could reveal a secret, make timing independent of the secret, by doing the same work regardless.

Testing timing defences is difficult, because timing differences are tiny and noisy, but you can test the simpler property: that your code uses compare_digest for secret comparisons, by reviewing code and searching for plain equality checks on secrets, and replacing them. That review, done once, and checked in code review for new code, is sufficient for most systems, because the attack requires many precise measurements, and constant-time comparison removes the signal it depends on. Timing attacks are advanced, but their defence is simple, and using it for secrets is a mark of careful engineering.

Section 38: Password Reset Flows Done Safely

Password reset is a sensitive flow, because it allows someone who has forgotten a password to regain access to an account, and if it is done poorly, it allows an attacker to take over an account, without knowing the password. A safe reset flow must verify that the person requesting the reset is the account's owner, or at least has access to something only the owner should have, usually their email inbox, and it must do so without creating new vulnerabilities, such as guessable reset links, or tokens that never expire. Reset flows deserve the same care as login flows, because they are an alternative path into an account, and attackers will use the weakest path available.

The standard safe flow works as follows. A user requests a reset by entering their email address, or username, and the system, if an account exists for that identifier, generates a random, unpredictable token, stores it with an expiry time, such as one hour, and sends a reset link containing the token, to the account's registered email address. The user clicks the link, the system verifies the token, checks it has not expired and has not already been used, and then allows the user to set a new password, after which the token is invalidated, and the password is stored safely, as covered earlier. Each step matters, and skipping one creates a vulnerability.

Several details are critical. The token must be random, generated with the secrets module, long enough to be unguessable, and stored hashed, like a password, where possible, so a database leak does not expose usable tokens. The token must expire quickly, so a leaked or intercepted link stops working soon, and it must be single-use, invalidated after it is used, or after a new reset is requested, so old links cannot be reused. The reset request response must be the same whether or not an account exists, to avoid revealing which email addresses have accounts, as covered in safe errors. And after a successful reset, the system should invalidate existing sessions, so a stolen session cannot continue to be used, and should notify the user by email, so they know their password was changed, and can act if it was not them.

Rate limiting, covered earlier, is essential for reset endpoints, to prevent attackers from flooding users with reset emails, or from guessing tokens, and the reset form itself should be protected against abuse, such as by requiring a CAPTCHA after repeated requests. Reset links should also be sent only to the registered email address, never displayed on screen, or sent to a new address supplied in the request, because that would allow an attacker to reset a victim's password to an address they control.

Testing a reset flow should cover each property: tokens are random and expire, used tokens are rejected, expired tokens are rejected, the response does not reveal account existence, sessions are invalidated after reset, and the user is notified. Those tests, in your own test environment, with fake email, ensure the flow is safe before it is offered to real users, because a reset flaw is an account takeover flaw, and account takeover is one of the most serious outcomes a back-end can suffer.

Section 39: Account Lockout Versus Enumeration

Account lockout and account enumeration are two security concerns that pull in opposite directions, and balancing them is a classic back-end design problem. Lockout means temporarily disabling an account after too many failed login attempts, to stop brute-force guessing, as covered earlier. Enumeration means an attacker discovering which accounts exist, by observing differences in system behaviour, such as different error messages, or different response times, for existing versus non-existing accounts, as covered in safe errors. The tension is that lockout, if implemented naively, can itself enable enumeration, or can be abused to lock legitimate users out of their accounts, a form of denial of service.

Consider a naive lockout: after five failed attempts, an account is locked, and further login attempts return "account locked". An attacker can probe usernames: for a non-existent user, login always returns "invalid credentials", but for an existing user, after five guesses, it returns "account locked", revealing that the user exists. The lockout mechanism, designed to protect accounts, has leaked their existence. Similarly, an attacker can deliberately lock out a victim's account, by making five failed attempts, preventing the legitimate user from logging in, which is a denial of service against that user, even though the attacker never guessed the password.

The solution is to design lockout and error messages together, so that lockout does not leak information, and cannot easily be abused. One approach is to return the same generic error, "invalid credentials", in all failure cases, whether the account is locked, the password is wrong, or the account does not exist, so an attacker learns nothing from the response. Another approach is to use soft lockouts, such as progressive delays or CAPTCHAs, rather than hard lockouts, so legitimate users are slowed but not blocked, while attackers are still impeded. A third approach is to lock out based on the source, such as the network address, as well as the account, so an attacker from one address cannot lock out a user for everyone else, and to allow legitimate users to unlock via email, or via a second factor, without waiting for a long lockout period.

The right balance depends on your system and its users. For a system with high-value accounts, stricter lockout, with a secure unlock process, may be justified. For a system where availability matters most, softer measures, such as delays and CAPTCHAs, may be better. What matters is that the design is deliberate, considering both brute-force protection and enumeration, and denial of service, rather than implementing lockout in isolation, and discovering its side effects later. Document the chosen balance, and test it: probe with existing and non-existing accounts, and confirm that responses are indistinguishable, and that a legitimate user can still regain access after a lockout, through the intended process.

This balancing act illustrates a broader security lesson: defences interact, and a defence that helps in one dimension can hurt in another, so security design must consider the whole system, not just individual controls in isolation. Lockout, enumeration, and availability, considered together, lead to a better design than any one considered alone.

Section 40: Two-Factor Authentication Basics

Two-factor authentication, usually shortened to 2FA, adds a second layer of proof, beyond a password, before granting access to an account. The idea is based on factors: something you know, such as a password, something you have, such as a phone or a hardware key, and something you are, such as a fingerprint. A password alone is one factor, something you know, and it can be guessed, phished, or leaked, as covered earlier. Adding a second factor, from a different category, such as a code from an app on your phone, something you have, means an attacker who steals your password still cannot access your account, unless they also steal your second factor, which is significantly harder.

The most common second factor for web systems is a time-based one-time code, generated by an authenticator app on the user's phone, which changes every thirty seconds, and which the user enters after their password. The server and the app share a secret, set up once, when 2FA is enabled, by scanning a code or entering a key, and both generate the same codes, independently, based on the current time, so the server can verify the code without needing to contact the phone. That design is secure, because the code is short-lived, and it is generated locally, not sent over a network where it could be intercepted, though the initial setup secret must be protected, and backup codes, provided for recovery if the phone is lost, must be stored safely, like passwords.

Implementing 2FA safely requires care in several places. The second factor check must happen after the password check, and the session should not be considered fully authenticated until both factors pass, so a partially authenticated session cannot access sensitive features. The setup flow must verify that the user can generate correct codes, before enabling 2FA, otherwise a user could lock themselves out by enabling it incorrectly. Recovery must be designed: backup codes, or an alternative verification method, should be provided, because users lose phones, and a recovery process that is too weak undermines 2FA, while one that is too strict locks users out permanently. And 2FA should be offered, and encouraged, for all users, and required, where feasible, for privileged accounts, such as administrators, whose compromise would be most serious.

SMS codes, sent by text message, are a weaker second factor, because messages can be intercepted, or redirected through SIM swapping, where an attacker convinces a carrier to transfer a victim's number to their own SIM, but they are still better than no second factor, and they may be appropriate where authenticator apps are not feasible, such as for users without smartphones. The choice of second factor should be based on your users and their risk, with authenticator apps or hardware keys preferred where possible, and SMS as a fallback, not as the only option.

Two-factor authentication is one of the most effective security improvements available, because it neutralises the most common attack, password theft, and it is worth implementing well, with careful setup, recovery, and session handling. A system that offers 2FA, and encourages its use, is a system that protects its users even when their passwords are compromised, which, given password reuse and phishing, is a matter of when, not if.

Section 41: Safe Session Storage on the Server

Sessions were introduced earlier, covering generation, expiry, and revocation, but where session data is stored, on the server, also matters for security, because session storage is a target: it contains the data that proves who a user is, and if it is compromised, sessions can be stolen, forged, or misused. Safe session storage means choosing a storage method that protects session data, limits its exposure, and allows it to be invalidated promptly, when needed, such as on logout or after a password change.

The simplest session storage is in memory, on the application server, which is fast and simple, and suitable for a small system running on one server, but it has limitations: sessions are lost when the server restarts, which logs users out unexpectedly, and it does not work when the system scales to multiple servers, because a session created on one server is not visible to another, unless sessions are shared. Those limitations are operational, but they also have security implications: a restart that clears sessions is safe, in that stolen sessions stop working, but it is disruptive, and a multi-server system that falls back to accepting sessions it cannot verify, to avoid logouts, would be insecure.

A more scalable option is a database, such as SQLite for a small system, or a dedicated session store, for a larger one, where each session is a row, with a random id, a user id, an expiry time, and any minimal data needed, such as permissions or preferences, but never sensitive data, such as passwords or full personal details, as covered earlier. Database storage allows sessions to survive restarts, to be shared across servers, and to be invalidated by deleting the row, which is immediate and reliable, unlike trying to expire a token that is stored only on the client. It also allows auditing: you can list a user's active sessions, and revoke them, which is a valuable security feature, for users who suspect their account is compromised.

A third option is client-side sessions, where session data is stored in a cookie, signed or encrypted by the server, so the server does not need to store it, and can verify it by checking the signature or decrypting it. That approach scales well, but sessions cannot be revoked promptly, because the server has no record to delete, and a session remains valid until it expires, even after logout or password change, unless a blocklist is added, which reintroduces server state. Client-side sessions are therefore less suitable where prompt revocation matters, and they must be encrypted or signed, never stored in plain text.

Whichever storage you choose, the security principles are the same: session ids must be random and unguessable, session data must be minimal, expiry must be enforced server-side, revocation must work promptly, and access to session storage must be restricted, like any sensitive data store. Test session storage by checking that logout invalidates the session, that expired sessions are rejected, that sessions survive a restart if they should, and that sessions are not shared across servers incorrectly. Session storage is infrastructure, but it is security infrastructure, and getting it right protects every authenticated interaction your system offers.

Section 42: Protecting Admin Endpoints

Admin endpoints are the most powerful parts of a back-end: they allow managing users, changing settings, viewing sensitive data, and performing actions that ordinary users cannot, and they are therefore the most attractive target for attackers. Protecting them requires more than ordinary authorisation, because the impact of a breach is much higher, and because admin functionality is often less tested, less used, and less scrutinised than ordinary features, making it more likely to contain a flaw. Admin protection should be deliberate, layered, and regularly reviewed.

The first layer is strong authorisation, as covered earlier, but applied strictly: admin endpoints must check, on every request, that the authenticated user has an admin role, using server-side data, not client-supplied claims, and they must deny access by default, for any user without that role, including authenticated ordinary users. Admin roles should be few, assigned only to people who genuinely need them, following least privilege, and reviewed regularly, so former team members, or people whose role has changed, do not retain admin access. Admin accounts should also be protected with two-factor authentication, as covered earlier, because an admin account without 2FA is a single password away from full system control.

The second layer is separation and obscurity, used correctly. Admin functionality should be on separate endpoints, clearly distinguished from ordinary endpoints, so authorisation can be applied uniformly, and so it can be monitored separately. It should not rely on obscurity, such as an unlisted URL, as its only protection, because attackers discover URLs by probing, but obscurity as an additional layer, such as not linking admin pages from public pages, reduces casual discovery, and is harmless when combined with real authorisation. Admin endpoints should also be rate limited, and monitored, with alerts for unusual admin activity, such as access from a new location, or bulk actions, which could indicate compromise.

The third layer is audit logging. Every admin action, such as creating or deleting a user, changing a setting, or accessing sensitive data, should be logged, with who did it, when, from where, and what changed, in a log that is protected from modification, as covered in security logging. Audit logs allow you to detect misuse, investigate incidents, and hold administrators accountable, and they are essential for trust, because admin power without accountability is dangerous, whether the threat is an outside attacker, or an insider misusing their access. Admin logs should be reviewed regularly, not just after an incident, because misuse is often subtle, and early detection limits harm.

Finally, admin functionality should be tested with the same rigour as ordinary features, including authorisation tests for every admin endpoint, asserting that ordinary users are denied, and that unauthenticated requests are denied, and including tests for the audit logging itself. Admin endpoints are often added quickly, for operational needs, and forgotten, so a periodic review of all admin endpoints, their authorisation, their logging, and their necessity, is a valuable security practice. A system whose admin endpoints are strongly authorised, protected with 2FA, audited, and reviewed, is a system whose most powerful features are also its most protected.

Section 43: Safe Handling of Personal Data

Personal data is any information that identifies, or can be combined to identify, a person, such as names, email addresses, phone numbers, addresses, dates of birth, and location data, and handling it safely is both a legal obligation, in many regions, and a moral responsibility, because a leak can cause real harm, from spam and fraud, to identity theft and physical danger. Safe handling starts with the minimisation principle, covered earlier, collect only what you need, but it continues through every stage of the data's life: collection, storage, use, sharing, and deletion, each of which must be handled with care.

Collection should be transparent and consented. Users should know what data you collect, why, and how it will be used, in plain language, not buried in legal text, and they should consent, where consent is required, before collection, not after. Data should be collected through secure channels, over HTTPS, with validation, as covered earlier, and it should be stored securely, encrypted at rest for sensitive fields, with access restricted to those who need it, following least privilege, and with logs that record access to sensitive data, so misuse can be detected. Those storage and access controls are the same as for other sensitive data, but they matter more for personal data, because the harm from a leak is personal, not just technical.

Use and sharing must be limited to the purposes for which the data was collected, or for which the user consented, and sharing with third parties, such as analytics providers, email services, or partners, should be minimised, documented, and covered by agreements that require the third party to protect the data, and to use it only as agreed. Data should never be shared casually, or for purposes the user did not expect, because unexpected sharing is a breach of trust, even if it is not a technical breach, and it can have legal consequences. Where data must be shared, share the minimum necessary, for example an email address for sending a message, not a full profile, and consider anonymisation, where data is transformed so individuals cannot be identified, for uses such as analytics, where individual identities are not needed.

Deletion and user rights are the final stage. Users should be able to request access to their data, correction of errors, and deletion, where applicable, and your system should be able to fulfil those requests, which requires knowing where personal data lives, in databases, logs, backups, and third-party systems, and having a process to find and remove it. That process should be tested, because a deletion request that cannot be fulfilled, due to scattered data, is a failure of design, not just of operations. Retention policies, covered earlier, support deletion, by ensuring data does not live longer than necessary, in the first place.

This section is not legal advice, and the specific rules vary by region and by the type of data, so for a real product, you should check the laws that apply to your users, and seek appropriate advice. The engineering habits, however, are universal: collect transparently, store securely, use and share minimally, and delete reliably, and your system will respect its users' privacy, as well as protect their data.

Section 44: Security Testing: Review and Checklists

Security testing is the practice of systematically checking your system for vulnerabilities, before attackers do, and it combines automated tools, manual review, and checklists, each of which catches different kinds of flaws. Automated tools can scan code for known patterns, such as SQL concatenation, unsafe deserialisation, or missing escaping, and they can test a running system for common vulnerabilities, quickly and repeatedly, but they miss logic flaws, such as missing authorisation checks, which require understanding what the system should do, not just how it is written. Manual review, by a person reading code and thinking adversarially, catches logic flaws, but it is slow, and it misses things when reviewers are tired or rushed. Checklists combine the strengths of both, by ensuring that known checks are not forgotten, even when time is short.

A practical security checklist for a back-end, based on this chapter, includes: input validation on every endpoint, parameterised queries for all database access, output escaping for all user data in pages, authentication on every protected endpoint, authorisation on every request, CSRF tokens on state-changing forms, HTTPS everywhere, Secure and HttpOnly cookies, security headers, rate limits, safe error messages, secrets in environment variables, not in code, and logging for security events. That list is not exhaustive, but it covers the most common vulnerabilities, and running through it, for each new feature, before release, catches many flaws that would otherwise reach production. The checklist should be a living document, updated when new vulnerabilities are learned about, or when the system gains new features, such as file uploads, which add their own checks.

Code review is where the checklist is applied, and it should be a normal part of development, not a special security event. A reviewer, reading a change, should ask the adversarial questions from this chapter: what if input is hostile, what if the user is not who they claim, what if this endpoint is called directly, what if this data is leaked? Those questions, asked consistently, catch flaws early, when they are cheap to fix, rather than after release, when they are expensive and potentially harmful. Review should also cover tests: does the change include tests for its security properties, such as authorisation denials, validation rejections, and token checks, or does it rely on hope? A change without security tests is a change whose security is unverified.

Automated security testing should be part of your regular test suite and deployment pipeline, where feasible, including dependency scanning, covered earlier, and static analysis, which checks code for known unsafe patterns, without running it. Those tools produce false positives, and their output must be reviewed, not blindly followed, but they catch issues humans miss, especially in large codebases, and they run on every change. For high-value systems, periodic penetration testing, by specialists who attempt to breach the system, with permission, provides a deeper check, but it does not replace regular review and checklists, because it is infrequent.

Security testing is not about achieving perfection, which is impossible, but about reducing risk systematically, by catching common flaws reliably, and logic flaws thoughtfully, before release. A team that reviews with a checklist, tests security properties, and scans dependencies, is a team that ships more secure systems, consistently, not by luck, but by process.

Section 45: Incident Response Basics

An incident is a security event that has happened, or is happening, such as a suspected breach, a compromised account, or a successful attack, and incident response is the planned process for handling it, to limit harm, recover safely, and learn from it. Many teams have no incident plan, and when an incident occurs, they improvise, under stress, making mistakes, such as deleting evidence, or restoring from a compromised backup, that worsen the situation. A basic plan, written in advance, practised, and known to the team, turns a crisis into a process, and significantly improves outcomes, even for a small team or a solo developer.

A simple incident response process has four phases. The first is detection and containment: notice the incident, through logs and alerts, covered earlier, confirm it is real, and stop it from spreading, by revoking compromised credentials, blocking malicious sources, or taking affected systems offline, if necessary, while preserving evidence, such as logs, for later investigation. Containment is urgent, but it should not destroy evidence: do not delete logs, or wipe a compromised system, before capturing what happened, because that evidence is needed to understand the scope, and to prevent recurrence. The second phase is investigation: determine what happened, what was accessed, and what was affected, using logs, and other evidence, and assess the impact, including whether personal data was involved, which may trigger notification obligations.

The third phase is recovery: remove the attacker's access, fix the vulnerability that allowed the incident, restore affected systems from clean backups, or rebuild them, and verify, through testing, that the system is safe, before returning it to normal use. Recovery should not rush: returning a system to service before the vulnerability is fixed, or before the attacker's access is fully removed, invites a repeat incident, which is worse than a longer outage. The fourth phase is learning: write a postmortem, as covered in monitoring, describing what happened, why, what was done, and what will change, to prevent recurrence, and share it with those who need to know, without blame, because a blameful culture discourages reporting, and unreported incidents are more dangerous than reported ones.

Preparation makes response possible. Before an incident, ensure logs are kept and protected, backups are tested, credentials can be revoked quickly, and contact information, for team members and for external help, such as hosting providers, is available, even if systems are down. Practise the plan, with a tabletop exercise, where the team walks through a hypothetical incident, discussing what they would do, which reveals gaps, such as missing access, or unclear responsibilities, before a real incident exposes them. For a solo developer, preparation is simpler, but still valuable: know how to revoke keys, restore backups, and contact your provider, and write down the steps, so stress does not erase them.

Incident response is not pessimism. It is realism: incidents happen, even to careful teams, and a team that has planned for them recovers faster, with less harm, and learns more, than a team that has not. A basic plan, practised, is one of the highest-value security investments a small team can make.

Section 46: Security for Background Jobs and Queues

Background jobs, covered in the email and notifications chapter, run work outside the main request, such as sending emails, generating reports, or processing uploads, and they have their own security considerations, because they operate without a user present, with system privileges, and on data that may be sensitive, often for a long time after the request that created them. A job that is safe when triggered by a request can become unsafe when it runs later, if its inputs, permissions, or data have changed, or if it is not protected against misuse, such as being triggered repeatedly, or with forged data.

The first consideration is job inputs. A job's payload, stored in a queue, is data, and it must be validated when the job runs, not just when it is created, because the queue could be tampered with, or the data could have become invalid since creation, such as a user who has since been deleted, or a file that has since been removed. A job that sends an email to a stored address should check, at run time, that the user still exists, and still wants that email, rather than blindly sending to an old address. A job that processes a file should check that the file still exists, and that its type and size are still acceptable, rather than assuming the original checks still hold. Validating at run time is defence in depth, applied to jobs.

The second consideration is job permissions. A job often runs with system privileges, because it has no user session, and it may need to access data for many users, such as sending a daily digest to all subscribers. That broad access must be limited: a job should access only the data it needs, for its specific purpose, and it should not use a master credential with unlimited power, where a scoped credential, or a per-user check, would suffice. For example, a report job should read only the data needed for that report, not the entire database, and a cleanup job should delete only data that matches its criteria, with safeguards, such as a limit on how many rows it can delete in one run, to prevent a bug from deleting everything.

The third consideration is job triggering and idempotency. Jobs should only be created through authorised paths, not by unauthenticated requests that can flood the queue, which is a denial-of-service risk, as covered earlier, and rate limits should apply to job creation, as they do to other endpoints. Jobs should also be idempotent, as covered earlier, so that a job run twice, due to a retry, does not cause harm, such as sending an email twice, or charging twice, because retries are normal in job systems, and a job that is unsafe to retry is a job that will eventually cause harm.

Finally, jobs must be logged and monitored, like other security-relevant activity, with entries for job creation, success, failure, and retries, so unusual patterns, such as a surge in jobs, or repeated failures, can be detected, and so a job's actions can be audited, if something goes wrong. A job system that is validated, scoped, idempotent, rate limited, and logged, is a job system that can be trusted with sensitive work, even when no user is watching it run.

Section 47: Safe Webhooks

A webhook is a way for one system to notify another about an event, by sending an HTTP request to a URL the receiver has registered, when something happens, such as a payment completing, or a task being created. Webhooks are powerful, because they allow systems to react automatically, without polling, but they are also risky, because they involve your server accepting requests from outside systems, and acting on them, often with real consequences, such as marking an order as paid, or provisioning a service. Safe webhook handling means verifying that a request genuinely came from the claimed sender, and that it is safe to act on, before doing anything.

The most important protection is signature verification. A trustworthy webhook sender signs each request, using a shared secret, known only to the sender and to you, and includes that signature in a header. Your server, on receiving the request, recomputes the signature, using the same secret and the request body, and compares it, using constant-time comparison, as covered earlier, with the signature provided. If they match, the request is genuine, because only someone with the secret could have produced that signature. If they do not match, the request is rejected, without acting on it, because it could be forged. That verification must happen before any action, and before trusting any data in the request, because unverified webhook data is untrusted input, like any other.

Several details matter for signature verification. The secret must be stored safely, in an environment variable, not in code, as covered earlier, and it must be rotatable, so it can be changed if leaked, without breaking the integration permanently. The signature must cover the exact request body, as received, without modification, such as re-encoding, which would change the signature, so verification should use the raw body bytes, not a parsed and re-serialised version. And the comparison must be constant-time, to avoid leaking the signature through timing, as covered earlier. Those details are easy to get wrong, and getting them wrong can silently disable verification, so test it: send requests with correct, incorrect, and missing signatures, in your own test environment, and assert that only correct ones are accepted.

Beyond verification, webhooks need the same protections as other endpoints: rate limiting, to prevent flooding, idempotency, to handle duplicate deliveries, because senders often retry, and validation, of the event data, before acting on it, because even a genuine sender can send unexpected data, due to a bug, or a change in their format. Webhook endpoints should also return quickly, acknowledging receipt, and process the event asynchronously, in a background job, rather than doing slow work during the webhook request, which can cause timeouts and duplicate retries. And webhook URLs themselves should be unpredictable, or protected, where possible, so they cannot be easily discovered and abused, though obscurity is not a substitute for signature verification.

Webhooks, handled with signature verification, rate limiting, idempotency, validation, and asynchronous processing, are a safe and powerful integration mechanism. Handled without verification, they are an open door, allowing anyone who discovers the URL to trigger actions in your system, which is one of the most dangerous misconfigurations a back-end can have.

Section 48: Common Security Mistakes

Even developers who understand security make mistakes, often the same ones, repeatedly, because they are easy to make, and hard to notice, until they cause harm. Knowing the most common mistakes, and checking for them, is a practical way to improve security, because it turns vague caution into specific things to look for, in your own code, and in code review. This section collects the mistakes that appear most often, in back-end systems, and that this chapter has covered, so you can recognise them, and avoid them, deliberately.

The first group of mistakes involves trusting input or the client: building SQL by concatenating input, displaying user text as raw markup, trusting prices or roles sent from the client, and skipping validation or authorisation on a new endpoint, because it was assumed to be internal, or because it was added quickly. Those mistakes share a root cause, forgetting that the server is the only trustworthy enforcement point, and that every input, and every request, must be checked, regardless of where it appears to come from. The fix is habit: validate, parameterise, escape, and authorise, on every endpoint, without exception, and test those properties, so a forgotten check is caught by a test, not by an attacker.

The second group involves secrets and credentials: hard-coding secrets in code, committing them to version control, logging them, storing passwords in plain text or with weak hashing, and using predictable tokens or session ids. Those mistakes share a root cause, treating secrets as ordinary data, rather than as sensitive assets that need special handling, from generation, through storage, to rotation and revocation. The fix is also habit: generate secrets randomly, store them in environment variables, hash passwords properly, never log secrets, and rotate on suspicion, with those habits enforced by review and by tooling, such as scanners that detect secrets in code.

The third group involves configuration and defaults: serving a site over plain HTTP, leaving detailed errors on in production, using default credentials, or overly permissive permissions, and forgetting security headers, rate limits, or logging. Those mistakes share a root cause, focusing on making a feature work, and forgetting to make it safe, in its deployed configuration, which is different from development. The fix is to treat production configuration as part of the feature, with a checklist, and with deployment checks, that confirm HTTPS, generic errors, headers, limits, and logging, are all in place, before release.

Recognising these mistakes, in your own work, is not a sign of failure. It is a sign of experience, because every developer makes them, and the difference between a secure developer and an insecure one is not that the secure developer never makes mistakes, but that they check for them, systematically, and fix them, before release. Use this section as a review checklist, for your own code, and for code you review, and you will catch many vulnerabilities, before they matter.

Section 49: Building a Security Checklist for Launch

A launch checklist is a list of security checks, run before a system, or a feature, goes live, to ensure that the protections covered in this chapter are actually in place, not just intended. It is valuable because launch is a stressful time, when details are easy to forget, and because a checklist turns memory into process, so safety does not depend on remembering everything, under pressure. A good checklist is specific, actionable, and owned, meaning someone is responsible for running it, and for confirming each item, before launch is approved.

A practical launch checklist, based on this chapter, starts with authentication and authorisation: are all endpoints authenticated, where required, and authorised, on every request, with tests for denials? It continues with input handling: is all input validated, are all queries parameterised, is all user data escaped in pages, and are CSRF tokens present on state-changing forms? It covers transport and session safety: is HTTPS enforced everywhere, with HTTP redirected, are cookies Secure, HttpOnly, and SameSite, and are sessions stored safely, with expiry and revocation? It covers secrets and data: are secrets in environment variables, not in code, are passwords hashed properly, is sensitive data encrypted at rest, and is personal data minimised, with a retention policy? It covers operations: are rate limits in place, are security headers set, are errors generic in production, are logs and alerts configured, and are dependencies up to date, with no known critical vulnerabilities?

Each item on the checklist should have a clear pass criterion, not just a vague intention. For example, "HTTPS enforced" should mean: requesting the site over HTTP redirects to HTTPS, and cookies carry the Secure flag, verified by a test, not just "we think we enabled HTTPS". "Authorisation checked" should mean: tests exist, for each endpoint, asserting that unauthorised users are denied, and those tests pass, not just "we added checks". That specificity turns a checklist from a ritual, into a verification, and it allows a reviewer to confirm each item, independently, rather than trusting that it was done.

The checklist should also be run, not just for initial launch, but for significant changes, such as new features, new integrations, or new data collection, because those changes can introduce new risks, even in a system that was previously safe. A new file upload feature, for example, adds the file upload checks, a new webhook adds signature verification checks, and a new admin feature adds admin protection checks. Treating the checklist as a living document, updated with each new feature type, keeps it relevant, as the system grows, rather than letting it become outdated and ignored.

Finally, a checklist should be honest about its limits. It catches known, common issues, reliably, but it does not catch novel logic flaws, or complex attack chains, which require review, testing, and, for high-value systems, specialist assessment. A checklist is a floor, not a ceiling: it ensures the basics are done, so that review and testing can focus on the harder, system-specific risks, rather than on rediscovering missing basics. A team that launches with a checklist, and follows it consistently, ships more secure systems, with fewer surprises, and with a clear record of what was checked, which is valuable for trust, and for learning.

Section 50: Security Is Never Finished

Security is never finished, because the systems it protects are never finished, and the threats against them never stop changing. New features add new attack surface, new dependencies add new vulnerabilities, new attackers develop new techniques, and new users bring new patterns of use, and misuse, that were not anticipated. A system that was secure at launch can become insecure, over time, through neglect, through changes made without security review, or through the discovery of a vulnerability in a dependency, or a platform, that was previously trusted. Accepting that security is ongoing, rather than a one-time task, is the most important mindset in this chapter, because it determines whether security is maintained, or whether it decays.

Ongoing security has several practices, all of which build on this chapter. The first is regular review: revisit your system periodically, and after significant changes, checking authorisation, input handling, secrets, dependencies, and configuration, against the checklist from the previous section, and updating the checklist as new risks are learned about. The second is monitoring and alerting, covered earlier, which provides continuous visibility into attacks and anomalies, so you can respond promptly, rather than discovering a breach months later. The third is updating: keep dependencies, platforms, and libraries up to date, with a process for urgent updates, when critical vulnerabilities are disclosed, because the window between disclosure and exploitation is short, and delay increases risk.

The fourth practice is learning. Security knowledge grows, through reading advisories, through postmortems, both your own, and those shared by others, and through studying new vulnerabilities, and understanding their root causes, in plain terms, so you can recognise similar patterns in your own systems. Learning should be shared within a team, through review, through discussion of incidents, and through updating checklists and tests, so that one person's lesson becomes the team's habit. A team that learns together, becomes more secure together, over time, while a team that does not learn, repeats the same mistakes, in new features.

The fifth practice is humility and honesty. No system is perfectly secure, and claiming otherwise is dangerous, because it discourages vigilance, and it hides risks that should be addressed. Honest security means acknowledging limitations, prioritising the most serious risks, with the resources available, and being transparent, with users, about what you protect, and how, within reason, without revealing details that would help attackers. It also means responding honestly, when incidents occur, notifying affected users, where required, and fixing vulnerabilities promptly, rather than hiding them, because trust, once lost through dishonesty, is harder to recover than trust lost through an incident handled well.

This chapter has covered the basics: thinking like a defender, validating input, protecting secrets, storing passwords safely, managing sessions and tokens, authorising every request, preventing injection and scripting, using HTTPS, handling files, errors, and personal data safely, testing, and responding to incidents. Those basics, applied consistently, and maintained over time, are sufficient to build back-end systems that are trustworthy, for their users, and resilient, against common attacks. Security is never finished, but it is also never out of reach: it is a habit, built one check, one test, and one review, at a time, and this chapter is your starting point for building that habit, and keeping it, for as long as you build systems.
