Chapter 29: Testing Back-End Code in Plain Words

Section 1: Why Test Back-End Code?

Testing means checking, systematically, that your code does what you intend it to do. It sounds obvious, but it is easy to skip, especially when a feature seems to work the first time you try it. The problem is that "seems to work" is a weak guarantee. Code that works for one input, on your machine, today, may fail for another input, on another machine, tomorrow, after a change you thought was unrelated. Testing replaces hope with evidence: instead of believing your code works, you can show that it works, for specific cases, and you can re-show it every time the code changes. That evidence is what makes software reliable enough for real users to depend on.

The most immediate benefit of testing is catching bugs early, when they are cheap to fix. A bug found while you are still writing a feature takes minutes to fix, because the code is fresh in your mind and the context is at hand. The same bug found by a user, weeks later, takes much longer: someone must report it, someone must reproduce it, someone must understand code they have not touched in weeks, and the fix must be deployed urgently, under pressure. The difference in cost is enormous, and it grows with every stage the bug survives. Testing moves bug discovery to the earliest, cheapest stage, which is while you are still at your keyboard.

A second benefit is confidence to change code. Back-end systems grow and change constantly: features are added, bugs are fixed, dependencies are updated. Without tests, every change is a risk, because you cannot tell whether you broke something that used to work. Developers in that situation become afraid to change code, and the code becomes rigid and stale, accumulating workarounds instead of improvements. With tests, a change can be checked quickly: run the tests, and if they pass, you have good reason to believe nothing broke. That confidence is what lets codebases stay healthy over years, rather than freezing in fear.

A third benefit is documentation. A well-written test shows, in code, what a function is supposed to do, with concrete examples: given this input, it should produce this output. That is often clearer than a written description, because it is exact and it is verified by running it. A new developer joining a project can read its tests to understand its intended behaviour, faster than reading its documentation alone, because tests cannot drift from reality the way prose can: if a test's expectation is wrong, the test fails, and someone notices. Tests are documentation that complains when it becomes outdated, which is a valuable property.

Finally, testing improves design. Code that is hard to test is usually hard to understand, because it mixes concerns, depends on hidden state, or does too many things at once. Writing a test forces you to think about a function's inputs, outputs, and dependencies, and that thinking often reveals a cleaner design: a function split in two, a dependency passed in rather than hidden. Testing is therefore not just a check on code. It is a design tool.

# A test is evidence: a specific input, an expected output, a check.
def add(a, b):
    return a + b

result = add(2, 3)
assert result == 5, f"Expected 5, got {result}"
print("Test passed: add(2, 3) == 5")

Section 2: What Is a Test?

A test is a small program, or a small part of a program, that runs a piece of your code with known inputs and checks that the result matches what you expect. That definition covers almost every kind of test, from the simplest check of a function to a full simulation of a user signing up and using your application. The structure is always the same, in three steps, often called arrange, act, and assert. Arrange means setting up what you need: data, objects, or a test database. Act means doing the thing you are testing: calling a function, making a request, or running a job. Assert means checking the result: is the output what you expected, did the database change correctly, was the right error raised? Those three steps, in that order, are the skeleton of every test you will write.

It helps to distinguish tests from the code they test. Your application code is written to serve users. Your test code is written to check application code. Test code is not shipped to users, it does not need to be fast in the same way, and it is allowed, even encouraged, to be repetitive and explicit, because clarity matters more than cleverness in tests. A test that is hard to read is a test that will be misunderstood, and a misunderstood test gives false confidence, which is worse than no test. Write tests plainly, with clear names that say what is being tested and what should happen, so that a failing test tells you, from its name alone, roughly what broke.

Tests also have a pass or fail outcome, and that binary result is their power. A test either passes, meaning the checked behaviour holds, or fails, meaning it does not, or the test itself is broken. There is no partial credit. A suite of passing tests means every checked behaviour holds, at least for the cases tested. That "at least" is the honest limit of testing: tests prove behaviour for the cases they cover, not for cases they do not, and a passing suite can still hide bugs in untested corners.

A test suite is a collection of tests, usually organised by the code they test, and run together with a single command. Running a suite should be easy and fast enough to do often, ideally after every change, because a suite that is hard to run will not be run, and a suite that is not run provides no protection. Python's standard library includes unittest, a framework for writing and running suites, which you will learn in this chapter, and there are other frameworks with more features, but the ideas are the same across all of them. The framework matters less than the habit: write tests, run them often, and fix failures promptly, before they accumulate into a suite that nobody trusts.

Finally, tests are not a substitute for thinking. A test can only check what its author thought to check, and it cannot catch a misunderstanding about what the feature should do. If you misunderstand a requirement, your tests will faithfully check the wrong behaviour, and they will pass, giving false confidence. Testing complements, but does not replace, understanding requirements, reviewing code, and trying the application as a user would.

# Arrange, act, assert: the three steps of every test.
def greet(name):
    return f"Hello, {name}!"

# Arrange: known input. Act: call the function. Assert: check the result.
name = "Ada"
result = greet(name)
assert result == "Hello, Ada!"
print("Test passed")

Section 3: Tests as a Safety Net

A safety net does not prevent a performer from falling. It catches them when they do, so a fall becomes a recoverable moment rather than a disaster. Tests work the same way for code. They do not prevent bugs from being written. They catch bugs when they are introduced, so that a mistake becomes a failing test, noticed immediately, rather than a broken feature, noticed by users weeks later. That catching function is the most practical way to think about tests, because it explains why they are valuable even when they feel like extra work: they turn expensive failures into cheap, early signals.

The safety net metaphor also explains why test suites must be run regularly. A net that is folded away in a cupboard catches nobody. A test suite that is written but never run, or run only before releases, catches bugs late, when they are more expensive. A suite run after every change, or automatically on every code update, catches bugs at the moment they are introduced, when the change is fresh and the fix is obvious. That is why automation matters, and why the chapter later covers continuous integration, which runs tests automatically. The net must be up, always, to do its job.

A safety net also has holes, and understanding them prevents overconfidence. A net catches falls within its area, but not outside it. A test suite catches bugs in behaviour it covers, but not in behaviour it does not cover. A new feature with no tests has no net. A changed behaviour with outdated tests has a net with a hole in exactly the place you changed. That is why coverage, covered later, matters, and why tests must be updated when behaviour changes, not left to rot. A suite that is not maintained develops holes, and a suite with holes gives false confidence, which is more dangerous than having no suite, because it discourages the caution that an untested codebase would inspire.

Another property of safety nets is that they must be trusted. A net that sometimes fails for no reason, because of flaky tests that pass and fail randomly, will not be trusted, and developers will start ignoring its signals, which defeats its purpose. Flaky tests, covered later, must be fixed promptly, because trust in the suite is a precious resource. Similarly, a net that is too slow to use, taking an hour to run, will be skipped, because developers will not wait. Keeping tests fast, reliable, and trusted is therefore not a luxury. It is what keeps the net up and respected.

Finally, a safety net changes how you work, for the better. With a trusted net, you can refactor, which means restructuring code without changing its behaviour, confidently, because the net will catch any accidental behaviour change. You can upgrade dependencies, knowing the net will catch incompatibilities. You can hand code to another developer, knowing the net will catch misunderstandings. That confidence to change, to improve, to hand over, is the long-term payoff of testing, and it is why experienced developers consider tests an investment, not a cost. The net does not make you infallible. It makes you recoverable, and recoverability is what lets a codebase grow without fear.

# A safety net: change the code, run the tests, catch mistakes immediately.
def total(prices):
    return sum(prices)

assert total([10, 20, 30]) == 60
assert total([]) == 0
print("Net holding: both checks passed")

Section 4: Manual Testing Versus Automated Testing

Before automated tests, there is manual testing: trying your application by hand, as a user would, clicking buttons, filling forms, and checking results. Manual testing is valuable and irreplaceable for some things, such as judging whether a page looks right, whether a flow feels natural, or whether an error message makes sense to a human. It is also slow, inconsistent, and unrepeatable at scale. A human tester may try ten cases in an hour, may forget a case, and may test slightly differently each time. Manual testing is excellent for exploration and judgement, and poor for regression, which is checking that old behaviour still works after changes.

Automated testing means writing code that checks your code, and running it with a command, as often as you like, with exactly the same cases every time. An automated suite can run hundreds of checks in seconds, with perfect consistency, and it can run after every change, catching regressions immediately. That repeatability is its superpower. A manual tester who checks a signup flow once a week will miss a regression for days. An automated suite that checks it after every change will catch it within minutes. For back-end code, where behaviour is defined by inputs and outputs rather than by appearance, automated testing is especially powerful, because most back-end behaviour can be checked precisely by code.

The two kinds of testing complement each other, and a healthy project uses both. Automated tests cover the repeatable, precise checks: does this function return the right value, does this endpoint return the right status, does this validation reject bad input? Manual testing covers the judgemental, exploratory checks: does this flow make sense, does this page look right on a phone, does this error message help a confused user? Neither replaces the other. A project with only manual testing will regress, because humans cannot repeat hundreds of checks after every change. A project with only automated testing may miss usability problems, because automated checks cannot judge whether something feels right.

There is also a cost difference. Manual testing costs human time every time it is done, and it does not scale: checking a hundred cases by hand takes a hundred times as long as checking one. Automated testing costs developer time once, to write the test, and then almost nothing to run, however many times it runs. That is why automation pays off quickly for checks that will be repeated often, which is most back-end checks. The rule of thumb is: if you will check it more than a few times, automate it.

Finally, remember that automated tests are themselves code, and they need care: they can have bugs, they can become outdated, and they can be flaky. A failing automated test does not always mean the application is broken. It might mean the test is wrong, or the test's assumptions changed. That is why reading test failures carefully, covered later, matters, and why tests should be reviewed like other code. Manual and automated testing, used together, with each doing what it does best, give you both the precision of automation and the judgement of a human, which is the combination that produces reliable software.

# Automated: the same check, run exactly the same way, as often as you like.
def is_valid_email(address):
    return "@" in address and "." in address

for address, expected in [("ada@example.com", True), ("not-an-email", False)]:
    assert is_valid_email(address) == expected
print("Automated checks passed, repeatable any time")

Section 5: Unit Tests in Plain Words

A unit test is a test of a small, isolated piece of code, usually a single function, or a single method, checked on its own, without involving the rest of the system. The "unit" is the smallest testable part, and the isolation is the key: a unit test for a function that adds numbers should not need a database, a web server, or an outside service. It should call the function with known inputs and check its outputs, quickly and reliably. Unit tests are the foundation of a test suite, because they are fast, focused, and precise: when a unit test fails, it points to a specific function, not to a vague area of the system.

Unit tests work best for code that is pure, meaning its output depends only on its inputs, with no hidden state or side effects. A function that validates an email address, calculates a total, formats a date, or sorts a list is a perfect unit test candidate, because its behaviour is fully described by inputs and outputs, and it can be tested exhaustively with many cases. Code with side effects, such as writing to a database or sending an email, is harder to unit test in isolation, because the test must set up and check the side effect, which is slower and more complex. That difficulty is a design signal: separating pure logic from side effects, so the pure parts can be unit tested easily, makes code both more testable and more understandable.

Writing a unit test follows the arrange, act, assert pattern from earlier, at a small scale. Arrange might mean choosing input values. Act means calling the function. Assert means checking the result equals the expected value, or that an expected error was raised. A good unit test checks one behaviour, with a clear name, such as "test_valid_email_accepted" or "test_empty_cart_totals_zero", so that a failure tells you what broke. A test that checks many behaviours at once is harder to diagnose when it fails, because you do not know which behaviour broke. One behaviour per test, clearly named, is the unit test discipline, and it pays off in diagnostic speed.

Unit tests are fast, and that speed matters. A suite of hundreds of unit tests can run in seconds, which means it can be run after every change, without interrupting your flow. That speed comes from isolation: no databases to set up, no servers to start, no networks to wait for. When unit tests become slow, it is usually because they are not truly isolated, they are doing integration work in disguise, such as hitting a real database. Keeping unit tests truly isolated preserves their speed, and speed preserves the habit of running them often.

Finally, unit tests have an honest limit: they test parts, not the whole. A system whose every function passes its unit tests can still fail when the parts are combined, because the parts might interact incorrectly. That is why unit tests are the base of the testing pyramid, covered later, not the whole pyramid. Integration and end-to-end tests cover the interactions that unit tests miss. But without unit tests, those higher-level tests must cover everything, which makes them slow, vague, and hard to diagnose.

# A unit test: one small function, isolated, checked on its own.
def calculate_total(prices):
    return sum(prices)

assert calculate_total([10, 20]) == 30
assert calculate_total([]) == 0
assert calculate_total([5]) == 5
print("Unit tests passed for calculate_total")

Section 6: Writing Your First Unit Test with unittest

Python's standard library includes unittest, a framework for writing and running tests, and it is the right place to start, because it requires no installation and it teaches the concepts that other frameworks share. A unittest test is written as a class, inheriting from unittest.TestCase, with methods whose names start with test_. Each method is one test, and it uses assertion methods, such as assertEqual, assertTrue, and assertRaises, to check behaviour. When you run the tests, the framework finds all test methods, runs each one, and reports which passed and which failed, with details for failures. That structure, class plus test methods plus assertions, is the standard shape of a Python test suite.

Let us build a small example. Suppose you have a function that validates a username: it should accept names of three to twenty characters, containing only letters, numbers, and underscores, and reject everything else. A test class for that function might have methods for a valid name, a name that is too short, a name with a forbidden character, and an empty name. Each method calls the function with a specific input and asserts the expected result. That is four tests, each checking one behaviour, each clearly named, each independent. Running them gives you four pass or fail results, and if one fails, its name tells you which behaviour broke. That clarity is the value of the framework's structure, compared to a loose collection of assert statements.

Running unittest tests is simple. You can run them from the command line with python -m unittest, which discovers test files and runs them, or you can run a test file directly, if it includes the standard boilerplate that calls unittest.main(). Discovery means the framework finds test files automatically, by name pattern, so you do not need to list each test. That automation matters as suites grow: a suite with a hundred test files should still run with one command, not with a hundred commands. Learning discovery early, and organising test files so discovery finds them, saves frustration later.

Assertion methods deserve attention, because they produce better failure messages than plain asserts. When assertEqual fails, it shows both values, expected and actual, so you can see the difference immediately. When assertRaises fails, it tells you the expected exception was not raised. Those messages are the difference between a failure you understand in seconds and one you must investigate. Use the framework's assertions, not plain assert statements, in unittest tests, because the framework's messages are designed for debugging, and because they integrate with the framework's reporting, which counts failures and shows summaries.

Finally, a habit to build: run your tests before you consider a feature done, and run them again after any change, however small. A feature is not done when it works once by hand. It is done when its tests pass, and when those tests cover its main behaviours and its edge cases. That definition of done, tests passing, is a professional standard, and it is one that will serve you in teams, where others rely on your code, and in solo projects, where your future self relies on your past self's diligence. Writing your first unittest test is a small step. Making it a habit is the larger, more valuable step.

import unittest

def is_valid_username(name):
    return 3 <= len(name) <= 20 and name.replace("_", "").isalnum()

class TestUsername(unittest.TestCase):
    def test_valid_name(self):
        self.assertTrue(is_valid_username("ada_123"))

    def test_too_short(self):
        self.assertFalse(is_valid_username("ad"))

    def test_bad_character(self):
        self.assertFalse(is_valid_username("ada!"))

if __name__ == "__main__":
    unittest.main()

Section 7: Assertions: Saying What Should Be True

An assertion is a statement that something should be true, and if it is not, the test fails. Assertions are the heart of testing, because they are where expectations become checks. Without assertions, a test might run code without verifying anything, which is useless: it would pass even if the code were completely wrong, as long as it did not crash. With assertions, a test becomes a precise claim: given this input, the output should be this, or this error should be raised, or this database row should exist. That precision is what makes tests trustworthy, and learning to write good assertions is learning to test well.

The most common assertion is equality: the result should equal an expected value. That covers most function tests, where you know the input and the expected output. But there are other kinds, each for a different claim. Truthiness assertions check that a value is true or false, useful for validation functions. Membership assertions check that an item is in a list, or a key is in a dictionary, useful for checking collections. Exception assertions check that a function raises a particular error for bad input, which is essential for testing validation and error handling, because a function that should reject bad input but silently accepts it is buggy, even if it does not crash. And approximate assertions check that numbers are close, not exactly equal, useful for calculations involving floating point, where exact equality is unreliable.

Writing good assertions means being specific. An assertion that checks a whole result is better than one that checks only part of it, because a partial check can pass while the rest is wrong. For example, testing a user creation function by asserting only that it returns without error is weak. Asserting that the returned user has the right name, the right email, and that the database contains a matching row, is strong, because it checks the full effect. Specificity also means asserting the right thing: if a function should return a list sorted by date, assert the order, not just the contents, because an unsorted list with the right items would pass a contents-only check while being wrong.

There is also a balance to strike: too few assertions, and the test is weak. Too many assertions in one test, and the test becomes hard to diagnose, because a failure could be any of them, and the test's purpose becomes unclear. The guideline from earlier applies: one behaviour per test, with the assertions needed to verify that behaviour fully, and no more. If a test needs many assertions to verify one behaviour, that is fine, because they all serve the same claim. If a test's assertions verify several unrelated behaviours, split it into several tests, each with a clear name. That discipline keeps tests both strong and diagnosable.

Finally, assertions should be about behaviour, not implementation. A test that asserts a specific internal data structure, rather than the observable result, will break when the implementation changes, even if the behaviour stays correct. That brittleness makes tests a burden, because developers must update tests for every refactoring. Asserting observable behaviour, what the function returns or what the database contains, keeps tests stable across refactorings.

import unittest

def divide(a, b):
    if b == 0:
        raise ValueError("cannot divide by zero")
    return a / b

class TestDivide(unittest.TestCase):
    def test_normal(self):
        self.assertEqual(divide(10, 2), 5)

    def test_zero_raises(self):
        with self.assertRaises(ValueError):
            divide(10, 0)

    def test_in_list(self):
        self.assertIn(5, [1, 5, 9])

Section 8: Testing Functions That Return Values

The simplest functions to test are those that take inputs and return outputs, without side effects, because their tests are straightforward: call the function, check the result. Many back-end helpers are like this: validation functions, formatting functions, calculation functions, and data transformation functions. Testing them well means choosing inputs that cover the important cases, including normal cases, edge cases, and invalid cases, and asserting the exact expected outputs. That coverage, not just one happy-path check, is what makes a function test trustworthy.

Start with the happy path: typical inputs that should work. For a function that calculates a discount, test a normal price and a normal discount rate, and assert the correct discounted price. Then test the edges: a price of zero, a discount of zero percent, a discount of one hundred percent, a very large price. Edges are where bugs hide, because they involve boundaries, such as zero, empty, maximum, and minimum, where code often has special cases or off-by-one errors. A function that works for typical inputs but fails for zero or empty inputs is a function with a bug waiting for a real user to trigger it, because real users do enter zero and empty values.

Then test invalid inputs, if the function is supposed to reject them. A function that should raise an error for a negative price, or for a discount over one hundred percent, should be tested with those inputs, asserting that the error is raised. Testing invalid inputs is as important as testing valid ones, because a function that silently accepts invalid data can cause corruption downstream, which is harder to diagnose than an immediate error. The discipline of testing both valid and invalid inputs, for every function that validates, is what makes validation reliable, rather than a hope.

There is also a technique called parametrisation, or table-driven testing, where a single test method runs the same check for many input-output pairs, listed in a table. That technique reduces repetition: instead of writing ten similar test methods, you write one method that loops over ten cases, asserting each. Parametrisation is efficient, but it has a trade-off: when one case fails, the test method fails, and you must look at which case failed, which is slightly less clear than a separately named test per case. Many frameworks support parametrisation with clear per-case reporting, which gives you the best of both. For unittest, a loop with a clear message per case, or a subTest, achieves a similar effect. Use parametrisation for cases that share the same behaviour, and separate tests for cases that represent distinct behaviours.

Finally, keep return-value tests fast and independent. They should not depend on each other, on shared state, or on outside services, because dependence makes them fragile and order-sensitive, which are problems covered later. Each test should set up its own inputs, call the function, and check the result, without relying on a previous test having run. That independence is what makes unit tests reliable and easy to run in any order, which is essential for a suite that will be run hundreds of times, by different people, in different environments.

import unittest

def discount(price, percent):
    if price < 0 or not 0 <= percent <= 100:
        raise ValueError("invalid price or discount")
    return price * (100 - percent) / 100

class TestDiscount(unittest.TestCase):
    def test_normal(self):
        self.assertEqual(discount(100, 20), 80)

    def test_zero_discount(self):
        self.assertEqual(discount(100, 0), 100)

    def test_full_discount(self):
        self.assertEqual(discount(100, 100), 0)

    def test_negative_price_raises(self):
        with self.assertRaises(ValueError):
            discount(-10, 20)

Section 9: Testing Functions with Side Effects

Not all functions simply return a value. Many do something: write to a database, create a file, send an email, or update a shared object. Those actions are called side effects, and testing them requires a different approach, because there is no return value to check, or the return value does not tell the whole story. Instead, you check the effect: after calling the function, is the database row present, is the file created, was the email recorded as sent, did the object's state change correctly? That effect-checking is the core of side-effect testing, and it is essential for back-end code, where most important work is side effects.

The first step is to make the side effect observable in the test. For a database write, that means using a test database, which you can query after the call to verify the row. For a file write, it means using a temporary directory, which you can inspect and then clean up. For an email send, it means using a fake sender, which records messages instead of delivering them, as covered in the email chapter, so the test can check what was recorded. For an object update, it means checking the object's attributes after the call. In each case, the test sets up an observable destination, acts, and then inspects that destination, rather than relying on the return value alone.

The second step is to isolate the side effect from the real world. A test that writes to a real database, sends a real email, or modifies a real file is dangerous: it can corrupt real data, spam real people, or leave the system in an unknown state. Test side effects must go to test doubles: a test database that can be discarded, a temporary directory that is cleaned up, a fake sender that records instead of delivering. That isolation protects both the real system and the test's reliability, because a test that depends on real-world state, such as a real mailbox, will be slow, flaky, and hard to run repeatedly. Isolation is not optional for side-effect tests. It is what makes them safe to run often.

The third step is to clean up after the test, so that one test's side effects do not affect the next test. That cleanup is part of teardown, covered in the next section, and it is essential for test isolation. A test that creates a database row and leaves it will cause the next test, which counts rows, to fail, even though the next test's code is correct. Cleanup can be done by deleting what was created, by using a fresh test database per test, or by running each test in a transaction that is rolled back. The method matters less than the principle: each test starts clean, and leaves clean, so tests do not interfere with each other.

Finally, side-effect tests should check both the effect and its absence when appropriate. A function that should create a row for valid input should be tested for valid input, checking the row exists, and for invalid input, checking that no row was created. Checking absence is as important as checking presence, because a function that always creates a row, even for invalid input, is buggy, and only an absence check will catch it.

import unittest

# A side effect: the function changes a store. Test by inspecting the store.
store = {}

def create_user(username):
    store[username] = {"active": True}

class TestCreateUser(unittest.TestCase):
    def setUp(self):
        store.clear()

    def test_creates_user(self):
        create_user("ada")
        self.assertIn("ada", store)
        self.assertTrue(store["ada"]["active"])

    def test_no_user_before_create(self):
        self.assertNotIn("ada", store)

Section 10: Test Setup and Teardown

Setup and teardown are the parts of a test that prepare and clean up its environment. Setup runs before each test, creating the data, objects, or connections the test needs. Teardown runs after each test, cleaning up what setup created, so the next test starts fresh. In unittest, setup is a method called setUp, and teardown is a method called tearDown, defined in the test class, and the framework calls them automatically around each test method. That automation is valuable, because it guarantees cleanup happens even if a test fails, and it removes repetitive setup code from individual tests, making them shorter and clearer.

Setup is where you create a clean slate. For a database test, setup might create a fresh in-memory database and its tables. For a file test, it might create a temporary directory. For an object test, it might create a fresh object with known state. The key principle is that setup creates everything the test needs, and nothing more, so the test itself can focus on the behaviour being checked, not on preparation. Setup should also be fast, because it runs before every test, and slow setup multiplied by hundreds of tests becomes a slow suite. Keep setup minimal, creating only what the tests in that class actually need.

Teardown is where you restore cleanliness. For a database test, teardown might close the connection and discard the database. For a file test, it might delete the temporary directory. For an object test, it might not be needed at all, if objects are discarded automatically. Teardown matters most when tests share resources, such as files, databases, or global state, because without it, one test's leftovers pollute the next test's environment. Even when teardown seems unnecessary, because Python's garbage collection will clean up objects, explicit teardown for external resources, like files and connections, is good practice, because it guarantees cleanup promptly, rather than relying on timing.

There is also a distinction between per-test setup and per-class setup. Per-test setup, setUp, runs before every test method, giving each test a fresh environment, which is the safest default, because it guarantees isolation. Per-class setup, setUpClass, runs once before all tests in a class, which is faster when setup is expensive, such as creating a large dataset, but it risks tests interfering with each other through shared state. Use per-test setup by default, and per-class setup only when setup is genuinely expensive and tests are carefully designed not to interfere, such as read-only tests that never modify the shared data. That caution preserves isolation, which is more valuable than the speed saved by sharing setup.

Finally, setup and teardown should themselves be simple and reliable. A setup that is complex, or that can fail in confusing ways, makes tests hard to understand and debug, because a failure in setup looks like a failure in the test. Keep setup code straightforward, use helper functions for repeated setup, and avoid logic in setup that branches on test names or conditions. Setup is infrastructure for tests, and like all infrastructure, it should be boring, predictable, and invisible when it works, so that attention stays on the behaviour being tested, not on the machinery around it.

        self.store.clear()

Section 11: Testing with a Test Database

Back-end code usually talks to a database, and testing that code requires a database to talk to, but not your real one. A test database is a separate, disposable database, created for tests, filled with known test data, and discarded afterwards, so tests can read and write freely without risking real data. Using a test database is essential for testing database code honestly: without it, you either skip testing database code, which leaves a large, important area untested, or you test against a real database, which is dangerous and unreliable. A test database gives you the best of both: real database behaviour, with no real risk.

For Python learners, SQLite in-memory databases are an excellent test database. An in-memory database lives only in RAM, is created instantly, and disappears when the connection closes, which makes setup and teardown trivial: create it in setUp, close it in tearDown, and every test starts with a clean, empty database. That cleanliness is the key benefit. Each test can create its own tables, insert its own rows, and check its own results, without worrying about leftovers from other tests. In-memory databases are also fast, because there is no disk involved, which keeps the suite quick, even with hundreds of database tests.

The pattern for a database test is straightforward. In setup, create the database and the tables your code needs, using the same schema as production, or a simplified version that covers what is tested. In the test, insert known rows, call the code under test, which should accept a database connection as a parameter, rather than creating its own, so the test can pass the test database, and then query the database to check the effect. That parameter, passing the connection in, is a design choice that makes code testable, and it is worth adopting generally: code that creates its own database connection internally is hard to test, because the test cannot substitute a test database. Code that receives its connection can be tested with any database, including an in-memory one.

Test data deserves thought. Use small, clear, realistic data, with names and values that make failures readable. A test that inserts a user named Ada with a known task, and then checks that task, is easier to debug than a test that inserts anonymous rows with random values. Use a few rows, not many, because each row adds setup time and complexity, and a test with three rows usually proves as much as a test with three hundred, for logic testing. And use distinct values per test, so that a test checking for a specific row cannot accidentally pass because of a leftover row from another test, which is another reason fresh databases per test matter.

Finally, remember that a test database tests your code's interaction with a database, not the database itself. You do not need to test that SQLite can insert a row, because that is SQLite's job, already tested by its authors. You need to test that your code inserts the right row, with the right values, under the right conditions, and that it reads, updates, and deletes correctly. Focus tests on your logic, not on the database's behaviour, and your database tests will be focused, fast, and meaningful, rather than slow re-tests of a well-tested system.

import sqlite3, unittest

Section 12: Testing API Endpoints with http.server

Testing an API endpoint means checking that a request to a URL produces the expected response: the right status code, the right body, and the right headers. For a Python back-end built with http.server, you can test endpoints without starting a real server on a network port, by calling the handler logic directly, or by starting a test server on a local port and making real HTTP requests to it. Both approaches are useful, and understanding when to use each helps you test APIs effectively, without unnecessary complexity or slowness.

The direct approach tests the handler function itself. If your request handling logic is separated into functions that take a request description and return a response description, you can call those functions in tests with known inputs and check their outputs, just like any other function test. That approach is fast and precise, because it skips networking entirely, and it is the reason to separate logic from transport: a handler that mixes HTTP details with business logic is hard to test directly, while a handler that delegates to pure functions is easy. Design your handlers with that separation, and endpoint testing becomes mostly function testing, which you already know how to do.

The live approach starts a real test server, on a local port, in a background thread, and makes HTTP requests to it using urllib, which is in the standard library. That approach tests the full stack: routing, headers, status codes, JSON encoding, and the server's behaviour, exactly as a real client would experience it. It is slower than the direct approach, because it involves networking and threads, and it requires careful setup and teardown, starting the server before tests and stopping it afterwards, but it catches problems the direct approach misses, such as a route that is not registered, a header that is wrong, or a response that is not valid JSON. For critical endpoints, the live approach is worth its cost.

A practical strategy combines both. Use direct tests for most endpoint logic, because they are fast and numerous, covering validation, business rules, and error cases. Use live tests for a smaller set, covering the critical paths, such as signup, login, and the main resource endpoints, to verify the full stack works end to end. That combination gives you broad coverage quickly, plus confidence in the real HTTP behaviour where it matters most. It also keeps the suite fast overall, because the slow live tests are few, while the fast direct tests are many.

When writing live endpoint tests, follow a few practices. Use a test database, so requests do not affect real data. Use a random or free port, so tests do not conflict with other servers or with each other. Clean up the server in teardown, so it does not linger after tests finish. And check the full response, not just the status: a 200 response with the wrong body is still a bug, and a test that only checks status will miss it. Check status, check body structure, check key fields, and check error responses for invalid requests, because error responses are part of the API's contract, and they deserve testing just as success responses do.

import json, unittest
from http.server import BaseHTTPRequestHandler, HTTPServer
import threading, urllib.request

# A tiny API, tested live on a local port with a real HTTP request.
class Handler(BaseHTTPRequestHandler):
    def do_GET(self):
        if self.path == "/tasks":
            body = json.dumps([{"title": "Finish report"}]).encode()
            self.send_response(200)
            self.send_header("Content-Type", "application/json")
            self.end_headers()
            self.wfile.write(body)

    def log_message(self, *args):
        pass  # keep test output clean

class TestAPI(unittest.TestCase):
    @classmethod
    def setUpClass(cls):
        cls.server = HTTPServer(("localhost", 0), Handler)
        cls.port = cls.server.server_address[1]
        cls.thread = threading.Thread(target=cls.server.serve_forever, daemon=True)
        cls.thread.start()

    @classmethod
    def tearDownClass(cls):
        cls.server.shutdown()

    def test_list_tasks(self):
        with urllib.request.urlopen(f"http://localhost:{self.port}/tasks") as r:
            self.assertEqual(r.status, 200)
            data = json.loads(r.read())
        self.assertEqual(data[0]["title"], "Finish report")

Section 13: Integration Tests in Plain Words

An integration test checks that several parts of your system work together correctly, rather than testing one part in isolation. While a unit test checks a single function, an integration test checks a combination: a request handler plus the database, a job plus the mail sender, an API plus its authentication. Integration tests are essential because parts that work perfectly alone can fail when combined, due to mismatched assumptions, incorrect wiring, or data format differences. A function that returns the right data is useless if the handler that calls it passes the wrong arguments, and only an integration test, exercising both together, will catch that.

Integration tests are slower and broader than unit tests, because they involve more components, more setup, and more possible failure points. A database integration test needs a test database. An API integration test needs a test server. A job integration test needs a queue and a worker, or a fake version of them. That setup cost is the main trade-off: integration tests give you more confidence about real behaviour, but they cost more to write and run, and when they fail, the cause is less obvious, because the failure could be in any of the parts involved, or in their interaction. Diagnosing an integration failure often requires narrowing it down with unit tests, or with logs, to find which part misbehaved.

A good integration test focuses on a meaningful interaction, not on everything at once. Testing a complete user signup, from request to database row to welcome email record, is a meaningful integration test, because it covers a real user journey through several parts. Testing every function together in one giant test is not, because it is slow, vague, and hard to diagnose. The guideline is to test interactions that matter, and that are likely to break at boundaries, such as between the API and the database, or between the application and an outside service, because boundaries are where assumptions mismatch. Internal interactions, within a single module, are usually covered adequately by unit tests.

Integration tests also need realistic, but controlled, dependencies. A test that integrates with a real outside service, such as a real mail provider, will be slow, flaky, and potentially harmful, because it depends on the service's availability and it may send real messages. The standard practice is to integrate with fakes for outside services, while integrating really with your own components, such as your database and your handlers. That balance, real for your code, fake for the outside world, gives you confidence about your system's behaviour without depending on the outside world's reliability. It is the same isolation principle as unit tests, applied at a larger scale.

Finally, integration tests sit in the middle of the testing pyramid, covered next: fewer than unit tests, because they are slower and broader, but more than end-to-end tests, because they are still relatively fast and focused. A healthy suite has many unit tests, a moderate number of integration tests, and a few end-to-end tests, reflecting the trade-off between speed, precision, and realism at each level. Integration tests are the bridge between parts and wholes, and they are where many real bugs, the ones that occur at boundaries, are caught, which makes them an indispensable part of a test suite, despite their cost.

# Integration: handler plus database together, not either alone.
import sqlite3

def create_task_endpoint(db, title):
    db.execute("INSERT INTO tasks (title) VALUES (?)", (title,))
    db.commit()
    return {"status": 201, "title": title}

db = sqlite3.connect(":memory:")
db.execute("CREATE TABLE tasks (title TEXT)")
response = create_task_endpoint(db, "Finish report")
rows = db.execute("SELECT title FROM tasks").fetchall()
assert response["status"] == 201 and rows == [("Finish report",)]
print("Integration passed: endpoint and database agree")

Section 14: End-to-End Tests in Plain Words

An end-to-end test, often shortened to E2E, checks a complete user journey through the whole system, from start to finish, exactly as a user would experience it. For a task application, an end-to-end test might sign up a user, log in, create a task, list tasks, and verify the task appears, all through the real API or interface, with the real database, and with fakes only for outside services. End-to-end tests are the closest automated equivalent to manual testing, and they give the highest confidence that the system works as a whole, because they exercise everything together, in the way users actually use it.

The strength of end-to-end tests is also their weakness: because they exercise everything, they are slow, they require extensive setup, and when they fail, the cause can be anywhere in the system, making diagnosis difficult. A failing end-to-end test tells you something is broken, but not what, and you must then use unit and integration tests, or logs, to narrow it down. That diagnostic cost is why end-to-end tests should be few and focused on critical journeys, not numerous and exhaustive. A suite with hundreds of end-to-end tests will be slow to run, hard to maintain, and frequently flaky, because any small change in any part can break many of them. A suite with a handful, covering signup, login, and the main features, gives high confidence at manageable cost.

End-to-end tests also need a realistic environment. They should run against a test deployment that resembles production, with a test database, test configuration, and fakes for outside services, so that they verify the real system, not a simplified version of it. Setting up that environment takes effort, and keeping it in sync with production, as the system grows, takes ongoing attention. That effort is justified for critical journeys, because those journeys are what users care about most, and a failure in them is the most damaging kind. For less critical features, integration tests are usually sufficient, and end-to-end tests would be overkill.

There is also a maintenance consideration. End-to-end tests are brittle, because they depend on many details: URLs, response formats, page structures, and data states, any of which can change and break the test, even when the underlying feature still works correctly. Keeping them passing requires updating them with every relevant change, which is work that must be budgeted, not ignored. A team that writes end-to-end tests but does not maintain them will soon have a suite full of failures that nobody trusts, which is worse than having no end-to-end tests, because it wastes time and erodes confidence in testing generally.

Despite those costs, end-to-end tests are indispensable for critical paths, because they are the only automated tests that verify the system as users experience it. Unit tests verify parts. Integration tests verify combinations. End-to-end tests verify the whole, and the whole is what users pay for, or use, or depend on. A system with good unit and integration tests but no end-to-end tests might still fail in production due to a wiring problem, a configuration error, or a deployment mistake that only a full journey would reveal. A few well-chosen end-to-end tests, maintained carefully, catch those whole-system failures, and they are the final safety net before users encounter a problem.

# End-to-end in miniature: signup, login, create, list, verify.
system = {"users": {}, "tasks": {}}

def signup(username):
    system["users"][username] = True

def create_task(username, title):
    system["tasks"].setdefault(username, []).append(title)

signup("ada")
create_task("ada", "Finish report")
assert "Finish report" in system["tasks"]["ada"]
print("End-to-end passed: full journey works")

Section 15: The Testing Pyramid

The testing pyramid is a model for how many tests of each kind a healthy suite should have, shaped like a pyramid: many unit tests at the base, fewer integration tests in the middle, and few end-to-end tests at the top. The shape reflects the trade-offs you have learned: unit tests are fast, cheap, and precise, so you can have many of them. Integration tests are slower and broader, so you have fewer. End-to-end tests are slowest, broadest, and most brittle, so you have fewest. A suite shaped like a pyramid is fast to run, precise in diagnosis, and confident about the whole, because each level covers what the levels below cannot, without duplicating their work excessively.

The opposite shape, sometimes called the ice cream cone, has few unit tests and many end-to-end tests. That shape is a warning sign, because it means the suite is slow, because end-to-end tests dominate, vague in diagnosis, because failures could be anywhere, and brittle, because many tests depend on the whole system. Ice cream cone suites are common in projects that started testing late, by automating manual user journeys, without building unit tests first, and they are painful to maintain. If your suite looks like a cone, the remedy is to add unit tests for the logic currently only covered end-to-end, and to reduce end-to-end tests to critical journeys, gradually reshaping towards a pyramid.

The pyramid is a guideline, not a strict rule with exact numbers. The right proportions depend on your system: a system with complex business logic needs many unit tests. A system with many integrations needs more integration tests. A system with critical user journeys needs enough end-to-end tests to cover them, even if that is more than a textbook pyramid suggests. The principle is the direction, not the exact count: prefer fast, precise tests where possible, and use slower, broader tests where they add unique confidence, not as a substitute for unit tests. A pyramid that is slightly top-heavy for a good reason is fine. A cone that is top-heavy by neglect is not.

There is also a cost argument for the pyramid. Unit tests are cheap to write, run, and maintain, because they are small and isolated. End-to-end tests are expensive on all three counts, because they are large, slow, and brittle. A suite dominated by expensive tests will be run less often, because it takes too long, and maintained less carefully, which erodes its value. A suite dominated by cheap tests will be run often, maintained willingly, and trusted. The pyramid is therefore an economic choice, favouring the tests that give the most confidence per unit of effort.

Finally, the pyramid helps you decide where to add a test for a new feature. Ask first: can this be tested as a unit, by checking a function? If yes, write a unit test. If not, because it involves several parts, write an integration test. If it is a critical user journey that only a full test can verify, write an end-to-end test. That decision process, applied consistently, naturally produces a pyramid, because most behaviours can be unit tested, fewer require integration, and only critical journeys require end-to-end. Let the pyramid guide your choices, and your suite will stay fast, precise, and trustworthy as it grows.

# The pyramid: many fast unit tests, fewer integration, few end-to-end.
pyramid = {"unit tests": 100, "integration tests": 30, "end-to-end tests": 5}
for kind, count in pyramid.items():
    print(kind, ":", count)

Section 16: What to Test First

When you are starting to test an existing, untested codebase, or a new feature, the question is where to begin, because testing everything at once is overwhelming, and testing the wrong things first wastes effort. The answer is to start with what matters most: the code that is most important, most complex, and most likely to break. Importance means the code users depend on, or the code where a bug causes the most harm, such as authentication, payments, or data storage. Complexity means code with many branches, calculations, or edge cases, where bugs are likely to hide. Likelihood of breaking means code that changes often, or that has broken before, because past failures predict future ones.

A practical order is to start with core business logic, in unit tests, because that logic is the heart of your application, it is usually pure and easy to test, and it is where bugs cause the most damage. For a task application, that might be task creation rules, validation, and calculations. Next, test the API endpoints for those core features, with integration tests, because endpoints are how users reach the logic, and because endpoint bugs, such as wrong status codes or missing validation, are common and visible. Next, add end-to-end tests for the critical journeys that use those features, so the whole path is verified. That order, logic, then endpoints, then journeys, builds confidence from the inside out, which is efficient, because logic tests are fast and catch most bugs early.

Another consideration is to test the code you are about to change, before you change it. If you need to fix a bug, write a test that reproduces the bug first, watch it fail, then fix the bug and watch the test pass. That test, called a regression test, ensures the bug never returns silently. If you need to refactor, write tests for the current behaviour first, so they can verify the refactoring did not change behaviour. That habit, test before change, turns testing into a tool for safe change.

Also, test the boundaries and the sad paths early, not just the happy paths. A feature that works for typical inputs but fails for empty, invalid, or extreme inputs is a feature with bugs waiting for real users, because real users provide all of those inputs, often accidentally. Testing validation, error handling, and edge cases early catches the bugs that are most embarrassing in production, because they affect users who are already confused or frustrated, such as a user who mistypes an email and gets a crash instead of a helpful error. Happy paths are necessary, but they are not sufficient, and a test suite that only covers them gives false confidence.

Finally, do not aim for perfect coverage at the start. Aim for meaningful coverage of the most important code, and grow from there, guided by bugs and incidents. When a bug is found in production, add a test for it, so it cannot return unnoticed. When a new feature is added, add tests for it as part of the feature, not afterwards. That incremental growth produces a suite that covers real risks, rather than one that covers easy code while leaving risky code untested.

# Test first: the most important, complex, and breakable code.
priorities = ["1. Core logic (validation, calculations)",
              "2. API endpoints for core features",
              "3. Critical user journeys",
              "4. Sad paths and edge cases"]
for p in priorities:
    print(p)

Section 17: Testing Happy Paths and Sad Paths

Every feature has a happy path, the sequence where everything goes as intended: a user provides valid input, the system processes it, and returns success. And every feature has sad paths, the sequences where something goes wrong: invalid input, missing data, a dependency failure, or an unauthorised request, and the system must handle it gracefully, with a clear error, not a crash or corruption. Testing both is essential, because a feature that only works on the happy path is a feature that will fail in production, where sad paths are common, not exceptional. Real users mistype, lose connections, and request things they should not, every day.

Happy path tests are the easiest to write and the most satisfying, because they confirm the feature works as designed. They should cover the main use cases, with typical, realistic data, and they should assert the full expected result, not just success. For a task creation endpoint, a happy path test might create a task with a valid title, assert a success status, and assert the returned task has the right title and an id, and that the database contains it. That thoroughness matters, because a happy path test that only checks status could pass while the data is wrong, giving false confidence about the feature's core behaviour.

Sad path tests are where reliability is built. For the same endpoint, sad path tests might include: a missing title, an empty title, a title that is too long, a request from an unauthenticated user, and a request for a user who does not exist. Each should assert a specific, appropriate response: a validation error with a clear message, an authentication error, or a not-found error, as appropriate, and, importantly, that no side effect occurred, such as no task created, no email sent. That absence check is crucial, because a sad path that returns an error but still creates a task, or still charges a user, is a bug that an error-only check would miss.

There is a tendency to under-test sad paths, because they feel less important. Resist that tendency. Sad paths are where users encounter your system at its worst, when they are already confused or mistaken, and how your system responds in those moments shapes their trust more than how it responds when everything goes well. A system that handles errors gracefully earns forgiveness for the error itself. A system that crashes or corrupts data on a sad path loses trust, even if its happy path is perfect.

A practical rule is to write at least one sad path test for every happy path test, and more for features with complex validation or authorisation. List the ways a request can go wrong, by thinking about each input, each dependency, and each permission, and write a test for each. That list, the sad path inventory, is a useful design exercise in itself, because it forces you to think about failure modes before they occur in production, which often reveals missing validation or error handling that can be fixed before release. Happy paths show a feature works. Sad paths show it is robust. Both are needed for a feature to be done.

# Happy path: valid input succeeds. Sad path: invalid input fails cleanly.
def create_task(title):
    if not title:
        raise ValueError("title is required")
    return {"title": title}

assert create_task("Finish report")["title"] == "Finish report"
try:
    create_task("")
    assert False, "should have raised"
except ValueError:
    print("Sad path handled: empty title rejected with a clear error")

Section 18: Edge Cases and Boundaries

Edge cases are inputs at the boundaries of what a system accepts: zero, one, empty, maximum, minimum, just inside a limit, and just outside it. Boundary testing is the practice of checking those edges specifically, because bugs cluster at boundaries, due to off-by-one errors, incorrect comparisons, and special-case handling. A function that accepts usernames of three to twenty characters might work for typical names, but fail for exactly three characters, or exactly twenty, or twenty-one, because of a comparison using the wrong operator, or a length check that is off by one. Only boundary tests will catch those errors, because typical inputs never touch the edges.

The classic boundary technique is to test, for each limit, three values: just below, exactly at, and just above the limit. For a minimum length of three, test two, three, and four characters. For a maximum of twenty, test nineteen, twenty, and twenty-one. For a price that must be positive, test zero, a small positive value, and a negative value. That systematic approach, applied to each boundary in your code, catches off-by-one errors reliably, because it probes the exact points where those errors manifest. It is a small amount of extra testing for a large amount of extra confidence, and it is a technique worth memorising, because it applies to every limit, in every system, in every language.

Edge cases also include special values that are not limits, but that behave unusually: empty strings, empty lists, None, very large numbers, and inputs with special characters, such as quotes, newlines, or Unicode. An empty list might cause a division by zero in an average calculation. A name with an apostrophe might break a query if not handled safely. A very large number might overflow, or cause performance problems. Those special values are not exotic. They occur in real data, provided by real users, often unintentionally, and code that crashes on them will crash in production. Testing special values is therefore not pedantry. It is preparation for reality.

There is also a category of edge cases involving time and state: the first and last items in a list, the transition from one state to another, and behaviour at midnight or month boundaries. Time boundaries are notorious for bugs, because they involve calendars, time zones, and arithmetic that is easy to get subtly wrong. Testing time edges often needs a fake clock, so you can set the time to a boundary and check behaviour, without waiting for it to occur naturally.

Finally, edge case testing should be guided by the code's actual boundaries, not by imagination alone. Read the code, find its comparisons, limits, and special cases, and test around each one. That code-guided approach is more effective than guessing, because it targets the places where bugs actually live, rather than the places you happen to think of. A test suite that systematically covers boundaries, for the code as written, is a suite that catches the class of bugs most likely to survive happy path testing, and that is a valuable complement to the happy and sad path tests you have already learned.

# Boundary testing: just below, exactly at, and just above each limit.
def is_valid_username(name):
    return 3 <= len(name) <= 20

for name, expected in [("ab", False), ("abc", True), ("abcd", True),
                       ("a" * 20, True), ("a" * 21, False)]:
    assert is_valid_username(name) == expected, name
print("Boundary tests passed for username length")

Section 19: Testing Validation and Bad Input

Validation is the code that checks whether input is acceptable, before acting on it, and it is one of the most important parts of a back-end system to test, because validation failures have direct consequences: bad data in the database, security vulnerabilities, or crashes. Testing validation means providing bad input, in many forms, and asserting that it is rejected, with the right error, and without side effects. That sounds straightforward, but validation has many forms of badness, and thorough testing requires thinking adversarially, like someone trying to break your system, not just like a user making a typo.

The forms of bad input to test include: missing fields, empty values, wrong types, such as a string where a number is expected, values out of range, such as a negative age or a percentage over one hundred, values with forbidden characters, such as a name with code in it, and values that are too long, which might overflow storage or cause performance problems. Each form should be tested, because each can cause a different failure if validation misses it. A validation function that checks for empty values but not for wrong types will accept a string where a number is expected, and downstream code may crash or behave strangely. Thorough validation testing probes each dimension separately, so that a gap in any one is caught.

Validation testing also needs to check the error response, not just rejection. A rejected request should return an appropriate status, such as 400 for bad input, and a message that helps the user fix the problem, such as "email is required" or "age must be a positive number", rather than a cryptic or generic error. Testing the message matters, because a message that says "error" does not help a user who mistyped, while a specific message does. It also matters for API clients, which may parse error messages or codes to decide what to do next. A validation test that only checks rejection, without checking the message, misses half the contract.

There is also a security dimension to validation testing, which connects to the security chapter. Validation is a defence against malicious input, such as code injection, oversized payloads, or attempts to access data through crafted parameters. Testing validation defensively means trying inputs that an attacker might try, within safe, authorised testing, and asserting they are rejected. That defensive testing does not require exploit techniques for systems you do not control, which this book does not teach, but it does require thinking about what malicious input looks like for your own system, and ensuring your validation rejects it. A validation test suite that includes adversarial cases is a security asset, not just a correctness asset.

Finally, validation tests should be maintained as validation rules change. When a new rule is added, a test for that rule should be added at the same time. When a rule changes, such as a length limit increasing, the boundary tests should be updated to probe the new boundary. Validation rules are part of your system's contract with users, and tests are how that contract is verified. A suite that drifts from the rules it checks gives false confidence.

# Validation testing: each form of bad input, rejected with a clear error.
def validate_age(age):
    if not isinstance(age, int) or age < 0:
        raise ValueError("age must be a non-negative number")
    return True

for bad in [-1, "old", None]:
    try:
        validate_age(bad)
        assert False, f"should have rejected {bad!r}"
    except ValueError:
        pass
print("Validation tests passed: bad ages rejected")

Check: Why should validation tests check the error message, not just that the input was rejected?

Section 20: Testing Authentication and Authorisation

Authentication, proving who you are, and authorisation, proving what you are allowed to do, are the most security-critical parts of a back-end system, and they deserve thorough testing, because a bug here can expose private data or allow unauthorised actions. Testing authentication and authorisation means checking, for each protected endpoint and action, that the right users are allowed, and the wrong users are denied, with the right errors, and without leaking information. That testing is not just about correctness. It is about security, and it should be approached with the same adversarial thinking as validation testing.

For authentication, test the main cases: valid credentials succeed, invalid credentials fail, missing credentials fail, expired tokens fail, and malformed tokens fail. Each case should assert the correct status, such as 401 for unauthenticated, and that no data is returned on failure. A common bug is returning data, or a different error, that reveals whether a username exists, which helps attackers enumerate accounts. Testing that authentication failures return the same generic response, regardless of whether the username or the password was wrong, catches that information leak. Another common bug is accepting expired tokens, or tokens for a different purpose, such as using a password reset token as a login token, which testing with expired and mismatched tokens will catch.

For authorisation, test the matrix of users and resources. For each protected resource, test that its owner can access it, that another user cannot, that an administrator can if appropriate, and that an anonymous user cannot. That matrix is the core of authorisation testing, and it should be applied to every endpoint, not just the obviously sensitive ones, because authorisation bugs often hide in less obvious places, such as a list endpoint that returns all users' data, or an update endpoint that does not check ownership. A test that creates two users, each with their own tasks, and asserts that each can only see and modify their own, catches the most common and most serious authorisation bug: missing ownership checks.

Authorisation tests should also check side effects on denial. A denied request should not change data, should not send notifications, and should not reveal data in its error message. For example, an attempt to delete another user's task should return an error and leave the task intact, not delete it and then report an error, or report success. Testing the state after a denied request, not just the response, catches bugs where authorisation is checked too late, after the action has already happened, which is a serious flaw that a response-only check would miss.

Finally, test authentication and authorisation after changes to those systems, and after changes to endpoints, because authorisation is easy to break accidentally, such as by adding a new endpoint without protection, or by refactoring a handler and dropping a check. A suite that covers authorisation for every endpoint, run after every change, is a safety net for security, catching regressions before they reach production. Security testing is not a one-time audit. It is a continuous practice, embedded in the test suite, so that every change is checked for the security properties users depend on.

# Authorisation matrix: owners allowed, others denied, state unchanged.
tasks = {"ada": ["Finish report"], "ben": ["Buy milk"]}

def can_access(user, owner):
    return user == owner

assert can_access("ada", "ada") is True
assert can_access("ben", "ada") is False
assert tasks["ada"] == ["Finish report"]  # denied access changed nothing
print("Authorisation tests passed")

Check: Why should authorisation tests check the state after a denied request, not just the error response?

Section 21: Testing Database Code

Database code is the code that reads, writes, updates, and deletes data, and testing it means verifying that those operations do exactly what they should, with the right data, under the right conditions. Database tests use a test database, as covered earlier, so they can run safely and repeatedly, and they follow a pattern: set up known data, call the code, and query the database to check the result. That pattern applies to every database operation, and mastering it gives you confidence about the part of your system where bugs cause the most lasting harm, because bad data persists long after a bug is fixed, while a bad response is forgotten as soon as the next request succeeds.

Testing reads means verifying that queries return the right rows, in the right order, for the right filters. Insert a few known rows, call the read function with different filters, and assert the returned rows match expectations, including order and count. Pay attention to empty results: a query that should return nothing for a filter with no matches should return an empty list, not an error, and not rows it should not return. Also test that reads do not modify data, which sounds obvious, but a read function with a bug might accidentally update a timestamp or a counter, and only a test that checks the data after a read will catch it. Reads should be pure in effect, even if they are not pure functions, and tests should verify that.

Testing writes means verifying that inserts, updates, and deletes change the database exactly as intended, and no more. For an insert, check the new row exists with the right values, and that no other rows were affected. For an update, check the target row changed, and that other rows did not. For a delete, check the target row is gone, and that other rows remain. Those "and no more" checks matter, because a write bug that affects the wrong rows, such as an update without a proper filter that updates every row, is catastrophic, and only a test that checks unaffected rows will catch it. Always assert on neighbours as well as targets, for write tests.

Testing constraints and errors is equally important. If a table has a unique constraint on email addresses, test that inserting a duplicate fails, with the expected error, and that the database is unchanged afterwards. If a foreign key requires a valid user, test that inserting a task for a non-existent user fails. Those constraint tests verify that your schema protects your data, not just that your code usually writes correctly, because code can have bugs, but constraints are a second line of defence, and they should be tested as such. A constraint that is missing, or that is not enforced because it was not enabled, will only be discovered by a test that tries to violate it.

Finally, test database code in isolation from production data. Tests should create their own schema matching production, and never depend on data in a shared database, because that data changes, and tests depending on it will fail unpredictably. Fresh, known, minimal data per test is the rule, and it is what makes database tests reliable and fast, for SQLite at least.

import sqlite3, unittest

# Write tests check the target row AND that neighbours were not affected.
class TestDbWrites(unittest.TestCase):
    def setUp(self):
        self.db = sqlite3.connect(":memory:")
        self.db.execute("CREATE TABLE tasks (id INTEGER PRIMARY KEY, title TEXT)")
        self.db.execute("INSERT INTO tasks VALUES (1, 'Keep me')")
        self.db.execute("INSERT INTO tasks VALUES (2, 'Change me')")

    def test_update_only_target(self):
        self.db.execute("UPDATE tasks SET title='Changed' WHERE id=2")
        rows = self.db.execute("SELECT title FROM tasks ORDER BY id").fetchall()
        self.assertEqual(rows, [("Keep me",), ("Changed",)])

Section 22: Testing CRUD Operations

CRUD stands for Create, Read, Update, and Delete, the four basic operations on stored data, and testing CRUD means testing each of those operations, for a resource, as a coherent set, because they interact: a create must produce data that read can find, an update must change what read returns, and a delete must remove what read would have found. Testing CRUD operations individually is necessary, but testing them as a lifecycle, create then read then update then read then delete then read, verifies that the operations agree with each other, which is a property individual tests can miss, such as a create that stores data in a format read cannot parse.

Start with create. Test that creating with valid data succeeds, returns the created item with its id, and that the item can then be read. Test that creating with invalid data fails, with a validation error, and creates nothing. Those two tests, valid create and invalid create, cover the entry point to your data, and they are the foundation for the rest, because every other operation depends on data created correctly. If create is buggy, read, update, and delete tests will fail in confusing ways, so getting create right, and tested, first, saves diagnostic time later.

Next, test read, in its forms: reading a single item by id, and listing items, possibly with pagination and filters, covered in the next section. For a single read, test that an existing item is returned correctly, and that a non-existent id returns a not-found error, not an empty success or a crash. For a list, test that it returns the created items, that it returns an empty list when there are none, not an error, and that it respects ownership, returning only the requesting user's items. Those read tests verify the most common operation, and they catch the most common read bugs: missing not-found handling, leaking other users' data, and crashing on empty results.

Next, test update. Test that updating an existing item with valid data changes it, and that a subsequent read shows the change. Test that updating with invalid data fails and leaves the original unchanged. Test that updating a non-existent item returns not-found, and creates nothing, because an update that silently creates is a bug, not a feature, unless upsert behaviour is explicitly intended and documented. And test that updating one user's item as another user is denied, and leaves the item unchanged, which is the authorisation check from earlier, applied to updates specifically, where it is easy to forget.

Finally, test delete. Test that deleting an existing item removes it, and that a subsequent read returns not-found. Test that deleting a non-existent item returns not-found, not success, because reporting success for a delete that deleted nothing is misleading. Test that deleting one user's item as another user is denied, and leaves the item intact. And test that deleting cleans up related data appropriately, according to your design, such as removing dependent rows or leaving them, but never leaving orphaned data that breaks other operations. A CRUD test set that covers create, read, update, and delete, with valid, invalid, missing, and unauthorised cases for each, is a thorough verification of a resource's data lifecycle, and it is a pattern you can repeat for every resource in your application.

# CRUD lifecycle: create, read, update, read, delete, read.
store = {}

def create(item_id, title):
    store[item_id] = title

def read(item_id):
    return store.get(item_id)

def update(item_id, title):
    if item_id in store:
        store[item_id] = title

def delete(item_id):
    store.pop(item_id, None)

create(1, "First")
assert read(1) == "First"
update(1, "Second")
assert read(1) == "Second"
delete(1)
assert read(1) is None
print("CRUD lifecycle passed")

Section 23: Testing Pagination, Filtering and Sorting

Pagination, filtering, and sorting are features that change which items a list returns, and in what order, and testing them means verifying those transformations precisely, because bugs here are subtle: a list that returns the wrong page, or the wrong order, or ignores a filter, looks almost right, and users may not notice immediately, but they will lose trust when they cannot find items they know exist, or when pages repeat or skip items. Testing lists therefore requires careful, small datasets where the expected result for each page, filter, and sort is known exactly, and can be asserted exactly.

For pagination, test with a known number of items, such as five, and a page size of two, so the pages are: page one has items one and two, page two has items three and four, page three has item five, and page four is empty. Assert each page's contents, not just its size, because a pagination bug that returns the right number of wrong items will pass a size-only check. Also test that pages do not overlap and do not skip: collecting all pages should give all items, exactly once, in order. That completeness check catches off-by-one errors in offset calculations, which are the most common pagination bugs. And test invalid pages, such as page zero or a negative page, asserting a clear error or a sensible default, according to your design, but never a crash or a misleading result.

For filtering, test each filter separately and in combination. If a list can be filtered by status and by owner, test status alone, owner alone, and both together, with data that distinguishes them, so you can tell whether each filter was applied. A filter test needs data where the filters disagree: an item matching one filter but not the other, so that a test asserting only matching items will fail if a filter is ignored. Without such distinguishing data, a test can pass even when filtering is broken, because all items happen to match. Design filter test data adversarially, with items that match each combination differently, so the test truly verifies the filter logic.

For sorting, test each sort field and direction, with data where the order is unambiguous and where ties occur. If sorting by date, use distinct dates, so the expected order is clear, and also test items with the same date, to verify the tie-break behaviour, such as a secondary sort by id, or a stable order. Assert the full ordered list, not just that the list is sorted, because a list can be sorted by the wrong field and still be sorted, in some sense, while being wrong for the requested field. Full-order assertions are the only way to be sure the requested sort was applied.

Finally, test pagination, filtering, and sorting together, because they interact: a filter changes which items are paginated, and a sort changes their order before pagination slices them. A test that filters, sorts, and paginates in one request verifies the pipeline as a whole, which is where integration bugs hide, such as sorting after pagination instead of before, producing pages that are individually sorted but globally out of order.

# Pagination test data: 5 items, page size 2, pages must not overlap or skip.
items = ["a", "b", "c", "d", "e"]

def page(items, number, size):
    start = (number - 1) * size
    return items[start:start + size]

assert page(items, 1, 2) == ["a", "b"]
assert page(items, 2, 2) == ["c", "d"]
assert page(items, 3, 2) == ["e"]
assert page(items, 1, 2) + page(items, 2, 2) + page(items, 3, 2) == items
print("Pagination tests passed")

Section 24: Testing Error Responses

Error responses are part of your API's contract, just as success responses are, and they deserve the same thorough testing, because clients depend on them to understand what went wrong and what to do next. An error response typically includes a status code, an error code or type, and a human-readable message, and each part should be tested: the status should be appropriate, such as 400 for bad input, 401 for unauthenticated, 403 for forbidden, and 404 for not found; the error type should be consistent, so clients can handle it programmatically; and the message should be clear and helpful, without leaking sensitive information, such as internal details or other users' data.

Testing error responses starts with triggering each error condition and asserting the full response. For a not-found error, request a non-existent id and assert 404, not 200 with an empty body, and not 500, which would indicate a crash rather than a handled error. For a validation error, send invalid data and assert 400, with a message naming the problem field, and with no side effect, such as no row created. For an authentication error, request without credentials and assert 401, with a generic message that does not reveal whether the resource exists. Each error test is a small, precise check, and together they verify that your API fails gracefully and informatively, rather than crashing or misleading clients.

There are also error response properties that are easy to overlook. Error responses should have a consistent shape, so clients can parse them reliably: if success responses are JSON objects with certain fields, error responses should be JSON objects with a predictable error structure, not plain text, not HTML, and not a different shape per endpoint. Testing that shape, by asserting the presence and types of error fields, catches inconsistencies that would break clients. Error responses should also not include stack traces or internal details in production, because those leak implementation information that attackers can use, and because they confuse users. Testing that production error responses are clean, without tracebacks, is a security check as well as a correctness check.

Another important error test is for unexpected errors: what happens when code raises an exception that was not anticipated? A well-designed API catches unexpected exceptions and returns a generic 500 error, with a safe message, while logging the details for developers. Testing that behaviour, by triggering an unexpected error in a test, and asserting a clean 500 response, verifies that your error handling does not leak, and that it does not crash the server. An API that returns a raw traceback for unexpected errors is an API with a security and reliability problem, and only a test that triggers such an error will reveal it.

Finally, error response tests should be maintained as error handling changes. When a new error condition is added, such as a rate limit, a test for its response should be added too. When an error message is improved, its test should be updated. Error responses are promises to clients, and tests are how promises are kept. A suite that thoroughly tests errors gives clients confidence that they can handle failures.

# Error responses: right status, clear message, consistent shape, no leaks.
def get_task(task_id, tasks):
    if task_id not in tasks:
        return {"status": 404, "error": "not_found",
                "message": "Task not found"}
    return {"status": 200, "task": tasks[task_id]}

response = get_task(99, {1: "Finish report"})
assert response["status"] == 404
assert response["error"] == "not_found"
assert "traceback" not in str(response)
print("Error response test passed")

Section 25: Testing with Fake Data and Fixtures

Fake data, and fixtures, are the test data and setup helpers that make tests repeatable, readable, and independent. A fixture is a known set of data, or a setup function, that prepares a test's environment: a user, a few tasks, a category, in a known state, so the test can act and assert without building everything from scratch each time. Fake data is data that looks realistic but is invented for tests, such as test users with names like Ada and Ben, and tasks with clear titles, rather than real user data, which must never be used in tests, for privacy and reliability reasons. Together, fixtures and fake data are the foundation of maintainable tests.

The value of fixtures is in reducing repetition without hiding meaning. Without fixtures, every test repeats the same setup: create a user, create tasks, set up categories, and tests become long and hard to read, with setup obscuring the behaviour being tested. With fixtures, setup is extracted into a helper or a setUp method, and each test starts with a known, named state, such as "a user with three tasks, one done, two pending", and the test itself focuses on the action and assertion. That clarity makes tests easier to write, easier to read, and easier to debug, because the starting state is explicit and consistent across tests.

Fixtures must be designed carefully to avoid coupling tests together. A fixture that is shared and mutated by tests will cause tests to interfere, because one test's changes affect the next test's starting state. The safe pattern is fresh fixtures per test: each test gets its own copy of the data, created in setup, and discarded in teardown, so tests are independent. Shared fixtures are acceptable only for read-only data that tests never modify, such as a list of categories, and even then, caution is needed, because a test that accidentally modifies shared data will break others in confusing ways. Fresh per test is the default. Shared is the exception, for read-only data, with clear documentation.

Fake data should be realistic but obviously fake, so it cannot be confused with real data, and so failures are readable. Names like Ada, Ben, and Chi, emails like ada@example.com, using the reserved example domain, and titles like "Finish report", are clear, realistic, and safe. Avoid real-looking data that could be mistaken for production data, and avoid random data that changes on every run, because random data makes failures hard to reproduce: a test that fails once with random data, and passes on rerun with different data, is a flaky test, and flakiness destroys trust. If random data is needed, seed it, so it is repeatable, or use fixed, varied values that cover the cases you need, deterministically.

Finally, fixtures should evolve with your system. When a new field is added, fixtures creating that kind of data should be updated to include it. When a fixture becomes complex, consider a factory helper, a function that creates a valid object with sensible defaults, allowing tests to override only the fields they care about. Factories reduce setup noise while keeping tests explicit about what matters. That balance is worth investing in, because fixtures are used by every test.

# A fixture: known test data, fresh per test, obviously fake.
def make_user_with_tasks():
    return {"user": "ada@example.com",
            "tasks": [{"title": "Finish report", "done": True},
                      {"title": "Buy milk", "done": False}]}

data = make_user_with_tasks()
assert len(data["tasks"]) == 2
print("Fixture ready: user with 2 tasks, 1 done")

Check: Why should fixtures be fresh per test, rather than shared and mutated across tests?

Section 26: Mocks and Fakes in Plain Words

When testing code that depends on something else, such as a database, an outside service, or the current time, you often need a stand-in for that dependency, so the test can run quickly, reliably, and without side effects. Two common kinds of stand-in are mocks and fakes, and they are often confused, so this section distinguishes them clearly. A fake is a simplified, working implementation of a dependency, such as an in-memory database standing in for a real database, or a fake mail sender that records messages instead of delivering them. A fake works, it just works more simply, and it can be used in place of the real thing for testing. A mock is a programmable object that records how it was called, and returns scripted answers, without implementing real behaviour, such as an object that pretends to be a mail service, records that it was called with a certain address, and returns success, without sending anything.

Fakes are generally preferred when a simple working implementation exists, because they test more real behaviour. An in-memory database fake tests real query logic, not just that a query function was called. A fake mail sender tests that your code builds the right message, because the fake records it and the test can inspect it. Fakes are more work to build than mocks, but they give higher confidence, because they exercise more of the real interaction. For common dependencies, fakes already exist: in-memory databases, fake file systems, fake clocks, and fake mail servers, all of which you have met or will meet in this chapter. Use them where they exist, before building your own.

Mocks are useful when a fake is impractical, or when the point of the test is to verify interaction, not behaviour. To test that your code calls a payment service exactly once, with the right amount, a mock that records calls is the direct tool, because a fake payment service would need to implement payment logic, which is unnecessary for that test. Mocks are also useful for simulating failures: a mock can be scripted to raise an error, so you can test how your code handles it, without needing a real service to fail on demand.

Mocks have a danger: they test your code's interaction with the mock, not with the real dependency, so if your understanding of the real dependency is wrong, the mock will reproduce your misunderstanding, and the test will pass while the real system fails. That is called over-mocking, and it happens when mocks are used for everything, or when mock expectations mirror internal implementation rather than observable behaviour. The antidote is to mock sparingly, at system boundaries, and to prefer fakes for your own components.

In Python, the unittest.mock module provides mocks, with tools to create mock objects, script their returns, and assert how they were called. Learning its basics, such as Mock and patch, which temporarily replaces a real object with a mock during a test, is worthwhile, because mocks are a standard tool. But remember the guideline: fakes where possible, mocks where necessary, and always ask whether the test verifies real behaviour or just your own imagination of a dependency.

from unittest.mock import Mock

# A mock records calls and returns scripted answers, without real behaviour.
mail_service = Mock()
mail_service.send.return_value = True
mail_service.send("ada@example.com", "Welcome")
mail_service.send.assert_called_once_with("ada@example.com", "Welcome")
print("Mock verified: mail service called exactly once, with the right arguments")

Section 27: Mocking Outside Services

Outside services, such as mail providers, payment services, and maps, are the dependencies most commonly mocked in back-end tests, because real calls to them are slow, unreliable, potentially costly, and potentially harmful, such as sending real emails or charging real money. Mocking an outside service means replacing it, in tests, with a stand-in that returns scripted responses, records calls, and simulates failures, so your code can be tested thoroughly without ever touching the real service. That replacement is essential for a fast, reliable test suite, and it is a standard practice in every serious back-end project.

The first step is to make the outside service replaceable. Code that calls an outside service directly, with a hard-coded client created inside the function, is hard to mock, because the test cannot substitute a stand-in. Code that receives its service client as a parameter, or that accesses it through a module-level object that can be patched, is easy to mock, because the test can pass a mock, or patch the object, before calling the code. That design choice, dependency injection, passing dependencies in rather than creating them internally, is a recurring theme in testable design, and it applies to databases, mail services, and every other dependency. Testable code is code whose dependencies can be substituted, and substitution starts with design, not with test tricks.

Once replaceable, the service can be mocked in several ways. The simplest is to pass a mock object directly, if the code receives its client as a parameter. The mock can be scripted to return success, or to raise an error, and the test can assert it was called with the right arguments. Another way is to use unittest.mock.patch, which temporarily replaces a real object, such as a module's client, with a mock, for the duration of a test, and then restores it. Patching is powerful, but it should be used carefully, because patching the wrong target, such as patching where a thing is defined rather than where it is used, is a common source of confusion, and a mock that does not actually replace the real call will let the real service be called, defeating the purpose.

What should you test with a mocked outside service? First, that your code calls the service correctly: with the right arguments, at the right time, and the right number of times. Second, that your code handles the service's responses correctly: success, failure, and edge cases such as a rate limit error, each scripted by the mock. Third, that your code handles the service being unavailable, by retrying, falling back, or failing gracefully. Those three cover the interaction thoroughly, and they catch most integration bugs with outside services.

Finally, remember that mocked service tests verify your code's interaction with your understanding of the service, not with the service itself. If the service's API changes, your mocks will not know, and your tests will pass while real calls fail. That gap is why mocked tests should be complemented, occasionally, with real checks, such as a manual test against a sandbox environment, or a small set of live tests run infrequently. Mocks give speed for everyday testing. Occasional real checks confirm your understanding is still correct.

from unittest.mock import Mock

# Mock an outside mail service: script success, verify the call, no real mail sent.
def signup(email, mail_service):
    mail_service.send(email, "Welcome")
    return "account created"

mock_mail = Mock()
mock_mail.send.return_value = True
assert signup("ada@example.com", mock_mail) == "account created"
mock_mail.send.assert_called_once_with("ada@example.com", "Welcome")
print("Outside service mocked: signup tested without sending real mail")

Check: Why must code receive its outside service client as a parameter, or through a patchable object, for mocking to work?

Section 28: Mocking Time and Randomness

Time and randomness are dependencies that make tests unreliable if not controlled, because they change on every run. A test that checks a token expiry, by waiting for real time to pass, will be slow. A test that checks a random token, by asserting its exact value, will fail, because the value differs every time. Mocking time and randomness means replacing them, in tests, with controlled stand-ins: a fake clock that you can set to any time, and a fake random generator that returns predictable values, or a seed that makes randomness repeatable. That control turns flaky, slow tests into fast, reliable ones, and it is essential for testing any code that depends on time or chance.

For time, the most common need is to test expiry, scheduling, and time-based logic, such as whether a token is expired, whether a reminder is due, or whether a cache entry is stale. Those tests should not wait for real time, which would make them slow, nor should they depend on the actual current time, which makes them fragile, because a test that passes at noon might fail at midnight, if it crosses a boundary. The solution is to inject time, by passing a clock function or a current-time value into the code, rather than calling the system clock directly inside it, so tests can pass a fake time. A fake clock can be as simple as a variable holding a fixed time, plus a function to advance it, giving tests full control over what "now" means.

For randomness, the most common need is to test code that generates tokens, ids, or random selections, where the exact value does not matter, but its properties do, such as its length, its format, or its uniqueness. Tests for random code should assert properties, not exact values: a token should be a certain length, should contain only allowed characters, and two tokens should differ, rather than asserting a token equals a specific string. When exact values are needed, such as for a deterministic algorithm that uses randomness internally, seeding the random generator with a fixed seed makes its output repeatable, so tests can assert exact values reliably. Python's random module supports seeding, and that feature exists precisely for reproducible testing.

There is a design lesson here, similar to mocking services: code that calls the system clock or the random generator directly, deep inside a function, is hard to test, because the test cannot control those calls. Code that receives time or randomness as parameters, or through a small, replaceable helper, is easy to test, because the test can substitute fakes. That design, injecting volatile dependencies, is a hallmark of testable code.

Finally, be careful not to over-mock time and randomness in a way that hides real bugs. A fake clock that never advances might hide a bug where code assumes time always moves forward. A seeded random generator might hide a bug that only appears with certain random values. Use fakes to control what you need, but also include tests with realistic variation, such as advancing a fake clock through several boundaries, or generating many tokens and checking their properties. Controlled does not mean trivial.

# Fake time: the test controls "now", so expiry tests are fast and reliable.
from datetime import datetime, timedelta

def is_expired(expires_at, now):
    return now > expires_at

now = datetime(2026, 10, 31, 12, 0, 0)
assert is_expired(now - timedelta(hours=1), now) is True
assert is_expired(now + timedelta(hours=1), now) is False
print("Time tests passed with a controlled clock")

Check: Why should tests for random tokens assert properties like length, rather than exact values?

Section 29: Testing Email Without Sending Mail

Testing email features without sending real mail is a problem you met in the email chapter, and it has a testing solution that fits naturally here: use a fake mail sender in tests, which records messages instead of delivering them, so tests can verify what would have been sent, without any message leaving the test environment. That approach is safe, fast, and precise, and it is the standard way to test email in back-end systems, where real delivery would be slow, unreliable, and potentially harmful, if test messages reached real users by mistake.

The fake sender pattern is simple. Your email-sending code should accept a sender object, or use a sender that can be replaced in tests, following the dependency injection principle from earlier. In production, that sender is the real mail service. In tests, it is a fake, which is often just a list, or a small class with a send method that appends the message to a list and returns success. After calling the code under test, the test inspects the list: how many messages were recorded, who they were addressed to, what their subjects were, and whether their bodies contain expected content, such as a confirmation link or a user's name. Those assertions verify the email logic thoroughly, without any network or delivery involved.

Fake senders also let you test failure handling. A fake can be scripted to raise an error on send, simulating a mail server failure, so you can test that your code retries, logs the failure, or reports it correctly, without needing a real server to fail on demand. A fake can also be scripted to record a bounce, or to be slow, so you can test timeout and retry logic. That failure simulation is difficult with real mail, and easy with fakes, which is another reason fakes are preferred for email testing. A test suite that only tests successful sends, and never tests failures, leaves the failure paths unverified, and failure paths are where email bugs most often hide, such as a signup that crashes when mail fails, instead of succeeding with a queued retry.

There are also integration-level email tests, which verify the full path from a user action to a recorded message, using the fake sender. For example, a test might sign up a user through the API, with the fake sender in place, and then assert that exactly one welcome message was recorded, addressed to the new user, with the right subject. That test covers the wiring, from endpoint to email logic to sender, which unit tests of the email function alone would miss, such as a handler that forgets to trigger the email, or triggers it twice. Integration tests with fakes give you that wiring confidence, at low cost, because fakes are fast and reliable.

Finally, keep email test data obviously fake, using example domains and test names, so that even if a configuration mistake caused a real send, the damage would be limited, though the goal is to make real sends impossible in tests, by configuration. Separate test and production mail settings, use fakes by default in tests, and never use production credentials in test code. Those safeguards make email testing safe, which allows you to test it thoroughly, without fear.

# Fake mail sender: records messages, delivers nothing, test inspects the record.
class FakeSender:
    def __init__(self):
        self.sent = []

    def send(self, to, subject, body):
        self.sent.append({"to": to, "subject": subject, "body": body})
        return True

sender = FakeSender()
sender.send("ada@example.com", "Welcome", "Hello Ada!")
assert len(sender.sent) == 1
assert sender.sent[0]["to"] == "ada@example.com"
print("Email test passed: message recorded, nothing really sent")

Section 30: Testing Background Jobs

Background jobs, which you learned about in the email and jobs chapter, need testing that accounts for their asynchronous nature: they do not run immediately, in response to a request, but later, picked up by a worker, possibly with retries and delays. Testing jobs therefore means testing three things: that jobs are queued correctly, that job handlers do the right work, and that the worker system handles retries, failures, and scheduling correctly. Each of those can be tested separately, and together they give confidence about a part of the system that is invisible to users until it fails.

Testing queuing means verifying that a user action, or a system event, creates the right job, with the right type, payload, and scheduled time, in the jobs table or queue. That test does not run the job. It checks that the job was recorded correctly, by inspecting the queue after the action, and asserting the job's fields. For example, signing up should queue a welcome email job, with the new user's address, and creating a task with a deadline should queue a reminder job, scheduled for the day before. Queuing tests catch bugs where jobs are forgotten, duplicated, or created with wrong data, which are common and consequential, because a forgotten job means a feature silently does not happen.

Testing handlers means testing the function that does a job's work, in isolation, with a known job payload, and checking its effect, just like any other function test. For an email job handler, pass a job with a recipient and subject, run the handler with a fake sender, and assert the message was recorded correctly. For a report job handler, pass a job with parameters, run it, and assert the report was created with the right content. Handler tests are unit tests, fast and precise, and they cover the job's logic, which is where most job bugs live, such as incorrect message content, wrong calculations, or missing error handling.

Testing worker behaviour means testing the loop that picks jobs, runs them, and handles outcomes. That includes: claiming a job before running it, so it is not run twice; marking it done on success; incrementing attempts and retrying on temporary failure, with backoff; and moving it to dead letters after maximum attempts, on permanent failure. Those behaviours can be tested with a test queue and fake handlers, by running one worker pass and asserting the job's resulting status and attempt count. Worker tests are integration tests, slightly slower than handler tests, but they cover the reliability machinery that makes jobs trustworthy, and they catch bugs such as jobs that are marked done before they finish, or that retry forever.

Finally, test scheduling and timing with fake clocks, so delayed and recurring jobs can be tested without waiting. A reminder job scheduled for tomorrow should not run today, and should run tomorrow, and a fake clock lets you verify both, by setting "now" to today and to tomorrow in turn. That time control is essential for job testing, because real-time job tests would be slow and flaky.

    jobs.append({"type": "send_email", "to": to, "status": "pending"})

def run_job(job, sender):
    sender.append(job["to"])
    job["status"] = "done"

sent = []
queue_email("ada@example.com")
run_job(jobs[0], sent)

print("Job test passed: queued, run, and recorded")

Section 31: Testing Caching Behaviour

Caching behaviour, which you learned about in the caching chapter, needs tests that verify the cache itself, not just the underlying logic, because a function can return the right answer while its cache is broken, for example by never storing, by storing under the wrong key, or by serving stale data. Testing caching means checking hits, misses, expiry, and invalidation, each with a controlled setup, so you can tell whether the cache helps or harms. Those tests are what give you confidence that caching is an optimisation, not a source of bugs, and they are worth writing for every cache you add.

Testing hits and misses starts with counting. Call a cached function twice with the same inputs, and verify that the underlying work was done once, not twice, by counting calls to the slow source, or by checking a hit counter, if your cache exposes one. Then call it with different inputs, and verify the work was done again, because a different input should miss. Those two checks, same input hits, different input misses, verify the basic cache contract, and they catch the most common caching bugs: keys that change on every call, so nothing ever hits, and keys that ignore an input, so different inputs wrongly hit. Both bugs are serious, and both are caught by simple counting tests.

Testing expiry means verifying that an entry stops being used after its lifetime. With a fake clock, or a very short TTL in the test, store an entry, advance time past its expiry, and call the function again, verifying the underlying work was done again, because the entry should have expired. Without a fake clock, you can use a TTL of zero, or a tiny TTL with a brief wait, though waiting makes tests slow and slightly flaky, so a fake clock is preferred where your cache supports injecting time. Expiry tests catch TTL bugs, such as lifetimes in the wrong unit, or entries that never expire, which would serve stale data forever.

Testing invalidation means verifying that changing data clears the affected entries. Update the underlying data, trigger the invalidation your code should perform, and call the function again, verifying fresh data is returned, not the old cached copy. Also test the negative: changing unrelated data should not invalidate the entry, so a subsequent call still hits, because over-invalidation, clearing too much, hurts performance, even if it does not cause incorrectness. Invalidation tests are where caching bugs most often hide, because invalidation logic is easy to forget for one data path, and a test that changes data through each path and checks freshness will catch those omissions.

Finally, test caching with multiple users and with personalised data, to verify keys include the user where they should. Call a cached function for two users, and assert each gets their own result, not the other's. That test catches the dangerous key bug from the caching chapter, where private data leaks through a shared key, and it should be part of every test suite for cached personalised data. Caching tests, covering hits, misses, expiry, invalidation, and key correctness, turn a cache from a hope into a verified optimisation, and they are cheap to write compared to the debugging cost of a caching bug discovered in production.

# Caching test: same input hits once, different input misses, expiry refetches.
calls = []

def slow_source(key):
    calls.append(key)
    return f"value-{key}"

cache = {}

def cached_get(key):
    if key not in cache:
        cache[key] = slow_source(key)
    return cache[key]

cached_get("a")
cached_get("a")
cached_get("b")
assert len(calls) == 2, calls  # "a" computed once, "b" once
print("Caching tests passed: hits, misses, and counting verified")

Section 32: Testing Logging Output

Logging output deserves testing, because logs are part of your system's behaviour, and because a log line that is missing, vague, or contains a secret is a bug, just as a wrong response is. Testing logging means capturing what your code logs, during a test, and asserting that the expected lines appear, with the expected level and content, and that forbidden content, such as secrets, does not appear. That testing is straightforward in Python, because the logging module lets you attach a test handler that records lines in memory, which the test can then inspect, without writing to files or terminals.

The most useful logging tests check that important events are logged. When a user signs up, is an info line recorded? When an email fails, is an error line recorded, with the recipient and the reason? When a job fails permanently, is it logged as an error, with its id and attempt count? Those tests verify that your logging covers the events you care about, which is important because a missing log line during an incident is a missing clue, and it is easy for a code change to accidentally remove a log call, or to change its level, without anyone noticing, unless a test checks for it. Logging tests make logging a verified feature, not a hopeful habit.

Logging tests should also check levels. An error should be logged as an error, not as info, because level determines whether it appears in production logs, whether it triggers alerts, and whether it can be filtered during investigation. A test that captures logs and asserts the level of a specific line catches level mistakes, such as logging a critical failure as debug, which would hide it in production, or logging routine events as errors, which would create noise. Level tests are cheap, because they use the same captured lines, with an extra assertion on level, and they enforce the level discipline from the logging chapter.

Another valuable logging test checks that secrets are not logged. Call a function that handles a password or token, capture its logs, and assert that the secret value does not appear in any line. That test is a safety net for the no-secrets rule, because it catches accidental logging of sensitive data, such as logging a whole request object that includes a password, before it reaches production. It is a simple test to write, and it protects against a serious class of incident, which makes it one of the highest-value tests per line of code you can write. Add it for every function that handles secrets, and run it on every change to that function.

Finally, keep logging tests focused and tolerant. Assert on the important parts of a line, such as its level, its key identifiers, and its message's core content, not on its exact formatting, including timestamps, which change on every run and would make tests brittle. A test that asserts an exact log line will fail every time, for the wrong reason. Logging tests should verify behaviour, not formatting, unless formatting itself is being tested, such as a structured log's JSON fields, which should be asserted as fields, not as exact text.

            log = logging.getLogger("taskday")
            log.error("Failed to send email to ada@example.com")
        self.assertIn("ada@example.com", captured.output[0])

Section 33: Test Isolation: Tests That Do Not Affect Each Other

Test isolation means that each test runs independently, unaffected by other tests, and without affecting them, so that tests can run in any order, alone or together, and give the same results. Isolation is a fundamental property of a trustworthy suite, because without it, a test's result depends on what ran before it, which makes failures hard to reproduce, hard to diagnose, and hard to trust. A test that passes alone but fails when run with others, or passes in one order but fails in another, is a test with an isolation problem, and isolation problems are among the most frustrating bugs in testing, because they make the suite itself unreliable.

The main threats to isolation are shared mutable state: global variables, shared databases, shared files, and shared external services, that one test modifies and another test reads. If test A creates a user named Ada, and test B counts users expecting zero, test B will fail when run after test A, but pass when run alone, which is confusing and misleading. The fix is fresh state per test: each test creates its own data, in setup, and cleans it up in teardown, so no test depends on another's leftovers. For databases, that means a fresh test database per test, or a transaction rolled back after each test. For files, it means a fresh temporary directory per test. For global state, it means resetting it in setup, or better, avoiding global mutable state in the code under test, by passing state as parameters.

Another threat is time and randomness, which make tests depend on when they run, or on chance, rather than on code. A test that depends on the current date will fail on some days and pass on others. A test that depends on random values will fail occasionally, for no code reason. Those are isolation failures in a broader sense: the test is not isolated from its environment. The fixes, covered earlier, are fake clocks and seeded or property-based randomness checks, which isolate the test from real time and chance, making its result depend only on the code being tested.

A third threat is order dependence through side effects, such as a test that changes configuration, or that starts a server on a fixed port, blocking the next test from doing the same. Configuration changes should be restored in teardown, or better, made per-test through parameters rather than globals. Servers should use free ports, chosen by the system, not fixed ports, so multiple tests can run without conflict. Those practices become more important as suites grow and tests run in parallel.

Finally, isolation should be verified, not assumed. Run your suite in different orders, run individual tests alone, and run tests in parallel if your setup supports it, and check that results are consistent. A suite that is truly isolated will pass in all those modes. A suite that is not will reveal its dependencies quickly, and those failures are valuable, because they point to hidden coupling that should be fixed, both in tests and in code.

# Isolation: each test gets fresh state, so order never matters.
import unittest

class TestIsolation(unittest.TestCase):
    def setUp(self):
        self.store = {}  # fresh per test, never shared

    def test_one(self):
        self.store["a"] = 1
        self.assertEqual(self.store, {"a": 1})

    def test_two(self):
        self.assertEqual(self.store, {})  # unaffected by test_one

Section 34: Order Independence

Order independence is the property that tests give the same results regardless of the order in which they run, and it is a direct consequence of isolation, worth its own section because it is a common failure mode with specific causes and fixes. A suite that is order-independent can be run in any order, in parallel, or in subsets, and its results will be consistent. A suite that is order-dependent will pass in the order its author ran it, usually the order tests were written, and fail in other orders, which is confusing, because the failure appears to be about the test, when it is really about hidden state shared between tests.

The most common cause of order dependence is shared data that is not reset. A test that inserts a row into a shared database, without cleaning it up, will affect the next test that counts rows, or that expects an empty table. A test that writes a file to a shared path, without deleting it, will affect the next test that checks that path. A test that modifies a global setting, without restoring it, will affect all subsequent tests. Each of these is a teardown failure, and the fix is the same: clean up in teardown, or use fresh resources per test, so that no test leaves anything behind. Teardown is not housekeeping. It is what guarantees order independence.

Another cause is tests that depend on each other intentionally, such as a test that creates data for a later test to use. That intentional dependence is a design mistake, even if it seems efficient, because it makes the suite fragile: the later test cannot run alone, cannot be understood alone, and will fail confusingly if the earlier test changes or is skipped. Each test should be self-contained, setting up its own data, even if that means repeating setup code, or extracting setup into a helper that each test calls. Repetition in setup is acceptable. Dependence between tests is not, because it couples tests in a way that makes the suite hard to maintain and hard to trust.

Order dependence can also arise from randomness or time, if tests share a random generator or depend on the current time in a way that interacts across tests, but those are less common than shared data causes, and they are fixed by the same isolation techniques. The general principle is that each test should be a closed world, with its own inputs, state, and assertions, never interacting with other tests through shared data or configuration.

To check for order independence, run your suite with tests in a shuffled order, if your framework supports it, or run tests in reverse, or run a single test file's tests in different orders, and compare results. Many frameworks support random ordering as an option, precisely to catch order dependence, and enabling it regularly, or in continuous integration, is a good practice, because it surfaces hidden coupling before it causes confusion in production debugging. A suite that passes shuffled is a suite you can trust, in any order, in any subset, and that trust is what makes a suite useful as a safety net, rather than a source of confusion.

# Order independence: no test depends on another test having run first.
import unittest

class TestOrder(unittest.TestCase):
    def test_a_creates(self):
        store = {"x": 1}
        self.assertEqual(store["x"], 1)

    def test_b_standalone(self):
        store = {}  # sets up its own data, needs nothing from test_a
        self.assertEqual(store, {})

Section 35: Flaky Tests and How to Fix Them

A flaky test is one that sometimes passes and sometimes fails, without any code change, and flaky tests are one of the most damaging problems a test suite can have, because they destroy trust. When a suite contains flaky tests, developers learn that failures might mean nothing, so they start ignoring failures, rerunning suites until they pass, and merging code despite red tests, which defeats the entire purpose of testing. A single flaky test can poison a whole suite's credibility, and fixing flakiness promptly, even at the cost of deleting a flaky test temporarily, is essential for maintaining trust.

Flakiness has a few common causes, each with a fix. The first is dependence on time: a test that waits a fixed amount of time for an asynchronous operation, and fails if the operation takes slightly longer on a slow machine, is flaky by design. The fix is to wait for a condition, with a timeout, rather than waiting a fixed time, or to use fake time and synchronous execution in tests, so timing is deterministic. The second is dependence on randomness or unordered data: a test that asserts an exact order for data that has no guaranteed order, such as rows from a database without an order clause, or items from a set, will fail when the order happens to differ. The fix is to sort before asserting, or to assert on sets rather than ordered lists, so the test checks what is guaranteed, not what happens to be true on one run.

The third cause is shared state and order dependence, where a test passes alone but fails with others. The fix is isolation: fresh state per test and proper teardown. The fourth cause is dependence on outside services or networks, where a test calls a real service that is sometimes slow or unavailable. The fix is to mock or fake outside services in tests. The fifth cause is resource contention, such as tests that use the same port or file and conflict when run in parallel. The fix is unique resources per test, such as free ports and temporary directories.

Fixing a flaky test starts with reproducing it. Run the test repeatedly, in isolation and with the suite, in different orders, until it fails, then investigate using the categories above as a checklist. Once the cause is found, fix it by making the test deterministic, not by weakening its assertions until it passes, which would hide the problem. If a flaky test cannot be fixed quickly, quarantine it: move it to a separate suite that does not block development, with a clear note that it needs fixing, rather than leaving it in the main suite to erode trust. Quarantine is temporary, and quarantined tests should be fixed or deleted promptly.

Finally, prevent flakiness by design. Write tests that are deterministic, isolated, fast, and independent of time, randomness, order, and outside services, from the start. Review new tests for flakiness risks, such as fixed waits and shared resources, before merging them. And track flakiness as a metric: count how often tests fail without code changes, and treat a rising flaky count as a quality problem to fix. A suite with no flaky tests is a suite developers trust.

# Flaky: asserting order where none is guaranteed. Fixed: sort first.
results = {"b", "a", "c"}  # a set has no guaranteed order
assert sorted(results) == ["a", "b", "c"]  # deterministic, not flaky
print("Deterministic test passed")

Section 36: Test Coverage: What It Means and What It Does Not

Test coverage is a measure of how much of your code is executed by your tests, usually expressed as a percentage of lines, branches, or functions covered. A coverage of 80 percent means your tests execute 80 percent of your code's lines, and do not execute the remaining 20 percent. Coverage is a useful metric, because it reveals untested code, which is code where bugs can hide unnoticed, and it guides you to write tests for the gaps. It is also a metric that is easy to misunderstand and misuse, so this section covers both its value and its limits, honestly.

The value of coverage is in finding gaps. If a critical function has 0 percent coverage, it has no tests, and that is a clear signal to add some. If a branch, such as an error handler, is never executed by tests, it might be dead code, or it might be an untested failure path that will fail in production. Coverage tools, which measure execution during test runs and report uncovered lines, make those gaps visible, with reports that highlight exactly which lines were missed. That visibility is coverage's main benefit: it turns "we should test more" from a vague feeling into a specific list of lines and branches to cover.

The limits of coverage are equally important. Coverage measures execution, not correctness. A test can execute a line without verifying its result, and that line will count as covered, even though a bug in it would not be caught. For example, a test that calls a function but asserts nothing about its output covers the function's lines, but proves nothing about its behaviour. That is why coverage must be read alongside assertion quality: high coverage with weak assertions gives false confidence, because the code is executed but not checked. A suite with 100 percent coverage and no assertions is a suite that proves nothing, despite its perfect number.

Coverage also does not measure whether the right cases were tested. A function with 100 percent line coverage might still have bugs for inputs that were never tried, because coverage counts lines executed, not inputs tested. A validation function tested only with valid input might cover all its lines, if the invalid-input branch is also executed by some other test, but it might still fail for a specific invalid input that was never tried. Coverage is therefore a necessary but not sufficient condition for good testing: uncovered code is definitely untested, but covered code is not definitely correct. That distinction is essential for interpreting coverage numbers honestly.

Finally, coverage targets should be treated as guidelines, not as goals to game. Aiming for 100 percent coverage often leads to tests written only to execute lines, without meaningful assertions, which inflates the number without improving quality, and wastes time on trivial code while complex logic remains under-tested. Aim for high coverage of critical code, such as business logic, validation, and security checks, and accept lower coverage for trivial code. Use coverage to find gaps and track trends, not as a pass or fail grade. A coverage number is a tool for judgement, not a substitute for it.

# Coverage counts execution, not correctness: this line is "covered" but unchecked.
def add(a, b):
    return a + b

add(2, 3)  # executed, so covered, but nothing asserted about the result
print("Covered, but not actually tested: no assertion was made")

Section 37: Reading a Test Failure

When a test fails, it produces output: the test's name, the assertion that failed, the expected and actual values, and often a traceback showing where the failure occurred. Reading that output well is a skill, because a failure message, properly understood, often points directly to the cause, while a failure message skimmed hastily leads to guessing and wasted time. This section teaches a method for reading failures, so that you can diagnose them quickly and accurately, even under pressure.

Start with the test's name. A well-named test, such as test_empty_title_rejected, tells you what behaviour broke, before you read any details. If the name is vague, such as test_1, you must read further to understand what was being tested, which is slower and more error-prone, and it is a sign the test should be renamed. Next, read the assertion message: what was expected, and what actually happened? For an equality failure, the difference between expected and actual is often the clue: a value that is off by one, a list in the wrong order, a string with a typo, or a None where a value was expected, each points to a different kind of bug. For an exception failure, the message tells you whether the wrong exception was raised, or no exception was raised when one was expected, which points to validation or error handling.

Next, read the traceback, but read it from the bottom up, not from the top down. The bottom of a traceback shows where the failure occurred, in your test or in the code under test, with file names and line numbers. The top shows the chain of calls that led there, which is useful for understanding context, but the bottom is where the action is. A common beginner mistake is to read tracebacks from the top, getting lost in framework internals, when the relevant line is at the bottom, in your own code. Focus on your code's lines first, then expand outward if needed. Framework lines are usually noise, unless the failure is in the framework itself, which is rare.

Next, consider whether the failure is in the code or in the test. Not every failing test means the application is broken. Sometimes the test is wrong: its expectation is outdated, because behaviour intentionally changed, or its setup is incorrect. Distinguishing a code bug from a test bug is essential, because fixing the wrong one makes things worse: changing code to satisfy a wrong test introduces a bug, while changing a test to hide a real bug destroys protection. To decide, check the requirement: what should the behaviour be? If the code matches the intent and the test does not, fix the test. If the test matches the intent and the code does not, fix the code.

Finally, reproduce the failure minimally. Run the failing test alone, to see if it fails in isolation, which rules out order dependence. Then reproduce the behaviour with a small script, outside the test, to confirm the bug exists in the code, not just in the test's setup. That minimal reproduction often clarifies the cause, because it strips away test machinery and shows the core behaviour.

# A failure message: expected vs actual tells you what went wrong.

#   Expected: 6 (a discount of 40 on 100 should be 60... wait, check the math)
# Reading carefully beats guessing: the expectation itself may be wrong.
print("Read failures bottom-up: the failing line first, then the context")

Section 38: Debugging with Tests

Tests are not just for verifying code. They are also a powerful debugging tool, because they let you reproduce a bug reliably, isolate it to a small case, and verify a fix, all in a fast, repeatable loop. Debugging with tests means turning a bug report into a failing test first, then using that test to guide your investigation, rather than debugging by staring at code or by manually trying the application repeatedly. That test-first debugging is more systematic than ad hoc debugging, and it leaves behind a regression test that prevents the bug from returning, which is a bonus that ad hoc debugging never provides.

The process starts with reproduction. Take the bug report, with its steps, inputs, and expected versus actual behaviour, and write a test that reproduces it: set up the reported inputs, call the code, and assert the expected behaviour. Run the test and confirm it fails, with the reported symptom. If it does not fail, your reproduction is wrong, or your understanding of the bug is wrong, and that itself is useful information, because it tells you to re-read the report or ask for more details. A test that reproduces the bug is a precise, repeatable description of the problem, far better than a vague report, because it can be run, inspected, and shared.

Next, narrow the test to isolate the cause. If the bug involves several parts, write smaller tests for each part, to find which part misbehaves. If the bug depends on specific data, reduce the data to the smallest case that still fails, by removing irrelevant fields and values, until only the essential trigger remains. That narrowing, sometimes called minimisation, often reveals the cause directly, because the minimal case makes the faulty logic obvious, whereas the full case obscures it with noise. It also produces a minimal regression test, which is clearer and faster than a test with a large, complex setup.

Next, use the failing test to guide your fix. Change the code, run the test, and see if it passes. If it does, run the full suite, to ensure the fix did not break anything else. If it does not, the test's failure message gives you new information about what is still wrong, guiding the next change. That loop, change, run test, read failure, repeat, is faster than manual debugging, because the test runs in seconds and checks precisely, without requiring you to repeat manual steps. It also keeps you focused: you are fixing the specific behaviour the test checks, not wandering through unrelated code.

Finally, keep the test. Once it passes, it becomes a regression test, guarding against the bug's return, and documenting the bug's nature for future developers. A debugging session that ends with a passing regression test has produced lasting value, beyond the fix itself. A debugging session that ends with only a fix, and no test, risks the bug returning silently in a future change, because nothing guards against it. Debugging with tests therefore does double duty: it finds the fix faster, and it prevents recurrence, which is why experienced developers reach for a test first, not last, when a bug is reported.

# Debugging with tests: reproduce first, then fix, then keep the test.
def double(n):
    return n * 2  # bug report said double(3) returned 5; fixed version here

assert double(3) == 6
assert double(0) == 0
print("Regression test passes: bug fixed and guarded")

Section 39: Test-Driven Development in Plain Words

Test-driven development, often shortened to TDD, is a way of writing code where tests come first, before the code they test, in a short, repeating cycle: write a failing test for a small piece of behaviour, write the minimal code to make it pass, then refactor, which means cleaning up the code without changing its behaviour, while keeping tests passing. That cycle, often summarised as red, green, refactor, where red means the test fails, green means it passes, and refactor means improve, is the core of TDD, and it changes the order of work, but not the nature of work: you still write code and tests, just in a different sequence, with different benefits.

The main benefit of TDD is that it forces you to think about behaviour before implementation. Writing a test first requires you to decide what a function should do, what inputs it takes, what outputs it returns, and what errors it raises, before you write the logic. That design thinking, done upfront, often produces cleaner interfaces, because you are designing from the caller's perspective, as a user of the function, rather than from the implementer's perspective, tangled in details. It also ensures tests exist, because they are written first, not left as an afterthought that may be skipped under time pressure. A TDD project has tests by construction, not by discipline alone.

TDD also gives you a tight feedback loop. Each cycle is small, a single behaviour, a single test, a minimal implementation, so you always know what you are working on, and you get immediate feedback when it works. That loop reduces the time spent debugging, because bugs are caught at the moment they are introduced, in a small change, rather than in a large feature completed all at once. It also makes progress visible: a growing suite of passing tests is a concrete measure of completed behaviour, more reliable than a feeling that a feature is "almost done". For learners, that visibility is encouraging, because it breaks large tasks into small, achievable steps.

TDD has limits that should be stated honestly. It can feel slow at first, because writing tests before code takes practice, and because the cycle requires discipline to keep steps small. It is less suited to exploratory work, where you do not yet know what the behaviour should be. And it does not guarantee good design by itself: tests written first can still be poorly designed, if the behaviour is poorly understood. TDD is a tool, not a magic method, and it works best for well-understood, incremental features, which covers much of back-end work.

Whether you adopt TDD fully, or use it selectively, its central lesson is valuable: think about expected behaviour, write it down as a test, and then implement to satisfy it. Even if you usually write code first, pausing to write a test before a tricky piece of logic, or before fixing a bug, captures much of TDD's benefit without adopting its full discipline. TDD is not an all-or-nothing choice. It is a spectrum, from writing tests after code, to writing tests before code, to letting tests drive design, and moving along that spectrum, even a little, towards tests first, generally improves both tests and code.

# TDD cycle: red (failing test), green (minimal code), refactor (clean up).
# Red: assert double(3) == 6  -> fails, no function yet
# Green: def double(n): return n * 2  -> passes
# Refactor: keep the code clean, tests still pass
def double(n):
    return n * 2

assert double(3) == 6
print("TDD cycle complete: red, green, refactor")

Section 40: Refactoring with Tests as a Safety Net

Refactoring means restructuring code without changing its observable behaviour: renaming variables for clarity, splitting a large function into smaller ones, removing duplication, or simplifying logic, all while the code continues to do exactly what it did before. Refactoring is essential for keeping a codebase healthy over time, because code that is never cleaned up accumulates complexity, duplication, and confusion, becoming harder to change and more prone to bugs. But refactoring without tests is risky, because a restructuring that accidentally changes behaviour will go unnoticed, until a user reports a regression. Tests are what make refactoring safe, by verifying that behaviour did not change, even as structure did.

The process is straightforward. Before refactoring, ensure the code has tests covering its current behaviour, and that those tests pass. If coverage is thin, add tests first, for the behaviours you care about, so the net is in place before you start. Then refactor in small steps, running tests after each step, so that if a step breaks behaviour, you know immediately which step caused it, and you can undo or fix that step, rather than untangling a large change. That small-step discipline is what makes refactoring manageable: each step is a minor restructuring, verified by tests, and the cumulative effect, over many steps, is a large improvement, achieved safely.

Tests also guide what refactoring is safe. A refactoring that changes internal structure, but keeps observable behaviour, should keep all tests passing, because tests assert behaviour, not implementation, as covered earlier. If a refactoring breaks tests, either the refactoring changed behaviour unintentionally, and should be fixed, or the tests assert implementation details, and should be updated to assert behaviour instead. That distinction, behaviour versus implementation, is crucial for refactoring, because tests that assert implementation will block every refactoring, making the suite a burden rather than a net. Keeping tests focused on behaviour is what keeps refactoring possible.

There are also refactorings that tests cannot fully verify, such as performance improvements, where behaviour is the same but speed differs, or changes to internal data structures that are not observable. For those, tests still help, by verifying behaviour did not change, but additional checks, such as performance measurements, are needed to verify the improvement itself. And there are refactorings that intentionally change behaviour, such as fixing a bug or changing a feature, which are not pure refactorings, and which require test updates to reflect the new behaviour, with the change documented and reviewed. Calling a behaviour change a refactoring, and updating tests to match it without discussion, hides a change that should be explicit. Honesty about what is refactoring and what is behaviour change is part of professional practice.

Finally, refactoring with tests builds confidence over time, in a virtuous cycle: tests enable refactoring, refactoring improves code, improved code is easier to test, which enables more refactoring. Codebases in that cycle stay healthy for years, adapting to new requirements without accumulating crippling complexity. Codebases without tests, or with tests that are ignored, fall into the opposite cycle: fear of change, accumulation of workarounds, and eventual stagnation or rewrite. Refactoring is not a luxury for clean code enthusiasts. It is maintenance, and tests are the safety equipment that makes maintenance possible without breaking what users depend on.

# Refactoring: same behaviour, cleaner structure, tests still pass.
def total_before(prices):
    s = 0
    for p in prices:
        s = s + p
    return s

def total_after(prices):
    return sum(prices)

assert total_before([1, 2, 3]) == total_after([1, 2, 3]) == 6
print("Refactoring safe: behaviour unchanged, tests pass")

Section 41: Testing Performance: Slow Tests and Timeouts

Performance testing, in the context of a test suite, has two meanings, and both matter. The first is testing that your code performs well enough, such as responding within a time limit, or handling a certain volume. The second is keeping your test suite itself fast, because a slow suite will not be run often, and a suite that is not run provides no protection. This section covers both, starting with the suite, because suite speed is the more immediate problem for most developers, and then covering performance checks for code, which are a specialised kind of test with their own pitfalls.

A test suite becomes slow for a few common reasons. Tests that use real databases, real networks, or real waiting, such as sleeping for seconds, are slow by nature, and a suite with many such tests will take minutes or hours. Tests that repeat expensive setup, such as creating a large dataset for every test, are slow by repetition. And tests that run sequentially when they could run in parallel are slow by organisation. Diagnosing slowness starts with timing: find the slowest tests, and ask whether each one needs to be slow, or whether it can be made faster with fakes, smaller data, or better setup.

Keeping a suite fast is a discipline with a few practices. Prefer unit tests, which are fast, over integration tests, which are slower, for most coverage, following the pyramid. Use fakes for outside services, in-memory databases, and fake clocks, so tests do not wait on the real world. Share expensive, read-only setup where safe, while keeping mutable setup fresh per test. And run tests in parallel where your framework supports it, provided tests are isolated, because parallelisation can cut suite time dramatically. A suite that runs in seconds will be run after every change. A suite that runs in an hour will be run rarely.

Testing code performance, as opposed to suite speed, means asserting that an operation completes within a limit, or handles a volume within a limit. For example, a test might assert that listing tasks for a user with a hundred tasks takes less than a second, or that an endpoint handles a hundred concurrent requests without errors. Those tests are valuable for catching regressions, such as a new query that makes a page ten times slower, but they are also flaky by nature, because performance varies with machine load, hardware, and environment. A performance test that passes on a fast developer machine might fail on a slower continuous integration machine, for no code reason, which makes it flaky, and flaky tests destroy trust, as covered earlier.

The way to handle that flakiness is to use performance tests as signals, not as strict gates, and to make them generous and stable. Set limits well above normal performance, so they catch large regressions, not small variations. Run them separately from the main suite, so a performance failure does not block development, but is still noticed. And measure trends over time, rather than single runs, because a trend is more informative than a single slow run, which might be noise.

import time

# A generous performance check: catches large regressions, not small variation.
def list_tasks(n):
    return [f"task {i}" for i in range(n)]

start = time.time()
list_tasks(1000)
elapsed = time.time() - start
assert elapsed < 5.0, f"Too slow: {elapsed:.2f}s"
print(f"Performance check passed: 1000 tasks listed in {elapsed:.3f}s")

Section 42: Testing Concurrency Basics

Concurrency means several things happening at the same time, such as multiple requests handled simultaneously, or multiple workers processing jobs in parallel, and testing concurrency means verifying that your code behaves correctly when that happens. Concurrency bugs are among the hardest to find, because they depend on timing: two operations that interfere only when they overlap in a particular way will pass most tests, which run sequentially, and fail occasionally in production, when timing aligns unluckily. Testing concurrency therefore requires deliberately creating overlap, and checking that shared data remains correct, even when operations run together.

The most common concurrency bug is a race condition, where two operations read and write shared data in an interleaved order that produces a wrong result. A classic example is two requests incrementing the same counter: both read the value as 10, both add one, both write 11, when the correct result should be 12, because two increments happened. That bug only occurs when the reads overlap, which is why sequential tests miss it. A concurrency test for that case would run many increments in parallel threads, and assert the final count equals the number of increments, which will fail if the increment is not protected, such as by a lock or an atomic database operation. That parallel test, run repeatedly, is how race conditions are exposed in testing, though it cannot prove their absence, because a race might still occur rarely, in a timing the test did not hit.

Testing concurrency in Python, using only the standard library, can be done with threads, which run functions concurrently in the same process, sharing memory, which is exactly the condition that exposes races in shared data. A test can start several threads, each performing an operation, wait for them all to finish, and then assert the final state. That pattern is simple and effective for shared-memory bugs, though it does not cover multiple processes or servers. For a learner, thread-based tests teach the core idea: overlap operations deliberately, and check that the result is as if they had run in some sequential order.

There are also concurrency properties beyond races that deserve testing. Deadlock, where two operations wait for each other forever, can be tested by running operations with a timeout and asserting they complete, rather than hanging. Lost updates, where one operation's change is overwritten by another's, can be tested by concurrent updates and asserting the final state reflects all updates. And queue behaviour under concurrency, such as two workers claiming the same job, can be tested by running workers in parallel and asserting each job was claimed once. Those tests should be used where concurrency matters, such as counters and queues, not everywhere, because their complexity is only justified where the risk is real.

Finally, accept the limit of concurrency testing honestly: passing tests do not prove the absence of races, because races depend on timing, and tests cannot cover every timing. Concurrency tests reduce risk, by catching common races, but they must be complemented by correct design, such as locks, atomic operations, and database transactions, which prevent races by construction. Testing finds some races. Design prevents them. Both are needed.

import threading

# A race exposed: two threads incrementing without protection can lose counts.
counter = {"value": 0}

def increment_many():
    for _ in range(1000):
        counter["value"] += 1  # not atomic: races possible

threads = [threading.Thread(target=increment_many) for _ in range(4)]
for t in threads:
    t.start()
for t in threads:
    t.join()
print("Counter after 4000 increments:", counter["value"],
      "(may be less than 4000 if a race occurred)")

Section 43: Testing Security Defensively

Security testing means checking that your system defends itself correctly, without teaching or using attack techniques against systems you do not control. That distinction matters, and this section stays firmly on the defensive side: it covers how to test that your own code, in your own test environment, with your own test data, rejects bad input, enforces authentication and authorisation, and does not leak sensitive information. It does not cover bypass techniques, exploit payloads, or attacks on live systems, which are outside this book's scope and which you should never attempt against a system you do not own or have explicit permission to test.

Defensive security testing starts with the checks you have already learned: validation tests, authentication tests, and authorisation tests, applied thoroughly, because most security bugs are ordinary bugs in those areas, such as missing validation, missing ownership checks, or error messages that leak information. A test that asserts an unauthenticated request is denied, an unauthorised request is denied without changing data, and a validation test that asserts malicious-looking input, such as a name containing code-like text, is stored safely as text and not executed, covers the most important defensive ground, without needing any attack knowledge beyond "input should be treated as data, not as code". That principle, treat input as data, is the core of defensive security, and tests that verify it are security tests.

Another defensive area is information leakage through responses, logs, and errors. Test that error responses do not include stack traces, internal paths, or database details in production mode. Test that logs do not include secrets, as covered earlier. Test that API responses do not include fields a user should not see, such as other users' private data, or internal fields like password hashes, even when the request is authenticated as the owner, because over-sharing in responses is a common leak. Those leakage tests are simple assertions on response contents and log contents, but they catch a class of bug that is easy to introduce accidentally, such as adding a field to a model and forgetting that it is serialised into every response.

A third defensive area is rate limiting and abuse prevention, which a later chapter covers in depth, but which can be tested defensively now: test that repeated failed logins are slowed or blocked, according to your design, by simulating many attempts and asserting the expected response after a threshold. Test that bulk requests are limited, by simulating many rapid requests and asserting that excess ones are rejected gracefully. Those tests verify your defences work, without needing to attack a live system.

Finally, security testing should be part of your regular suite, not a separate, occasional audit, because security regressions, like other regressions, occur when code changes, and only a suite run after every change will catch them promptly. Add security tests alongside feature tests, when a feature involves authentication, authorisation, validation, or sensitive data, so that the security properties of that feature are verified from the start and guarded thereafter. Defensive security testing, embedded in the normal test suite, is how a team maintains security continuously, rather than discovering problems in a rare, stressful audit, or worse, in a real incident.

# Defensive security test: input is treated as data, never as code to run.
def display_name(name):
    return f"Hello, {name}"

result = display_name("<script>alert('x')</script>")
assert "<script>" in result  # stored as text, not executed by this function
print("Defensive check passed: input kept as plain text data")

Section 44: Keeping Tests Fast

A fast test suite is a suite that gets run, and a slow suite is a suite that gets skipped, so keeping tests fast is not a minor optimisation. It is essential for the suite's value. This section collects the practices that keep suites fast, most of which you have already met in other contexts, now applied specifically to test speed. The goal is a suite that runs in seconds or, for larger projects, in a few minutes, so that running it after every change is painless, and developers do it habitually, rather than reluctantly.

The biggest speed win is the testing pyramid itself: many fast unit tests, fewer slower integration tests, and few slowest end-to-end tests. A suite dominated by unit tests will be fast, because unit tests are isolated and in-memory. A suite dominated by end-to-end tests will be slow, because each test involves servers, databases, and networks. Reshaping towards the pyramid, by moving logic from end-to-end tests into unit tests where possible, is the single most effective speed improvement for most suites, and it also improves diagnosis, because unit failures point to specific functions.

The next wins come from fakes and isolation. Using in-memory databases instead of disk databases, fake senders instead of real mail, mocked outside services instead of real calls, and fake clocks instead of real waits, all remove the slowest parts of tests, which are I/O and waiting. A test that sleeps for five seconds to wait for a job will make a suite of a hundred such tests take over eight minutes, for waiting alone, while a test that runs the job synchronously, or with a fake clock, takes milliseconds. Replacing waits with deterministic execution is one of the highest-value speed practices, and it also improves reliability, because waits are a source of flakiness, as covered earlier.

Setup efficiency is another win. Creating a large dataset for every test, when most tests need only a few rows, wastes time multiplied by the number of tests. Keep setup minimal per test, creating only what that test needs, and share read-only setup where safe, such as a pre-built reference dataset that tests never modify. Also, avoid repeating expensive operations, such as starting a server, for every test, when once per class or once per suite is sufficient, provided tests remain isolated. That balance, minimal per-test setup, shared read-only setup, is the key to fast suites that remain trustworthy.

Finally, run tests in parallel where possible, and measure suite time regularly, so slowness is noticed before it becomes a habit-breaking problem. Parallelisation, using multiple processes or threads, can cut suite time dramatically, but it requires isolation, as covered earlier, because parallel tests that share resources will conflict. Measuring suite time, and setting a budget, such as "the suite should run in under two minutes", gives you a target to defend, and a signal when it is exceeded, prompting investigation into which tests slowed down and why. A fast suite is a maintained suite, and maintenance means watching its speed, just as you watch its coverage and its flakiness, as a health metric for the testing practice itself.

# Fast tests avoid real waits: run the work synchronously in tests.
def do_job():
    return "done"

assert do_job() == "done"  # instant, no sleeping or waiting involved
print("Fast test passed in milliseconds, not seconds")

Section 45: Organising Tests in a Project

As a test suite grows, organisation becomes essential, because a pile of test files with unclear names and no structure is hard to navigate, hard to run selectively, and hard to maintain. Organising tests well means giving them a clear home, clear names, and a structure that mirrors the code they test, so that any developer can find the tests for a feature, run them, and add new ones in the right place, without guessing. Good organisation is not bureaucracy. It is what keeps a large suite usable, and it is worth establishing early, before the suite grows large enough to be painful to reorganise.

The standard organisation is a tests directory, separate from application code, with a structure that mirrors the application's structure. If your application has modules for tasks, users, and email, your tests directory might have test files for each, such as test_tasks.py, test_users.py, and test_email.py, each containing test classes for the functions and endpoints in that module. That mirroring makes it obvious where a test belongs, and where to find tests for a piece of code, which is invaluable during debugging, when you need to find the tests for a failing feature quickly. It also makes it easy to run a subset: run only test_tasks.py when working on tasks, and the full suite when working across features.

Naming matters at every level. Test files should be named test_*.py, so discovery tools find them automatically. Test classes should be named after what they test, such as TestTaskCreation. Test methods should be named test_ followed by a description of the behaviour, such as test_empty_title_rejected, so that a failure's name tells you what broke. That naming discipline, applied consistently, turns test output into a readable summary of what works and what does not, rather than a list of cryptic identifiers. It also helps new developers understand the intended behaviour of code, by reading test names as a specification, which is a form of documentation that stays accurate because tests are run.

Test organisation also includes separating kinds of tests, where helpful. Unit tests, which are fast and numerous, might live in one directory, while integration and end-to-end tests, which are slower, live in another, so they can be run separately: unit tests after every change, integration tests before merging, end-to-end tests before release. That separation avoids running slow tests when only fast feedback is needed, and it makes clear which tests are expected to be fast.

Finally, keep test helpers and fixtures organised too. Shared setup helpers, fake data factories, and mock utilities should live in a common test module, clearly named, so they can be reused without duplication, and so that changes to shared helpers are made in one place. Avoid duplicating setup code across many test files, because duplication makes maintenance painful: a change to a data model requires updating setup in many places, which will be missed in some, causing confusing failures. Centralising shared helpers, while keeping per-test setup explicit about what matters for that test, is the balance that keeps a large suite maintainable, and it is a balance worth establishing early, before duplication becomes entrenched.

# Organisation by mirroring: tests mirror the code they test.
structure = {"app/tasks.py": "tests/test_tasks.py",
             "app/users.py": "tests/test_users.py",
             "app/email.py": "tests/test_email.py"}
for code, test in structure.items():
    print(code, "->", test)

Section 46: Running Tests Automatically

Running tests by hand, by remembering to type a command after every change, is unreliable, because humans forget, especially under time pressure, and a forgotten test run is a missed opportunity to catch a bug early. Running tests automatically means setting up systems that run tests without human prompting, at key moments, such as on every code change, before merging, or on a schedule, so that test results are always available, and failures are noticed promptly, even if the developer forgot to run them. Automation turns testing from a habit that must be remembered into a safety net that is always up, which is a significant reliability improvement.

The simplest automation is a script or a command that runs the full suite with one invocation, so that running tests is easy, even if it is still manual. That single command should be documented, and it should be the same command everyone uses, so results are consistent across developers and environments. A more advanced automation is a pre-commit hook, a script that runs tests, or a subset of fast tests, automatically when code is committed, blocking the commit if tests fail. That hook catches failures at the moment of committing, before the code is shared, which is early and cheap, though it can be annoying if the suite is slow, which is another reason to keep fast tests fast, and to run only fast tests in hooks, leaving slower tests for later stages.

A more complete automation is continuous integration, covered in the next section, which runs tests on a separate machine, on every push or pull request, and reports results, so that failures are visible to the whole team, not just to the developer who made the change. Continuous integration also runs tests in a clean environment, which catches problems that do not appear on a developer's machine, such as missing dependencies, or tests that depend on local files. That clean-environment check is valuable, because "it works on my machine" is a common and frustrating problem, and automated runs in a standard environment eliminate it as an excuse.

Automation also includes scheduled runs, such as nightly test runs, which catch problems that develop over time, such as tests that depend on the date, and which provide a regular health check for the suite itself, even when no code changed. A nightly run that suddenly fails, without a code change, points to an environmental problem, such as a dependency update or a flaky test, which should be investigated promptly.

Finally, automation should report results clearly and visibly. A test run that produces output nobody sees is barely better than no run, because failures will be missed. Results should be posted where the team looks: in a pull request, in a chat channel, or on a dashboard, with a clear pass or fail, and with failure details accessible for investigation. And failures should block progress, such as blocking a merge, when they indicate real problems, because an automated run that does not block anything will be ignored, just as a manual run that is forgotten will be missed. Automation's value comes from its consequences: it must be easy to see, and it must matter, or it will be treated as decoration.

# Automation: tests run on every change, not just when someone remembers.
automation = ["on every commit: fast unit tests",
              "on every pull request: full suite",
              "nightly: full suite plus slow tests"]
for step in automation:
    print(step)

Section 47: Continuous Integration in Plain Words

Continuous integration, often shortened to CI, is the practice of merging code changes frequently, and automatically building and testing the merged code, on every change, so that integration problems are caught early, when they are small and easy to fix, rather than late, when many changes have accumulated and their interactions are hard to untangle. The name emphasises continuity: integration happens continuously, with every change, not in a large, painful event before a release. CI is a workflow, supported by tools, and it is one of the most widely adopted practices in modern software development, because it dramatically reduces the pain of combining work from many developers.

The basic CI workflow is simple. A developer pushes code to a shared repository, or opens a pull request proposing a change. A CI system, which is a service that watches the repository, automatically checks out the new code, in a clean environment, installs its dependencies, and runs its test suite, and possibly other checks, such as linting or security scanning. It then reports the result: pass, meaning the change did not break tests, or fail, meaning it did, with details for investigation. If the change passes, it can be merged. If it fails, the developer fixes it, pushes again, and CI runs again. That loop, push, test automatically, fix if needed, is the heart of CI, and it ensures that the shared codebase is always in a tested, working state, or at least that broken states are known immediately, not discovered weeks later.

CI provides several benefits beyond automated testing. It catches environment problems, because it runs in a clean, standard environment, not on a developer's personal machine, so missing dependencies are exposed. It provides a shared, visible record of test results, so the whole team can see whether the codebase is healthy. It enforces a quality gate, because merges can be blocked until tests pass, preventing broken code from entering the main codebase. And it encourages small, frequent changes, because small changes are easier to test, review, and revert than large, infrequent ones.

Setting up CI for a small Python project is straightforward with modern services, which provide configuration files that describe what to run, such as installing dependencies and running unittest, and which run those steps on every push. The configuration is usually a small file in the repository, and the service handles the rest. For a learner, setting up CI for a personal project is a valuable exercise, because it teaches the workflow and gives you a safety net that runs even when you forget to run tests locally.

There are also practices that make CI effective. Keep the CI suite fast enough that developers do not wait too long, by running fast tests first, and slower tests later or in parallel. Keep CI configuration in the repository, versioned with the code. And treat CI failures as urgent, fixing them promptly, rather than letting a broken main branch persist, because ignoring CI failures teaches the team that CI does not matter. CI is a discipline as much as a tool.

# CI workflow: push, test automatically in a clean environment, report, merge or fix.
workflow = ["1. Developer pushes a change",
            "2. CI checks out code in a clean environment",
            "3. CI runs the test suite",
            "4. Pass -> merge; Fail -> fix and push again"]
for step in workflow:
    print(step)

Section 48: A Small Test Suite Design

You have now met the pieces of testing. This section puts them together into a small, complete test suite design that you could actually build for a modest back-end application, using Python's unittest and standard library only, and that embodies the lessons of this chapter. The design is deliberately modest: it covers unit, integration, and a few end-to-end tests, organised clearly, run automatically, and maintained with discipline. Modest designs are valuable because they can be built, understood, and maintained, and then grown. A grand test suite that never gets built helps nobody, while a small one that runs on every change protects the code from day one.

Start with organisation. Create a tests directory, mirroring your application structure, with files for each module, such as test_tasks.py, test_users.py, test_email.py, and test_api.py. Within each file, use test classes per feature, with methods named for the behaviour they check. Use a shared test helpers module for fixtures and fakes, such as a fake mail sender, a test database helper, and a factory for creating users and tasks, so setup is consistent and not duplicated. That organisation makes the suite navigable: any developer can find the tests for a feature, run them selectively, and add new ones in the right place, without guessing.

Next, decide the mix, following the pyramid. Aim for many unit tests, covering validation, calculations, and pure logic, because those are fast and precise. Add integration tests for API endpoints and database operations, using in-memory test databases and live test servers for critical endpoints, covering happy paths, sad paths, and authorisation. Add a few end-to-end tests for critical journeys, such as signup, login, and task creation, run through the real API with fakes for outside services, to verify the whole path. That mix gives you broad, fast coverage, plus whole-system confidence where it matters most, without the slowness and brittleness of an end-to-end heavy suite.

Next, set up running and automation. Provide a single command to run the full suite, such as python -m unittest discover, documented in the project's readme, so anyone can run it. Add a pre-commit hook or a simple script that runs fast unit tests on commit, and set up continuous integration, even in simple form, to run the full suite on every push, reporting results visibly and blocking merges on failure. Those automation steps ensure the suite is actually run, not just written, which is the difference between a safety net that is up and one that is folded away. Automation should be set up early, when the suite is small, so it grows with the project, rather than being added later, when the suite is large and the habit is missing.

Finally, adopt the maintenance practices. Run the suite after every change, and fix failures promptly, before they accumulate. Review new tests for clarity, isolation, and meaningful assertions, not just coverage. Track suite time, coverage of critical code, and flakiness as health metrics. Write regression tests for every bug found in production. And refactor tests along with code, keeping them focused on behaviour, so they remain a safety net for refactoring, not a barrier to it.

Section 49: Common Testing Mistakes

Like every practice, testing has its classic mistakes, and this section collects them so you can avoid the most common ones. They are familiar by now, because they echo the mistakes from other chapters, but applied to testing, where their consequences are a suite that misleads, frustrates, or is abandoned, rather than a suite that protects. Reading this list is a cheap way to learn from others' testing failures instead of your own.

The first mistake is testing too little, or only happy paths, leaving sad paths, edge cases, and error handling untested, where bugs hide. The fix is to test sad paths and boundaries as thoroughly as happy paths, as covered earlier. The second mistake is testing too much of the wrong thing, such as testing trivial code exhaustively while leaving complex logic untested, or testing implementation details that break on every refactoring. The fix is to focus tests on behaviour, especially for complex and critical code, and to keep implementation tests minimal. The third mistake is writing tests that are hard to read, with vague names, huge setups, and unclear assertions, so that failures are hard to diagnose and tests are hard to maintain. The fix is clear names, minimal setup, and one behaviour per test.

The fourth mistake is shared state and order dependence, causing tests that pass alone but fail together, which destroys trust. The fix is isolation: fresh state per test, proper teardown, and no dependence between tests. The fifth mistake is flaky tests, left in the suite to erode trust, rather than fixed or quarantined promptly. The fix is to treat flakiness as urgent, to fix its cause, and to quarantine only temporarily. The sixth mistake is slow tests, especially end-to-end heavy suites, that are run rarely because they take too long, providing theoretical rather than real protection. The fix is the pyramid, fakes, and parallelisation, to keep the suite fast enough to run often.

The seventh mistake is mocking everything, so tests verify interactions with mocks, not real behaviour, and pass while the real system fails. The fix is fakes where possible, mocks only at boundaries, and occasional real integration checks. The eighth mistake is chasing coverage numbers, writing tests only to execute lines, without meaningful assertions, inflating coverage while proving nothing. The fix is to use coverage to find gaps in important code, and to judge tests by their assertions, not by their coverage contribution. The ninth mistake is never running tests, or running them only before releases, so bugs are caught late, when they are expensive. The fix is automation: run tests on every change, in CI, and fix failures promptly.

The tenth mistake is treating tests as a one-time effort, rather than a living part of the codebase, so tests rot as code changes, becoming outdated and eventually ignored. The fix is maintenance: update tests with code changes, refactor tests along with code, and track suite health metrics. None of these mistakes comes from bad intentions. They come from enthusiasm, time pressure, or learning testing on the job. The antidote is the habit this chapter has built: test behaviour, test sad paths and edges, keep tests isolated, fast, and trustworthy, automate them, and maintain them as living code.

Section 50: Testing in Your Back-End Toolkit

This chapter began with a simple observation: code that seems to work is not the same as code that is verified to work, and verification requires tests. It ends with a toolkit: practices and habits for testing that belong in every back-end developer's repertoire, alongside databases, APIs, and authentication. Testing is not a separate phase, done at the end if time allows. It is part of writing code, part of changing code, and part of debugging code, woven into the daily work of development. A developer who tests habitually produces code that is more reliable, more understandable, and easier to change, not because testing is magic, but because it forces clarity about behaviour, and it provides a net that catches mistakes early, when they are cheap.

Let us review the toolkit. You know what a test is, its arrange, act, assert structure, and why tests are a safety net that must be run regularly to be useful. You know the kinds of tests: unit, integration, and end-to-end, and how they form a pyramid, with many fast unit tests, fewer integration tests, and few end-to-end tests for critical journeys. You know how to write tests with unittest, how to use assertions well, how to test functions with return values and with side effects, how to use setup and teardown, test databases, and live API servers, and how to test CRUD, pagination, filtering, sorting, and error responses thoroughly, including happy paths, sad paths, and boundaries.

You also know the advanced tools: fixtures and fake data, mocks and fakes and when to use each, mocking outside services, time, and randomness, testing email and background jobs without real side effects, testing caching, logging, performance, concurrency, and security defensively, and keeping tests fast, isolated, and order-independent. You know about coverage, how to read failures, how to debug with tests, how test-driven development works, and how tests enable safe refactoring.

There are things this chapter did not cover in depth, and you should know their names so you can learn them next. Other test frameworks, with features like parametrisation, extend the unittest basics you learned here. Property-based testing generates many random inputs and checks that properties hold for all of them, extending the edge case testing you learned here. And load testing tools simulate many users and measure behaviour under load. You do not need those yet. The foundation you have now will make them much easier when you reach them.

Your next step is practice. Take a small back-end feature you have built, or build one now, and write tests for it, following this chapter: unit tests for its logic, integration tests for its endpoints, a few end-to-end tests for its critical journey, with fakes for outside services and a test database for data. Run the suite, watch it pass, then break the feature on purpose, and watch the suite catch it. That cycle, build, test, break, catch, is how testing skill is really learned, and it is a cycle you will repeat throughout your career.
