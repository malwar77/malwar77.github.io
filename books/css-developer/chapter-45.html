Chapter 45: Performance: Lean CSS and Fast Paints

Section 1: Why CSS Performance Matters

CSS performance matters because stylesheets affect how quickly a page becomes visible and interactive, especially on slower connections, less powerful devices, and larger sites where stylesheets can grow to hundreds of kilobytes. A large stylesheet must be downloaded, parsed, and matched against every element on the page before the browser can render correctly, and each of those steps takes time that delays the first paint — the moment readers first see content — and the moment the page becomes usable. On a fast desktop connection, that delay may be imperceptible, but on a mobile connection in an area with poor coverage, or on a low-end phone with limited processing power, it can be the difference between a page that feels instant and one that feels sluggish, causing readers to leave before content appears. Performance is therefore not a luxury for large sites; it is a core part of reader experience, affecting engagement, accessibility, and even search visibility, because slow pages rank and convert worse than fast ones.

CSS performance also matters because it compounds: a stylesheet that is slightly too large, with slightly too many complex selectors, and slightly too many expensive properties, will not cause a dramatic failure on its own, but together those small costs add up to a noticeably slower page, especially when combined with large images, scripts, and fonts that also compete for download and processing time. That compounding is why performance work should address CSS alongside other resources, rather than treating CSS as free because it is text: text still needs to be downloaded and parsed, and CSS parsing and matching happen on the main thread, where they compete with script execution and layout. A lean stylesheet frees main-thread time for other work, making the whole page faster, not just its styling.

A third reason CSS performance matters is that it affects readers unevenly, hitting those with the least capable devices and connections hardest, which makes it an accessibility and equity issue as well as a technical one. A developer testing on a powerful desktop with a fast connection may never notice a stylesheet problem that a reader on an older phone with a slow connection experiences on every page, and that gap in experience can exclude readers who already face barriers to access. Designing for lean CSS — small files, simple selectors, cheap animations — is therefore a way of designing for all readers, not just for those with ideal conditions, and it aligns performance work with accessibility work, both of which aim to make pages usable for everyone, regardless of device or connection.

Section 2: How Browsers Render CSS

Browsers render CSS through a series of steps that turn HTML and CSS into pixels on screen, and understanding those steps helps you see where CSS performance costs arise and where optimisations can help. First, the browser parses HTML into a document tree, and parses CSS into a stylesheet model, resolving imports, layers, and variables along the way. Next, it combines those two trees into a render tree, which contains only the elements that will be displayed, with their computed styles, excluding elements hidden with display none and head elements that are not rendered. Then, it calculates layout, also called reflow, determining the size and position of each element in the render tree, based on its styles, its content, and its container. After layout, it paints, filling in pixels for text, colours, borders, backgrounds, and images, often in layers that can be composited together. Finally, it composites those layers into the final image shown on screen, a step that can be accelerated by graphics hardware for certain properties.

Each of those steps has a cost that depends on stylesheet characteristics. Parsing cost depends on stylesheet size: a larger file takes longer to download and to parse into the browser's internal model, regardless of whether its rules are used. Matching cost depends on selector complexity and on the number of elements: the browser must check each rule against each element, or use optimised indexes to narrow that checking, but complex selectors, especially deep descendants and relational selectors, require more checking than simple class selectors. Layout cost depends on layout properties and on document size: a change to a layout property, such as width or margin, can trigger layout for a whole subtree, while a change to a paint-only property, such as colour, triggers only paint for affected elements, and a change to a composite-only property, such as transform or opacity, may trigger only compositing, which is cheapest. Understanding those cost tiers — layout most expensive, paint middle, composite cheapest — is the key to choosing efficient styles and animations.

Style recalculation is another step that occurs whenever styles change, whether through script, interaction, or animation, and its cost depends on how many elements are affected and how complex the selectors are that must be re-evaluated. A change to a custom property on a high ancestor, for example, can trigger recalculation for thousands of descendants that use that property, while a change to a property on a single element affects only that element. Similarly, a :has() rule that depends on descendants can trigger recalculation for many elements when a descendant changes, because the browser must re-check whether the :has() condition still holds. Those recalculation costs are not always visible in static page load, but they affect interaction responsiveness, especially on pages with many elements or frequent style changes, such as animations or live updates.

Section 3: The Critical Rendering Path

The critical rendering path is the sequence of steps the browser must complete before it can first paint content to the screen, and CSS is a render-blocking resource on that path, meaning the browser will not paint until it has downloaded and parsed the stylesheets in the document head, because painting without styles would produce a flash of unstyled content that then corrects itself, which is jarring and wasteful. That blocking behaviour is intentional and desirable for the main stylesheet, but it means that the size and delivery speed of that stylesheet directly determine how quickly readers see content: a large stylesheet, or one served slowly, will delay first paint, while a small, fast stylesheet will allow an early paint. Optimising the critical rendering path therefore starts with optimising the main stylesheet's size and delivery, through minification, compression, caching, and splitting, as discussed in later sections.

The critical path also includes HTML parsing, script execution, and other resources, and CSS interacts with those steps in ways that affect overall path length. A script in the head that blocks parsing will delay stylesheet discovery if the stylesheet link comes after the script, while a stylesheet that is large will delay script execution if the script depends on styles being ready. Ordering resources correctly — stylesheets in the head, in priority order, scripts deferred where possible — shortens the critical path by allowing the browser to discover and download stylesheets early, in parallel with other resources, rather than sequentially after blocking scripts. That ordering is a simple, high-value optimisation that requires no code changes to styles themselves, only to document structure, yet it can significantly improve first paint, especially on slower connections where sequential downloads are most costly.

Critical CSS, discussed in the previous chapter, is a technique for shortening the critical path further, by inlining the subset of styles needed for above-the-fold content directly in the document, so that the browser can paint that content without waiting for the full stylesheet, which then loads asynchronously in the background. That technique can improve perceived performance, because readers see content sooner, even though total download size increases slightly due to duplication, but it also adds build complexity and the risk of a stale or incomplete critical subset, as discussed earlier. Critical CSS should therefore be considered only after basic optimisations — small, compressed, cached stylesheets loaded efficiently — have been applied and measured, and only when first paint is still unacceptably slow, because it is a targeted optimisation for a measured problem, not a default practice for every page.

Order stylesheets and scripts carefully in the head, so the browser discovers critical styles early instead of waiting for blocking scripts.

Section 4: Measuring CSS Performance

Measuring CSS performance means quantifying how stylesheets affect load time, rendering time, and interaction responsiveness, using tools and metrics that reveal where time is actually spent, rather than guessing from file size alone. The most accessible measurements come from browser developer tools, which show stylesheet sizes, download times, parsing times, and rendering performance in timelines that break down layout, paint, and composite costs for interactions such as scrolling or animating. Those timelines are invaluable for diagnosing runtime performance problems, because they show which properties trigger expensive layout or paint, and which elements are affected, allowing you to target optimisations to the actual bottlenecks rather than to theoretical ones. Learning to read a performance timeline — identifying long layout tasks, frequent style recalculations, and paint-heavy animations — is a core skill for CSS performance work.

Lighthouse and similar audit tools provide higher-level measurements, such as first contentful paint, largest contentful paint, total blocking time, and cumulative layout shift, along with specific suggestions for CSS, such as removing unused CSS, minifying, or reducing render-blocking resources. Those audits are useful for benchmarking and for tracking performance over time, because they produce consistent scores that can be compared across releases, but they should be interpreted with care: a Lighthouse score is a synthetic measurement on a simulated device and connection, not a direct measurement of real readers' experiences, and a high score does not guarantee that a page feels fast to all readers, just as a low score does not necessarily mean a page is unusable. Use Lighthouse as a guide and a regression check, not as the sole definition of performance.

Real-user measurements, where available, complement synthetic audits by showing how actual readers experience a page, across diverse devices, connections, and locations, which synthetic tests cannot fully simulate. Those measurements, collected through browser APIs or analytics, reveal distributions — for example, that most readers experience fast loads, but a tail of readers on slow connections experience very slow loads — which is important for equity, because optimising for the average may still leave the slowest readers behind. A performance strategy that considers both synthetic benchmarks and real-user distributions will be more robust than one based on either alone, because it balances reproducible testing with real-world diversity.

Finally, measurement should be continuous, not a one-time audit, because stylesheet performance degrades gradually as new components, utilities, and themes are added, and a one-time optimisation will be undone by gradual growth if it is not monitored. Integrating performance measurements into continuous integration — for example, failing a build if stylesheet size exceeds a budget, or if Lighthouse scores drop below a threshold — ensures that performance regressions are caught when they are introduced, while they are still attributable to a single change, rather than discovered months later when many changes have accumulated. That continuous measurement, combined with periodic manual profiling for interaction performance, is the sustainable approach to CSS performance, turning it from a periodic rescue effort into a routine part of development.

Section 5: File Size: Smaller Is Faster

File size is the most direct CSS performance factor for load time, because a smaller stylesheet downloads faster, parses faster, and uses less memory, especially on slower connections where download time dominates, and on less powerful devices where parsing time is significant. Every kilobyte of CSS must be transferred over the network, decompressed, parsed into the browser's internal model, and matched against elements, so reducing file size reduces each of those costs, even though the per-kilobyte cost is small individually. For a stylesheet of a few kilobytes, size hardly matters, but for a stylesheet of several hundred kilobytes — common in large sites with utility frameworks, many components, and multiple themes — size becomes a major load-time factor, and reducing it by tens or hundreds of kilobytes can improve first paint by a noticeable amount, especially on mobile connections.

Reducing file size starts with removing what is not needed, which is more effective than compressing what is needed, because unused rules still cost parsing and matching time even after compression, and they still increase the file that must be downloaded, albeit compressed. Dead code removal, purging unused utilities, and splitting by page are therefore the highest-value size reductions, because they remove code entirely, rather than merely encoding it more efficiently. After unused code is removed, minification and compression further reduce the remaining file's transfer size, though they do not reduce its parsing cost as much, because the browser must still parse the minified code into its internal model, even if it downloads faster. That distinction — removal reduces all costs, compression reduces only transfer cost — is important for prioritising size optimisations.

Another size factor is duplication: the same rule, value, or component defined in multiple places, or the same colour, spacing, or font size written literally in many rules rather than through tokens, increases file size without adding functionality, and it also increases maintenance cost, because each duplicate must be updated when the value changes. Using tokens, shared classes, and component reuse reduces duplication, which reduces size and improves maintainability simultaneously, making it a doubly valuable optimisation. Similarly, shorthand properties, such as margin or background, can reduce size compared with writing each longhand property separately, though the saving is small per rule and should not be pursued at the cost of readability, because a shorthand that is hard to understand may cause bugs that outweigh its size benefit.

Finally, file size should be measured after compression, because that is the size actually transferred, and because compression ratios vary by content: repetitive CSS, such as utility classes with similar patterns, compresses very well, while diverse, unique rules compress less well, so two stylesheets with the same uncompressed size may have very different compressed sizes and therefore different download times. Reporting both uncompressed and compressed sizes, and tracking compressed size against a budget, gives a more accurate picture of load-time impact than uncompressed size alone. A size budget, as discussed in the previous chapter, should be set on compressed size per page, because that is what readers actually download, and it should be monitored continuously, so that gradual growth does not silently erode load performance over time.

Section 6: Minification in Plain Words

Minification is the process of removing unnecessary characters from CSS — whitespace, comments, and sometimes redundant semicolons or units — without changing its meaning, producing a smaller file that downloads faster, though it becomes harder for humans to read. That trade-off — smaller for machines, less readable for humans — is acceptable for production files, because production files are not meant to be read directly; they are meant to be downloaded and parsed by browsers, and developers read source files, not production files, with source maps bridging the gap for debugging. Minification is therefore a standard production optimisation, applied automatically by build tools, not by hand, because hand-minifying is error-prone and because build tools can minify reliably and reversibly, preserving source files for development while shipping minified files for production.

The size saving from minification is typically modest — often ten to thirty percent of uncompressed size — because much of CSS's redundancy is already removed by compression during transfer, which also removes whitespace patterns efficiently. That means minification alone will not transform a very large stylesheet into a small one; its value lies in combination with compression, removal of unused code, and splitting, each contributing a portion of the total saving. Minification's main benefit, beyond its direct size saving, is that it is safe and automatic: a mature minifier will not change a stylesheet's meaning, it requires no developer effort beyond enabling it in the build, and it can be verified by comparing the minified output's rendering with the source's rendering, which should be identical. That safety and automation make minification a default production step, even though its individual saving is modest.

Minification also interacts with source maps, which are files that map minified code back to source code, allowing browser tools to show original file names, line numbers, and code when debugging production styles, even though the browser downloaded minified code. Without source maps, debugging production CSS is difficult, because minified code has no meaningful line numbers and its selectors and declarations are compressed onto few lines, making it hard to locate a rule's source. Generating source maps alongside minified files is therefore an essential part of minification in practice, not an optional extra, and build configurations should ensure that maps are generated and that they are available to developers, though not necessarily to all readers, depending on whether maps should be public or restricted to development use.

Finally, minification should not be confused with obfuscation or with optimisation that changes semantics, such as merging rules, removing supposedly unused rules, or reordering rules in ways that affect the cascade. A minifier's job is only to remove unnecessary characters, not to change which rules apply or in what order, because any semantic change risks breaking appearance in subtle ways that are hard to detect. Optimisations that change semantics — such as purging, splitting, or reordering — should be separate build steps, with their own verification, rather than being bundled into minification, so that each step's effect can be understood and tested independently. Keeping minification purely cosmetic ensures that it remains safe, while semantic optimisations are handled with the care they deserve.

Section 7: Compression: Gzip and Brotli

Compression is the process of encoding CSS files more efficiently for transfer, using algorithms such as Gzip or Brotli, which exploit repetition in the file — repeated selectors, properties, values, and patterns — to represent the file in fewer bytes than its original text, without losing any information, because the browser decompresses it exactly before parsing. Compression is applied by the server during transfer, not by the build tool, though build tools may pre-compress files to reduce server work, and it is one of the most effective size optimisations available, often reducing CSS transfer size by seventy percent or more, especially for repetitive stylesheets such as utility frameworks, where many rules share similar patterns that compress extremely well. That large saving is why compression should always be enabled for CSS, regardless of other optimisations, because it provides a bigger benefit than minification alone, with no change to the stylesheet's meaning or to developer workflow, beyond server configuration.

Gzip is the older, widely supported compression algorithm, available on virtually all servers and browsers, and it provides good compression for text files such as CSS, with moderate server CPU cost for compressing on the fly. Brotli is a newer algorithm, developed specifically for web text compression, that typically achieves ten to twenty percent better compression than Gzip for CSS, at the cost of slightly higher server CPU for compression, though that cost is mitigated by pre-compression or by caching compressed responses, so that each file is compressed once rather than on every request. Most modern servers and browsers support Brotli, and a server configured to serve Brotli to supporting browsers and Gzip to others will achieve the best compression for each reader, without compatibility problems, because browsers advertise which algorithms they support and servers choose accordingly.

Compression interacts with other optimisations in ways that affect total saving: minification before compression provides only a small additional saving beyond compression alone, because compression already removes whitespace redundancy efficiently, while removal of unused code before compression provides a larger saving, because unused code, even compressed, still contributes bytes and parsing cost. That interaction means that compression should not be used as an excuse to keep unused code, on the grounds that it compresses well, because unused code still costs parsing and matching time after decompression, and it still increases the compressed size, albeit less than its uncompressed size. The most effective combination is removal first, then minification, then compression, each step reducing a different cost, with compression providing the largest transfer saving but removal providing the largest total saving across download, parsing, and matching.

Verify compression headers after deployment, because a misconfigured server can silently serve full-size files even when compression is believed enabled.

Section 8: Removing Unused CSS

Removing unused CSS is the process of identifying rules that are never applied on a site — because their components were removed, their pages were redesigned, or their utilities were generated but never used — and deleting them, so that the stylesheet becomes smaller, faster to parse, and easier to maintain. That process, discussed in the previous chapter for dead code generally, is especially important for performance, because unused rules cost download, parsing, and matching time without providing any visual benefit, and in large stylesheets, unused rules can account for a significant fraction of total size, particularly in utility frameworks where hundreds of generated utilities may never be used on a given page, or in legacy stylesheets where old components remain defined long after their markup was removed. Removing those rules is therefore one of the highest-value performance optimisations, often yielding larger savings than minification or compression alone, because it removes code entirely rather than merely encoding it more efficiently.

Identifying unused CSS requires analysing the relationship between stylesheets and markup, templates, and scripts, to determine which selectors actually match elements on live pages, including dynamic states that may not appear in initial markup, such as modals, error messages, or hover states that are triggered by interaction. Tools that crawl pages and report unused selectors provide a starting point, but they require human judgement to confirm, because a selector that appears unused in a crawl may be used in a rare state, in user-generated content, in a third-party embed, or in a page that was not crawled, and deleting it based solely on a tool report risks breaking that rare case. That caution is especially important for performance-motivated removal, because a performance optimisation that breaks functionality is worse than no optimisation, and it should be verified by testing affected pages and states after removal, not just by trusting a tool's report.

Removal should be done incrementally and safely, as discussed for dead code: identify candidates, check for dynamic and rare uses, remove in a separate, reviewable change, and verify appearance on representative pages, with version control providing a safety net for restoration if a mistake is discovered. That incremental approach is slower than bulk deletion, but it prevents the regressions that bulk deletion often causes, and it allows the team to learn which kinds of rules are commonly dead — for example, old page files, deprecated components, or generated utilities for breakpoints that are never used — so that future dead code can be prevented through process improvements, such as requiring stylesheet removal when a component is removed, or enabling purging in the build. Prevention, combined with periodic removal, keeps a stylesheet lean continuously, without requiring large, risky cleanups.

Section 9: Purging Utilities Safely

Purging utilities is a specific form of unused CSS removal, applied to utility frameworks or utility-heavy stylesheets, where a build tool scans markup, templates, and scripts for utility class names and removes generated utilities that are never used, producing a much smaller production stylesheet that contains only the utilities actually needed. That purging is essential for utility frameworks, because a full utility set may contain thousands of classes for every spacing, colour, and layout combination, most of which are never used on a given site, and shipping the full set would be wasteful, increasing download and parsing time for no benefit. Purging transforms a large, generic utility set into a small, site-specific one, which is why utility frameworks are viable for production despite their large source size: their production size, after purging, is often smaller than a hand-written stylesheet for the same design, because purging removes exactly the unused utilities, leaving only those that are used.

Purging safely requires configuring the tool to scan all sources where utility classes may appear, including HTML templates, script files that generate class names dynamically, content files, and any third-party content that uses utilities, because a utility that appears only in a source the scanner does not check will be purged by mistake, breaking the page or component that uses it. Dynamic class names are the main risk: a class name constructed by concatenating strings in script, such as "text-" plus a colour name, will not appear literally in any file for the scanner to find, so it will be purged even though it is used at runtime, producing a missing style that only appears when that dynamic code runs. Safelisting — explicitly listing dynamic utilities or patterns that should never be purged — is the standard mitigation for that risk, and it requires developers to identify dynamic utilities when they write them, rather than discovering them after purging breaks a page.

Testing after purging is equally important, because a purging configuration that works for most pages may still miss a utility used on a rare page or in a rare state, such as an error page, a modal, or a print stylesheet, that was not included in the scanner's sources or in manual testing. A post-purge test should therefore include not only main pages, but also rare pages, interactive states, and dynamic content, checking that all utilities appear correctly, and it should be part of continuous integration, so that a purging regression — for example, a new dynamic utility that was not safelisted — is caught when it is introduced, rather than after deployment. That testing, combined with safelisting, makes purging safe enough for production, despite its inherent risk of removing a needed utility, because the risk is managed through configuration and verification, not ignored.

Section 10: Selector Performance Basics

Selector performance basics start with the understanding that browsers match selectors efficiently, using optimised data structures and indexes, so that most selectors, even in large stylesheets, do not cause noticeable performance problems on their own, and that selector performance only becomes a concern in specific situations: very large documents with thousands of elements, very complex selectors that require checking many ancestors or siblings, or frequent style recalculations triggered by animations, interactions, or script changes that force re-matching. For typical pages with hundreds of elements and simple class selectors, selector matching cost is negligible compared with layout, paint, and script costs, and optimising selectors in such pages will yield no measurable improvement, even though it may feel like a performance win. That perspective is important, because it prevents wasted effort on selector micro-optimisation that does not help readers, while focusing attention on the selector patterns that actually matter in large or dynamic pages.

The browser's matching process, in simplified terms, works right-to-left for most selectors: it starts with the rightmost, or key, selector — the element that the rule actually styles — and then checks whether that element's ancestors, siblings, or other conditions satisfy the rest of the selector. That right-to-left evaluation means that the key selector's specificity and frequency matter most for matching cost: a key selector that matches many elements, such as a universal selector or a generic element, will require checking many candidates, while a key selector that matches few elements, such as a distinctive class, will narrow candidates quickly and reduce checking. It also means that a long descendant selector with a generic key, such as div p, will be more expensive than a short class selector, because many paragraphs must be checked against their ancestors, even though most will not match the full selector. Understanding that right-to-left logic helps authors write selectors with distinctive, low-frequency key selectors, which is the main selector performance habit.

Another basic principle is that selector matching cost is proportional to both selector complexity and document size, so a selector that is cheap on a small page may become expensive on a large page with many elements, especially if it is re-evaluated frequently due to style changes. A page with ten thousand rows in a table, for example, will pay a much higher matching cost for a complex row selector than a page with ten rows, and that cost will be paid on every style recalculation, such as when a row is added, removed, or highlighted. That scaling is why selector performance guidance often emphasises large documents and dynamic pages, rather than small static pages, where matching cost is trivial regardless of selector complexity. Testing selector performance, when it is a concern, should therefore be done on realistic document sizes and with realistic interaction patterns, not on tiny test pages that hide scaling effects.

Section 11: Expensive Selectors to Avoid

Expensive selectors are those that require the browser to do more work than necessary to determine whether they match, usually because they have generic or high-frequency key selectors, deep descendant chains, or relational conditions that depend on many elements. The most expensive common pattern is a deep descendant selector with a generic key, such as a rule that styles paragraphs inside a container inside a section inside a page, because the browser must check many paragraphs against multiple ancestors, even though only a few will match the full chain. That cost is multiplied by document size and by recalculation frequency: on a large page, or on a page where styles change frequently, a deep selector will be re-evaluated many times, each time checking many candidates, producing a measurable performance cost that a simple class selector would avoid entirely, because a class key narrows candidates immediately.

Another expensive pattern is the universal selector used as a key or as part of a complex selector, such as a rule that styles all elements inside a container, or all elements with a certain pseudo-class, because the universal selector matches every element, forcing the browser to check every element against the rest of the selector, even though most will not match. That pattern is sometimes used for resets, where a universal rule sets box-sizing or margin for all elements, and in that case the cost is usually acceptable, because the rule is simple and is evaluated once at load, but using universal selectors in complex, frequently recalculated rules — such as a universal selector combined with :has() or with a sibling combinator — can become expensive, because the browser must re-check every element whenever relevant content changes. The lesson is not to avoid universal selectors entirely, but to use them simply and sparingly, and to avoid combining them with expensive conditions.

Relational selectors, such as :has(), sibling combinators, and :nth-child() with complex arguments, can also be expensive, because they require the browser to check relationships between elements, not just properties of a single element. A :has() rule that checks whether a container contains a certain descendant, for example, must re-check that container whenever its descendants change, which can be frequent on dynamic pages where content is added, removed, or updated by script. Similarly, a sibling rule that styles an element based on its preceding siblings must re-check siblings whenever the sibling list changes. Those relational costs are justified when the relationship is essential to the design — for example, styling a form group differently when it contains an invalid input — but they should not be used where a simple class, toggled by script or by markup, would express the same condition more cheaply, because a class check is a single-element check, while a relational check involves multiple elements.

Section 12: The Universal Selector Cost

The universal selector, written as *, matches every element in a document, and its cost depends entirely on how it is used: as a simple, standalone rule, it is usually cheap, because the browser can apply it efficiently during initial style calculation, but as part of a complex selector, or in a rule that is frequently recalculated, it can become expensive, because it forces the browser to consider every element as a candidate, even though most candidates will not match the full selector. That distinction is important, because universal selectors are often used in resets, where they set box-sizing, margin, or padding for all elements, and those resets are generally considered acceptable performance-wise, despite matching every element, because they are simple, they are evaluated primarily at load, and their benefit — consistent box sizing and spacing across browsers — outweighs their small cost. The problem arises when universal selectors are used casually in other contexts, where their cost is not justified by a corresponding benefit.

A universal selector combined with a descendant combinator, such as a rule that styles all elements inside a container, is more expensive than a standalone universal rule, because the browser must check every descendant of that container against the rule, and must re-check them whenever the container's contents change, which can be frequent on dynamic pages. Similarly, a universal selector combined with a pseudo-class or pseudo-element, such as a rule that styles the before pseudo-element of every element, will generate pseudo-elements for every element, increasing paint and layout work dramatically, even though most of those pseudo-elements may be empty or invisible. Those combinations should be avoided, or used only with a clear understanding of their cost, because they turn a cheap, simple selector into an expensive, broad one, by multiplying its reach across the whole document.

Another cost of universal selectors is that they have zero specificity, which means they lose to almost any other author rule, including element selectors, and they therefore cannot be relied upon to enforce styles that must win over other rules. That low specificity is actually a benefit for resets, because reset rules should yield easily to component styles, but it is a drawback for rules that are meant to guarantee an outcome, such as a safety or accessibility style that must not be overridden accidentally. A universal rule intended as a guarantee will fail, because any more specific rule will beat it, and the author may then be tempted to add important to force it, which creates a new set of cascade problems. Understanding universal specificity — zero, always yielding — helps authors use universal selectors only where yielding is desired, namely resets and defaults, and not where enforcement is needed.

Section 13: Deep Descendants and Matching

Deep descendant selectors, which chain several ancestors before the target element, such as a rule that styles a link inside a list item inside a list inside navigation inside a header, are expensive to match and fragile to maintain, for reasons that go beyond raw performance and into the realm of code quality. From a matching perspective, the browser evaluates such selectors right-to-left, starting with the target link, then checking whether its ancestors include a list item, then a list, then navigation, then a header, in order, for each candidate link on the page. That ancestor checking must be repeated for every link, even those that are not inside a header navigation, because the browser cannot know without checking, and on a page with many links, that checking adds up, especially when styles are recalculated frequently due to interaction or script changes. A simple class on the target link, by contrast, requires only a class check, with no ancestor traversal, making it both faster and simpler.

From a maintainability perspective, deep descendants are fragile because they depend on exact markup structure: adding a wrapper element, changing a list to a div, or moving navigation to a different container will break the selector, even though the link's role has not changed, requiring a stylesheet change for a markup refactoring that should not affect styling. That fragility is a cost that is paid in developer time, not just in browser time, because every markup change must be checked against deep selectors that might depend on the old structure, and every deep selector must be updated when markup changes, creating a coupling between markup and styles that makes both harder to evolve. A class-based selector, by contrast, survives markup restructuring, because it depends only on the target element's class, not on its ancestors, making both markup and styles more flexible.

Deep descendants also increase specificity, because each part of the chain adds to the selector's weight, making the rule harder to override and more likely to cause specificity conflicts, as discussed in earlier chapters. A deep descendant rule with four classes or elements will beat a simple class override, forcing overrides to be equally deep or to use important, which escalates specificity creep and makes the stylesheet harder to maintain. That specificity cost, combined with matching cost and fragility, makes deep descendants a poor choice in most cases, even when they seem precise, because their precision is achieved at the expense of performance, maintainability, and overrideability, three qualities that matter more than the ability to describe an exact ancestry in a selector.

Prefer a distinctive class on the target element, which survives markup restructuring and keeps matching, specificity, and maintenance costs low.

/* Deep descendant: fragile, specific, and slow to match. */
.header .nav ul li a { color: #0b5fff; }

Section 14: :has() Performance Notes

The :has() pseudo-class, which styles an element based on its descendants or siblings, is powerful for expressing conditional styles without script, but it carries performance considerations that authors should understand before using it widely, especially on large or dynamic pages. Because :has() depends on relationships, the browser must re-evaluate a :has() rule whenever relevant descendants or siblings change, not just when the target element itself changes, which means that a page with frequent content updates — such as a live feed, a form with validation, or a list that is filtered by script — will trigger :has() re-evaluation frequently, potentially for many elements, if :has() rules are broad. That re-evaluation cost is not necessarily prohibitive, because browsers optimise :has() matching, but it is higher than a simple class check, which only depends on the target element itself, and it scales with the number of elements matched by :has() and with the frequency of content changes that affect those matches.

The scope of a :has() argument also affects its cost: a :has() rule with a simple, specific argument, such as :has(img) on a card, requires checking only whether the card contains an image, which is a relatively cheap check, especially if images are few and stable. A :has() rule with a complex argument, such as :has(.featured > .badge + .label), requires checking a chain of descendants and siblings, which is more expensive, and a :has() rule applied to many elements, such as every list item on a large page, multiplies that cost across all those elements. Keeping :has() arguments simple and specific, and applying :has() rules only to elements where the conditional style is genuinely needed, rather than to every element of a type, keeps :has() costs manageable, while still gaining its expressive benefit for the cases where it matters.

Another performance consideration is that :has() can trigger style recalculation for subtrees that would otherwise be unaffected by a change, because a change deep inside a subtree can affect whether an ancestor matches :has(), which in turn affects that ancestor's styles and potentially its layout and paint. That upward propagation — a descendant change affecting an ancestor's style — is the opposite of the usual top-down inheritance flow, and it means that :has() can make style recalculation less local than it would be without :has(), potentially affecting larger subtrees on each change. That effect is usually small for occasional changes, but it can become noticeable on pages with frequent updates and broad :has() rules, where each update triggers recalculation for ancestors and their subtrees, rather than only for the changed element itself.

Use :has() selectively for meaningful conditions, test it on realistic pages, and prefer a class toggle where a simple class expresses the same condition.

/* :has() is powerful; keep arguments simple and scope narrow. */
.card:has(img) { padding-top: 0; }

Section 15: Layout, Paint, Composite

Layout, paint, and composite are the three main rendering stages after style calculation, and understanding their relative costs is essential for choosing efficient CSS properties, especially for animations and interactions. Layout, also called reflow, calculates the size and position of elements, based on their styles, content, and containers, and it is the most expensive stage, because a layout change to one element can affect the layout of many others — for example, changing an element's width can reflow its siblings, its parent, and its descendants, potentially triggering layout for a large subtree or even the whole page. Paint, also called rasterisation, fills in pixels for an element's visual properties — text, colours, borders, backgrounds, shadows, and images — and it is less expensive than layout, because it affects only the element itself and its visual area, not the positions of other elements, though painting a large or complex element, such as one with a large shadow or blur, can still be costly. Composite combines painted layers into the final image, using graphics hardware where possible, and it is the cheapest stage, because it only moves and blends already-painted layers, without recalculating layout or repainting pixels, which is why properties that can be handled in compositing alone, such as transform and opacity, are the cheapest to animate.

That cost hierarchy — layout most expensive, paint middle, composite cheapest — should guide property choices for animations and for frequent style changes. Animating a layout property, such as width, height, margin, or top, will trigger layout on every frame, which can easily cause jank, especially on lower-end devices or on pages with many elements, because layout must be recalculated and then paint and composite must follow, for each frame. Animating a paint property, such as colour, background, or box-shadow, will trigger paint on every frame, which is cheaper than layout but still costly, especially for large elements or for shadows and blurs that require expensive pixel calculations. Animating a composite property, such as transform or opacity, will trigger only compositing on most browsers, because the element's painted layer can be moved, scaled, or faded by the compositor without repainting or reflowing, making it smooth even on modest devices. That is why transform and opacity are the recommended animation properties, and why layout and paint animations should be avoided for frequent or continuous motion.

Static styles also benefit from that hierarchy, though less dramatically, because a static layout property is calculated once at load, not on every frame, so its cost is paid once rather than repeatedly. Nevertheless, a page with many elements that use expensive paint properties — such as large box-shadows, backdrop filters, or complex gradients on many elements — will pay a higher initial paint cost than a page with simpler visuals, and that cost can delay first paint, especially on low-end devices. Simplifying paint for large or repeated elements, such as using a solid colour instead of a gradient, or a small shadow instead of a large blur, can reduce initial paint time without noticeably changing design, if applied judiciously to the elements that dominate paint cost, as identified through profiling rather than through assumption.

/* Animate transform and opacity; avoid width, margin, and top. */
.card { transition: transform 0.2s ease, opacity 0.2s ease; }

Section 16: Animating Cheap Properties

Animating cheap properties — primarily transform and opacity, and to a lesser extent, properties that affect only compositing or only a small paint area — is the foundation of smooth CSS animation, because those properties can be handled by the compositor without triggering layout or large repaints, allowing animations to run at sixty frames per second even on modest devices. Transform includes translate, rotate, scale, and skew, each of which moves, rotates, or resizes an element's painted layer without changing its layout box, meaning that surrounding elements do not need to reflow when a transformed element moves, and the element itself does not need to be repainted, because its pixels are simply moved as a layer. Opacity similarly fades an element's layer without changing its layout or requiring a repaint of its content, because the compositor can blend the existing layer at a different opacity, which is a cheap operation for graphics hardware. Together, transform and opacity cover most common animation needs — sliding, fading, scaling, and rotating — without incurring layout or paint costs, which is why they are the recommended animation properties in virtually all CSS performance guidance.

Using transform and opacity effectively requires thinking in terms of layers and visual effects, rather than in terms of layout properties that achieve a similar visual result through a more expensive path. A slide-in animation, for example, should use translateX or translateY to move an element from off-screen to its position, rather than changing its left, margin, or width, which would trigger layout on every frame and cause jank, especially if the sliding element is large or if many elements are sliding simultaneously. A fade-in should use opacity, rather than changing colour or visibility in a way that triggers paint, and a scale effect should use scale, rather than changing width and height, which would trigger layout and paint for the element and its surroundings. Those substitutions — transform for position and size, opacity for visibility — preserve the visual effect while moving the work to the cheapest rendering stage, which is the core technique for cheap animation.

Cheap properties also include, in some cases, properties that trigger only paint for a small area, such as colour changes for text, though those are less cheap than transform and opacity, because they still require repainting the affected text, albeit for a small area. For small elements, such as a button's background colour on hover, a paint-triggering transition may be perfectly smooth, because the repaint area is small and the change is infrequent, triggered only on hover rather than continuously. The distinction is therefore not absolute — paint animations are not always bad — but relative to frequency and area: a paint animation on a small element, triggered occasionally, is fine, while the same paint animation on a large element, triggered continuously, may cause jank, and a layout animation on any element, triggered continuously, is likely to cause jank regardless of size. Judging cheapness requires considering property, element size, and animation frequency together, not just the property name alone.

/* Cheap animation: transform and opacity only. */
.fade-slide { transition: transform 0.3s ease, opacity 0.3s ease; }

Section 17: Animating Expensive Properties

Animating expensive properties — primarily layout properties such as width, height, margin, padding, top, and left, and paint-heavy properties such as box-shadow with large blur, background gradients that change, and filters such as blur — is costly because each animation frame triggers layout or paint work that must be completed within about sixteen milliseconds to maintain sixty frames per second, and on many devices, especially low-end ones, that work cannot be completed in time, causing dropped frames, stuttering, and a janky experience that feels worse than no animation at all. Layout animations are the most expensive, because changing an element's size or position through layout properties forces the browser to recalculate layout for that element and potentially for its siblings, parent, and descendants, then to repaint affected areas, then to composite, for every frame, which is a full rendering pipeline on each frame, rather than just the compositing step that transform animations require. That full pipeline cost is why layout animations should be avoided for continuous motion, such as sliding, growing, or moving elements, and reserved for infrequent, discrete changes, such as a layout change on a breakpoint switch, where a single reflow is acceptable because it is not animated frame-by-frame.

Paint-heavy animations are less expensive than layout animations, but still costly, because they require repainting pixels on every frame, and the cost scales with the painted area and with the complexity of the paint operation. Animating box-shadow, for example, requires recalculating the shadow's blur and spread for each frame, which is expensive for large shadows, while animating a gradient requires recalculating colour stops and interpolation for each pixel in the gradient area, which is expensive for large gradients. Animating filter blur is similarly expensive, because blur requires sampling neighbouring pixels for each output pixel, a operation that grows with blur radius and with element size. Those paint costs may be acceptable for small elements animated briefly, such as a button shadow on hover, but they become problematic for large elements, for many simultaneous animations, or for continuous animations that run for seconds, where the cumulative paint cost overwhelms the frame budget.

A common expensive animation pattern is animating height or width for an accordion or expandable section, where the content's height changes from zero to full, which seems natural to animate through height, but which triggers layout on every frame as the height interpolates, causing jank, especially if the accordion contains many elements or if its expansion affects surrounding layout. Better alternatives for such patterns include animating transform scaleY, though that distorts content, using grid-template-rows with a transition, which still triggers layout but may be optimised in some browsers, or simply not animating height at all, instead toggling visibility instantly, which is less visually smooth but far more performant and often acceptable for accessibility, especially when combined with a fade or transform effect that gives a sense of motion without layout cost. Choosing an alternative requires weighing visual smoothness against performance, and in many cases a simpler, cheaper effect is preferable to a smooth but janky layout animation.

/* Expensive: animating width triggers layout every frame — avoid. */
.accordion { transition: height 0.3s ease; }

Section 18: Transitions and Performance

Transitions in CSS animate a property change over time, when an element's style changes from one state to another, such as on hover, focus, or class toggle, and their performance depends on which properties are transitioned, how long the transition lasts, and how many elements transition simultaneously. A transition on transform or opacity, as discussed, will be cheap, because it can be handled in compositing, while a transition on a layout or paint-heavy property will be expensive, because it triggers layout or paint on every frame of the transition, which may last several hundred milliseconds and therefore many frames, each requiring full rendering work. That per-frame cost, multiplied by transition duration and by the number of transitioning elements, determines whether a transition feels smooth or janky, and it is why transition property choice matters more than transition duration alone: a long transform transition will still be smooth, while a short layout transition may still jank, because its per-frame cost is high regardless of duration.

Transition duration and timing also affect perceived performance, though not in the same way as per-frame cost. A very long transition, such as two seconds for a hover effect, will feel sluggish even if it is smooth, because readers expect immediate feedback for interactions, while a very short transition, such as fifty milliseconds, may be imperceptible, making the transition pointless, though it will still cost a few frames of rendering work. A duration of around two to three hundred milliseconds is a common sweet spot for hover and focus transitions, because it is long enough to be perceived as smooth motion, but short enough to feel responsive, and it limits the total number of frames that must be rendered, reducing total work compared with a longer transition. Timing functions also matter: an ease function that starts fast and ends slow, or vice versa, can feel more natural than a linear function, without affecting per-frame cost, because timing only changes the interpolation curve, not the rendering stages required.

Simultaneous transitions are another performance factor, because transitioning many elements at once — for example, animating a grid of cards on hover, or transitioning a whole page's colours on theme switch — multiplies per-frame cost by the number of elements, potentially overwhelming the compositor or paint system, even if each individual transition is cheap. That multiplication is why transitions should be applied selectively, to the elements that actually need motion feedback, rather than globally to all elements, and why a theme switch that transitions every element's colours may cause a noticeable stutter, even though each colour transition is individually cheap, because hundreds of elements repainting simultaneously is expensive in aggregate. Limiting transitions to interactive elements, and avoiding global transition rules such as * { transition: all 0.3s; }, which transitions every property on every element, is a key performance habit for transitions.

/* Transition cheap properties only; avoid transition: all. */
.btn { transition: background-color 0.2s ease, transform 0.2s ease; }

Section 19: Keyframe Animations Efficiently

Keyframe animations, defined with @keyframes and applied with the animation property, allow complex, multi-step motion that transitions cannot express, such as a loading spinner that rotates continuously, a banner that slides in and then fades, or an element that pulses repeatedly, and their performance depends on the same property-cost principles as transitions: animating transform and opacity in keyframes will be cheap, while animating layout or paint properties in keyframes will be expensive, frame after frame, for the animation's entire duration, which may be infinite for spinners or pulsing effects, making per-frame cost even more critical than for short transitions. An infinite layout animation, for example, will trigger layout continuously for as long as the page is open, consuming main-thread time and battery, even when the animated element is off-screen or unnoticed, which is a significant waste that a transform-based infinite animation would avoid, because compositing is cheaper and can often be offloaded to graphics hardware.

Keyframe efficiency also depends on animation duration, iteration count, and the number of animated elements, because a long or infinite animation multiplies per-frame cost over time, while many simultaneous keyframe animations multiply it across elements, potentially overwhelming rendering even if each animation individually is cheap. A page with dozens of pulsing, rotating, or sliding elements, each with its own keyframe animation, may jank even though each animation uses transform, because the compositor must manage dozens of layers and update them all each frame, which can exceed memory or bandwidth limits on low-end devices. Limiting the number of simultaneously animated elements, pausing animations for off-screen elements, and using animation-play-state to pause animations when they are not needed — for example, pausing a spinner when its loading completes, rather than leaving it running hidden — are practical ways to reduce keyframe costs without sacrificing the animations that matter.

Another efficiency consideration for keyframes is the use of animation-fill-mode and the number of keyframe steps: a keyframe animation with many steps, or with complex intermediate values that require interpolation of many properties, will cost more to calculate per frame than a simple two-step animation, though the difference is usually small compared with property costs. More important is to avoid animating properties that trigger layout or paint in keyframes, even for a few steps, because those steps will still trigger expensive stages for their frames, and to prefer transform and opacity for all keyframe steps, even when a layout effect seems more natural, by finding a transform-based equivalent, such as using scale instead of width for a growing effect, or translate instead of left for movement. That substitution, applied consistently to keyframes, ensures that even complex, multi-step animations remain cheap, because every step uses cheap properties.

/* Efficient keyframes: transform and opacity only, pause when hidden. */
@keyframes spin { to { transform: rotate(360deg); } }
.spinner { animation: spin 1s linear infinite; }

Section 20: Transforms and Opacity

Transforms and opacity are the two CSS properties that are most reliably handled in the compositing stage, making them the cheapest properties to animate and the safest choices for motion, and understanding why they are cheap — and what their limits are — helps you use them effectively without overusing them in ways that create new costs. Transform, which includes translate, rotate, scale, skew, and matrix, changes an element's visual position, size, or orientation without changing its layout box, meaning that surrounding elements do not reflow when a transformed element moves, and the transformed element's own layout does not need to be recalculated, because its layout box remains where it was, with only its painted layer moved. That layer-based behaviour is what makes transform cheap: the browser paints the element once, promotes it to a compositor layer, and then moves that layer with graphics hardware, without repainting or reflowing, for each frame of an animation or transition.

Opacity similarly changes an element's transparency without changing its layout or requiring a repaint of its content, because the compositor can blend the element's existing layer at a different opacity, which is a cheap graphics operation, especially when the element is already on its own layer. That cheapness makes opacity ideal for fade effects, for showing and hiding elements with a smooth transition, and for combining with transform for slide-and-fade effects that are both smooth and cheap, because both properties can be handled in compositing together, without triggering layout or paint. Together, transform and opacity cover the vast majority of motion design needs — movement, scaling, rotation, fading — which is why performance guidance so consistently recommends them: they are not just cheap in theory, but sufficient in practice for most animations, making more expensive properties unnecessary for most motion.

There are limits and costs to transforms and opacity that authors should understand, to avoid misusing them in ways that create new problems. Transforming an element does not change its layout box, which means that a transformed element may visually overlap other elements or extend beyond its container, without affecting layout, which can be surprising if the author expected layout to adapt to the transformed position, as it would for a layout property change. That visual-only effect is usually desired for animations, where layout should remain stable while an element moves, but it can be confusing for static transforms, where an element is permanently translated or scaled, yet its layout box remains in its original position, affecting hit-testing, focus order, and surrounding layout in ways that may not match its visual position. Similarly, opacity below one creates a stacking context, which can affect z-index and overlapping in ways that surprise authors who only intended a fade effect, though that side effect is usually manageable once understood.

/* Transform moves the layer, not the layout box. */
.card:hover { transform: translateY(-4px); }

Section 21: Will-Change: Use Sparingly

Will-change is a CSS property that hints to the browser that an element is about to change in a specified way — for example, will-change: transform tells the browser to prepare for transform changes — allowing the browser to optimise in advance, such as by promoting the element to its own compositor layer before the change begins, so that when the change does occur, it can be handled smoothly in compositing without a costly layer promotion mid-animation. That advance preparation can improve animation smoothness for elements that will definitely animate soon, such as a carousel slide that is about to move, or a modal that is about to fade in, because the layer promotion cost is paid before the animation starts, rather than during its first frame, where it could cause a stutter. Will-change is therefore a useful hint for predictable, imminent changes, where the browser's advance work will actually be used and will improve the experience.

The reason will-change must be used sparingly is that its optimisations have costs, primarily memory and layer management, that are paid whether or not the anticipated change actually occurs, and that accumulate when will-change is applied to many elements or left on elements permanently. Promoting an element to its own layer uses additional memory for that layer's pixels, and promoting many elements — for example, applying will-change: transform to every card in a grid, in anticipation that any card might be hovered — can use significant memory, especially on low-end devices, and can actually degrade performance by overwhelming the compositor with too many layers to manage efficiently. Similarly, will-change hints that are left on an element after its animation completes continue to consume memory and to prevent the browser from reclaiming that layer, even though no further change is expected, which is wasteful and can cause the very jank will-change was meant to prevent, by starving other animations of memory.

Best practice for will-change is therefore to apply it sparingly, to a small number of elements, shortly before they change, and to remove it after the change completes, rather than applying it statically in stylesheets to many elements. In practice, that often means toggling will-change through script: adding it on hover intent or on interaction preparation, and removing it on animation end, so that its cost is paid only for the brief period when it is needed. For CSS-only animations, where script toggling is not available, will-change can be applied to the animated element itself, but only if that element is few in number and its animation is frequent or important enough to justify the permanent layer cost, such as a single hero animation or a loading spinner, rather than to every interactive element on a page. That selectivity — few elements, imminent changes, temporary application — is what makes will-change a performance win rather than a cost.

/* Will-change: few elements, imminent change, remove after. */
.carousel-slide { will-change: transform; }

Section 22: Containment: contain and content-visibility

Containment is a CSS feature that tells the browser that an element's subtree is isolated in certain ways — layout, paint, size, or style — allowing the browser to skip rendering work for outside elements when the contained subtree changes, and vice versa, which can significantly improve performance for large pages with many independent sections, such as feeds, dashboards, or lists with many cards. The contain property expresses that isolation explicitly: contain: layout means the element's layout does not affect outside layout, contain: paint means its painting is clipped to its own box and does not overflow outside, contain: size means its size does not depend on its children's size, and contain: style means its counters and quotes do not affect outside elements, with contain: content as a shorthand for layout, paint, and style, and contain: strict as a shorthand for all, including size. Each type of containment allows the browser to optimise differently, by limiting the scope of recalculation when the contained element changes, so that a change inside a contained card, for example, does not trigger layout or paint for the whole page, but only for that card's subtree.

Content-visibility is a related feature that goes further, by allowing the browser to skip rendering work entirely for off-screen content, until it approaches the viewport, at which point it is rendered on demand. Content-visibility: auto, applied to a section or card that is initially off-screen, tells the browser that it may skip layout and paint for that section's contents until they are near the viewport, which can dramatically improve initial load and rendering time for long pages with much below-the-fold content, because the browser does not need to render content readers have not yet scrolled to. Setting an approximate intrinsic size for off-screen sections, based on typical content height, mitigates that shift, though it requires tuning for each section type.

Both containment and content-visibility require care, because incorrect containment can break layout or appearance in ways that are hard to diagnose. Contain: size, for example, requires the element to have an explicit size, because its size will no longer be determined by its children, so an element with contain: size but without a set height may collapse to zero height, hiding its content, which looks like a bug rather than an optimisation. Contain: paint clips overflowing content, so an element with dropdowns, tooltips, or shadows that extend beyond its box may have those parts clipped unexpectedly when paint containment is applied, breaking its design. Content-visibility: auto can break features that depend on off-screen content being rendered, such as find-in-page for text in off-screen sections, or script that measures off-screen elements' sizes, because those elements may not be rendered until they scroll into view, and their measurements may be unavailable or approximate until then. Those side effects mean containment should be applied selectively, to sections where its isolation is genuinely true, and tested with real content and interactions, rather than applied globally to all sections in the hope of a performance win.

/* Containment isolates a subtree; content-visibility skips off-screen work. */
.feed-card { contain: content; }
.long-section { content-visibility: auto; }

Section 23: Avoiding Layout Thrashing

Layout thrashing is a performance problem that occurs when script repeatedly reads layout information — such as an element's size or position — and then writes style changes that invalidate layout, in an alternating read-write pattern that forces the browser to recalculate layout many times in a single frame or task, rather than batching reads and writes efficiently. Though layout thrashing is primarily a script problem, CSS contributes to it through the properties and structures that script interacts with: a stylesheet with many layout-dependent properties, complex selectors, or large subtrees that must be recalculated on each layout pass will make each thrashing iteration more expensive, amplifying the script problem. Understanding thrashing from a CSS perspective therefore means understanding how stylesheet choices affect the cost of each layout recalculation, and how to structure CSS so that even if script thrashes, each recalculation is as cheap as possible, though the primary fix for thrashing remains in script — batching reads, then batching writes, rather than interleaving them.

From a CSS standpoint, the cost of a layout recalculation depends on the size of the subtree that must be laid out, the complexity of its layout properties, and whether containment isolates that subtree from the rest of the page. A page with a flat, simple layout, where most elements use flex or grid with straightforward sizing, will recalculate layout faster than a page with deeply nested, interdependent layouts, where a change to one element's size propagates through many ancestors and descendants. Similarly, a page that uses containment for independent sections will recalculate only the affected section on a change inside it, while a page without containment may recalculate much more, because the browser cannot assume that a change inside one section does not affect others. Those CSS choices — simple layouts, containment for independent sections — reduce thrashing cost, even though they do not eliminate thrashing itself, which requires script changes to batch operations.

Another CSS contribution to thrashing is the use of properties that force synchronous layout when read by script, such as offsetWidth, offsetHeight, or getBoundingClientRect, which return layout information that must be up to date, forcing the browser to recalculate layout immediately if styles have changed since the last layout, rather than waiting for the next frame's scheduled layout. That forced synchronous layout is expensive, especially if it occurs repeatedly in a loop that alternates reads and writes, because each read forces a full layout pass before the next write can proceed. CSS cannot prevent script from reading layout properties, but it can reduce the cost of each forced layout by keeping layouts simple and contained, and by avoiding layout properties that are particularly expensive to recalculate, such as those involving complex grids, tables with auto layout, or deeply nested flex containers with many items, where each layout pass must resolve many interdependent sizes.

/* Simple layouts and containment make each layout pass cheaper. */
.feed-card { contain: layout; }

Section 24: Fonts and CSS Performance

Fonts affect CSS performance in several ways, because web fonts must be downloaded, parsed, and applied before text can render in its intended typeface, and during that download, browsers must decide whether to show fallback text, hide text until the font arrives, or swap fonts once the download completes, each choice affecting perceived performance and layout stability. A page that uses several web font families, each with multiple weights and styles, may need to download many font files, each tens of kilobytes, which adds to total page weight and to critical path length if fonts block text rendering, especially on slower connections where font downloads compete with stylesheet, image, and script downloads for bandwidth.

Font display strategies, controlled through font-display in @font-face rules, determine how the browser handles text while fonts are downloading, and each strategy trades off between showing text quickly and avoiding layout shifts or flashes when fonts swap. Font-display: swap shows fallback text immediately, then swaps to the web font when it arrives, which ensures text is readable quickly but causes a flash of unstyled text and a potential layout shift if the web font's metrics differ from the fallback's, which can be jarring and can affect cumulative layout shift scores. Font-display: block hides text for a short period while the font downloads, then shows it in the web font, avoiding a flash but delaying text visibility, which can feel slow if the font download is slow. Font-display: fallback and optional provide intermediate behaviours, with shorter block periods or with a preference for fallback if the font does not arrive quickly, each suited to different priorities — readability speed versus visual stability — and the choice should be made deliberately for each font, based on how critical that font is to the page's design and readability.

Font loading can also be optimised through preloading, subsetting, and format choices, each of which reduces font cost without changing design significantly. Preloading a critical font — for example, the main text font used for headings and body — with a link preload tells the browser to download it early, in parallel with the stylesheet, rather than discovering it only after the stylesheet is parsed, which shortens the time until text renders in its intended font. Subsetting a font to include only the characters actually used on a site — for example, Latin characters only, rather than full Unicode coverage — can dramatically reduce font file size, especially for fonts with large character sets, though it requires tooling and care to ensure that needed characters, such as accented letters or symbols used in content, are not omitted, which would cause those characters to render in a fallback font inconsistently. Format choice also matters: modern formats such as WOFF2 compress better than older formats, producing smaller files for the same typeface, and serving WOFF2 to supporting browsers, with a fallback for older browsers, is a standard optimisation that should be part of any font loading strategy.

/* Font loading: preload critical fonts, subset, prefer WOFF2. */
@font-face {

Section 25: Font Loading Strategies

Font loading strategies are the set of techniques used to deliver web fonts efficiently and to handle the period while they are downloading, and choosing a strategy requires balancing design goals — distinctive typography, consistent branding — against performance goals — fast text rendering, minimal layout shift, and low total page weight. The simplest strategy is to load no web fonts at all, using only system fonts, which is fastest and most stable, but least distinctive, and it is appropriate for sites where typography is not a brand differentiator, or where performance on slow connections is paramount, such as for readers in areas with limited bandwidth. That strategy's simplicity is its strength: no font downloads, no flash of unstyled text, no layout shifts from font swaps, and no font loading code to maintain, which makes it attractive for performance-focused sites, even though it sacrifices typographic distinctiveness.

A more common strategy is to load a small number of web fonts — typically one family for headings and one for body, each with one or two weights — using font-display: swap or fallback, with preloading for the most critical font, and with subsetting and WOFF2 formats to minimise size. That strategy balances distinctiveness and performance, by limiting font count and weight, which are the main drivers of font cost, while still allowing a distinctive typeface for headings, where it has the most visual impact, and a readable typeface for body text, where it matters most for long reading. It requires discipline to keep font count low, because it is tempting to add a new font for each new design element — a display font for heroes, a mono font for code, a serif font for quotes — each addition increasing download size and critical path length, often without a corresponding design benefit that justifies its cost. A font budget, similar to a CSS size budget, can enforce that discipline, by limiting total font weight per page and requiring justification for new fonts.

Advanced font loading strategies include using the Font Loading API in script to control when fonts are applied, such as loading a font only when it is needed for a specific component, or swapping fonts after they are loaded to avoid flashes, and using variable fonts, which encode multiple weights and styles in a single file, rather than requiring separate files for each weight, potentially reducing total download size when many weights are needed, though variable font files themselves are larger than a single-weight file, so their benefit depends on how many weights are actually used. Those advanced strategies require script and build tooling, and they should only be adopted when their benefit is measured, because their complexity can introduce bugs — such as fonts not loading in certain browsers, or variable font axes not rendering correctly — that outweigh their performance gains for most sites. For most projects, the simple strategy — few fonts, swap or fallback display, preload critical, subset, WOFF2 — provides most of the benefit with the least complexity, and advanced strategies should be reserved for sites where font performance is a measured bottleneck.

/* Few fonts, swap display, preload critical, subset, WOFF2. */
@font-face {
  font-family: "Site Headings"; src: url("headings.woff2") format("woff2");
  font-display: swap;
}

Section 26: Images, Backgrounds and Paint

Images and CSS backgrounds affect paint performance because they require the browser to decode image data, scale it to its display size, and paint its pixels, often over large areas, which can be expensive, especially for large images, high-resolution images on small displays, or backgrounds that repeat, cover, or use complex positioning. A background image that covers a large hero section, for example, must be decoded, scaled to cover the section, and painted across its entire area, which costs more than painting a solid colour, and that cost is paid on initial paint and again on every repaint that affects that area, such as when content above it changes or when the page is scrolled and the background must be repainted. Optimising images for CSS backgrounds therefore involves both image optimisation — choosing appropriate formats, sizes, and compression — and CSS optimisation — using background-size, position, and repeat efficiently, and avoiding backgrounds that require expensive scaling or tiling on every paint.

Background-size choices affect paint cost in subtle ways: a background with size cover or contain must be scaled to fit its container, which requires resampling image pixels, a operation whose cost grows with image size and with container size, while a background with a fixed size that matches its natural size requires no scaling and is cheaper to paint. Similarly, a repeating background, such as a small pattern tiled across a large area, requires painting the pattern many times, which can be expensive if the pattern is complex or if the area is large, though browsers optimise tiling for simple patterns. A background with background-attachment: fixed, which keeps the background fixed while content scrolls, is particularly expensive, because it requires repainting the background on every scroll frame, as content moves over it, which can cause jank on scrolling, especially on mobile devices where scrolling is frequent and graphics resources are limited. Avoiding fixed backgrounds, or using them only for small areas, is a practical paint optimisation for scrolling performance.

Image format and size choices, though often considered outside CSS, interact with CSS paint because the browser paints the image as specified by CSS, regardless of its intrinsic size, and an image that is much larger than its display size wastes decode and scaling time, as well as download time, for pixels that will never be seen at full resolution. Serving appropriately sized images — for example, a hero image sized for its display width, with responsive variants for different viewports, rather than a single very large image for all viewports — reduces both download and paint costs, and it should be coordinated with CSS, so that background-size and image dimensions match the intended display, rather than relying on CSS to scale a huge image down to a small area. That coordination between image assets and CSS is part of paint performance, even though image optimisation itself is often handled by build tools or content management systems, because CSS determines how images are displayed and therefore how much paint work they require.

/* Background paint: avoid fixed attachment on large areas. */
.hero { background-image: url("hero.jpg"); background-size: cover; }

Section 27: Shadows, Filters and Blur Costs

Shadows, filters, and blur effects are visually appealing CSS features that can significantly increase paint cost, because they require the browser to calculate pixel values that depend on neighbouring pixels, rather than simply filling an area with a solid colour, and that calculation grows with the size of the affected area and with the blur radius or filter complexity. A box-shadow with a large blur radius, for example, requires blurring the shadow's shape over a large area, sampling many neighbouring pixels for each output pixel, which is expensive for large elements or for many elements with shadows, such as a grid of cards each with a large, soft shadow, where the cumulative shadow paint cost can dominate total paint time. Similarly, a drop-shadow filter, which shadows an element's rendered shape rather than its box, requires rendering the element, then blurring its alpha channel, which is more expensive than a box-shadow for the same visual effect, because it involves an extra rendering pass.

Filters in general — blur, brightness, contrast, grayscale, hue-rotate, and others — each require per-pixel calculations, and combining multiple filters multiplies that cost, because each filter must be applied in sequence to every pixel in the element's area. A backdrop-filter, which blurs or otherwise filters the content behind an element, such as a frosted-glass modal or navigation bar, is particularly expensive, because it requires sampling and filtering the backdrop content, which may itself be complex and changing, on every paint, and it can cause significant paint cost for even a small backdrop area if the backdrop is complex. That cost is why backdrop-filter should be used sparingly, for small, stable areas, rather than for large, scrolling, or frequently changing backgrounds, where its paint cost will be paid repeatedly and may cause jank, especially on low-end devices where graphics processing is limited.

Optimising shadows and filters involves reducing their area, blur radius, and frequency, while preserving their visual effect as much as possible. A smaller blur radius, a smaller shadow area, or a shadow that is applied only on hover rather than always, will all reduce paint cost, because less area needs to be blurred and fewer frames require shadow calculation. For static shadows, pre-rendering or using a simpler shadow — for example, a solid border or a small, hard shadow instead of a large, soft one — can achieve a similar depth effect with much lower paint cost, and for filters, applying them to small elements or to elements that do not change frequently, rather than to large, animated, or scrolling elements, limits their cost to occasions where it is justified. Those trade-offs — visual richness versus paint cost — should be made deliberately, based on profiling that shows which shadows or filters actually dominate paint time, rather than by removing all shadows and filters indiscriminately, which would sacrifice design for a performance gain that may not be needed.

/* Large blurs are expensive: keep radius small and area limited. */
.card { box-shadow: 0 2px 8px rgb(0 0 0 / 0.12); }

Section 28: Borders, Gradients and Paint

Borders and gradients are common CSS visual features whose paint costs are generally modest, but which can become significant when used extensively, with complex patterns, or on large areas, and understanding their costs helps authors choose efficient variants without sacrificing design. Borders themselves are cheap to paint when they are solid, thin, and simple, because the browser can fill a border area with a solid colour quickly, but border styles such as dashed, dotted, or double require more complex pixel calculations to render their patterns, especially for thick borders or for borders on large elements, where the pattern must be repeated many times. Border-radius also adds cost, because rounded corners require clipping and anti-aliasing to render smooth curves, which is more expensive than square corners, though the difference is small for typical radii and element sizes, and it becomes noticeable only for very large radii, for many elements with rounded corners, or for animated border-radius changes, which require repainting the rounded shape on every frame.

Gradients, whether linear, radial, or conic, require the browser to calculate colour interpolation for each pixel in the gradient area, based on its position and on the gradient's colour stops, which is more expensive than painting a solid colour, where every pixel has the same value and can be filled quickly. That cost scales with gradient area and with the number of colour stops and the complexity of the gradient's shape: a simple two-colour linear gradient over a small button is cheap, while a multi-stop radial gradient over a large hero section, especially one that animates or changes on interaction, can be measurably more expensive to paint, though still usually less expensive than a large blurred shadow or a backdrop filter. Gradients that are static and painted once at load are less concerning than gradients that are animated or that cover areas that repaint frequently, because static paint cost is paid once, while animated or frequently repainted gradients pay their cost on every frame or repaint, multiplying their impact.

Optimising borders and gradients involves choosing simpler variants where the visual difference is negligible, such as using a solid border instead of a dashed one for a large element, or a two-stop linear gradient instead of a multi-stop radial one for a background, and avoiding animating border-radius or gradient properties, which trigger paint on every frame and can cause jank, especially for large elements. For animated gradient effects, alternatives such as animating opacity between two gradient layers, or animating transform for a gradient's position, can achieve a similar visual effect with lower paint cost, because opacity and transform are handled in compositing, while gradient interpolation requires repainting. Those alternatives require more markup or more complex CSS, but they are worth considering when a gradient animation is central to a design and its paint cost is measured to be high, because they preserve the visual effect while moving its cost to a cheaper stage.

/* Gradients cost more than solid colours; keep them simple and static. */
.hero { background: linear-gradient(180deg, #0b5fff, #0842a0); }

Section 29: Media Queries and Performance

Media queries affect performance primarily through the styles they enable or disable at different viewport sizes, rather than through the queries themselves, which are cheap to evaluate, because the browser only needs to check viewport width, height, orientation, or other media features, which change infrequently, typically only on resize or orientation change, rather than on every frame. That infrequent evaluation means that media queries themselves do not cause ongoing performance costs, unlike animations or frequent style changes, and a stylesheet with many media queries will not be noticeably slower than one with few, as long as the rules inside those queries are efficient. The performance impact of media queries comes from the rules they contain: a media query that enables a complex layout, large backgrounds, or many shadows at a certain viewport size will incur those rules' layout and paint costs only when that query matches, which is the intended behaviour, but it also means that performance can vary dramatically by viewport, with a desktop layout being more expensive than a mobile layout, or vice versa, depending on which rules each query enables.

That viewport-dependent performance variation should be considered when designing responsive layouts, because a layout that is efficient on mobile, where it stacks content vertically with simple styles, may become expensive on desktop, where it uses a complex grid, large images, and multiple shadows, or vice versa, and testing performance at only one viewport may miss costs that appear at another. Performance testing should therefore include multiple viewports — mobile, tablet, and desktop, at least — checking load, layout, and paint times at each, and identifying viewport-specific bottlenecks, such as a desktop grid that triggers expensive layout, or a mobile layout that paints large backgrounds unnecessarily. That multi-viewport testing ensures that responsive design does not inadvertently create a performance problem at a viewport that was not tested, which is a common oversight when performance is only checked on a developer's primary viewport.

Media queries also interact with stylesheet size and delivery, because all media query rules are downloaded and parsed regardless of whether their queries currently match, even though only matching rules are applied to rendering. That means a stylesheet with extensive desktop-only rules will still be downloaded and parsed on mobile, where those rules do not apply, increasing download and parsing costs for mobile readers without benefit, unless the stylesheet is split by media, using link elements with media attributes that allow the browser to download non-matching stylesheets at lower priority or not at all, depending on browser behaviour. Splitting by media, through separate link elements for print, screen, or specific viewport ranges, can reduce critical download and parsing costs for the current viewport, though it adds request complexity and requires careful ordering to preserve cascade behaviour, as discussed for splitting generally. For most sites, a single stylesheet with media queries is simpler and its download cost is acceptable, but for very large stylesheets with large viewport-specific sections, media splitting may be worth considering, measured against its complexity.

/* Media queries themselves are cheap; their rules determine cost. */
@media (min-width: 40rem) {
  .card { padding: 2rem; }
}

Section 30: Container Queries Cost

Container queries, which allow a component to respond to its container's size rather than the viewport's, carry performance considerations that are similar to media queries but with additional complexity, because container size can change more frequently and for more reasons than viewport size, such as when content inside the container changes, when siblings resize, or when layout shifts due to interaction, each of which may trigger container query re-evaluation for components inside that container. That more frequent re-evaluation means that container query rules may be checked more often than media query rules, though the check itself — comparing container size against a query condition — is cheap, and the main cost, as with media queries, comes from the rules that container queries enable, such as layout changes, which trigger layout and paint when they switch on or off. A container query that switches a card from stacked to horizontal layout when its container widens will trigger layout for that card and potentially for its surroundings, which is the intended behaviour, but if that switch occurs repeatedly due to content changes that oscillate container size around the breakpoint, it can cause layout thrashing or flickering, where the layout switches back and forth rapidly, degrading performance and user experience.

Avoiding container query loops, where a query's result changes the container's own size, which then changes the query's result again, is a key container query performance concern, because such loops can cause unstable layout that never settles, or that settles only after many iterations, each triggering layout and paint. That risk is highest when a container query changes properties that affect the container's size itself, such as padding, margin, or width of the container, rather than properties that affect only the component's internal layout, which does not affect the container's size. Designing container queries to change only internal layout — for example, a card's internal grid, not its own width — avoids loops, because the component's internal change does not feed back into its container's size, breaking the loop at its source. That design principle — container queries should affect descendants, not the container itself — is both a correctness and a performance guideline, because it prevents the most expensive container query failure mode.

Container queries also require the browser to track container sizes and to establish containment for query containers, which adds a small overhead compared with media queries, because the browser must observe container dimensions and maintain query state for each container, rather than only for the viewport. That overhead is generally small for a reasonable number of containers, but it can grow if every element on a page is made a container, or if containers are nested deeply, creating many query evaluations on each layout change. Limiting container queries to components that genuinely need them — reusable components that appear in different widths — rather than applying them universally, keeps that overhead manageable, while still gaining container queries' benefits for the components that need them most. That selectivity mirrors the general performance principle of using a feature where it solves a real problem, not everywhere it could theoretically be used.

/* Container queries: change internal layout, not container size itself. */
.card { container-type: inline-size; }

Section 31: Layers, Scope and Performance

Layers and scope affect performance mainly through how they change style matching and recalculation, though their direct costs are usually small compared with layout, paint, and file size. Layers add a sorting step to the cascade: the browser must determine each rule's layer before comparing specificity, which is a small additional check per rule, but one that is highly optimised and does not noticeably slow matching for typical stylesheets. Scope adds a boundary check: the browser must determine whether an element is inside a scope root and outside its limit, which requires walking ancestors to find the nearest scope root, a cost that grows with tree depth but remains small for shallow, well-structured documents. Neither mechanism inherently makes a page slow, and both can improve performance indirectly, by enabling simpler selectors and clearer organisation that reduce matching and maintenance costs elsewhere.

The indirect performance benefit of layers is that they allow low-specificity selectors to win through layer order, rather than through long, specific selectors that are more expensive to match and harder to override. A utility in the last layer, for example, can be a single class that reliably beats a component, whereas without layers, that utility might need a longer selector or an important flag to win, increasing matching cost and cascade complexity. Similarly, scope allows component styles to be local without long descendant chains, because the scope boundary itself provides locality, so a scoped rule can be a simple class inside a scope, rather than a deep descendant selector that describes the component's ancestry. Those simplifications — shorter selectors enabled by layers and scope — are where the real performance benefit lies, not in layers or scope themselves, but in the selector simplicity they make possible.

There are cases where layers and scope could hurt performance if misused, though those cases are rare and usually involve extreme patterns. A stylesheet with dozens of layers, each containing many rules, could increase cascade sorting cost, though that cost remains small compared with layout and paint, and it would only become noticeable on very large stylesheets with frequent recalculations. A scope with a very broad root, such as the body, combined with many scoped rules that must be checked for every element, could increase boundary-checking cost, because every element must be checked against that broad scope, though again, that cost is small for typical pages. The practical guidance is therefore not to avoid layers or scope for performance reasons, but to use them sensibly — a handful of layers with clear purposes, scopes rooted at components rather than at the whole document — so that their costs remain negligible and their organisational benefits dominate.

Use layers and scope for organisation first, and let their selector simplifications provide any performance benefit as a bonus.

/* Layers and scope enable short selectors; that is their performance win. */
@layer components, utilities;

Section 32: Custom Properties Performance

Custom properties, or CSS variables, affect performance through style recalculation, because changing a variable's value on an element can trigger recalculation for all descendants that use that variable, as well as for the element itself, since the variable's computed value must be resolved at each point of use. That propagation is the same inheritance mechanism that makes variables powerful for theming — changing a token on a container updates every component inside it — but it also means that a variable change on a high ancestor, such as the root or body, can trigger recalculation for thousands of descendants, even if only a few of them actually use the variable in a way that affects their rendered appearance. That broad recalculation cost is usually small per element, because resolving a variable is a simple lookup, but it scales with subtree size and with change frequency, so a variable that changes frequently, such as one animated or updated by script on every frame, can cause significant recalculation work if it is defined on a high ancestor with many descendants.

The frequency and scope of variable changes are therefore the key performance considerations for custom properties. A variable that changes rarely, such as a theme token that changes only when a reader switches themes, will trigger recalculation only on theme switch, which is infrequent and acceptable, even if it affects many elements, because the cost is paid once per switch, not continuously. A variable that changes frequently, such as one driven by scroll position, mouse movement, or an animation, will trigger recalculation on every change, and if that variable is defined on a high ancestor, each change will recalculate a large subtree, potentially causing jank, especially on large pages. For frequently changing variables, defining them on the smallest subtree that needs them — for example, on the animated element itself, rather than on the root — limits recalculation to that subtree, reducing cost dramatically, even though the variable's value is the same in effect for that element.

Another performance consideration is the number of variables and their use in complex calculations, such as calc() expressions that combine multiple variables, which must be re-evaluated whenever any variable in the expression changes. A calc() expression with many variables, used on many elements, will cost more to recalculate than a simple variable reference, though the difference is usually small compared with layout and paint costs, and it only matters when variables change frequently or when the expression is used on many elements. Keeping calc() expressions simple, and avoiding deeply nested variable references where a direct value would suffice, reduces recalculation cost, though the saving is modest and should not be pursued at the cost of readability or maintainability, because variable-based calculations are often clearer than hard-coded values, even if they cost slightly more to resolve.

/* Variables recalculate descendants; keep frequent changes local. */
.card { --accent: #0b5fff; color: var(--accent); }

Section 33: CSS Variables and Recalculation

CSS variables and recalculation are linked through inheritance: when a variable's value changes on an element, the browser must recalculate styles for that element's descendants, because each descendant's computed value for that variable may have changed through inheritance, even if the descendant does not directly use the variable in its own rules. That recalculation is necessary for correctness, because a descendant that uses the variable with var() must get the new value, and the browser cannot know which descendants use the variable without checking them, though it optimises by tracking variable dependencies where possible. The cost of that checking scales with subtree size, so a variable change on a leaf element with few descendants is cheap, while a change on the root with thousands of descendants is more expensive, even if only a handful of those descendants actually consume the variable, because the browser must still walk the subtree to determine which ones do.

Recalculation cost also depends on what the variable affects: a variable used for colour will trigger paint recalculation for elements that use it, because their colours change, while a variable used for layout, such as spacing or width, will trigger layout recalculation, which is more expensive, because layout changes can affect siblings and ancestors as well as descendants. That distinction — colour variables trigger paint, layout variables trigger layout — mirrors the general layout-paint-composite hierarchy, and it means that frequently changing a layout variable, such as one controlling spacing or size, will be more expensive than frequently changing a colour variable, even if both are defined on the same element and affect the same number of descendants. Choosing variables for paint properties where possible, and avoiding frequent changes to layout variables, especially on high ancestors, reduces recalculation cost for dynamic variables.

Another factor is whether variable changes are batched or frequent: a theme switch that changes many variables at once will trigger one recalculation pass that handles all changes together, which is efficient, because the browser can batch style updates and layout passes, rather than recalculating separately for each variable. By contrast, a script that changes variables one by one in a loop, with layout reads between changes, will trigger multiple recalculation passes, each more expensive than a single batched pass, which is a form of layout thrashing applied to variables. Batching variable changes — setting all theme variables together, or setting a theme class that redefines many variables at once, rather than setting each variable individually with reads in between — allows the browser to optimise recalculation and is a practical habit for script-driven variable changes, similar to batching style writes generally.

Measure variable recalculation before optimising it, because most pages change variables rarely and their cost is already low.

/* Batch variable changes; avoid layout variables changing frequently. */
:root { --gap: 1rem; }

Section 34: Reducing Repaints

Reducing repaints means minimising the number of times, and the area over which, the browser must repaint pixels, because repainting is a significant rendering cost, especially for large elements, complex visuals, or frequent changes, and it can cause jank when it occurs on every frame of an animation or interaction. Repaints are triggered whenever an element's visual properties change in a way that affects its pixels, but not its layout — for example, changing colour, background, border, shadow, or opacity in a way that requires repainting, rather than compositing alone — and the cost of a repaint scales with the repainted area and with the complexity of the pixels being painted, such as gradients, shadows, or images, which require more calculation per pixel than solid colours. Reducing repaints therefore involves both reducing how often visual properties change, and reducing the area and complexity of what must be repainted when they do change, through techniques such as promoting animated elements to their own layers, so that their repaints do not affect surrounding content, and simplifying visuals for elements that repaint frequently.

One effective technique for reducing repaint area is to isolate frequently changing elements on their own compositor layers, using transform, will-change sparingly, or other layer promotion hints, so that when such an element changes, only its layer needs to be repainted or composited, rather than the entire page or a large subtree. That isolation is particularly valuable for animations, where an element changes every frame: if that element shares a layer with surrounding content, each frame's repaint must repaint both the element and its surroundings, multiplying cost, while if it has its own layer, each frame only composites that layer, without repainting surroundings, which is much cheaper. Layer promotion should be used selectively, as discussed for will-change, because each layer uses memory, but for a few frequently changing elements, such as a carousel slide, a tooltip, or a loading indicator, the repaint saving outweighs the memory cost, making layer isolation a net win.

Another technique is to avoid paint-triggering changes where a composite-only change would achieve the same visual effect, such as using transform instead of top for movement, opacity instead of visibility with paint, or a transform-based scale instead of a width change that would also trigger paint. Those substitutions, discussed for animations, also reduce repaints for interactions, because a transform or opacity change that is handled in compositing does not require repainting at all, while a layout or paint change does, even for a single interaction such as hover. For hover effects, for example, changing a button's background colour on hover will trigger a small repaint of that button, which is acceptable because the area is small and the change is infrequent, but changing a large hero section's background on hover would trigger a large repaint, which might be noticeable, and a transform-based hover effect, such as a slight lift, would be cheaper and often equally effective visually, while avoiding the large repaint entirely.

/* Isolate frequently changing elements on their own layers. */
.tooltip { transform: translateZ(0); }

Section 35: Reducing Reflows

Reducing reflows means minimising layout recalculations, which are the most expensive rendering stage, by avoiding layout-triggering style changes where possible, by batching layout-affecting changes, and by structuring layouts so that changes affect as small a subtree as possible. Reflows are triggered whenever an element's size, position, or layout-affecting properties change, or when content changes in a way that affects layout, such as adding or removing elements, changing text that wraps differently, or resizing the viewport or a container. Each reflow recalculates layout for the affected subtree and potentially for ancestors and siblings, depending on how layout dependencies propagate, so a reflow triggered by a small change in a complex, interdependent layout can be much more expensive than the same change in a simple, contained layout, where the reflow is localised to a small subtree. That localisation — through simple layouts, containment, and avoiding layout dependencies between distant elements — is the key to reducing reflow cost, even when reflows cannot be avoided entirely.

One practical way to reduce reflows is to prefer transform and opacity for visual changes, as discussed, because those properties do not trigger reflow at all, being handled in compositing, while layout properties such as width, height, margin, padding, and position trigger reflow on every change, making them expensive for animations and frequent interactions. For discrete layout changes, such as a breakpoint switch or a content update that genuinely requires a new layout, a single reflow is unavoidable and acceptable, because it occurs once, not on every frame, and its cost is amortised over the time until the next layout change. The problem arises when layout changes occur frequently — for example, on every animation frame, on every scroll event, or in a script loop that alternates reads and writes — because each frequent reflow multiplies its cost, turning a single acceptable reflow into many expensive ones that cause jank. Avoiding frequent layout changes, by using transform for motion and by batching layout-affecting updates, is therefore more important than avoiding layout changes entirely, which is impossible for real pages that must adapt to content and viewport changes.

Another way to reduce reflows is to use containment, as discussed, to isolate layout subtrees, so that a layout change inside a contained element does not propagate outside it, limiting reflow to that element's subtree rather than to the whole page. Contain: layout, applied to independent sections such as cards, feed items, or widgets, tells the browser that those sections' internal layout does not affect outside layout, allowing it to skip outside layout work when inside layout changes, which can dramatically reduce reflow cost for large pages with many independent sections, where a change to one section would otherwise trigger layout for the whole page. That containment must be applied correctly, with an understanding of its side effects, such as size containment requiring explicit sizes, but when applied to genuinely independent sections, it is a powerful reflow optimisation that requires no change to the sections' internal styles, only an added containment declaration.

/* Avoid frequent layout changes; use transform for motion. */
.slider { transform: translateX(0); }

Section 36: Efficient Hover and Focus Styles

Efficient hover and focus styles are those that provide clear visual feedback for interaction without triggering expensive layout or large repaints, because hover and focus changes occur frequently — every time a reader moves a mouse over an element or tabs to a new element — and their cost, though small per interaction, can accumulate if many elements have expensive hover styles or if hover styles affect large areas. A hover style that changes a button's background colour, for example, triggers a small repaint of that button, which is cheap and acceptable, because the button is small and the repaint is infrequent, occurring only when the reader hovers that specific button. A hover style that changes a large section's layout, such as expanding its width or changing its margin, triggers a reflow for that section and potentially for surrounding content, which is more expensive and can cause a noticeable layout shift that feels janky, especially if the reader moves the mouse quickly across many such sections, triggering many reflows in succession. Choosing hover properties that are cheap — colour, transform, opacity, shadow with small blur — over expensive ones — width, margin, layout — keeps hover feedback smooth, even when readers interact rapidly.

Focus styles deserve similar efficiency consideration, with the added requirement that they must remain highly visible, because focus is essential for keyboard navigation, and a focus style that is cheap but invisible fails its purpose, while one that is visible but expensive may cause jank when tabbing quickly through many elements. A focus style using outline, which is painted outside an element's box without affecting layout, is both visible and cheap, because it does not trigger reflow and its paint area is limited to the outline's border, making it ideal for focus feedback that must be applied to many elements in succession as a reader tabs through a page. A focus style that changes an element's size, padding, or border width, by contrast, would trigger layout or larger paint, and could cause layout shifts as focus moves, which is distracting and potentially disorienting for keyboard users, who rely on stable layout to navigate. Outline-based focus, with sufficient contrast and thickness, is therefore the efficient and accessible choice for most focus styles, supplemented by transform or colour changes where additional feedback is desired, but without layout changes.

Hover and focus styles should also be tested for performance in context, by hovering and tabbing through a page's interactive elements and observing whether feedback feels immediate and smooth, or whether it lags or causes layout shifts, especially on lower-end devices where paint and layout costs are higher. That testing, combined with profiling that shows paint and layout times for hover and focus interactions, reveals whether a particular hover style is actually expensive in practice, or whether it is merely theoretically expensive but practically fine for the elements and frequencies involved. A hover shadow with a large blur on a large card, for example, may be noticeably slower than a small shadow on a button, and that difference will be visible in testing, guiding a decision to reduce blur radius or to use a transform lift instead of a shadow change for large cards, preserving feedback while reducing cost.

Section 37: Print and Performance

Print styles affect performance in a different way from screen styles, because printing involves rendering a page for paper, often with different layout, pagination, and media handling, and because print stylesheets, though usually small, can trigger a full re-render of the page in print layout when a reader chooses to print, which can be slow if the print stylesheet is large or if it forces complex layout changes for the entire document. That print rendering cost is paid only when printing, which is infrequent for most readers, so print performance is less critical than screen performance for most sites, but it still matters for readers who print frequently, such as for articles, receipts, or forms, where a slow print preview or a broken print layout can be frustrating, especially if the print stylesheet causes the page to reflow extensively or to download additional resources, such as print-specific images or fonts, that delay printing.

Print stylesheets should therefore be kept small and focused, containing only the adjustments that differ for print — hiding navigation, decorative backgrounds, and interactive elements, adjusting colours for black-and-white printing, and controlling page breaks — rather than duplicating the entire screen stylesheet with print-specific versions of every rule, which would increase both file size and print rendering time without benefit. That minimal print approach, discussed in earlier chapters for nesting and organisation, also benefits performance, because a small print stylesheet parses and applies quickly, and its layout changes are limited to the elements that actually differ for print, rather than reflowing the whole page unnecessarily. A print stylesheet that is loaded with a media attribute for print will also not block screen rendering, because the browser can download it at lower priority or defer it until printing, which is a performance benefit for screen readers who never print, as they do not pay the cost of downloading and parsing print rules that they will never use.

Page breaks are a specific print performance and layout concern, because controlling breaks — for example, avoiding breaks inside tables, cards, or headings, or forcing breaks before sections — requires the browser to calculate pagination, which involves layout for the entire printed document, including content that may span many pages. Excessive or conflicting break rules can cause the browser to recalculate pagination multiple times, or to produce a printed document with many pages and awkward breaks, which is both a performance and a usability problem. Using break rules sparingly, only where they genuinely improve printed readability, such as keeping a heading with its following paragraph or keeping a table row intact, and testing printed output with real content at different lengths, ensures that break rules help rather than hinder print performance and quality.

  .nav { display: none; }
}

Section 38: Dark Mode Performance Notes

Dark mode performance is generally similar to light mode performance, because switching themes typically involves changing colour variables or theme classes, which triggers paint recalculation for elements whose colours change, but not layout recalculation, unless the theme also changes layout properties such as spacing or sizing, which it should not, as discussed for themes generally. That paint-only cost, paid once per theme switch, is usually acceptable, because theme switches are infrequent — a reader switches themes once per session, or when their system preference changes, not continuously — and because paint for colour changes, even across many elements, is relatively cheap compared with layout, especially if colours are changed through variables that are resolved efficiently. Dark mode therefore does not introduce a significant ongoing performance cost, beyond the one-time paint cost of switching, which is a reassuring conclusion for sites that offer dark mode, as long as theme changes are implemented through variables or theme classes that change only colours, not layout.

There are dark mode performance pitfalls to avoid, however, particularly around images, shadows, and filters that may need different treatment in dark mode, and around theme switches that transition colours over time, which can cause many paint frames if the transition is applied to many elements simultaneously. An image with a transparent background that looks fine on light mode may need a different treatment in dark mode, such as a background or a filter, and applying a filter to many images on theme switch could trigger expensive paint for each image, especially if the filter involves blur or colour adjustments that require per-pixel calculations. Similarly, a theme switch that animates colours over several hundred milliseconds, with a transition on every element, will trigger paint on every frame for every element whose colour changes, which can cause a noticeable stutter during the switch, even though each individual colour paint is cheap, because the aggregate paint across many elements and many frames is large. Avoiding global colour transitions on theme switch, or limiting them to a few key elements, prevents that aggregate cost, while still providing a smooth switch through an instant change or a short, targeted transition.

Another dark mode performance consideration is the use of prefers-color-scheme media queries versus theme classes, because media query-based dark mode, which responds to system preference, is applied by the browser without script, and its cost is the same as any media query — evaluated only when the preference changes, which is infrequent — while class-based dark mode, which requires script to toggle a class and potentially to persist the preference, adds a small script cost but allows reader choice independent of system preference, which many sites offer as a toggle. Either approach is performant for theme switching, as long as the theme change itself is paint-only and not layout-affecting, and the choice between them should be based on user experience — system preference versus manual toggle — rather than on performance, because their performance difference is negligible compared with the paint cost of the theme change itself, which is the same in both cases.

/* Dark mode switch: paint only, no layout, no global transition. */
.theme-dark { --color-bg: #111; --color-text: #eee; }

Section 39: Third-Party CSS Costs

Third-party CSS — stylesheets from libraries, frameworks, widgets, embeds, and advertising or analytics providers — can dominate a page's CSS performance costs, because third-party files are often large, are loaded from external servers with additional network costs, and may contain many rules that are never used on the page, yet must still be downloaded, parsed, and matched, increasing load and rendering times without corresponding benefit. A single third-party widget, for example, might ship a stylesheet of tens of kilobytes, with styles for many widget variants, only a few of which appear on a given page, yet the entire file must be downloaded and parsed, because the browser cannot know which rules are unused without analysing the widget's markup, which it does only after downloading. That unused third-party cost is similar to unused first-party cost, but harder to control, because the file is not authored by the site team and cannot be easily edited or purged without risking breakage when the third party updates, as discussed for vendor files generally.

Network costs for third-party CSS are also significant, because external files require additional DNS lookups, connections, and potentially slower servers than the site's own server, each adding latency to the critical rendering path if the third-party stylesheet is render-blocking, as many are when loaded in the head. That latency can delay first paint, even if the third-party file itself is small, because the browser must wait for the external server to respond before it can proceed, and on slow or unreliable third-party servers, that wait can be long and variable, making page performance unpredictable and dependent on external infrastructure that the site team does not control. Mitigations for third-party network costs include loading third-party styles asynchronously where possible, hosting critical third-party styles locally where licensing allows, and deferring non-critical third-party widgets until after initial rendering, so that they do not block first paint, even if they still add cost later.

Third-party CSS can also cause cascade and specificity costs, because its rules may conflict with first-party styles, requiring overrides that increase stylesheet size and complexity, or may use high specificity, important flags, or global selectors that affect first-party elements unintentionally, causing visual bugs that require debugging and fixing, which is a maintenance cost as well as a performance cost. A third-party stylesheet that styles all buttons globally, for example, will affect first-party buttons, requiring overrides to restore their intended appearance, and those overrides add rules and increase matching work, even though they merely undo third-party effects. Evaluating a third-party library's CSS before adopting it — checking its size, its specificity, its global selectors, and its layer behaviour — helps predict those costs, and choosing a library with a small, scoped, layered stylesheet will save both performance and maintenance costs compared with a large, global, high-specificity one, even if the latter offers more features.

Section 40: Framework CSS Costs

Framework CSS — stylesheets from comprehensive frameworks that provide a full design system, grid, components, and utilities, such as Bootstrap, Tailwind in its unpurged form, or similar — can be large, because frameworks are designed to be general-purpose, covering many components and utilities that a given site may not use, yet shipping all of them by default unless the site configures the framework to include only needed parts or purges unused parts in the build. That generality is the framework's strength for rapid development, because it allows developers to build many designs without writing custom CSS, but it is also its main performance cost, because the shipped stylesheet may be hundreds of kilobytes, with most rules unused on any given page, increasing download, parsing, and matching costs for no benefit, unless purging or selective inclusion is used to trim it to the site's actual needs. A framework used without purging or configuration is therefore one of the most common causes of large CSS performance problems, and it should be addressed as a first step when framework CSS is suspected to be slow.

Configuring a framework to include only needed components, or purging its unused utilities and components in the build, as discussed for purging generally, transforms framework CSS from a large, generic file into a small, site-specific one, often with dramatic size reductions — for example, from hundreds of kilobytes to tens of kilobytes — which directly improves load and parsing times. That configuration requires understanding the framework's build options, such as which components can be disabled, which utilities can be excluded, and how purging should be configured to safelist dynamic classes, as discussed earlier, and it requires testing after configuration to ensure that needed framework styles were not accidentally removed, especially for dynamic or rarely used components. That testing is essential, because a misconfigured purge that removes a needed framework component will break pages that use it, in a way that may not be noticed until readers report it, if those pages are not included in testing.

Framework CSS also has specificity and cascade costs, because frameworks often use specific naming, layering, or important flags for their utilities, which may conflict with custom styles, requiring overrides that increase complexity, or may use global styles that affect elements outside their intended components, requiring resets or adjustments. A framework that uses important for utilities, for example, will make custom overrides difficult, forcing developers to use important as well or to use higher specificity, escalating cascade complexity, while a framework that uses a particular grid or component structure may require custom styles to adapt to that structure, rather than to a structure chosen for the site's own needs. Evaluating a framework's CSS architecture — its naming, specificity, layers, and global rules — before adopting it, and choosing a framework whose architecture aligns with the site's own architecture, reduces those cascade costs, compared with adopting a framework solely for its component library without considering its stylesheet's impact on custom code.

Section 41: Splitting for Performance

Splitting CSS for performance means dividing a stylesheet into smaller files that are loaded only where needed, rather than shipping one large file to every page, which reduces download and parsing time for pages that use only a subset of components. The most common split is between shared styles — base, tokens, and commonly used components — which are cached across pages, and page-specific styles, which are loaded only on pages that need them, with both loaded in correct cascade order so that page styles can override shared styles where intended. That split balances size and caching: shared styles are downloaded once and reused, while page styles are small and specific, so total per-page download is smaller than a single global file that contains every component for every page. Splitting is most valuable for large sites with many components, where a global file may be several hundred kilobytes but a typical page uses only a fraction of it.

Implementing splitting requires a build system or server logic that knows which components each page uses, either through manual page bundles, where developers list needed components per page, or through automatic analysis, where a tool scans templates to determine dependencies. Manual bundles give control but require maintenance as pages change, because a new component added to a page must also be added to its bundle, or its styles will be missing, while automatic splitting removes that maintenance but requires tooling that understands templates and dynamic content, including components loaded by script or shown only in certain states, which must be included even if they are not in initial markup. Whichever approach is used, it must account for dynamic components, as discussed for purging, because a split bundle that omits a dynamically loaded component's styles will produce an unstyled component when that component appears, which is worse than shipping a slightly larger bundle that includes it from the start.

Cascade order across split files is a critical detail, because split files must load in an order that preserves the intended priority — shared first, page-specific later, with layers preserved — or page overrides will fail and shared styles will win unintentionally. That order should be centralised in the entry or build configuration, as discussed for cross-file order generally, and verified in the built output, by testing key overrides on each page type, to ensure that splitting did not change cascade behaviour compared with a single-file build. Layer information must also survive splitting: if shared and page files use layers, their layer declarations must be consistent across files, with a single layer order declaration, so that a page file in the utilities layer still beats a shared file in the components layer, regardless of load order, which is the guarantee layers provide when correctly configured.

@layer base, components;

Section 42: Caching for Performance

Caching for CSS performance means allowing browsers to reuse a previously downloaded stylesheet on subsequent pages, rather than re-downloading it on every page, which dramatically reduces load time for returning readers and for multi-page visits, where the same shared stylesheet would otherwise be downloaded repeatedly. That reuse is achieved through cache headers and versioned filenames, as discussed in the previous chapter: a stylesheet with a content-based hash in its filename can be cached for a long time, because a content change produces a new filename that browsers will fetch fresh, while unchanged content keeps the same filename and can be served from cache instantly, without any network request. That long cache, combined with compression, means that a returning reader's second and subsequent page loads may require no stylesheet download at all, making them much faster than first loads, which is a significant performance benefit for sites where readers visit multiple pages per session, as most content sites are.

Cache configuration must be correct to realise that benefit, because a stylesheet served with a short cache expiry, or with headers that require revalidation on every load, will not be effectively cached, even if its filename is versioned, and readers will re-download it more often than necessary, wasting bandwidth and time. Conversely, a stylesheet served with a long expiry but without versioned filenames risks serving stale content after an update, because browsers will use the cached old version even though a new version exists, until the expiry passes, which could be days or weeks, during which readers see outdated styles. The correct combination — versioned filenames plus long expiry — solves both problems, by ensuring freshness through filename changes and efficiency through long caching, and it should be verified by checking response headers for stylesheets after deployment, to confirm that both versioning and caching are actually in effect, rather than merely configured in theory.

Caching also interacts with splitting, because split bundles have different cache lifetimes: shared bundles, which change rarely, can be cached for a long time and will be reused across many pages, while page-specific bundles, which change more frequently as pages are updated, may need shorter cache or more frequent version changes, though versioned filenames handle both cases correctly, because each bundle's filename changes only when its content changes, regardless of how often that occurs. That per-bundle versioning means that updating one page's styles does not invalidate the shared bundle's cache for other pages, which is a benefit of splitting combined with versioning: only the changed bundle needs to be re-downloaded, while unchanged bundles remain cached, reducing total download for readers who visit multiple pages after an update. That efficiency is a strong argument for splitting plus versioning together, rather than either alone, for large sites with frequent updates to individual pages.

Section 43: HTTP/2, HTTP/3 and CSS Delivery

HTTP/2 and HTTP/3 are newer versions of the web's transfer protocol that improve how stylesheets and other resources are delivered, primarily through multiplexing — allowing many resources to be downloaded in parallel over a single connection, without the head-of-line blocking and request limits that made many small files expensive under HTTP/1.1 — and through header compression and, in HTTP/3's case, improved handling of packet loss, which together reduce the overhead of loading multiple stylesheet files and make splitting less costly than it once was. Under HTTP/1.1, each stylesheet file required a separate connection or a queued request, with significant overhead per file, which favoured combining all CSS into one large file to minimise requests, even at the cost of downloading unused rules. Under HTTP/2 and HTTP/3, that overhead is much lower, so splitting CSS into several smaller files — for example, shared plus page-specific bundles — incurs little additional request cost, while still providing the benefit of downloading only needed styles per page, shifting the optimal balance from "one file always" toward "several files where splitting helps."

That shift does not mean that splitting is now free, or that file count no longer matters, because each file still requires parsing, matching, and cache management, and because many small files can still be less efficient than a few well-chosen bundles, due to per-file overhead in the browser and in the build system. The practical implication is that HTTP/2 and HTTP/3 relax the old rule against many files, allowing teams to split more granularly — for example, one file per component, loaded only where needed — without the severe request penalty that HTTP/1.1 imposed, but they do not eliminate the need to think about file organisation, because a page that loads fifty tiny stylesheet files will still be slower to parse and manage than one that loads a few bundled files, even if network overhead is low. The optimal number of files under HTTP/2 and HTTP/3 is therefore a balance: enough splitting to avoid downloading large amounts of unused CSS, but not so much splitting that file management overhead outweighs the saving, a balance that should be determined by measuring per-page download and load times for different splitting strategies, rather than by assuming that more splitting is always better under new protocols.

HTTP/2 and HTTP/3 also affect prioritisation: the browser and server can prioritise critical resources, such as the main stylesheet, over less critical ones, such as print styles or deferred third-party styles, ensuring that render-blocking CSS downloads first, while non-critical CSS downloads in the background without delaying first paint. That prioritisation, combined with server push in HTTP/2 — though server push is now deprecated in favour of preload hints — and with preload links that tell the browser to fetch critical stylesheets early, allows teams to optimise delivery order without changing stylesheet content, by simply indicating which files are critical and which can wait. Using preload for the main stylesheet, and deferring non-critical stylesheets with media attributes or async loading techniques, leverages HTTP/2 and HTTP/3 prioritisation to improve first paint, even for sites with multiple stylesheet files, because critical files are fetched first and non-critical files do not block rendering.

Section 44: Performance Budgets Revisited

Performance budgets for CSS, introduced in the previous chapter as limits on size, request count, or other metrics, deserve revisiting in a performance-focused chapter, because budgets are the mechanism that turns performance principles into enforceable practice, preventing gradual degradation that would otherwise occur as new features add styles without regard for total cost. A budget that is set but never enforced is merely a suggestion, while one that is enforced through tooling — for example, a build check that fails if total CSS per page exceeds a hundred kilobytes compressed, or if the number of stylesheet requests exceeds a set limit — makes performance a requirement for every change, not an afterthought that is considered only when performance becomes noticeably bad. That enforcement should be integrated into continuous integration, so that a change that would exceed the budget is flagged when it is proposed, while it is still cheap to optimise or to reconsider, rather than after it is deployed and its cost is already borne by readers.

Setting a realistic budget requires baselining current performance and understanding audience constraints, as discussed earlier, but it also requires revisiting the budget as the project evolves, because a budget that was appropriate for a small site may become too strict for a larger site with more components, or too lax for a site whose audience shifts to slower connections, where a previously acceptable size becomes unacceptable. That revisiting should be a deliberate team decision, documented with reasons — for example, "budget increased from one hundred to one hundred and twenty kilobytes to accommodate a new design system, with a plan to optimise within two releases" — rather than a silent adjustment to make a failing build pass, because a budget that is adjusted without reason loses its credibility and will be ignored in future, while one adjusted transparently, with a plan to return to a lower size, remains a useful guardrail. Budgets are living agreements, not fixed laws, and their value lies in making performance trade-offs explicit and reviewable, rather than in any specific number.

Budgets should also cover more than just file size, because size alone does not capture all CSS performance costs: a small stylesheet with expensive selectors, layout animations, or large shadows could still perform poorly, while a larger stylesheet with simple selectors and cheap animations could perform well, so a size-only budget might block a harmless large change while allowing a harmful small one. A comprehensive budget might therefore include limits on total size, on number of rules, on maximum specificity, on number of important flags, and on animation properties used, each enforced through linting or build checks, providing a fuller picture of CSS health than size alone. That comprehensiveness should be balanced against complexity, however, because a budget with too many metrics becomes hard to understand and to enforce, and teams may ignore it entirely if it feels bureaucratic, so starting with size and one or two additional metrics, such as specificity or important count, and adding more only where they address measured problems, is a practical approach to budget design.

Section 45: Profiling in DevTools

Profiling CSS performance in browser developer tools means using the performance panel to record a page's rendering behaviour during load and interaction, and then analysing that recording to identify which stages — style calculation, layout, paint, or composite — dominate time, and which elements, selectors, or properties cause those stages to be expensive. That analysis is the most direct way to diagnose CSS performance problems, because it shows actual time spent, rather than theoretical costs, and it reveals bottlenecks that file size or Lighthouse scores alone cannot, such as a single element with an expensive shadow that dominates paint time, or a script-driven style change that triggers layout thrashing, visible as repeated layout tasks in the timeline. Learning to record, read, and interpret a performance profile is therefore a core skill for CSS performance work, more valuable than memorising lists of expensive properties, because it allows you to find the actual bottleneck for a specific page, rather than optimising properties that may not matter for that page.

A typical profiling workflow starts by recording a page load, to see initial style, layout, and paint costs, then by recording interactions — scrolling, hovering, animating, resizing — to see runtime costs, with the recording configured to show rendering events, paint flashing, and layer borders where helpful, to visualise which areas repaint and which elements are promoted to layers. That workflow reveals patterns: long layout tasks indicate layout-heavy styles or thrashing, long paint tasks indicate paint-heavy visuals such as shadows or gradients, and long style calculation tasks indicate complex selectors or frequent variable changes that trigger recalculation. Each pattern points to a different optimisation — simplifying layout, reducing paint area, or simplifying selectors — and profiling allows you to choose the right optimisation for the observed pattern, rather than guessing based on general guidance that may not apply to the page in question.

Interpreting a profile requires understanding what each event means and what a healthy profile looks like: style calculation should be brief for static pages, layout should occur mainly at load and on genuine layout changes, paint should be limited to changed areas, and composite should dominate animation frames, with frame times under sixteen milliseconds for smooth sixty-frames-per-second motion. A profile that shows layout on every animation frame, for example, indicates a layout animation that should be switched to transform, while one that shows large paint tasks for a small hover effect indicates a paint-heavy hover style that should be simplified, and one that shows frequent style recalculation for a page with many variables indicates a variable scope problem that should be localised. Those interpretations, learned through practice with real profiles, turn profiling from a confusing timeline into a diagnostic tool that directly suggests fixes.

Section 46: Auditing with Lighthouse

Auditing CSS performance with Lighthouse means running its automated checks on a page, reviewing its performance score and its specific CSS-related suggestions — such as removing unused CSS, minifying, reducing render-blocking resources, and avoiding large layout shifts — and using those suggestions to prioritise optimisations, while understanding Lighthouse's limitations as a synthetic, lab-based tool. Lighthouse simulates a mobile device with throttled CPU and network, loads a page in a controlled environment, and measures metrics such as first contentful paint, largest contentful paint, total blocking time, and cumulative layout shift, each of which is affected by CSS in different ways: unused CSS increases download and parsing time, affecting first paint; render-blocking CSS delays first paint directly; and layout-shifting CSS, such as fonts or images without dimensions that cause reflow when they load, affects cumulative layout shift. Those metrics, together with Lighthouse's opportunities list, which quantifies potential savings from each optimisation, provide a prioritised starting point for CSS performance work, showing which optimisations would save the most time for that page, rather than requiring developers to guess.

Interpreting Lighthouse results for CSS requires distinguishing between opportunities that are genuinely valuable and those that are artefacts of the lab environment or of the page's specific test conditions. For example, Lighthouse may flag unused CSS that is actually used on other pages or in rare states, because it only audits the single page it loaded, not the whole site, so removing all flagged unused CSS based solely on Lighthouse could break other pages or states that were not audited, as discussed for purging generally. Similarly, Lighthouse may flag render-blocking CSS that is actually critical for first paint and should remain blocking, because its suggestion to defer non-critical CSS applies only to CSS that is not needed for initial rendering, not to the main stylesheet that defines above-the-fold content. Those distinctions require human judgement, using Lighthouse as a guide rather than as an automatic instruction, and verifying each suggested optimisation against the site's actual pages, states, and user needs before applying it.

Lighthouse audits should be run regularly and tracked over time, because a single audit score is less useful than a trend: a score that drops after a release indicates a regression introduced by that release, which can be investigated while its cause is still fresh, while a score that improves after an optimisation confirms that the optimisation worked, providing evidence for future performance decisions. Integrating Lighthouse into continuous integration, with thresholds that fail a build if scores drop below a set level, automates that tracking and prevents regressions from reaching production unnoticed, though thresholds should be set realistically, allowing for normal variation between runs, because Lighthouse scores can vary by a few points due to test environment fluctuations, and a threshold that is too strict will cause false failures that developers learn to ignore, undermining the audit's credibility. Section 47: Common Performance Mistakes

Common CSS performance mistakes are patterns that seem harmless or even beneficial in isolation, but that cause measurable slowdowns when applied at scale, frequently, or to large elements, and recognising them helps teams avoid the most frequent performance pitfalls without needing deep profiling for every change. One common mistake is using * { transition: all; } or a global transition rule, which transitions every property on every element, causing paint and layout work for any style change, even ones that should be instant, and multiplying that work across all elements on a page, as discussed for transitions generally. That global rule is tempting because it makes every change feel smooth with one line of code, but its cost is that every hover, focus, class toggle, or script-driven style change triggers transitions for properties that do not need them, and for elements that do not need motion, wasting rendering time and potentially causing jank, especially on pages with many elements.

Another common mistake is animating layout properties, such as width, height, margin, or left, for effects that could be achieved with transform or opacity, as discussed for animations generally, because layout animations trigger full rendering pipelines on every frame, while transform animations trigger only compositing, and the visual difference between the two is often negligible, especially for slide, fade, and scale effects that are the most common animations. That mistake persists because layout properties feel more intuitive — moving an element by changing its left position seems natural, while translating it with transform feels indirect — but that intuition leads to janky animations that could have been smooth with a simple property substitution, and it is worth training teams to think in transform terms for motion, even when layout terms feel more familiar, because the performance difference is large and the visual difference is usually nil.

A third common mistake is shipping large, unpurged framework or utility stylesheets, as discussed for frameworks generally, because developers adopt a framework for its components and utilities without configuring it to include only needed parts, resulting in a stylesheet that is several times larger than necessary, with most rules unused, yet still downloaded, parsed, and matched on every page. That mistake is easy to make because frameworks work correctly without purging — pages look right, just slower — so the performance cost is invisible unless it is measured, and it persists because purging requires build configuration and testing that teams may postpone, especially under deadline pressure, even though purging is one of the highest-value optimisations available for framework-based sites. Making purging part of the initial framework setup, rather than a later optimisation, prevents that mistake from becoming entrenched, because a framework project that starts purged will stay lean, while one that starts unpurged will accumulate unused rules that are harder to purge later, when dynamic uses have proliferated.

Section 48: Performance on Low-End Devices

Performance on low-end devices — phones and computers with slower processors, less memory, weaker graphics, and slower connections — deserves special attention in CSS performance work, because those devices magnify every CSS cost that is negligible on powerful desktops, turning a stylesheet that feels fast in development into one that feels slow for a significant portion of readers, especially in regions or demographics where low-end devices are common. A large stylesheet that parses in milliseconds on a desktop may take hundreds of milliseconds on a low-end phone, a complex selector that matches quickly on a desktop may take noticeably longer when the document is large and the processor is slow, and a shadow or blur that paints smoothly on desktop graphics hardware may stutter on integrated mobile graphics, where paint calculations compete with other tasks for limited resources. Those magnified costs mean that low-end performance cannot be inferred from desktop performance; it must be tested explicitly, through throttling, emulation, or real low-end devices, to reveal bottlenecks that desktop testing hides.

Designing for low-end devices involves the same lean CSS principles as general performance work, but applied more strictly, because margins for error are smaller: file sizes should be smaller, selectors simpler, animations limited to transform and opacity, shadows and filters used sparingly and with small radii, and fonts limited in count and weight, because each of those choices has a larger impact on low-end devices than on desktops, where excess cost is absorbed by spare capacity. That strictness does not mean sacrificing design entirely for low-end devices, but it does mean prioritising: a design element that is nice to have on desktop, such as a large blurred background or a complex gradient animation, may need to be simplified or omitted on low-end devices, either through media queries that detect reduced capabilities, through progressive enhancement that offers simpler visuals by default and richer visuals only where they perform well, or through a general design that is lean enough to perform well everywhere, without needing device-specific variants. That general leanness — a design that is simple enough to be fast on low-end devices, yet rich enough to be appealing on desktops — is often the best approach, because it avoids maintaining separate designs for different device tiers, which is costly and error-prone.

Testing on low-end devices should include both synthetic throttling, where browser tools simulate slower CPU and network, and, where possible, real device testing, where a page is loaded and interacted with on an actual low-end phone, to capture factors that throttling cannot fully simulate, such as thermal throttling, memory pressure from other apps, and real network variability. That testing should cover load — first paint and largest contentful paint under throttled conditions — and interaction — scrolling smoothness, animation frame rates, and hover and focus responsiveness — because a page that loads acceptably on a low-end device may still jank during interaction if its animations or scroll handlers are expensive, and vice versa. A testing checklist that includes low-end load and interaction, applied to new features before release, ensures that low-end performance is considered routinely, rather than only when readers complain, by which time the problem may have affected many readers for a long time.

Section 49: Performance and Accessibility Together

Performance and accessibility together are often treated as separate concerns, but they share many solutions and should be considered jointly, because optimisations that improve one often improve the other, and trade-offs that sacrifice one for the other should be made consciously, not accidentally. A fast page, for example, is more accessible to readers on slow connections or low-end devices, who may otherwise abandon a slow page before its content becomes available, while an accessible page, with clear focus styles, readable text, and reduced-motion support, is often also a performant page, because its focus styles use cheap outline properties, its text uses system or efficiently loaded fonts, and its reduced-motion support disables expensive animations for readers who prefer them, reducing rendering work for those readers. Those alignments — fast equals accessible for slow devices, cheap focus equals visible focus, reduced motion equals less animation work — show that performance and accessibility are not competing goals, but complementary aspects of a page that works well for all readers, and that optimising for both together yields a better result than optimising for either alone.

There are also cases where performance and accessibility appear to conflict, and those cases require careful judgement to balance both, rather than sacrificing one entirely for the other. A visually rich animation, for example, may be performant when implemented with transform and opacity, but still be inaccessible for readers with vestibular disorders who prefer reduced motion, so it should be disabled or simplified for those readers through a prefers-reduced-motion query, even though it is performant, because accessibility requires respecting reader preference regardless of performance. Conversely, a highly accessible design that uses many large, high-contrast images or complex layouts to aid comprehension may be less performant than a simpler design, but its accessibility benefit may justify its performance cost, especially if that cost is mitigated through image optimisation, lazy loading, or other techniques that preserve accessibility while improving speed. Those trade-offs should be documented and decided explicitly, with input from both performance and accessibility perspectives, rather than being made implicitly by a developer who considers only one perspective.

Joint testing for performance and accessibility is also more efficient than testing each separately, because many test procedures overlap: a keyboard navigation test that checks focus visibility also reveals whether focus styles cause layout shifts or jank when tabbing quickly, a screen reader test that checks content order also reveals whether off-screen content-visibility breaks find-in-page or reading order, and a performance profile that shows paint times for animations also reveals whether reduced-motion handling actually disables those animations, by comparing profiles with and without reduced-motion preference. That overlap means that a combined test plan — checking focus, motion, contrast, load time, and interaction smoothness together for new features — is both more thorough and more efficient than separate plans, because it catches interactions between performance and accessibility that separate plans might miss, such as a focus style that is visible but causes layout shift, or a content-visibility optimisation that breaks screen reader navigation for off-screen content.

/* Fast and accessible: cheap focus, reduced motion, lean loading. */
.btn:focus-visible { outline: 3px solid #0b5fff; }

Section 50: Lean CSS Playbook

A lean CSS playbook is a short set of habits that keeps stylesheets small, fast, and smooth, without requiring developers to reconsider every performance decision from scratch for each change. Start with size: remove unused rules, purge unused utilities, split by page where it helps, minify, compress, and cache with versioned filenames, so that readers download only needed, efficiently encoded CSS, and reuse it across pages. Keep selectors simple — single classes with distinctive keys, avoiding deep descendants, generic keys, and unnecessary relational conditions — so that matching and recalculation stay cheap, even on large documents. Choose cheap properties for motion — transform and opacity for animations and transitions, avoiding layout and paint-heavy properties for continuous motion — and use will-change and containment sparingly, only where profiling shows they help, so that rendering stays in the cheapest stages, layout and paint are minimised, and reflows and repaints are localised to small areas. Those size, selector, and property habits, followed consistently, produce lean CSS by default, rather than requiring periodic rescue optimisations.

Inside that playbook, organise performance work as a routine part of development, not as a separate phase: set a size budget and enforce it in builds, profile new features for load and interaction performance, audit with Lighthouse for regressions, and test on throttled, low-end conditions, so that performance problems are caught when they are introduced, while they are still attributable to a single change and cheap to fix, rather than discovered months later when many changes have accumulated. Document performance decisions — why a particular animation uses transform, why a shadow radius was reduced, why a font was omitted — with comments or in the style guide, so that future developers understand the reasoning and do not reintroduce expensive patterns inadvertently, thinking they are improvements. That documentation, combined with budgets and profiling, turns performance from a personal habit into a team practice, where every developer contributes to lean CSS and every reviewer checks for it, rather than relying on a single performance expert to catch problems after the fact.

When performance problems do occur, follow the playbook's debugging sequence: measure first, using DevTools profiles and Lighthouse audits to identify which stage — style, layout, paint, or composite — dominates time, and which elements or properties cause that dominance, rather than guessing based on general guidance that may not apply to the specific page. Fix the dominant stage first, whether by simplifying selectors, switching animation properties, reducing paint area, adding containment, or removing unused code, and measure again to confirm improvement, rather than applying multiple optimisations at once and not knowing which helped, which is a common debugging mistake that wastes effort and obscures learning. If a fix does not help, revert it and try another, because a performance optimisation that does not measurably improve performance is not worth its complexity or maintenance cost, even if it follows general best practice, since best practice is a guide, not a guarantee, for a specific page's actual bottleneck.

/* Playbook: small files, simple selectors, transform and opacity only. */
.card { padding: 1rem; transition: transform 0.2s ease; }
