Chapter 44: Naming Systems: BEM in Plain Words

Section 1: Why Naming Matters

Naming matters in CSS because a class name is the main way a developer, or a future version of yourself, understands what a rule is for, where it belongs, and whether it is safe to change. A clear name such as card-title tells you immediately that the rule styles a title inside a card, while a vague name such as title, big, or style1 tells you almost nothing, and forces you to read the rule, search for its uses in markup, and guess its intent before you can safely edit it. That guessing takes time on every change, and it increases the risk of mistakes, because a developer who misunderstands a name may change a rule that is used in places they did not expect, breaking pages they never checked. Good names reduce that risk by making intent visible.

Naming also affects collisions, which become more likely as a stylesheet grows. A generic name such as title, defined for one component, may collide with the same name defined for another component, or with a name used by a library, producing a rule that applies in both places unintentionally. A distinctive, namespaced name, such as card-title or article-title, avoids that collision, because the component prefix distinguishes the two titles even though both contain the word title. That distinction is especially important in large projects with many developers, where two people may independently choose the same generic name for different purposes, without realising the collision until a page looks wrong. A naming system that requires a prefix or namespace prevents those accidental collisions by construction.

A third reason naming matters is searchability and tooling. A distinctive name can be found with a simple text search across stylesheets and markup, revealing every place it is used, which is essential for refactoring, for dead-code removal, and for understanding a component's impact before changing it. A vague name, by contrast, produces many false positives in search — every title, every big, every style — making it hard to find the relevant uses among the noise. That searchability is a practical benefit that pays off daily, especially when a component needs to be renamed, removed, or restyled, because the developer can confidently find all its uses and update them together, rather than missing one and leaving a broken page behind.

Finally, naming is a form of communication within a team, because names encode shared agreements about how components are structured and how they relate. When a team agrees that card__title means the title element of a card block, and card--large means a large variant of a card, every team member can read a new component's markup and understand its structure without asking the author, and can write new components that follow the same pattern without needing detailed instructions. That shared language reduces onboarding time, makes code review faster, because reviewers can check names against the convention, and makes the stylesheet system feel coherent, even when many people contribute to it. Naming, in short, is not cosmetic; it is the interface through which developers understand and maintain a stylesheet system.

/* Clear names make intent, scope, and impact visible. */
.card-title { font-size: 1.25rem; }

Section 2: What Is BEM?

BEM stands for Block, Element, Modifier, and it is a naming methodology for CSS classes that was developed to make stylesheets more structured, predictable, and maintainable, especially in large projects with many developers. A block is an independent, reusable component, such as a card, a button, or a navigation bar, that makes sense on its own and can be used anywhere on a page. An element is a part of a block that has no standalone meaning outside its block, such as a card's title, a button's icon, or a navigation's link, and it is always used as part of its block. A modifier is a variation of a block or an element, such as a large card, a primary button, or a disabled input, that changes its appearance or behaviour in a specific way, without creating a new block.

The core idea of BEM is that class names should encode the relationship between a component and its parts and variants, so that the name itself tells you the structure. A block name is a single word or hyphenated phrase, such as card or main-nav. An element name combines the block name with the element name, separated by two underscores, such as card__title or main-nav__link, which makes it clear that the title belongs to the card and the link belongs to the navigation. A modifier name combines the block or element name with the modifier name, separated by two hyphens, such as card--large or card__title--featured, which makes it clear that large is a variant of card and featured is a variant of the card's title. That encoding is the whole methodology in miniature: names that say what they are and where they belong.

BEM's benefits follow from that encoding. Because element and modifier names include their block name, they are unlikely to collide with names from other blocks, even when different blocks have similarly named parts, such as a card title and an article title, which become card__title and article__title, distinct by prefix. Because BEM classes are flat — each class is used on its own, without requiring descendant selectors — their specificity is low and predictable, usually one class, which makes overrides cheap and cascade behaviour easy to understand. And because BEM names are descriptive, they serve as documentation in markup, where a reader can see a component's structure from its class attributes without opening the stylesheet.

BEM is not a language feature or a tool; it is a convention that developers follow voluntarily, and its value depends entirely on consistent application. A project that uses BEM for some components and vague names for others will gain only part of BEM's benefits, because the inconsistent parts will still suffer from collisions, high specificity, and unclear names. Conversely, a project that follows BEM consistently, with documentation and review to enforce it, will gain a stylesheet system where components are findable, reusable, and safe to change, which is especially valuable as the project grows. BEM's simplicity is its strength: three concepts, two separators, and a discipline of applying them consistently, are enough to organise a large stylesheet system.

/* BEM: block card, element card__title, modifier card--large. */
.card { padding: 1rem; }
.card__title { font-size: 1.25rem; }
.card--large { padding: 2rem; }

Section 3: Blocks: Independent Pieces

A block in BEM is an independent, reusable component that makes sense on its own, without needing a parent context to explain what it is or how it should look. Examples include a card, a button, a form, a navigation bar, a modal, and a search box — each of these can appear in different places on a page, in different containers, and in combination with other blocks, while retaining its own appearance and behaviour. That independence is the defining test for a block: if a piece of design can be moved from one page to another, or from a sidebar to a main column, without changing its styles, it is a block. If it only makes sense inside a specific parent, it is more likely an element of that parent, not a block in its own right.

Block independence has practical consequences for how blocks are written. A block's styles should not depend on its parent element or on its position on the page, which means avoiding descendant selectors that style a block only inside a particular container, and avoiding layout properties that assume a specific page arrangement. A card block, for example, should define its own padding, border, and internal spacing, but should not define its margin in a page grid, because that margin is a property of the page layout, not of the card itself. Keeping that boundary clear — block styles for what the block is, layout styles for where it sits — is what makes blocks reusable, because a reusable block must work in any layout, not just in the layout where it was first designed.

Block names should be clear, concise, and descriptive of the component's purpose, not of its appearance in one context. A name such as card, search-form, or main-nav describes what the component is for, and it will remain accurate even if the component's colours or sizes change, while a name such as blue-box or left-panel describes appearance or position, which may change and render the name misleading. That purpose-based naming is a general principle for all BEM names, but it is most important for blocks, because block names are the foundation on which element and modifier names are built, and a misleading block name will propagate to every element and modifier that includes it. Choosing a block name carefully, at creation time, saves renaming work later, when the block is used in many places.

Finally, blocks can contain other blocks, which is normal and expected in BEM: a card block may contain a button block, a form block may contain an input block, and a page header block may contain a navigation block and a logo block. That nesting of blocks in markup does not make the inner block an element of the outer block, because the inner block remains independent and reusable elsewhere; it is simply a block used inside another block's markup. Distinguishing block-in-block from element-in-block is a key BEM skill, because it determines whether the inner piece gets its own block name, with its own elements and modifiers, or an element name tied to the outer block. The test is independence: if the inner piece makes sense alone, it is a block, even when it appears inside another block.

/* Block: independent, reusable, usable anywhere. */
.card { padding: 1rem; border: 1px solid #ddd; }

Section 4: Elements: Parts of a Block

An element in BEM is a part of a block that has no standalone meaning outside its block, and that is always used as part of that block's markup. Examples include a card's title, image, body, and footer; a form's label, input, and error message; and a navigation's list, item, and link. Each of those parts makes sense only in the context of its block: a card title without a card is just a heading, a form label without a form field is just text, and a navigation link without navigation is just a link. That lack of standalone meaning is the defining test for an element, and it distinguishes elements from blocks, which do make sense alone, even when they are used inside other blocks.

Element names encode that dependence by including the block name, separated by two underscores, such as card__title, form__label, or nav__link. That encoding serves several purposes: it prevents collisions, because a card title and an article title become distinct names even though both are titles; it makes the relationship visible in markup, because a reader can see from the class name alone that the title belongs to a card; and it makes the element findable, because searching for card__ will find all of a card's elements together. That findability is a practical benefit when a block needs to be changed, because all its parts can be located by searching for its block prefix, rather than by searching for generic part names that appear in many blocks.

Elements should not be styled in a way that depends on other elements' presence or on deep nesting, because that would make the element less reusable within its block and more fragile to markup changes. An element's styles should describe the element itself — its size, spacing, typography, and colour — not its relationship to sibling elements, except where that relationship is genuinely part of the block's design, such as spacing between a title and body that is defined as part of the block's internal layout. Where element-to-element relationships matter, they should be expressed as part of the block's structure, with clear class names, rather than as descendant selectors that chain elements together, because chaining increases specificity and makes the elements harder to reuse or to restyle independently.

A common question is how to name an element that appears in multiple blocks, such as a title that appears in both cards and articles. In BEM, that title is not a single shared element; it is two elements, card__title and article__title, each defined for its block, even if their styles are initially similar. That duplication may seem wasteful, but it preserves independence: if card titles later need a different size from article titles, each can change without affecting the other, whereas a shared title class would force a choice between changing both or adding an override. If the similarity is genuine and should be shared, the shared styling can be extracted into a separate block, a utility, or a shared variable, rather than by making one block's element depend on another block's element.

/* Element: part of a block, named block__element. */
.card__title { font-size: 1.25rem; margin-bottom: 0.5rem; }
.card__body { line-height: 1.6; }

Section 5: Modifiers: Variations

A modifier in BEM is a variation of a block or an element that changes its appearance, behaviour, or state in a specific way, without creating a new block or element. Examples include a large card, a primary button, a disabled input, a featured article title, and a collapsed navigation menu. Each modifier is applied in addition to the base block or element class, not instead of it, so that an element carries both classes — for example, card and card--large together — and the modifier rule overrides or extends the base rule for the properties that differ. That additive pattern is important: the base class provides the shared foundation, and the modifier provides only the differences, which keeps modifier rules small and makes it clear what changes in the variant.

Modifier names encode their target by including the block or element name, separated by two hyphens, such as card--large for a large card, button--primary for a primary button, or card__title--featured for a featured card title. That encoding prevents collisions, because a large card and a large modal become card--large and modal--large, distinct even though both are large, and it makes the modifier's purpose visible in markup, because a reader can see from the class list that an element is a card, in its large variant, without opening the stylesheet. It also makes modifiers findable, because searching for card-- will find all of a card's variants together, which is helpful when a block's variants need to be reviewed or changed as a group.

Modifiers should change one aspect, or a small set of related aspects, rather than redefining the whole component, because a modifier that redefines everything is really a new block in disguise, and it should be named as such. A large card modifier, for example, should change padding and font sizes, not redefine the card's border, background, layout, and typography from scratch, because those shared properties belong in the base card rule and should be inherited by all variants. That restraint keeps modifiers small, makes their differences easy to review, and ensures that a change to the base card — such as a new border colour — automatically applies to all variants, because variants do not duplicate base properties. A modifier that duplicates base properties will drift from the base when the base changes, creating inconsistency between variants.

Modifiers can also represent states, such as disabled, active, or hidden, though some teams prefer separate state classes for states that are managed by script, as discussed in a later section. Whether a state is written as a BEM modifier or as a state class, the principle is the same: the state class is added in addition to the base class, it changes only the properties relevant to that state, and it is removed when the state ends, returning the element to its base appearance. That additive, temporary nature distinguishes modifiers and states from base classes, which are permanent parts of an element's identity. Understanding that distinction helps authors decide whether a new variation should be a modifier, a state, or a new block, based on whether it is a permanent variant, a temporary state, or an independent component.

/* Modifier: base class plus modifier class, modifier changes only differences. */
.card { padding: 1rem; }
.card--large { padding: 2rem; }

Section 6: Writing a BEM Class Name

Writing a BEM class name correctly requires following three naming steps in order: name the block, name the element if there is one, and name the modifier if there is one, using the separators that distinguish each part. Start with the block name, which is a lowercase, hyphenated phrase describing the component, such as card, search-form, or main-nav. If the class is for an element, append two underscores and the element name, also lowercase and hyphenated, such as card__title or search-form__input, which together form the element's full name. If the class is for a modifier, append two hyphens and the modifier name to the block or element name it modifies, such as card--large, search-form__input--disabled, or card__title--featured, which together form the modifier's full name. That step-by-step construction ensures that every BEM name is unambiguous about what it is and what it modifies.

The separators themselves carry meaning and must not be confused: two underscores mean "element of," while two hyphens mean "modifier of." A single underscore or a single hyphen in those positions would be ambiguous, because single hyphens are already used within block, element, and modifier names themselves, to separate words, such as in search-form or card-title. The double separators stand out visually, making it easy to parse a BEM name at a glance: everything before the double underscore is the block, everything between the double underscore and the double hyphen is the element, and everything after the double hyphen is the modifier. That visual parsing is a practical benefit in markup, where a long class list can be scanned quickly if its structure is consistent.

BEM names should be lowercase, because CSS class names are case-sensitive and lowercase is the conventional style that avoids confusion between Card, card, and CARD, which would be three different classes. They should use hyphens, not underscores, within each part, to separate words, because hyphens are the standard word separator in CSS class names and are easier to read than concatenated words or camelCase in a stylesheet context. They should avoid abbreviations unless the abbreviation is widely understood, such as nav for navigation, because an abbreviation that is clear to one developer may be opaque to another, and BEM names are meant to be self-documenting. Those style choices — lowercase, hyphenated, unabbreviated where possible — are not part of BEM's core definition, but they are common conventions that make BEM names consistent across a project.

When writing BEM names in markup, apply the base class first, then the modifier class, and list element classes alongside their block, so that the class attribute reads as a description of the element's identity and variants. For example, a large card's title in its featured variant might carry card__title and card__title--featured, while the card itself carries card and card--large. That ordering — base before modifier — is a convention that makes class lists easier to read, because the reader encounters the identity before the variation, and it also reflects the cascade, where the modifier rule, ordered after the base rule in the stylesheet, will win for differing properties. Consistent ordering in markup, like consistent naming, is a small habit that makes BEM code easier to scan and to review.

/* BEM construction: block, __element, --modifier. */
.search-form { display: flex; }
.search-form__input { flex: 1; }
.search-form__input--disabled { opacity: 0.5; }

Section 7: Double Underscore, Double Hyphen

The double underscore and double hyphen in BEM are not arbitrary punctuation; they are deliberate separators chosen to be visually distinct from the single hyphens used within names, so that a BEM name can be parsed into its parts at a glance. A single hyphen separates words within a part, such as search-form, where search and form are two words in one block name, while a double underscore separates the block from its element, and a double hyphen separates a block or element from its modifier. That distinction is essential, because without it, a name such as card-title-large could be read as a block named card, an element named title, and a modifier named large, or as a block named card-title with a modifier large, or as a single block named card-title-large, with no way to tell which reading is intended. The double separators remove that ambiguity by marking the boundaries between parts unambiguously.

That unambiguity has practical benefits for tooling and searching, as well as for human reading. A search for __ will find all element names, a search for -- will find all modifier names, and a search for a block name followed by __ will find all of that block's elements, which makes it easy to audit a block's structure or to find all its variants. Those searches work because the double separators are unique to BEM structure, while single hyphens appear in many names for word separation and cannot be used to distinguish structure from wording. A naming system that uses only single hyphens for both purposes, such as card-title-large, loses that searchability, because a search for title will find both block names containing title and element names containing title, without distinguishing them.

Some teams use alternative separators, such as a single underscore for elements or a single hyphen with a different convention for modifiers, but those alternatives sacrifice the visual distinctness that double separators provide, and they can conflict with other naming conventions or with preprocessor syntax. The double underscore and double hyphen are the classic BEM separators, documented in BEM's original methodology, and using them ensures that developers familiar with BEM from other projects will immediately understand your names, without needing to learn a local variant. Consistency with the wider BEM community is a benefit in itself, because it reduces onboarding time for developers who have used BEM elsewhere and makes your code more understandable to external reviewers.

When you encounter a BEM name, practise parsing it by its double separators: split first on __ to separate block from element, then split on -- to separate the base from the modifier, and read the remaining hyphenated words as the names of each part. That parsing habit, applied to examples such as main-nav__link--active, yields block main-nav, element link, modifier active, in a single glance, without needing to consult documentation. That instant readability is the point of the double separators: they turn a class name into a small, structured description that can be understood without context, which is exactly what a naming system should do for a large stylesheet.

/* __ separates block from element; -- separates base from modifier. */
.main-nav__link--active { font-weight: 700; }

Section 8: BEM in Markup

BEM in markup means applying block, element, and modifier classes to elements in a way that reflects the component's structure, with each element carrying the classes that describe its identity and its variants, and no element carrying classes that belong to another component. A card in markup, for example, might be a div with class card and card--large, containing an image with class card__media, a heading with class card__title, a paragraph with class card__text, and a footer with class card__footer containing a button that is itself a block, with class btn and btn--primary. That markup reads as a description of the card's structure, because each class name says which block it belongs to, which part it is, and which variant it carries, without needing to infer structure from nesting or from element types.

A key principle for BEM markup is that elements should carry their full BEM class, including the block prefix, rather than relying on descendant selectors or on parent classes to imply their identity. A card title should carry card__title explicitly, even though it is inside a card element, because that explicit class makes the title findable, styleable independently, and movable within the card without losing its styling. Relying on a descendant selector, such as .card h2, to style a title would tie the title's appearance to its element type and to its position inside the card, making it fragile to markup changes — for example, changing the title from an h2 to an h3 would break its styling — and making it harder to find the title's styles by searching for its class, because it has no distinctive class to search for. Explicit BEM classes in markup avoid those problems by making identity independent of element type and position.

BEM markup also handles mixes, where an element belongs to two blocks at once, such as a button that is both a standalone btn block and a card's action element, by carrying both classes, for example btn and card__action, each with its own styles, as discussed in a later section on mixes. It requires care in the stylesheet, to ensure that the two classes' rules do not conflict in unintended ways, but in markup it is simply a matter of listing both classes, in an order that reflects their roles, usually block first, then element, or vice versa by team convention, as long as the order is consistent.

Finally, BEM markup should be kept clean by avoiding unnecessary classes and by using modifiers only where they genuinely vary an element's appearance. An element that carries many modifier classes, or that carries classes for every possible state, becomes hard to read, because its class attribute becomes a long list that obscures its identity. A card that carries card, card--large, card--featured, card--dark, and card--rounded, for example, may be trying to express too many variations at once, and some of those variations might be better expressed as separate blocks, themes, or utilities. BEM markup, like BEM stylesheets, benefits from restraint: classes should describe identity and meaningful variations, not every possible styling detail, and the markup should remain readable as a description of structure, not as a list of style instructions.

/* Markup carries full BEM classes; CSS styles those classes flat. */
.card__title { font-size: 1.25rem; }

Section 9: BEM in Stylesheets

BEM in stylesheets means writing flat rules for each BEM class, with one class per selector in most cases, ordered so that base rules come before modifier rules, and element rules are grouped with their block, either by file organisation or by comments, rather than by nesting them inside block rules in a way that raises specificity. A card's stylesheet, for example, might list .card first, then .card__media, .card__title, .card__text, and .card__footer, then .card--large and .card__title--featured, in that order, so that a reader can see the block's structure by scanning the file from top to bottom, and so that modifiers, which appear later at equal specificity, win over base rules for differing properties.

Flat BEM selectors are a deliberate choice, not a limitation, because they keep specificity at one class for most rules, which makes overrides cheap and cascade behaviour easy to predict. A BEM element styled with .card__title alone has a specificity of one class, so it can be overridden by another single class later in the same layer, or by a utility in a later layer, without needing a longer selector. If the same element were styled with a descendant selector, such as .card .card__title, its specificity would be two classes, making it harder to override and undermining BEM's flat-specificity benefit, even though the descendant selector might seem more precise. That is why BEM style guides insist on flat selectors, even when nesting is available: nesting a BEM element inside its block, as discussed in the previous chapter, raises its specificity to two classes, which is a trade-off that should be made deliberately, not by default.

Grouping BEM rules in a stylesheet can be done by file, by section, or by both: one file per block, with that block's elements and modifiers inside it, is a common pattern that mirrors the one-file-per-component rule from the previous chapter, and it makes finding a block's rules trivial, because the file name is the block name. Within a file, rules should be ordered logically — base, elements in markup order, modifiers, states — with comments separating those groups, so that a reader can navigate the file without searching. That ordering is a convention, not a language requirement, but consistency within a project matters more than which specific order is chosen, because a consistent order allows developers to predict where a rule will be, rather than searching for it.

BEM stylesheets should also avoid global element selectors for BEM components, because a global rule such as h2 { font-size: 2rem; } will affect BEM elements that happen to use h2 tags, even though those elements are meant to be styled by their BEM classes alone. Base element styles are fine for unstyled content, but BEM components should be self-contained, with their appearance defined by their BEM classes, not by element defaults that may change. Where a BEM element uses an element tag, its BEM class should fully define its appearance, so that changing the tag — for example, from h2 to h3 for heading hierarchy — does not change its appearance, because its BEM class remains the same. That tag independence is a practical benefit of BEM's class-based approach, and it is worth preserving by keeping BEM rules flat and complete.

/* BEM stylesheet: flat selectors, base before modifiers. */
.card { padding: 1rem; }
.card__title { font-size: 1.25rem; }
.card--large { padding: 2rem; }

Section 10: Blocks Should Not Depend on Parents

A BEM block should not depend on its parent context for its appearance, because that dependence breaks the block's independence and reusability, which are its defining qualities. A card that looks correct only inside a main column, because its styles assume a certain width, background, or font from its parent, will look wrong in a sidebar, a modal, or a grid, where those parent properties differ, and it will require overrides for each new context, defeating the purpose of a reusable block. A truly independent block defines its own padding, border, colours, typography, and internal spacing, so that it looks the same wherever it is placed, and any differences required by context are expressed as modifiers or as layout rules outside the block, not as hidden dependencies inside the block's styles.

Parent dependence often creeps in through descendant selectors, inherited properties that are assumed rather than defined, or layout properties that assume a parent's structure. A block that relies on inheriting a font from its parent, without defining its own font, will change appearance when placed inside a parent with a different font, which may be intended for text content but is surprising for a component that should be consistent. A block that uses a descendant selector such as .sidebar .card to adjust its appearance for sidebars creates a second, context-specific version of the block that is not visible from the block's own file, and that will be missed when the block is changed. Those dependencies are not always wrong — layout and theming do involve context — but they should be explicit, through modifiers, theme classes, or layout wrappers, rather than hidden inside the block's styles.

The test for parent independence is to place the block in different contexts — a page, a sidebar, a modal, a grid, a dark theme section — and check whether it still looks correct and consistent, without needing context-specific overrides. If it does, the block is independent. If it does not, the block has a hidden parent dependence that should be made explicit: either by defining the missing property in the block itself, so that it no longer depends on the parent, or by creating a modifier for the context-specific version, so that the dependence is visible as a variant rather than as an assumption. That test, applied to new blocks during review, prevents parent dependence from accumulating, because it forces authors to consider contexts beyond the one where the block was first designed.

Parent independence also applies to JavaScript and to markup structure, not just to styles: a block's markup should not require a specific parent element to function, and its behaviour should not assume a particular ancestor's presence. A navigation block, for example, should work whether it is inside a header, a sidebar, or a footer, without requiring a header-specific wrapper, and a modal block should work whether it is triggered from a card, a button, or a form, without assuming a particular trigger's structure. That broader independence is what makes blocks truly reusable across a site, rather than merely reusable within one page's structure, and it is a goal worth pursuing even though perfect independence is rarely achievable for complex components.

/* Block independence: define its own appearance, not its parent's. */
.card { padding: 1rem; font-family: system-ui, sans-serif; }

Section 11: Elements Should Not Stand Alone

BEM elements should not stand alone, because an element's meaning and appearance are defined by its block, and using an element class without its block context produces a fragment that is incomplete and potentially misleading. A card__title used outside a card, for example, might still render with the card title's font size and spacing, because its class defines those properties, but it will lack the card's surrounding structure, border, and padding, so it will look like a stray heading rather than a card title, and a reader will wonder why a card title appears without a card. That visual incompleteness is a sign that the element is being misused: elements are parts, not independent pieces, and they should appear only as parts of their block's markup, where their context makes their purpose clear.

That rule also has a stylesheet implication: element styles should not be written in a way that makes them usable alone, such as by giving an element all the properties it would need to look complete on its own, because that would blur the distinction between elements and blocks and encourage standalone use. An element's styles should describe the element as a part — its size relative to the block, its spacing within the block, its colour as part of the block's palette — not as a complete component that could be dropped anywhere. If an element's styles are so complete that it looks fine alone, that may indicate that the element is really a block in disguise, and it should be promoted to block status, with its own elements and modifiers, rather than remaining an element that is misused alone.

In markup, the no-standalone rule means that an element class should always appear inside its block's markup, as a descendant of the block element, even though its styles are flat and do not require that descendant relationship to apply. That markup containment is a convention, not a technical requirement, because a flat .card__title rule will apply wherever the class appears, regardless of ancestors, but following the convention ensures that the markup's structure matches the stylesheet's intent, and that a reviewer can tell from the markup whether an element is being used correctly. A card__title outside a card in markup is a review flag, even if it renders acceptably, because it suggests a misunderstanding of the component's structure or a missing block wrapper that should be added.

There are edge cases where an element appears to stand alone but is really part of a block that is rendered elsewhere, such as a portal or a dynamically inserted element that is logically part of a block but physically elsewhere in the document. Those cases should be handled by making the logical relationship explicit — through documentation, through a block class on the element itself as a mix, or through a comment explaining the portal — rather than by silently using an element alone. The goal is not to forbid every unusual markup pattern, but to ensure that element usage is intentional and documented, so that a future developer does not mistake an intentional exception for a general rule that elements can be used anywhere.

/* Element classes belong inside their block's markup. */
.card__title { font-size: 1.25rem; }

Section 12: Modifiers Change One Thing

A BEM modifier should change one thing, or a small set of closely related things, rather than redefining a component, because a modifier's purpose is to express a variation, not a new component. A card--large modifier that changes padding and font sizes is a good modifier, because large is a single dimension of variation — size — even though it affects several properties that together express size. A card--large modifier that also changes colours, borders, layout, and shadows, in addition to size, is a poor modifier, because it conflates several dimensions — size, theme, layout — into one name, making it hard to combine with other modifiers, such as card--dark, without conflicts, and hard to understand what large actually means for that card. Single-dimension modifiers compose well; multi-dimension modifiers do not.

That composability is the practical benefit of single-thing modifiers. A card that needs to be both large and dark can carry card--large and card--dark together, and each modifier will change only its own dimension, so the combination produces a large, dark card predictably, without either modifier overriding the other's properties unintentionally. If large also changed colours, then combining large with dark would produce a conflict over colour, where the winner depends on stylesheet order rather than on design intent, and the resulting card might be large but not dark, or dark but not large, depending on order. That order-dependent combination is fragile and confusing, and it is avoided by keeping each modifier focused on one dimension, so that combinations are order-independent for distinct properties.

Single-thing modifiers are also easier to document, test, and review, because each modifier's effect can be described in one sentence — "large increases padding and font sizes" — and can be tested by comparing a base component with its modified version and checking only the properties that should differ. A multi-dimension modifier, by contrast, requires a longer description, a broader test, and a more careful review, because its effects span many properties and may interact with other modifiers in ways that are hard to predict. That review burden grows with each additional dimension, so keeping modifiers focused is a way of keeping review manageable, especially in a large system with many modifiers.

When a design requires a variation that genuinely spans multiple dimensions — for example, a featured card that is larger, darker, and has a different border — that variation should be expressed as a combination of single-dimension modifiers, such as card--large, card--dark, and card--featured-border, applied together, rather than as a single featured modifier that does everything. That combination is more verbose in markup, but it is more flexible, because each dimension can be reused independently, and it is clearer, because each modifier's name says exactly what it changes. If the combination is used so frequently that it deserves a shorthand, that shorthand can be documented as a recommended combination, rather than as a new modifier that duplicates the individual modifiers' rules.

/* One modifier, one dimension: size only, not colour or layout. */
.card--large { padding: 2rem; font-size: 1.125rem; }

Section 13: Boolean vs Key-Value Modifiers

BEM modifiers come in two forms: boolean modifiers, which indicate the presence of a variation, such as card--large or button--disabled, and key-value modifiers, which indicate a variation with a specific value, such as card--size-large, button--theme-primary, or card--align-center. Boolean modifiers are simpler and more common, because most variations are either present or absent — a card is either large or it is not, a button is either disabled or it is not — and a boolean name captures that presence directly, without needing to specify a value. Key-value modifiers are more explicit, because they name both the dimension and the value, which is useful when a dimension has several possible values that need to be distinguished, such as size with small, medium, and large options, or theme with primary, secondary, and accent options.

The choice between boolean and key-value forms depends on how many values a dimension has and whether those values are likely to grow. A dimension with only two states — present or absent — is naturally boolean, and using a key-value form for it, such as card--large-true, would be verbose without benefit. A dimension with three or more values, or with values that may be added later, is naturally key-value, because a boolean form would require a separate boolean modifier for each value — card--small, card--medium, card--large — which are mutually exclusive but look independent in markup, inviting the mistake of applying two size modifiers at once, such as card--small and card--large together, with an order-dependent result. A key-value form, such as card--size-small versus card--size-large, makes the mutual exclusivity visible in the name, because both modifiers share the size key, signalling that only one should be applied at a time.

Key-value modifiers also help with documentation and tooling, because the key groups related values together, making it easy to list all options for a dimension — size: small, medium, large — and to check that a component uses only one value per dimension. That grouping is valuable in a design system, where dimensions and their values are part of the system's API, and where consumers need to know which values are available and which combinations are valid. Boolean modifiers, by contrast, are harder to group, because each boolean is an independent name, and listing all booleans for a component does not reveal which ones are mutually exclusive or which dimensions they belong to, without additional documentation.

In practice, many projects use boolean modifiers for most variations and reserve key-value modifiers for dimensions with multiple values, such as size, theme, or alignment, and that hybrid approach works well as long as it is documented and applied consistently. A team should decide, for each dimension, whether it is boolean or key-value, document that decision, and review new modifiers against it, asking whether a new boolean is really a value of an existing key-value dimension, or whether a new key-value is really a boolean in disguise. That review prevents the common drift where a dimension starts as booleans, grows to many values, and becomes confusing, because no one recognised that it had become a key-value dimension that needed a different naming form.

/* Boolean: card--large. Key-value: card--size-large. */
.card--size-large { padding: 2rem; }

Section 14: BEM and Nesting Together

BEM and nesting together require a deliberate trade-off, because BEM's flat, single-class selectors and nesting's grouped, indented blocks pull in opposite directions: BEM wants each class styled alone, while nesting wants related rules grouped inside a parent block, which raises specificity when the nested rule expands. As discussed in the previous chapter, nesting a BEM element inside its block, such as writing .card__title inside a .card block, expands to a selector with two classes, .card .card__title, which has higher specificity than the flat BEM selector .card__title alone, and which therefore undermines BEM's low-specificity benefit, even though the nested code looks tidy. That trade-off must be decided consciously, not by defaulting to nesting because it is available.

One common compromise is to nest BEM modifiers and states inside the block, while keeping BEM elements flat, because modifiers genuinely compound with the block — .card--large expands from &.card--large inside .card to .card.card--large, which is the correct flat BEM modifier selector with two classes, as intended — while elements do not need the block prefix in their selector, because their names already include it. That compromise preserves BEM's flat specificity for elements, which are the most numerous BEM classes, while gaining nesting's grouping benefit for modifiers and states, which are fewer and where the compound selector is already expected. Another compromise is to nest everything but to accept the two-class specificity for elements, documenting that BEM elements in the project have block-plus-element weight, so that overrides are written accordingly. Both compromises can work, as long as they are consistent and documented, because inconsistency — some elements nested, some flat, without a rule — is what confuses reviewers and breaks overrides.

A third approach is to use nesting only as an organisational device, with the & symbol used in a way that does not add specificity, such as nesting elements inside a block but writing them with a selector that expands to the flat BEM class alone, though native CSS nesting does not provide a direct way to do that without :where() or similar tricks. Using :where() for the parent, for example, can neutralise the parent's specificity, so that a nested BEM element expands to a low-specificity selector, but that technique is advanced and can confuse readers who are unfamiliar with :where(). It should only be used if the team understands it and documents it, because a clever nesting trick that is not understood by the team will become a maintenance burden, even if it is technically correct.

The safest default for a team new to combining BEM and nesting is to keep BEM elements flat, nest only modifiers and states, and document that rule with examples, so that every developer follows the same pattern without needing to reason about specificity trade-offs for each rule. That default preserves BEM's core benefits — flat specificity, findability, low override cost — while still gaining nesting's grouping for the parts of a component where grouping is most valuable, namely its variants and states, which are naturally understood as refinements of the block. As the team gains experience with nesting, it can revisit that default and adjust it, but starting with a conservative, documented compromise is better than starting with unrestricted nesting and discovering specificity problems later.

/* Compromise: elements flat, modifiers nested with &. */
.card { padding: 1rem; }
.card__title { font-size: 1.25rem; }

Section 15: BEM and Specificity

BEM and specificity are closely linked, because BEM's flat, single-class selectors are designed to keep specificity low and consistent, which is one of BEM's main benefits for cascade management. A BEM block, element, or modifier, styled with a single class, has a specificity of one class, regardless of whether it is a block, an element, or a modifier, because the selector contains only that class, even though the class name itself encodes a relationship. That consistency means that any BEM rule can be overridden by any other BEM rule later in the same layer, or by a utility in a later layer, without needing a longer selector, which makes overrides predictable and cheap. It also means that the order of BEM rules in the stylesheet matters: base rules must come before modifier rules, so that modifiers, which are meant to win for differing properties, do so by order at equal specificity.

That low-specificity design breaks down when BEM selectors are combined with descendant selectors, ids, or nesting that adds extra classes, because each addition raises specificity above one class, making the rule harder to override and less predictable. A descendant BEM rule such as .card .card__title has two classes, a rule with an id has an id's weight, and a nested BEM element, as discussed, also has two classes, all of which defeat BEM's flat-specificity promise. Those additions are sometimes justified — for example, a modifier that compounds with its base, .card.card--large, intentionally has two classes, because it should beat the base .card rule — but they should be deliberate and documented, not accidental, because accidental specificity increases are the ones that cause override problems later, when a developer expects a single-class override to work and finds it does not.

BEM specificity also interacts with layers, in a way that is generally favourable: because BEM rules are low-specificity, placing them in layers gives layer order the deciding role for cross-group contests, such as utilities beating components, without needing to raise BEM specificity. A BEM component in the components layer and a utility in the utilities layer will resolve by layer, regardless of their single-class specificities, which is the intended behaviour. Within a single layer, BEM specificity remains one class for most rules, so order decides, which is why BEM files should be ordered base before modifiers, and why a modifier that appears before its base in the file will lose, even though it was meant to win, because order, not intent, decides at equal specificity.

Reviewing BEM specificity is therefore a matter of checking that most selectors are single classes, that compound selectors are intentional modifiers or states, and that no descendant, id, or unnecessary nesting has raised specificity above that baseline. A linter that flags selectors with specificity above one class, except for documented modifier compounds, can automate that check, and a reviewer who counts classes in a new BEM rule can do it manually. That discipline keeps BEM's specificity benefit intact as the project grows, because it prevents the gradual creep where each new rule adds a little specificity for convenience, until the system as a whole is no longer flat, even though it still uses BEM names. Names alone do not guarantee low specificity; flat selectors do, and they must be maintained.

/* BEM specificity: one class for most rules, order decides ties. */
.card { padding: 1rem; }
.card--large { padding: 2rem; }

Section 16: BEM and Layers

BEM and layers complement each other well, because BEM provides naming and flat specificity, while layers provide explicit priority between groups, and together they give a stylesheet system that is both findable by name and predictable by priority. A BEM component file placed in the components layer, a BEM utility placed in the utilities layer, and a BEM base style placed in the base layer will resolve contests by layer first, then by specificity and order within a layer, which means that a utility will beat a component, and a component will beat a base style, regardless of their single-class specificities. That layer-based priority is more robust than file-order-based priority, because it survives file reordering and build changes, as long as the layer declaration is correct and no unlayered rules slip in.

Placing BEM rules in layers requires deciding which layer each BEM group belongs to, and that decision should follow the same grouping logic as other architectures: base element styles in base, layout blocks in layout, component blocks and their elements in components, theme modifiers in theme, and utility-like BEM classes, if any, in utilities. That mapping is usually straightforward, because BEM blocks are components, BEM elements are parts of components, and BEM modifiers are variants of components, so they all belong in the components layer, except where a modifier is really a theme or utility, in which case it belongs in that layer instead. Documenting that mapping — which BEM groups go in which layers — helps developers place new BEM rules correctly, especially for modifiers that could belong to several layers depending on their purpose.

A common layer mistake in BEM systems is to leave BEM files unlayered, because BEM predates layers and many BEM examples show flat, unlayered files, which in a layered system will beat all layered rules and undermine the layer order. That mistake is easy to make when migrating a BEM system to layers, because existing BEM files may not have layer blocks, and adding a new layered file alongside them will lose to the old unlayered files, producing confusing overrides. The fix is to layer all BEM files, either by wrapping each file's content in its layer block or by importing each file into its layer from the entry file, as discussed in the previous chapter, and to audit for unlayered BEM files after migration, so that no stray file jumps the layer queue.

Layers also help with BEM theme and state handling, because theme modifiers in a theme layer will beat component rules in the components layer, and state classes in a high layer will beat component rules, without needing higher specificity or important flags. That structural priority is cleaner than the specificity-based theme handling that BEM systems historically used, where theme rules needed longer selectors or later file positions to win, and it makes theme and state logic easier to reason about, because priority is declared in the layer list rather than hidden in selector length or file order. A BEM system that adopts layers therefore gains a clearer priority story, while retaining BEM's naming and flat-specificity benefits within each layer.

/* BEM in layers: components layer for blocks, utilities last. */
@layer components, utilities;
@layer components { .card { padding: 1rem; } }

Section 17: BEM and Scope

BEM and scope address different problems — BEM addresses naming and specificity, scope addresses where styles apply and how near their root is — and they can be used together, though their combination requires care to avoid redundancy or confusion. BEM names already make a component's parts distinctive, so a card__title will not collide with an article__title, even without scope, because their names differ. Scope adds a boundary that BEM names alone do not provide: it can prevent a card's styles from leaking into a nested card or widget, even if that nested component happens to use the same BEM names, or it can limit a component's styles to a specific subtree, such as a card inside a particular section, without needing a new BEM modifier for that section. That boundary is scope's contribution, beyond what BEM naming already achieves.

Using scope with BEM is most valuable when components nest inside each other and share part names, or when a component's styles should apply only in a specific context, such as a card inside a dashboard versus a card inside an article. In those cases, scoping the card's rules to the dashboard subtree, or adding a scope limit that excludes nested callouts, provides a boundary that BEM names alone cannot, because BEM names distinguish components by name, not by position in the tree. A card__title inside a nested callout will still match a flat .card__title rule, because the class is the same, but a scoped card rule with a limit that excludes callouts will not match it, because the scope boundary stops at the callout. That positional boundary is scope's unique value, even in a BEM system.

There is also a redundancy risk: scoping every BEM component, when BEM names already distinguish them, adds complexity without benefit, because the scope boundary duplicates the naming boundary that BEM already provides. A team that scopes all BEM components by default will produce stylesheets where every rule is both BEM-named and scoped, making the code harder to read and harder to debug, because a style's failure could be due to either its BEM name or its scope boundary, and both must be checked. A more selective approach — use BEM naming for all components, and add scope only where a boundary problem actually occurs, such as nested components with shared names or context-specific styling — captures scope's benefit without its overhead, and it keeps the stylesheet's complexity proportional to the problems it actually solves.

When scope is used with BEM, document the scope's root, limit, and purpose alongside the BEM block, so that a developer who encounters a scoped BEM rule understands both its naming and its boundary. A comment such as "card scope: root .card, limit .callout, so card styles do not leak into callouts" gives the reader the full picture in one place, rather than requiring them to infer the scope from a separate file or from browser tools. That documentation is especially important for cross-file scope, where the scope definition and the BEM rules may live in different files, as discussed in the previous chapter, because the scope's effect is global to the document, not local to its file.

/* BEM names distinguish; scope adds a positional boundary. */
@scope (.card) to (.callout) {
  .card__title { font-size: 1.25rem; }
}

Section 18: Naming Blocks Clearly

Naming blocks clearly is the foundation of BEM, because block names are reused in every element and modifier name, so a unclear block name propagates confusion to all its parts and variants. A clear block name describes the component's purpose in a few words, using familiar, unambiguous terms, such as card, search-form, main-nav, or product-list, each of which immediately suggests what the component is for and where it might be used. An unclear block name, such as box, item, wrapper, or thing, describes almost nothing, because many components are boxes, items, or wrappers, and a reader encountering box__title cannot tell whether it belongs to a card, a modal, or a sidebar, without opening the stylesheet and searching for its uses. That ambiguity defeats BEM's purpose, which is to make structure visible from names alone.

Clear block names should be specific enough to distinguish the block from similar blocks, but general enough to remain accurate as the block evolves. A name such as product-card distinguishes a product card from a generic card, which is useful if both exist, but a name such as product-card-with-image-and-price-and-button is too specific, because it describes one instance's content rather than the block's purpose, and it will become inaccurate if the card's content changes. A good balance is to name the block after its role — product-card for a card that displays a product — rather than after its current content or appearance, so that the name remains accurate even as content, colours, or sizes change. That role-based naming, similar to token naming, is a long-term investment in the name's stability.

Block names should also avoid terms that are tied to a specific page or context, such as homepage-card or sidebar-card, unless the block is genuinely specific to that page or context and will never be reused elsewhere. A card that is named homepage-card but is later used on a product page will have a misleading name, and developers will either rename it — requiring updates to markup and stylesheets — or live with the misleading name, which confuses new contributors. If a block is truly page-specific, it should be documented as such and, ideally, live in a page file rather than in the shared component system, so that its page-specific nature is explicit. If it might be reused, it should have a general name from the start, even if its first use is on one page.

Finally, block names should be checked for collisions and for consistency with existing blocks before they are created, because a new block name that collides with an existing block, or that uses a different naming style from existing blocks, will create confusion that is expensive to fix later. A quick search for similar names, and a check against the project's naming guide, takes a minute at creation time and prevents a rename that would require updating many files later. Reviewers should ask, for every new block, whether its name clearly says what it is, whether it collides with existing names, and whether it will remain accurate as the block evolves, because those three questions capture most block-naming problems before they become entrenched.

/* Clear block name: purpose, not appearance or position. */
.product-card { padding: 1rem; }

Section 19: Naming Elements Clearly

Naming elements clearly follows the same principles as naming blocks, with the added consideration that an element name must make sense as a part of its block, not as an independent concept. A clear element name, such as card__title, card__media, or form__label, immediately suggests both the part and its block, because the block prefix provides context and the element name provides the part's role within that block. An unclear element name, such as card__thing, card__content1, or card__stuff, provides no information about the part's role, forcing a reader to open the stylesheet or markup to learn what the element is for, which defeats BEM's goal of making structure visible from names alone. Element names should therefore be as descriptive as block names, within the context of their block.

Element names should be concise but complete, using familiar terms for the part's role, such as title, text, media, footer, label, input, and action, rather than vague terms such as part, section, or area, which could refer to any part of any block. That conciseness matters because element names appear in markup alongside block and modifier names, and a long class list with verbose element names becomes hard to read, while a short list with clear, familiar part names remains readable. A balance is needed: card__title is clear and concise, while card__heading-that-appears-at-the-top-of-the-card is clear but verbose, and card__h is concise but unclear. The familiar, role-based term is usually the right balance, because it is both short and meaningful to developers who know the component's domain.

Element names should also be consistent across blocks where the same part role appears, so that title means title in every block, label means label in every form, and action means action in every card or modal, rather than using different terms for the same role in different blocks. That consistency helps developers learn new blocks quickly, because they can predict part names from familiar roles, and it helps tooling and searching, because a search for __title will find titles across blocks, revealing patterns or inconsistencies. Inconsistency, by contrast, forces developers to learn each block's part names separately, which slows onboarding and increases the chance of inventing a new name for an existing role, creating duplication.

Finally, element names should not encode the element's HTML tag, such as card__h2 or card__div, because the tag may change for semantic or accessibility reasons — for example, changing a title from h2 to h3 to fit a page's heading hierarchy — and a tag-based name would then become misleading, requiring a rename that touches markup and stylesheets. Instead, element names should describe the part's role, which is stable across tag changes, so that a card__title remains a card__title whether it is rendered as an h2, an h3, or a div with a heading role. That tag independence is a practical benefit of role-based naming, and it is worth preserving by avoiding tag names in element names, even when the current tag seems permanent.

/* Clear element name: block prefix plus part role. */
.form__label { display: block; margin-bottom: 0.25rem; }

Section 20: Naming Modifiers Clearly

Naming modifiers clearly requires that the modifier name, combined with its block or element, immediately suggests what changes and in what way, without needing to open the stylesheet to learn its effect. A clear modifier name, such as card--large, button--primary, or input--disabled, tells you the dimension — size, theme, state — and the value — large, primary, disabled — in a few words, so that a reader encountering the modifier in markup can predict its effect. An unclear modifier name, such as card--big2, button--special, or input--x, tells you almost nothing, forcing you to search the stylesheet to learn what it does, and making it hard to distinguish from other modifiers that might have similar effects. That clarity is especially important for modifiers, because modifiers are applied in addition to base classes, and a reader must understand the combination — base plus modifier — at a glance, without decoding vague names.

Modifier names should be consistent in form across a project, using either boolean or key-value forms as discussed earlier, and using the same terms for the same dimensions, so that large means large in every block, primary means primary in every button-like component, and disabled means disabled in every form control. That consistency allows developers to predict a modifier's effect from its name, even for a block they have not seen before, because they have seen the same modifier term elsewhere. Inconsistency, such as using large for cards, big for modals, and huge for banners, all to mean the same size increase, forces developers to learn each block's modifier vocabulary separately, which slows work and increases the chance of inventing a new term for an existing dimension, creating duplication.

Modifier names should also be specific enough to avoid collisions and ambiguity, but general enough to be reusable within their block. A modifier named card--large is specific to cards, through its block prefix, but general within cards, because it can be applied to any card that needs to be large, regardless of its content. A modifier named card--large-for-homepage-hero is too specific, because it ties the modifier to one context, making it misleading when used elsewhere and discouraging reuse. Conversely, a modifier named card--l is too general and abbreviated, because it does not say what l means, forcing a reader to guess or to search. The balance — block prefix plus a clear, reusable dimension term — is the same balance as for block and element names, applied to variations.

Finally, modifier names should be reviewed for whether they describe a genuine variation or a new block in disguise, because a modifier name that tries to describe a completely different component — such as card--modal, for a card that is really a modal — suggests that the variation has outgrown modifier status and should become its own block. That review question — "is this a variation of the block, or a different block?" — is a useful check for modifier naming, because it prevents modifiers from becoming a dumping ground for new components that should have their own names, elements, and modifiers. A modifier system that is kept focused on genuine variations will remain clear and composable, while one that accumulates disguised blocks will become confusing, even if each modifier name individually looks clear.

/* Clear modifier name: dimension and value, at a glance. */
.button--primary { background: #0b5fff; color: #fff; }

Section 21: Avoiding Overly Long Names

Overly long BEM names are a common problem, because BEM names already include block, element, and modifier parts, so a long block name combined with a long element name and a long modifier name can produce a class that is difficult to read, type, and scan in markup. A name such as product-listing-page-main-content-card__title--featured-large, for example, contains so much information that it obscures the essential structure — block, element, modifier — behind a wall of words, and a reader must parse it carefully to understand which part is the block, which is the element, and which is the modifier, even with double separators to help. That parsing burden defeats BEM's goal of instant readability, and it makes markup with many such names hard to scan, because each class attribute becomes a paragraph rather than a short description.

Long names usually result from one of three causes: a block name that is too specific, an element name that describes content rather than role, or a modifier name that tries to encode multiple dimensions at once. A block named product-listing-page-main-content-card is too specific because it describes a page, a section, and a component, when the component itself is simply a product card, usable in many contexts, and the page and section context should be expressed through layout or page classes, not through the block name. An element named card__title-that-appears-at-the-top-with-an-icon is too descriptive because it describes content and layout details that belong in styles, not in a name, while a simple card__title would suffice. A modifier named card--large-dark-featured-rounded is too multi-dimensional because it combines size, theme, featured status, and shape into one name, when those dimensions should be separate modifiers that compose.

Shortening long names requires identifying which part is overly long and replacing it with a shorter, role-based term, while preserving distinctiveness. A long block name can often be shortened by removing page or section context, leaving only the component's role. A long element name can be shortened by removing content details, leaving only the part's role within the block. A long modifier name can be split into several single-dimension modifiers, each with a short name, applied together in markup. Each shortening should be checked against existing names to ensure it does not collide with another block, element, or modifier, because a shortened name that collides is worse than a long name that is distinctive, even though it is shorter. Distinctiveness and readability must be balanced, not traded blindly.

A practical guideline is to keep total BEM names under a reasonable length — for example, under about thirty characters where possible — while allowing exceptions for genuinely distinctive components where a longer name is necessary to avoid collision. That guideline is not a strict rule, because some domains require longer names to distinguish similar components, but it serves as a review prompt: a name longer than the guideline should be justified, with a reason why a shorter name would collide or mislead. Reviewers who ask "could this name be shorter without losing meaning?" for every new BEM name will catch most overly long names at creation time, when shortening is cheap, rather than after the name is used in many places, when shortening requires a rename across markup and stylesheets.

/* Short, distinctive names beat long, exhaustive ones. */
.product-card__title { font-size: 1.25rem; }

Section 22: Abbreviations in BEM

Abbreviations in BEM names are a trade-off between brevity and clarity, because a short abbreviation saves typing and reduces name length, but it risks obscurity for developers who do not know what the abbreviation means, especially new team members or developers from different domains. Widely understood abbreviations, such as nav for navigation, btn for button, or img for image, are usually safe, because they are familiar from HTML, from common libraries, and from everyday developer language, and they are unlikely to be misunderstood. Less familiar abbreviations, such as prod for product, hdr for header, or cnt for content, are riskier, because they may be clear to their author but opaque to others, and they may collide with other abbreviations that look similar but mean different things, such as cnt for content versus count.

The decision to abbreviate should therefore be based on familiarity, not just on length saved. An abbreviation that saves only a few characters, such as prod instead of product, is rarely worth the clarity cost, because product is only four characters longer and is unambiguous, while prod could mean product, production, or productivity, depending on context. An abbreviation that saves many characters and is widely known, such as nav instead of navigation, is more justifiable, because the saving is significant and the meaning is standard. That cost-benefit calculation — characters saved versus clarity lost — should be applied to each abbreviation, rather than abbreviating habitually, because habitual abbreviation produces a stylesheet full of short, cryptic names that are hard to learn, even though each individual abbreviation seemed harmless at creation time.

Consistency in abbreviation is as important as the choice of abbreviations themselves, because using both nav and navigation for the same concept in different blocks creates confusion, even if each abbreviation individually is clear. A team should decide, for each common term, whether to use the full word or a specific abbreviation, document that decision in its naming guide, and apply it consistently across all blocks, elements, and modifiers. That consistency allows developers to predict names: if navigation is abbreviated as nav in one block, it will be nav in all blocks, so a developer looking for a navigation component will search for nav, not for both nav and navigation. Inconsistency forces developers to search for multiple variants, which is slower and more error-prone.

Finally, abbreviations should be avoided in block names for major, distinctive components, where clarity matters most, and reserved for very common, generic terms where brevity is genuinely valuable and meaning is standard. A product card should be product-card, not prod-card, because product is a domain term that should be clear, while a navigation link might be nav__link, because nav is a standard abbreviation in web development. That distinction — domain terms full, generic web terms abbreviated where standard — is a useful guideline, though it requires judgement for terms that fall in between. When in doubt, prefer the full word, because clarity is more valuable than brevity in a name that will be read many times by many developers, while the typing cost of a longer name is paid only once at creation.

/* Familiar abbreviations only: nav is standard, prod is not. */
.main-nav__link { color: #0b5fff; }

Section 23: BEM for Layout Components

Layout components in BEM are blocks whose purpose is to arrange other blocks on a page, such as grids, containers, sidebars, and page sections, and they require careful naming because they are often confused with the components they arrange. A layout block, such as page-layout, grid, or two-column, should be named after its layout role, not after the content it contains, because its role is to arrange, not to display content itself, and it should be reusable for different content in the same arrangement. A grid block that arranges cards, for example, should be named grid or card-grid if it is specific to cards, but not product-grid if it is used for other content as well, because a name tied to one content type will mislead when the layout is reused for different content. That role-based naming for layout blocks mirrors the role-based naming for content blocks, applied to arrangement rather than display.

Layout blocks should not style the content blocks they contain beyond arrangement — spacing, alignment, and sizing of the layout's children as layout items — because styling content is the content block's job, and a layout block that restyles its children's typography or colours creates a hidden dependency between layout and content that breaks content reusability. A grid block, for example, should define gap, columns, and alignment for its items, but should not define the cards inside it, their titles, or their colours, because those are defined by the card block itself. If a layout needs to adjust a content block's spacing as a layout item — for example, removing a card's margin when it is inside a grid, because the grid's gap already provides spacing — that adjustment should be expressed as a layout item rule or as a modifier on the content block for grid use, documented as a layout concern, rather than as a descendant rule inside the layout block that silently restyles content.

Elements of layout blocks are typically layout items or regions, such as grid__item, layout__sidebar, or layout__main, each of which describes a region's role in the layout, not the content that fills it. Those element names should be generic enough to be reused for different content in the same region, because a sidebar region may contain navigation on one page and filters on another, and its name should remain accurate for both. A layout element named layout__navigation would be inaccurate when the sidebar contains filters, while layout__sidebar remains accurate for both uses, because it names the region, not its current content. That region-based naming for layout elements is the counterpart to role-based naming for content elements, and it preserves layout reusability across pages with different content.

Keep layout blocks focused on arrangement, and content blocks will remain reusable wherever the layout places them.

/* Layout block: arranges, does not restyle its content blocks. */

Section 24: BEM for Navigation

Navigation in BEM is typically a block named nav, main-nav, or site-nav, with elements for its list, items, and links, and modifiers for its variants, such as horizontal versus vertical, or collapsed versus expanded on mobile. A typical navigation block might have elements nav__list, nav__item, and nav__link, each with a clear role: the list structures the navigation items, each item wraps a link, and each link is the interactive element that navigates. That structure mirrors the markup — a nav element containing a list containing items containing links — but BEM elements are named for their role in the block, not for their HTML tags, so nav__link remains nav__link whether it is rendered as an anchor inside a list item or, in a simpler navigation, as a direct child of the nav element without a list. That tag independence, discussed earlier, is valuable for navigation, because navigation markup may change for accessibility or responsive reasons without changing its BEM structure.

Navigation modifiers include variants for layout, such as nav--horizontal and nav--vertical, for state, such as nav__link--active for the current page, and for responsive behaviour, such as nav--collapsed for a mobile menu that is hidden until toggled. Each modifier should change only its dimension, as per the single-thing principle, so that a navigation can be both horizontal and collapsed, or vertical and expanded, by combining modifiers predictably, without conflicts over properties that both modifiers try to change. The current-page modifier, nav__link--active, deserves special attention, because it is often managed by server rendering or by script that marks the link for the current page, and its style — typically bold text, a different colour, or an underline — must be distinct enough to be recognisable, while still fitting the navigation's overall design and maintaining contrast.

Dropdown navigation adds complexity to BEM naming, because a dropdown is a sub-component within navigation, with its own list, items, and links, which could be named as elements of the navigation block, such as nav__dropdown, nav__dropdown-list, and nav__dropdown-link, or as a separate block, such as dropdown, used inside navigation. The choice depends on independence: if the dropdown is only ever used inside navigation and shares navigation's styling and behaviour, naming it as navigation elements is reasonable, though it risks the element-of-element problem discussed later, where a dropdown link becomes nav__dropdown__link, which BEM discourages. If the dropdown is reusable elsewhere, such as in a toolbar or a form, it should be its own block, with its own elements, used inside navigation as a block-in-block, which preserves its independence and avoids deep element nesting. That independence test, applied to dropdowns, is the same test as for other sub-components, and it should be applied deliberately rather than by defaulting to deep element names.

Section 25: BEM for Cards

Cards in BEM are a textbook block, because a card is a self-contained, reusable component with a clear set of parts and variants, and its BEM structure is easy to describe: block card, elements card__media, card__title, card__text, card__footer, and card__action, modifiers card--large, card--featured, card--horizontal, and so on. That structure, when applied consistently, makes cards easy to find, easy to reuse, and easy to vary, because every card on a site follows the same pattern, and a new card can be built by composing known elements and modifiers, rather than by inventing new class names for each card instance. Cards are therefore a good first BEM component for a team learning BEM, because their structure is intuitive and their BEM names map directly onto their visual parts, which helps developers connect BEM concepts to real markup.

Card elements should be named for their role within the card, not for their content or tag, so that card__title remains card__title whether the title is a heading, a link, or a div, and card__media remains card__media whether the media is an image, a video, or a placeholder. That role-based naming preserves the card's structure across content changes, which is important because cards are often used for different content types — products, articles, profiles, events — each with slightly different media and text, but with the same overall card structure. A card element named card__product-image would be inaccurate for an article card that uses the same element for an article image, while card__media remains accurate for both, because it names the role — media at the top of the card — rather than the specific content type. That generality within a block is a key BEM skill: element names should be general enough to cover all uses of that part within the block, but specific enough to distinguish that part from other parts of the same block.

Card modifiers should follow the single-dimension principle, so that a card can be large, featured, horizontal, and dark by combining modifiers, each changing only its dimension, without conflicts. A horizontal card modifier, for example, should change layout — from stacked to side-by-side — but should not also change colours or padding beyond what layout requires, because those dimensions belong to other modifiers. That composability is especially valuable for cards, because cards appear in many contexts — grids, lists, sidebars, modals — and each context may require a different combination of size, layout, and theme, which can be expressed by combining modifiers in markup, rather than by creating a new card variant for each context. A card system with composable modifiers is therefore more flexible than one with monolithic variants, even though its markup carries more classes, because those classes combine predictably.

Section 26: BEM for Forms

Forms in BEM are typically structured as a form block, with elements for groups, labels, inputs, help text, and error messages, and modifiers for states such as disabled, invalid, or required, though the exact structure depends on whether the form is treated as one large block or as a collection of field blocks. A common pattern is to treat each field as a block, such as field, with elements field__label, field__input, field__help, and field__error, and to treat the form itself as a container block, such as form, that arranges fields, rather than as a block that owns every field element directly. That field-as-block pattern is advantageous because fields are reusable across forms — a name field, an email field, and a password field share the same field structure, even though they appear in different forms — and treating each field as a block preserves that reusability, while treating fields as elements of a specific form would tie them to that form and prevent reuse.

Form element naming should distinguish labels, inputs, and messages clearly, because those parts have different roles and different styling needs, and confusing them in naming will lead to confusing styles. A field__label should style the label text, a field__input should style the input control itself, a field__help should style supplementary guidance, and a field__error should style validation messages, each with its own class, even though they appear together in markup for a single field. That separation allows each part to be styled, hidden, or shown independently — for example, an error message that appears only when the field is invalid, or help text that appears only on focus — without affecting the other parts, which is essential for form interaction states that change part visibility dynamically.

Form modifiers and states include disabled, invalid, required, and focused variations, each of which should be expressed as a modifier on the relevant block or element, following the single-dimension principle. A disabled field might carry field--disabled, which styles its label, input, and help text as muted, or it might carry field__input--disabled on the input alone, depending on whether disabled affects the whole field or only the input, and that choice should be documented, because it affects how disabled styles are written and reviewed. An invalid field similarly might carry field--invalid on the field block, with nested rules or flat rules that style its input border and error message, or it might carry field__input--invalid and field__error--visible as separate modifiers, depending on the team's convention for state handling. Consistency in that choice across forms is more important than which specific convention is chosen, because inconsistent state naming across forms will confuse developers and reviewers.

Test form fields in every state before shipping, because a field that looks right statically may fail when it becomes invalid or disabled.

/* Field block: label, input, help, error elements. */
.field__error { color: #b00020; font-size: 0.875rem; }

Section 27: BEM for Buttons

Buttons in BEM are a classic block, because buttons are ubiquitous, reusable, and varied, with many sizes, themes, and states, all of which benefit from a clear BEM structure. A button block is typically named btn, with elements such as btn__icon and btn__label for buttons that contain an icon plus text, and modifiers such as btn--primary, btn--secondary, btn--large, btn--small, and btn--disabled for its variants and states. That structure allows a button's appearance to be described completely by its class list — for example, btn btn--primary btn--large for a large primary button — without needing to know its context, because the button block is independent and its modifiers compose predictably, each changing only its dimension, as per the single-dimension principle.

Button elements, such as btn__icon and btn__label, deserve attention because they are often overlooked in favour of styling button content through descendant selectors or through generic classes, which breaks BEM's flat, findable structure. An icon inside a button should carry btn__icon, with styles for its size, spacing, and alignment within the button, so that the icon's appearance is defined as part of the button block, not as a generic icon style that happens to apply inside buttons. Similarly, a label inside a button that contains both icon and text should carry btn__label, though many buttons use text directly without a label element, in which case the button's own text styles suffice and a label element is unnecessary. The decision to add an element should be based on whether that part needs distinct styling; if it does not, it should not get an element class merely for completeness, because unnecessary elements add markup noise without benefit.

Button modifiers should be organised by dimension — size, theme, state — so that combinations are predictable, as discussed earlier. Size modifiers, such as btn--small, btn--medium, and btn--large, or a key-value form such as btn--size-large, should change only padding and font size, not colours or borders. Theme modifiers, such as btn--primary, btn--secondary, and btn--danger, should change only colours and borders, not size or layout. State modifiers, such as btn--disabled, should change only the disabled appearance, such as opacity and cursor, and should be applied in addition to theme and size modifiers, so that a large primary disabled button carries all three modifiers and looks large, primary, and disabled simultaneously, without conflicts. That dimensional organisation is what makes button BEM scalable, because new button variants can be created by combining existing modifiers, rather than by creating new monolithic button classes for each combination.

Finally, buttons often appear inside other blocks, such as cards, forms, and modals, and in those contexts they should remain btn blocks, not become elements of the containing block, unless the button is genuinely specific to that container and will never be reused as a button elsewhere. A card action area might be card__action, containing a btn block, which preserves both structures: the card's action area is a card element, and the button inside it is a reusable button block. That block-in-block pattern, applied to buttons, is a recurring BEM judgement that keeps buttons reusable across the site, rather than fragmenting them into card buttons, form buttons, and modal buttons that all look similar but have different names and styles, creating duplication and inconsistency.

Section 28: BEM for Modals and Dialogs

Modals and dialogs in BEM are blocks that overlay page content, typically named modal or dialog, with elements for their backdrop, container, header, title, body, footer, and close button, and modifiers for sizes, themes, and states such as open or hidden. That structure mirrors the modal's visual parts, but it also reflects its behaviour: a modal's backdrop dims the page behind it, its container centres it, its header contains its title and close action, its body contains its main content, and its footer contains its actions, each of which is a distinct part with distinct styling needs. Naming those parts as modal elements — modal__backdrop, modal__container, modal__header, modal__title, modal__body, modal__footer, modal__close — makes the modal's structure visible in markup and in stylesheets, and allows each part to be styled, hidden, or adjusted independently, which is essential for modal variations such as a large modal, a fullscreen modal, or a modal without a footer.

Modal modifiers include size variants, such as modal--large and modal--small, which change the container's width, and state modifiers, such as modal--open, which controls visibility, often in combination with script that toggles the modifier class or an open attribute. Visibility handling for modals deserves care, because a modal that is hidden with display none should also be hidden from assistive technologies and from keyboard navigation, which is achieved through proper markup and attributes, not through BEM classes alone. BEM classes describe appearance, while attributes such as hidden, aria-modal, and inert describe behaviour and accessibility, and both should be used together: a modal--open modifier might change display and opacity for appearance, while script manages focus and inertness for behaviour, with the two systems coordinated rather than conflated. That separation — BEM for appearance, attributes and script for behaviour — keeps modal code understandable, because each system handles its own concern.

Modal content often contains other blocks, such as forms, cards, or buttons, which should remain blocks-in-blocks, not become modal elements, because those inner pieces are reusable elsewhere and have their own BEM structures. A form inside a modal should be a form block, with its own field blocks, not modal__form, unless the form is genuinely specific to that modal and will never appear elsewhere, in which case a modal element might be appropriate, though that specificity should be questioned, because most modal forms — login, signup, confirmation — are variations of general forms that could be reused. That block-in-block judgement, applied to modals, prevents modal files from becoming monolithic, containing styles for every piece of content that might appear inside a modal, which would make modal styles hard to maintain and would duplicate styles for reusable blocks.

Section 29: BEM for Tables and Lists

Tables and lists in BEM are blocks whose elements are their repeating parts — rows, cells, headers for tables, and items, markers for lists — and whose modifiers describe variations such as striped, bordered, compact, or numbered, each of which should be named clearly to reflect its role within the table or list block. A table block, for example, might be named data-table, with elements data-table__header, data-table__row, and data-table__cell, and modifiers data-table--striped, data-table--bordered, and data-table--compact, each changing only its dimension, as per the single-dimension principle. That structure makes the table's appearance predictable: a striped, bordered table carries both modifiers, and each modifier's effect can be understood and tested independently, without needing to know the table's content.

List BEM follows a similar pattern, with a block such as list, menu-list, or todo-list, elements such as list__item, and modifiers such as list--ordered, list--unstyled, or list--compact, each describing a variation in marker style, spacing, or layout. Lists that nest inside each other present a naming challenge, because a nested list's items could be named as elements of the outer list, such as list__item__subitem, which BEM discourages as element-of-element, or as a separate list block inside a list item, which preserves independence and avoids deep element names. The latter is usually preferable: a nested list is a list block inside a list item, with its own list__item elements, rather than a sub-element of the outer list, because the nested list is reusable as a list in its own right, even though it appears inside another list's item. That block-in-block pattern for nested lists mirrors the pattern for nested cards and other components, and it keeps list BEM flat and reusable.

Table and list modifiers should be tested with varied content, including long cell text, wrapped list items, empty cells, and many rows or items, because those content variations reveal whether a modifier's styles hold up in practice or only in a simple example. A striped table modifier, for example, should be tested with an odd and an even number of rows, to ensure striping starts correctly, and with rows that span multiple lines, to ensure striping does not break on wrapped content. A compact list modifier should be tested with long items that wrap, to ensure spacing remains readable when items span multiple lines. Those content tests are part of BEM review for tables and lists, because their repeating structure means that a small styling error will repeat across many rows or items, amplifying its visual impact.

Section 30: BEM Mixes: Two Blocks on One Element

A BEM mix is when a single element in markup carries classes from two different blocks, or a block class plus an element class from another block, because that element plays two roles at once: it is a reusable block in its own right, and it is also a part of another block's structure. A classic example is a button inside a card's footer: the button is a btn block, with its own styles, and it is also the card's action, with card__action styles that position it within the card's footer or add card-specific spacing. Carrying both classes — btn and card__action — allows the element to combine the button's reusable appearance with the card's contextual positioning, without duplicating either set of styles and without creating a new card-button block that would fragment button styles. Mixes are therefore a powerful BEM pattern for composition, allowing reusable blocks to be placed inside other blocks with contextual adjustments.

Mixes require care in the stylesheet, because the two classes' rules may conflict for the same property, and the winner will be determined by cascade order, specificity, and layer, just as for any other conflicting rules. If btn defines padding and card__action also defines padding, the later rule at equal specificity will win, which may not be the intended result if the card action's padding was meant to be additional spacing rather than a replacement for the button's padding. To avoid such conflicts, mixes should be designed so that the two classes control different properties: the block class controls the element's intrinsic appearance, such as the button's colours and padding, while the element class controls its extrinsic positioning within the parent block, such as its margin or alignment in the card footer. That separation — intrinsic versus extrinsic — is the key to mixes that compose predictably, because the two classes do not compete for the same properties.

In markup, mixes should be written with both classes listed, in a consistent order, usually block first, then element, or vice versa by team convention, as long as the order is consistent, because consistent ordering makes mixes easier to scan and to review. A reviewer encountering an element with two classes should be able to tell, from the names, which class is the block and which is the element, and what each contributes, without opening the stylesheet. That readability depends on clear naming: btn clearly says button block, card__action clearly says card action element, and together they say "a button, acting as a card action," which is exactly the mix's meaning. Vague names would obscure that meaning, making mixes confusing rather than compositional.

Keep mixes to two classes where possible, and use a wrapper element when an element would otherwise need three or more roles.

/* Mix: btn block plus card__action element, different properties each. */
.card__action { margin-top: 1rem; text-align: right; }

Section 31: BEM and JavaScript Hooks

JavaScript hooks are classes or attributes used by script to find and interact with elements, and they should be kept separate from BEM styling classes, because mixing the two creates a fragile coupling where a styling change can break behaviour, or a behaviour change can break styling. A common pattern is to use a js- prefix for hook classes, such as js-modal-toggle or js-tab-button, which are used only by script and carry no styles, while BEM classes, such as modal__close or tab__button, carry styles and are used only by stylesheets. That separation means a developer can rename or restyle a BEM class without breaking script, as long as the js- hook remains, and can change script logic without affecting styles, as long as BEM classes remain. It also makes code searchable: searching for js- finds behaviour, searching for BEM names finds styling, without overlap.

An alternative to js- classes is to use data attributes for hooks, such as data-modal-toggle or data-tab, which script can query without needing a class at all, and which are even clearer as behaviour markers, because they do not look like styling classes. Data attributes have the advantage that they cannot be mistaken for styles, even by a developer unfamiliar with the js- convention, and they can carry values, such as data-tab="profile", which script can read directly. Their disadvantage is that they require script to query attributes rather than classes, which is a minor difference in code, but one that a team must agree on, because mixing js- classes and data attributes for hooks in the same project creates two hook systems that developers must learn. Whichever hook system is chosen — js- classes or data attributes — it should be used consistently and documented, so that styling and behaviour remain separate throughout the project.

The danger of mixing hooks and styles is illustrated by a common bug: a developer renames a BEM class during a redesign, from modal__close to modal__dismiss, and updates the stylesheet, but forgets that script also queries modal__close to close the modal, so the modal's close button stops working even though it looks correct. That bug is invisible in a visual test, because the button still appears, but it fails in interaction testing, where clicking it does nothing, and it may not be noticed until readers report it. Separating hooks from styles prevents that bug, because renaming a BEM class would not affect the js- hook or data attribute that script uses, and the close button would continue to work after the redesign, as long as the hook remains on the element.

Document the hook system alongside BEM components, so implementers know which hooks script expects and reviewers can check that markup includes them.

.modal__close { background: transparent; border: 0; }

Section 32: BEM and State Classes

State classes in BEM describe temporary conditions of a block or element, such as active, disabled, open, or hidden, and they can be written either as BEM modifiers, such as nav__link--active, or as separate state classes, such as is-active, depending on the team's convention and on whether the state is managed by stylesheets, script, or both. BEM modifiers for states have the advantage of consistency with other modifiers: they follow the same naming pattern, they are scoped to their block or element, and they are easy to find by searching for the block's modifiers. Separate state classes, often prefixed with is- or has-, have the advantage of being generic and reusable across blocks: is-active can be applied to a navigation link, a tab, or a card, with each block defining what is-active means for it, or with a global is-active rule that applies across blocks. Both approaches are valid, but mixing them inconsistently — some states as modifiers, some as is- classes, without a rule — creates confusion about how to express a new state.

A useful guideline is to use BEM modifiers for states that are intrinsic to a block's design, such as a featured card or a primary button variant that is really a state of the design, and to use is- state classes for states that are managed dynamically by script, such as an open modal, an active tab, or a selected item, where the state is added and removed by interaction rather than being a permanent variant chosen at authoring time. That distinction — design variants as modifiers, dynamic states as is- classes — helps developers decide which form to use for a new state, based on whether the state is chosen by the author in markup or toggled by script at runtime. It also helps script authors, because they can search for is- classes to find dynamic states, without needing to know each block's modifier names for states.

State classes, in either form, should be applied in addition to base classes, not instead of them, following the same additive pattern as modifiers, so that removing the state class returns the element to its base appearance. That additive pattern is essential for dynamic states, because script toggles the state class on and off, and the element must look correct in both states, without needing script to also toggle base classes. It also means that state rules should change only the properties relevant to that state, not redefine the whole component, so that a state change is a small, predictable adjustment rather than a wholesale restyle that might conflict with other modifiers. A state rule that redefines many properties is a sign that the state is really a new variant or a new block, rather than a temporary condition.

Section 33: BEM and Themes

Themes in BEM are site-wide or section-wide appearance variations, such as dark mode or brand themes, and they interact with BEM in a way that requires care to avoid duplicating every block's styles for each theme. The cleanest BEM theme pattern, as with other architectures, is token-based: blocks use custom properties for colours, spacing, and other themeable values, and a theme redefines those tokens on a theme container, so that all BEM blocks using tokens adapt automatically, without needing theme-specific BEM modifiers for each block. That pattern keeps theme logic out of BEM files, except for token definitions, and it ensures that new BEM blocks automatically support all themes, as long as they use tokens rather than hard-coded values, which is a discipline that should be enforced through review and linting for hard-coded colours in BEM files.

When a block needs a theme adjustment beyond tokens — for example, a shadow that should soften in dark mode, or an image treatment that should change — that adjustment can be expressed as a BEM modifier for the theme, such as card--dark, applied to blocks inside a dark section, or as a contextual rule, such as .theme-dark .card, which styles cards inside a dark container. The modifier form is more explicit in markup, because each themed block carries its theme modifier, while the contextual form is more convenient for theming whole sections, because a single theme class on the container themes all blocks inside it. Many systems use both: contextual themes for page or section theming, and modifiers for individual blocks that need a different theme from their surroundings, such as a dark card inside a light article. Whichever forms are used, they should be documented, so that developers know how to theme a new block and how to test it in each theme.

Theme modifiers in BEM should follow the single-dimension principle, changing only theme-related properties, not size, layout, or other dimensions, so that a themed block can combine theme with size and other modifiers predictably, without conflicts. A card--dark modifier that changes only colours and shadows, for example, can combine with card--large, which changes only size, to produce a large dark card, without either modifier overriding the other's properties unintentionally. If dark also changed size, then combining dark with large would produce a conflict over size, where the winner depends on stylesheet order rather than design intent, which is the same composability problem as with other multi-dimension modifiers, applied to themes. Keeping theme modifiers focused on theme properties is therefore essential for composable theming in BEM.

Test every theme with forms, tables, and error states, because those components often reveal hard-coded colours or low contrast that simple text tests miss.

/* Theme via tokens: blocks adapt without theme-specific BEM rules. */
.theme-dark { --color-bg: #111; --color-text: #eee; }

Section 34: BEM and Responsive Variants

Responsive variants in BEM are versions of a block or element that apply at certain viewport or container sizes, such as a navigation block that is horizontal on desktop and vertical on mobile, or a card that is stacked on narrow screens and horizontal on wide screens, and they can be expressed either as BEM modifiers that are applied conditionally, or as media or container queries inside BEM rules that change properties at breakpoints. The modifier form — for example, card--horizontal applied by script or by server rendering based on context — is explicit in markup, but it requires logic to decide when to apply the modifier, which may depend on viewport size that markup alone cannot know, making it awkward for purely viewport-responsive variations. The query form — a media query inside the card's BEM rules that changes layout at a breakpoint — is more natural for viewport responsiveness, because the browser applies it automatically based on viewport size, without needing markup changes or script logic.

A practical pattern for responsive BEM is to use queries for viewport and container responsiveness, and modifiers for contextual variations that are not size-based, such as a card that is horizontal because it appears in a list context, regardless of viewport size, versus a card that is horizontal because the viewport is wide. That distinction — size-based variations via queries, context-based variations via modifiers — helps developers decide which mechanism to use for a new responsive requirement, based on whether the variation depends on size or on context. It also prevents the common mistake of using a modifier for a size-based variation, which then requires script to watch viewport size and toggle the modifier, duplicating what media queries already do automatically and less reliably.

Responsive BEM rules should be organised within their block's file, grouped with the block's other rules, so that a reviewer can see a block's responsive behaviour alongside its base behaviour, rather than searching a separate responsive section for it. That grouping can be achieved by nesting media queries inside BEM rules, as discussed in the nesting chapter, or by listing responsive rules after base rules in the same file, with comments naming their breakpoints, depending on whether the project uses nesting or flat BEM. Whichever organisation is used, it should be consistent across blocks, so that responsive rules are always found in the same place relative to base rules, making them easy to locate and to review for completeness, such as checking that a responsive variation adjusts all relevant properties, not just layout, but also spacing and typography where needed.

Test responsive variants at sizes near breakpoints and in real contexts, because a rule that works in isolation may fail in a narrow sidebar or modal.

/* Responsive BEM: queries for size, modifiers for context. */
.card { padding: 1rem; }
@media (min-width: 40rem) {
  .card--horizontal { display: grid; }
}

Section 35: BEM in Large Projects

BEM in large projects requires additional discipline beyond the basic block-element-modifier rules, because the number of blocks, developers, and pages amplifies every naming, specificity, and organisation problem that BEM is meant to solve. A large project may have hundreds of blocks, each with elements and modifiers, used across dozens of pages by several teams, and without a central registry or catalogue of blocks, developers will duplicate blocks — creating a new card-like block because they did not know an existing card block existed — or will misuse existing blocks, applying a block in a context it was not designed for, because they did not understand its purpose. A component catalogue, as discussed in the previous chapter, is therefore essential for large BEM projects, because it makes existing blocks discoverable, with example markup and variants, so that developers reuse rather than duplicate.

Large BEM projects also need stricter naming governance, because the chance of collisions and inconsistencies grows with the number of contributors. A naming guide that documents block, element, and modifier conventions, with examples and with a process for proposing new blocks, helps prevent the drift where similar blocks get different names, or different blocks get similar names, both of which confuse developers and make the system harder to maintain. That governance should include a review step for new blocks, where a reviewer checks whether a similar block already exists, whether the new block's name clearly distinguishes it, and whether its elements and modifiers follow conventions, before the block is added to the shared system. That review is a small cost at creation time, compared with the cost of renaming or merging duplicated blocks later, after they are used in many places.

File organisation for large BEM projects typically follows one-file-per-block, with blocks grouped by category or feature, and with an entry file that imports blocks in layer order, as discussed in the previous chapter. That organisation makes blocks findable by file name, enables parallel work by different teams on different blocks, and allows per-page inclusion of only the blocks a page uses, which is a performance benefit for large sites. It also requires tooling to manage imports and to detect unused blocks, because a large system with many files can accumulate dead blocks that are no longer used but remain in the build, increasing size and confusion. Regular audits for dead blocks, using tooling that scans markup for BEM class usage, should be part of large-project maintenance, just as dead-code audits are for stylesheets generally.

Plan block evolution with deprecation and versioning, so large BEM systems can change without breaking the many pages and teams that use them.

A catalogue that shows every block with its variants prevents duplication and helps new developers reuse existing blocks.

Section 36: BEM File Organisation

BEM file organisation typically follows one file per block, with that file containing the block's base styles, its elements, its modifiers, and its states, ordered logically and grouped with comments, so that the file is a complete definition of the block that can be understood, changed, and reviewed in isolation. That one-file-per-block rule mirrors the component file rule from the previous chapter, and it has the same benefits: findability by file name, safe parallel work, easy review, and per-page inclusion for performance. A file named card.css that contains .card, .card__media, .card__title, .card__text, .card__footer, .card--large, and .card--featured is a self-contained definition of the card block, and a developer who needs to change a card can open that one file and see everything relevant, without searching other files for card-related rules that might be scattered elsewhere.

Within a block file, rules should be ordered to reflect the block's structure: base block first, then elements in markup order, then modifiers, then states, then responsive and print adjustments, each group separated by a comment that names the group. That ordering makes the file easy to scan, because a reader knows where to look for each kind of rule, and it ensures that modifiers, which appear after base rules at equal specificity, win for differing properties, which is the intended cascade behaviour for BEM. It also makes review easier, because a reviewer can check that all elements and modifiers are present, that states are covered, and that responsive adjustments are complete, by scanning the file's groups in order, rather than by searching for rules that might be in unexpected places.

Shared BEM files, such as a file for tokens, utilities, or base styles, should be separate from block files, because they are not blocks and should not be confused with them. Tokens belong in a tokens file, base element styles in a base file, layout blocks in layout files, and utilities in utility files, each with its own naming and organisation, as discussed in the previous chapter. Mixing shared styles into block files — for example, defining a utility inside a card file because that utility was first needed for cards — creates a hidden dependency, where other blocks that need the same utility must either duplicate it or import the card file for a non-card rule, both of which are confusing. Shared styles should live in shared files, and block files should contain only their block's styles, with dependencies on shared files made explicit through imports or comments.

Finally, BEM file organisation should be documented in a short readme or style guide section that lists the file structure, the naming convention for files, and the ordering convention within files, so that new contributors can place new blocks correctly on their first try. That documentation should include examples of a well-organised block file, showing base, elements, modifiers, and states in order, so that developers can copy the pattern rather than inventing their own ordering for each new block. Consistent file organisation, like consistent naming, is a habit that pays off through easier navigation and review, and it should be checked in review, just as naming is, because a block file that is disorganised will be harder to maintain even if its individual rules are correct.

/* card.css: base, elements in order, modifiers, states. */
.card { padding: 1rem; }
.card__title { font-size: 1.25rem; }
.card--large { padding: 2rem; }

Section 37: BEM Documentation

BEM documentation should describe each block's purpose, its elements, its modifiers, its states, and its usage examples, so that developers can use the block correctly without needing to read its stylesheet or to copy an existing usage blindly. That documentation can take several forms: comments in the block's file, a component catalogue page that renders the block with example markup, or a separate documentation file that lists blocks and their APIs, each with its own strengths. File comments are the most immediate form, because they travel with the code and are visible to anyone editing the block, but they are limited in space and cannot show rendered examples. A catalogue page, by contrast, can show the block rendered with each variant and state, which is invaluable for visual understanding, but it requires tooling or manual maintenance to keep it in sync with the code. A combination — concise file comments plus a catalogue for visual reference — is often the most practical documentation strategy for BEM.

Documentation for a BEM block should include its purpose in one sentence, its elements with a brief description of each part's role, its modifiers with a description of what each changes, its states with how each is triggered, and at least one example of correct markup, showing the block with its elements and a typical modifier combination. That example markup is especially important, because BEM's explicit class structure means that correct usage is not obvious from the block name alone: a developer needs to see which elements go inside which block, in what order, and with which classes, to implement the block correctly. An example that shows a card with media, title, text, and footer, in order, with a large modifier on the card, teaches more in a few lines than a paragraph describing the card's structure in prose.

Documentation should also note a block's dependencies and its constraints, such as other blocks it contains, hooks it expects for script, themes it supports, and contexts where it should not be used. A card block that contains a button block, for example, should note that it expects btn classes for its actions, rather than card-specific button styles, so that implementers do not invent card__button classes for actions. A modal block should note its focus and accessibility requirements, so that implementers do not use it in a way that breaks keyboard navigation. Those constraints are part of a block's API, just as much as its elements and modifiers, and documenting them prevents misuse that would otherwise only be discovered through bugs or review feedback.

Update BEM documentation in the same change as the code, so documentation stays accurate and developers can trust it when implementing blocks.

Section 38: Common BEM Mistakes: Element of Element

The element-of-element mistake in BEM is writing an element name that contains another element name, such as card__header__title or form__group__label, which suggests a hierarchy of elements within elements, rather than a flat list of elements belonging to a block. BEM discourages that pattern, because it creates deep, fragile names that mirror markup nesting too faithfully, making elements harder to reuse, harder to rename, and harder to understand, since their meaning depends on a chain of ancestors rather than on a direct relationship to the block. A card header title, for example, is really just a card title that happens to be inside a card header in one markup arrangement, but if the header wrapper is removed or restructured, the element-of-element name becomes misleading, even though the title's role within the card has not changed. Flat element names, such as card__title, remain accurate regardless of intermediate wrappers, because they describe the title's role in the card, not its exact position in the markup tree.

The fix for element-of-element names is usually to flatten: identify the element's role within the block, give it a direct element name under the block, and remove the intermediate element from its name, even if the intermediate element remains in markup as a structural wrapper. A card with a header containing a title and actions, for example, might have a card__header wrapper for layout, but its title should still be card__title, not card__header__title, because the title's role is as the card's title, not as the header's title, and its styles should be defined as a card element, not as a header element's element. That flattening preserves the element's independence from intermediate wrappers, so that a markup change that adds or removes a wrapper does not require renaming the element, which would touch markup and stylesheets together.

There are cases where an element-of-element name seems necessary, such as a complex block with a distinct sub-component that has its own parts, where the sub-component's parts genuinely belong to the sub-component, not to the outer block. In those cases, the correct BEM solution is usually to promote the sub-component to its own block, with its own elements, rather than to nest elements within elements. A card header that contains a title, actions, and a badge, for example, could be a header block used inside a card, with header__title, header__actions, and header__badge, rather than card__header__title and similar deep names. That promotion preserves BEM's flat structure at both levels: the card has its elements, the header has its elements, and the header block is used inside the card as a block-in-block, which is a clean, reusable pattern that avoids deep names entirely.

Flag element-of-element names in review, and ask whether the inner part belongs directly to the block or to a separate sub-block instead.

/* Wrong: card__header__title. Right: card__title, or a header block. */
.card__title { font-size: 1.25rem; }

Section 39: Common BEM Mistakes: Modifier on Element

The modifier-on-element mistake is a subtle one, because modifiers on elements are actually allowed in BEM — for example, card__title--featured is a valid modifier of a card title element — so the mistake is not using a modifier on an element at all, but using it incorrectly, such as applying a block modifier to an element, applying an element modifier to the wrong element, or creating a modifier that duplicates a block modifier's effect on an element where it does not belong. A common version is applying card--large to a card__title element, expecting it to make the title large, when card--large is a modifier of the card block, not of its title, and it will have no effect on the title unless the stylesheet defines a rule for that combination, which it should not, because modifiers should apply to the block or element they name, not to other elements. That misapplication produces a style that appears to do nothing, confusing the author, who may then add a new rule to make it work, creating a non-standard modifier that breaks BEM's naming logic.

Another version is creating an element modifier that should really be a block modifier, such as card__title--large for a large card, when the largeness belongs to the whole card, not just its title, and should therefore be card--large on the card block, with the title's size adjusting as part of the card's large variant, either through a card--large rule that styles card__title, or through the title inheriting size from the card. Applying a title-only large modifier to a card that should be large overall produces a card with a large title but normal padding, spacing, and other parts, which looks inconsistent and is not what the author intended when they chose a large card. That mistake stems from not asking whether the variation belongs to the block or to the element, and it is fixed by moving the modifier to the correct level — block for whole-component variations, element for part-specific variations — and by defining the modifier's effects accordingly.

A related mistake is using an element modifier to style a different element, such as applying card__title--featured to a card__text element, expecting it to make the text featured, when the modifier's name says it modifies the title, not the text, and its stylesheet rule will only match title elements carrying that modifier, not text elements. That misapplication, like the block-modifier-on-element mistake, produces a style that does nothing, and it suggests that the author needs a text modifier, such as card__text--featured, or a block modifier, such as card--featured, depending on whether featuredness belongs to the text alone or to the whole card. The fix is to choose the modifier that names the element or block that should actually change, rather than reusing a modifier name for a different target because it happens to have the desired visual effect in one case.

/* Modifier must name its target: card--large on .card, not on .card__title. */
.card--large { padding: 2rem; }

Section 40: Common BEM Mistakes: Global Names

Global names in BEM are class names that are not tied to a specific block, such as title, button, large, or active, used as standalone classes without a block prefix, and they are a mistake in a BEM system because they reintroduce the collisions, ambiguity, and specificity problems that BEM names are meant to prevent. A global title class, defined for one purpose, may be applied to titles in many blocks, producing a shared style that seems convenient at first, but that becomes a problem when one block's title needs a different style from another's, because changing the global title rule will affect all titles, while overriding it for one block will require a more specific rule that defeats BEM's flat specificity. That shared-global pattern is the opposite of BEM's block-scoped naming, where each block's title has its own name and can change independently, without affecting other blocks' titles.

Global names also make code harder to search and to maintain, because a search for title will find the global rule, all its uses across blocks, and possibly unrelated uses of the word title in other contexts, making it hard to determine the global rule's impact before changing it. A BEM name such as card__title, by contrast, can be searched precisely, revealing only card titles, which makes its impact clear and its change safe. That searchability difference is a practical reason to avoid global names, even for seemingly universal concepts such as titles, buttons, or containers, because universality in name does not imply universality in style: a card title and an article title may both be titles, but they may need different sizes, colours, or spacing, and giving them distinct BEM names allows those differences to be expressed without overrides or conflicts.

There are legitimate uses for global classes outside BEM, such as utilities, which are intentionally global and single-purpose, and base element styles, which apply to elements regardless of block, but those globals should be clearly distinguished from BEM blocks, through naming conventions such as utility prefixes or through separate files and layers, so that they are not mistaken for BEM blocks. A utility class such as text-center is global by design, because it does one thing everywhere, while a BEM block class such as card is scoped by design, because it defines a specific component. Mixing the two — using a global class as if it were a BEM block, or a BEM class as if it were a utility — creates confusion about whether a class is meant to be reusable everywhere or specific to one component, and that confusion leads to misuse.

Audit global names periodically, converting unintended globals to scoped BEM names or to documented utilities, so the system stays predictable.

/* Avoid global names: use card__title, not title, in BEM systems. */
.card__title { font-size: 1.25rem; }

Section 41: BEM Versus Other Naming Systems

BEM is one of several naming systems for CSS, each with different trade-offs, and comparing BEM with others — such as SMACSS naming, OOCSS naming, utility naming, and scoped or CSS-module naming — helps you understand when BEM is the right choice and when another system, or a hybrid, might fit better. SMACSS naming, for example, uses prefixes for layout and state, such as l- for layout and is- for state, but does not encode block-element relationships as explicitly as BEM, relying instead on file organisation and developer discipline to keep components distinct. That lighter naming is easier to write for small projects, but it provides less protection against collisions and less visibility of structure in markup, compared with BEM's explicit block prefixes, which is why larger projects often prefer BEM's verbosity for its clarity.

OOCSS naming, by contrast, emphasises reusable, single-purpose classes for structure and skin, such as a size class and a colour class combined in markup, rather than a single block class with elements and modifiers. That approach produces very reusable classes, because a size class can be used on any component, but it produces markup with many classes and a stylesheet where a component's appearance is scattered across many small rules, rather than grouped under one block name. BEM, by contrast, groups a component's appearance under its block, with elements and modifiers that belong to that block, which makes a component easier to find, understand, and change as a unit, at the cost of less reuse for individual properties across blocks. The choice between OOCSS and BEM is therefore a choice between property-level reuse and component-level coherence, and many projects combine them, using BEM for components and OOCSS-style utilities for shared properties.

Scoped naming systems, such as CSS Modules or scoped styles in frameworks, solve collisions differently, by automatically generating unique class names at build time, so that developers can use short, simple names in source that become unique in output, without needing BEM prefixes. That automation removes the naming burden from developers and guarantees no collisions, but it also makes class names in output unreadable, which complicates debugging in browser tools, and it ties the naming system to a build tool or framework, whereas BEM works in plain CSS without any tooling. A project that already uses a framework with scoped styles may not need BEM's manual namespacing, while a project using plain CSS, or a design system consumed by many frameworks, may prefer BEM's portable, human-readable names that work everywhere without a build step.

Choose the hybrid that fits your project, document it clearly, and enforce it consistently, rather than forcing every class into a single pattern.

A documented hybrid beats an undocumented pure system every time.

/* BEM for components, utilities for single-purpose adjustments. */
.card { padding: 1rem; }
.text-center { text-align: center; }

Section 42: BEM Versus Utility Naming

BEM naming and utility naming serve different purposes, and understanding that difference helps you decide when to use each, rather than treating them as competing systems where one must win. BEM names describe components — blocks with parts and variants — and they are meant to be stable, descriptive, and scoped to their block, so that a card's title can be found, changed, and reused as part of the card. Utility names describe single properties — margin, text alignment, display, colour — and they are meant to be global, short, and composable, so that a local adjustment can be made in markup without writing new CSS. A card built with BEM carries card, card__title, and card--large, which describe what it is, while a local spacing adjustment on that card might carry a utility such as m-0, which describes one property change, not the card's identity. Both kinds of names can coexist on the same element, as a mix, without conflict, as long as each kind is used for its purpose.

The main difference in practice is specificity and priority: BEM classes, with one class each, live in the components layer, while utilities, also with one class each, live in the utilities layer, which is later, so utilities win for properties they both set, which is the intended behaviour for local adjustments. That layer-based priority means that a utility and a BEM class can be applied together predictably, without needing to know their order in a file, as long as the layer order is correct. Without layers, the same predictability requires file order — utilities loaded after components — which is more fragile, as discussed earlier, but still workable for small projects. Either way, the utility's purpose is to win locally, while the BEM class's purpose is to define the component generally, and that division of labour is what makes their coexistence workable.

Naming style also differs: BEM names are long and descriptive, because they encode block, element, and modifier, while utility names are short and abbreviated, because they encode a single property and value, such as m-0 for margin zero, p-4 for padding, or text-center for text alignment. That brevity is appropriate for utilities, because they are used frequently in markup and their meaning is standardised, so a short name is quickly learned, while BEM names' verbosity is appropriate for components, because components are fewer, more complex, and benefit from descriptive names that explain their structure. A utility system that used BEM-like long names for every utility would be verbose in markup, while a BEM system that used utility-like abbreviations for components would be cryptic, so each system's naming style fits its purpose, and mixing the styles — long utilities or abbreviated components — would undermine both.

/* BEM defines the component; utility adjusts it locally. */
.card { padding: 1rem; }
.m-0 { margin: 0; }

Section 43: BEM Versus Atomic Naming

Atomic naming, as in atomic CSS, takes utility naming to its extreme, where every class represents a single CSS declaration — for example, a class for margin-top zero, a class for font-weight bold, or a class for display flex — and components are built entirely in markup by combining dozens of atomic classes, without any component class at all. That approach differs sharply from BEM, where a component is defined by a block class with elements and modifiers, and its appearance is defined in a stylesheet, not in markup. Atomic naming's advantage is that it eliminates almost all custom stylesheet writing, because new designs can be composed from existing atomic classes, and it guarantees no unused component styles, because there are no component styles to become dead, only atomic classes that are either used or purged. Its disadvantage, as discussed in the previous chapter, is markup verbosity and the difficulty of changing a component that appears in many places, because each appearance must be edited in markup, rather than changing one stylesheet rule.

BEM's advantage over atomic naming is component coherence: a card defined as a BEM block can be changed once, in its stylesheet file, and every card on the site will update, which is essential for a component used in many places or for a design system where consistency matters. Atomic naming's advantage over BEM is composition speed for one-off designs, where a new layout can be built quickly from existing utilities without writing a new component, which is valuable for prototyping or for marketing pages with unique designs that will never be reused. Those advantages point to different use cases, not to a universal winner: reusable, stable components favour BEM, while unique, rapidly changing designs favour atomic utilities, and most real projects contain both kinds of design, which is why a hybrid approach is often the most practical.

A hybrid of BEM and atomic naming might use BEM for core, reusable components — cards, buttons, navigation, forms — and atomic utilities for page-specific layouts, spacing adjustments, and one-off compositions that do not deserve a new BEM block. That hybrid requires a documented boundary, such as "if a design will be reused three or more times, make it a BEM block; if it is used once, build it with utilities," so that developers can decide which approach to use for a new design without debating it each time. Without such a boundary, a hybrid system can drift, with some developers building everything with utilities, producing verbose markup, and others building everything with BEM, producing many single-use blocks, both of which undermine the hybrid's benefits. A clear, simple boundary, even if arbitrary, is better than no boundary, because it gives the team a shared decision rule.

/* Atomic: many small classes in markup. BEM: one block class. */
.card { padding: 1rem; }

Section 44: Migrating to BEM Safely

Migrating an existing stylesheet to BEM safely requires an incremental approach, because a bulk rename of all classes at once would require changing markup and stylesheets together across the whole site, with a high risk of missing a usage or breaking a page that was not tested. The safe approach is to migrate one component at a time, starting with a low-risk, well-understood component, such as a button or a card, renaming its classes to BEM, updating its markup usages, and verifying appearance before moving to the next component. That pilot migration establishes the BEM pattern for the project, reveals any naming or specificity issues with the chosen BEM conventions, and gives the team a reference example for subsequent components, all while the rest of the site continues to use the old naming, so that a problem with one component does not block the whole site.

During migration, old and new naming will coexist, which requires care to prevent collisions and confusion. A component migrated to BEM should have its old classes removed from markup and stylesheets once migration is verified, rather than leaving both old and new classes in place, because dual classes create duplication and make it unclear which class is authoritative. If a component is used in many places, its migration may need to be staged — first adding BEM classes alongside old classes, then updating markup usages gradually, then removing old classes once all usages are migrated — with a migration list tracking which pages have been updated and which remain. That staged approach, with a clear list, prevents the common migration failure where some pages are migrated and others are forgotten, leaving a mix of old and new classes that is harder to maintain than either system alone.

Tooling can help migration, by searching for old class names across markup and stylesheets, by renaming classes systematically, and by reporting usages that were missed, but tooling cannot replace human judgement about whether a class is a block, an element, or a modifier, or whether a piece of design should become a new block or remain an element. Those judgements require understanding the component's purpose and structure, which is why migration should be done by developers who understand the components, not solely by automated renaming, and why each migrated component should be reviewed for BEM correctness — block independence, element flatness, modifier single-dimension — not just for visual equivalence. A migration that preserves appearance but violates BEM principles will not gain BEM's maintainability benefits, even though it uses BEM names, because its structure will still be unstructured underneath the new names.

Track migration progress with a list of migrated and unmigrated components, so no page is forgotten and the system converges instead of mixing old and new.

Section 45: Refactoring Non-BEM CSS to BEM

Refactoring non-BEM CSS to BEM is similar to migrating to BEM, but it focuses on restructuring existing rules — which may use descendant selectors, ids, or generic class names — into BEM's flat, block-element-modifier structure, without changing appearance, which is the definition of safe refactoring. The first step is to identify a component's existing rules, including its base, parts, states, and variants, which may be scattered across files or expressed through descendant selectors that chain the component's structure, such as .sidebar .card h2 for a card title inside a sidebar. Those scattered, chained rules must be grouped by component, flattened to single BEM classes, and renamed to BEM names, with each new BEM class defined in the component's file, in base-before-modifier order, so that the refactored component's stylesheet is a clean BEM definition, not merely old rules with new names.

A key refactoring judgement is deciding what is a block, what is an element, and what is a modifier in the existing code, because non-BEM code often does not make those distinctions explicitly. A rule such as .card h2 might be a card title element, which should become .card__title, while a rule such as .card.large might be a large card modifier, which should become .card--large, and a rule such as .sidebar .card might be a layout concern, which should become a layout rule or a card mix, rather than a BEM modifier. Those judgements require understanding the component's design intent, not just its current selectors, and they should be documented for each refactored component, so that reviewers can check whether the BEM structure correctly captures the original design, or whether it has introduced a new structure that changes behaviour subtly, such as by flattening a descendant rule that previously only applied inside a specific container.

Specificity changes are a major refactoring risk, because flattening a descendant rule with two classes to a single BEM class reduces its specificity, which may cause it to lose contests it previously won, especially against other rules that have not yet been refactored and still have higher specificity. That risk should be managed by refactoring in layer order, or by verifying appearance after each component's refactoring, and by fixing any specificity regressions through layer placement or order, rather than by reintroducing descendant selectors to restore old specificity, which would defeat BEM's flat-specificity benefit. If a refactored component's styles break because of a specificity drop, that breakage reveals a dependency on high specificity that should be addressed structurally — for example, by moving a competing rule to a lower layer — rather than by preserving the old high-specificity selector under a new BEM name.

Verify each refactored component visually before moving to the next, so specificity changes are caught while they are still attributable to one component.

/* Refactor: group by component, flatten to BEM, verify appearance. */
.card__title { font-size: 1.25rem; }

Section 46: Reviewing BEM Code

Reviewing BEM code requires checking naming, structure, specificity, and usage together, because a BEM rule can be correct in isolation — a well-named class with correct styles — but incorrect in context, if it is applied to the wrong element, if it duplicates an existing block, or if it violates the project's BEM conventions in a subtle way. A BEM review checklist helps make that context check systematic, asking: is this a new block, element, or modifier, and is its name correct for that role; does its name follow separator, case, and abbreviation conventions; is its selector flat and single-class, except for intentional modifier compounds; does it change only its dimension, if it is a modifier; is it used correctly in markup, with base plus modifier and with elements inside their block; and does it duplicate an existing block or utility that should be reused instead? Each question catches a common BEM mistake, and answering them for a change takes only a few minutes, yet it prevents most BEM inconsistencies from reaching production.

Reviewers should also check BEM code for the mistakes discussed earlier in this chapter: element-of-element names, modifiers applied to the wrong target, global names, blocks that depend on parents, and elements used standalone, each of which can be spotted by reading class names in markup and in stylesheets together, rather than by reading either alone. A stylesheet review that does not check markup will miss misapplied modifiers, while a markup review that does not check stylesheets will miss incorrectly defined modifiers, so BEM review must consider both sides together, ideally by viewing the component rendered with its example markup, as in a catalogue, where both markup and styles are visible at once. That rendered view is the most reliable way to review BEM, because it shows whether the naming structure actually produces the intended appearance, not just whether names look correct in isolation.

BEM review should also consider the component's place in the larger system: does it belong in the shared component system, or is it page-specific and therefore better placed in a page file; does it use tokens rather than hard-coded values, so that it supports themes; does it handle states, responsive behaviour, and accessibility, as discussed for other components; and does it have documentation, with purpose, elements, modifiers, and example markup, that will allow other developers to use it correctly? Those system-level questions distinguish a BEM review from a simple naming check, because they ensure that a new block fits the system, rather than merely following BEM syntax while duplicating an existing block or breaking theme support. A block that follows BEM syntax but duplicates an existing block is still a problem, even though its names are correct, because duplication undermines the shared system that BEM is meant to create.

Section 47: BEM Style Guide for Teams

A BEM style guide for teams should be a short, practical document that records the team's BEM decisions — separator usage, block-element-modifier definitions, boolean versus key-value modifiers, naming conventions for blocks, elements, and modifiers, the boundary between BEM and utilities, state class conventions, file organisation, and review practices — with examples of correct and incorrect usage for each decision, drawn from the team's own components where possible. That guide serves as the single reference for BEM in the project, so that developers do not need to consult external BEM documentation, which may describe a different variant of BEM, or to guess at conventions for cases the guide does not cover, which would lead to inconsistency. A guide that is short and example-rich will be used, while one that is long and abstract will be ignored, so brevity and examples are more important than completeness for its own sake.

The style guide should start with the core BEM definitions, illustrated with a single example component — typically a card — that shows a block, its elements, and its modifiers, in both markup and stylesheet, so that a new developer can learn BEM's basics from one component before reading further. It should then cover the decisions that cause most confusion in practice: when to use a block versus an element, how to handle mixes, how to name modifiers, when to use boolean versus key-value forms, how to handle states, and how to combine BEM with nesting, layers, and scope, each with a correct example and a common mistake to avoid. Those sections, each short and focused, address the questions developers actually ask when writing BEM, rather than restating BEM theory that they can find elsewhere.

The guide should also include a section on file organisation and documentation, specifying one file per block, ordering within files, and what documentation each block needs, because those organisational decisions are part of BEM practice in a team, even though they are not part of BEM's core naming definition. It should include a review checklist, such as the one described in the previous section, so that reviewers can check BEM changes consistently, without needing to remember every convention from scratch. And it should include a process for proposing new blocks, for deprecating old blocks, and for updating the guide itself, so that the guide remains a living document that evolves with the project, rather than a static document that becomes outdated as the project grows.

Finally, the style guide should be maintained by the team as a whole, with updates proposed, reviewed, and documented like other code changes, rather than being owned by a single person who may leave or become unavailable. That shared maintenance ensures that the guide reflects the team's current practices, not just its initial decisions, and that new developers can contribute to it as they learn BEM and encounter cases the guide does not cover. A style guide that is maintained collectively will be trusted and followed, while one that is imposed and never updated will be ignored, even if its initial content was excellent. BEM adoption, like other architectural adoption, succeeds through shared ownership and continuous maintenance, not through a single document written once and forgotten.

Section 48: When Not to Use BEM

Knowing when not to use BEM is as important as knowing how to use it, because BEM applied indiscriminately to every style — including utilities, base styles, and one-off page adjustments — creates unnecessary verbosity and obscures the distinction between reusable components and local tweaks. Utilities, for example, should not be named as BEM blocks, because they are global and single-purpose, not components with parts and variants, and giving them BEM names such as margin__zero or text__center would be misleading, suggesting a block structure that does not exist, while also making utility names longer without benefit. Base element styles, similarly, should not be BEM blocks, because they apply to elements regardless of component, and naming them as blocks would tie them to a component they do not belong to. BEM is for components; utilities and base styles have their own naming systems, and using BEM for them conflates categories that should remain distinct.

BEM is also less useful for very small projects with few components, where the overhead of BEM naming, file organisation, and documentation may outweigh its benefits, because a small stylesheet with a handful of components can be understood without a formal naming system, and the time spent learning and enforcing BEM might be better spent on other aspects of the project. That does not mean small projects should use vague names — clear, descriptive class names are valuable at any scale — but it does mean that a full BEM system, with strict block-element-modifier discipline, may be disproportionate for a project with three components that will never grow. A small project can adopt BEM principles — clear names, flat selectors, component grouping — without adopting every BEM rule strictly, and can formalise into full BEM later if it grows, which is a more proportionate approach than imposing full BEM from the start on a tiny codebase.

BEM may also be a poor fit for projects that already use a different naming or scoping system effectively, such as CSS Modules, scoped framework styles, or a well-established utility system, where introducing BEM would create two naming systems that conflict or duplicate each other, confusing developers about which system to use for a new style. In those projects, the existing system's benefits — automatic scoping, for example — may already solve the problems BEM addresses, such as collisions, without needing BEM's manual namespacing, and adding BEM on top would add complexity without benefit. The decision to use BEM should therefore consider the project's existing tooling and conventions, not just BEM's merits in isolation, because a naming system that conflicts with existing tooling will be resisted and inconsistently applied, undermining both systems.

Adopt BEM principles proportionally for small projects, formalising into full BEM only if the project grows enough to need it.

Section 49: BEM and Accessibility Naming

BEM and accessibility naming intersect in several ways, because class names can support or hinder accessibility, even though they are not themselves exposed to assistive technologies in the same way as semantic markup and attributes. The most important intersection is that BEM class names should not replace semantic elements or accessibility attributes: a button block should still be a button element, or an element with appropriate button semantics, not a div with a btn class that looks like a button but is not announced as one, and a navigation block should still use nav and list elements where appropriate, with BEM classes for styling, not divs that look like navigation but lack its semantics. That principle — BEM for styling, semantics for meaning — ensures that a component's appearance, described by BEM, does not come at the cost of its accessibility, described by markup and attributes, and it should be checked in review for every new BEM component.

Another intersection is state naming: BEM state modifiers or is- classes, such as disabled, active, or selected, should correspond to actual states that are also conveyed through attributes, such as disabled, aria-selected, or aria-expanded, so that visual state and programmatic state agree. A button that looks disabled through a btn--disabled class, but is still focusable and clickable because it lacks a disabled attribute, is misleading for keyboard and screen reader users, who may try to activate it and fail, or who may not realise it is disabled at all. Similarly, a tab that looks active through a tab--active class, but lacks aria-selected, will not be announced as active to screen reader users, even though sighted users can see its active styling. BEM state classes should therefore be applied together with the corresponding attributes, by script or by server rendering, so that visual and programmatic states stay in sync, rather than relying on class names alone to convey state.

Focus and contrast, discussed in earlier chapters, also relate to BEM naming, because a BEM component's focus styles and colour tokens should be defined as part of the block, with clear names that make their accessibility purpose visible. A focus modifier or a focus rule for a BEM block, such as btn:focus-visible, should be listed with the block's other states in its file, so that reviewers can check that focus is covered, and its colour tokens should be chosen from accessible token pairs, as discussed for tokens, so that contrast is guaranteed by the token system rather than by individual component choices. That integration — focus and contrast as part of BEM block definitions, not as afterthoughts — makes accessibility a routine part of BEM component development, rather than a separate audit that happens after components are built.

Section 50: BEM Playbook

A BEM playbook is a short set of habits that lets a team use BEM confidently without reconsidering every naming decision from scratch. Start by identifying blocks as independent, reusable components, naming them clearly after their purpose, and giving each block its own file, with its elements, modifiers, and states ordered base first, then elements in markup order, then modifiers, then states. Name elements as block__element, with role-based names that do not encode HTML tags, and name modifiers as block--modifier or block__element--modifier, changing only one dimension each, using boolean forms for present-or-absent variations and key-value forms for dimensions with multiple values. Use flat, single-class selectors for most BEM rules, place BEM files in the correct layers, use tokens for themeable values, and keep JavaScript hooks separate, with js- classes or data attributes, so that styling and behaviour do not couple. Those habits, followed consistently, produce a BEM system that is findable, reusable, and safe to change.

Inside a BEM block, organise work in a logical sequence that mirrors how a reader encounters the component: base appearance first, then parts, then variants, then states, then responsive and print adjustments, each group separated by a comment, so that the file reads as a complete description of the block. When a new variation is needed, ask first whether it is a modifier of an existing block, a new element of that block, a mix with another block, or a new block entirely, using the independence test — does this piece make sense alone? — to decide, rather than defaulting to a new modifier for every variation, which would pollute the block with disguised new components. When a block grows too large, split it: extract a sub-component as its own block, move page layout out, or flatten a part that has become reusable, rather than letting the block become unwieldy for the sake of keeping everything in one file.

When something goes wrong with a BEM component, follow the debugging playbook: check the class names in markup against the stylesheet, checking that modifiers name their correct target, that elements are inside their block, and that no element-of-element or global names have crept in; check specificity, ensuring most selectors are single classes and that modifiers come after base rules; check layers, ensuring BEM files are layered correctly and no unlayered file jumps the queue; and check the rendered result, with visual and interaction testing, to confirm that the fix actually resolves the problem rather than merely changing class names. Document exceptions — a mix, a deep element, a global utility used inside a BEM block — with a comment that names the reason, so the exception does not become a mystery for the next reader, and so that reviewers can distinguish intentional exceptions from mistakes.

/* Playbook: blocks independent, elements flat, modifiers single-dimension. */

.card__title { font-size: 1.25rem; }
.card--large { padding: 2rem; }
