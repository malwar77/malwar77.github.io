Chapter 42: Nesting Rules the Modern Way

Section 1: Nesting: A Gentler Way to Write CSS

Nesting lets you write a child rule inside its parent rule, instead of repeating the parent selector on every line, which makes the relationship between styles visible in the structure of the code itself. In flat CSS, a card and its title, text, and button are separate rules that happen to share a prefix, and a reader must compare selectors to see that they belong together. In nested CSS, those rules sit physically inside the card rule, so the grouping is obvious at a glance. That visual grouping is the main benefit of nesting: it turns a list of loosely related rules into a small, coherent block that reads like a description of one component.

The idea is not new. Preprocessors such as Sass have offered nesting for many years, and many developers learned to organise components that way long before browsers supported it natively. Native nesting brings the same ergonomics to plain CSS, without a build step, which means the code you write is the code the browser reads, and there is no compilation stage to hide mistakes. That directness is valuable for learning, because what you see in your file is what the browser's tools will show you, with no generated selectors to untangle when something goes wrong.

Nesting does not change what CSS can do; it only changes how you write it. A nested rule is equivalent to a flat rule with the parent selector combined with the nested selector, and the cascade treats the resulting selector exactly as if you had written it flat. That equivalence is reassuring: you are not learning a new styling model, only a more compact syntax for an existing one. If a nested rule behaves unexpectedly, you can always expand it mentally into its flat form and reason about it with the cascade rules you already know from the previous chapter.

The risk of nesting is the same as its benefit: because grouping is so easy, it is tempting to nest everything, including rules that do not truly belong together, and to nest so deeply that the resulting selectors become long and specific. A nested block that mirrors the document tree too faithfully will produce descendant selectors that are brittle and hard to override, just as flat descendant selectors would. The discipline of nesting, which this chapter develops, is to nest for readability and component cohesion, not to reproduce every level of markup, and to keep nesting shallow enough that the expanded selectors stay short.

A good starting rule is to nest only when the nested rule is genuinely part of the parent component, and to stop nesting when the child could stand alone as a reusable piece. That test keeps blocks focused and prevents the nesting from becoming a map of the whole page. With that habit, nesting makes stylesheets shorter, clearer, and easier to maintain, without sacrificing the cascade control you learned to value in the previous chapter.

.card {
  padding: 1rem;
  .card-title { font-size: 1.25rem; }
  p { line-height: 1.6; }
}

Section 2: The & Symbol: Referring to the Parent

The ampersand, written as &, is the nesting selector: inside a nested rule, it stands for the parent selector, so you can build compound, pseudo-class, and modifier selectors that refer back to the parent element itself. Without &, a nested rule always creates a descendant relationship, because the nested selector is combined with the parent as a descendant. With &, you can say something different: this nested rule applies to the parent itself, when it is hovered, when it carries a modifier class, or when it matches another selector. That distinction is the key to using nesting well.

A common use is a hover state for a component. Inside a card rule, writing &:hover creates a rule for a hovered card, which expands to .card:hover in flat form. Writing :hover without & inside the same block would instead create a rule for a hovered descendant of the card, which is a different element entirely and a frequent source of confusion for beginners. Learning to reach for & whenever you mean "this same element, in a different state" prevents that mistake, and it makes the intent of the nested block obvious to anyone reading it.

The & symbol can also appear in the middle or at the start of a compound selector, not only at the beginning. You can write a modifier as &.card--large to mean a card that also carries the large modifier, or you can write a contextual selector such as .theme-dark & to mean a card inside a dark theme container, where & stands for the card and the ancestor comes first. That flexibility lets you express relationships that flat CSS would require you to write as separate, top-level rules, while keeping them grouped with the component they belong to. It is a small symbol with a large expressive range.

There are limits to keep in mind. The & symbol always refers to the immediate parent rule's selector, not to the original top-level selector when nesting is several levels deep, so in deeply nested blocks & means the nearest parent, which may not be what you intended. That is another reason to keep nesting shallow: with one or two levels, & is unambiguous, but with four or five levels, tracking what & refers to becomes a puzzle. When in doubt, expand the nested block mentally into flat selectors and check that & expands to the selector you meant.

Practise & with a few deliberate examples — a hover state, a modifier class, and a contextual ancestor — and the symbol will quickly feel natural. It is the tool that turns nesting from a simple grouping device into a full way of writing component styles, because it lets you describe states, variants, and contexts without leaving the component's block. Used with restraint, & keeps component code together without making its selectors longer than they need to be.

.card {
  padding: 1rem;
  &:hover { box-shadow: 0 4px 16px rgb(0 0 0 / 0.15); }
  &.card--large { padding: 2rem; }
}

Section 3: Nesting Selectors Inside Rules

Nesting a selector inside a rule creates a descendant relationship by default, which means the nested rule applies to elements matching the nested selector that are descendants of the parent element. That default is intuitive for component parts: a title nested inside a card rule applies to titles inside cards, and a link nested inside a navigation rule applies to links inside navigation. The browser expands the nested rule by combining the parent selector with the nested selector, separated by a descendant combinator, so the result is exactly the flat descendant selector you would have written by hand.

That default also means you should choose nested selectors that are clear on their own, because the expanded form will include the parent. A nested class such as .card-title is clear both inside the block and when expanded, because the full selector reads as a card containing a card title. A nested generic element such as p is less clear when expanded, because it reads as any paragraph inside a card, which may be broader than intended if the card contains paragraphs in nested components too. Prefer distinctive class names for nested parts, and reserve generic element selectors for cases where you genuinely mean every matching descendant.

Nesting also affects how you think about specificity, because the expanded selector's specificity is the sum of its parts. A class nested inside a class has the specificity of two classes, which is higher than either class alone, and that higher weight can make the nested rule harder to override than a flat single-class rule would be. That is not necessarily a problem — component parts often should be a little more specific than base styles — but it is a cost to be aware of. If a nested part needs to be easily overridden by a utility or a variant, consider whether it should be nested at all, or whether a flat single-class rule in the right layer would serve better.

A useful habit is to read a nested block aloud as a set of flat rules before you finish writing it, checking that each expanded selector matches the elements you intend and no others. That mental expansion takes only a moment, and it catches the two most common nesting errors: a nested rule that is broader than intended because it matches nested components, and a nested rule that is narrower than intended because it requires a descendant relationship that the markup does not have. Both errors are easier to fix at writing time than after the page is built.

Finally, remember that nesting is a writing convenience, not a requirement, and that mixing nested and flat rules in the same stylesheet is perfectly acceptable. A component whose parts are tightly coupled may benefit from nesting, while a utility or a base style may be clearer flat. The goal is a stylesheet where each rule's form matches its purpose, not a stylesheet where every rule is nested because nesting is available. Choose nesting where grouping helps, and flat rules where simplicity helps.

.nav {
  display: flex;
  a { color: #0b5fff; text-decoration: none; }
  a:hover { text-decoration: underline; }
}

Section 4: Nesting Pseudo-Classes with &

Pseudo-classes such as hover, focus, and active describe states of an element, and nesting them with & is the cleanest way to write state styles inside a component block. Inside a button rule, &:hover means the button itself when hovered, &:focus-visible means the button itself when it receives keyboard focus, and &:active means the button itself while being pressed. Each expands to a flat selector that combines the component class with the pseudo-class, which is exactly the selector you would write by hand, but grouped with the component's other styles so the state logic stays in one place.

The alternative — writing :hover without & — is a trap that catches many beginners, because it looks like a state style but actually targets hovered descendants. Inside a card rule, :hover alone expands to a descendant selector for hovered elements inside the card, which is rarely what the author meant, and the resulting style may appear to do nothing, or to affect inner elements strangely, when the card itself is hovered. The fix is always the same: add & before the pseudo-class when you mean the parent element's state. Making that check automatic — "does this pseudo-class describe the parent or a child?" — prevents a whole class of nesting bugs.

Nesting pseudo-classes also helps you keep related states together and in a sensible order. A button block can list its base style, then its hover, focus, active, and disabled states in that order, which mirrors the order in which a reader encounters them and makes it easy to check that all states are covered. That grouping is especially valuable for accessibility, because focus styles are less likely to be forgotten when they sit beside hover styles in the same block, rather than in a separate section of the file. A component block that shows all its states at once is easier to review for completeness.

Be careful not to nest pseudo-classes that describe children when you mean the parent, and vice versa. A rule such as &:has(:focus) inside a form group describes the group itself when it contains a focused element, which is a parent-state pattern, while :focus inside the same block would describe a focused descendant. Both are valid, but they mean different things, and choosing the wrong one produces a style that applies to the wrong element. Reading the nested selector aloud — "the group, when it has focus inside it" versus "a focused element inside the group" — usually reveals which form you need.

When state styles grow complex, with multiple pseudo-classes combined, nesting still helps, because the combinations stay inside the component block where their context is clear. A rule such as &:hover:focus-visible, or &:not(:disabled):hover, reads as a refinement of the component's state, rather than as an isolated top-level rule whose component must be inferred from its selector. Keep those combinations as simple as the design allows, and test each state with keyboard and mouse, because a state style that is only tested with a mouse may hide a focus problem.

.btn {
  padding: 0.5rem 1rem;
  &:hover { background: #0842a0; }
  &:focus-visible { outline: 3px solid #0b5fff; }
}

Section 5: Nesting Pseudo-Elements

Pseudo-elements such as before and after create virtual elements that are children of the target element, and nesting them with & is the natural way to define decorative or supplementary content for a component. Inside a card rule, &::before means the before pseudo-element of the card itself, which expands to .card::before in flat form. That pseudo-element can hold a decorative bar, an icon, or a background layer, without adding extra markup to the document, and grouping it with the card's other styles keeps the decoration visibly tied to the component it decorates.

The same & rule that applies to pseudo-classes applies here, and the same trap awaits if you forget it. Writing ::before without & inside a nested block would create a rule for before pseudo-elements of descendants, not for the component's own before pseudo-element, which is almost never intended and can produce confusing results. The habit to build is consistent: whenever a nested selector is meant to describe the parent element itself — whether as a pseudo-class, a pseudo-element, or a modifier class — it begins with &. That consistency makes nested code easier to scan, because the presence or absence of & immediately signals whether the rule is about the parent or about a descendant.

Pseudo-elements require a content property to render, and that requirement is easy to forget when the pseudo-element is buried inside a nested block. A ::before rule without content will simply not appear, and the author may blame nesting or the cascade when the real cause is a missing declaration. Always include content, even if it is an empty string for a purely decorative shape, and set display and sizing properties explicitly, because pseudo-elements default to inline behaviour that may not match the intended layout. Those details are the same in nested and flat CSS, but they are worth restating because nested blocks can hide them from a quick scan.

Nesting pseudo-elements also helps with state combinations, such as a card whose before element changes on hover, which can be written as &:hover::before inside the card block, or as &::before with a nested &:hover inside it, depending on readability. Both forms expand to the same flat selector, so choose the form that reads most clearly for that component. For simple decorations, a single nested pseudo-element rule is enough; for decorations that change across states, grouping the state variations near the pseudo-element definition keeps the logic together.

Finally, use pseudo-elements for decoration and enhancement, not for essential content, because content in a pseudo-element is not part of the document structure in the same way as real markup, and it may not be available to assistive technologies. A decorative line, an icon that duplicates a visible label, or a background shape are good uses; a paragraph of essential text is not. Nesting does not change that guidance, but grouping pseudo-element styles with their component makes it easier to review whether each pseudo-element is truly decorative.

.card {
  position: relative;
  &::before {
    content: ""; display: block; height: 4px; background: #0b5fff;
  }
}

Section 6: Descendant Nesting Without &

Descendant nesting without & is the default form of nesting, and it is the right choice when the nested rule genuinely describes a descendant of the parent element, rather than the parent itself in a different state. A title inside a card, a link inside navigation, a paragraph inside an article — all of these are descendants, and writing them without & expresses that relationship directly. The nested selector is combined with the parent selector using a descendant combinator, so the expanded rule matches any matching descendant at any depth, not just direct children, which is important to remember when components nest inside each other.

The depth question is the main caution with descendant nesting. Because the combinator matches at any depth, a nested paragraph rule inside a card will also match paragraphs inside a nested card, a callout, or any other component placed inside the card, unless a scope limit or a more specific rule intervenes. That breadth is sometimes desired — an article's paragraph style should apply throughout the article — but often it is leakage, where a component's internal paragraph style unintentionally styles a nested component's paragraphs. Choosing distinctive class names for nested parts reduces that risk, because a class such as .card-text is less likely to appear in a nested component than a generic p element.

Child combinators offer a middle path when you want nesting but need to limit depth. Inside a nested block, you can write > .card-title to mean a direct child title, which expands to a selector that requires the title to be a direct child of the card. That restriction is useful for components whose immediate children have specific roles, such as a list whose direct items are styled differently from nested lists. Use the child combinator deliberately, not by default, because requiring direct parentage makes the style fragile if markup changes to add a wrapper element, which is a common refactoring that should not break styling.

A good test for descendant nesting is to ask whether the nested element's meaning depends on its parent. A card title means something because it is inside a card; a generic paragraph does not necessarily mean something different inside a card than outside it, unless the card genuinely restyles all its text. If the meaning does not depend on the parent, a flat rule or a standalone class may be clearer than a nested descendant rule. Nesting should reflect a real relationship, not merely a convenient grouping, because the expanded selector will enforce that relationship whether you intended it or not.

When descendant nesting is the right choice, it makes component code remarkably readable, because the block mirrors the component's structure without repeating the parent selector on every line. That readability is the reward for choosing nesting carefully. When it is the wrong choice, the same block hides a broad selector behind a tidy indentation, and the breadth only becomes visible when a nested component looks wrong. Reading nested blocks as their expanded flat selectors, at least during review, keeps that hidden breadth visible.

.article {
  line-height: 1.7;
  p { margin-bottom: 1rem; }
  > h2 { margin-top: 2rem; }
}

Section 7: Compound Selectors and Nesting

Compound selectors combine multiple simple selectors that must all match the same element, such as an element with a particular class, or a class with a pseudo-class, and nesting with & makes compound selectors easy to write inside a component block. Inside a button rule, &.btn--primary means a button that also carries the primary modifier, and &:disabled means a button that is disabled, while &input would be invalid because an element cannot be both a button class and an input element in the way that combination suggests. Understanding what can be compounded — classes, attributes, pseudo-classes, and pseudo-elements on the same element — helps you write nested compounds that actually match.

Modifiers are the most common compound use in nested code. A card block can contain &.card--large for a larger variant, &.card--dark for a dark variant, and &.card--featured for a featured variant, each expanding to a flat selector with two classes. Those modifiers are clear because they name the variant on the element itself, and they are easy to override because they have the specificity of two classes, which is higher than the base card but still modest. Avoid stacking too many modifiers in one compound, because a selector with four classes is harder to override and harder to read than two separate modifier rules that each handle one aspect.

Nesting also allows compound selectors where & appears not at the start, but in a position that expresses context. For example, .theme-dark & inside a card block means a card inside a dark theme container, which expands to a descendant selector with the theme ancestor first and the card second. That form is useful for theme variants that should not require a modifier class on every component, because the theme container provides the context. It also reads naturally inside the component block: "when this component is inside a dark theme, adjust like this." Use that form sparingly, because it creates a dependency on an ancestor that may not be obvious from the component's markup alone.

A common error is to compound selectors that cannot match the same element, such as a class and an element type that do not correspond, or two ids, or a pseudo-element compounded with a descendant. Those selectors will simply never match, and the style will appear to do nothing, which can look like a nesting bug when it is really a selector logic error. Expanding the nested compound into its flat form and asking "can one element satisfy all these conditions at once?" usually reveals the mistake. That question is a useful review habit for any compound selector, nested or flat.

Compound nesting shines when it keeps variant logic with the component, because a reader can see all the ways a component can appear — base, large, dark, disabled, hovered — in one block, rather than scattered across a file. That completeness aids review and maintenance, as long as the compounds stay short and each one names a real variant. When a compound grows long or combines unrelated conditions, split it into separate rules or reconsider whether the variant belongs in a different layer or as a separate component.

.btn {
  padding: 0.5rem 1rem;
  &.btn--primary { background: #0b5fff; color: #fff; }
  &:disabled { opacity: 0.5; }
}

Section 8: Nesting Media Queries Inside Rules

Nesting a media query inside a rule lets you write responsive adjustments for that component right beside its base styles, instead of collecting all responsive rules in a separate section at the end of the stylesheet. Inside a card rule, an @media block that changes padding or layout at a certain viewport width applies only to that card, and the reader does not need to jump to another part of the file to see how the card responds. That locality is the main benefit of nested media queries: the component's responsive behaviour is visible in the same block as its default behaviour.

The syntax is straightforward: inside the parent rule, you write @media followed by its condition, then a block of declarations that apply to the parent element itself when the condition is true. You do not need to repeat the parent selector inside the media block, because the declarations are already inside the parent rule's context, and the browser understands them as applying to the parent. You can also nest selectors inside the media block, for example to adjust a card title's size at a breakpoint, and those nested selectors will expand relative to the parent, just as they would outside the media query.

Nested media queries do not change cascade behaviour: a declaration inside a nested media query has the same layer, specificity, and order position as if it were written flat, except that it only applies when the media condition is true. That means a nested media rule can still lose to a later rule in a higher layer, or to a more specific rule, even when its condition is met. If a responsive adjustment mysteriously fails, check its layer and specificity, not just its breakpoint, because the media query only gates applicability; it does not grant priority. That distinction is easy to forget when the breakpoint feels like the deciding factor.

Organising responsive code with nested media queries works best when each component has a small number of breakpoints that are meaningful for that component, rather than a global set of breakpoints applied uniformly. A card might need one adjustment at a narrow width, while navigation might need several, and nesting lets each component declare its own breakpoints without forcing a shared structure. For components that share a breakpoint system, documenting the breakpoints in variables or comments helps keep them consistent, even though each component's media query is written locally.

Be careful not to fragment responsive logic so much that a page-level responsive change becomes hard to make. If a layout change requires adjusting many components at the same breakpoint, a separate responsive section or a container query approach may be clearer than hunting through nested media blocks. Nested media queries are ideal for component-local responsiveness; they are less ideal for coordinated, page-wide responsive redesigns. Choose the organisation that matches the scope of the change, and document breakpoints so they can be found.

.card {
  padding: 1rem;
  @media (min-width: 40rem) {
    padding: 2rem;
    .card-title { font-size: 1.5rem; }
  }
}

Section 9: Nesting Supports Queries

Nesting a supports query, written with @supports, inside a rule works like nesting a media query: it lets you write an enhancement for that component right beside its fallback, gated by whether the browser supports a particular feature. Inside a card rule, an @supports block that applies grid layout when grid is supported, with a block or flex fallback outside the query, keeps the fallback and the enhancement together, so a reader can see both versions without searching the file. That locality makes progressive enhancement easier to review, because the two versions of the same component are adjacent.

The pattern mirrors the media query pattern: write the fallback declarations first, in the parent rule itself, then write the @supports block with the enhanced declarations for the same element. When the browser supports the feature, the enhanced declarations apply and, being later at equal specificity, they win over the fallback. When the browser does not support the feature, the @supports block is ignored and the fallback remains, so the component still works, albeit more simply. That fallback-first order is essential; reversing it would let the fallback win even in supporting browsers, defeating the enhancement.

You can also nest selectors inside a supports block, just as with media queries, to enhance a component part only when a feature is available. For example, a card title might use a modern sizing function only when it is supported, while keeping a simpler size as fallback. Those nested enhancements expand relative to the parent, and they participate in the cascade normally when their condition is true. As with media queries, the supports condition gates applicability only; it does not grant extra priority, so layer and specificity still decide contests between the enhancement and other rules.

Supports queries are especially useful for adopting newer CSS features gradually, such as nesting itself, container queries, or scope, in a codebase that must still work in older browsers. A component can offer a modern layout when available and a simpler layout otherwise, without requiring a build step or a separate stylesheet for older browsers. That graceful degradation is a practical benefit, but it requires that the fallback be genuinely usable, not a broken placeholder that only works in the author's imagination. Test the fallback by disabling the feature or by testing in a browser that lacks it, where possible.

Document the features you gate with supports queries, because a future maintainer may not realise that a particular block is conditional, and may edit the fallback without updating the enhancement, or vice versa. A comment naming the feature and why it is gated helps, as does keeping the fallback and enhancement close together, which nested supports queries already do. When a feature becomes universally supported for your audience, you can remove the query and keep only the enhancement, simplifying the component in a single, reviewable step.

.card {
  display: block;
  @supports (display: grid) {
    display: grid; gap: 1rem;
  }
}

Section 10: Nesting Container Queries

Nesting a container query inside a rule combines two modern features — nesting and container queries — to let a component adapt to its container's size while keeping that adaptation grouped with the component's other styles. Inside a card rule, a @container block that changes the card's layout when its container is wide enough applies to the card itself, and the reader can see the container-based adaptation beside the card's base styles, without jumping to a separate responsive section. That grouping is particularly valuable for reusable components, because their container-based behaviour is part of their definition, not an afterthought.

The container query pattern requires that some ancestor be established as a container, using container-type, and that the query condition refer to that container's size. Inside a nested rule, you write @container followed by its condition, then declarations for the parent element, just as with media and supports queries. When the container meets the condition, those declarations apply; when it does not, they are ignored and the base styles remain. As with other conditional rules, the container condition gates applicability only, and layer, specificity, and order still decide contests when the condition is true.

A common design is a card that stacks vertically in a narrow container and switches to a horizontal layout in a wider container, with the container query nested inside the card rule so the two layouts are adjacent in the code. That adjacency makes it easy to compare the layouts and to check that both are complete, including spacing, alignment, and title sizing, rather than discovering that the wide layout forgot a detail that the narrow layout handled. It also makes the component portable: wherever the card is placed, it adapts to its container, without needing viewport breakpoints that may not match the card's actual width on that page.

Be careful about container query loops, where a container query changes the size of its own container in a way that toggles the query on and off repeatedly. That risk exists whether the query is nested or flat, but nesting can hide it, because the query sits inside the component block and the container relationship is less visible. Name the container explicitly where possible, and test the component at container widths near the breakpoint, watching for flicker or unstable layout. Avoid container queries that change the container's own size, and prefer queries that change the component's internal layout, which is the safer pattern.

Container queries nested inside component rules also interact with scope and layers in the usual way: the nested container rule's layer is the layer of the surrounding rule, and its specificity is that of the expanded selector. Keep those factors consistent with the component's other rules, so a container adaptation does not lose unexpectedly to a theme or utility rule. When it does lose, trace the cascade as you would for any other rule, rather than assuming the container condition is at fault, because the condition and the cascade are separate mechanisms that both must succeed for the style to appear.

.card {
  container-type: inline-size;
  @container (min-width: 30rem) {
    display: grid; grid-template-columns: 1fr 2fr;
  }
}

Section 11: Nesting and Custom Properties

Custom properties work naturally inside nested rules, because a variable defined on a parent element is inherited by descendants, and a nested rule can both define and consume variables in the same block. Inside a card rule, you can define a local variable for the card's accent colour, and then use that variable in nested rules for the card's title, button, or border, so the whole component shares a consistent accent without repeating a colour value.

Nested rules can also redefine a variable for a subtree, which is useful for variants. A dark card variant, written as &.card--dark inside the card block, can redefine the card's background and text variables, and all nested parts that consume those variables will automatically adapt, without needing their own dark-mode rules. That pattern keeps variant logic in one place — the variant redefines the tokens, and the parts follow — rather than scattering dark-mode overrides across every part. It is the same principle as theming at page level, applied at component level, and nesting makes the relationship visible because the variant and its parts share a block.

There is a subtlety worth learning: a variable's value is resolved at the point of use, after cascade and inheritance have run for the element that uses it, not at the point where the rule that uses it is written. That means a nested title rule that uses a variable will get the variable's value as defined on the title element itself, which may have been redefined by a variant on the card, by a theme on an ancestor, or by the title's own rule. Tracing a wrong colour therefore requires checking the variable's computed value on the element, not just the rule that consumes it, and browser tools show that computed value alongside other properties. That habit applies to nested and flat CSS alike, but nesting can hide the chain because the variable definition and its use may be several levels apart in the same block.

Avoid defining too many local variables inside a nested block, because a block with a dozen variables becomes harder to follow than a block with a few well-named tokens. Reserve local variables for values that genuinely vary by component or variant, such as accent, spacing, or radius, and use global tokens for site-wide values that do not change per component. A nested block that defines a variable, uses it in three places, and redefines it in one variant is a model of clarity; a block that defines a variable for every property, including ones that never change, is just indirection without benefit.

Finally, remember that custom properties participate in the cascade like any other property, so a variable defined in a nested rule still competes with variables defined elsewhere on the same element, by layer, specificity, and order. A utility that redefines a variable in a later layer will beat a component's variable definition, which is often the intended behaviour for a local override, but it can surprise authors who think of variables as exempt from the cascade. They are not exempt; they are ordinary properties with an inheritance superpower, and nesting does not change that. Treat variable definitions with the same cascade care as any other declaration.

.card {
  --accent: #0b5fff;
  border-top: 4px solid var(--accent);
  .card-title { color: var(--accent); }
  &.card--dark { --accent: #7fb0ff; }
}

Section 12: Nesting Depth: How Deep Is Too Deep?

Nesting depth is the number of levels a nested rule sits inside other rules, and it is the single most important discipline in nested CSS, because depth directly determines the length and specificity of the expanded selector. One level of nesting — a part inside a component — expands to a selector with two parts, which is usually fine. Two levels — a part inside a part inside a component — expands to three parts, which is already getting heavy. Three or more levels expand to four or more parts, which are brittle, hard to override, and often mirror the document tree too faithfully, so that a small markup change breaks the style. Depth is therefore a cost, not just a formatting choice.

A practical limit that many teams adopt is two levels of nesting, with three levels allowed only for a clear reason that is documented in a comment. That limit is not a rule of the language; it is a team agreement that keeps expanded selectors short and overrides cheap. When you find yourself nesting a third level, pause and ask whether the deeply nested element could carry its own class and be styled flat, or as a single-level nested rule inside the component, rather than as a descendant of a descendant. In most cases the answer is yes, and the flatter version is clearer, because it names the element directly instead of describing its ancestry.

Deep nesting also harms readability, even when the selectors still work. A block nested four levels deep forces a reader to track four levels of context to understand a single declaration, and the indentation alone pushes the code far to the right, making it hard to scan. A flat rule with a clear class name, by contrast, can be understood on its own, without holding the whole ancestor chain in mind. Readability is not a luxury in a stylesheet that will be maintained by a team; it is the difference between a change that takes minutes and a change that takes an hour of tracing ancestors.

There are legitimate cases for deeper nesting, such as a complex component with a distinct sub-component that only ever appears inside its parent, where the nesting genuinely reflects a containment relationship that will not change. Even then, consider whether scope or a distinctive class would express the relationship more robustly, because a class survives markup restructuring while a deep descendant chain does not. If you do nest deeply for a genuine reason, add a comment explaining why the depth is necessary, so a future simplifier does not flatten a structure that was deliberate.

A useful review question for any nested block is: "What is the expanded selector, and would I write that selector flat?" If the expanded selector looks unreasonably long or specific when written flat, the nesting is too deep, regardless of how tidy the indented block looks. That question turns an aesthetic judgement into a concrete test, and it keeps nesting honest. The goal is not to avoid nesting, but to nest only as deeply as the resulting flat selector would still be reasonable to write by hand.

/* Two levels is usually plenty; deeper needs a reason. */
.card {
  .card-body {
    p { line-height: 1.6; }
  }

Section 13: Nesting and Specificity

Nesting affects specificity because the expanded selector's specificity is the sum of all its parts, including the parent selector and every nested level. A single class nested inside another class has the specificity of two classes, a class nested inside a class inside a class has three, and so on. That accumulation is automatic and invisible in the indented code, which is why nested code can develop specificity problems without any author deliberately writing a long selector. The indentation hides the weight, but the browser counts it all the same, and an override that would have beaten a flat single class may lose to the nested version.

That accumulation matters most when a nested component part needs to be overridden by a utility, a variant, or a theme. A utility in the last layer will still win, because layers are checked before specificity, but a variant in the same layer as the nested rule will need to match or exceed the nested rule's weight, which may require a longer selector than the variant author expected. A theme rule with a single class may lose to a nested component rule with two classes, even though the theme was intended to win. Those surprises are not bugs in nesting; they are the predictable consequence of combining nesting with the cascade, and they must be planned for.

There are several ways to keep nested specificity under control. The simplest is to keep nesting shallow, so expanded selectors stay at one or two classes. Another is to use :where() for the parent or for grouping, since :where() contributes zero specificity and can neutralise the parent's weight where a low-specificity nested rule is desired. A third is to place nested component rules and their overrides in different layers, so layer order, not specificity, decides the contest. Each technique has a place, and the right choice depends on whether the nested rule is meant to be a strong component default or a weak base that should yield easily.

A practical habit is to check the expanded specificity of nested rules during review, especially for rules that are meant to be overridden. Browser tools show the selector as expanded, and reading it there reveals the true weight in a way the indented source does not. If a nested rule's expanded specificity is higher than its purpose warrants, flatten it, shorten it with :where(), or move the override to a higher layer. That check takes a moment and prevents the slow accumulation of specificity that turns a nested stylesheet into a specificity war in disguise.

Finally, remember that nesting does not create a new specificity mechanism; it only provides a compact syntax for selectors you could have written flat. Any specificity advice that applies to flat CSS applies equally to nested CSS, once you expand the selectors. That equivalence is liberating, because it means you do not need a separate mental model for nested specificity — you only need the discipline to expand nested code mentally, or in browser tools, before you predict a winner. Short nesting plus layer awareness gives you that discipline with minimal effort.

/* Nested: two classes of specificity, not one. */
.card {
  .card-title { font-size: 1.25rem; }
}

Section 14: Nesting Versus Flat CSS

Choosing between nesting and flat CSS is a matter of matching the code's form to the relationship it describes, not a matter of loyalty to one style. Nesting excels when a set of rules forms a coherent component, with parts, states, and variants that are most easily understood together. A card with a title, text, button, hover state, and large variant reads beautifully as a single nested block, because the block tells the component's whole story in one place. Flat CSS excels when rules are independent, reusable, or meant to be easily overridden, because a flat single-class rule can be understood and changed on its own, without tracking parent context.

Flat CSS also has advantages for searching and tooling. A flat selector can be found with a simple text search for its full form, while a nested rule's full selector only exists after expansion, so searching for the expanded form will not find it in the source. That matters when you are debugging or refactoring, because you may need to find every rule that affects an element, and nested rules hide their full selectors behind indentation. Some tools expand nesting for search, but not all do, and a team that relies heavily on nesting should be aware of that tooling gap and compensate with clear naming and good organisation.

Performance and file size differences between nesting and flat CSS are negligible in practice, because the browser expands nested rules internally to the same selectors it would have parsed flat, and the source file size difference is small compared with the overall stylesheet. Do not choose nesting or flat CSS for performance reasons; choose based on readability, maintainability, and the team's familiarity. A stylesheet that mixes both forms, using each where it fits, will usually outperform a stylesheet that forces every rule into one form, because the mixed stylesheet can be clear in more situations.

A good team approach is to agree on when nesting is preferred and when flat is preferred, and to document that agreement with examples. For instance, a team might agree that component parts and states are nested, while utilities, base styles, and cross-component overrides are flat. That agreement gives reviewers a standard to check against, and it prevents the stylesheet from drifting into a mixture without reason. The agreement should also cover depth limits and & usage, because those are the details where nested code most often becomes confusing.

Ultimately, nesting and flat CSS are two syntaxes for the same language, and a skilled author moves between them as the situation requires. The test for either form is the same: can a new reader understand what the rule matches, can they predict its cascade behaviour, and can they override it when needed without escalation? If the answer is yes, the form is right, whether it is nested or flat. If the answer is no, changing the form — flattening a deep nest, or grouping a scattered component — is often the fix.

/* Flat is clearer for independent, reusable rules. */
.text-center { text-align: center; }
.m-0 { margin: 0; }

Section 15: Nesting in Component Styles

Component styles are the natural home for nesting, because a component is a bundle of related parts, states, and variants that are easier to understand when they are grouped together. A well-written nested component block reads like a specification: here is the component's layout, here are its parts, here is how it looks when hovered or focused, and here are its variants. That completeness helps a new team member understand the component in one reading, without hunting through a file for scattered rules that happen to share a prefix. It also helps reviewers check that all states and variants are present, because gaps are visible as missing nested rules.

The key to good component nesting is to nest parts that are truly part of the component, and to keep the component's public interface — its base class and its modifier classes — flat and clear. Parts such as a card's title, body, and footer are internal to the card, so nesting them inside the card block is appropriate. Elements that are reused across components, such as a generic button or a generic icon, should not be nested inside one component, because that would tie them to that component's context and make them harder to reuse elsewhere. A button inside a card should use the shared button class, not a card-specific nested button rule, unless the card genuinely needs a distinct button style.

State styles belong inside the component block, using & for parent states, because states are properties of the component itself. Hover, focus, active, and disabled states, written as nested & rules, keep the component's interactive behaviour visible alongside its static appearance. Variant styles also belong inside the block, as nested modifier compounds, because a variant is a version of the same component, not a separate component. That grouping means a change to the component's base style can be checked against all its states and variants in one place, rather than across a file.

Layout inside a component also benefits from nesting, as long as the layout rules are about the component's internal arrangement, not about page layout. A card's internal grid, a navigation's flex arrangement, or a form group's spacing are internal layout concerns that belong inside the component block. Page layout — how cards are arranged in a grid, or how navigation sits beside content — belongs outside the component, in layout rules that treat components as units. Keeping that boundary clear prevents component blocks from becoming page-layout blocks in disguise, which would make the component harder to reuse on a different page.

A component block that follows these guidelines will be moderately sized, with one or two levels of nesting, clear part names, and visible states and variants. It will not be the longest block in the file, because a component that tries to contain everything becomes unwieldy. When a component block grows too large, that is a signal to split it: extract a sub-component, move page layout out, or flatten a part that has become reusable. Nesting should make components easier to understand, not larger for its own sake.

.card {
  padding: 1rem; border: 1px solid #ddd;
  .card-title { font-size: 1.25rem; margin-bottom: 0.5rem; }
  .card-footer { margin-top: 1rem; }
  &:hover { border-color: #0b5fff; }
}

Section 16: Nesting Layout Rules

Layout rules inside a nested component block describe how that component arranges its own children, which is a different concern from page layout, and nesting helps keep that internal layout visible with the component it belongs to. A card that uses grid to arrange an image beside text, a navigation bar that uses flex to space its links, or a form group that stacks a label above an input — all of these are internal layouts that make sense grouped with the component. Writing them nested means a reader who opens the component block sees its layout immediately, rather than finding it in a separate layout section.

The distinction between internal and page layout is worth maintaining, because conflating them makes components less reusable. A card's internal grid is a property of the card, wherever it appears, so it belongs inside the card block. The grid that arranges cards on a page is a property of the page, not of any single card, so it belongs in a layout rule outside the card block, where it can arrange cards without changing what a card is. If page layout creeps into a component block, the component becomes tied to one page's arrangement and cannot be reused elsewhere without carrying that page's layout with it.

Nested layout rules also interact with responsive behaviour in a useful way. A component's internal layout can change with a nested media or container query, so the component adapts to its own width or to the viewport, while its page layout is handled separately. That separation of concerns — internal adaptation inside the component, external arrangement outside it — mirrors the separation between a component and its context in other parts of design, and it makes both kinds of layout easier to reason about. When a layout bug appears, you can ask first whether it is internal or external, and look in the corresponding place.

Be careful with layout properties that have side effects on descendants, such as display, flex direction, or grid template, when they are nested deeply, because a layout rule that applies to a nested part may also affect that part's children in unexpected ways. For example, setting display flex on a nested container changes how its children are laid out, which is intended, but it also changes the container's own behaviour as a flex item in its parent, which may not be intended. Testing layout changes with real content, including long text and varied child counts, reveals those side effects before they reach readers.

Finally, keep nested layout rules as simple as the component allows, preferring a small number of well-chosen properties over a complex grid or flex setup that only works for one exact content shape. A card layout that works for short and long titles, with and without images, is more robust than one tuned to a single example. Nesting does not make layout simpler by itself; it only groups layout rules with their component. Simplicity still comes from choosing the right layout model and testing it against varied content.

.card {
  display: grid; gap: 1rem;
  .card-media { width: 100%; }
  .card-body { display: flex; flex-direction: column; gap: 0.5rem; }
}

Section 17: Nesting State Styles: hover, focus, active

State styles describe how a component looks and behaves in different interaction states, and nesting them inside the component block keeps the full interaction story in one place. A button block that lists its base style, then &:hover, &:focus-visible, &:active, and &:disabled in order, tells a reader everything about how that button responds to a user, without requiring them to search the file for scattered state rules. That completeness is especially valuable for accessibility review, because a missing focus style is immediately visible as a gap in the block, rather than hidden by the absence of a rule elsewhere in the file.

Order matters for state styles, because states can overlap: an element can be both hovered and focused, or both active and disabled, and the cascade decides which state's declarations win when they set the same property. The traditional order — link, visited, hover, focus, active — exists to ensure that later states win over earlier ones in the cases where that matters, and nesting does not change that logic. Inside a nested block, list states in an order that reflects their priority, with focus-visible and active generally after hover, so that a focused or pressed element does not lose its indicator to a hover style. Document the order you use, so reviewers can check it.

Disabled states deserve special attention in nested blocks, because a disabled element should not show hover or active styles that suggest it is interactive. A nested &:disabled rule that reduces opacity and changes the cursor, placed after hover and active rules, will win for disabled elements at equal specificity by source order, which is the desired behaviour. If hover is placed after disabled, a disabled button may still highlight on hover, which is confusing. Testing disabled states with a mouse and keyboard, after writing the nested block, catches that ordering error quickly, and the fix is simply to reorder the nested rules.

State styles for descendants are a different pattern from parent states, and nesting makes the distinction visible through the presence or absence of &. A card that highlights its title when the card is hovered uses &:hover with a nested title rule inside it, or a nested title rule inside an &:hover block, depending on readability, while a card that styles a hovered link inside it uses a nested link rule with &:hover inside the link's block. Both patterns are valid, but they describe different elements' states, and confusing them produces styles that apply to the wrong element. Reading the nested structure aloud — "the card, when hovered, its title" versus "a link inside the card, when hovered" — clarifies which pattern you need.

Finally, test every state you write, including combinations, because a state style that is never tested is a state style that may be broken. Hover with a mouse, focus with a keyboard, active by holding a press, and disabled by disabling the control, and check that each state is visually distinct where it should be, and that focus remains visible in all combinations. Nested state styles make that testing easier, because the states are listed together and can be checked off one by one, which is a small but real benefit of grouping them.

.btn {
  padding: 0.5rem 1rem;
  &:hover { background: #0842a0; }
  &:focus-visible { outline: 3px solid #0b5fff; outline-offset: 2px; }
  &:active { transform: translateY(1px); }
  &:disabled { opacity: 0.5; cursor: not-allowed; }
}

Section 18: Nesting Sibling and Child Combinators

Combinators describe relationships between elements — child, descendant, adjacent sibling, and general sibling — and nesting with combinators lets you express those relationships inside a component block without repeating the parent selector. A child combinator, written as > before a nested selector, means a direct child of the parent, while a descendant combinator, which is the default without &, means any descendant at any depth. Sibling combinators, written with + for an adjacent sibling or ~ for a general sibling, describe elements that follow another element at the same level, and they can be nested in ways that require careful reading, because the sibling relationship is between the nested element and its preceding sibling, not between the nested element and the parent.

Child combinators are useful when a component's immediate children have distinct roles that nested components should not share. A list component, for example, might style its direct list items differently from list items inside nested lists, and a child combinator inside the list block expresses that restriction directly. The cost is fragility: if markup changes to wrap a direct child in an extra element, the child rule stops matching, even though the visual role is unchanged. Use child combinators where the direct-child relationship is a genuine part of the component's contract, and prefer descendant or class-based selectors where the relationship is looser and should survive markup refactoring.

Sibling combinators inside nested blocks are subtler, because they describe a relationship that does not involve the parent at all, except as context. Inside a form group block, a nested rule such as label + input would describe an input that immediately follows a label, but only if that input is inside the form group, because the nesting adds the group as an ancestor. That combination — ancestor context plus sibling relationship — is powerful, but it can be hard to read, because the nested selector's meaning depends on both the parent and the preceding sibling.

Adjacent and general siblings also have different scopes that matter in nested code. An adjacent sibling rule with + matches only the immediately following sibling, while a general sibling rule with ~ matches any following sibling, which is broader and more likely to affect elements you did not intend, especially in a component with repeated parts. Prefer + when you mean the next element specifically, such as a caption following an image, and reserve ~ for cases where any following sibling should be affected, such as spacing after a heading. Testing sibling rules with varied content — including cases where the sibling is absent — reveals whether the rule is as precise as you intended.

As with other nesting patterns, the test for a combinator inside a nested block is to expand it into its flat form and ask whether the expanded selector matches exactly the elements you intend, and whether it will survive reasonable markup changes. If the expanded selector is precise and robust, the nested combinator is a good choice. If it is fragile or overly broad, a class on the target element, styled flat or as a simple nested rule, will usually be clearer and more maintainable. Combinators are precise tools, and nesting should not be used to hide their precision behind indentation.

.form-group {
  label + input { margin-top: 0.25rem; }
  > .field { margin-bottom: 1rem; }
}

Section 19: Nesting :is() and :where()

Grouping pseudo-classes :is() and :where() work inside nested rules just as they do in flat CSS, with the same specificity difference: :is() takes the specificity of its most specific argument, while :where() contributes zero specificity. Inside a nested block, that difference interacts with the parent's specificity, because the expanded selector's total weight includes both the parent and the grouped arguments. A nested :is() rule that groups a class with an element will therefore be heavier than a nested :where() rule that groups the same alternatives, and that weight difference can decide whether an override succeeds. Choosing between them inside a nested block is thus a specificity decision, not just a grouping convenience.

A common nested use for :is() is to group equivalent parts or states that should share a style, such as headings inside a card, or hover and focus states for a link inside navigation. Writing .card :is(h2, h3) as a nested :is() inside the card block groups the heading levels without repeating the card selector, and the resulting rule is easy to maintain because adding a heading level means editing one group, not several rules. The specificity cost is that the group counts as the most specific argument, so if one argument is a class, the whole group counts as a class, even for the element alternatives, which may make the rule heavier than a simple element rule would have been.

The :where() alternative is ideal for nested base styles that should yield easily to overrides. A nested :where() rule for article headings, for example, provides a default size that any single class on a heading can override, because the :where() part contributes nothing to specificity. That yielding behaviour is exactly what base styles should do, and nesting with :where() lets you write those defaults inside the component block while still keeping them weak. Without :where(), a nested base rule would have the parent's weight plus the heading's weight, making it surprisingly strong for a default.

When you group selectors inside a nested block, also consider readability: a group with many alternatives, or with alternatives of very different weights, can be hard to understand, even if it is technically correct. Keep groups short and homogeneous where possible, grouping elements with elements and classes with classes, so the specificity of the group is predictable. If a group must mix weights, add a comment noting the most specific argument, because a future reader may not realise that the group's weight comes from one alternative rather than from the group as a whole. That note prevents a well-meaning edit from accidentally changing the group's specificity.

Finally, remember that :is() is forgiving of invalid selectors in its list, while a traditional selector list is not, which makes :is() robust for complex groupings inside nested blocks where one alternative might be experimental or browser-specific. That forgiveness is a practical benefit, but it does not remove the need to test the grouped rule against its intended overrides. Expand the nested :is() or :where() rule mentally, count its specificity, and verify that the intended override still wins, before relying on the grouping in production code.

.card {
  :is(h2, h3) { margin-top: 1rem; }
  :where(p) { line-height: 1.6; }
}

Section 20: Nesting and :has()

The :has() pseudo-class lets a nested rule depend on what an element contains, which, combined with nesting, allows a component block to describe conditional styles for the component itself and for its parts. Inside a card block, &:has(img) means a card that contains an image, while a nested image rule with a :has() condition could describe an image that contains or is followed by something else, depending on the argument. That conditional power means a nested block can express "this component, when it contains X, looks like this" without needing a modifier class to be added by markup or script, which keeps the markup simpler and the style in sync with content automatically.

The most useful :has() pattern in nested code is the parent-conditional variant, where the parent's style changes based on its children. A card with an image might need different padding, a form group with an error might need a different border, or a navigation item with a submenu might need a different indicator, and each of those can be written as &:has(...) inside the component block, grouped with the component's other variants. That grouping is valuable because the conditional variant is visible alongside the ordinary variants, and a reviewer can see all the ways the component can appear, including content-dependent ways, in one place.

Specificity for :has() follows the usual rules: the argument's specificity counts, plus the outer selector's specificity, so a :has() rule can be heavier than it looks, especially when its argument contains a class. Inside a nested block, that weight adds to the parent's weight, so a nested &:has(.featured) rule may be surprisingly strong, and an override that would have beaten a simple variant may lose to it. When a :has() style mysteriously wins, expand the full selector, including the argument, and count its weight, rather than treating :has() as a weightless condition. That check resolves most :has() cascade surprises.

Dynamic behaviour is the second consideration with nested :has(). Because :has() depends on content, a style can appear or disappear when content changes — when an image loads, when an error appears, when a child is added — even though no stylesheet changed. That is often the desired behaviour, but it can cause layout shifts if the :has() rule changes layout properties, so prefer :has() for visual adjustments that do not change layout, and test with the content states that actually occur, including empty and loading states. A :has() rule that is only tested with its triggering content present may hide a broken appearance when that content is absent.

Use :has() in nested code where it replaces a fragile class-management pattern, such as adding a class to a parent whenever a child has a certain state, because the CSS version cannot drift from the markup. Avoid :has() where a simple modifier class would be clearer, especially in large lists where relational matching may cost performance, and document any :has() rule that affects layout or visibility, so content changes are reviewed against it. Nesting plus :has() is a powerful combination, but its power comes from matching content, and content changes should therefore be treated as style changes for those components.

.card {
  padding: 1rem;
  &:has(img) { padding-top: 0; }
  &:has(.badge) { border-color: #0b5fff; }
}

Section 21: Nesting in Theme Rules

Theme rules describe how a component looks under a particular theme, such as dark mode or a brand variation, and nesting theme adjustments inside the component block keeps the theme logic visible alongside the component's default appearance. Instead of writing a separate theme section that restyles every component from afar, you can nest a theme context inside each component — for example, .theme-dark & inside a card block — so the card's dark appearance sits beside its light appearance.

The cleanest theme pattern, however, still uses custom properties, with nesting providing the structure for redefining them. A card block can define its colours through variables, and a nested theme variant can redefine those variables, after which all nested parts that consume the variables adapt automatically. That approach keeps theme rules small — mostly variable redefinitions — and avoids duplicating every part rule for each theme. Nesting makes that pattern readable, because the variable redefinition sits inside the component block, clearly marked as a theme variant, rather than in a distant theme stylesheet where its connection to the component is less obvious.

There are two nesting forms for themes, and choosing between them is a design decision. The first is a modifier on the component itself, such as &.card--dark, which means the card carries a dark class and should use dark colours. The second is a contextual ancestor, such as .theme-dark & , which means the card is inside a dark-themed container and should adapt, even though the card itself carries no theme class. The modifier form is explicit and local, while the contextual form is convenient for theming whole pages or sections with a single class. Many systems use both: contextual themes for page-level switching, and modifiers for individual components that need a different theme from their surroundings.

Be careful that theme nesting does not create specificity or layer problems. A theme rule nested inside a component has the component's specificity plus the theme context, which may make it stronger than a utility or a state style that should win. Placing theme rules in a theme layer, or ensuring that state styles live in a layer above themes, keeps the priority predictable. Also test themes with real content, including forms, tables, and code, because a theme that looks fine on simple text may fail on complex components where nested parts use hard-coded colours that bypass the variable system. Searching for literal colours inside a themed component is a quick way to find those bypasses.

Finally, document the theme nesting pattern your team uses, so a new component follows the same form as existing ones. If some components use modifiers and others use contextual ancestors, without a documented reason, reviewers will struggle to predict how a new theme should be applied. A short style guide entry — with one example of each form and guidance on when to use it — turns theme nesting from a collection of individual choices into a shared system. Consistency in theme nesting is what makes a multi-theme site maintainable, because it means a theme change can be applied, reviewed, and tested in the same way for every component.

.card {
  background: var(--bg, #fff); color: var(--text, #222);
  .theme-dark & { --bg: #111; --text: #eee; }
}

Section 22: Nesting Dark Mode Rules

Dark mode rules nested inside a component block follow the same principles as theme rules generally, but they deserve separate attention because dark mode is the most common theme, and its mistakes — poor contrast, invisible focus, disappearing images — are the most visible to readers. A component block that contains its dark-mode adjustment, whether as a media query for prefers-color-scheme, as a contextual .theme-dark & rule, or as a modifier, lets a reviewer check the light and dark versions side by side, which is the best way to catch a dark-mode oversight before it reaches readers. That side-by-side visibility is nesting's main contribution to dark mode quality.

The media query form nests @media (prefers-color-scheme: dark) inside the component rule, with declarations for the component itself, or nested rules for its parts, inside the query. That form respects the reader's system preference automatically, without requiring a theme class to be toggled by script, and it keeps the dark adjustment local to the component. The class form, by contrast, requires a theme class on a container, but it allows the reader to choose a theme independently of their system setting, which many sites offer as a toggle. Some sites support both: a class form that overrides the media query form, or vice versa, with a documented priority between them so the two forms do not fight.

Whichever form you use, prefer variable redefinition over duplicating component rules for dark mode. A card that uses variables for background, text, border, and accent needs only a dark-mode block that redefines those variables, while a card that hard-codes colours needs a dark-mode rule for every part that uses a colour. The variable approach is shorter, less error-prone, and easier to audit for contrast, because the dark palette is defined in one place and can be checked as a set of foreground-background pairs. Nesting helps here because the variable redefinition sits inside the component block, making the dark palette's connection to the component explicit.

Test dark mode for every component that uses nesting, not just for the page as a whole, because a component that looks fine in light mode may have a nested part — a badge, a code snippet, a form control — that uses a hard-coded colour and stands out in dark mode. Check focus indicators against dark backgrounds, check muted text for contrast, and check images with transparent backgrounds, which can disappear or look odd on a dark background. Those checks are part of dark-mode review, and nesting makes them easier because the component's dark rules are grouped where the reviewer is already looking.

Finally, avoid forcing dark mode with important flags, because that indicates a cascade problem — usually a layer or specificity issue — that should be fixed structurally. A dark-mode rule in the correct layer, or a variable redefinition that components consume, will win cleanly without flags, and will remain easy to override with a utility where a local exception is needed. Clean dark mode, like clean theming generally, is a sign that the cascade structure is sound, and nesting, used well, supports that structure by keeping theme logic with its component.

.card {
  background: var(--bg, #fff);
  @media (prefers-color-scheme: dark) {
    --bg: #111;
  }
}

Section 23: Nesting Form Styles

Form styles benefit from nesting because a form is a collection of related parts — labels, inputs, help text, error messages, and buttons — whose styles are most easily understood when grouped by field or by form. A form group block that nests its label, input, help text, and error styles tells a reader how a single field looks in all its states, including focused, invalid, and disabled, without requiring them to assemble that picture from scattered rules. That grouping is especially valuable for forms, because a field's appearance depends on the interaction between its parts: a label's position, an input's border, and an error message's visibility are a single design, not independent choices.

Nesting form states with & is the natural way to write field behaviour. Inside an input rule, &:focus-visible can define a visible focus ring, &:invalid can define an error border, and &:disabled can define a muted appearance, each grouped with the input's base style. Inside a form group rule, &:has(:invalid) or &:has(:focus) can style the group itself when it contains an invalid or focused field, which is a pattern that previously required script to add a class to the group. Those group-level states, written as nested & rules, keep the field's logic together and ensure that the group's appearance stays in sync with its fields automatically.

Be careful with form controls' browser defaults, because inputs, selects, and buttons have their own default fonts, colours, and sizing that do not always inherit from the page. A nested form block that sets font properties only on the form element may leave inputs with a different font, because the browser default for inputs is a direct rule that beats inheritance. Setting font, colour, and line height explicitly on form controls, or using inherit on them, inside the nested block, removes that surprise and keeps forms visually consistent with surrounding text. Test forms with real inputs, including selects and textareas, because each control type reveals different defaults.

Error and help text also benefit from nesting, because their visibility often depends on the field's state. An error message nested inside a form group can be hidden by default and shown when the group contains an invalid input, using a :has() rule or a sibling combinator, grouped with the group's other styles. That logic is easier to review when it sits inside the group block, where the relationship between the error message and the field is visible, than when it sits in a separate validation section. Similarly, help text that appears on focus can be nested with the field it helps, so the help and the field are maintained together.

Finally, keep form nesting shallow and use distinctive class names for field parts, because forms often contain nested components — a search box inside a form, a date picker with its own parts — and deep descendant nesting can leak field styles into those nested components. A field's input style should not restyle a nested widget's inputs, and a scope limit or a distinctive class can prevent that leakage. Test forms with nested widgets and with varied field types, and review the expanded selectors for form rules, to ensure that a form's styles stay within the form they belong to.

.field {
  label { display: block; margin-bottom: 0.25rem; }
  input {
    padding: 0.5rem; border: 1px solid #ccc;
    &:focus-visible { outline: 3px solid #0b5fff; }
    &:invalid { border-color: #b00020; }
  }
}

Section 24: Nesting Navigation Styles

Navigation styles are a classic nesting use case, because navigation is a hierarchical structure — a bar containing a list containing items containing links, sometimes with dropdowns — and nesting mirrors that hierarchy in code. A navigation block that nests its list, items, links, and dropdowns reads like a map of the navigation itself, and a reader can follow the structure from the bar down to a single link without jumping between sections of a file.

A practical navigation block nests one level for the list and links, uses & for link states such as hover, focus, and current page, and handles dropdowns as a distinct sub-component rather than as a deeply nested continuation of the main list. A dropdown, for example, can be a nested block inside navigation that defines its own parts, but its internal structure should not be nested three levels deep inside the navigation list item, because that depth makes the dropdown hard to reuse or to restyle independently. Treating dropdowns as sub-components, with their own class and a shallow nested block, keeps navigation maintainable even as menus grow more complex.

Current-page indication is a good example of a navigation state that benefits from nesting. A link with a modifier class for the current page, written as &.current inside a nested link rule, or as a nested rule for links with that modifier, groups the current-page style with the link's other states, so a reviewer can see how a current link differs from a hovered or focused link in one place. That grouping prevents the common bug where a current-page style is forgotten or overridden by a hover style, because the states are listed together and their order can be checked. Test navigation with keyboard focus as well as mouse hover, because navigation is a primary keyboard path through a site.

Responsive navigation also benefits from nesting, because a navigation bar that collapses into a menu button on narrow screens has responsive behaviour that is specific to navigation, not to the page as a whole. Nesting a media query inside the navigation block, with adjustments to layout and to dropdown behaviour, keeps that responsive logic with the navigation it affects. That locality is valuable, but it should not hide the fact that responsive navigation often involves script for toggling the menu, and the CSS should be reviewed together with that script, to ensure that the toggled states match the CSS states.

Finally, keep navigation selectors as short as the design allows, even when nesting tempts you to describe the full hierarchy. A link class nested inside navigation has the specificity of two classes, which is manageable, but a link nested inside an item inside a list inside navigation has four, which is not. If your navigation block is producing selectors with more than two or three parts, flatten the deepest parts into classes of their own, or split a sub-component out. Navigation that is easy to restyle — for a new section, a new theme, or a mobile variant — is navigation that will survive the site's growth.

.nav {
  display: flex; gap: 1rem;
  a {
    color: #0b5fff; text-decoration: none;
    &:hover { text-decoration: underline; }
    &.current { font-weight: 700; }
  }
}

Section 25: Nesting Card Styles

Card styles are the textbook example for nesting, because a card is a self-contained component with a clear set of parts — image, title, body, footer, actions — and a small set of states and variants that are easy to list in one block. A nested card block that defines the card's layout, then its parts, then its hover and featured variants, reads as a complete description of the card, and a new team member can understand the card by reading that one block. That completeness is why cards appear in so many nesting examples, and why they are a good first component to write with nesting when you are learning the syntax.

The parts of a card should use distinctive class names, such as card-title, card-text, and card-action, rather than generic elements, because generic nested elements leak into nested components inside the card. A card that contains a nested card, a callout, or a widget should not restyle that inner component's paragraphs or headings with the outer card's paragraph rules, and distinctive classes prevent that leakage. That naming discipline is more important than nesting depth, because a shallow nest with generic elements can leak just as badly as a deep nest with distinctive classes, while a shallow nest with distinctive classes stays local.

Card variants are where nesting's grouping really pays off. A featured card, a horizontal card, and a compact card can each be written as a nested modifier compound inside the card block, with adjustments to layout, padding, or colour that are visible alongside the base card. That grouping makes it easy to compare variants and to check that each variant is complete — that a horizontal card, for example, adjusts its image sizing as well as its layout, rather than only one of those. It also makes it easy to remove a variant, because its rules are contained in one nested block, rather than scattered across a file where a removal might miss a rule.

Card states, such as hover elevation or focus indication, also belong inside the card block, using & for parent states, because a card's interactive behaviour is part of its definition. A card that is clickable as a whole, for example, needs a focus style that is visible when the card receives keyboard focus, and that focus style should be reviewed alongside the hover style, so that keyboard and mouse users get equivalent feedback. Grouping states with the card ensures that focus is not forgotten, and that hover and focus do not conflict in a way that hides the focus indicator.

Finally, cards are often used in grids and lists, and their internal styles should not depend on their page context. A card block should define the card itself, not how cards are arranged on a page, because that arrangement belongs to the page layout, not to the card. Keeping that boundary clear means a card can be reused in a sidebar, a grid, and a modal without carrying page-specific layout with it, and it means a page layout change does not require editing the card block. That reusability is the real test of a well-nested card: it looks right wherever it is placed, because its block describes the card, not its surroundings.

.card {
  border: 1px solid #ddd; border-radius: 0.5rem; overflow: hidden;
  .card-title { font-size: 1.25rem; }
  .card-text { color: #444; }
  &:hover { box-shadow: 0 4px 16px rgb(0 0 0 / 0.15); }
}

Section 26: Nesting Table and List Styles

Tables and lists are structured content with repeating parts — rows, cells, headers, items, markers — and nesting can make their styles easier to follow, as long as the nesting reflects the structure without becoming a faithful copy of every table or list level. A table block that nests its header, rows, and cells, with adjustments for striped rows or hovered rows, groups the table's appearance in one place, so a reviewer can see how headers differ from cells and how striped rows are achieved without searching a file.

Striped rows are a good example of a table pattern that benefits from nesting with pseudo-classes. Inside a table block, a nested row rule with &:nth-child(even) can define the striped background, grouped with the row's other styles, so the striping logic is visible beside the row definition. That grouping is clearer than a separate striped-rows section, and it makes it easy to check that striping does not conflict with hover or selected-row styles, because those states can be listed in the same nested block in an order that reflects their priority. Test striped tables with varied row counts, including a single row, because striping logic that assumes many rows can look odd on small tables.

Lists benefit from similar grouping, especially for nested lists, where the outer list's markers or spacing should differ from inner lists' markers. A list block that nests its items, and then nests a further list inside an item with different marker styling, describes that distinction directly, but it also risks producing a deep selector that is hard to override. A safer pattern is to give nested lists their own class, such as a sublist modifier, and to style that class as a shallow nested rule inside the list block, rather than as a descendant of a descendant of a descendant. That modifier approach keeps the nesting shallow while still distinguishing outer and inner lists.

Be careful with list markers and table borders, because those properties have their own quirks that nesting does not change. List markers are generated by the list item's marker pseudo-element, and table borders collapse or separate based on the table's border model, both of which are independent of whether the rules are nested or flat. Nesting groups those rules, but it does not simplify their underlying behaviour, and a nested table or list block should still be tested with real content, including long cell text, wrapped list items, and empty cells, to ensure that the grouped styles produce a readable result in practice.

Finally, tables and lists are often used for data that must remain accessible, so their nested styles should preserve semantic structure and readability. Do not use nesting to hide table headers, to remove list semantics, or to restyle a table as a non-table layout without considering how assistive technologies will interpret the result. A nested block that styles a table should still leave the table recognisable as a table, with headers associated with cells, and a nested block that styles a list should still leave the list recognisable as a list. Nesting is a writing tool, not a licence to break structure for appearance.

.data-table {
  border-collapse: collapse; width: 100%;
  th { text-align: left; border-bottom: 2px solid #222; }
  td { padding: 0.5rem; border-bottom: 1px solid #ddd; }
  tr:nth-child(even) td { background: #f5f5f5; }
}

Section 27: Nesting with BEM Names

BEM is a naming system that uses blocks, elements, and modifiers — for example, card, card__title, and card--large — and nesting pairs with BEM in a way that is both convenient and potentially confusing, because BEM names already encode the parent-child relationship that nesting also expresses. Inside a card block, nesting a rule for card__title feels redundant, because the name already says it belongs to the card, yet grouping it inside the card block still helps readability, because the element's styles sit beside the block's styles.

The specificity problem arises because a BEM element nested inside its block expands to a selector with two classes — the block and the element — while the BEM convention intends the element class alone to be sufficient, with a specificity of one class. That extra weight makes the nested BEM element harder to override than a flat BEM element, and it undermines one of BEM's main benefits, which is flat, predictable specificity. If you nest BEM elements inside their blocks, you should be aware that you are trading BEM's flat specificity for nesting's grouping, and you should decide deliberately whether that trade is worth it for your project.

One common compromise is to nest BEM modifiers and states inside the block, while keeping BEM elements flat, or to nest elements but use & in a way that avoids adding the block class twice. For example, a card block can contain &.card--large for a modifier, because the modifier genuinely compounds with the block, while card__title can be written flat, outside the block, with a comment linking it to the card. Another compromise is to nest elements inside the block but to accept the two-class specificity, documenting that BEM elements in this project have block-plus-element weight, so overrides are written accordingly. Either compromise can work, as long as it is consistent and documented, because inconsistency — some elements nested, some flat, without a rule — is what confuses reviewers.

A related consideration is searching and tooling: a flat BEM element can be found by searching for its full class name, while a nested BEM element's full selector only appears after expansion, so a search for the expanded form will not find it. That tooling gap matters less if your team uses tools that expand nesting, but it matters more if you rely on simple text search to find styles. Weigh that practical cost against the readability benefit of grouping, and choose the pattern that fits your team's workflow, not just the pattern that looks tidiest in an example.

Ultimately, BEM and nesting are both organisation tools, and they should be used together only where each adds value. BEM adds clear, flat naming; nesting adds grouping. If grouping is more valuable for a particular component, nest its BEM elements and accept the specificity cost, documenting it. If flat specificity is more valuable, keep BEM elements flat and use nesting only for modifiers and states. The worst outcome is to nest BEM elements without realising the specificity cost, and then to fight that cost with longer selectors later. Awareness, documented as a team decision, prevents that outcome.

.card {
  padding: 1rem;
  &.card--large { padding: 2rem; }
}
.card__title { font-size: 1.25rem; }

Section 28: Nesting and Utility Classes

Utility classes are single-purpose classes for spacing, alignment, or display, and they generally should not be nested inside component blocks, because their value lies in being independent, reusable, and reliably able to override component styles. A utility nested inside a component would only apply inside that component, which defeats its purpose as a general tool, and its expanded selector would be heavier than a flat utility, which defeats its purpose as a reliable override. Utilities belong flat, in a utilities layer, where their single-class specificity and last-layer position guarantee that they win local adjustments, regardless of which component they are applied to.

There is a narrow exception: a utility-like adjustment that is genuinely specific to one component and will never be reused elsewhere might be written as a nested modifier inside that component, rather than as a global utility. That nested modifier is not really a utility; it is a component variant with a utility-like name, and naming it as such — for example, a card-specific spacing modifier — avoids confusion about its scope. The distinction matters for maintenance: a global utility can be changed safely because its effect is understood to be general, while a component-specific modifier can be changed safely because its effect is understood to be local. Mixing the two — a global name with a local nested definition — creates a utility that behaves differently in different places, which is confusing.

Nesting can also be used to define utilities that apply within a specific context, such as spacing utilities that only make sense inside a particular layout, but that pattern should be used sparingly and documented clearly, because it breaks the expectation that a utility means the same thing everywhere. If a utility's meaning changes by context, it is no longer a utility in the usual sense, and a reader who applies it elsewhere will be surprised. Prefer a component variant or a contextual class with a distinct name for context-specific adjustments, and reserve utility names for classes whose meaning is truly global.

The interaction between nesting and utilities in the cascade is also worth noting. A nested component rule, with two classes of specificity, will beat a flat utility in the same layer, which is why utilities are usually placed in a later layer: layer order, not specificity, guarantees that utilities win. If your project does not use layers, a nested component rule may defeat a utility unexpectedly, and the fix is either to place utilities later in source order, to keep component selectors flat, or to adopt layers. Understanding that interaction prevents the common complaint that "utilities do not work" in a nested stylesheet, when the real cause is a layer or specificity mismatch.

Finally, review nested component blocks for utility-like rules that have crept in — a nested margin adjustment, a nested text alignment, a nested display change that is really a local tweak rather than a component property. Those tweaks are often better expressed as utilities applied in markup, rather than as nested rules, because they are then visible in the markup where the exception occurs, and they can be removed without editing the component. Nesting should contain the component's definition, not every local exception to it, and utilities are the right tool for those exceptions.

/* Utilities stay flat and in the last layer. */
@layer components, utilities;
@layer components { .card { margin: 1rem; } }
@layer utilities { .m-0 { margin: 0; } }

Section 29: Nesting in Large Files

Nesting in large files requires more discipline than nesting in small examples, because the benefits of grouping scale differently from the costs of depth and specificity. In a small file with a few components, a nested block for each component is easy to scan, and the file's structure mirrors the site's components. In a large file with dozens of components, nested blocks can make the file harder to navigate, because each block is longer, indentation pushes code to the right, and finding a specific rule requires expanding blocks mentally or with tooling. Large files therefore benefit from splitting by component or by layer, rather than from nesting everything into one file.

A practical structure for large projects is one file per component, or one file per layer group, with each file containing a small number of nested blocks. That structure lets a developer open the file for the component they are changing, see its nested block, and make the change without scrolling through unrelated components. It also makes code review easier, because a change to a component touches only that component's file, and reviewers can see the full nested block in context. Build tools can then combine those files in layer order, preserving the cascade while keeping the source organised by component.

Within a large file, nesting depth and block length become more important, because a long nested block can hide its own structure. A component block that runs for hundreds of lines, with multiple levels of nesting, is difficult to review and difficult to test, because its parts, states, and variants are spread across a large indented area. Splitting such a block — extracting a sub-component, flattening a part, or moving a variant to its own block — restores readability, even if it means the component's styles are no longer in a single nested block. Readability at scale matters more than the aesthetic of a single block.

Large files also amplify the tooling concerns around nesting, such as searching for expanded selectors and understanding specificity. A team working on a large nested stylesheet should invest in tools that expand nesting for search and that show expanded selectors in review, or should adopt conventions — such as distinctive class names and shallow nesting — that make simple text search effective even without expansion. Those conventions are not just style preferences; they are practical measures that keep a large codebase navigable as it grows.

Finally, large projects should document their nesting conventions in a style guide, with examples of preferred depth, & usage, and the boundary between nested and flat rules. That guide should be short and practical, with examples drawn from the project's own components, rather than abstract rules that nobody follows. A style guide that reflects the project's real components will be used, while a generic guide will be ignored, and the difference shows up in the consistency of the stylesheet over time. Nesting at scale is a team discipline, not just a syntax choice.

/* One component per file keeps large projects navigable. */
.card {
  padding: 1rem;
  .card-title { font-size: 1.25rem; }
}

Section 30: Nesting Order and the Cascade

Nesting does not create a new cascade order; nested rules participate in the cascade exactly as their expanded flat selectors would, with the same origin, layer, specificity, and source order. A nested rule in a later layer beats a nested rule in an earlier layer, a nested rule with higher specificity beats one with lower specificity in the same layer, and a nested rule later in source order beats an earlier one at equal specificity and layer. Nesting changes syntax, not priority.

Source order inside a nested block deserves attention, because the order of nested rules within a block determines their relative order when expanded, but the block's position in the file also matters. Two nested rules inside the same parent block are ordered relative to each other by their position inside the block, while a nested rule and a flat rule outside the block are ordered by the block's position in the file and by the nested rule's position within the block, as expanded.

Layer placement for nested rules is determined by the layer of the surrounding rule, or by a layer block that wraps the nested rule, not by the nesting itself. A nested block inside a components layer belongs to that layer, and its nested rules share that layer, unless a nested layer declaration changes it. That means you can place an entire component, with all its nested parts and states, into a layer by wrapping the component block in a layer block, which is a convenient way to organise layered, nested code. Conversely, a nested block outside any layer is unlayered, and will beat layered rules, just as a flat unlayered rule would, which is a mistake to watch for in nested code where the layer wrapper may be far from the nested rule itself.

Specificity, as discussed earlier, is the sum of the expanded selector's parts, so nesting order and specificity interact: a nested rule that appears later but has lower specificity will still lose to an earlier rule with higher specificity in the same layer. That interaction is the same as in flat CSS, but it can be harder to see in nested code, because the specificity is hidden behind indentation. Reviewing nested code with expanded selectors in mind — or in browser tools, where selectors are shown expanded — makes the interaction visible and prevents ordering mistakes that look correct in indented form but fail in the cascade.

A practical habit for nested cascade order is to keep nested blocks short and to place state and variant rules after base part rules inside the block, mirroring the order you would use flat. That habit ensures that, within a component, states and variants win over base parts at equal specificity by order, which is usually the intended behaviour. It also makes the block read in a logical sequence: base, parts, states, variants, responsive adjustments. When that sequence is followed consistently, nested cascade order becomes predictable, and the equivalence between nested and flat CSS becomes a practical advantage rather than a hidden trap.

.card {
  padding: 1rem;
  .card-title { font-size: 1.25rem; }
  &:hover { border-color: #0b5fff; }
}

Section 31: Debugging Nested CSS

Debugging nested CSS starts with the same systematic approach as debugging flat CSS, with one extra step: expanding the nested rules mentally, or in browser tools, into their flat forms before you reason about the cascade. A nested rule that looks simple in indented form may expand to a long, specific selector that loses or wins for reasons that are invisible until expansion. Always check the expanded form first when a nested style surprises you.

The most common nested debugging questions are: does the nested selector mean the parent or a descendant, does it require a relationship the markup does not have, and is its expanded specificity higher than you intended? The first question is answered by checking for &: a nested pseudo-class or modifier without & is a descendant, not a parent state. The second is answered by comparing the expanded selector with the actual markup, including any wrapper elements that may have been added since the rule was written. The third is answered by counting the expanded selector's classes, ids, and elements, and comparing that count with the competing rule's count in the same layer.

A nested rule that appears to do nothing often has a simple cause that expansion reveals. It may never match because it compounds selectors that cannot match the same element, because it requires a descendant relationship that does not exist, because it is inside a media, supports, or container query whose condition is false, or because it is inside a layer that loses to a competing rule. Each of those causes has a different fix — correcting the selector, flattening the rule, adjusting the condition, or moving the layer — and guessing the fix without identifying the cause often adds a second problem. Expansion plus the cascade checklist from the previous chapter gives you the cause quickly.

Also check for nesting syntax errors, because a missing bracket or a misplaced & can invalidate a whole nested block, causing several rules to disappear at once in a way that looks like a cascade failure. A validator or a careful bracket check will catch those errors, and browser tools will show the block as missing rather than as losing, which is a clue that the problem is syntax, not priority. Similarly, a nested rule inside a rule that itself never matches will never apply, no matter how correct the nested selector is, so check the parent rule's matching as well as the nested rule's. Debugging from the outside in — parent first, then nested rule — prevents wasted time on a nested selector whose parent is the real problem.

Finally, when you fix a nested bug, document the fix if it reveals a pattern — a missing &, a too-deep nest, a layer misplacement — because nested bugs tend to recur in the same forms across a codebase. A short comment, or a note in the style guide, that names the pattern helps the next developer avoid it, and it turns a single debugging session into a team improvement. Nested CSS is easier to debug than it first appears, once expansion becomes a habit, because the expanded form is just flat CSS, and flat CSS debugging skills transfer directly.

/* Expand nested rules mentally before debugging the cascade. */
.card {
  .card-title { font-size: 1.25rem; }
}

Section 32: DevTools and Nested Rules

Browser developer tools display nested rules in their expanded flat form, which is both a help and a potential source of confusion if you expect to see the nested source exactly as you wrote it. When you inspect an element styled by a nested rule, the styles panel shows the expanded selector, its source file and line number, and its cascade position, just as it would for a flat rule. That expanded view is accurate for cascade reasoning, because the browser itself works with the expanded selector, but it can be disorienting if you search the source file for the expanded selector and do not find it, because the source contains the nested form, not the expanded form. Learning to map between the two views is a key DevTools skill for nested CSS.

The line number shown in DevTools points to the nested rule's location in the source, even though the selector is shown expanded, so you can navigate from the expanded view back to the nested source by following that line number. That navigation is the bridge between the two views: the expanded selector tells you what the browser matched, and the line number tells you where you wrote it, in nested form. Use that bridge deliberately when debugging, rather than searching the file for the expanded selector, which will fail and waste time.

Experimenting in DevTools with nested rules works the same as with flat rules: you can disable a declaration, change a value, or add a new declaration to a rule, and the page updates immediately. Those experiments test hypotheses about nested rules just as they do for flat rules, with the caveat that a change made in DevTools to an expanded rule must be translated back into nested form when you edit the source. A value change translates directly, but a selector change must be expressed as a change to the nested selector, its parent, or both, depending on which part of the expanded selector you changed. Keeping that translation in mind prevents edits that look correct in DevTools but are written incorrectly in nested source.

DevTools also reveal nesting-related cascade information that is easy to miss in source, such as the layer a nested rule belongs to, whether a rule is inside a media or container query, and which competing rules were struck through and why. Reading that information for a nested rule, alongside its expanded selector, gives you the full cascade picture: layer, specificity, order, and condition, all in one place. That picture is often enough to identify the fix without further investigation, especially when the expanded selector reveals a specificity or relationship problem that the indented source hid.

Make DevTools inspection a regular part of working with nested CSS, not only a debugging step when something breaks. After writing a new nested component, inspect a few of its elements and check that the expanded selectors match your intent, that the layers are correct, and that the states and variants appear as expected. That quick check catches nesting mistakes early, while the component is still fresh in your mind, and it builds the habit of reading expanded selectors fluently, which is the foundation for confident nested CSS work.

  .card-title { font-size: 1.25rem; }
  &:hover { border-color: #0b5fff; }
}

Section 33: Nesting and Browser Support

Native CSS nesting is a modern feature, and its browser support determines whether you can use it directly or whether you need a fallback, a build step, or a progressive enhancement strategy for your audience. Support has grown rapidly since nesting was introduced, and most current browsers now support it, but older browsers will ignore nested rules or, in some cases, invalidate the entire parent rule if they do not understand nesting syntax. That failure mode matters: unlike some features that simply do nothing when unsupported, invalid nesting can remove the parent rule's styles as well, leaving a component unstyled rather than merely un-nested. Checking support for your actual audience is therefore essential before relying on nesting for critical styles.

The safest approach for a broad audience is to check your project's browser support policy and test in the oldest browser you must support, rather than assuming support from general trends. If that browser lacks nesting, you have several options: write flat CSS for critical styles and use nesting only for enhancements, use a build tool that compiles nested CSS into flat CSS for production, or use a feature query to gate nested rules behind support, with a flat fallback outside the query. Each option has trade-offs in complexity and maintenance, and the right choice depends on how central nesting is to your stylesheet and how strict your support requirements are.

A build tool that compiles nesting is a common solution in larger projects, because it lets authors write nested source while shipping flat CSS that works everywhere. That approach preserves the readability benefits of nesting during development, while removing the support risk in production, but it adds a build step that must be maintained and understood by the team. It also means that the shipped CSS differs from the source, so debugging in production requires mapping back to the nested source, which tools can help with through source maps. Weigh that complexity against the simpler alternative of writing flat CSS for the parts that must work everywhere.

Feature queries for nesting itself are another option, though they require care, because a nested rule inside a supports query still needs a fallback outside the query that provides a usable appearance when nesting is unsupported. That fallback is often the flat version of the same component, which duplicates code and creates a maintenance burden: every change to the component must be made in both the flat fallback and the nested enhancement. That duplication is acceptable for a small number of components, but it scales poorly, which is why a build tool is often preferred when nesting is used extensively.

Document your nesting support strategy in the project, so a new contributor knows whether they can write nested CSS freely, whether they must provide a flat fallback, or whether a build step handles the conversion. That documentation prevents the common situation where one developer writes nested CSS assuming a build step exists, while another developer ships the nested source directly to browsers that do not support it. Support is a team decision, not an individual preference, and it should be recorded where the team will see it when they write styles.

/* Native nesting needs current browsers; check your audience. */

Section 34: Fallbacks for Older Browsers

Fallbacks for older browsers that do not support nesting follow the same progressive enhancement pattern as other modern features: provide a usable flat version first, then enhance with nesting where it is supported, or compile nesting away with a build tool so the shipped code is flat. The flat fallback approach works best when the component is simple, because the flat version is short and easy to maintain alongside the nested version. For a card with a few parts, writing the flat rules first and then adding nested enhancements is manageable, but for a complex component with many parts and states, maintaining two versions quickly becomes error-prone, and a build tool becomes the better choice.

When you write a flat fallback by hand, keep it genuinely usable, not a placeholder. A fallback card should have its layout, typography, and colours, even if it lacks a subtle nested enhancement such as a container-query layout or a :has() variant. Readers on older browsers deserve a working, readable component, not a broken layout with a note that their browser is old. Test the fallback by disabling nesting support where possible, or by testing in an older browser, and check that the component's essential content and interactions still work. That test is the real definition of a fallback: it works, not merely that it exists.

A build tool fallback, by contrast, requires no hand-written duplicate code, because the tool generates the flat version from the nested source automatically. That automation is its main advantage, and it scales to large stylesheets where hand-written fallbacks would be impractical. Its main disadvantage is the build dependency: the team must maintain the tool, understand its output, and debug through source maps when production styles differ from source. For most professional projects, that trade-off is worthwhile, because the build tool also handles other modern features and optimisations, but for a small project without a build step, adding one solely for nesting may be disproportionate.

Another fallback strategy is to avoid nesting for critical layout and to use it only for non-critical enhancements, such as hover decorations or minor spacing adjustments, so that unsupported browsers lose only polish, not structure. That strategy lets you write nested code freely for enhancements, while keeping the core layout in flat CSS that works everywhere. It requires discipline to distinguish critical from non-critical styles, and it requires review to ensure that a nested rule does not accidentally become critical — for example, a nested layout rule that is essential to the component's readability. Documenting which parts of a component are critical helps reviewers make that distinction.

Whichever fallback strategy you choose, test it and document it, because an untested fallback is an assumption, not a safety net. Record the browsers you support, the fallback method for each modern feature you use, and how to test the fallback, so that a future change to a component is tested in both its modern and fallback forms. Fallbacks are part of the component's definition, not an afterthought, and treating them that way is what makes progressive enhancement reliable rather than aspirational.

/* Flat fallback first; nested enhancement where supported. */
.card { padding: 1rem; }
.card-title { font-size: 1.25rem; }

Section 35: Nesting and Preprocessors Compared

Preprocessors such as Sass and Less offered nesting long before browsers did, and comparing native nesting with preprocessor nesting helps you understand what has changed and what has stayed the same. The core syntax is similar: both let you write child rules inside parent rules, both support & for the parent selector, and both expand nested rules into flat selectors. That similarity means that developers with preprocessor experience will find native nesting familiar, and many nesting habits — shallow depth, clear naming, grouping by component — transfer directly from preprocessor workflows to native CSS.

The differences are in the details and in the tooling. Preprocessor nesting historically allowed more flexibility, such as nesting without & in some contexts where native nesting requires it, or nesting properties and at-rules in ways that native CSS handles differently. Native nesting has stricter parsing rules, designed to keep the language unambiguous for browsers, which means some preprocessor patterns will not work natively and must be rewritten. For example, native nesting requires that a nested rule begin with a selector, an at-rule, or &, in certain positions, while some preprocessors were more permissive. Those strictness differences are not flaws; they are the cost of moving nesting from a build-time transformation to a browser-native feature.

Another difference is that preprocessors offer features beyond nesting — variables, mixins, functions, and imports — that native CSS now covers in different ways, through custom properties, @layer, @scope, and other native features. A project migrating from a preprocessor to native CSS therefore needs to translate more than just nesting: preprocessor variables become custom properties, mixins become either repeated rules or custom property patterns, and imports become native @import with layers. That broader migration is a larger project than simply converting nested syntax, and it should be planned as such, with testing at each step.

The main advantage of native nesting over preprocessor nesting is directness: the code you write is the code the browser reads, with no compilation step to hide errors or to complicate debugging. That directness makes browser tools more accurate, because the source and the shipped code are the same, and it removes a build dependency for small projects that do not otherwise need one. The main disadvantage is support: preprocessor nesting works everywhere because it is compiled away, while native nesting requires browser support or a fallback strategy, as discussed in the previous sections. For a project with a broad audience, that support gap may still justify a preprocessor or a build tool, even though native nesting is available.

When you compare the two, focus on your project's needs rather than on novelty. If your project already uses a preprocessor for other features, its nesting may remain the practical choice, even as native nesting grows. If your project is new, small, or already uses native features for variables and layers, native nesting may be simpler and more direct. Either way, the nesting discipline — shallow depth, clear naming, grouping by component — is the same, because it is about human readability, not about which tool expands the nesting.

/* Native nesting: no build step, same grouping idea as Sass. */
.card {
  padding: 1rem;
  .card-title { font-size: 1.25rem; }
}

Section 36: Migrating Sass Nesting to Native CSS

Migrating Sass nesting to native CSS is a translation exercise that requires attention to syntax differences, because Sass nesting and native nesting are similar but not identical. Start by identifying Sass-specific patterns in your codebase: nested rules that rely on Sass's more permissive parsing, parent selector usages that native CSS handles differently, and nested properties or at-rules that have no native equivalent. Those patterns are the migration risks, and they should be listed before any code is changed, so the migration can be planned around them rather than discovering them one file at a time.

A practical migration approach is to convert one component at a time, starting with a simple component that uses only basic nesting — child rules, & for states and modifiers, and shallow depth — and verifying that the converted component renders identically in a supporting browser. That first conversion establishes the pattern and the tooling, such as whether a build step is still needed for other Sass features, and it gives the team a reference example for subsequent components. More complex components, with deep nesting, Sass variables, or mixins, can then be converted with that pattern in mind, and with extra testing for the Sass-specific features they use.

Sass variables and mixins require separate translation, because they do not map directly to nesting. Sass variables, which are compile-time values, often become custom properties, which are runtime values with cascade and inheritance behaviour, and that change in behaviour must be considered: a custom property can be overridden per element or per theme in ways a Sass variable cannot, which is usually an advantage, but it can also change the result if the Sass variable was used in a calculation that custom properties handle differently. Mixins, which generate repeated rules, may become repeated nested blocks, custom property patterns, or simply duplicated rules, depending on how complex the mixin was. Each mixin deserves its own translation decision, documented for future maintainers.

Testing is essential throughout a Sass-to-native migration, because a syntax that looks equivalent may expand differently. Compare each converted component visually before and after, in the browsers you support, and check not only appearance but also interaction states, responsive behaviour, and theme variations. Automated screenshot comparison helps for large migrations, but even a manual pass over key pages will catch most differences, especially if the migration is done one component at a time and each component is verified before the next begins. A migration done in small, verified steps is far safer than a bulk conversion followed by a single large test.

Finally, decide what to do with the Sass toolchain after migration. If Sass is still needed for other features, such as complex functions or imports, it may remain, with nesting written in native syntax inside Sass files, which Sass will pass through. If Sass is no longer needed, removing it simplifies the build, but that removal should be a separate step after the nesting migration is verified, so that a problem with the toolchain removal is not confused with a problem in the nesting conversion. Migration is a sequence of small, reversible steps, not a single leap, and each step should be verified before the next begins.

/* Sass-like nesting, now native: check & usage carefully. */
.card {
  padding: 1rem;
  &:hover { border-color: #0b5fff; }
}

Section 37: Nesting Mistakes: Over-Nesting

Over-nesting is the most common nesting mistake, and it happens when a developer nests rules to mirror the document tree, rather than to group a component's parts, states, and variants. The result is a block nested four, five, or six levels deep, whose expanded selectors are long, specific, and brittle, even though the indented code looks tidy and organised. Over-nesting feels productive while you are writing it, because each level of indentation feels like progress, but it creates a stylesheet that is hard to override, hard to search, and hard to maintain, because every rule's meaning depends on a long chain of ancestors that may change.

The symptoms of over-nesting are easy to recognise once you know them. Expanded selectors have four or more parts, overrides require equally long selectors or important flags, a small markup change — adding a wrapper element, for example — breaks several styles at once, and reviewers struggle to understand a rule without reading its entire ancestor chain. If you see those symptoms, the nesting is too deep, regardless of how logical the indentation looks. The fix is to flatten: give deeply nested elements their own classes, style those classes as shallow nested rules or flat rules, and remove the intermediate ancestor levels from the selector. Flattening often reduces the stylesheet's size as well, because the same class can be reused in different contexts without repeating its ancestry.

Over-nesting often starts with good intentions: a developer wants to ensure that a style applies only inside a particular component, so they nest it inside that component, then inside a section of that component, then inside a part of that section, until the style is locked to one exact location. That intention — locality — is valid, but nesting is not the only way to achieve it, and it is often not the best way. A distinctive class name achieves locality with one class, without the specificity cost, and scope achieves locality with a boundary, without requiring the full ancestry. Choosing the right locality tool, rather than defaulting to nesting depth, prevents over-nesting at its source.

A useful discipline is to set a depth limit — two levels is a good default — and to require a comment for any rule that exceeds it, explaining why the depth is necessary. That limit forces a conversation about each deep nest, and most deep nests will not survive that conversation, because a flatter alternative will be found. The limit also helps reviewers, because they can check depth at a glance, without needing to expand every selector. Teams that enforce a depth limit consistently produce nested stylesheets that stay readable as they grow, while teams without a limit often discover over-nesting only when the stylesheet becomes unmaintainable.

When you inherit an over-nested stylesheet, refactor it gradually, one component at a time, flattening the deepest rules first and verifying appearance after each component. Over-nesting is reversible, but only with care and testing, which is why preventing it with a depth limit is far cheaper than fixing it later.

/* Over-nested: brittle and hard to override. */
.page .main .card .body p { line-height: 1.6; }

Section 38: Nesting Mistakes: & Misuse

Misuse of & is the second most common nesting mistake, after over-nesting, and it usually takes one of two forms: forgetting & when it is needed, or using & when it is not needed, both of which produce a selector that matches a different element than intended. Forgetting & before a pseudo-class or modifier means the rule becomes a descendant rule, so &:hover becomes :hover for descendants, and &.card--large becomes .card--large for descendants, neither of which styles the parent element itself. Using & unnecessarily, such as writing & .card-title when a simple .card-title would do, does not change the result, but it adds noise and can confuse readers about whether the rule is about the parent or a descendant. Both forms stem from not asking, for each nested rule, whether it describes the parent or a descendant.

The forgetting form is more harmful, because it produces a style that appears to do nothing or to affect the wrong elements, and the cause is not obvious from the indented code, where :hover looks like a state style. The remedy is a habit: whenever you write a nested pseudo-class, pseudo-element, or modifier, start with & unless you can state a reason why the rule should be a descendant.

The unnecessary-use form is less harmful but still worth correcting, because it obscures the code's meaning. Writing & before a descendant selector, such as & .card-title, expands to the same selector as .card-title inside the block, because & followed by a descendant combinator is redundant. That redundancy does not break anything, but it suggests to a reader that something special is happening, when nothing is, and it can lead to confusion when the code is later edited.

A related & mistake is using & to refer to the wrong parent in a deeply nested block, where & means the immediate parent, not the top-level component. In a block nested three levels deep, & refers to the third-level parent, which may be a part, not the component, and a modifier written as &--large inside that deep block would expand to a modifier of the part, not of the component. That mistake is another reason to keep nesting shallow: with one or two levels, & is unambiguous, but with deeper nesting, its meaning becomes harder to track. When you need to refer to the top-level component from deep inside a block, flatten the rule or move it to the component level, rather than relying on a deep & that may refer to the wrong parent.

Finally, test & usage with the states and variants that actually occur, because a & mistake may only appear in one state — for example, a hover style that works for descendants but not for the component itself will look correct in some tests and broken in others. A checklist for nested review — & for parent states, no & for descendants, & refers to the immediate parent — catches most & errors in a minute, and it is worth adding to your team's nesting style guide. Correct & usage is a small discipline with a large payoff in nested code clarity.

/* Correct: & for parent states, no & for descendants. */
.card {
  &:hover { border-color: #0b5fff; }
  .card-title { font-size: 1.25rem; }
}

Section 39: Nesting Mistakes: Specificity Creep

Specificity creep in nested code is the gradual increase in selector weight that happens when nesting depth, compound modifiers, and :has() or :is() arguments accumulate without anyone noticing, until the stylesheet's selectors are far heavier than their purposes require. Creep is insidious because each individual nested rule looks reasonable — a part inside a component, a modifier on a part, a state on a modifier — but together they produce expanded selectors with three, four, or more classes, which are hard to override and hard to reason about. Unlike a single long flat selector, which is visible as long, creep hides behind indentation, so it can grow for months before anyone notices that overrides have become difficult.

The causes of creep are familiar: over-nesting, compounding modifiers unnecessarily, grouping heavy selectors with :is(), and adding :has() conditions that raise weight, all without checking the expanded specificity. Each cause is manageable on its own, but together they compound, literally, because specificity adds. A nested part with two classes, plus a modifier with a third class, plus a :has() argument with a fourth, produces a selector that no single-class utility or variant can beat in the same layer, even though each step felt like a small refinement. That is why specificity creep is a system problem, not a single-rule problem, and why it requires a system response.

The system response has three parts: limits, checks, and refactoring. Limits include a depth limit and a guideline against stacking modifiers, so new rules cannot creep beyond an agreed weight without review. Checks include reviewing expanded selectors in browser tools or with a linter that reports selector specificity above a threshold, so creep is visible before it becomes entrenched. Refactoring includes periodically flattening the heaviest rules, replacing deep nests with distinctive classes, and moving overrides to higher layers where layer order, not specificity, decides the contest. Together, those practices keep specificity in a healthy range, even as a nested stylesheet grows.

A practical way to spot creep is to look for overrides that require long selectors or important flags, because those overrides are symptoms of underlying creep, not independent problems. When an override needs three classes to beat a component rule, ask why the component rule has three classes, and whether it could be flattened to one or two without losing its meaning. That question, asked consistently during review, prevents creep from becoming the normal state of the stylesheet, and it encourages authors to simplify component rules rather than escalating overrides. Over time, the stylesheet's average specificity will stay low, and overrides will stay cheap.

Finally, remember that layers and :where() are tools for managing creep, not excuses to ignore it. Layers let a utility beat a heavy component rule, but they do not reduce the component rule's weight, and a heavy rule in the same layer as its override will still win. :where() can neutralise weight for defaults, but it should not be used to hide creep in rules that are meant to be strong. The goal is a stylesheet where most selectors are short, a few are moderately specific for good reasons, and none are heavy by accident. That goal is achievable with nesting, but only if specificity is checked as regularly as appearance.

/* Creep: each level adds weight, invisibly in source. */
.card {
  .card-body {
    .card-text { color: #444; }
  }
}

Section 40: Nesting and Performance

Nesting has a negligible direct effect on rendering performance, because browsers expand nested rules into flat selectors and then match them with the same optimised machinery they use for flat CSS. A nested rule and its flat equivalent, once expanded, cost the same to match, so choosing nesting over flat CSS for performance reasons is misguided. Performance differences, when they exist, come from the selectors that nesting produces, not from nesting itself: a deeply nested rule expands to a long descendant selector, which costs more to match than a short class selector, because the browser must check ancestors for each candidate element. The performance lesson of nesting is therefore the same as its maintainability lesson: keep expanded selectors short.

Large stylesheets also affect performance through parsing and matching, regardless of whether they are nested or flat, so the size of the stylesheet matters more than its syntax. A nested stylesheet that is shorter in source because it avoids repeating parent selectors may be slightly smaller to download, but once expanded, its matching cost depends on the expanded selectors, not on the source size. Conversely, a flat stylesheet with many repeated selectors may be larger to download but no more expensive to match, if its selectors are short. Do not optimise for source size at the expense of expanded selector length; optimise for short, distinctive selectors, however they are written.

Relational selectors inside nested blocks, such as :has(), deserve performance attention, because they require the browser to check descendants or siblings, which can be expensive when applied to many elements or when the checked content changes frequently. A :has() rule nested inside a component that appears hundreds of times on a page, with an argument that matches many descendants, may cost more than a simple class-based variant, even though the :has() version is more convenient to write. Measure such rules on realistic pages, with realistic content counts, before adopting them widely, and prefer class-based variants for high-frequency components where the performance cost is measurable.

Animations and transitions inside nested blocks follow the same performance guidance as flat CSS: animate transform and opacity where possible, because those properties do not force layout recalculations, and avoid animating layout properties such as width, margin, or padding on every frame. Nesting does not change which properties are cheap to animate, but grouping animation rules with their component, as nested rules, makes it easier to review which properties are being animated and whether cheaper alternatives exist. A nested animation block that animates a layout property on a frequently used component is a performance risk that review should catch, regardless of syntax.

Finally, avoid premature performance optimisation for nesting, because most stylesheets are fast enough and most nesting performance concerns are theoretical. Profile a real page with real content, identify whether style matching is actually a bottleneck — it rarely is, compared with layout, paint, and script — and only then simplify the selectors that profiling shows to be expensive. That measurement-first approach prevents wasted effort on optimisations that do not help, and it keeps the focus on the performance factors that matter most, such as image sizes, script execution, and layout stability, rather than on nesting syntax itself.

/* Short expanded selectors match faster than deep chains. */
.card-title { font-size: 1.25rem; }

Section 41: Nesting for Responsive Components

Responsive components adapt to their context — viewport width, container width, or both — and nesting keeps those adaptations grouped with the component, so a reader can see all the ways a component responds without searching a separate responsive section. A card that stacks vertically on narrow screens and switches to a horizontal layout on wider screens can nest its media query or container query inside the card block, with the wide layout's adjustments to image sizing, spacing, and title size visible beside the base layout.

The choice between media queries and container queries for a responsive component depends on what the component should respond to. Media queries respond to the viewport, which is appropriate when the component's layout should change with the overall page width, such as navigation that collapses at a global breakpoint. Container queries respond to the component's container, which is appropriate when the same component appears in different widths on the same page, such as a card in a sidebar versus a card in a main column. Nesting supports both forms equally, because both can be written as nested at-rules inside the component block, and many responsive components use both: a container query for internal layout, and a media query for page-level adjustments that affect the component.

A responsive nested block should be organised to make the breakpoints visible. List the component's base styles first, then its responsive adjustments in order of increasing width, so the progression from narrow to wide reads naturally. If a component has several breakpoints, a comment naming each breakpoint and its purpose — for example, "narrow: stacked, medium: two columns, wide: horizontal with image" — helps reviewers understand the responsive story at a glance. Without that organisation, a nested block with multiple media and container queries can become a tangle of conditions that is hard to follow, even though each query individually is simple.

Testing responsive nested components requires testing at multiple widths, for both viewport and container, because a component that looks fine at one width may break at another, especially near breakpoints where rules switch on and off. Use browser tools to resize the viewport and to inspect container query behaviour, and check the component in its actual contexts — sidebar, main column, grid, modal — rather than only in isolation, because a container query's behaviour depends on its container, not on the viewport alone. Pay attention to content that changes size, such as long titles or images with different aspect ratios, because those can push a component across a breakpoint unexpectedly.

Finally, keep responsive nesting from becoming a substitute for a genuinely responsive design. A component that needs a dozen breakpoints to look acceptable is probably trying to compensate for a layout model that does not flex well, and a simpler layout — using flex wrapping, grid auto-placement, or fluid sizing — may achieve the same result with fewer queries. Nesting makes responsive rules easy to write, but it does not make a complex responsive design simpler; it only groups the complexity. Use responsive queries where they are needed, prefer flexible layout where it suffices, and document the breakpoints so they can be maintained.

.card {
  padding: 1rem;
  @media (min-width: 40rem) {
    padding: 2rem; display: grid; grid-template-columns: 1fr 2fr;
  }
}

Section 42: Nesting Print Styles

Print styles describe how a component looks when printed, and nesting them inside the component block keeps the print version grouped with the screen version, so a reviewer can check that a component prints sensibly without searching a separate print stylesheet. Inside a card rule, an @media print block can hide decorative elements, adjust colours for printing, or change layout to fit a page width, and those adjustments sit beside the card's screen styles, making the print logic visible where the component is defined.

The print adjustments themselves follow familiar principles: hide navigation, decorative backgrounds, and interactive elements that have no meaning on paper, ensure that text contrast remains readable in black and white, and avoid breaking a component across pages in a way that separates its title from its body. Nesting those adjustments inside the component block makes it easy to check them per component: does this card hide its decorative pseudo-element when printed, does this table avoid breaking rows across pages, does this form hide its buttons? Each question can be answered by reading the component's nested print block, rather than by scanning a global print stylesheet for rules that happen to mention the component.

Print styles also interact with the cascade in the usual way: a nested print rule has the same layer and specificity as its expanded form, and it only applies when the print media condition is true. That means a print adjustment can still lose to a higher-layer or more specific screen rule if the layer placement is wrong, though in practice print rules are often placed in a print-specific context that avoids such conflicts. If a print adjustment mysteriously fails, check its layer and specificity, not just its media condition, because the condition gates applicability only, as with other conditional rules. Testing with print preview, which browsers provide, reveals whether the print rules actually apply, without needing to print on paper.

Be careful not to duplicate a component's entire style inside its print block, because that duplication will drift when the screen version changes. A print block should contain only the adjustments that differ for print — hiding, colour, layout, page breaks — not a copy of the whole component. That minimal approach keeps print maintenance cheap: when the screen version changes, the print version usually needs no change, unless the change affects something print-specific. A print block that is short and focused is also easier to review, because its purpose is clear: these are the differences for paper, nothing more.

Finally, test print styles for the whole page, not just for individual components, because page-level print concerns — headers, footers, page breaks between sections, and the total page count — emerge only when components are combined. Print preview the full page, check that sections break sensibly, that no component is cut in half in a confusing way, and that the printed result is readable without colour. Nesting print rules per component helps with component-level print quality, but page-level print quality still requires a whole-page check, and that check should be part of the review for any significant print change.

.card {
  padding: 1rem;
  @media print {
    box-shadow: none; border: 1px solid #000;
  }
}

Section 43: Nesting Accessibility Styles

Accessibility styles — focus indicators, reduced-motion adjustments, high-contrast adaptations, and readable text sizing — benefit from nesting because grouping them with their component ensures they are not forgotten when the component is written or reviewed. A button block that lists its focus-visible style beside its hover style is more likely to have a complete focus style than a button whose focus style lives in a separate accessibility section, because the gap is visible as a missing nested rule. That visibility is nesting's main accessibility benefit: it makes accessibility part of the component's definition, rather than an addition to be made later.

Focus styles deserve particular attention in nested blocks, because they must remain visible in all states and themes, and nesting helps ensure that. A nested &:focus-visible rule inside a component, placed after hover and before or after active in a deliberate order, guarantees that keyboard focus is indicated, and grouping it with the component's other states makes it easy to check that the focus indicator contrasts with the component's background in both light and dark themes. Test focus with a keyboard, not just with a mouse, because a focus style that is only tested with a mouse may be hidden by a hover style that wins in the cascade when both states apply.

Reduced-motion styles also belong inside component blocks, as nested media queries for prefers-reduced-motion that disable or simplify animations and transitions for readers who prefer less motion. A card block that animates on hover, for example, can nest a reduced-motion query that removes the animation, grouped with the animation itself, so a reviewer can see both versions together and check that the reduced-motion version is genuinely calmer, not merely a different animation. That grouping prevents the common error where a reduced-motion rule is written for one component but forgotten for another, because each component's block can be checked for its own reduced-motion handling.

High-contrast and forced-colours adaptations are similar: a component that uses colours or shadows to convey meaning should nest a forced-colours adjustment that ensures that meaning remains available when colours are overridden by the reader's settings. That adjustment may involve using system colours, adding borders where colour alone conveyed a distinction, or ensuring that icons remain visible. Grouping those adjustments with the component makes them reviewable, and it reminds authors that colour alone should not convey essential information, because that information must survive colour overrides.

Finally, accessibility nesting should be reviewed as part of component review, with a checklist that covers focus, motion, contrast, and colour independence for each component block. That checklist, applied to nested blocks, turns accessibility from a separate audit into a routine part of writing components, which is more reliable than auditing at the end of a project, when fixes are more expensive. Nesting does not make a component accessible by itself, but it makes accessibility visible, and visibility is the first step toward completeness.

.btn {
  padding: 0.5rem 1rem; transition: background 0.2s;
  &:focus-visible { outline: 3px solid #0b5fff; outline-offset: 2px; }
  @media (prefers-reduced-motion: reduce) {
    transition: none;
  }
}

Section 44: Nesting Animation and Transition Rules

Animation and transition rules describe how a component changes over time, and nesting them inside the component block keeps the motion logic grouped with the static styles it animates between. A card block that defines its base shadow, then a transition for that shadow, then a hover state with a larger shadow, tells the complete motion story in one place: what changes, how quickly, and in which state. That grouping helps reviewers check that transitions are smooth, that they do not animate layout properties unnecessarily, and that they respect reduced-motion preferences, because all the motion information is visible together.

Transitions are the simpler case: a nested transition property inside a component, or inside a state rule, defines which properties animate and over what duration when the component changes state. Grouping the transition with the component ensures that the transition applies to all state changes for that component, rather than being defined in a separate animation section where it might be missed for a new state. It also makes it easy to check that the transitioned properties are cheap to animate — transform and opacity are preferred, while width, margin, and other layout properties can cause expensive recalculations on every frame. A nested transition that animates a layout property on a frequently used component is a performance risk that review should catch.

Animations with keyframes are a slightly different pattern, because keyframes themselves are defined at the top level with @keyframes, not nested inside a component, but the animation property that applies those keyframes can be nested inside the component block. A button block, for example, can nest an animation property that references a shared keyframe definition, grouped with the button's other styles, so the connection between the component and its animation is visible. The keyframe definition itself remains top-level, because it may be shared by several components, and duplicating it inside each component would be wasteful. That split — shared keyframes top-level, component-specific animation properties nested — is a practical organisation for animated components.

Reduced-motion handling for animations and transitions also belongs inside the component block, as a nested media query that disables or simplifies motion for readers who prefer it. Grouping that query with the animation it suppresses makes the reduced-motion version easy to verify: does this component's animation actually stop when reduced motion is requested, or does it merely slow down? That question can be answered by reading the component block, rather than by searching a global reduced-motion section. It also prevents the error where a new animation is added without a corresponding reduced-motion rule, because the block's structure prompts the author to consider motion handling for each animation.

Finally, test animations and transitions in the browser, with real interaction, because a transition that looks correct in code may feel too fast, too slow, or too jarring in practice. Hover, focus, and press the component, watch the motion, and check that it enhances rather than distracts from the interaction. Nesting helps that testing, because the motion rules are listed with the component, so a tester can check them off one by one. Motion, like other component behaviour, is part of the component's definition, and nesting makes that definition complete.

.card {
  transition: box-shadow 0.2s ease;
  &:hover { box-shadow: 0 4px 16px rgb(0 0 0 / 0.15); }

Section 45: Nesting in Design Systems

Design systems — shared component libraries used across many products — benefit from nesting because it provides a consistent way to write each component's styles, with parts, states, variants, and responsive behaviour grouped in a predictable block structure. That consistency helps consumers of the system, because every component's styles follow the same pattern, so learning one component's block teaches the pattern for all of them. It also helps the system team, because a consistent block structure makes review, testing, and documentation easier: a reviewer can check each component block against the same checklist, and documentation can describe the block pattern once, rather than per component.

The system should document its nesting conventions explicitly, including depth limits, & usage, the boundary between nested and flat rules, and how layers, scope, and variables interact with nesting. That documentation is part of the system's contract, because consumers who override or extend system components need to know how the system's nested rules expand, what their specificity is, and which layer they belong to. Without that documentation, a consumer who tries to override a nested component rule may be surprised by its expanded specificity, and may resort to important flags or long selectors, fragmenting the system. With documentation, the consumer can override correctly, using the system's own layer and variant mechanisms.

Versioning is also a nesting concern in design systems, because changing a component's nesting structure — flattening a part, adding a level, changing a modifier from nested to flat — can change its expanded selectors and therefore break consumer overrides, even if the component's appearance is unchanged. The system team should treat nesting structure as part of the component's public interface, announce changes to it in release notes, and provide a migration path for overrides that depend on the old structure. A changelog entry that says "card title flattened from nested to flat, specificity reduced from two classes to one" is far more helpful than a silent change that breaks consumer pages.

Consumers should also be given approved extension points, such as variant classes, container classes, or variable redefinitions, so they do not need to override nested internal rules directly. A system that provides a variant for every common customisation reduces the need for consumers to fight nested specificity, because the variant is part of the system and its specificity is designed to work. When consumers repeatedly override the same nested rule in the same way, that is a signal that the system should add a variant or a token for that customisation, rather than expecting consumers to keep overriding. Listening to override patterns is how a design system improves its nesting conventions over time.

Finally, design system nesting should be tested across products, because a nested component that works in one product's context may break in another's, where it appears inside different containers, themes, or scopes. Testing a component in isolation is not enough; it must be tested in the contexts where consumers actually use it, including nested inside other components, inside different themes, and at different container widths. That cross-product testing reveals nesting issues — leakage, specificity conflicts, layer mismatches — that isolation testing hides, and it ensures that the system's nesting conventions work in practice, not just in examples.

/* Design system: consistent nested block per component. */
.card {
  padding: 1rem;
  .card-title { font-size: 1.25rem; }
  &:hover { border-color: #0b5fff; }
}

Section 46: Refactoring Flat CSS into Nested CSS

Refactoring flat CSS into nested CSS is a restructuring exercise that should be done one component at a time, with visual verification after each component, rather than as a bulk conversion of an entire stylesheet. Start by identifying a component's flat rules — its base, parts, states, and variants — which will usually share a common prefix or class name, and group them into a single nested block under the component's base class. Verifying that the expanded selectors match the original flat selectors is the key check for each component.

A practical refactoring sequence is to first group the component's rules without changing their selectors' meaning, then simplify where nesting makes simplification possible, such as removing repeated parent prefixes, and only then consider deeper changes such as flattening parts or adjusting specificity. That sequence separates organisation from simplification, so a visual regression can be attributed to one step or the other. If you group and simplify at the same time, a regression could be caused by either change, and debugging becomes harder. Small, verified steps are the theme of all safe refactoring, and nesting refactoring is no exception.

Watch for flat rules that should not be nested, even though they share a prefix with a component. Utilities, cross-component overrides, and page layout rules that happen to mention a component class should remain flat, because nesting them inside the component would change their scope or specificity in ways that break their purpose. A utility that mentions a component in its selector is usually a mistake to begin with, but if it exists, nesting it inside the component would make it even more specific and less reusable. Similarly, a page layout rule that arranges components should remain outside the component block, because it describes the page, not the component. Refactoring is an opportunity to correct those misplacements, not to preserve them in nested form.

Also watch for flat rules with high specificity that, when nested, become even heavier, because nesting adds the parent's weight to an already heavy selector. A flat rule with three classes, nested inside a component with one class, becomes four classes, which is almost certainly too heavy. In such cases, flattening the original rule — giving its target a distinctive class and styling that class alone — should come before nesting, so the nested version starts from a clean, low-specificity base. Refactoring into nesting should reduce complexity, not preserve or increase it, and a heavy flat rule is a signal that simplification is needed first.

Finally, document the refactoring as you go, noting which components have been converted, which remain flat, and any specificity or layer changes that resulted from the conversion. That progress note helps the team coordinate, prevents duplicate work, and gives reviewers context for changes that might otherwise look like unrelated edits. When the refactoring is complete, the progress note can be replaced by a permanent style guide entry describing the nesting conventions that the refactoring established. A refactoring that is documented is one that the team can maintain, while an undocumented refactoring may drift back to flat CSS as new contributors follow old habits.

/* Flat: .card, .card .card-title — nested: group under .card. */
.card {
  padding: 1rem;
  .card-title { font-size: 1.25rem; }
}

Section 47: Reviewing Nested Code

Reviewing nested code requires a different reading habit from reviewing flat code, because the meaning of a nested rule depends on its parent context, its depth, and its use of &, all of which must be checked together. A reviewer should start by reading the parent block's purpose, then check each nested rule's expanded selector, asking whether it matches the intended elements, whether its specificity is appropriate, and whether it leaks into nested components. That expanded-selector check is the core of nested review, and it can be done mentally for shallow blocks, or with browser tools for deeper ones, but it cannot be skipped, because the indented form alone hides the true selector.

A nested review checklist helps make that check systematic. Ask: is the nesting depth within the team's limit, does each nested rule use & correctly for parent states versus descendants, are part names distinctive enough to avoid leakage, are states listed in a sensible order with focus visible, are variants complete and not conflicting, and are responsive and print adjustments grouped sensibly? Each question corresponds to a common nesting mistake, and answering them for a block takes only a few minutes, yet it catches most nested bugs before they reach production. That checklist should be part of the team's review culture, not just a personal habit, so that nested code is reviewed consistently regardless of who wrote it.

Reviewers should also check the interaction between nesting and other cascade mechanisms, such as layers, scope, and custom properties, because a nested rule's layer is determined by its surrounding context, and its variable dependencies may span several levels of the block. A nested rule in the wrong layer, or a variable redefinition that affects more parts than intended, will not be obvious from the nested block alone, unless the reviewer checks the layer wrapper and the variable's scope. That cross-mechanism check is especially important for components that use both nesting and layers, because the two systems together determine priority, and a mistake in either can produce a confusing override.

Finally, reviewers should check for readability, not just correctness, because a nested block that is technically correct but hard to understand will become a maintenance burden. Is the block's structure clear at a glance, are its parts, states, and variants easy to distinguish, and would a new team member understand the component by reading the block alone? If the answer is no, the block should be split, flattened, or reorganised, even if its styles are correct, because readability is a requirement for maintainable code, not a luxury. Reviewing for readability, alongside correctness, is what keeps a nested stylesheet usable as it grows.

A reviewer should also verify that the block does not duplicate styles already defined elsewhere, because duplication in nested code is easy to miss when rules are grouped by component rather than by property.

Section 48: Nesting Style Guide for Teams

A nesting style guide for teams should be short, practical, and illustrated with examples from the team's own components, because a guide that is long, abstract, or based on unfamiliar examples will be ignored. The guide should cover the decisions that actually cause confusion in nested code: maximum depth, & usage for parent versus descendant rules, naming for nested parts, the boundary between nested and flat rules, layer placement for nested blocks, and how to handle states, variants, and responsive adjustments. Each topic deserves a short rule, a correct example, and an incorrect example, so the guide is usable as a reference during writing and review, not just as a document to be read once.

Depth is usually the first rule in such a guide, and a limit of two levels, with exceptions documented, is a good starting point that many teams adopt. The guide should explain why the limit exists — expanded selector length and specificity — not just state it, because a rule with a reason is more likely to be followed than a rule without one. It should also give guidance for the exception case: when deeper nesting is allowed, what comment is required, and who reviews it. That exception process prevents the limit from being either too rigid, blocking legitimate deep structures, or too lax, allowing depth to creep back in through unreviewed exceptions.

The guide should also address & usage with the simple rule: & for parent states, modifiers, and pseudo-elements, no & for descendants, and & refers to the immediate parent in deep blocks. That rule, with examples of correct and incorrect & use, prevents the most common nesting bug, and it gives reviewers a standard to check against. Naming guidance should follow: nested parts use distinctive class names, preferably following the team's naming system, so that nested rules do not leak into nested components and so that expanded selectors remain searchable. Those three rules — depth, &, naming — cover most nesting decisions, and a guide that covers them well is already valuable.

Finally, the guide should be maintained as a living document, updated when the team encounters a new nesting pattern or mistake, and reviewed periodically to ensure it still matches the codebase. A guide that is never updated will drift from practice, and developers will stop trusting it, while a guide that is updated in response to real code will remain relevant. The guide's owner, or the team as a whole, should review it after significant nesting refactors or after a nesting bug reveals a gap, and should update its examples to reflect the current codebase. A style guide is a team agreement, and like any agreement, it needs maintenance to remain useful.

/* Style guide example: depth 2, & for parent states. */
.card {
  .card-title { font-size: 1.25rem; }
  &:hover { border-color: #0b5fff; }

Section 49: When Not to Nest

Knowing when not to nest is as important as knowing how to nest, because nesting applied indiscriminately creates stylesheets that are harder to maintain than flat equivalents. Do not nest when the rule is independent and reusable, such as a utility class, a base style, or a cross-component override, because nesting would tie that rule to a parent context it does not need and would raise its specificity unnecessarily. A utility nested inside a component is no longer a utility, and a base style nested inside a component is no longer a base, even if the indented code looks tidy. Independence is a reason to stay flat.

Do not nest when the nested rule's relationship to its parent is incidental rather than essential. A rule that happens to apply inside a component on one page, but could equally apply elsewhere, should not be nested inside that component, because the nesting suggests a permanent relationship that does not exist. Similarly, do not nest page layout rules inside components, because page layout describes how components are arranged, not what a component is, and nesting it inside a component makes the component less reusable. Ask whether the rule would still make sense if the component moved to a different page or context; if it would, it probably should not be nested inside that component.

Do not nest when nesting would make the expanded selector unreasonably long or specific, even if the indentation looks clean. A rule nested four levels deep, or a rule that compounds several modifiers and conditions, will produce a selector that is hard to override and fragile to markup changes, regardless of how tidy the source looks. In those cases, flatten the rule, give its target a distinctive class, or use scope or layers to achieve locality without selector length. The test is always the expanded selector: if you would not write it flat, do not write it nested, because nesting does not make a long selector shorter, it only hides its length.

Do not nest when the team or tooling cannot handle it well. If your audience includes browsers without nesting support and you have no build step or fallback, nesting critical styles is risky. If your tools cannot search expanded selectors or show nesting structure clearly, heavy nesting will slow debugging. If your team is unfamiliar with nesting and has no style guide, introducing nesting everywhere at once will produce inconsistent code that is harder to review than the flat code it replaces. In those situations, introduce nesting gradually, for components where its benefit is clearest, and build the tooling, documentation, and familiarity alongside it, rather than nesting everything immediately.

Finally, do not nest for its own sake, as a demonstration that you know the syntax, because a stylesheet's quality is measured by its readability and maintainability, not by how many modern features it uses. A flat rule that is clear, short, and easy to override is better than a nested rule that is clever, deep, and hard to follow. Nesting is a tool, and like any tool, its value lies in using it where it helps and leaving it aside where it does not. That judgement — knowing when not to nest — is the mark of a mature CSS author.

Section 50: Nesting Playbook

A nesting playbook is a short set of habits that lets you use nesting confidently without needing to reconsider every decision from scratch. Start by grouping a component's parts, states, and variants inside its block, with a depth limit of two levels, distinctive class names for parts, and & for parent states, modifiers, and pseudo-elements, and no & for descendants. Place the component block in the correct layer, use custom properties for values that vary by theme or variant, and list states in a sensible order with focus visible. Those habits, followed consistently, produce nested blocks that are readable, predictable, and easy to override, which is the goal of nesting in the first place.

Inside the block, organise rules in a logical sequence that mirrors how a reader encounters the component: base layout and appearance first, then parts, then states, then variants, then responsive and print adjustments. That sequence makes the block easy to scan, because a reader knows where to look for each kind of rule, and it makes review easier, because gaps — a missing focus state, a variant without a responsive adjustment — are visible as breaks in the sequence. When a block grows too long or too deep, split it: extract a sub-component, flatten a part, or move page layout out, rather than letting the block become unwieldy for the sake of keeping everything in one place.

When something goes wrong with a nested style, follow the debugging playbook: expand the nested rules mentally or in browser tools, name the deciding cascade step, and apply the smallest fix at that step, whether it is adding or removing &, flattening a deep rule, moving a layer, or simplifying a selector. Do not escalate to important or to longer selectors until you have tried those fixes, because escalation in nested code, as in flat code, creates specificity creep that is hidden behind indentation and therefore harder to reverse. Document exceptions — a deeper nest, a redundant &, a layer override — with a comment that names the reason, so the exception does not become a mystery for the next reader.

Finally, keep the playbook alive by reviewing it when the project grows, when a new nesting pattern emerges, or when a nesting bug reveals a gap. Update the style guide, share the lesson with the team, and check that new components follow the updated playbook. Nesting, like the cascade, is a system to be designed and maintained, not a syntax to be used once and forgotten. A playbook that is followed, reviewed, and updated turns nesting from a novelty into a reliable part of your CSS practice, and it lets a team write component styles that are grouped, readable, and maintainable, without sacrificing the cascade control that makes CSS predictable.
