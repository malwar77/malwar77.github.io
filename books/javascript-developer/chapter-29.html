Chapter 29: Error Handling: try, catch and throw

Section 1: Why Errors Happen in Real Programs

Errors are not a sign that you are a bad programmer. They are a normal part of running software in the real world, where inputs are unpredictable, networks fail, files go missing, and users do things you never anticipated. Even perfectly written code can fail when a server is down, when a user enters unexpected text, or when a dependency changes its behaviour. Accepting errors as normal, rather than as rare disasters, is the first step toward writing reliable programs. Your job is not to write code that never fails, which is impossible, but to write code that fails gracefully, explains what happened, and gives users a way forward.

Many errors come from outside your program. A network request can fail because of a lost connection, a file can be missing because it was moved, or an API can return data in a different shape than you expected because it was updated. Other errors come from inside your program, such as a bug where you try to read a property from undefined, or a calculation that divides by zero, or a loop that runs past the end of an array. Both kinds of errors need handling, but they need different responses. External errors often deserve a retry or a fallback, while internal bugs deserve fixing at the source, not just catching and hiding, because hiding a bug can mask a deeper problem that will cause worse failures later.

Users experience errors very differently depending on how you handle them. A program that crashes with a blank screen and a technical message feels broken and untrustworthy, even if the underlying problem was minor, such as a single failed image load. A program that shows a clear message, such as Could not load this image, with a retry button, feels reliable, even though it also failed, because it communicated and offered a next step. That difference in experience is entirely about error handling, not about whether an error occurred. Good error handling therefore directly improves user trust, retention, and satisfaction, which are business outcomes, not just technical niceties.

Learning error handling also makes you a better debugger, because you start to think about failure modes before they happen. When you write a function, you begin to ask what could go wrong with its inputs, its dependencies, and its outputs, and you design checks and fallbacks accordingly. That proactive thinking, often called defensive programming, prevents many bugs from reaching users at all, because you validate inputs, check for missing data, and handle edge cases explicitly. Over time, that habit becomes automatic, and your code becomes more robust without feeling defensive or cluttered, because the checks are placed where they matter most, at boundaries and risky steps.

In this chapter, you will learn the full error handling toolkit: try, catch, and finally, throwing your own errors, custom error classes, logging, testing error paths, and designing graceful degradation. By the end, you will be able to anticipate common failures, handle them in the right place, communicate them clearly to users, and fix the underlying causes when they are bugs in your own code. That skill set is essential for professional JavaScript development, where reliability is often what separates a demo from a product people depend on every day.

function safeDivide(a, b) {
  if (b === 0) {
    throw new Error("Cannot divide by zero");
  }
  return a / b;
}

try {
  console.log(safeDivide(10, 0));
} catch (error) {
  console.log("Caught: " + error.message);
}

Section 2: Understanding Error Objects

An Error object in JavaScript is a value that represents a failure, with useful properties for understanding and debugging it. The most important property is message, a human-readable string describing what went wrong, such as Cannot divide by zero or User not found. Another important property is name, which identifies the kind of error, such as Error, TypeError, RangeError, or a custom name you define. The third key property is stack, a string containing a stack trace that shows the sequence of function calls leading to the error, with file names and line numbers where available. Together, message, name, and stack give you everything you need to diagnose an error: what happened, what kind of problem it was, and where in the code it originated.

JavaScript provides several built-in error types, each for a specific kind of failure. TypeError occurs when an operation is performed on a value of the wrong type, such as calling a non-function or reading a property from undefined. ReferenceError occurs when you try to use a variable that does not exist. RangeError occurs when a value is outside an allowed range, such as an array length that is too large or a number that is out of range for a function. SyntaxError occurs when code cannot be parsed, usually at load time rather than at runtime. Understanding these types helps you diagnose errors quickly, because the name alone often points to the category of mistake, such as a type mismatch versus a missing variable, guiding your search for the cause.

When you throw an error, you should always throw an Error object, or an instance of a subclass, rather than a string, number, or other value, because Error objects carry stack traces and names that make debugging possible. Throwing a string, such as throw "Something failed", loses the stack trace, making it hard to know where the error came from, and it forces catch blocks to handle a plain string without name or stack properties. Throwing an Error with a clear message, such as throw new Error("Failed to load user 7: network timeout"), preserves debugging information and makes catch blocks uniform, because they can always expect an Error object with message, name, and stack. That uniformity is a professional habit that pays off every time you debug a failure in a large program.

Error objects can also carry additional custom properties, such as a code, a status, or the input that caused the failure, which help callers decide how to handle the error. For example, an error for a failed fetch might carry a status property with the HTTP status code, allowing the caller to distinguish a not-found error from a server error without parsing the message string. Similarly, a validation error might carry a field property naming the invalid field, allowing display code to highlight that field specifically. Adding such structured information to errors, rather than encoding it only in message text, makes error handling programmatic and reliable, because callers can check properties with code, rather than parsing human-readable messages that might change.

try {
  const user = null;
  console.log(user.name);
} catch (error) {
  console.log("Name: " + error.name);
  console.log("Message: " + error.message);
}

Section 3: try, catch and finally in Depth

The try, catch, and finally blocks form the core of JavaScript error handling, and understanding each block's role in depth will help you use them precisely. The try block contains code that might throw an error, such as a risky operation, a function call that could fail, or an await for a promise that could reject. If no error occurs in try, execution continues after the whole try-catch-finally structure, skipping catch entirely. If an error occurs, execution jumps immediately to catch, skipping the rest of try, which prevents code that depends on successful completion from running with incomplete or invalid results. That jump-on-error behaviour is the key to try's safety: it ensures that failure stops the normal path before it can cause further damage.

The catch block receives the thrown error as a parameter, traditionally named error, err, or e, and contains recovery code. Recovery can take many forms: showing a user message, returning a fallback value, retrying the operation, logging the error, or rethrowing it for a higher-level handler to deal with. The choice depends on context: a low-level helper might log and rethrow, while a high-level user interface handler might show a message and return a fallback. What catch should not do is swallow errors silently with an empty block, because silent swallowing hides failures from both users and developers, making bugs hard to find and leaving users with unexplained missing data. Even if you cannot recover, you should at least log the error before rethrowing or returning a fallback, so that failures are visible in logs.

The finally block runs after try and catch, regardless of whether an error occurred, whether catch handled it, or whether try returned early or threw again. That guarantee makes finally ideal for cleanup, such as closing files, hiding loading indicators, re-enabling buttons, or releasing resources, as discussed in earlier chapters. Finally does not receive the error or the return value, and it should not return or throw itself, because doing so would override the original outcome and confuse callers. Keeping finally focused on cleanup, without return or throw, preserves the original success or failure outcome while ensuring cleanup always happens, which is exactly the reliability guarantee you want for resources and interface states.

Nesting try blocks is also common and useful. You might have an outer try that handles overall feature failures with a user message, and inner tries that handle specific steps with specialised recovery, such as retrying a single fetch or using a fallback for one section. That nesting allows different levels to handle different aspects of failure: inner handlers deal with recoverable, local problems, while outer handlers deal with unrecoverable, feature-level problems. Designing that nesting deliberately, rather than wrapping everything in one giant try, gives you precise control over recovery and makes error handling easier to understand, because each catch block's purpose is clear from its scope and its recovery code.

function workWithCleanup(shouldFail) {
  console.log("Starting work");
  try {
    if (shouldFail) {
      throw new Error("Work failed");
    }
    console.log("Work succeeded");
    return "done";
  } catch (error) {
    console.log("Caught: " + error.message);
    return "failed";
  } finally {
    console.log("Cleanup always runs");
  }
}

workWithCleanup(false);
workWithCleanup(true);

Section 4: Catching Specific Errors by Type

Catching specific errors by type means handling different kinds of failures differently, rather than treating all errors the same way in a single catch block. For example, a TypeError might indicate a bug in your code that should be fixed and logged, while a network error might indicate a transient problem that should be retried, and a validation error might indicate user input that should be corrected with a field-specific message. Treating those three errors identically, with a generic message, would be unhelpful for all three cases, because the user's next step differs for each. Specific handling, by checking error name, error class with instanceof, or a custom code property, allows you to tailor recovery and messages to each error type, which is more helpful and more professional.

Checking error type can be done in several ways. The simplest is to check error.name, which is a string such as TypeError or RangeError for built-in errors, or a custom name for custom errors. A more robust way for built-in errors is to use instanceof, such as error instanceof TypeError, which checks the error's prototype chain and works even if the name property was changed. For custom errors with codes, you can check error.code, such as error.code === "NOT_FOUND", which is precise and programmatic, without relying on message text that might change. Choosing among these methods depends on how errors are created in your program: for built-in errors, instanceof is reliable, for custom errors, code checking is often clearest, and for errors from external libraries, name checking may be the only option if the library does not export its error classes.

A common pattern for specific handling is to have a single catch block that branches on error type with if and else, handling known types specifically and rethrowing unknown types for higher-level handling. That pattern, catch, check, handle known, rethrow unknown, is safer than handling all errors in one place, because it prevents your code from accidentally handling an error it does not understand, such as a bug that should crash visibly during development rather than being masked as a user message. Rethrowing unknown errors preserves the principle that you should only handle errors you understand and can recover from, while letting other errors propagate to handlers that do understand them, or to global handlers that log them for fixing. That discipline prevents error handling from becoming error hiding, which is a common anti-pattern where catch blocks swallow bugs and make programs harder to debug.

You should also consider that specific handling adds complexity, so it should be used where different errors genuinely need different responses, not for every catch block. For simple features where all errors lead to the same user message, such as Could not load data, a generic catch is sufficient and clearer. For features where errors have distinct remedies, such as sign-in for authentication errors, correction for validation errors, and retry for network errors, specific handling is worth the extra code, because it guides users correctly. That judgement, generic when remedies are same and specific when remedies differ, keeps error handling proportionate to user needs, rather than over-engineered for every case or under-specified for cases where specificity matters.

function riskyOperation(kind) {
  if (kind === "type") {
    throw new TypeError("Wrong type");
  }
  if (kind === "range") {
    throw new RangeError("Out of range");
  }
  throw new Error("Unknown problem");
}

try {
  riskyOperation("type");
} catch (error) {
  if (error instanceof TypeError) {
    console.log("Handle type error specifically");
  } else if (error instanceof RangeError) {
    console.log("Handle range error specifically");
  } else {
    throw error;
  }
}

Section 5: Throwing Your Own Errors

Throwing your own errors means deliberately signalling a failure from your code when a condition is detected that should not proceed, such as invalid input, a missing resource, or a violated business rule. Instead of returning a special value such as null or false, which callers might forget to check, throwing forces callers to handle the failure, either by catching it or by letting it propagate, because unhandled throws become visible failures rather than silent wrong results. That forcing property is valuable for serious failures where proceeding would be incorrect or dangerous, such as saving invalid data or charging a payment with missing details. For minor, expected outcomes, such as a search with no results, returning an empty list is usually better than throwing, because no results is not a failure, it is a valid outcome that callers can handle normally without exception machinery.

When you throw, you should throw an Error object with a clear, specific message that explains what failed and, where helpful, what input caused it, such as throw new Error("Age must be a positive number, got -5"). That message should be written for developers first, because it will appear in logs and stack traces, but it should also be translatable to a user message by catch blocks, which can map technical messages to friendly ones. Including relevant identifiers, such as user ids or field names, in error messages helps debugging, as discussed earlier, without exposing sensitive data such as passwords or tokens, which should never appear in error messages, because logs and error displays might be visible to people who should not see secrets. That balance, detailed enough to debug and safe enough to share, is a key skill in writing good error messages.

Choosing when to throw versus when to return an error value is a design decision that affects your program's style and reliability. Throwing is appropriate for exceptional conditions that break normal flow and that callers should not ignore, such as invalid arguments to a function that cannot proceed, or a failed operation that the caller must know about. Returning an error value, such as an object with success false and an error message, is appropriate for expected failures that are part of normal flow, such as validation results where multiple errors need to be collected, or operations where callers need to inspect errors without exception overhead. Many programs use both: throwing for programming errors and unexpected failures, and returning error objects for validation and expected business failures, with the choice documented so that callers know which pattern to expect from each function.

For example, a function that validates all inputs at the start and throws on the first invalid input, before starting any work, is easier to reason about than a function that starts work, fails halfway, and leaves partial state that must be cleaned up. That early validation and throwing, often called fail fast, is a defensive pattern that keeps programs in consistent states, because failures happen before state changes, not after partial changes that are hard to roll back. Combining early throwing with guard clauses, which we will discuss later, gives you clean, predictable functions where invalid inputs are rejected promptly and valid inputs proceed with confidence.

function setAge(age) {
  if (typeof age !== "number") {
    throw new TypeError("Age must be a number");
  }
  if (age < 0) {
    throw new RangeError("Age cannot be negative");
  }
  return "Age set to " + age;
}

try {
  console.log(setAge(-5));
} catch (error) {
  console.log(error.name + ": " + error.message);
}

Section 6: Error Messages That Help Users

Error messages that help users are written in plain language, explain what happened in terms users understand, and tell users what to do next, rather than exposing technical details or blaming users for the failure. A helpful message for a failed load might be We could not load your posts. Check your connection and try again, which explains the problem in user terms, suggests a likely cause, and offers a next step, retrying. An unhelpful message for the same failure might be TypeError: Failed to fetch, which is accurate for developers but meaningless for most users, who do not know what fetch is or what a TypeError means, and who are left without guidance on what to do. That contrast shows that user messages and developer messages serve different audiences and should be written separately, even when they describe the same failure.

Writing helpful user messages starts with identifying the user's goal and the barrier that prevented it. If the user was trying to save a document and saving failed, the message should mention saving, not a technical operation such as POST or database write, because users think in terms of their goals, not implementation details. It should also be specific enough to guide action: if the problem is a connection issue, say check your connection; if it is invalid input, say which field is invalid and what a valid value looks like; if it is a server problem, say try again later, rather than immediately, to avoid repeated failed attempts during an outage. That specificity, goal plus cause plus next step, is the formula for helpful messages, and it applies to almost every error a user might encounter, from form validation to network failures to permission problems.

Tone in user error messages also matters, as discussed for fetch errors earlier. Messages should be calm, factual, and non-blaming, avoiding language such as You made a mistake or Fatal error, which increases anxiety and reduces trust. Instead, use neutral language such as We could not save your changes, or That username is already taken, please choose another, which states the problem without attributing fault. For errors that are the program's fault, such as server errors, acknowledging the problem with We are sorry or We had a problem, without over-apologising, shows accountability and reassures users that the problem is being taken seriously, even if they cannot fix it themselves. That tone, calm and accountable, is part of a professional user experience that respects users even when things go wrong.

Inline messages next to the relevant field are best for validation errors, because they pinpoint the problem in context. Banner messages at the top of a page are better for feature-level failures, such as a failed load, because they are visible without scrolling to a specific field. Toast messages that appear briefly are suitable for transient failures that do not block the user's main task, but they should not be used for serious errors that require action, because users might miss them. Choosing the right display location, inline for field errors, banner for feature errors, and toast for transient notices, ensures that messages are seen in context and at the right level of urgency, which is as important as the message text itself for helping users recover.

function userMessage(error) {
  if (error.name === "TypeError") {
    return "Something went wrong with the data. Please try again.";
  }
  return "We could not complete that action. Please try again.";
}

Section 7: Validation Errors Versus System Errors

Validation errors and system errors are two fundamentally different kinds of failure, and distinguishing them is essential for correct handling, because they have different causes, different remedies, and different implications for users and developers. Validation errors occur when user input or data does not meet expected rules, such as a missing required field, an invalid email format, or a value outside an allowed range. They are expected, common, and usually fixable by the user, who can correct their input and retry immediately. System errors occur when the program or its environment fails unexpectedly, such as a network outage, a server crash, a database failure, or a bug in code, which users generally cannot fix by changing their input, and which may require waiting, retrying later, or contacting support. Treating these two kinds identically, with the same message and handling, would mislead users, because it would suggest that a system problem can be fixed by correcting input, or that a validation problem requires waiting for a server fix.

Handling validation errors should be immediate, specific, and field-focused. When validation fails, you should show messages next to the offending fields, explaining what is wrong and what a valid value looks like, and you should preserve the user's other inputs, so they can correct only the invalid fields without re-entering everything. You should also collect all validation errors at once, rather than reporting them one at a time, so users can fix all problems in one pass, rather than submitting repeatedly to discover new errors each time. That batch reporting, with field-specific messages and preserved input, is the standard for good form validation, and it respects users' time and effort, turning validation from a frustrating barrier into a helpful guide toward correct input.

Handling system errors, by contrast, should be general, reassuring, and focused on next steps that do not involve correcting input. When a system error occurs, you should show a message such as We had a problem on our side. Please try again in a few minutes, log the technical details for developers, and offer options such as retry, go back, or contact support, depending on severity. You should not show technical details to users, because they cannot act on them, and you should not suggest that changing input will help, because it will not. You should also ensure that system errors do not lose user work: if a save fails due to a system error, the user's input should be preserved, either in the form or in a draft, so they can retry without retyping, which is a crucial usability detail that is often overlooked in system error handling.

System errors, by contrast, are often thrown as exceptions, because they are unexpected and break normal flow, requiring catch blocks to handle them as failures. That representation difference, returned validation results versus thrown system errors, reflects the conceptual difference: validation is part of normal flow, where multiple errors can be collected and reported, while system failure is an exception to normal flow, where execution must stop and recovery must happen. Understanding that distinction helps you design functions that return validation results for input checking, while throwing for system failures, with clear documentation so callers know which pattern to expect.

function validateName(name) {
  const errors = [];
  if (!name || name.trim() === "") {
    errors.push("Name is required");
  }
  return errors;
}

console.log(validateName(""));
console.log(validateName("Ada"));

Section 8: Handling Errors in Functions

Handling errors in functions involves deciding, for each function, whether it should handle errors internally, propagate them to callers, or both, and that decision shapes your program's error architecture. A function that handles errors internally catches them, recovers with a fallback or a user message, and returns a normal result, hiding the failure from callers. That approach is appropriate when the function knows how to recover, such as a function that loads cached data when a fetch fails, or a function that returns a default value when a calculation fails for a specific input. A function that propagates errors, by not catching them or by rethrowing after logging, lets callers decide how to handle the failure, which is appropriate when the function does not know the context, such as a low-level helper that fetches data but does not know whether the caller is a dashboard, a detail page, or a background job, each of which might handle failure differently.

A common and effective pattern is to handle errors at the level where recovery is possible and where context is sufficient, and to propagate them otherwise. Low-level helpers, such as fetch wrappers, should propagate errors with clear messages and structured information, because they lack user context. Mid-level functions, such as feature loaders, might handle specific recoverable errors, such as using cached data for a failed section, while propagating unrecoverable errors to higher levels. High-level functions, such as event handlers or page loaders, should handle errors with user messages and fallbacks, because they have the full user context and are the last line of defence before an error becomes a user-visible crash. That layered handling, propagate low, recover mid where possible, and display high, creates a coherent error architecture where each level does what it is best positioned to do, without duplicating handling or hiding failures.

Documenting a function's error behaviour is also important, because callers need to know whether a function throws, what kinds of errors it throws, and whether it returns fallbacks instead of throwing. That documentation can be in comments, in a function's name, or in its return type, but it should be explicit, especially for functions that throw for some inputs and return normally for others. For example, a function named loadUserOrNull might return null on failure instead of throwing, while a function named loadUser might throw on failure, and that naming difference communicates error behaviour to callers without them needing to read implementation details. Consistent naming and documentation for error behaviour prevents caller mistakes, such as forgetting to catch a throwing function or checking for null from a function that never returns null, which are common sources of unhandled errors in larger programs.

For each function, you should test at least one success case and one failure case for each error type it can throw or return, confirming that success returns correct data and that failure produces the expected error, fallback, or message. That error-path testing, combined with success testing, gives you confidence that functions behave correctly under both normal and abnormal conditions, which is the definition of reliability: correct behaviour not just when everything works, but also when something fails.

function lowLevel(value) {
  if (value < 0) {
    throw new Error("Negative value not allowed");
  }
  return value * 2;
}

function highLevel(value) {
  try {
    return lowLevel(value);
  } catch (error) {
    return "Handled at top level: " + error.message;
  }
}

console.log(highLevel(5));
console.log(highLevel(-1));

Section 9: Returning Errors Versus Throwing Them

Returning errors versus throwing them is a design choice that affects how callers handle failures, and understanding the trade-offs helps you choose consistently for your programs. Throwing an error uses JavaScript's exception mechanism, which unwinds the call stack until a catch block is found, skipping intermediate code and forcing handling, which is powerful for serious failures that should not be ignored. Returning an error, typically as an object with a success flag or an error field, or as a null value with a separate error indicator, uses normal return flow, which callers must explicitly check, but which allows multiple errors to be collected, allows failures to be treated as normal outcomes, and avoids the performance and control-flow complexity of exceptions. Each approach has strengths, and the best programs use both, choosing based on whether a failure is exceptional or expected.

Throwing is best for exceptional conditions that are unexpected, that break invariants, or that should not be ignored, such as a function receiving invalid arguments that it cannot proceed with, a required resource being missing, or an operation failing in a way that leaves state inconsistent. In those cases, forcing callers to handle the failure, by catching or propagating, is desirable, because ignoring such failures would lead to wrong results or corrupted state that is worse than a visible error. Throwing also simplifies code for the success path, because success code does not need to check for errors after every call; it can assume success until an exception interrupts it, which makes success logic cleaner and easier to read, especially for sequences of operations where any step could fail.

Returning errors is best for expected failures that are part of normal flow, such as validation results where multiple field errors need to be reported together, search results where no matches is a valid outcome, or operations where callers need to decide based on error details without exception overhead. Returning errors also works well for functions that are called in performance-critical loops, where throwing exceptions for common cases would be slower than returning error values, although that performance difference is rarely significant for most applications. More importantly, returning errors makes failures explicit in the function's return type, so callers can see from the function's signature or documentation that it can return an error, and they are reminded to check for it, whereas throwing is less visible in the signature and can be forgotten, leading to unhandled exceptions.

A hybrid approach, used by many modern libraries, is to return a result object that contains either a value or an error, such as {ok: true, value: data} on success and {ok: false, error: message} on failure, which combines explicitness with the ability to handle errors without exceptions. That result-object pattern is verbose, because callers must check ok before using value, but it is explicit and safe, because failures cannot be ignored silently; a caller that forgets to check ok will find value undefined, which is a visible bug, rather than a hidden exception that might be caught elsewhere. That pattern is popular in languages with explicit error handling, and it appears in JavaScript libraries as well, especially for operations where failures are common and need detailed handling, such as validation or file operations.

function divideReturning(a, b) {
  if (b === 0) {
    return { ok: false, error: "Cannot divide by zero" };
  }
  return { ok: true, value: a / b };
}

console.log(divideReturning(10, 2));
console.log(divideReturning(10, 0));

Section 10: Errors in Async Code Revisited

Errors in async code follow the same principles as errors in synchronous code, but with additional considerations due to promises, timing, and the fact that async failures travel as rejections rather than as immediate throws. In an async function, a thrown error becomes a rejected promise returned by that function, which callers must handle with try and catch inside another async function, or with catch on the returned promise. If neither handling occurs, the rejection becomes unhandled, which browsers and Node report as an unhandled rejection, often with a warning or a crash, depending on environment and configuration. That unhandled rejection behaviour is the async equivalent of an uncaught synchronous throw, and it should be treated with the same seriousness: every async function call that could reject should be awaited in a try block or have a catch handler attached, without exception.

A common async error mistake is forgetting to await a promise that rejects, leaving its rejection unhandled even though the code appears to handle errors elsewhere. For example, calling an async function without await and without catch, inside a try block, will not catch its rejection, because the try block completes before the async function rejects, and the rejection occurs after the try block has already exited. That timing mismatch, try completes before async failure, is a subtle bug that catches many beginners, because synchronous intuition suggests that try should catch any error from code inside it, regardless of timing, but async errors respect timing: try only catches errors that occur synchronously inside it or that are awaited inside it. The fix is to always await async calls inside try, or to attach catch directly to the promise, ensuring that the error handling is connected to the async operation's timeline, not just to its call site's synchronous timeline.

Another async error consideration is error handling in parallel groups, where Promise.all rejects on the first failure, discarding other results, while Promise.allSettled reports each result's success or failure separately, as discussed in earlier chapters. Choosing between those behaviours for error handling is a design decision: use all when every result is required and any failure should abort the whole group, and use allSettled when partial results are useful and failures should be handled per item. That choice affects how errors propagate: with all, a single failure becomes the group's failure, while with allSettled, failures become data to be inspected, not exceptions to be caught, which changes the handling code from try and catch to result status checking. Understanding that difference helps you design parallel error handling that matches user needs, whether they need all-or-nothing or partial success.

That guarantee is especially important for async code, because async operations take time, during which users might navigate away, cancel, or trigger other actions, and cleanup must happen regardless of how the async operation ends, including cancellation via AbortController, which causes a rejection that finally still handles. Designing async functions with try, catch, and finally, where catch handles errors and finally handles cleanup, gives you a robust structure that works for both success and failure, for both fast and slow operations, and for both normal completion and cancellation.

async function flakyAsync(shouldFail) {
  await new Promise((resolve) => setTimeout(resolve, 100));
  if (shouldFail) {
    throw new Error("Async failure");
  }
  return "Async success";
}

async function handleAsync() {
  try {
    const result = await flakyAsync(true);
    console.log(result);
  } catch (error) {
    console.log("Caught async: " + error.message);
  }
}

Section 11: Unhandled Errors and What They Do

Unhandled errors are errors that occur without any catch block to handle them, and their effects depend on where they occur and on the environment. In a browser, an uncaught synchronous error stops the current script execution, logs the error to the console, and may leave the page in a partially updated state, with some interface changes applied and others missing. It does not necessarily crash the whole page, because other scripts and event handlers can still run, but it does leave the feature that failed in an inconsistent state, which users may experience as a button that stops working or a form that never submits. In Node.js, an uncaught error typically crashes the process, because there is no page to leave partially working; the program exits with an error code, which is appropriate for a server that should not continue in an unknown state, but which requires careful handling to avoid downtime.

Unhandled promise rejections are the async equivalent, and their handling has evolved over time. In browsers, an unhandled rejection triggers an unhandledrejection event on window, logs a warning to the console, and in some configurations, may be treated as a serious error. In Node.js, unhandled rejections historically warned but allowed the process to continue, while modern Node versions crash the process by default, treating unhandled rejections as fatal, because continuing after an unknown async failure is risky. That evolution toward crashing reflects a consensus that unhandled errors should not be ignored silently, because they indicate a bug or a missing handling path that should be fixed, not tolerated. As a developer, you should treat every unhandled error warning as a bug to fix, by adding appropriate handling, rather than as noise to ignore, because warnings that are ignored tend to accumulate and hide real problems.

Preventing unhandled errors starts with the disciplines already discussed: always await async calls inside try blocks or attach catch handlers, always validate inputs before risky operations, and always handle errors at the highest level where user context exists, even if lower levels propagate them. A last line of defence is a global error handler, such as window.onerror for synchronous errors and window.addEventListener for unhandledrejection for async errors in browsers, or process handlers in Node, which can log unhandled errors, show a generic user message, and report them for fixing, even when specific handling was missed. Global handlers should not be used as a substitute for specific handling, because they lack context to recover gracefully, but they are valuable as a safety net that ensures no error goes completely unreported, and that users see a message rather than a silent failure when specific handling fails.

Read the stack trace, locate the failing code, determine whether the error should have been handled locally with a fallback, propagated to a higher handler with context, or prevented with validation, and then add the appropriate handling. That fixing process, unhandled error to handled error, is a normal part of development, and it improves your program's reliability with each iteration. Over time, as you add handling for each unhandled error you encounter, your program will have fewer unhandled errors, not because errors stop occurring, but because they are handled in the right places, which is the goal of error handling in general.

Section 12: Debugging with Stack Traces

Stack traces are the primary tool for debugging errors, because they show the path your program took to reach the failure, including function names, file names, and line numbers for each call in the chain. When an error is thrown, JavaScript captures the current call stack, which is the sequence of function calls that are currently active, from the function where the error occurred, back through its callers, to the top-level code that started the chain. Reading that stack from top to bottom tells you where the error happened first, and how the program got there, which is often more informative than the error message alone, because it reveals the context and the sequence of decisions that led to failure, not just the final failure itself.

Reading a stack trace effectively involves focusing on your own code first, ignoring library and runtime frames that are less relevant to your bug. The top frame is usually where the error was thrown, which is the immediate cause, while the frames below it show callers, which may reveal why the throwing function was called with problematic inputs, or why it was called at all in that context. For example, if a function throws because it received undefined, the stack trace's caller frames will show which function passed undefined and why, which is the root cause, while the throwing function's frame alone only shows the symptom. That root cause analysis, following the stack from symptom to source, is the core of stack trace debugging, and it requires looking beyond the top frame to understand the full call chain.

Async stack traces, as discussed earlier, include async frames that show where async calls originated, even though the functions that started them may have already returned by the time the error occurs. Modern JavaScript engines preserve async stack information, linking an awaited promise's rejection back to the async function that awaited it, and to the caller that started that function, creating a coherent async call chain that resembles a synchronous stack. That async stack preservation is a significant improvement over older JavaScript, where async errors lost their origin, making them hard to debug. When you read an async stack trace, look for async markers and for your async function names in the chain, which will guide you to the await point where the failure occurred and to the code that initiated the async work.

Practical stack trace debugging also involves reproducing the error reliably, so that you can inspect the stack under controlled conditions, with breakpoints or logs at key frames. Setting a breakpoint at the throwing line, or at a caller frame, allows you to inspect variables at that point, confirming hypotheses about why inputs were wrong or why state was inconsistent. Without reproduction, stack traces from production logs are still useful, because they show the failure path, but they lack live variable inspection, so you must infer variable values from code and from logged context. Adding contextual logging, such as logging inputs before risky operations, complements stack traces by providing variable values that stack traces alone do not include, making production debugging more effective even without live breakpoints.

Section 13: Logging Errors Usefully

Logging errors usefully means recording enough information for developers to diagnose and fix a problem, without recording so much that logs become noisy, slow, or privacy-violating. A useful error log includes the error's name, message, and stack trace, the time it occurred, the context in which it occurred, such as the function name, user action, or request details, and any relevant input values that help reproduce the problem, such as ids or parameters, but not sensitive values such as passwords, tokens, or personal data that should not appear in logs. That balance, detailed enough to debug and safe enough to protect privacy, is the core of useful logging, and it requires thought about what information is truly needed for diagnosis versus what is merely convenient to log in full.

Log levels help organise error logging by severity. Error level is for failures that prevent a feature from working and need fixing, such as a failed save or a crashed function. Warning level is for problems that did not prevent success but indicate a potential issue, such as a deprecated API use, a retry that succeeded after initial failure, or a fallback that was used. Info level is for normal operations, such as a successful save, which are useful for tracing user journeys but not for diagnosing failures. Debug level is for detailed diagnostic information, such as intermediate values, which is useful during development but too verbose for production. Using levels consistently allows developers to filter logs by severity, focusing on errors when investigating a problem, without wading through info and debug noise, which is essential when logs contain thousands of entries from many users.

Structured logging, where log entries are objects with fields such as timestamp, level, message, error name, and context, rather than free-form strings, makes logs searchable and analysable, especially in production systems where logs are collected centrally and queried. For example, a structured log entry might be {level: "error", message: "Failed to load user", userId: 7, error: "Network timeout"}, which can be searched by userId, filtered by level, and aggregated by message, revealing patterns such as which users or which operations fail most often. Free-form log strings, such as Failed to load user 7: Network timeout, are readable for humans but harder to query systematically, because they require text parsing to extract fields. For beginners, structured logging can be as simple as logging an object with consistent fields, rather than a concatenated string, which is a small change that greatly improves log usefulness as programs grow.

In Node, logs go to files or to centralised logging services, where they persist and can be analysed over time. For production applications, using an error reporting service that collects errors from clients, groups them by type, and alerts developers to new or frequent errors, is more effective than relying on console logs alone, because it ensures that errors users encounter are actually seen and fixed, rather than disappearing when users close their browsers. That production logging infrastructure is beyond beginner scope to build, but knowing it exists helps you understand why development console logging is only the first step in useful error logging.

Section 14: Errors in Loops and Batches

Errors in loops and batches present a special challenge, because a single failing item should not necessarily abort the entire loop, and the handling strategy depends on whether items are independent or dependent. For independent items, such as processing a list of files or records where each item's success does not depend on others, a failing item should be logged, recorded in a failures list, and skipped, allowing the loop to continue with remaining items and to report a summary at the end, such as Processed 9 of 10 items, 1 failed. That partial success handling, with per-item try and catch inside the loop, is the standard for batch processing, because it maximises useful work even when some items fail, and it gives users a complete report rather than stopping at the first failure and leaving remaining items unprocessed. For dependent items, where each item depends on previous items, a failure should stop the loop, because continuing would be incorrect or unsafe, and the error should propagate to the caller for handling at the batch level.

Implementing per-item error handling in a loop involves placing try and catch inside the loop body, around the processing of each item, rather than outside the loop, where a single catch would abort the loop on first failure. Inside the loop, catch should log the item and error, push the failure to a failures array, and continue to the next iteration, either explicitly with continue or by simply reaching the end of the catch block and looping naturally. After the loop, you can check the failures array: if it is empty, the batch succeeded fully; if it contains some failures, you can report partial success with details; if it contains all failures, you can report total failure. That post-loop summary, based on successes and failures collected during the loop, gives callers and users a clear picture of batch outcomes, which is far more informative than a simple success or failure boolean that hides partial results.

For async loops, per-item handling follows the same pattern, with await inside try inside the loop for sequential processing, or with Promise.allSettled for parallel processing, where each item's result status is inspected after all complete. That parallel batch handling, with allSettled, is the async equivalent of per-item try and catch in a sequential loop, because it allows independent async items to succeed or fail individually without aborting the group. Choosing between sequential per-item handling and parallel allSettled handling depends on whether items can run concurrently safely, as discussed for loops generally, but the error handling principle is the same: independent items should be handled individually, with failures recorded rather than aborting the batch, unless the batch requires all items to succeed for correctness.

function processBatch(items) {
  const successes = [];
  const failures = [];
  for (const item of items) {
    try {
      if (item === "bad") {
        throw new Error("Bad item");
      }
      successes.push(item);
    } catch (error) {
      failures.push({ item: item, error: error.message });
    }
  }
  console.log("Successes: " + successes.length + ", Failures: " + failures.length);
  console.log(failures);
}

Section 15: Fail Fast Versus Fail Gracefully

Fail fast and fail gracefully are two opposing strategies for handling errors, and choosing between them depends on the nature of the failure and the context in which it occurs. Fail fast means detecting an error as soon as possible and stopping immediately, with a clear error, rather than continuing with invalid or incomplete data that could cause worse problems later. That strategy is appropriate for programming errors, invalid inputs to critical functions, and situations where continuing would corrupt data, violate invariants, or produce misleading results that are worse than a visible failure. For example, a function that calculates a payment total should fail fast if it receives invalid prices, rather than calculating a wrong total that could charge users incorrectly, because a wrong total is far more harmful than a visible error that prevents charging until prices are fixed.

Fail gracefully, by contrast, means handling an error by degrading functionality, using fallbacks, or showing partial results, rather than stopping completely, so that users can continue using the parts of a program that still work, even when one part fails. That strategy is appropriate for non-critical features, such as a dashboard section that fails to load, a recommendation feature that is unavailable, or a non-essential image that fails to display, where stopping the entire application for a minor failure would be disproportionate and frustrating. Graceful degradation, as discussed for partial failures, allows a program to remain useful under imperfect conditions, which is especially important for user-facing applications where availability and partial functionality are valued more than perfect correctness for every feature, as long as critical features remain correct.

The key to choosing between fail fast and fail gracefully is to assess the severity and scope of the failure. If a failure affects critical data integrity, security, or correctness, fail fast, because continuing could cause harm that outweighs the inconvenience of stopping. If a failure affects only a non-critical feature, a display enhancement, or an optional data source, fail gracefully, because users can still accomplish their main goals without that feature, and stopping everything for it would be excessive. That severity assessment should be made deliberately for each feature and each error type, not by defaulting to one strategy for all errors, because a program that fails fast for everything will feel brittle and frustrating, while a program that fails gracefully for everything may hide serious bugs and data corruption behind partial functionality that looks normal but is actually wrong.

In practice, many programs use both strategies in different layers: low-level functions fail fast on invalid inputs, to catch bugs early and prevent corrupted state, while high-level user interfaces fail gracefully for non-critical failures, to keep users productive. That layered combination, fail fast low and fail gracefully high, gives you the benefits of both: bugs are caught early where they originate, while users experience resilience where it matters most, at the interface level. For example, a data validation function might fail fast on invalid data, throwing an error that a higher-level loader catches and handles gracefully by showing a warning and using cached data, rather than crashing the page. That combination shows that fail fast and fail gracefully are not mutually exclusive, but complementary strategies applied at different levels of a program's architecture.

Section 16: Guard Clauses to Prevent Errors

Guard clauses are early checks at the start of a function that validate inputs and preconditions, returning early or throwing immediately if those checks fail, before the main logic runs. They prevent errors by ensuring that the main logic only runs with valid, expected inputs, rather than trying to handle invalid inputs throughout the logic with nested conditionals. For example, a function that processes a user object might start with if (!user) throw new Error("User is required");, which guards against null users before any property access that would otherwise throw a TypeError. That early guard is clearer than wrapping the entire function body in an if (user) block, because it keeps the main logic at the top level, without extra indentation, and it makes the function's requirements explicit at the start, where readers can see them immediately.

Guard clauses improve readability by reducing nesting and by separating validation from logic. Without guards, a function that checks multiple conditions might nest its main logic inside several if blocks, creating a pyramid of indentation that is hard to follow. With guards, each invalid condition is handled at the top with an early return or throw, and the main logic follows at the top level, flat and easy to read, because readers know that by the time they reach the main logic, all guards have passed and inputs are valid. That flat structure is a hallmark of well-written functions, and it is especially valuable for functions with many inputs or preconditions, where nested validation would otherwise obscure the main purpose of the function.

Guard clauses also improve debugging, because failures happen at the guard, with a clear message about which precondition failed, rather than deep inside main logic where an invalid input causes a confusing secondary error. For example, if a function receives a negative age and guards against it at the start with a clear message, the error points directly to the invalid input, whereas without a guard, the negative age might cause a later calculation to produce a nonsensical result, such as a negative discount, which is harder to trace back to the original invalid input. That early, clear failure, like fail fast generally, makes bugs easier to locate and fix, because the error occurs close to its cause, both in code location and in time, rather than propagating through layers of logic before manifesting as a symptom far from its source.

Writing effective guard clauses involves checking the most important preconditions first, such as required arguments being present, types being correct, and values being within allowed ranges, and using clear messages that state the requirement and the actual value received, such as Age must be a non-negative number, got -5. Guards should be concise and focused, checking one condition per guard, rather than combining many conditions into a single complex check that is hard to understand and whose failure message cannot pinpoint which condition failed. That one-condition-per-guard discipline makes guards easy to read, easy to test, and easy to adjust when requirements change, because each guard can be modified or removed independently without affecting others.

  if (!user) {
    throw new Error("User is required");
  }
  if (typeof user.age !== "number" || user.age < 0) {
    throw new Error("Age must be a non-negative number");
  }
  if (!user.name || user.name.trim() === "") {
    throw new Error("Name is required");
  }
  return "User created: " + user.name;
}

Section 17: Defensive Checks Before Risky Work

Defensive checks before risky work are similar to guard clauses, but applied more broadly to any operation that could fail due to external conditions, not just function inputs. Examples include checking that a file exists before reading it, that a network connection is available before fetching, that an element exists in the page before updating it, or that a value is of the expected type before calling a method on it. Those checks prevent errors by verifying preconditions for risky operations, rather than relying on try and catch to handle failures after they occur. While try and catch is essential for handling unexpected failures, defensive checks are better for expected, checkable conditions, because they allow you to handle the condition gracefully before attempting risky work, with a clear message or fallback, rather than letting the risky work fail and then recovering, which may be less efficient or less clear.

The difference between defensive checks and try and catch is one of intent and efficiency. Defensive checks are for conditions you can test cheaply before acting, such as whether a variable is null, whether an array is empty, or whether a string matches a pattern. Try and catch is for conditions you cannot test cheaply, or for failures that are genuinely unpredictable, such as network failures, server errors, or race conditions where a condition changes between checking and acting. Using defensive checks for checkable conditions and try and catch for unpredictable failures gives you the best of both: efficient, clear handling for known conditions, and robust handling for unknown failures, without overusing either approach. Overusing defensive checks for unpredictable failures leads to race conditions, where a check passes but the operation still fails because conditions changed, while overusing try and catch for checkable conditions leads to verbose exception handling for simple cases that a single if check could handle more clearly.

A practical guideline is to use defensive checks for input validation, for null and type checks, and for state checks such as whether a feature is enabled or whether data is loaded, and to use try and catch for I/O operations, such as fetching, file reading, and parsing, where failures are external and unpredictable. That guideline, checks for inputs and state, try for I/O, covers most cases and keeps code balanced: input handling is explicit and clear, while I/O handling is robust against external variability. As you gain experience, you will refine that guideline for specific contexts, such as using try for parsing even though it is checkable in theory, because parsing is complex and try is simpler than manual syntax checking, which shows that guidelines are starting points, not rigid rules, and that judgement matters for each operation's characteristics.

    return "Anonymous";
  }
  return user.name;
}

Section 18: Handling Missing Data Errors

Missing data errors occur when code expects a value to exist but finds undefined, null, or a missing field, and handling them well requires distinguishing between data that is required and data that is optional, because required missing data is a serious failure while optional missing data is a normal case that deserves a fallback. For required data, such as a user id needed to load a profile, missing data should be treated as an error, with a clear message and a halt to the operation that needs it, because proceeding without required data would produce wrong results or crash later with a confusing error. For optional data, such as a user's nickname or profile picture, missing data should be handled with a fallback, such as Anonymous or a default image, allowing the operation to continue normally, because the missing value does not prevent the main task from succeeding. That required versus optional distinction is the key to missing data handling, and it should be made explicitly for each field, rather than treating all missing data identically.

Techniques for handling missing data include optional chaining and nullish coalescing for safe access with fallbacks, as discussed earlier, validation at boundaries to catch required missing data early with clear errors, and default parameters or default values in functions to provide fallbacks for missing arguments. For example, a function that displays a user might use user?.nickname ?? "No nickname" for optional nickname, while a function that loads a user by id might throw if id is missing, because it cannot proceed without it. Those techniques, used together, give you a complete missing data toolkit: validation for required, fallbacks for optional, and safe access for nested data where any level might be missing. Applying the right technique to each field, based on whether it is required or optional, prevents both crashes from required missing data that was treated as optional, and unnecessary errors from optional missing data that was treated as required.

Missing data can also arise from API changes, where a field that used to exist is removed or renamed in a new version, causing old code that expects it to fail. Handling API evolution gracefully involves versioning, as discussed for stored data, and defensive coding that does not assume fields will always exist, even if they do today. For example, if an API might rename a field in the future, your mapping code should handle both old and new names, or should use fallbacks that work with either, rather than hard-coding a single field name that will break on rename. That forward-compatible handling, anticipating change rather than assuming stability, is a professional habit for API consumers, because APIs do evolve, and code that handles evolution gracefully will continue working through changes that break brittle code that assumes a fixed shape forever.

function displayUser(user) {
  if (!user || user.id === undefined) {
    throw new Error("User id is required");
  }
  const nickname = user.nickname ?? "No nickname";
  return "User " + user.id + ": " + nickname;
}

console.log(displayUser({ id: 2 }));

Section 19: Handling Type Errors

Type errors occur when code tries to perform an operation on a value of the wrong type, such as calling a string as a function, reading a property from null, or using a number where an array is expected, and handling them well requires both prevention through validation and recovery through catching and fallbacks. Prevention involves checking types before operations that require specific types, such as using typeof to confirm a value is a function before calling it, Array.isArray to confirm a value is an array before mapping over it, or typeof to confirm a value is a string before calling string methods on it. Those checks, placed before risky operations, prevent TypeErrors from occurring in the first place, which is preferable to catching them after they occur, because prevention gives you control over the error message and fallback, while catching after the fact must deal with a failure that has already interrupted normal flow.

When a TypeError does occur despite prevention, catching it should focus on diagnosing the type mismatch and providing a helpful message, rather than silently continuing with wrong types that could cause further errors. For example, if a function expects an array but receives a string, catching the resulting TypeError and logging Expected array but got string, with the actual value's type, helps developers fix the caller that passed the wrong type, whereas swallowing the error and returning an empty array might hide the caller bug and cause the program to display wrong data without any indication that input was wrong. That diagnostic focus, logging expected versus actual type, is important for TypeErrors, because they often indicate bugs in calling code, not just data problems, and hiding them can allow bugs to persist and cause larger failures later, when wrong types propagate through more code before finally causing a visible failure far from their source.

Type errors also arise from API and JSON data where types are not guaranteed, as discussed for validation, because JSON numbers can arrive as strings, booleans as strings, or arrays as single objects, depending on server implementation or version changes. Handling those cases involves normalising types after validation, such as converting string numbers to numbers with explicit conversion, or wrapping single objects in arrays when an array is expected, with clear rules for when such normalisation is safe versus when it masks a real data problem that should be reported. For example, converting a string "42" to number 42 is usually safe, because the intent is clear, while converting an object to an array by wrapping it might hide a server bug where an array was expected but an object was sent for a different reason, such as an error object instead of a list. That normalisation judgement, safe conversion versus masking bugs, requires understanding the data source and its likely variations, and it should be made deliberately for each type mismatch you handle, not by applying blanket coercion to all mismatched types.

Section 20: Handling Range and Reference Errors

Range errors and reference errors are two specific built-in error types that indicate different kinds of problems, and handling them specifically helps you diagnose and fix their causes. RangeError occurs when a value is outside an allowed range, such as an array length set to a negative number, a number passed to a function that only accepts values within a range, or a recursive function that exceeds the call stack limit, which also manifests as a RangeError with a message about maximum call stack size exceeded. ReferenceError occurs when code tries to use a variable or function that does not exist, such as a typo in a variable name, a variable used before declaration in a temporal dead zone, or a variable that was never defined because of a scope mistake. Those two error types, range versus reference, point to very different bugs: range errors point to value problems, while reference errors point to naming and scope problems, and handling them differently helps you fix the right cause.

Range errors for values, such as invalid array lengths or out-of-range numbers, should be prevented with validation, checking that values are within allowed ranges before using them, and throwing a RangeError with a clear message if they are not, as with other validation. For example, a function that sets a page size should validate that the size is a positive integer within a maximum, throwing a RangeError if it is not, rather than allowing an invalid size to cause a later failure when it is used to slice an array or to make a request with an invalid limit parameter. That early range validation, like other guard clauses, makes range errors explicit and local, rather than letting invalid ranges propagate into calculations or API calls where they cause confusing secondary failures.

Range errors for call stack overflow, which occur with infinite or excessively deep recursion, are a special case that requires a different fix: identifying and correcting the recursion logic, such as adding a base case, limiting depth, or converting recursion to iteration, rather than simply catching the error and continuing, because a stack overflow indicates a fundamental logic problem that catching alone cannot fix. Catching a stack overflow and continuing might allow the program to proceed, but it will likely overflow again on the next recursive call, because the underlying infinite recursion remains. That is why stack overflow errors should be treated as bugs to fix at the source, not as runtime conditions to handle gracefully with fallbacks, except in rare cases where deep recursion is expected and needs to be limited with explicit depth checks before recursing.

Catching ReferenceErrors and continuing as if nothing happened would hide bugs and allow programs to run with incorrect logic, producing wrong results without any indication that a variable was misspelled. The correct handling for ReferenceErrors is to let them surface during development, fix the typo or scope issue, and use tools such as linters and type checkers to catch them before runtime, rather than writing catch blocks that swallow them. That fix-at-source approach, for reference errors specifically, reflects the principle that some errors are bugs that should be fixed, not conditions to be handled, and distinguishing those errors from handleable conditions is a key judgement in error handling design.

function setPageSize(size) {
  if (typeof size !== "number" || size < 1 || size > 100) {
    throw new RangeError("Page size must be between 1 and 100");
  }
  return "Page size set to " + size;
}

Section 21: Custom Error Classes

Custom error classes allow you to define your own error types for specific failures in your program, with names, properties, and behaviours tailored to your domain, rather than relying solely on built-in Error types that are generic. To create a custom error class, you extend the built-in Error class, define a constructor that calls super with a message, sets the name property to the custom class name, and optionally adds custom properties such as a code, a field, or a status. For example, a ValidationError class might carry a field property naming the invalid field, while a NotFoundError class might carry a resource id, allowing catch blocks to handle those errors specifically by checking instanceof, and to access their custom properties for tailored messages and recovery. That specificity, custom types with custom data, makes error handling more precise and more expressive than generic Error objects with only messages.

Using custom error classes improves code readability and maintainability, because error types become part of your program's vocabulary, describing failures in domain terms that other developers understand, such as ValidationError, AuthenticationError, or PaymentError, rather than generic Error with messages that must be parsed to understand the failure kind. When a catch block checks error instanceof ValidationError, its intent is clear: it handles validation failures specifically, while other errors propagate. When a function throws a NotFoundError, its documentation can state that it throws NotFoundError for missing resources, which is clearer than stating that it throws Error with a message containing not found. That clarity, through named types, is a form of self-documenting code that helps teams collaborate, because error types communicate failure semantics without requiring readers to inspect message strings or implementation details.

Custom error classes also enable consistent error handling across a codebase, because all instances of a given custom error share the same name, structure, and properties, making it easy to write handlers that work for all occurrences of that error type, regardless of where they originate. For example, a global handler for ValidationError can display field-specific messages for any validation failure in the program, without needing to know which function threw it, because all ValidationErrors carry a field property in the same format. That consistency, enforced by the class definition, prevents the fragmentation that occurs when different functions throw generic Errors with different message formats for the same kind of failure, forcing handlers to parse messages or handle each function's errors separately. Centralising error definitions in custom classes therefore simplifies handling and improves consistency, especially in larger programs with many features that share failure types.

In modern JavaScript, the pattern class ValidationError extends Error { constructor(message, field) { super(message); this.name = "ValidationError"; this.field = field; } } works correctly, preserving stack traces and instanceof behaviour, and it is the standard pattern you should use. Testing custom errors involves checking that they are instances of both the custom class and Error, that their name and message are correct, and that their custom properties are set, confirming that the subclassing pattern works as expected in your environment before relying on it in production code.

Section 22: Error Codes for Programmatic Handling

Error codes are short, stable identifiers attached to errors, such as NOT_FOUND, VALIDATION_FAILED, or RATE_LIMITED, that allow programs to handle errors programmatically, by checking codes rather than parsing human-readable message strings. Messages are for humans: they explain failures in plain language, they may change wording over time, and they may be localised into different languages, making them unreliable for code to check. Codes are for machines: they are stable, language-independent, and easy to compare with equality checks, making them reliable for branching logic, such as if (error.code === "NOT_FOUND") showNotFound(); else if (error.code === "RATE_LIMITED") retryLater();. That separation, messages for humans and codes for machines, is a fundamental principle of robust error design, because it prevents handling logic from breaking when message wording changes, and it allows messages to be improved for users without affecting code that handles errors.

Designing good error codes involves choosing names that are clear, consistent, and granular enough to distinguish failures that need different handling, but not so granular that handlers must check dozens of codes for similar failures. For example, distinguishing NOT_FOUND from VALIDATION_FAILED is useful, because those failures need different user actions, while distinguishing every possible validation failure with a separate code for each field might be excessive, because field-specific handling can use a field property alongside a general VALIDATION_FAILED code, rather than a separate code per field. That balance, codes for handling categories and properties for details, gives you both programmatic branching and detailed information, without code explosion. Codes should also be documented, with a list of possible codes for each function or API, so that callers know which codes to expect and how to handle each, which is essential for API consumers who cannot inspect server code to discover codes by trial and error.

Error codes are especially important for APIs, where clients in different languages need to handle server errors consistently, without parsing English messages that might change or be translated. A REST API that returns a JSON error body with a code field, such as {code: "USER_NOT_FOUND", message: "User 7 was not found"}, allows clients to branch on code reliably, while still showing the message to users in a friendly form. That API error design, code plus message, is standard practice for professional APIs, and it mirrors the custom error class design for local code, where code properties complement messages. When you consume an API, you should check its error codes first, before falling back to status codes or messages, because codes are the most specific and stable identifier of failure kind that the API provides, and they often distinguish failures that share the same HTTP status, such as different validation failures that all return four hundred.

The custom class approach is cleaner, because it ensures that every instance of that error type carries the correct code, while the ad-hoc property approach is more flexible for one-off errors but risks inconsistency if different code paths set codes differently for the same failure kind. Whichever approach you choose, consistency is key: the same failure kind should always carry the same code, regardless of where it occurs, so that handlers can rely on codes without needing to know the failure's origin, which is the whole point of codes as a stable contract between error producers and error consumers.

Section 23: Retrying After Errors

Retrying after errors, as introduced for async and fetch work, is a general error recovery strategy that applies to many kinds of operations, not just network requests, and it requires careful design to be effective without causing harm. The basic retry pattern, try an operation, and if it fails with a retriable error, wait briefly and try again, up to a maximum number of attempts, works for transient failures such as temporary network glitches, brief server overloads, or file locks that clear quickly, where a later attempt is likely to succeed even though an earlier attempt failed. It does not work for permanent failures such as invalid input, missing resources, or bugs, where repeating the same operation will fail the same way every time, wasting time and resources, and potentially causing side effects if the operation is not idempotent, meaning safe to repeat without duplicating its effect. Distinguishing retriable from non-retriable errors, as discussed for fetch, is therefore the first step in designing retry logic for any operation.

Retry design also involves choosing the number of attempts, the delay between attempts, and whether delays should increase with each attempt, known as backoff, as discussed earlier. For most operations, three to five attempts with exponential backoff, starting with a short delay and doubling each time, is a reasonable starting point that balances recovery chance against user waiting time and server load. For operations where user waiting time is critical, such as interactive searches, fewer attempts with shorter delays may be better, because users prefer a quick failure with a manual retry option over a long automatic retry sequence that locks the interface. For background operations where users are not waiting, such as sync jobs, more attempts with longer delays may be appropriate, because there is no user waiting to be frustrated by delay, and recovery is more valuable than speed. Those context-dependent choices, attempts and delays tuned to operation type and user expectations, show that retry design is not one-size-fits-all, but a judgement based on failure characteristics and user experience.

Retrying non-idempotent operations, such as payments, order creation, or other writes that change state, requires special care, because a retry after a failure where the first attempt actually succeeded but its response was lost could create duplicates, such as charging a user twice or creating two orders for one request. To retry such operations safely, you need idempotency mechanisms, such as unique request ids that the server uses to detect duplicate requests and return the original result instead of performing the operation again, or explicit checks before retrying, such as checking whether an order already exists before creating a new one. Without idempotency, retrying writes is dangerous and should be avoided, with failures instead reported to users for manual follow-up, rather than automatically retried in hopes that duplication will not occur. That safety consideration, idempotency before retry for writes, is one of the most important lessons in retry design, because duplicate side effects can be far more harmful than a single failed operation that users can retry manually with awareness.

function delay(ms) {
  return new Promise((resolve) => setTimeout(resolve, ms));
}

async function retryTask(task, attempts, isRetriable) {
  for (let i = 1; i <= attempts; i++) {
    try {
      return await task();
    } catch (error) {
      if (i === attempts || !isRetriable(error)) {
        throw error;
      }
      await delay(100 * i);
    }
  }
}

Section 24: Fallback Values After Errors

Fallback values are safe, default values used when an operation fails, allowing a program to continue with degraded but usable data instead of crashing or showing nothing, and they are a key technique for graceful degradation. For example, if loading a user's profile picture fails, a fallback might be a default avatar image, allowing the profile page to display with a generic picture instead of a broken image or a blank page. If loading a list of recommendations fails, a fallback might be an empty list with a message, or a cached list from a previous load, allowing the main content to display while recommendations are hidden or marked as unavailable. Those fallbacks, chosen per feature and per failure type, turn failures from blocking problems into minor degradations that users can tolerate, often without even noticing that a fallback was used, if the fallback is well-designed and honest about its nature, such as labelling cached data as cached rather than pretending it is fresh.

Choosing appropriate fallbacks requires understanding what data is essential versus optional, and what fallback would be safe and honest for each case. For essential data, such as a user's account balance or a document's content, there is often no safe fallback, because showing a wrong or outdated value could mislead users into making decisions based on incorrect information, such as spending money they do not have or editing an outdated document version. In those cases, failing visibly with an error message is safer than showing a fallback that looks correct but is actually wrong, because honesty about failure is better than misleading success. For optional data, such as recommendations, images, or secondary statistics, fallbacks are usually safe, because their absence or replacement with defaults does not prevent users from accomplishing their main goals, and showing a fallback is better than blocking the entire feature for a minor data failure. That essential versus optional distinction, like required versus optional for missing data, guides fallback choices and prevents the dangerous practice of using fallbacks for critical data where accuracy matters more than availability.

Implementing fallbacks typically involves catching an error and returning a fallback value in the catch block, rather than rethrowing, which is a deliberate decision to handle the failure locally and continue, rather than propagating it for higher-level handling. That local handling should be documented, so that callers know that a function returns fallbacks on failure instead of throwing, because callers that expect throwing might miss the fact that a returned value is a fallback, not fresh data, and might treat it as accurate when it is actually a default or cached value. To make fallbacks transparent, you can return fallback values with a flag indicating that they are fallbacks, such as {data: fallback, fromCache: true}, or you can log fallback use for developers, while showing users a subtle indicator that data is cached or default, rather than fresh. That transparency, for both code and users, prevents fallbacks from becoming silent misleading data, which would erode trust when users discover that displayed data was not what it appeared to be.

    console.log("Using fallback after error: " + error.message);
    return fallback;
  }
}

Section 25: User-Friendly Error Displays

User-friendly error displays translate technical failures into interface elements that users can understand and act on, and they involve choices about message text, placement, visual design, and available actions, all of which affect how users perceive and recover from errors. A user-friendly display for a form validation error shows the message next to the relevant field, in a colour and style that indicates an error without being alarming, with a clear description of what is wrong and how to fix it, such as Password must be at least 8 characters, rather than a generic Invalid input at the top of the form that leaves users guessing which field is wrong. A user-friendly display for a feature failure, such as a failed data load, shows a banner or card in place of the missing content, with a message explaining the problem in user terms, a retry button to attempt loading again, and optionally a link to support or a way to continue with other features, rather than a blank area or a technical stack trace that users cannot act on.

Visual design for error displays should balance visibility with calmness: errors should be noticeable enough that users do not miss them, but not so alarming that they cause panic or distrust. Using a consistent error colour, such as a muted red for errors, with an icon indicating a problem, and with sufficient contrast for accessibility, helps users recognise errors quickly without feeling overwhelmed. Error messages should also be accessible to screen readers, using appropriate roles and live regions so that assistive technology announces errors when they appear, which is essential for users who cannot see visual error indicators. Those accessibility considerations, colour plus icon plus text plus screen reader announcement, ensure that error displays work for all users, not just for sighted users who can see colour changes, which is a professional standard for inclusive design that is often overlooked in error handling.

Available actions in error displays are as important as messages, because a message without an action leaves users stuck, even if they understand the problem. For validation errors, the action is to correct the field and resubmit, which should be obvious from the message and from the form's focus behaviour, such as focusing the first invalid field automatically. For load failures, the action is typically a retry button that reloads the failed data without reloading the whole page, preserving the user's place and other loaded data. For permission errors, the action might be to sign in with a different account or to contact an administrator, with links to those actions where appropriate. For system errors, the action might be to try again later, with a suggestion to check status or to contact support if the problem persists, giving users a path forward even when immediate recovery is not possible. Designing error displays with actions, not just messages, turns errors from dead ends into recoverable situations, which significantly improves user experience and reduces support contacts.

Section 26: Errors in Event Handlers

Errors in event handlers require special attention, because event handlers are called by the browser in response to user actions, and errors that escape them do not propagate to a caller that can handle them, unlike errors in functions called directly by your code. When a click handler throws, the browser logs the error and continues, but the user sees no message unless the handler itself displays one, because there is no caller waiting to catch the error and show a message. That caller-less nature of event handlers means that every async event handler, and every event handler that performs risky work, must handle its own errors internally with try and catch, displaying messages and cleaning up interface state, rather than relying on outer handlers to catch errors for them, which will not happen for events. That self-contained error handling is a fundamental rule for event-driven code, and violating it leads to silent failures where users click buttons and nothing happens, with only a console error as evidence that something went wrong.

For synchronous event handlers, errors also escape to the browser, but they are at least visible as uncaught errors in the console, and they stop the handler's remaining code, which may leave interface state inconsistent, such as a button remaining disabled or a form remaining in a submitting state. To prevent that inconsistency, event handlers should use try, catch, and finally, where finally restores interface state, such as re-enabling buttons and hiding spinners, regardless of success or failure, as discussed for async handlers earlier. That finally-based cleanup, applied to both synchronous and async handlers, ensures that interface state always returns to a usable state after an event, even when the event's work fails, which is essential for users to retry the action or to continue using other features without being trapped by a stuck interface from a failed event.

For async event handlers, error handling must also account for the timing issue discussed earlier: errors from awaited promises inside the handler are caught by try inside the handler, but errors from promises that are not awaited inside the handler, or from callbacks passed to other functions inside the handler, may escape the handler's try block and become unhandled rejections. To prevent those escapes, async handlers should await all async work inside their try blocks, or attach catch handlers to any promises they start but do not await, ensuring that every async operation initiated by an event has an error handler connected to it. That comprehensive awaiting and catching, for all async work in a handler, is more work than for synchronous handlers, but it is necessary for reliable event handling, because async work's errors do not respect the handler's synchronous boundaries unless explicitly awaited or caught.

    console.log("Click action succeeded");
  } catch (error) {
    console.log("Show user message: " + error.message);
  } finally {
    loading = false;
    console.log("Button state restored");
  }

Section 27: Errors in Fetch and Network Code

Errors in fetch and network code, as introduced in earlier chapters, deserve a dedicated review in the context of general error handling, because network errors have unique characteristics that affect handling design. Network errors are external, transient, and often outside the user's control, such as lost connections, DNS failures, server outages, or slow responses that time out, and they require handling that is patient, informative, and retry-friendly, rather than blaming users or suggesting input corrections that cannot help. That external, transient nature means that network error handling should focus on communication, explaining that the problem is with connection or server, not with user input, on patience, suggesting waiting and retrying, and on preservation, keeping user work and previously loaded data visible while network problems are resolved, rather than clearing displays and leaving users with nothing.

Distinguishing network error types, as discussed earlier, is essential for network handling: network failures where fetch rejects, HTTP errors where fetch resolves with an error status, and parsing errors where fetch succeeds but body is not valid JSON, each require different messages and actions, as covered in detail for fetch. That distinction, applied in general error handling terms, shows that network code should not have a single generic catch that treats all network failures identically, but should branch on error type and status, as with specific error handling generally, to provide tailored messages and actions for each network failure kind. For example, a network rejection should lead to a connection message, a 404 should lead to a not-found message, a 500 should lead to a server problem message with retry later, and a parsing error should lead to a data problem message with a suggestion to try again, each guiding users correctly for that specific failure, rather than a single Could not load message that hides useful distinctions.

Network error handling should also be integrated with loading states, timeouts, retries, and caching, as discussed for fetch and async work, because those patterns together form a complete network resilience strategy, not isolated techniques. Loading states communicate that work is in progress, timeouts bound waiting, retries recover from transient failures, and caching provides fallbacks when fresh data cannot be loaded, and error handling ties them together by deciding when to show errors versus when to retry, when to use cached data versus when to show an error, and when to stop retrying and report failure to users. That integrated strategy, loading plus timeout plus retry plus cache plus error display, is what makes network features feel reliable, even when networks themselves are unreliable, because users experience a program that tries, waits reasonably, falls back gracefully, and communicates clearly, rather than a program that fails immediately and silently on the first network hiccup.

Section 28: Timeouts and Errors Together

Timeouts and errors together form a combined strategy for handling slow or hung operations, where a timeout is treated as a specific kind of error that triggers recovery, rather than as a separate concern from error handling. When an operation exceeds its allowed time, you treat that as a timeout error, with a message such as Operation timed out, a suggestion to retry or to check connection, and a decision about whether to retry, to use a fallback, or to report failure, just as you would for any other error type. That unified treatment, timeout as error, simplifies handling code, because timeout errors flow through the same try and catch, logging, and display mechanisms as other errors, rather than requiring a separate timeout handling path that duplicates error logic. It also makes timeout handling testable, because you can test timeout errors like other errors, with fake slow operations that exceed a short timeout, confirming that handling produces the expected timeout message and recovery.

Implementing timeouts as errors, using Promise.race or AbortController as discussed earlier, involves racing the real operation against a timeout that rejects or aborts after a period, causing the combined promise to reject with a timeout error if the timeout wins. That race implementation must handle cleanup correctly, such as clearing the timeout timer when the real operation succeeds, to avoid leaking timers or causing a timeout error to fire after success and overwrite a successful result with a spurious timeout. That cleanup, clearing timers in finally or in success paths, is a detail that is easy to overlook but important for correctness, because a timer that fires late can cause confusing secondary errors or logs that suggest a timeout occurred even though the operation succeeded, undermining trust in logs and in error reporting. Careful timer management, create, clear on success, and handle on timeout, is therefore part of correct timeout-as-error implementation.

Choosing timeout values and retry behaviour for timeouts requires balancing user patience against operation needs, as discussed for fetch timeouts generally. For interactive operations, short timeouts with quick failure messages and manual retry options are better than long timeouts that leave users waiting without feedback, because users can decide to retry or to try a different approach sooner. For background operations, longer timeouts with automatic retries may be better, because users are not waiting and recovery is more valuable than quick failure. In both cases, timeout errors should be logged separately from other errors, so that developers can identify slow operations that frequently time out and optimise them, rather than treating timeouts as generic failures that hide performance problems. That separate logging, timeouts as a distinct error category, helps teams distinguish performance issues from correctness issues, which require different fixes: performance optimisation for frequent timeouts versus bug fixing for other errors.

Section 29: Testing Error Paths

Testing error paths means deliberately causing failures in your code and verifying that it handles them correctly, with appropriate messages, fallbacks, and state restoration, rather than only testing success paths where everything works. Error path testing is essential because error handling code is often the least tested code in a program, since developers naturally test with valid inputs and successful operations during manual exploration, and error handling code that is never tested may contain bugs that only appear in production when real failures occur, turning a recoverable failure into a secondary crash or a silent wrong result. By testing error paths systematically, with simulated failures for each error type your code can encounter, you ensure that error handling actually works when it is needed most, which is the definition of reliability: correct behaviour under failure, not just under success.

Designing error path tests involves identifying, for each function, what failures it can encounter, such as invalid inputs, missing data, network failures, or dependency errors, and then writing tests that trigger each failure and assert the expected handling, such as a specific error message, a fallback value, a logged error, or a restored interface state. For example, testing a function that loads a user should include tests for success, for not-found, for network failure, and for invalid data shape, each asserting the correct handling for that case. That failure enumeration, listing possible failures per function, is a useful design exercise in itself, because it forces you to think about failure modes before writing tests, and it often reveals handling gaps where a failure kind was not considered during implementation, which can then be fixed before testing even begins, improving design as well as test coverage.

Simulating failures for tests can be done with fake functions, mocked dependencies, or invalid inputs, as discussed for fetch and async testing earlier, without needing real failures to occur naturally. Those simulation techniques, fakes and invalid inputs, make error path testing fast, deterministic, and repeatable, which means tests can run frequently, such as on every code change, catching regressions in error handling before they reach production, which is especially important because error handling regressions are often silent, with no user-visible failure until a real error occurs and handling fails.

Those negative checks, verifying that handling does not over-handle or under-clean, are as important as positive checks that handling produces correct messages, because over-handling can hide bugs and under-cleaning can leave programs in inconsistent states that cause later failures unrelated to the original error, making debugging harder.

Section 30: Simulating Errors for Practice

Simulating errors for practice means intentionally creating failures in a safe, controlled environment, so that you can learn how your code handles them without waiting for real failures to occur naturally, which are unpredictable and often disruptive. Simulation techniques include using fake functions that throw or reject on demand, passing invalid inputs to functions, disconnecting network simulations, corrupting test data, and using timers to create timeouts, all in test code or in development experiments, rather than in production. Section 31: Errors and Data Integrity

Errors and data integrity are closely linked, because an error that occurs during a data operation can leave data in a partially updated, inconsistent state, which is often worse than a complete failure that leaves data unchanged. For example, if a function updates a user's profile in two steps, changing their name and then their email, and it fails after the first step, the profile will have a new name but an old email, which is inconsistent and may confuse users or break other code that assumes name and email change together. Preventing such partial updates requires thinking about data operations as transactions, where either all steps succeed and data changes completely, or none succeed and data remains as before, with no partial state in between. That transactional thinking, all-or-nothing for related changes, is essential for data integrity, especially for operations that involve multiple writes, multiple files, or multiple systems that must stay consistent with each other.

Achieving transactional behaviour in JavaScript often involves validating all inputs before making any changes, performing changes in memory first and only committing them to storage after all steps succeed, or using rollback logic that undoes partial changes if a later step fails. Validation before changes, as discussed for guard clauses, prevents many partial update scenarios, because invalid inputs are rejected before any data changes, so no rollback is needed. In-memory staging, where you build a new version of data in a variable, validate it fully, and then replace the old data with the new version in a single assignment, ensures that observers never see a partially updated version, because the replacement is atomic: either old data is visible or new data is visible, never a mix. That staging pattern is simple and effective for in-memory and localStorage data, where replacement is a single operation, and it is a good default for data updates that involve multiple fields.

For operations that involve external systems, such as multiple API calls that must succeed together, transactional behaviour is harder, because each API call is independent and cannot be rolled back automatically if a later call fails. In those cases, you need compensating actions, which are operations that undo previous steps, such as deleting a created resource if a subsequent step fails, or restoring previous values if an update fails midway. Designing compensating actions requires understanding each operation's inverse, such as create versus delete, or update versus restore old values, and implementing them in catch blocks that run when later steps fail. That compensation logic is more complex than simple rollback, but it is necessary for multi-system operations where consistency matters, such as creating an account and then setting up its profile, where a failure in profile setup should not leave an account without a profile, or should at least report that inconsistency clearly for manual fixing if automatic compensation is not possible.

Section 32: Cleaning Up After Errors

Cleaning up after errors means restoring a program to a consistent, usable state after a failure, including releasing resources, resetting interface states, and undoing partial changes, so that users can retry or continue using other features without being affected by the failed operation's leftovers. Cleanup tasks include closing files or connections opened before the failure, hiding loading indicators shown before the failure, re-enabling buttons disabled before the failure, clearing timers started before the failure, and removing temporary data created before the failure. Without cleanup, a failed operation can leave a program in a stuck state, such as a spinner that never hides, a button that remains disabled, or a file that remains locked, preventing users from retrying or from using other features, even though the failure itself was minor and recoverable. That stuck state, caused by missing cleanup, is often more frustrating to users than the original failure, because it blocks further action and requires a page reload or restart to clear, which loses other work in progress.

The finally block is the primary tool for cleanup after errors, because it runs whether an operation succeeds or fails, guaranteeing that cleanup code executes in both cases, as discussed in depth earlier. By placing cleanup in finally, you avoid duplicating cleanup code in success and error paths, and you ensure that cleanup is not forgotten in one path when code changes later. For example, a function that shows a spinner, tries to load data, and hides the spinner in finally, will always hide the spinner, even if loading throws, returns early, or is cancelled, which is the reliability guarantee you want for interface states. That finally-based cleanup should be written as soon as you acquire a resource or change interface state, before writing success and error handling, so that cleanup is designed in from the start, rather than added as an afterthought that might be incomplete or inconsistent across paths.

Cleanup should also be idempotent where possible, meaning that running it twice has the same effect as running it once, so that cleanup can be safely called from multiple places, such as from both a catch block and a finally block, or from both a timeout handler and a normal completion handler, without causing secondary errors. For example, hiding a spinner that is already hidden should be safe, closing a connection that is already closed should be safe, and clearing a timer that has already fired should be safe, all without throwing errors that would mask the original failure. Designing cleanup to be idempotent, by checking state before acting, such as if (spinnerVisible) hideSpinner(), or by using operations that are naturally idempotent, such as setting a flag to false regardless of its current value, prevents cleanup itself from becoming a source of errors, which is a common problem when cleanup code assumes a specific state that may not hold after a failure that occurred at an unexpected point.

Section 33: Errors in Callbacks

Errors in callbacks present unique challenges, because callbacks are functions passed to other functions, which decide when and how to call them, and errors thrown inside callbacks do not necessarily propagate to the code that passed the callback, depending on how the receiving function handles callback errors. For synchronous callbacks, such as array methods like map or forEach, errors thrown inside the callback propagate to the caller of the array method, which can catch them with try and catch around the method call, because the callback runs synchronously inside the method's execution. For asynchronous callbacks, such as event handlers, timers, or promise callbacks, errors thrown inside the callback do not propagate to the code that registered the callback, because that code has already returned by the time the callback runs, and the error becomes an uncaught error or an unhandled rejection, depending on the callback's context, rather than a catchable error for the registrant. That timing difference, synchronous propagation versus asynchronous escape, is the key to callback error handling, and it requires different strategies for each kind of callback.

For synchronous callbacks, the handling strategy is straightforward: wrap the calling code in try and catch, and handle callback errors at the call site, where context is available to decide recovery. For example, if a map callback throws for one item, the entire map operation fails, and the caller can catch the error and decide whether to retry, to use a fallback, or to report the failure, with the knowledge that no partial map result is available, because map aborts on first callback error, unlike a manual loop with per-item try and catch, which could continue past a failing item. That all-or-nothing behaviour of map and similar methods, where one callback error aborts the whole operation, is important to understand, because it differs from loop handling where per-item errors can be collected, and it affects whether map is appropriate for operations where individual items might fail but others should still be processed, in which case a manual loop with per-item handling is better than map.

For asynchronous callbacks, the handling strategy is to handle errors inside the callback itself, with try and catch around its async work, and to display messages or log errors there, rather than relying on the registrant to catch them, because the registrant cannot. For example, a timer callback that performs async work should catch its own errors and log them, because the timer mechanism will not propagate callback errors to the code that set the timer. Similarly, an event handler callback should catch its own errors, as discussed earlier, because the browser will not propagate them to the code that added the listener. That self-contained handling for async callbacks, where each callback is responsible for its own errors, is a fundamental rule for event-driven and timer-driven code, and violating it leads to silent failures and unhandled rejections that are hard to debug, because they occur far from the code that initiated the callback, with no caller to report them to.

    }
    return n * 2;
  });
} catch (error) {
  console.log("Sync callback error caught at call site: " + error.message);
}

Section 34: Promise Rejection Handling

Promise rejection handling is the async counterpart to try and catch for synchronous errors, and it involves attaching catch handlers to promises, using try and catch with await, and ensuring that no promise rejection goes unhandled, because unhandled rejections indicate missing error handling that should be fixed. A promise rejects when its operation fails, such as a fetch that cannot connect, an async function that throws, or a promise explicitly rejected with an error. That rejection travels through promise chains until it reaches a catch handler, where it can be handled with recovery, logging, or user messages, similar to synchronous catch blocks. If no catch handler is ever attached, the rejection remains unhandled, triggering warnings or crashes as discussed earlier, which is why every promise chain should end with a catch, or be awaited inside a try block that serves as its catch, without exception for promises that are expected to always succeed, because even reliable operations can fail unexpectedly in production.

Handling rejections in promise chains involves understanding how then and catch interact: then handlers receive fulfillment values, catch handlers receive rejection reasons, and both return new promises that can be chained further, allowing you to transform values, handle errors, and continue chains after recovery. For example, a chain that fetches data, processes it, and displays it, with a catch at the end, will handle rejections from any step in the chain, because rejections skip subsequent then handlers and jump directly to the next catch, similar to how synchronous throws skip code until a catch block. That skipping behaviour, rejection jumps to catch, is powerful because it allows a single catch at the end of a chain to handle failures from any step, without needing error checks after each step, which simplifies chain code and centralises error handling for the whole chain, as long as the catch is placed correctly at the end and not in the middle where it might be bypassed by later steps that also fail.

A subtle promise rejection issue is that catch handlers themselves can throw, creating a new rejection that propagates to the next catch in the chain, or becomes unhandled if there is no further catch. That chaining of catch errors means that error handling code itself must be robust, with its own try and catch if it performs risky operations, such as logging to a failing service or displaying a message that itself throws due to missing elements. While catch code is usually simple and unlikely to throw, being aware that it can throw, and that its throws become new rejections, helps you design chains where final catches are simple and safe, such as logging to console and showing a static message, rather than performing complex operations that could fail and create secondary rejections that are harder to diagnose than the original failure.

function failingPromise() {
  return Promise.reject(new Error("Promise failed"));
}

  .catch((error) => {
    console.log("Caught rejection: " + error.message);
    return "Recovered value";
  })
  .then((value) => console.log("Chain continued with: " + value));

Section 35: Global Error Handlers

Global error handlers are last-resort handlers that catch errors not handled anywhere else in a program, logging them, reporting them for fixing, and showing users a generic message, rather than leaving errors completely unreported or crashing silently. In browsers, global handlers include window.onerror for synchronous uncaught errors, window.addEventListener for unhandledrejection for async rejections, and window.addEventListener for error events from resources such as failed image loads, each of which provides information about the error and its source, allowing a central handler to log it and to display a fallback interface, such as a message that something went wrong and to try refreshing the page. In Node, global handlers include process.on for uncaughtException and unhandledRejection, which similarly log errors and allow graceful shutdown or reporting, rather than abrupt crashes without diagnostics. Those global handlers are safety nets, not substitutes for specific handling, because they lack the context to recover gracefully for specific features, but they ensure that no error goes completely unnoticed, which is valuable for production monitoring and for user experience when specific handling fails or was missed.

Designing global handlers involves deciding what to log, what to show users, and whether to attempt recovery or shutdown. For browsers, a global handler should log the error details, including message, stack, and URL, to a reporting service if available, or to the console for development, and should show users a non-technical message, such as Something went wrong. Please try refreshing the page, without exposing stack traces or technical details that users cannot act on and that might reveal implementation details to attackers. It should not attempt to recover the specific failed feature, because it does not know which feature failed or how to recover it, but it can offer a general recovery action, such as refreshing the page, which often restores a consistent state after an unhandled error that left the page partially updated. That general recovery, refresh to reset, is a reasonable last resort for unhandled errors, where specific recovery is impossible due to missing context.

For Node servers, global handlers have higher stakes, because an unhandled error might leave the server in an inconsistent state, with corrupted data or leaked resources, where continuing to serve requests could cause further harm, such as serving wrong data or corrupting more records. In those cases, the safest global handling is often to log the error, attempt a graceful shutdown, and let a process manager restart the server in a clean state, rather than continuing in an unknown state that could worsen the problem. That shutdown-on-unhandled-error strategy, which modern Node enforces by default for unhandled rejections, reflects a philosophy that unknown errors should not be tolerated in servers, because the cost of continuing incorrectly exceeds the cost of a brief restart, especially when process managers can restart quickly and users can retry. For browsers, where a page refresh is user-initiated and less disruptive than a server restart, continuing with a generic message is more acceptable, because the page's state is isolated to one user and refreshing is a familiar recovery action.

Section 36: Reporting Errors Without Exposing Secrets

Reporting errors without exposing secrets means sharing enough information for developers to diagnose and fix problems, while withholding sensitive information that could be misused if exposed in logs, error messages, or user displays. Sensitive information includes passwords, authentication tokens, API keys, personal data such as addresses or health information, and internal system details such as database connection strings, file paths on servers, or stack traces that reveal code structure to attackers. When an error occurs, its message, stack trace, and context data might inadvertently contain such secrets, especially if error messages include input values, request bodies, or environment details that were not intended for logging. Carelessly logging full error objects, request data, or user inputs can therefore leak secrets into logs that are accessible to support staff, to other developers, or to attackers who gain log access, turning a minor error into a security incident.

Preventing secret exposure in error reporting involves several practices: never include passwords, tokens, or keys in error messages, even in development logs, because development logs can be copied or persisted and later shared; mask sensitive fields when logging request or user data, such as showing only the last few characters of a token, or replacing passwords with asterisks, rather than logging full values; avoid logging full stack traces to users, because stack traces reveal file names, function names, and line numbers that help attackers understand code structure, while users cannot act on them; and sanitise error context before sending it to external reporting services, removing fields known to be sensitive, or using a denylist or allowlist approach where only known-safe fields are included in reports. That sanitisation, applied consistently to error logging and reporting, ensures that developers receive useful diagnostics without receiving secrets they do not need, which is a principle of least privilege applied to logs: logs should contain the minimum information necessary to diagnose, not the maximum information available at failure time.

User-facing error displays should be especially careful about secret exposure, because users might screenshot error messages and share them publicly, or attackers might intentionally trigger errors to extract system information from error pages. A user-facing error should contain only a generic message and a reference id that developers can use to look up detailed logs internally, rather than technical details, stack traces, or system information that could aid attacks. That reference id pattern, where users see Error reference: ABC123 and developers look up ABC123 in internal logs to find full details, balances user communication with security, giving users a way to report problems without exposing internals, and giving developers a way to correlate user reports with detailed logs without sharing those logs publicly. That pattern is standard for professional error reporting, and it is worth adopting even for small applications, where a simple reference, such as a timestamp plus a random id, can serve as a correlation key without revealing system details.

Section 37: Errors in User Input Processing

Errors in user input processing occur when users provide data that is missing, malformed, or outside expected ranges, and handling them well is crucial because user input is the most common source of errors in interactive applications, and because users' experience of an application is largely determined by how it responds to their mistakes. Unlike system errors, which users cannot fix, input errors are usually fixable by users, provided they receive clear, specific, and timely feedback about what is wrong and how to correct it. That feedback should be immediate, ideally as users type or on submission, field-specific, pointing to the exact field that is wrong, and actionable, describing a valid value or format, rather than generic, such as Invalid input, which leaves users guessing what to fix and often leads to repeated submissions with the same mistake, frustration, and abandonment.

Processing user input safely involves several steps: trimming whitespace, normalising formats where appropriate, validating types and ranges, checking required fields, and sanitising values before use, especially before displaying them or sending them to servers, to prevent security issues such as script injection through input fields. Each step should be performed in order, with errors collected for all fields, rather than stopping at the first error, so that users can fix all problems in one pass, as discussed for validation generally. That batch validation, with field-specific messages and preserved input, is the standard for good input processing, and it respects users' effort by not requiring them to submit repeatedly to discover new errors one by one, which is a common frustration in poorly designed forms that validate fields sequentially and report only the first failure each time.

Input processing errors also include cases where input is technically valid but semantically wrong, such as a date in the past for a future event, a quantity that exceeds available stock, or a username that is already taken, which can only be detected by checking against business rules or server data, not by simple format validation. Those semantic errors require server validation or business logic checks after initial format validation, and their messages should explain the business rule, such as That date must be in the future, or That username is already taken, please choose another, rather than generic validation messages that do not explain why a formally valid input was rejected. That business-rule explanation, with a suggestion for a valid alternative where possible, such as suggesting available usernames, helps users correct semantic errors efficiently, rather than guessing why their valid-looking input was rejected, which is a common source of confusion in forms that only validate formats and not business rules.

Handling input securely involves validating length limits, escaping or sanitising values before display, using parameterised queries for database access rather than concatenating input into queries, and rejecting or neutralising inputs that contain dangerous patterns, rather than trusting them because they passed format validation. While full input security is an advanced topic covered in the security chapter, the basic principle for this chapter is clear: never trust user input without validation and sanitisation, even if it looks harmless, because input processing is a primary attack surface for web applications, and errors in input handling can become security vulnerabilities, not just usability problems, if malicious inputs are processed without checks.

Section 38: Errors in File and Storage Code

Errors in file and storage code, such as reading or writing files, accessing localStorage, or interacting with databases, have unique characteristics because they involve external resources that can fail for reasons outside your program's control, such as missing files, permission denied, quota exceeded, corrupted data, or concurrent access conflicts. Section 39: Errors in Date and Number Code

Errors in date and number code are common because dates and numbers have specific formats, ranges, and precision limits that are easy to violate with invalid inputs or incorrect calculations, leading to errors such as Invalid Date, NaN, or out-of-range values that propagate through programs and cause confusing downstream failures if not caught early. Date errors often arise from parsing invalid date strings, such as new Date("not a date"), which produces an Invalid Date object rather than throwing, so code that checks for thrown errors will miss it, and must instead check validity with isNaN(date.getTime()), as discussed earlier. Number errors often arise from invalid numeric inputs, such as Number("abc") producing NaN, or from arithmetic that produces Infinity, such as dividing by zero in floating-point arithmetic, or from precision loss for large integers or decimal fractions, as discussed for JSON numbers earlier. Those number errors, like Invalid Date, often do not throw, but produce special values, NaN or Infinity, that must be checked explicitly with Number.isNaN or Number.isFinite, before using results in displays or further calculations, otherwise users will see NaN or Infinity in interfaces, which looks like a bug even if the underlying calculation was technically performed correctly according to floating-point rules. Handling date and number errors well involves validation at input boundaries, where date strings and numeric strings are parsed, with explicit checks for validity and with clear messages for invalid inputs, such as Please enter a valid date in YYYY-MM-DD format, or Age must be a number between 0 and 120, rather than allowing invalid parsed values to flow into programs and cause later failures. Section 40: Avoiding Silent Failures

Silent failures are errors that occur without any visible indication to users or developers, such as a function that returns undefined instead of throwing, a catch block that swallows an error without logging, or a feature that fails to load data but displays an empty area without a message, leaving users confused about whether data is truly empty, still loading, or failed to load, and leaving developers unaware that a failure occurred at all, because no log or alert was generated. Silent failures are among the most harmful error handling anti-patterns, because they hide problems that could be fixed, they mislead users into believing that a program is working correctly when it is actually failing, and they allow bugs and data corruption to accumulate undetected, until they manifest as larger, harder-to-diagnose problems later, such as missing data that was silently discarded weeks earlier and cannot be recovered. Avoiding silent failures is therefore a fundamental principle of reliable error handling: every failure should be visible somewhere, either to users as a message, to developers as a log, or preferably to both, with appropriate detail for each audience, so that failures are never completely invisible.

Common causes of silent failures include empty catch blocks, catch blocks that only log at debug level that is disabled in production, functions that return null or undefined on failure without indicating that failure occurred, and code that ignores promise rejections or return values that indicate errors, such as fetch responses with error statuses that are not checked. Each of those causes can be fixed by ensuring that every catch block either logs, displays, rethrows, or returns a clear failure indicator, rather than doing nothing, and that every function that can fail documents whether it throws, returns an error object, or returns a fallback, so callers know to check for failure and do not mistake a fallback or null return for success. That documentation and handling discipline, no empty catches and no ignored error indicators, is a simple rule that prevents most silent failures, and it should be enforced in code reviews, where empty catches and ignored return values are flagged as bugs, not as acceptable shortcuts for handling errors that developers did not know how to handle at the time.

To avoid that transparency problem, fallbacks should be logged for developers, with a message indicating that a fallback was used and why, and where appropriate, indicated to users with a subtle label, such as Cached data or Default settings, so that users understand that displayed data may not be current, and developers understand that a feature's primary path is failing and needs fixing, even though users are not blocked by the failure. That transparency, logging fallbacks and labelling them for users when they affect accuracy, turns fallbacks from silent masking into visible degradation, which is the correct form of graceful handling: degraded but honest, rather than degraded and misleading.

Section 41: When to Let an Error Crash

Letting an error crash a program, rather than catching and handling it, is sometimes the correct choice, especially for programming errors, invariant violations, and situations where continuing would cause more harm than stopping. A crash, in this context, means allowing an uncaught error to stop the current operation, to log a stack trace, and, in Node, to exit the process, or in a browser, to stop the current script and show a generic error, rather than catching the error and attempting to continue with potentially corrupted state. That crashing behaviour is appropriate when an error indicates a bug that should be fixed, not a condition that can be recovered from, because continuing after a bug could produce wrong results, corrupt data, or hide the bug from developers who need to fix it, whereas crashing makes the bug visible, with a stack trace that points to its source, and prevents further harm from operating in an unknown state. That visibility and harm prevention, crashing as a safety mechanism, is why many systems treat uncaught programming errors as fatal, rather than attempting to handle them gracefully at runtime.

Examples of errors that should crash include invariant violations, where a program's internal state contradicts its assumptions, such as a data structure that should never be empty being empty, or a function that should never receive null receiving null due to a bug in its caller, where catching and continuing would allow the program to operate with broken invariants that could cause worse failures later, such as incorrect calculations based on invalid state. Another example is out-of-memory or stack overflow errors, where the program's resources are exhausted and continuing is impossible or unsafe, because any further operation might also fail due to lack of resources, and the safest action is to stop and restart in a clean state. A third example is security violations, where an operation attempts to access data or perform an action it should not, and continuing could allow unauthorised access or data leakage, whereas stopping immediately prevents further unauthorised actions and alerts developers to a potential security bug that needs fixing, not handling.

In contrast, errors that should not crash include expected user input errors, transient network failures, and missing optional data, where recovery is possible and where crashing would be disproportionate, frustrating users for problems that are common and fixable, such as a mistyped email or a brief network glitch. Crashing for those errors would turn minor, recoverable problems into major disruptions, requiring users to restart applications or lose work, when a simple message and retry would have sufficed. That distinction, crash for bugs and invariants versus handle for expected and transient failures, is the key judgement for deciding when to let an error crash, and it should be made deliberately for each error type, based on whether the error indicates a bug that must be fixed, or a condition that can be recovered from, rather than defaulting to always catching or always crashing for all errors, which would be incorrect for many cases.

Section 42: Error Boundaries in Plain Words

Error boundaries are a concept, popularised by React and other user interface frameworks, for containing errors within a part of a user interface, so that a failure in one component does not crash the entire page, but instead shows a fallback interface for that component while other components continue working. In plain words, an error boundary is like a compartment in a ship: if one compartment floods, watertight doors prevent water from spreading to other compartments, allowing the ship to stay afloat even though one section is damaged. Similarly, an error boundary catches errors from its child components, logs them, and displays a fallback, such as Something went wrong in this section, with a retry button, while the rest of the page, including navigation, other sections, and user input in unaffected areas, continues to work normally, rather than the entire page crashing to a blank screen because one widget failed.

In plain JavaScript without a framework, you can implement error boundary-like behaviour manually, by wrapping risky sections of code in try and catch blocks that display fallbacks for those sections specifically, rather than letting errors propagate to a global handler that would affect the whole page. For example, a dashboard page with several independent widgets can load each widget inside its own try and catch, so that a failure in one widget's loading shows a fallback for that widget alone, while other widgets load normally, which is the same principle as framework error boundaries, applied manually with try and catch per section. That per-section handling, as discussed for partial failures and dashboards earlier, is the plain JavaScript equivalent of error boundaries, and it achieves the same user experience benefit: isolated failures with local fallbacks, rather than global crashes for local problems, which is a significant improvement in reliability and user trust for complex pages with many independent features.

Error boundaries also involve decisions about what fallback to show and how to allow recovery, such as a retry button that attempts to reload the failed section, a link to support, or a message explaining that the section is temporarily unavailable, all of which should be specific to the failed section, not generic to the whole page. For example, a failed chart widget might show Chart unavailable, with a retry button that reloads only the chart data, while a failed comments widget might show Comments unavailable, with a note that comments can be viewed later, each fallback tailored to its section's purpose and to users' expectations for that section. That tailored fallback design, section-specific messages and actions, is more helpful than a single generic page error, because users understand exactly which part failed and what they can still do with other parts, rather than being left with a vague page-level error that suggests everything is broken when only one part is affected.

function loadSection(name, shouldFail) {
  try {
    if (shouldFail) {
      throw new Error(name + " failed to load");
    }
    console.log(name + " loaded successfully");
  } catch (error) {
    console.log(name + " fallback: section unavailable, other sections still work");
  }
}

Section 43: Writing Error Handling Tests

Writing error handling tests involves creating test cases that verify how code behaves when failures occur, in addition to tests for success cases, and it requires thinking about failure modes, simulation techniques, and assertions for error behaviour, as discussed for testing error paths generally. A good error handling test starts by identifying a specific failure, such as invalid input, missing data, network failure, or dependency error, then simulating that failure with a fake, invalid input, or mocked dependency, then asserting that the code under test produces the expected error handling outcome, such as throwing a specific error type, returning a specific fallback, logging a specific message, or restoring interface state to a usable condition. Those assertions, specific to error handling outcomes, are what distinguish error tests from success tests, which assert correct values, because error tests assert correct failure behaviour, which is equally important for reliability but often overlooked in test suites that focus only on happy paths.

Structuring error tests clearly helps other developers understand what failure is being tested and what handling is expected, by naming tests descriptively, such as should throw ValidationError for missing name, or should return fallback when fetch fails, rather than generic names such as test error handling, which do not convey which error or which handling is being verified. Each test should focus on one failure kind, rather than combining multiple failures into a single test, because single-failure tests are easier to debug when they fail, pinpointing exactly which handling broke, while multi-failure tests that fail leave developers guessing which failure's handling is incorrect. That single-failure-per-test discipline, like single-assertion-per-test for simple cases, makes test suites more maintainable and more useful as documentation of expected error behaviour, because each test's name and assertions together describe one failure scenario and its expected handling in a self-contained way.

Error tests should also verify that error handling does not have side effects that cause further problems, such as leaving resources open, leaving interface state stuck, or swallowing errors that should propagate, as discussed for cleanup and rethrow discipline earlier. For example, a test for a function that opens a resource and fails should assert that the resource is closed after failure, by checking a flag or a mock that records close calls, in addition to asserting that the correct error is thrown or fallback returned. Similarly, a test for a function that should rethrow unknown errors should assert that unknown errors do propagate, by expecting a throw in the test, rather than only testing known errors that are handled. Those side-effect assertions, for cleanup and propagation, ensure that error handling is complete, not just that it produces a correct message for the tested failure, but also that it leaves the program in a consistent state for subsequent operations, which is essential for reliability in real programs where failures are followed by retries or by other features that depend on clean state.

Section 44: Documenting Error Behaviour

Documenting error behaviour means writing down, in comments, documentation, or function signatures, what errors a function can throw or return, under what conditions, and how callers should handle them, so that other developers, including future you, can use functions correctly without reading their implementation details to discover error behaviour by trial and error. Good error documentation includes, for each function, a list of error types or codes it can produce, the conditions that trigger each error, whether errors are thrown or returned, and what recovery actions are appropriate for each, such as retrying, showing a validation message, or propagating to a higher handler. That documentation, placed near the function's definition, serves as a contract between the function and its callers, similar to how parameter documentation describes inputs and return documentation describes outputs, but for failures, which are equally part of a function's behaviour and equally important for correct use.

Without error documentation, callers must guess error behaviour, leading to common mistakes such as forgetting to catch a throwing function, checking for null from a function that never returns null, or handling all errors generically when specific handling is needed for different error types. Those mistakes, caused by undocumented error behaviour, are preventable with clear documentation that states throwing versus returning, error types, and handling guidance, in a concise form that callers can read quickly without studying implementation. For example, a comment such as Throws ValidationError if name is missing, throws NotFoundError if user id does not exist, otherwise returns user object, tells callers everything they need to know to handle that function correctly, in one sentence, whereas without that comment, callers would need to read the function body, understand its validation and lookup logic, and infer error behaviour, which is time-consuming and error-prone, especially for functions with complex logic or multiple failure modes.

Error documentation should be kept up to date as functions evolve, because outdated documentation that lists errors a function no longer throws, or omits new errors it now throws, is worse than no documentation, because it misleads callers into handling errors incorrectly, such as catching errors that never occur while missing new errors that do occur and become unhandled. Keeping documentation current requires discipline, such as updating comments whenever error behaviour changes, and reviewing error documentation during code reviews, where reviewers check that documentation matches implementation for error cases, just as they check that parameter documentation matches actual parameters. That review discipline, applied consistently, ensures that error documentation remains a reliable contract, rather than a stale description that diverges from code over time and eventually becomes ignored by developers who have learned not to trust it, which undermines the whole purpose of documentation.

Good API error documentation includes, for each endpoint, a list of possible error responses, with status codes, error codes, message examples, and handling guidance, such as retry for 500 errors, correct input for 400 errors, and sign in for 401 errors, as discussed for status codes and error codes earlier. That API documentation, published alongside endpoint documentation, allows clients to implement correct error handling before encountering errors in production, rather than discovering error behaviour through trial and error with live requests, which is inefficient and risky for production integrations where error handling mistakes can cause data loss or user frustration.

Section 45: Refactoring Messy Error Code

Refactoring messy error code means improving the structure and clarity of existing error handling without changing its behaviour, so that it becomes easier to read, maintain, and extend, while still handling the same failures in the same ways. Messy error code often takes forms such as deeply nested try blocks, duplicated catch blocks with identical logging and messages in many places, catch blocks that swallow errors silently, or error handling scattered throughout business logic, making it hard to understand which errors are handled where and how. Refactoring such code involves extracting common handling into helper functions, such as a logError helper or a userMessage helper, centralising error definitions into custom classes or codes, flattening nested tries by extracting helper functions for risky steps, and removing silent catches by adding logging or rethrowing, all while preserving behaviour, so that refactoring improves clarity without introducing new bugs or changing user-visible error handling outcomes.

A common refactoring technique is to extract error handling helpers for repeated patterns, such as a safeParse helper for JSON, a fetchJson helper for fetch with ok checks, or a handleError helper that logs and displays a user message for a given error, which can then be reused across many call sites, replacing duplicated catch blocks with single helper calls. That extraction reduces duplication, ensures consistency, because all call sites use the same helper logic for logging and messaging, and makes future changes easier, because updating the helper updates handling everywhere, rather than requiring changes in many duplicated blocks that might be missed. When extracting helpers, you should test that behaviour is preserved, by running existing success and failure tests before and after refactoring, confirming that the same inputs produce the same outputs and handling, which is the definition of safe refactoring: improved structure with unchanged behaviour, verified by tests, not just by inspection.

Another refactoring technique is to replace generic error handling with specific handling where different errors need different responses, or conversely, to replace overly specific handling with generic handling where different errors actually need the same response, depending on which direction simplifies the code without losing necessary specificity. For example, if many catch blocks handle all errors with the same generic message, they can be replaced with a single higher-level catch that handles all errors for a feature, removing duplication and clarifying that feature-level handling is intentional, not accidental duplication. Conversely, if a single generic catch handles errors that actually need different messages, such as validation versus system errors, it should be split into specific branches that handle each error type appropriately, improving user guidance even though code becomes slightly longer, because the extra specificity is necessary for correct user experience, not just for code elegance. That specificity judgement, generic when remedies are same and specific when remedies differ, as discussed earlier, guides refactoring decisions toward clarity and correctness, not just brevity.

function logAndShow(error) {
  console.log("Logged: " + error.message);
  console.log("Show user: Something went wrong, please try again.");
}

  try {
    if (shouldFail) {
      throw new Error("Work failed");
    }
    console.log("Work succeeded");
  } catch (error) {
    logAndShow(error);
  }
}

Section 46: Errors in Third-Party Code

Errors in third-party code, such as libraries, frameworks, or APIs that your program depends on, require handling that accounts for the fact that you do not control that code, cannot fix its bugs directly, and may not fully understand its error behaviour from its documentation alone. Third-party code can throw errors due to bugs, due to invalid inputs you passed to it, due to version changes that alter its behaviour, or due to external failures such as network or file issues that it encounters internally, and your code must handle those errors gracefully, even when their exact types, messages, or codes are not well-documented, by catching broadly at integration boundaries, logging details for diagnosis, and providing fallbacks or user messages that do not depend on precise third-party error details. That boundary handling, catch at integration points and log for diagnosis, is essential for programs that depend on external code, because third-party failures are outside your control but still affect your users, and your program should not crash or misbehave simply because a library it uses failed in a way you did not anticipate.

Handling third-party errors specifically involves wrapping third-party calls in try and catch blocks at the points where you call them, rather than letting their errors propagate unhandled through your program, where they might be caught by generic handlers that lack context about the third-party operation and cannot provide appropriate recovery. For example, if you call a chart library to render a chart and it throws due to invalid data, you should catch that error at the chart rendering call site, log the library error details for debugging, and show a fallback for the chart section, rather than letting the error propagate to a page-level handler that might treat it as a general page failure and hide other sections that are working correctly. That call-site handling, with section-specific fallbacks, mirrors error boundary principles for third-party code, isolating library failures to the features that use them, rather than allowing them to affect unrelated features that do not depend on the failing library.

Version changes in third-party code are a particular source of errors, because updating a library to a new version can change its error behaviour, its API, or its handling of edge cases, causing previously working code to fail in new ways that were not anticipated when the code was originally written. To handle version-related errors, you should pin dependency versions for production, test updates in a staging environment before deploying them, read changelogs for breaking changes, and write tests that verify your integration with third-party code, including its error behaviour, so that version updates that break integration are caught by tests before reaching users. That version discipline, pinning, testing, and changelog reading, is a professional practice for dependency management that prevents many third-party error surprises, because it ensures that updates are deliberate and verified, rather than automatic and untested, which can introduce errors silently when a library changes its behaviour without your knowledge.

  return "Chart rendered";

Section 47: Graceful Degradation After Errors

Graceful degradation after errors means designing a program to continue functioning at a reduced level when some features fail, rather than failing completely, by prioritising essential features, providing fallbacks for non-essential features, and communicating clearly which features are available and which are degraded. That design philosophy, essential first and optional degraded, is especially important for complex applications with many features, where a failure in one non-essential feature, such as recommendations, analytics, or a secondary data source, should not prevent users from accomplishing their main goals, such as reading content, completing a purchase, or saving work, which are essential features that must remain available even when secondary features fail. Implementing graceful degradation involves identifying essential versus optional features during design, implementing fallbacks for optional features, and testing degradation scenarios where optional features fail, to confirm that essential features still work and that users understand which parts are degraded, rather than being confused by silent missing features that look like bugs.

A practical approach to graceful degradation is to structure features as independent modules or sections, each with its own loading, error handling, and fallback, as discussed for error boundaries and dashboards earlier, so that failures are isolated to their modules and do not cascade to other modules. That modular structure, with per-module try and catch and fallbacks, is the architectural foundation for graceful degradation, because it prevents a single module's failure from becoming a global failure, and it allows each module to degrade independently, with its own fallback that is appropriate to its purpose, such as a cached list for a failed recommendations module, or a static image for a failed interactive chart module. Without modular isolation, a program is fragile, where one failure can bring down everything, because modules are tightly coupled and share error handling or state in ways that allow failures to propagate, which is a design flaw that graceful degradation aims to fix by decoupling modules and their failure handling.

Communicating degradation to users is as important as implementing it, because users need to know which features are degraded and why, to adjust their expectations and to avoid making decisions based on missing or fallback data that they believe is complete. For example, if a price comparison feature fails and shows cached prices, users should see a label indicating that prices are cached and may be outdated, so they do not make purchase decisions based on stale prices they believe are current. If a comments feature fails, users should see a message that comments are temporarily unavailable, rather than a blank comments section that looks like there are no comments, which would mislead them into believing that no one commented, when in fact comments exist but could not be loaded. That honest communication about degradation, with labels and messages for degraded sections, preserves user trust even when features fail, because users understand the situation and can work around it, rather than being misled by silent degradation that looks like normal operation but is actually incomplete.

To bring this chapter together, let us design a complete mini project that combines error handling patterns into a realistic feature: a task manager that loads tasks from storage, allows adding and completing tasks, and handles errors at every step with appropriate messages, fallbacks, and cleanup. The task manager starts by loading tasks from a simulated storage layer, using safe parsing with a fallback to an empty list if storage is missing or corrupted, and displaying a message if fallback was used, so users know that previous tasks could not be loaded. Storage functions handle parsing, quota, and corruption errors with fallbacks and logging. That layered separation, storage, validation, logic, display, with error handling appropriate to each layer, is a clean architecture for error handling that scales from mini projects to large applications, where each layer's error responsibilities are clear and testable in isolation.

Section 49: Common Error Handling Mistakes

Common error handling mistakes fall into a handful of categories, and learning to recognise and avoid them will significantly improve the reliability of your programs, just as with fetch and JSON mistakes earlier. The first category is silent failures, where catch blocks are empty, or errors are swallowed without logging or user messages, hiding problems from both users and developers, as discussed in depth earlier. The fix is to never leave a catch block empty, to always log, display, rethrow, or return a clear failure indicator in every catch, and to review code for empty catches during code reviews, treating them as bugs rather than as acceptable handling for errors that developers did not know how to handle at the time, which should instead be logged and rethrown for higher-level handling if local recovery is not possible.

The second category is over-catching, where try blocks are too broad, catching errors from unrelated code that should propagate as bugs, or where catch blocks handle all errors generically, including programming errors that should crash visibly during development, rather than being treated as user-facing failures. The fix is to narrow try blocks to only risky operations, to handle specifically only errors you understand and can recover from, and to rethrow unknown errors for higher-level handling or for global logging, as discussed for specific handling earlier. That narrowing and rethrowing discipline prevents error handling from becoming error hiding, where bugs are masked as user messages and persist undetected, causing larger failures later when hidden bugs affect data or logic in ways that are harder to trace back to their original, swallowed error.

The third category is poor error messages, where messages are technical, vague, blaming, or missing next steps, leaving users confused about what happened and what to do, even when handling itself is technically correct in terms of catching and logging. The fix is to write user messages in plain language, with goal, cause, and next step, as discussed for user-friendly messages, and to write developer messages with specific details, such as field names, ids, and expected versus actual values, for logs, rather than generic messages such as Something went wrong, which are unhelpful for both audiences, albeit for different reasons: users need guidance, developers need specifics, and a single generic message serves neither well. Separating user and developer messages, with tailored content for each, is the fix for poor messaging, and it should be applied consistently across a program, with helpers that map technical errors to user messages, as discussed earlier.

The fourth category is missing cleanup, where finally blocks are omitted, or cleanup is duplicated in success and error paths but forgotten in one path, leaving resources open, interface states stuck, or partial data changes unrolled after failures. The fix is to use finally for all cleanup, to make cleanup idempotent, and to test cleanup on both success and failure paths, as discussed for cleanup earlier, ensuring that programs always return to a consistent state after operations, regardless of outcome. That finally-based cleanup, tested on both paths, prevents stuck spinners, disabled buttons, and leaked resources that frustrate users and cause secondary failures, which are often more noticeable to users than the original failure itself, because they block further action even after the original problem has been resolved or retried.
