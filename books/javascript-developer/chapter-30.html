Chapter 30: Regular Expressions for Everyday Text

Section 1: What Regular Expressions Are

A regular expression, often shortened to regex, is a pattern that describes a set of strings, such as all email-like texts, all numbers, or all words starting with a capital letter. Instead of writing code that checks text character by character with loops and conditionals, you write a compact pattern, and JavaScript's regex engine checks whether text matches that pattern, finds matches inside text, or replaces matched parts. That compactness is powerful: a pattern of a few characters can describe thousands of possible strings, such as any three-digit number or any word of a certain shape, which would take many lines of manual code to describe otherwise.

Regex patterns appear in many everyday tasks: validating form inputs, searching documents, cleaning up pasted text, extracting numbers or dates from messages, and reformatting lists. For example, a form might use a regex to check that a username contains only letters, numbers, and underscores, while a text tool might use a regex to find all hashtags in a post. Those tasks share a common need: to recognise text by its shape, not by its exact content, because you cannot list every possible valid username or hashtag in advance, but you can describe their shape with a pattern. Learning regex therefore gives you a general tool for text shape recognition, applicable across many features.

In JavaScript, you can write a regex as a literal between slashes, such as /cat/, or as a RegExp object created with new RegExp("cat"), which is useful when the pattern comes from a variable. Both forms create the same kind of pattern object, with methods such as test, which checks for a match, and with string methods such as match, replace, and split, which use patterns to find, change, or divide text. The literal form is more common for fixed patterns, because it is shorter and easier to read, while the constructor form is needed when patterns are built dynamically, such as when a search term comes from user input and must be escaped before becoming a pattern, a topic we will cover later.

It is important to approach regex with a balanced mindset. Regex is excellent for simple, well-defined text shapes, such as numbers, codes, and simple validations, but it is not suitable for complex, nested structures such as full HTML or programming languages, where a proper parser is needed. Beginners sometimes try to use regex for everything, leading to long, unreadable patterns that are hard to debug and that fail on edge cases. A good rule is to use regex when the pattern is short, clear, and testable with examples, and to use ordinary string methods or parsers when the task is complex or when a pattern would become longer than the manual code it replaces. That judgement, regex for simple shapes and other tools for complex structures, will keep your regex use effective and maintainable.

In this chapter, you will learn regex step by step, from literal matches and character classes to quantifiers, groups, flags, and practical validations, with examples you can test immediately in a console.

const pattern = /cat/;
console.log(pattern.test("I have a cat"));
console.log(pattern.test("I have a dog"));
console.log("I have a cat".match(/cat/));

Section 2: Literal Matches: Finding Exact Text

A literal match is the simplest regex: a pattern that matches exactly the characters written in it, with no special meaning. For example, the pattern /cat/ matches the three letters c, a, and t in that order, wherever they appear in text. It will match cat in I have a cat, it will also match cat inside larger words such as catalog or scatter, because regex by default searches anywhere in the text, not only for whole words, unless you add boundaries, which we will learn later. That substring behaviour is important to understand from the start, because it explains why a simple literal pattern can match more than you intended, and why you often need additional pattern elements to narrow a match to exactly what you want.

Literal matching is case-sensitive by default, so /cat/ matches cat but not Cat or CAT, unless you add the i flag for case-insensitive matching, which we will cover in the flags section. That case sensitivity is useful when case matters, such as matching a code that must be lowercase, but it can surprise beginners who expect cat to match Cat in a sentence starting with a capital letter. When case should not matter, you should either add the i flag, or include both cases in your pattern, with the flag being the cleaner choice for most cases. Testing literal patterns with different cases, such as cat, Cat, and CAT, will quickly show you how case sensitivity works and when to use the i flag to handle it.

Literal patterns can include spaces, punctuation, and digits, as long as those characters are not special regex characters, which we will learn to escape in the next section. For example, /hello world/ matches the exact phrase hello world with a single space, while /2026/ matches the digits 2026 wherever they appear. Those literal patterns are useful for simple searches, such as finding a specific word, phrase, or code in a document, and they are the building blocks for more complex patterns, where literals are combined with character classes, quantifiers, and groups to describe shapes that include both fixed parts and variable parts, such as a fixed prefix followed by variable digits.

When you use literal patterns with string methods, you should understand the difference between test, which returns true or false for whether a match exists, and match, which returns details about the match, such as the matched text and its position. For a simple existence check, such as Does this text contain cat, test is the clearest choice, because it returns a boolean directly. For finding what matched and where, match is more informative, because it returns the matched substring and, with certain flags, all matches in the text. Choosing the right method for your question, existence versus details, makes regex code clearer and avoids unnecessary work, such as using match and checking its result for null when test would have given a boolean directly.

console.log(/cat/.test("catalog"));
console.log(/cat/.test("Cat"));
console.log(/cat/i.test("Cat"));
console.log("hello world".match(/hello world/));

Section 3: Special Characters and Escaping

Special characters in regex are characters that have a meaning beyond their literal appearance, such as dot for any character, star for repetition, plus for one or more, question mark for optional, brackets for classes, parentheses for groups, caret for start, dollar for end, pipe for alternation, and backslash for escaping. When you want to match one of those characters literally, such as a dot in a decimal number, a plus in a phone number, or a question mark at the end of a sentence, you must escape it with a backslash, writing \. for a literal dot, \+ for a literal plus, and \? for a literal question mark. Without escaping, the regex engine will interpret those characters as pattern instructions, not as literal text, leading to matches that are broader or different than you intended, which is a common beginner mistake when searching for punctuation or symbols in text.

Escaping is also needed for characters that are special in certain contexts, such as slashes in regex literals, where a forward slash ends the pattern, so a literal slash must be written as \/ inside a literal, or the pattern must be built with the RegExp constructor where slashes do not terminate the pattern in the same way. Similarly, backslashes themselves must be escaped as \\ when you want to match a literal backslash, such as in a Windows file path, because a single backslash starts an escape sequence, and an unescaped backslash at the end of a pattern or before an ordinary character can cause errors or unexpected behaviour. Learning which characters are special, and escaping them when you mean them literally, is essential for writing correct patterns, especially for patterns that include punctuation, which is common in validations for emails, URLs, and codes that contain dots, plus signs, and other symbols.

A helpful habit when writing patterns with special characters is to test them with examples that include both the special character and similar characters that should not match, to confirm that escaping works as intended. For example, if you write a pattern for a decimal number as /\d+\.\d+/, with an escaped dot, test it against 3.14, which should match, and against 3x14, which should not match, because the dot is literal, not any character. If you had forgotten to escape the dot, writing /\d+.\d+/, the pattern would match 3x14 as well, because the unescaped dot matches any character, including x, which would be a bug for decimal validation, allowing invalid numbers to pass. That test pair, valid with dot and invalid with other character, reveals escaping errors immediately, and it is a good testing pattern for all special characters: test the literal character that should match, and test a different character that should not match if escaping is correct.

When patterns are built dynamically from user input, such as a search term that a user types, escaping becomes even more important, because user input may contain special characters that would otherwise change the pattern's meaning or cause errors.

console.log(/\d+\.\d+/.test("3.14"));
console.log(/\d+\.\d+/.test("3x14"));
console.log(/C\+\+/.test("I learn C++"));
console.log(/hello\?/.test("hello?"));

Section 4: Character Classes: [abc] and Ranges

Character classes allow a pattern to match any one character from a set, rather than a single specific character, which is essential for describing variable text such as letters, digits, or vowels. A character class is written inside square brackets, such as [abc], which matches a single character that is either a, b, or c, but not any other character, and not multiple characters at once, unless combined with a quantifier, which we will learn later. For example, /[abc]/ matches a in apple, b in banana, and c in cat, but it does not match d in dog, because d is not in the class. That single-character, set-membership behaviour is the core of character classes: they describe a choice of one character from a set, at a single position in the text, which can then be repeated with quantifiers to match longer sequences from the same set.

Ranges inside character classes make it easy to describe sets without listing every character, such as [a-z] for any lowercase letter, [A-Z] for any uppercase letter, [0-9] for any digit, and [a-zA-Z] for any letter of either case, by combining ranges. Those ranges are based on character code order, so [a-z] includes all letters from a to z in order, which is intuitive for letters and digits, but ranges can also include other characters, such as [0-9a-f] for hexadecimal digits, which combines a digit range with a letter range for hex letters. When you write a range, you should ensure that its start comes before its end in code order, otherwise the range is invalid and will cause a pattern error, such as [z-a], which is not a valid range because z comes after a. That ordering rule is easy to forget, but it is enforced by the regex engine, which will throw an error for reversed ranges, helping you catch the mistake early during pattern testing.

Character classes can also include multiple individual characters and ranges together, such as [abc0-9] for a letter a, b, or c, or any digit, or [a-zA-Z0-9_] for any word character, which is actually the same as the shorthand \w, which we will learn next. Inside a class, most special characters lose their special meaning and are treated literally, with a few exceptions: the caret at the start negates the class, as we will learn next, the hyphen defines a range unless it is at the start or end where it is literal, the closing bracket ends the class unless escaped, and the backslash still escapes characters. That mostly-literal behaviour inside classes simplifies patterns for punctuation sets, such as [!?.] for sentence-ending punctuation, where dot and question mark do not need escaping inside the class, unlike outside where they are special, which is a convenient detail that reduces escaping burden for character sets.

Using character classes effectively involves choosing the right set for your task: for vowels, [aeiou] is clear; for digits, [0-9] or \d is clear; for letters, [a-zA-Z] is clear; for hexadecimal, [0-9a-fA-F] is clear.

console.log(/[aeiou]/.test("hello"));
console.log(/[0-9]/.test("abc123"));
console.log(/[A-Z]/.test("Hello"));
console.log(/[a-z]+/.test("hello"));

Section 5: Negated Classes and Shorthand Classes

Negated character classes match any single character except those listed in the class, by placing a caret as the first character inside the brackets, such as [^abc], which matches any character that is not a, b, or c. That negation is powerful for describing text by exclusion, such as matching any character except a digit, except a letter, or except a specific punctuation mark, which is useful for cleaning text, for finding characters that should not be present, or for matching until a delimiter is reached, such as matching any characters except a comma when parsing a simple CSV field. For example, /[^0-9]/ matches any non-digit, including letters, spaces, and punctuation, while /[^,]+/ matches a sequence of non-comma characters, which is a common pattern for simple field extraction where fields are separated by commas and should not contain commas themselves.

Shorthand character classes are convenient abbreviations for common sets, which make patterns shorter and more readable once you learn them. The most common shorthands are \d for any digit, equivalent to [0-9], \w for any word character, equivalent to [A-Za-z0-9_], including letters, digits, and underscore, and \s for any whitespace, including space, tab, newline, and other whitespace characters. Each shorthand also has a negated capital version: \D for any non-digit, \W for any non-word character, and \S for any non-whitespace character, which are equivalent to negated classes for those sets, but shorter to write. Learning those six shorthands, \d, \D, \w, \W, \s, \S, covers a large proportion of everyday regex needs, because digits, word characters, and whitespace are the most common character categories in text processing, from validation to cleaning to extraction.

Using shorthands correctly involves understanding their exact definitions, especially for \w, which includes underscore but not other punctuation, and for \s, which includes several whitespace types beyond the ordinary space, such as tab and newline, which matters when cleaning text that may contain varied whitespace from pasting or from different systems. For example, a pattern that uses \s to match whitespace will correctly handle tabs and newlines in addition to spaces, while a pattern that uses a literal space will only match spaces, missing tabs that should also be treated as whitespace for cleaning purposes. That broader matching, with shorthands covering all members of a category, is usually what you want for general text processing, whereas literal characters are better when you mean only a specific character, such as only a space and not a tab, which is a distinction worth making deliberately based on your task's requirements.

Negated classes and shorthands can also be combined with other pattern elements, such as quantifiers to match sequences, or with literals to describe shapes, such as \d+ for one or more digits, \w+ for a word, or \S+ for a non-whitespace sequence, which are extremely common patterns for numbers, words, and tokens in text. Those combinations, shorthand plus quantifier, are the workhorses of regex, appearing in validations, extractions, and cleanups throughout real code, and mastering them will give you a large portion of practical regex skill with a small set of patterns.

console.log(/\d/.test("abc1"));
console.log(/\w/.test("_hello"));
console.log(/\s/.test("hello world"));
console.log(/[^0-9]/.test("a"));
console.log(/\D/.test("a"));

Section 6: Anchors: Start and End of Text

Anchors are pattern elements that do not match characters themselves, but match positions in text, specifically the start and end of the text or of a line, allowing you to require that a pattern matches the whole text or a whole line, rather than a substring anywhere inside it. The caret ^ matches the start of the text, or the start of a line when the multiline flag is used, which we will cover later, while the dollar $ matches the end of the text, or the end of a line with the multiline flag. For example, /^cat/ matches cat only at the start of text, not inside catalog at a later position, while /cat$/ matches cat only at the end of text, and /^cat$/ matches only the exact text cat, with nothing before or after, which is the pattern for whole-text validation, such as checking that an entire input is exactly a code or a username, rather than merely containing that code somewhere inside a longer string.

Anchors are essential for validation, because without them, a pattern that describes a valid shape will also match that shape as a substring of invalid text, allowing invalid inputs to pass validation incorrectly. For example, a pattern for a three-digit code, /\d{3}/, without anchors, will match 123 inside the invalid input abc123def, because it finds three digits somewhere inside, even though the whole input is not a three-digit code. With anchors, /^\d{3}$/, the same pattern requires the entire input to be exactly three digits, rejecting abc123def correctly, because the anchors require that the match starts at the beginning and ends at the end, with no extra characters before or after. That whole-text requirement, enforced by anchors, is the difference between searching for a pattern inside text and validating that text against a pattern, and it is a critical distinction for form validation, where you almost always want whole-text validation, not substring searching.

Anchors can also be used partially, to require only a start or only an end, depending on your task. For example, /^https:/ requires text to start with https:, which is useful for checking that a URL uses a secure protocol, without requiring the entire URL to match a specific pattern, while /\.com$/ requires text to end with .com, which is useful for checking domain endings, without requiring the whole domain to match. Those partial anchor uses, start-only or end-only, are common for prefix and suffix checks, where you care about one end of the text but not the other, and they are more precise than unanchored patterns that could match the prefix or suffix anywhere inside text, not necessarily at the required end. Choosing start, end, both, or neither anchors, based on whether you need whole, prefix, suffix, or substring matching, is a key pattern design decision that should be made deliberately for each pattern, rather than defaulting to unanchored patterns for all tasks, which is a common beginner mistake that leads to overly permissive matches.

console.log(/^cat/.test("catalog"));
console.log(/cat$/.test("a cat"));
console.log(/^cat$/.test("cat"));
console.log(/^cat$/.test("catalog"));
console.log(/^\d{3}$/.test("123"));
console.log(/^\d{3}$/.test("1234"));

Section 7: Quantifiers: *, +, ?, and {n,m}

Quantifiers specify how many times the preceding pattern element should repeat, allowing you to describe sequences of variable length, such as one or more digits, zero or more letters, or exactly three characters, without writing each repetition explicitly. The star * means zero or more repetitions, so /a*/ matches zero a's, which is an empty match, one a, or many a's, which is useful for optional sequences that may be absent, but it can also match empty strings in surprising places, which is a detail to be aware of when using star for validation, where zero repetitions might allow empty inputs to pass incorrectly if you do not also require at least one character elsewhere in the pattern. The plus + means one or more repetitions, so /a+/ matches one a or many a's, but not zero a's, which is the quantifier you want when at least one occurrence is required, such as one or more digits for a number, where zero digits would not be a valid number.

The question mark ? means zero or one repetition, making the preceding element optional, so /colou?r/ matches both color and colour, with the u optional, which is useful for optional characters, optional parts of words, or optional groups, as we will learn later. That optional behaviour, zero or one, is distinct from star's zero or more and plus's one or more, and choosing among them based on whether an element is required, optional once, or repeatable many times, is a fundamental pattern design decision that affects which strings match and which do not. For example, a pattern for a phone number with an optional country code might use an optional group for the code, while a pattern for a word might use plus for letters, because a word must have at least one letter, and a pattern for whitespace between words might use star or plus depending on whether whitespace is required or optional in that context.

Brace quantifiers {n,m} provide precise control over repetition counts, where {n} means exactly n repetitions, {n,} means at least n repetitions with no maximum, and {n,m} means between n and m repetitions inclusive. For example, /\d{3}/ matches exactly three digits, /\d{2,}/ matches at least two digits, and /\d{2,4}/ matches two, three, or four digits, but not one or five. Those precise counts are essential for fixed-length codes, such as three-digit area codes, four-digit years, or passwords with length requirements, where exact or ranged lengths are part of the validation rules, and where star, plus, and question mark would be too vague, allowing lengths that should be rejected. Brace quantifiers also combine with other elements, such as [a-z]{2,5} for a word of two to five lowercase letters, or \d{4}-\d{2} for a year-month pattern, giving you fine-grained length control for many practical patterns.

Quantifiers apply to the immediately preceding element only, which is a crucial detail that beginners often misunderstand.

console.log(/a*/.test(""));
console.log(/a+/.test(""));
console.log(/a+/.test("aaa"));
console.log(/a?/.test(""));
console.log(/a{2,3}/.test("aa"));
console.log(/a{2,3}/.test("aaaa"));

Section 8: Greedy Versus Lazy Matching

Greedy and lazy matching describe how quantifiers behave when they can match different lengths, such as when a pattern with * or + could match a short sequence or a long sequence, both of which would allow the overall pattern to succeed. By default, quantifiers are greedy, meaning they match as much as possible, while still allowing the rest of the pattern to match, which is useful for most cases, such as matching a whole word or a whole number, where you want the longest possible match. For example, the pattern /<.*>/ applied to the text <b>hello</b> with greedy matching will match from the first < to the last >, giving <b>hello</b> as a single match, because .* greedily consumes as much as possible, including the middle > and < characters, before backtracking just enough to allow the final > to match. That greedy behaviour, longest match first, is often surprising for beginners who expect <.*> to match only <b> and then </b> separately, but greedy matching explains why it matches the whole string as one tag-like sequence instead.

Lazy matching, also called non-greedy or reluctant matching, is achieved by adding a question mark after a quantifier, such as *?, +?, or ??, making the quantifier match as little as possible, while still allowing the rest of the pattern to match. For example, /<.*?>/ applied to <b>hello</b> with lazy matching will match <b> first, because .*? matches as few characters as possible before the next >, which is immediately after b, giving a short match, and with the global flag, it will then match </b> as a second match, which is the behaviour most people expect when extracting tags from HTML-like text. That lazy behaviour, shortest match first, is useful when you want to match the smallest possible sequence that satisfies the pattern, such as the first closing delimiter, rather than the last one, which is common for quoted strings, tags, and delimited fields where you want to stop at the first delimiter, not the last.

Choosing between greedy and lazy depends on your task: use greedy when you want the longest match, such as matching a whole line, a whole word, or a whole number, where longer is correct, and use lazy when you want the shortest match, such as matching up to the first delimiter, where longer would overshoot into subsequent delimiters and include unwanted content. A common mistake is to use greedy matching for delimited text, such as quoted strings, where greedy will match from the first quote to the last quote in a line, including intermediate quotes and content, rather than matching each quoted string separately, which lazy matching would do correctly by stopping at the first closing quote. Recognising that delimited text usually needs lazy matching, while whole-value matching usually needs greedy matching, is a key pattern design judgement that will help you avoid overshoot bugs where matches include too much text because greedy quantifiers consumed beyond the intended boundary.

const text = "<b>hello</b> and <i>world</i>";
console.log(text.match(/<.*>/));
console.log(text.match(/<.*?>/g));
console.log('"one" and "two"'.match(/".*?"/g));

Section 9: Groups and Capturing

Groups, written with parentheses, serve two main purposes in regex: they group pattern elements together so that quantifiers and alternation apply to the whole group, rather than to a single element, and they capture the text matched by the group, so that it can be retrieved separately after matching, which is useful for extracting parts of a match, such as area code from a phone number or username from an email. For example, /(ab)+/ groups ab together, so the plus applies to the whole ab sequence, matching ab, abab, and ababab, whereas /ab+/ without grouping applies plus only to b, matching ab, abb, and abbb, which is a different set of strings, as discussed for quantifier scope earlier. That grouping for quantifiers and alternation, parentheses as grouping, is the first purpose, and it is essential for describing repeated sequences or alternative sequences that consist of multiple characters, rather than single characters.

The second purpose, capturing, means that when a pattern with groups matches, each group's matched text is stored separately and can be accessed via match results, such as match[1] for the first group, match[2] for the second group, and so on, in order of opening parentheses, with match[0] being the entire match. For example, the pattern /(\d{3})-(\d{4})/ applied to 555-1234 will capture 555 as group one and 1234 as group two, allowing you to extract area and number parts separately, rather than only getting the whole match 555-1234, which would require further splitting to separate its parts. That capturing extraction, groups as named or numbered parts of a match, is extremely useful for parsing structured text, such as dates, phone numbers, URLs, and log lines, where you need individual fields, not just the whole matched string, and it is one of the most powerful features of regex for data extraction tasks.

Groups can be nested, with groups inside groups, and their numbering follows the order of opening parentheses, from left to right, including outer groups before inner groups, which can be confusing for complex patterns with many nested groups, but which becomes manageable if you count opening parentheses in order and keep patterns as simple as possible, avoiding unnecessary nesting where a flat group structure would suffice. For example, in /((\d{3})-(\d{4}))/, group one is the whole match inside outer parentheses, group two is the area code, and group three is the number part, because opening parentheses appear in that order: outer first, then area, then number. That numbering, by opening order, is a rule worth memorising, because it determines how you access captured groups from match results, and miscounting groups is a common bug when patterns have many groups, leading to accessing the wrong group index and getting unexpected text.

Groups also interact with alternation, where parentheses define the scope of alternatives, such as /(cat|dog)/ matching either cat or dog as a whole, versus /cat|dog/ without grouping, which also matches cat or dog, but with different precedence when combined with other pattern elements, such as /^cat|dog$/ which matches cat at start or dog at end, rather than a whole cat or dog string, because alternation has low precedence and applies to the largest surrounding pattern unless grouped.

const match = "555-1234".match(/(\d{3})-(\d{4})/);
console.log(match[0]);
console.log(match[1]);
console.log(match[2]);

Section 10: Non-Capturing Groups

Non-capturing groups, written as (?:...) with a question mark and colon after the opening parenthesis, group pattern elements together for quantifiers and alternation, just like capturing groups, but they do not capture their matched text for later retrieval, which is useful when you need grouping for structure but do not need to extract the group's text separately. For example, the pattern /(?:ab)+/ matches one or more ab sequences, just like /(ab)+/, but it does not store ab sequences as a captured group, so match results will not include a group for ab, which is cleaner when you only care about the whole match, not about its parts, and when you want to avoid cluttering group numbering with groups that are only for structure, not for extraction. That cleanliness, grouping without capturing, becomes important in complex patterns with many groups, where capturing groups for structure would shift the numbering of groups you actually want to capture, making it harder to access the right groups by index and increasing the chance of off-by-one errors in group access.

Non-capturing groups are also slightly more efficient than capturing groups, because the regex engine does not need to store captured text for them, although that performance difference is usually negligible for everyday patterns and should not be the primary reason to choose non-capturing groups; clarity and group numbering are more important reasons. The primary reason to use non-capturing groups is to keep group numbering clean and to signal intent: when a reader sees (?:...), they know immediately that the group is for structure only, not for extraction, whereas when they see (...), they expect that the group's text will be used somewhere, either in code that accesses match groups or in a replacement that references groups, as we will learn later. That intent signalling, through group syntax, improves pattern readability for other developers, who can distinguish structural groups from extraction groups at a glance, without needing to search code for group accesses to determine which groups matter.

A common use of non-capturing groups is for optional or repeated parts of a pattern that are not needed separately, such as an optional country code in a phone pattern, written as (?:\+\d{1,3} )? for an optional plus followed by digits and a space, where the whole country code part is optional as a unit, but its text does not need to be captured separately from the whole phone number, because the whole match already includes it if present. Another common use is for alternation groups that are part of a larger pattern, such as /(?:cat|dog) food/ for cat food or dog food, where the animal part is an alternative, but you do not need to capture which animal matched separately, because the whole match already contains it, and capturing it would add an unnecessary group to match results. Those examples show that non-capturing groups are not a rare advanced feature, but a common tool for everyday patterns where grouping is needed for structure but extraction is not needed for that particular group.

console.log("abab".match(/(?:ab)+/));
console.log("abab".match(/(ab)+/));
console.log("555-1234".match(/(?:\d{3})-(\d{4})/));

Section 11: Alternation: This or That

Alternation, written with a vertical bar |, allows a pattern to match any one of several alternatives, such as cat or dog, red or blue, or a specific set of words, codes, or formats, which is essential for describing text that can take multiple forms, where a single literal or class cannot capture all possibilities. For example, /cat|dog/ matches either cat or dog, wherever either appears, while /(?:red|blue|green)/ matches any one of those three colours as a unit, which is useful for validating inputs that must be one of a known set, such as a colour choice, a category, or a file type, where the valid values are enumerable and few, rather than describable by a character class or quantifier alone. Alternation is therefore a choice operator, similar to OR in logic, where the pattern succeeds if any alternative matches, and fails only if none match, which is a flexible way to describe varied but finite possibilities in text.

Alternation has low precedence, meaning it applies to the largest surrounding pattern unless grouped, as discussed for groups earlier, which can cause surprising matches when alternation is combined with other elements without grouping. For example, /^cat|dog$/ matches either cat at the start of text, or dog at the end of text, but not necessarily a whole cat or dog string, because the alternation splits the pattern into ^cat and dog$, two separate branches, each with its own anchor, rather than into a single anchored cat-or-dog pattern. To match a whole cat or dog string, you must group the alternatives and anchor the group, as /^(?:cat|dog)$/, where the anchors apply to the grouped alternatives as a unit, requiring the entire text to be exactly one alternative, with nothing before or after. That grouping for alternation scope, like grouping for quantifiers, is essential for correct alternation patterns, especially for validation where whole-text matching is required, and forgetting to group is a common alternation mistake that leads to overly permissive matches.

Order of alternatives in alternation matters for matching, because the regex engine tries alternatives from left to right and returns the first one that allows the overall pattern to succeed, rather than the longest or best alternative overall. For example, /cat|catalog/ applied to catalog will match cat first, because cat is listed first and matches at the start, even though catalog is a longer and more complete match for the text, and the engine will not try catalog if cat already allows the pattern to succeed, unless backtracking due to later pattern elements requires a longer alternative. That left-to-right, first-success behaviour means that for overlapping alternatives, you should generally list longer alternatives first, such as /catalog|cat/, so that the longer match is tried before the shorter one that is a prefix of it, ensuring that the intended longer match is preferred when both could match. That ordering rule, longer first for overlapping alternatives, is a practical tip that prevents prefix alternatives from shadowing longer ones, which is a subtle bug that can cause extraction to return truncated matches instead of full ones.

Section 12: The Dot and Matching Any Character

The dot . is a special regex character that matches any single character except a newline, by default, which makes it useful for describing patterns where a character's exact value does not matter, only that a character exists at that position, such as matching any three-letter word with a pattern like /.../ or matching a character between two known characters, such as /a.c/ for a, any character, c, which matches abc, aXc, and a c, but not ac, because dot requires exactly one character, not zero, and not a newline unless the dotAll flag is used, which we will cover later. That any-character behaviour, with the newline exception, is powerful for flexible matching, but it is also overly broad for many tasks, where you actually mean a specific set, such as a digit or a letter, and using dot instead of a specific class would allow invalid characters to match, such as matching a digit position with any character, including letters and punctuation, which would be incorrect for number validation. That over-breadth, dot matches too much for specific tasks, is why dot should be used carefully, only when any character is truly acceptable, and why specific classes are preferable when the character set is known and limited.

Dot's newline exception is important for multiline text, where dot will not match newline characters, so a pattern like /a.*b/ applied to text with a newline between a and b will not match across the newline by default, because .* cannot cross the newline boundary, stopping at the end of the line. That line-boundary behaviour is useful for line-based matching, where you want to match within a single line, not across lines, such as matching a word on one line without including the next line's content, but it can surprise beginners who expect dot to match absolutely any character, including newlines, and who find that their patterns fail on multiline text for no apparent reason, when the real reason is dot's newline exception. To match across lines, you need the dotAll flag, written as s, which makes dot match newlines as well, or you need to use a character class that explicitly includes newline, such as [\s\S], which matches any character including newline by combining whitespace and non-whitespace, a common workaround before dotAll was widely available, and still useful for compatibility with older environments where dotAll may not be supported.

Dot also interacts with greedy and lazy quantifiers, as discussed earlier, where .* greedily matches as much as possible within a line, and .*? lazily matches as little as possible, both respecting the newline boundary by default, which affects match lengths for patterns that use dot with quantifiers to match sequences of unknown characters, such as matching quoted strings, tags, or delimited fields, where dot's breadth can cause overshoot if greedy, or correct short matches if lazy, depending on delimiters and on whether newlines should be included.

Section 13: Word Boundaries

Word boundaries, written as \b, are zero-width assertions that match a position between a word character, as defined by \w, and a non-word character, or between a word character and the start or end of text, without consuming any characters themselves, which makes them ideal for matching whole words rather than substrings inside larger words. For example, /\bcat\b/ matches cat as a whole word in I have a cat, but it does not match cat inside catalog or scatter, because in those larger words, cat is not bounded by word boundaries on both sides: in catalog, cat is followed by a word character a, not a boundary, and in scatter, cat is preceded by a word character s, not a boundary, so the boundary assertions fail even though the letters cat appear as a substring. That whole-word matching, boundaries on both sides, is the primary use of \b, and it solves the substring problem discussed for literal matches earlier, where simple literals matched inside larger words unintentionally, by requiring that matched words stand alone as separate tokens, separated by spaces, punctuation, or text boundaries.

Word boundaries are defined in terms of \w, which includes letters, digits, and underscore, so a boundary exists where a \w character meets a non-\w character, or where a \w character meets the start or end of text. That definition means that underscore is considered a word character, so /\bcat\b/ will not match cat inside _cat or cat_, because underscore is a word character and therefore does not create a boundary, which can surprise beginners who think of underscore as punctuation, but who should remember that \w includes underscore by design, for programming identifiers and similar word-like tokens where underscore is part of words. Similarly, digits are word characters, so /\b123\b/ will match 123 as a whole number token, but not 123 inside 1234, because the following digit is a word character and prevents a boundary, which is correct for whole-number matching, where you want to match complete numbers, not prefixes of longer numbers.

The negated word boundary, written as \B, matches positions that are not word boundaries, such as between two word characters or between two non-word characters, which is less commonly used than \b, but useful for specific tasks such as matching a substring that must be inside a larger word, rather than at its edge, or for ensuring that a pattern does not start or end at a word boundary when you want to match internal parts of words. For example, /\Bcat/ matches cat inside scatter, where cat is preceded by a word character and therefore not at a boundary, but it does not match cat as a standalone word, where cat is at a boundary at its start. That internal matching, with \B, is a specialised tool for tasks where you specifically want non-boundary positions, such as finding infixes or suffixes inside words, and it complements \b by allowing you to express both boundary and non-boundary requirements explicitly, rather than relying on substring matching alone, which cannot distinguish boundary from non-boundary positions.

console.log(/\bcat\b/.test("scatter"));

Section 14: Flags: g, i, m, and s

Flags are letters added after a regex literal's closing slash, such as /pattern/gi, that modify how the pattern matches, including whether it is case-sensitive, whether it finds all matches or only the first, whether anchors apply per line or per text, and whether dot matches newlines. The most common flags are g for global, which finds all matches in text rather than stopping at the first, i for case-insensitive, which ignores case differences between pattern and text, m for multiline, which makes ^ and $ match at line starts and ends rather than only at text start and end, and s for dotAll, which makes dot match newline characters as well as other characters. Learning those four flags, g, i, m, s, covers most everyday flag needs, and understanding each flag's effect on matching behaviour is essential for writing patterns that work correctly for searches, replacements, and validations where case, multiplicity, line structure, or newline handling matter.

The global flag g affects methods such as match, replace, and matchAll, by causing them to process all matches in text, rather than only the first, which is the default without g. For example, "cat and cat".match(/cat/) without g returns only the first cat, while "cat and cat".match(/cat/g) returns both cats as an array, which is necessary when you need to count, extract, or replace all occurrences, not just the first. For test, the global flag has a subtle side effect involving lastIndex, where test remembers the position of the last match and starts the next test from there, which can cause alternating true and false results when the same global regex is tested repeatedly against different strings, a common beginner pitfall that is avoided by either not using g with test, or by resetting lastIndex to zero before each test, or by creating a fresh regex for each test. That lastIndex behaviour, global regexes are stateful, is important to understand, because it makes global patterns behave differently from non-global patterns in ways that are not obvious from their syntax alone, and it is a frequent source of confusing test results for developers who reuse global regex objects across multiple test calls.

The case-insensitive flag i makes matching ignore case, so /cat/i matches cat, Cat, CAT, and any mixed case variation, which is useful for searches and validations where case should not matter, such as checking for a word in user text that might be capitalised at sentence starts, or validating a code that should be accepted in any case. Without i, matching is case-sensitive, as discussed earlier, which is appropriate when case matters, such as for passwords or for codes where uppercase and lowercase have different meanings, but for most text searches, i is the right choice to avoid missing matches due to capitalisation differences that users do not consider meaningful. Combining i with other flags, such as gi for global case-insensitive matching, is common, allowing you to find all matches regardless of case, which is the typical requirement for search and replace features that should handle varied capitalisation in user text.

console.log("cat and cat".match(/cat/g));
console.log(/^cat/m.test("dog\ncat"));
console.log(/a.c/s.test("a\nc"));

Section 15: Testing with test()

The test method is a RegExp method that checks whether a pattern matches anywhere in a given string, returning true if a match exists and false otherwise, without returning match details, which makes it ideal for simple existence checks, such as validating whether an input contains a required pattern, whether a text includes a keyword, or whether a string matches a validation pattern as a whole, when combined with anchors. For example, /^\d+$/.test("123") returns true, because the entire string is digits, while /^\d+$/.test("12a") returns false, because the string contains a non-digit, and /cat/.test("I have a cat") returns true, because cat appears somewhere in the text, even though the whole text is not cat. That boolean return, true for match and false for no match, is the simplest regex result, and it is the right tool when your question is Does this match, rather than What matched or Where did it match, which require other methods that return match details.

Using test correctly involves understanding its interaction with the global flag, as discussed earlier, where a global regex remembers its lastIndex and starts the next test from there, rather than from the start of the string, which can cause surprising alternating results when the same global regex object is reused for multiple test calls. For example, a global regex /cat/g tested against "cat" will return true on first call, with lastIndex set to after the match, and then false on second call against the same string, because it starts searching from lastIndex, which is at the end of the string, finds no further match, and resets lastIndex to zero, only to return true again on third call, creating a true, false, true pattern that confuses beginners who expect test to be stateless and to return true consistently for matching strings. To avoid that statefulness, you should either use non-global regexes with test, which are stateless and always start from the beginning, or reset lastIndex to zero before each test with a global regex, or create a fresh regex object for each test, all of which ensure consistent, predictable test results. For most validation and existence checks, using a non-global regex with test is the simplest and safest choice, because you do not need global matching for a boolean existence check, and non-global test avoids lastIndex pitfalls entirely.

Test is also useful in conditionals and in array methods such as filter, where you need to select strings that match a pattern, such as filtering a list of filenames to those ending with .txt, using a pattern like /\.txt$/ and test in a filter callback, which returns true for matching filenames and false for others, producing a filtered list of only matching items. That filter-plus-test pattern, array.filter(item => pattern.test(item)), is a common idiom for regex-based filtering, and it is concise and readable, because test's boolean return fits naturally into filter's predicate requirement, which also expects a boolean.

Section 16: Searching with search()

The search method is a String method that takes a regex pattern and returns the index of the first match in the string, or -1 if no match exists, which makes it useful for finding where a pattern first occurs, rather than just whether it occurs, as test does, or what it matches, as match does. For example, "hello world".search(/world/) returns 6, because world starts at index 6 in the string, counting from zero, while "hello world".search(/cat/) returns -1, because cat does not appear, which is a clear signal for no match that can be checked with === -1 or >= 0, similar to indexOf for literal strings, but with regex pattern power instead of literal-only searching. That index return, position of first match or -1, is the key difference between search and test, which returns a boolean, and between search and match, which returns match details but not directly an index, although match results also include an index property that can be used similarly, but search is more direct when only the position is needed.

Search ignores the global flag, always finding the first match and returning its index, regardless of whether the regex is global, which distinguishes it from test with global regexes, where lastIndex affects subsequent calls, and from match with global flag, where all matches are returned. That ignoring of global flag makes search predictable and stateless, always starting from the beginning and returning the first match position, which is appropriate for its purpose, finding the first occurrence, where global matching for all occurrences would be unnecessary work and would complicate the return value, which is a single index, not a list. For tasks where you need all match positions, you should use matchAll or a loop with exec and global flag, rather than search repeatedly, because search always returns the first position and cannot be used to find subsequent positions without slicing the string and searching again, which is inefficient and error-prone compared to proper global matching methods.

Search is particularly useful for tasks such as finding the position of a pattern to extract surrounding context, such as finding where a keyword first appears in a document to show a snippet around it, or for checking whether a pattern appears before or after another pattern, by comparing search indices for two patterns. For example, to check whether a document contains a title before a body section, you might search for title pattern and body pattern and compare their indices, ensuring that title index is less than body index, which is a positional check that test alone cannot provide, because test only tells you whether each pattern exists, not their relative order. That positional reasoning, using search indices to understand text structure, is a valuable skill for document processing, log analysis, and other tasks where the order and location of patterns matter, not just their existence.

Section 17: Matching with match()

The match method is a String method that takes a regex pattern and returns match details, with behaviour that depends on whether the pattern has the global flag, which is a crucial distinction to understand for correct use. Without the global flag, match returns a single match object, similar to exec, containing the full matched text as element zero, captured groups as subsequent elements, an index property indicating where the match starts, and an input property containing the original string, or null if no match exists. That single-match object, with groups and index, is rich in details and is ideal when you need to extract one match and its parts, such as a phone number's area code and number, or a date's year, month, and day, from a string where only one match is expected, or where you only care about the first match. With the global flag, match returns an array of all matched substrings, without group details or indices, or null if no matches exist, which is ideal when you need all matches as simple strings, such as all numbers in a text, but insufficient when you need groups or positions for each match, in which case matchAll or exec in a loop is more appropriate, as we will discuss later.

Understanding match's dual behaviour, single detailed match without g versus array of simple matches with g, prevents confusion when match returns different shapes for seemingly similar patterns that differ only by a flag. For example, "555-1234".match(/(\d{3})-(\d{4})/) without g returns an object with full match, groups, index, and input, allowing you to access area code via match[1] and number via match[2], while "555-1234 and 555-5678".match(/(\d{3})-(\d{4})/g) with g returns ["555-1234", "555-5678"], an array of full matches without group details, so accessing match[1] would give the second full match, not the first group, which is a different meaning for the same index, leading to bugs if you assume group access works with global match. That shape difference, groups without g versus strings with g, is a frequent source of match bugs, and it is why you should choose match without g for group extraction and match with g for simple all-matches listing, and use matchAll for all-matches with groups, which combines global matching with detailed group information in a way that match alone cannot provide.

Match also returns null on no match, in both global and non-global forms, which must be checked before accessing match elements, otherwise you will get a TypeError from trying to read properties of null, such as match[1] when match is null because no match was found. That null check, if (match) before using match details, is a standard defensive practice for match, similar to -1 checking for search and false checking for test, and it should become automatic whenever you use match, because forgetting it is a common bug where no-match cases crash programs that assumed a match would always exist, such as when validating user input that might not match, or when searching documents that might not contain the pattern.

Section 18: Replacing with replace()

The replace method is a String method that takes a regex pattern and a replacement, and returns a new string with matched parts replaced, without modifying the original string, which is essential for text cleaning, formatting, and transformation tasks where you need to change text based on patterns, rather than just finding matches. Without the global flag, replace replaces only the first match, while with the global flag, it replaces all matches, which is a crucial distinction for cleaning tasks where you typically want to replace all occurrences, such as removing all extra spaces, replacing all commas, or masking all numbers, rather than only the first occurrence, which would leave other occurrences unchanged and produce incomplete cleaning that looks correct for the first match but fails for subsequent ones. That global versus first-only behaviour, like match's dual behaviour, must be understood to use replace correctly, and forgetting the global flag is a common replace bug where only the first match is replaced and users wonder why other matches remain in the cleaned text.

Replacement strings in replace can include special patterns for captured groups, such as $1 for the first captured group, $2 for the second, $& for the entire match, and $$ for a literal dollar sign, allowing you to build replacement text that incorporates parts of the original match, rather than replacing it with a fixed string. For example, replacing a date pattern /(\d{4})-(\d{2})-(\d{2})/ with "$3/$2/$1" rearranges year-month-day to day/month/year, using group references to reorder parts, which is a powerful transformation that would be tedious to implement with manual string splitting and joining, but is concise with replace and group references. Similarly, replacing with a function, where the replacement argument is a function that receives match details and returns the replacement string, allows dynamic replacements based on match content, such as uppercasing matched words, masking digits with asterisks based on length, or formatting numbers with commas, which fixed replacement strings cannot do, because they cannot compute based on match values. That function replacement, replace with a callback, is an advanced but valuable technique for transformations where replacement depends on matched text, and it is worth learning after mastering fixed replacements with group references.

Replace is also useful for cleaning tasks such as removing unwanted characters, normalising whitespace, and reformatting text, where patterns describe what to remove or change, and replacements describe what to put in its place, often an empty string for removal, a single space for whitespace normalisation, or a formatted version for reformatting. For example, replacing /\s+/g with a single space normalises multiple spaces, tabs, and newlines into single spaces, which is useful for cleaning pasted text that may contain irregular whitespace, while replacing /[^a-zA-Z0-9 ]/g with an empty string removes all characters except letters, digits, and spaces, which is useful for creating safe slugs or for cleaning input for display, although that removal should be used carefully, as discussed for sanitisation, where removing characters is not always the right approach versus escaping them.

Section 19: Splitting Text with split()

The split method is a String method that takes a regex pattern as a separator and divides a string into an array of substrings, split at each match of the separator, without including the separator itself in the results, unless the pattern contains capturing groups, in which case captured group texts are also included in the result array, which is a useful detail for splitting where separators themselves contain information you want to keep, such as splitting a log line by spaces while keeping the spaces, or splitting by delimiters while keeping delimiter values for further processing. For example, "a,b,c".split(/,/) returns ["a", "b", "c"], splitting at commas and discarding them, while "a1b2c".split(/(\d)/) returns ["a", "1", "b", "2", "c"], including captured digits in the results, because the separator pattern contains a capturing group whose matched text is preserved in the split output, which is a behaviour that can be surprising if you do not expect it, but useful when you need separators as well as parts.

Split with regex is more powerful than split with a literal string, because regex separators can describe variable delimiters, such as one or more whitespace characters with /\s+/, which splits at any whitespace sequence, regardless of whether it is spaces, tabs, or newlines, and regardless of length, producing clean parts without empty strings for multiple spaces, whereas split with a literal single space would produce empty strings for consecutive spaces, requiring additional filtering to clean up. That variable delimiter handling, with quantifiers and classes in the separator pattern, is the main advantage of regex split over string split, and it is essential for parsing text with irregular separators, such as pasted lists with mixed spaces and tabs, log lines with variable spacing, or CSV-like data with optional spaces after commas, where literal splitting would fail to handle variability correctly and would produce messy results with empty or whitespace-padded parts that need further cleaning.

Section 22: Validating Usernames and Passwords

Validating usernames and passwords with regex involves checking that they meet rules for allowed characters, length, and composition, such as usernames containing only letters, numbers, and underscores, with a length between three and twenty characters, and passwords containing a mix of character types, such as at least one uppercase letter, one lowercase letter, one digit, and one special character, with a minimum length, although password rules should be designed carefully to balance security with usability, as overly strict rules can frustrate users and lead to weaker passwords written down or reused, while overly lax rules allow easily guessed passwords that compromise security. Section 32: Multiline Matching

Section 33: DotAll and Matching Across Lines

DotAll, enabled by the s flag, makes the dot character match newline characters in addition to all other characters, allowing patterns with dot to match across line boundaries, which is essential for matching multiline structures such as quoted strings spanning lines, comments spanning lines, or blocks of text that start with a marker on one line and end with a marker on a later line, where the content between markers includes newlines that dot must cross to match the whole block as a single match. Without dotAll, dot stops at newlines, so a pattern like /"[^"]*"/ for quoted strings will fail to match a quoted string that spans lines, because the dot or negated class inside must cross a newline to reach the closing quote on a later line, and dot's newline exception prevents that crossing, causing the pattern to fail or to match only up to the newline, depending on the pattern's structure and on whether a negated class that includes newline is used instead of dot, which is a workaround for dotAll in older environments, as discussed earlier, where [\s\S] matches any character including newline by combining whitespace and non-whitespace, which together cover all characters, including newline, without needing the s flag.

Section 34: Lookahead in Plain Words

Lookahead is a zero-width assertion that checks whether text following the current position matches a pattern, without consuming that following text as part of the match, allowing you to require that a match be followed by a specific pattern, without including that following pattern in the matched result, which is useful for validations and extractions where context after a match matters for whether it should match, but should not be part of the extracted text itself. A positive lookahead, written as (?=...), succeeds if the following text matches the pattern inside, and fails otherwise, without advancing the matching position past the following text, so that subsequent pattern elements can still match that following text if needed, or so that the overall match ends before the lookahead pattern, excluding it from the result. For example, /\d+(?= dollars)/ matches digits only when they are followed by a space and the word dollars, returning only the digits, not the dollars part, which is useful for extracting prices where you want the number but not the currency word, or for validating that a number is followed by a specific unit, without including that unit in the extracted number itself.

A negative lookahead, written as (?!...), succeeds if the following text does not match the pattern inside, and fails if it does, also without consuming following text, allowing you to require that a match not be followed by a specific pattern, which is useful for excluding certain contexts, such as matching a word only when it is not followed by a specific suffix, or matching a username only when it is not followed by a disallowed character, or for password validation where you want to ensure that a password does not contain a forbidden substring, by using a negative lookahead at the start to reject passwords containing that substring, regardless of where it appears, which is a common lookahead use for negative requirements that cannot be expressed with simple character classes or quantifiers alone, because they involve absence of a pattern anywhere after a position, rather than presence of a specific character at a position.

Lookaheads are particularly useful for password validation with multiple requirements, as discussed earlier, where a single pattern can check for multiple independent requirements anywhere in the password, by using multiple lookaheads at the start, each checking for one requirement, such as (?=.*[A-Z]) for at least one uppercase letter anywhere, (?=.*\d) for at least one digit anywhere, and (?=.*[^A-Za-z0-9]) for at least one special character anywhere, followed by a main pattern for length and allowed characters, such as .{8,}, which together require all lookahead conditions to be satisfied for the overall pattern to match, regardless of the order in which required characters appear in the password, which is impossible to express with a simple sequential pattern that would require uppercase, digit, and special characters to appear in a fixed order, rather than in any order, as users naturally type passwords with mixed character types in arbitrary orders.

Section 35: Lookbehind in Plain Words

Lookbehind is a zero-width assertion that checks whether text preceding the current position matches a pattern, without consuming that preceding text as part of the match, allowing you to require that a match be preceded by a specific pattern, without including that preceding pattern in the matched result, which is the mirror image of lookahead, which checks following text, while lookbehind checks preceding text, both without consuming the checked text, so that matches can be context-sensitive on either side, with context requirements that do not become part of extracted text. A positive lookbehind, written as (?<=...), succeeds if the preceding text matches the pattern inside, and fails otherwise, without moving the matching position backward or including preceding text in the result. For example, /(?<=\$)\d+/ matches digits only when they are preceded by a dollar sign, returning only the digits, not the dollar sign, which is useful for extracting prices where you want the number but not the currency symbol, or for extracting values that follow a label, such as numbers after Price: where you want the number but not the label, by using a lookbehind for the label pattern that must precede the number, without including the label in the extracted number itself.

A negative lookbehind, written as (?<!...), succeeds if the preceding text does not match the pattern inside, and fails if it does, also without consuming preceding text, allowing you to require that a match not be preceded by a specific pattern, which is useful for excluding certain contexts, such as matching a word only when it is not preceded by a specific prefix, or matching a number only when it is not part of a larger number or identifier, by using a negative lookbehind for a digit or letter that would indicate that the number is actually part of a longer token, rather than a standalone number, which is a more precise way to handle token boundaries than word boundaries alone, because lookbehind can check for specific preceding characters or patterns, not just for word versus non-word boundaries, giving you finer control over preceding context requirements for matches where generic boundaries are insufficient, such as distinguishing a standalone price from a price inside a product code where preceding characters indicate a different context.

Lookbehind support in JavaScript has historically been more limited than lookahead support, with lookbehind being added to JavaScript in recent versions and not supported in older browsers, which means that patterns using lookbehind may fail in older environments with a syntax error, rather than simply not matching, which is a compatibility consideration that should guide your use of lookbehind in production code, where you should check browser support for your target audience, or provide fallback patterns without lookbehind for older environments, such as matching with preceding context included and then trimming it in code, rather than relying solely on lookbehind for extraction, which would break in older browsers.

Section 36: Backreferences in Plain Words

Backreferences allow a pattern to match the same text again that was previously matched by a capturing group, by referring to that group's number with a backslash, such as \1 for the first group, \2 for the second, and so on, which is useful for matching repeated words, paired delimiters, and other structures where the same text must appear twice in a specific relationship, such as matching a word, then later the same word again, or matching an opening quote, then later the same closing quote character, rather than any quote character, which is a distinction that matters for correctly matching quoted strings where opening and closing quotes must match in type, such as single quotes must close with single quotes and double quotes with double quotes, not with the opposite type, which a pattern without backreferences, such as /(['"]).*\1/ with backreference, handles correctly by requiring the closing quote to be the same as the opening quote captured in group one, whereas a pattern without backreference, such as /(['"]).*['"]/ , would incorrectly allow a single opening quote to close with a double quote, or vice versa, because it does not enforce that closing quote matches opening quote, only that some quote appears at each end, which is insufficient for correct quote matching.

Backreferences are also useful for finding repeated words in text, such as detecting duplicate words like the the in a sentence, with a pattern like /\b(\w+)\s+\1\b/ which captures a word, then requires whitespace, then requires the same word again, with word boundaries ensuring whole-word matching, which will match the the as a repeated word, but not the and then a different word, because \1 requires exactly the same text as group one, including case, unless the case-insensitive flag is used, in which case \1 matching becomes case-insensitive as well, matching The and the as the same word despite case difference, which may or may not be desired depending on whether duplicate detection should be case-sensitive or not, a detail that should be considered when using backreferences for duplicate detection in text where capitalisation at sentence starts could cause false positives or false negatives if case handling is not thought through. Using backreferences correctly involves understanding that they refer to the text actually matched by the group in a specific match attempt, not to the pattern that defined the group, so \1 matches the exact substring captured by group one in that attempt, which could be different for different match attempts, depending on what group one matched in each attempt, due to backtracking or due to different starting positions in the text.

Section 37: Common Regex Mistakes

Common regex mistakes fall into a handful of categories, and learning to recognise and avoid them will significantly improve the correctness of your patterns, just as with fetch, JSON, and error handling mistakes earlier. The first category is forgetting anchors for validation, where a pattern intended to validate an entire input is written without ^ and $, allowing it to match as a substring of invalid inputs, as discussed for anchors earlier, leading to invalid inputs passing validation because they contain a valid substring somewhere inside them, even though the whole input is invalid. The fix is to add anchors to validation patterns, requiring whole-text matching, and to test validation patterns with invalid inputs that contain valid substrings, such as abc123def for a three-digit code pattern, to confirm that anchors correctly reject them, rather than only testing with valid inputs that pass both anchored and unanchored patterns, which would not reveal the missing anchor bug, because valid inputs pass either way, while invalid substring inputs distinguish anchored from unanchored behaviour clearly.

The second category is forgetting to escape special characters, where a pattern intended to match literal punctuation, such as a dot, plus, or question mark, is written without escaping, causing the pattern to match broader text than intended, such as a dot matching any character instead of only a literal dot, leading to validation bugs where invalid characters pass because dot matched them as any character, rather than rejecting them as non-dot characters. The fix is to escape special characters when you mean them literally, and to test patterns with both the literal character and with other characters that should not match if escaping is correct, such as testing a decimal pattern with 3.14 versus 3x14, to confirm that dot is literal, not any character, which is a test pair that reveals escaping errors immediately, as discussed for escaping earlier, and which should become a habit for every pattern containing punctuation that could be special.

The third category is using greedy quantifiers for delimited text, where a pattern with .* greedily matches from the first delimiter to the last delimiter, merging multiple delimited items into one large match, instead of matching each item separately, as discussed for greedy versus lazy earlier, leading to extraction bugs where multiple quoted strings, tags, or fields are returned as one merged match, rather than as separate matches that can be processed individually. The fix is to use lazy quantifiers, such as .*?, for delimited text, or to use negated classes that explicitly exclude the delimiter, such as [^"]* for quoted strings, both of which stop at the first delimiter correctly, and to test delimited patterns with texts containing multiple delimited items, to confirm that they return separate matches, not one merged match, which is a test that reveals greedy overshoot immediately, whereas testing with a single delimited item would not, because greedy and lazy both return the same single item correctly when only one item exists, hiding the overshoot bug that only appears with multiple items.

Section 38: Catastrophic Backtracking in Plain Words

Catastrophic backtracking is a performance problem that occurs when a regex pattern with nested quantifiers, or with overlapping alternatives, causes the regex engine to try an exponentially large number of matching possibilities before failing, leading to extremely slow matching or freezing, especially for inputs that do not match but are close to matching, where the engine explores many combinations of quantifier lengths and alternative choices in an attempt to find a match that does not exist, wasting time exponentially as input length grows. In plain words, catastrophic backtracking happens when a pattern gives the engine too many ways to divide input text among its parts, such as a pattern like /(a+)+$/ applied to a long string of a's followed by a non-a character, where the engine must try all ways to split the a's between the inner and outer quantifiers, each split failing because the final character is not a, but the engine tries every split before concluding failure, with the number of splits growing exponentially with input length, turning a pattern that looks simple into one that can hang for seconds, minutes, or longer on moderately long inputs, which is a serious performance and availability risk, especially for patterns applied to user input, where attackers can craft inputs that trigger catastrophic backtracking deliberately, causing denial of service by making a server or browser spend excessive time on a single regex match, a vulnerability known as ReDoS, or regex denial of service.

Understanding catastrophic backtracking in plain words involves recognising patterns that are vulnerable: nested quantifiers, such as (a+)+, (a*)*, or (\w+\s*)+, where an inner quantifier and an outer quantifier both can match the same characters, creating many ways to partition input between them; overlapping alternatives, such as (a|aa)+, where alternatives overlap and the engine must try both for each position, creating many combinations; and patterns with quantifiers followed by optional parts that can also match the same characters, such as \d+.* where both parts can match digits, creating ambiguity about which part should match which digits. Those vulnerable patterns share a common feature: ambiguity, where the same input characters can be matched in many different ways by different parts of the pattern, and the engine must explore all ways when the overall pattern fails, because it cannot know in advance which way, if any, will lead to success, so it tries them all, with backtracking, leading to exponential exploration for ambiguous patterns on failing inputs, while succeeding inputs may match quickly via the first successful path, hiding the vulnerability until a failing input triggers the exponential search, which is why catastrophic backtracking often appears only in production with specific inputs, not in development with simple succeeding examples that match quickly and do not trigger extensive backtracking.

Section 40: Building Regex Step by Step

Building regex step by step means starting with a simple pattern for the core shape, testing it with examples, and then adding one element at a time, such as anchors, character classes, quantifiers, groups, or flags, testing after each addition to confirm that the pattern still matches intended examples and rejects unintended ones, rather than writing a complete complex pattern all at once and then debugging it as a whole when it fails, which is difficult because a failure in a complex pattern could be due to any of its parts, and isolating the faulty part requires breaking the pattern down anyway, which is more work than building it incrementally from the start, where each addition's effect is verified immediately and faulty additions are identified at the step where they were added, rather than after many steps have obscured which addition caused the failure. Section 43: Matching Word Lists and Keywords

Matching word lists and keywords with regex involves building a pattern that matches any of several words, using alternation, such as /\b(cat|dog|bird)\b/ which matches cat, dog, or bird as whole words, with word boundaries ensuring that longer words containing those keywords as substrings, such as caterpillar containing cat, do not incorrectly match as cat, which is important for keyword search, content filtering, and text analysis where whole-word matching is required, and where substring matching would produce false positives for words that merely contain keywords, but are not themselves keywords, a distinction that matters for search relevance, where users searching for cat expect results about cats, not about caterpillars, which happen to contain cat as letters, but are unrelated topics, showing that word boundaries are essential for keyword patterns, just as they are for single-word patterns, but even more important for lists where multiple keywords increase the chance of substring false positives across many words in a document, each of which could contain a keyword as a substring by coincidence, leading to many irrelevant matches if boundaries are omitted.

Building keyword patterns from lists programmatically, by joining list items with | inside a group, such as new RegExp("\\b(" + keywords.join("|") + ")\\b", "gi"), is a common technique for dynamic keyword lists that change at runtime, such as user-defined keywords, topic lists, or filter lists that are loaded from data, rather than hardcoded in pattern literals, which would require code changes for every list change, whereas programmatic construction allows lists to be updated in data without changing pattern code, with the pattern built from the list at runtime, which is more maintainable for lists that grow or change frequently, such as content filters that add new banned words, or search systems that add new topics, where list updates should be data changes, not code changes, and where pattern construction from lists automates that data-to-pattern conversion, handling joining, grouping, and boundary wrapping automatically, rather than requiring manual pattern editing for each list change, which is error-prone and tedious for large lists with many keywords that would be difficult to maintain as a single hardcoded pattern string.
