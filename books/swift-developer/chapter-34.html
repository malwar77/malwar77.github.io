Chapter 34: Security Basics for Swift Programs

Section 1: What Security Means for a Program

Security, for a program, means protecting the people who use it, their data, and the program itself from harm, whether that harm comes from mistakes, misuse, or deliberate attack. It is not a single feature that can be added at the end, like a coat of paint; it is a way of designing and writing code that considers, at each step, what could go wrong and who could be hurt. A secure program protects confidentiality, meaning private information stays private; integrity, meaning data is not changed without permission; and availability, meaning the program keeps working for legitimate users. Those three goals, often called the CIA triad, are a useful lens for thinking about any feature: does this feature keep private data private, does it prevent unauthorised changes, and does it keep working under misuse? Security also involves thinking about trust: which parts of a program can be trusted, which inputs can be trusted, and which users can be trusted with which actions? The default answer, in secure design, is to trust as little as possible: inputs from users, files, and networks should be treated as untrusted until they have been checked, and users should be given only the permissions they need. That cautious default is called zero trust for inputs and least privilege for permissions, and it is the foundation of most security practice. Security is not about paranoia; it is about care. A program that handles people's notes, messages, or personal details owes those people careful handling, and the habits in this chapter are how that care is expressed in code.

struct UserProfile {
    let username: String
    let isAdmin: Bool
}

func canEditSettings(_ user: UserProfile) -> Bool {
    return user.isAdmin
}

let regularUser = UserProfile(username: "Ada", isAdmin: false)
print(canEditSettings(regularUser))

The profile example shows least privilege in miniature: only an admin user may edit settings, and a regular user is correctly denied. That check, small as it is, is a security control, because it enforces a permission rule in code. Without it, any user could change settings, which might seem harmless in a tiny program but becomes serious as soon as settings affect other users or the program's behaviour. Security controls are often this small: a check here, a validation there, a permission test before an action. Their power comes from being applied consistently, at every point where a sensitive action is possible. As you read this chapter, look for those points in your own programs: places where data is read, changed, shared, or deleted, and ask who should be allowed to do each, and what checks enforce that. That questioning habit is the beginning of secure design, and it applies to programs of every size, from a command-line task manager to a large service.

Security thinking also applies to small, local programs, not just to large services. A local program that stores personal notes still owes its user confidentiality, and a local program that deletes files still owes its user integrity, because a mistake or a misused feature can cause real harm even without a network attacker.

Section 2: Threat Modelling in Plain Words

Threat modelling is the practice of thinking, before you build or while you are building, about what could go wrong, who might cause it, and what the consequences would be. It sounds formal, but in plain words it is just asking four questions: what are we protecting, who might try to harm it, how might they try, and what would happen if they succeeded? The answers guide where you spend your security effort, because you cannot protect everything equally, and you should protect the most valuable things against the most likely harms first. For a task manager like SwiftDay, the valuable things are the user's tasks and notes, which may be personal. The likely harms are accidental loss, unauthorised reading if the data file is shared, and corruption if the file is edited by another program. The unlikely harms, for a local tool, include sophisticated attacks that are more relevant to large services. Threat modelling helps you focus on the likely harms for your program, rather than worrying equally about every imaginable threat. It also helps you make trade-offs: a protection that is expensive or inconvenient may be worth it for highly sensitive data, but not for trivial data. A simple threat model can be written in a few sentences, and it should be revisited when a program changes, because new features bring new things to protect and new ways to harm them. Threat modelling is not about imagining movie-style attacks; it is about practical, proportionate thinking, grounded in what your program actually does and who actually uses it. That practicality is what makes it useful, even for small programs.

struct Note {
    let title: String
    let body: String
    let isPrivate: Bool
}

func displayTitle(of note: Note) -> String {
    if note.isPrivate {
        return "Private note"
    }
    return note.title
}

let privateNote = Note(title: "My diary", body: "Personal thoughts", isPrivate: true)
print(displayTitle(of: privateNote))

The note example shows a small threat-model decision in code: private notes have their titles hidden in listings, because a title itself might reveal something personal. That decision follows from asking what is being protected, personal notes, and how it might be harmed, by being seen in a list by someone glancing at the screen. The fix is small, showing a generic label instead of the title, but it reflects a considered judgement about sensitivity. Not every note needs that treatment; only private ones do, which is a proportionate response. When you threat-model your own programs, start with the data: which pieces are sensitive, and in what ways could they be exposed? Then look at the features: which features display, share, or change that data, and what checks do they need? Those two questions, about data and about features, produce a practical threat model without any formal framework. Write it down in a few sentences, keep it with the project, and update it when features change. That living document will guide your security decisions far better than vague worry.

A threat model should also consider accidental harm, not only deliberate attack. A user who mistypes a command, a program that deletes the wrong file, or a backup that overwrites good data are all harms that threat modelling can anticipate, and protections against them are often the same as protections against deliberate misuse.

Section 3: Validating Input from Users

Input validation means checking data that comes from outside your program, such as user typing, file contents, or network messages, before trusting or using it. It is one of the most important security habits, because unvalidated input is the source of a large fraction of program failures and security problems. Validation has two parts: checking that input has the expected shape, such as the right type, length, and format, and checking that it has sensible values, such as a number within range, or a string without unexpected control characters. A program that assumes input is well-formed will break, or behave insecurely, when it is not, and real input is often not well-formed, whether by mistake or by design. The defensive approach is to validate at the boundary, meaning as soon as input enters the program, before it is stored, displayed, or used in any operation. Validating early prevents bad data from spreading through the program, where it becomes harder to trace and more likely to cause harm. Validation should be strict: accept only what you know is safe, and reject everything else, rather than trying to list every possible bad input, which is an endless task. That allow-list approach, accepting known-good patterns, is more reliable than a deny-list approach, which tries to block known-bad patterns and inevitably misses new ones. For example, a username rule that accepts only letters, numbers, and a few safe characters is stronger than one that tries to block every dangerous character, because the safe set is small and known, while the dangerous set is large and changing. Validate early, validate strictly, and validate every input, not just the ones you expect to be problematic.

func isValidUsername(_ name: String) -> Bool {
    if name.isEmpty || name.count > 20 {
        return false
    }
    let allowed = CharacterSet.alphanumerics.union(CharacterSet(charactersIn: "_-"))
    return name.unicodeScalars.allSatisfy { allowed.contains($0) }
}

print(isValidUsername("Ada_123"))
print(isValidUsername("Ada Smith!"))

The username validator uses an allow-list: it accepts only letters, numbers, underscores, and hyphens, within a length limit, and rejects everything else. That strictness is a security strength, because it guarantees that any accepted username is safe to display, store, and use, without needing to check it again later. A username with a space or an exclamation mark is rejected, not because those characters are always dangerous, but because they are outside the known-safe set, and the program does not need them. That trade-off, a slightly narrower set of accepted inputs in exchange for guaranteed safety, is typical of good validation. When you write validators, define the safe set explicitly, check length and format, and reject anything outside the set with a clear message. Apply validation to every input boundary: user commands, file contents, configuration values, and network data. Consistent, strict validation at boundaries is one of the highest-value security habits, and it prevents a wide range of problems, from crashes to injection attacks, which are covered later in this chapter in defensive terms.

Section 4: Never Trust File Contents Blindly

Files are a common source of input, and their contents should never be trusted blindly, because a file may have been edited by hand, corrupted, created by an older version of the program, or supplied by someone else. A program that reads a file and assumes its contents are well-formed will crash, misbehave, or expose data when the file is not as expected. Defensive file handling starts by checking that the file exists and can be read, then by parsing its contents with a parser that reports errors, rather than by assuming the parse will succeed. If parsing fails, the program should report a clear error and, where appropriate, fall back to a safe default, such as an empty list, rather than crashing or using partial, possibly corrupt data. It should also validate the parsed values, just as it validates user input, because a file can contain values that are well-formed but out of range, such as a negative count or an absurdly large number that would cause excessive memory use. Another file hazard is size: a file that is far larger than expected could exhaust memory if loaded entirely, so programs that handle untrusted files should check size before loading, or read incrementally. Path handling is another file concern: a program that builds a file path from user input must ensure the resulting path stays within the intended folder, rather than allowing a crafted input to point elsewhere. That path check is a defensive measure that prevents a whole class of file access problems. Treat every file as untrusted input, validate its contents after parsing, and handle errors gracefully, and file handling becomes a safe, reliable part of your program rather than a source of surprises.

import Foundation

func loadTextSafely(from path: String) -> String? {
    guard FileManager.default.fileExists(atPath: path) else {
        return nil
    }
    return try? String(contentsOfFile: path, encoding: .utf8)
}

let text = loadTextSafely(from: "/tmp/example.txt")
print(text ?? "File could not be loaded")

The safe loader checks that a file exists before reading it, and returns nil gracefully if reading fails, rather than crashing. The caller handles nil with a clear fallback message, which is the graceful degradation that defensive file handling aims for. A program that crashed on a missing file would be fragile, while one that reports the problem and continues with a safe default is robust. You can extend this pattern by checking file size before reading, by validating the contents after reading, and by ensuring that paths built from user input stay within an allowed folder. Each of those checks is a small addition, but together they make file handling trustworthy. When you write file code, ask what could be wrong with the file: missing, unreadable, malformed, too large, or pointing elsewhere, and handle each case explicitly. That checklist turns file handling from a hopeful assumption into a verified process, which is the essence of defensive programming.

File handling should also consider what happens when two programs write to the same file at once, because the result can be a mixture of both writes. Using an actor to guard file access, as in an earlier chapter, or writing to a temporary file and then replacing the original, prevents that mixture.

Section 5: Safe Handling of Secrets in Code

Secrets, such as passwords, API keys, tokens, and private keys, require special handling in code, because a secret that leaks can be used by anyone who finds it, often without the owner knowing. The first rule is never to write a secret directly into source code, because source code is often shared, copied, or published, and a secret in code is a secret that has been given away. Instead, secrets should be supplied at runtime, from a secure store, an environment variable, or a configuration file that is not shared, and the code should read them from there. The second rule is never to log, print, or display a secret, as discussed in the logging chapter, because logs and screens are also places where secrets leak. The third rule is to keep secrets in memory only as long as needed, and to avoid storing them in plain text in files, unless those files are protected by the operating system's permissions and are never shared. The fourth rule is to use the platform's secure storage where it is available, such as a keychain or a credential store, rather than inventing your own storage, because platform stores are designed and tested for this purpose. The fifth rule is to rotate, meaning change, a secret if you suspect it has leaked, rather than hoping it has not been noticed, because a leaked secret remains usable until it is changed. These rules are simple, but they are violated surprisingly often, usually by convenience: it is easier to paste a key into code than to set up secure storage, and it is easier to print a token while debugging than to work with a masked value. Resist that convenience, because the cost of a leaked secret, unauthorised access, data exposure, and the work of cleaning up, far exceeds the effort of handling secrets properly from the start.

import Foundation

func apiKeyFromEnvironment() -> String? {
    return ProcessInfo.processInfo.environment["MY_APP_API_KEY"]
}

if let key = apiKeyFromEnvironment() {
    print("API key is set, length \(key.count)")
} else {
    print("API key is not set")
}

The example reads an API key from an environment variable, rather than embedding it in code, and it prints only whether the key is set and its length, never the key itself. That pattern, read from a secure source and never display, is the core of secret handling. In a real program, the key would then be used to authenticate a request, and it would not be stored in a log, a file, or a message. If the key were ever suspected of leaking, it would be changed in the secure source, and the code would pick up the new value without needing to change. That separation, code that uses a secret without containing it, is what makes secret rotation possible and leak cleanup manageable. When you need a secret in your programs, follow this pattern: obtain it from a secure source at runtime, use it only where needed, never display it, and never commit it to source code or to shared files. Those four habits will prevent the most common and most damaging secret leaks.

Section 6: Least Privilege in Your Own Programs

Least privilege is the principle that every part of a program, and every user of it, should have only the permissions it needs to do its job, and no more. It applies at several levels. For users, it means a regular user cannot perform admin actions, and an admin cannot do things that are not part of administration, which limits the damage if an account is misused. For code, it means a function that only needs to read a file should not be given permission to write or delete it, and a component that only needs one piece of data should not be given access to all data. For files, it means data files should be readable and writable only by the user who owns them, not by everyone on the system, which is controlled by file permissions. Least privilege limits damage in two ways: it reduces the harm if a part of the program is compromised, because the compromised part can only do what it was already allowed to do, and it reduces the harm from mistakes, because a mistaken operation cannot exceed its permissions. Applying least privilege requires thinking about permissions deliberately, rather than granting broad access for convenience. It is tempting to give everything full access while developing, to avoid permission errors, but that habit, if carried into a finished program, leaves it wide open. Instead, start with minimal permissions and add only what is needed, testing as you go. That approach produces permission errors during development, which are easy to fix by granting the specific permission needed, rather than security holes in production, which are hard to discover. Least privilege is a mindset as much as a technique: always ask, what is the minimum this user, function, or component needs, and grant exactly that.

struct FileAccess {
    let canRead: Bool
    let canWrite: Bool
}

func readFileIfAllowed(_ access: FileAccess) -> String {
    if access.canRead {
        return "File contents"
    }
    return "Access denied"
}

let readerOnly = FileAccess(canRead: true, canWrite: false)
print(readFileIfAllowed(readerOnly))

The file access example models permissions explicitly: a reader-only user can read but cannot write, and the code checks the permission before acting. That explicit check is the enforcement of least privilege. In a real program, permissions might come from the operating system, from a user account, or from a role system, but the pattern is the same: check before acting, and grant the minimum. A program that checks permissions consistently, at every sensitive action, is far harder to misuse than one that checks only at login, because a check at login does not prevent a regular user from reaching an admin function through another path. Defence in depth, meaning checks at multiple layers, is a related principle: check at the interface, and check again at the operation itself, so that a bypass of one check does not grant access. Least privilege plus defence in depth, applied consistently, is the backbone of secure program design, and it starts with the simple habit of asking, for each action, who should be allowed to do it, and enforcing that answer in code.

Section 7: Injection Problems in Plain Words

Injection is a class of security problem where untrusted input is mistaken for instructions, causing a program to do something the input's author intended rather than what the program's author intended. The classic example is a program that builds a command, a query, or a piece of structured text by inserting user input directly into it, without separating the input from the instructions. If the input contains characters that have special meaning in that structure, such as quotes, semicolons, or delimiters, those characters can change the structure's meaning, turning data into instructions. The defensive solution is to keep data and instructions separate, by using safe methods that treat input purely as data, never as instructions. For database queries, that means using parameterised queries, where the query structure is fixed and inputs are supplied as parameters that cannot alter the structure. For commands, it means avoiding building command strings from input, and instead passing arguments separately, so that they cannot be interpreted as additional commands. For structured text, such as HTML or formatted output, it means escaping special characters, so that they are displayed as text rather than interpreted as markup. The general principle is to use the safe, structured method provided by the platform or library, rather than building structured text by concatenation, which is fragile and error-prone. Injection problems are a large topic, and this section introduces only the concept and the general defence, because the specific defences vary by context. The key takeaway is the separation principle: data should stay data, and instructions should stay instructions, and any method that mixes them by string concatenation should be treated with suspicion and replaced by a structured alternative.

func safeMessage(for name: String) -> String {
    let escaped = name
        .replacingOccurrences(of: "<", with: "&lt;")
        .replacingOccurrences(of: ">", with: "&gt;")
    return "Hello, \(escaped)!"
}

print(safeMessage(for: "Ada"))
print(safeMessage(for: "<script>"))

The safe message function escapes angle brackets in a name before including it in output, so that a name containing markup characters is displayed as text rather than interpreted as markup. That escaping is a simple example of keeping data as data: the name is still shown, but its special characters are neutralised, so they cannot change the output's structure. In a real program, escaping should be done by a well-tested library for the specific output format, rather than by hand, because hand-written escaping often misses cases. But the principle is the same, whatever the format: treat input as data, neutralise its special characters for the context where it will be used, and prefer structured methods that do this automatically. When you build any output that combines fixed text with user input, ask whether the input could alter the output's structure, and if so, use escaping or a parameterised method. That question, asked consistently, prevents injection problems, which are among the most serious and most preventable security issues in software.

Injection defences should also be applied to output formats you might not think of as structured, such as file names, log messages, and command-line arguments, because each of those has characters with special meaning. Whenever input flows into a structured context, check how that context interprets special characters.

Section 8: Protecting Data at Rest

Data at rest means data stored somewhere, such as in a file, a database, or on a device, as opposed to data in transit, which is data being sent somewhere. Protecting data at rest involves several measures, depending on how sensitive the data is. The simplest measure is file permissions, which restrict who can read or write a file, as discussed under least privilege. A more thorough measure is encryption, which scrambles data so that it cannot be read without a key, even if someone gains access to the file itself. Encryption is appropriate for highly sensitive data, such as passwords, which should never be stored in plain text at all, a topic covered in the next chapter, or personal notes that a user wants to keep private. For less sensitive data, such as a task list, file permissions may be sufficient, and encryption may be unnecessary complexity. The decision depends on your threat model: what data is sensitive, who might gain access to the storage, and what would happen if they did? Another aspect of protecting data at rest is minimisation: do not store data you do not need, and delete data that is no longer needed, because data that does not exist cannot be exposed. A program that keeps old, unnecessary copies of sensitive data multiplies its exposure for no benefit. Backups are a related consideration: a backup of sensitive data needs the same protection as the original, because a backup is just another copy. When you design storage for a program, ask what data is stored, how sensitive it is, who can access the storage, and how long the data is kept. Those answers will tell you whether permissions are enough, whether encryption is warranted, and whether old data should be deleted. Protecting data at rest is not about encrypting everything; it is about matching protection to sensitivity, proportionately.

import Foundation

func savePrivateNote(_ text: String, to path: String) {
    let data = Data(text.utf8)
    try? data.write(to: URL(fileURLWithPath: path), options: [.completeFileProtection])
    print("Note saved with file protection")
}

savePrivateNote("Personal thoughts", to: "/tmp/private-note.txt")

The example saves a note with a file protection option, which is a platform feature that restricts access to the file, particularly when a device is locked. That option is a simple, platform-provided protection, and it illustrates the principle of using available protections rather than inventing your own. For more sensitive data, full encryption with a user-supplied key would be a stronger measure, but it also adds complexity, such as key management, which must be handled carefully. The right choice depends on sensitivity and on the platform's capabilities. For the programs in this book, the lesson is to think about storage protection deliberately: set appropriate file permissions, use platform protections where available, minimise stored sensitive data, and never store passwords in plain text. Those habits, applied proportionately, protect data at rest without adding unnecessary complexity. When in doubt, protect more sensitive data more strongly, and delete data you no longer need, because the safest data is data that does not exist.

Section 9: Protecting Data in Transit

Data in transit means data being sent from one place to another, such as from a program to a server, or between two programs, and it needs protection because networks, especially public ones, can be observed or interfered with by others. The standard protection for data in transit is encryption during transmission, using a secure protocol such as HTTPS for web traffic, which encrypts the data so that observers on the network cannot read it, and verifies the identity of the server, so that the program is talking to the intended server rather than an impostor. Using HTTPS, and the secure equivalents for other protocols, is not optional for sensitive data; sending sensitive data over an unencrypted connection exposes it to anyone on the network path. Another aspect of protecting data in transit is verifying what is received: a program that downloads data should check that it came from the expected source and has not been altered, using signatures or checksums where they are provided. That verification prevents a program from trusting tampered data, which could otherwise cause it to misbehave or to expose further data. A related habit is to avoid sending sensitive data unnecessarily: if a program can do its work without sending a password, a token, or personal details, it should, because data that is never sent cannot be intercepted. Minimising transmission, like minimising storage, reduces exposure. For the small programs in this book, which mostly work locally, data in transit is less central, but the principles still apply whenever a program talks to a network, even for a simple download. Use secure protocols, verify what you receive, and send only what is needed, and data in transit will be protected proportionately to its sensitivity.

import Foundation

func isSecureURL(_ urlString: String) -> Bool {
    guard let url = URL(string: urlString) else {
        return false
    }
    return url.scheme == "https"
}

print(isSecureURL("https://example.com/data"))
print(isSecureURL("http://example.com/data"))

The secure-URL check illustrates a simple defensive habit: before fetching data, check that the URL uses HTTPS, and refuse or warn if it uses plain HTTP for sensitive data. That check is not a complete security solution, because a secure protocol also involves certificate verification and other details handled by the platform's networking libraries, but it is a useful first line of defence, and it makes the program's expectation explicit. In a real program, you would use the platform's secure networking APIs, which handle encryption and verification, rather than implementing them yourself, because implementing cryptography correctly is extremely difficult and error-prone. The lesson is to use well-tested, platform-provided secure methods for network communication, and to check that you are using them, rather than assuming a connection is secure because it works. A connection that works over plain HTTP is not secure, even though it functions, and a program that accepts it for sensitive data is exposing that data. Check the scheme, use secure APIs, and verify received data, and data in transit will be handled responsibly.

Section 10: Authentication Versus Authorisation

Authentication and authorisation are two distinct security concepts that are often confused, and distinguishing them is essential for designing secure programs. Authentication is proving who you are, such as by providing a password, a token, or another credential that verifies your identity. Authorisation is proving what you are allowed to do, once your identity is known, such as whether you may read a particular file, edit a setting, or perform an admin action. A program must do both, in that order: first authenticate, to establish identity, and then authorise, to check permission for the specific action. Skipping authentication means anyone can claim any identity. Skipping authorisation means any authenticated user can do anything, regardless of their role. Both failures are serious, and they occur surprisingly often, usually because a developer assumes that one implies the other, or that checking at login is sufficient. Checking at login establishes identity, but it does not authorise every later action, because different actions require different permissions. Each sensitive action should therefore be authorised at the point where it is performed, based on the authenticated user's permissions, not merely on the fact that they are logged in. That point-of-action authorisation is a form of defence in depth, and it prevents a user who gains access to one function from automatically gaining access to all functions. The next chapter covers passwords and login concepts in more depth, including how credentials should be protected. For now, remember the distinction: authentication answers who are you, authorisation answers what may you do, and a secure program answers both, for every sensitive action, every time.

struct Account {
    let username: String
    let role: String
}

func isAuthenticated(_ account: Account?) -> Bool {
    return account != nil
}

func canDelete(_ account: Account?) -> Bool {
    guard let account = account else {
        return false
    }
    return account.role == "admin"
}

let admin = Account(username: "Ada", role: "admin")
let regular = Account(username: "Ben", role: "user")
print(isAuthenticated(admin))
print(canDelete(regular))

The account example separates the two checks: isAuthenticated merely checks that an account exists, while canDelete checks both that an account exists and that its role is admin. A regular user is authenticated but not authorised to delete, which is the correct outcome. If the program only checked authentication before deleting, the regular user would be wrongly allowed to delete. That distinction, applied at each sensitive action, is the core of secure access control. When you design a program with different user roles, write separate functions for authentication and for each authorisation check, and call the authorisation check at the point of the action, not just at login. That structure makes the security rules explicit and testable: you can write tests that check that regular users are denied admin actions, and that unauthenticated users are denied everything sensitive. Those tests are security tests, and they are as important as functional tests, because they verify the program's protections, not just its features.

Authorisation should also be rechecked when a user's role changes during a session, rather than caching a permission decision forever. A user who is demoted should lose admin abilities immediately, not at their next login, and a program that caches permissions indefinitely will fail that test.

Section 11: Safe Defaults

Safe defaults mean that a program, when it is first installed or when a setting is not specified, behaves in the safest reasonable way, rather than in the most permissive or most convenient way. For example, a program that shares data should default to sharing nothing, requiring the user to explicitly enable sharing, rather than defaulting to sharing everything and requiring the user to opt out. A program that asks for permissions should ask for the minimum it needs, rather than for broad access that it might use later. A feature that could expose private data should be off by default, and turned on only by a deliberate user choice. The reason safe defaults matter is that most users never change defaults, either because they do not know the settings exist, or because they trust the program's judgement. If the defaults are unsafe, most users will be unsafe, even though a safer option exists somewhere in the settings. Safe defaults therefore protect the majority of users, including those who never think about security. Designing safe defaults requires thinking about each setting from the user's perspective: what would a careful user want if they understood the implications, and is that the default? If a default is permissive for convenience, ask whether the convenience is worth the risk to users who will never change it. Often it is not, and a safer default, with an explicit opt-in for the permissive behaviour, is the right choice. Safe defaults are a form of respect for users: they assume users want protection, and they require a deliberate choice to give it up, rather than assuming users want exposure and requiring a deliberate choice to gain protection.

struct SharingSettings {
    var shareTasks = false
    var shareNotes = false
}

func describeSharing(_ settings: SharingSettings) -> String {
    if settings.shareTasks || settings.shareNotes {
        return "Sharing is enabled"
    }
    return "Sharing is disabled by default"
}

print(describeSharing(SharingSettings()))

The sharing settings default to disabled, so a new user shares nothing until they explicitly enable sharing. That default protects privacy without requiring any action from the user, which is exactly what safe defaults should do. If the defaults had been enabled, a user who never looked at settings would be sharing their tasks and notes without realising it, which is a privacy failure caused by a design choice, not by user error. When you design settings for your own programs, start with everything sensitive disabled, and require explicit opt-in for each sensitive capability. That starting point makes the program safe for the majority who never change settings, and it makes the choice to share a deliberate, informed one for those who do. Safe defaults are a small design decision with a large protective effect, because defaults are, for most users, the program's actual behaviour.

Safe defaults also apply to data collection: a program should collect nothing by default, and only start collecting a piece of data when the user enables the feature that needs it. That collection-by-need default prevents a program from gathering data it never uses, simply because a feature was left on.

Section 12: Fail Safely, Not Openly

Failing safely means that when something goes wrong, a program defaults to denying access, refusing an operation, or preserving data, rather than to granting access, performing the operation, or discarding data. The opposite, failing openly, means that an error causes a program to grant access it should not, or to proceed as if a check had passed, which is a serious security flaw. For example, if a permission check fails because of an error, the safe failure is to deny the action, because the program cannot confirm permission. An unsafe failure would be to allow the action, on the grounds that the check could not be completed, which turns an error into a bypass. Similarly, if a validation fails, the safe response is to reject the input, not to accept it in the hope that it is harmless. If a save fails, the safe response is to keep the old data and report the error, not to discard the old data and leave nothing. Failing safely requires thinking about each failure mode in advance: what happens if this check errors, if this file is missing, if this network call fails, and is the resulting behaviour safe? That thinking should be part of designing error handling, not an afterthought, because error paths are where security flaws often hide. A program that behaves securely in its normal paths but fails openly in its error paths is not secure, because attackers and accidents both tend to trigger error paths. Test your error paths deliberately, by simulating failures, and check that each one fails safely. That testing is a security practice as much as a reliability practice, and it catches the class of bugs where an error becomes an unintended permission.

enum PermissionResult {
    case granted
    case denied
    case error
}

func canProceed(_ result: PermissionResult) -> Bool {
    switch result {
    case .granted:
        return true
    case .denied, .error:
        return false
    }
}

print(canProceed(.granted))
print(canProceed(.error))

The permission function treats an error exactly like a denial, which is the fail-safe behaviour. An error in checking permission does not grant access; it denies it, because the program cannot confirm that access is allowed. That single design choice, grouping error with denied rather than with granted, prevents a whole class of bypasses. When you write code that checks permissions, validates input, or verifies data, decide in advance what the error case should do, and make it the safe option: deny, reject, or preserve. Write that decision explicitly in code, as in the switch above, rather than letting it fall out of a default case that might be wrong. Explicit fail-safe handling is easy to test: simulate an error and check that the result is denial, not permission. That test, simple as it is, guards against one of the most dangerous kinds of bug, where an error silently becomes an authorisation. Fail safely, always, and your program's error paths will be as secure as its normal paths.

Section 13: Keeping Software Updated

Keeping software updated, meaning using current versions of languages, libraries, frameworks, and tools, is a basic security practice, because updates often fix security vulnerabilities discovered in older versions. A program that uses an outdated library with a known vulnerability is exposed to that vulnerability, even if its own code is correct, because the vulnerability is in the dependency, not in the program. Attackers actively look for programs using known-vulnerable versions, because those vulnerabilities are documented and have known exploits, which makes them easy to use. Updating does not guarantee security, because new vulnerabilities are discovered in new versions too, but it removes the known, documented ones, which are the easiest to exploit. For a Swift program, updating means using a current Swift toolchain, keeping packages and dependencies current, and applying operating system updates to the machines where the program runs. It also means paying attention to security advisories for dependencies you use, and updating promptly when a vulnerability is announced, rather than postponing it indefinitely. Updating can introduce its own risks, such as a new version changing behaviour, so updates should be tested, as with any change, before being adopted. But the risk of not updating, leaving a known vulnerability open, is usually greater than the risk of updating carefully. Make updating a routine, such as checking for updates regularly, rather than a rare event, and your program will stay protected against the vulnerabilities that are easiest to exploit. That routine is a small investment with a large security return.

func isVersionSupported(_ version: Int, minimumSupported: Int) -> Bool {
    return version >= minimumSupported
}

print(isVersionSupported(5, minimumSupported: 3))
print(isVersionSupported(2, minimumSupported: 3))

The version check illustrates a simple policy: versions below a minimum supported version are not accepted, because they may lack security fixes. In a real program, that policy might apply to a dependency, a data format, or a protocol version, where older versions are known to be insecure. Enforcing a minimum version is a defensive measure that prevents a program from operating with outdated, vulnerable components. When you manage dependencies, record their versions, check for updates regularly, and set a minimum supported version where it matters. That record-keeping makes updating a deliberate process rather than an afterthought. It also helps when a vulnerability is announced: you can quickly check whether you use the affected version, and update if you do, rather than guessing. Keeping software updated is not exciting, but it is one of the most effective security practices, because it closes the vulnerabilities that are publicly known and actively sought by attackers.

Updating also includes the tools and platforms a program runs on, because an outdated operating system or runtime may lack security fixes that the program relies on. A program cannot be more secure than the platform it runs on, so platform updates are part of the program's security posture.

Section 14: Protecting Against Accidental Data Loss

Security is not only about deliberate attack; it also includes protecting data against accidental loss, which can be just as harmful to users. Accidental loss happens when a program deletes, overwrites, or corrupts data through a bug, a mistaken user action, or a failure during saving. Defensive measures against loss include confirming destructive actions, such as asking a user to confirm before deleting, and making deletion reversible where possible, such as moving items to a trash or archive instead of deleting them permanently. Another measure is safe saving: writing new data to a temporary file and then replacing the old file only after the write succeeds, so that a failure during saving does not destroy the old data. That atomic save pattern, where a save either fully succeeds or leaves the old data intact, prevents the worst kind of loss, where a crash during saving leaves a half-written file and no valid copy. Backups are another layer: a program that encourages or automates backups gives users a way to recover from loss, whether accidental or malicious. For a task manager, losing a user's tasks is a serious failure, even if no attacker is involved, because the tasks represent work, plans, and commitments. Protecting against loss is therefore part of security in the broad sense of protecting users and their data. When you design data handling, ask what happens if saving fails halfway, if a user deletes by mistake, or if a file is corrupted, and design measures, confirmations, reversible deletion, atomic saves, and backups, that limit the harm in each case. Those measures are not just conveniences; they are protections for the user's work.

import Foundation

func atomicSave(_ text: String, to path: String) -> Bool {
    let temporaryPath = path + ".tmp"
    do {
        try text.write(toFile: temporaryPath, atomically: true, encoding: .utf8)
        try FileManager.default.moveItem(atPath: temporaryPath, toPath: path)
        return true
    } catch {
        return false
    }
}

print(atomicSave("Important tasks", to: "/tmp/tasks.txt"))

The atomic save writes to a temporary file first, and only replaces the original after the write succeeds. If the write fails, the original remains untouched, so no data is lost. If the program crashes during the write, the temporary file may be left behind, but the original is still valid, which is far better than a half-written original. That pattern is a simple, effective defence against loss during saving, and it is worth using for any data that matters to users. You can combine it with backups, by keeping a copy of the previous version, and with confirmation for deletions, to cover the other loss scenarios. Each measure addresses a different failure mode, and together they make data loss unlikely and recoverable. When you handle user data, treat its preservation as a security responsibility, not just a functional one, and design saving, deletion, and backup with that responsibility in mind. Users trust programs with their work, and that trust deserves protection against accidents as well as against attacks.

Loss prevention should also consider that a user might run a program on a device that runs out of storage during a save. Checking available space before a large save, or handling a write failure gracefully with the old data intact, prevents a storage failure from becoming a data loss event.

Section 15: Privacy by Design

Privacy by design means considering users' privacy from the start of building a program, rather than adding privacy protections afterwards, and it involves several concrete practices. The first is data minimisation, which means collecting only the data a program genuinely needs, and no more. A task manager does not need a user's location, contacts, or browsing history, and collecting those would be a privacy violation, even if the data were stored securely, because the collection itself is unnecessary. The second is purpose limitation, which means using collected data only for the purpose it was collected for, and not repurposing it without consent. Data collected to save tasks should not be used for advertising, or shared with third parties, without the user's clear agreement. The third is transparency, which means telling users, in plain language, what data is collected, why, and how it is used, so that they can make informed choices. The fourth is user control, which means giving users ways to view, correct, and delete their data, because data about a user belongs, in a moral sense, to that user. Privacy by design is not just a legal requirement in many places; it is a design ethic that respects users as people, not as sources of data. It also reduces security risk, because data that is never collected cannot be leaked, and data that is deleted promptly cannot be exposed later. When you design a program, ask for each piece of data whether it is truly needed, what it will be used for, how long it will be kept, and how a user can delete it. If you cannot answer those questions satisfactorily, do not collect the data. That restraint is the heart of privacy by design, and it produces programs that users can trust with their personal information.

struct CollectedData {
    var tasks: [String] = []
    var notes: [String] = []
}

func describeCollection(_ data: CollectedData) -> String {
    return "This program stores \(data.tasks.count) tasks and \(data.notes.count) notes, and nothing else."
}

print(describeCollection(CollectedData(tasks: ["Buy milk"])))

The collected-data example stores only tasks and notes, which are the data a task manager needs, and its description states that plainly, with nothing else collected. That transparency, stating exactly what is stored, is a privacy practice in itself, because it lets users verify that the program collects only what it claims. A program that collected location or contacts without mentioning it would violate transparency, even if the data were never misused. When you build programs, be explicit about what you collect, collect only what you need, and provide a way to delete it. Those three practices, minimisation, transparency, and control, are the practical core of privacy by design. They are also good engineering, because less data means less storage, less complexity, and less exposure. Privacy and simplicity reinforce each other, and a program that respects privacy is usually a simpler, more focused program as well.

Privacy by design also includes being careful with analytics and crash reports, which can inadvertently collect personal data. If a program sends diagnostics, it should send only what is needed to diagnose, with personal details removed, and it should tell users that it does so.

Section 16: Secure Error Messages

Error messages should help legitimate users and developers understand what went wrong, without helping attackers understand how to exploit a program. That balance is the challenge of secure error messages. A message that is too vague, such as something went wrong, frustrates legitimate users, because they cannot tell what happened or what to do. A message that is too detailed, such as revealing a file path, a database structure, a username that exists, or an internal error that exposes implementation details, helps attackers, because it gives them information about the program's internals that they can use to craft an attack. The safe middle ground is to give users enough information to act, such as what went wrong in general terms and what to do next, while keeping internal details in logs that only developers can see. For example, a login failure should say that the username or password was incorrect, without saying which one, because saying the username does not exist tells an attacker that they can try other usernames until one is recognised as existing, which is information they should not have. Similarly, a file error should say that a file could not be loaded, without revealing its full path or the system's layout. Secure error messages require thinking about who will read the message and what they could do with the information in it. Messages shown to users should be general and actionable. Messages in logs, for developers, can be detailed, because logs are not shown to users and are protected by access controls. That separation, general for users and detailed for logs, is the key to error messages that are both helpful and safe.

func userFacingMessage(for error: String) -> String {
    switch error {
    case "notFound":
        return "The item could not be found. Please check and try again."
    case "permission":
        return "You do not have permission to do that."
    default:
        return "Something went wrong. Please try again later."
    }
}

print(userFacingMessage(for: "notFound"))
print(userFacingMessage(for: "unknown"))

The user-facing messages above are general and actionable, without revealing internal details. A not-found error tells the user to check and try again, which is what they need to know, without revealing what was searched for or where. An unknown error gives a generic message, rather than exposing an internal error code or stack trace that could help an attacker. Detailed diagnostics for those errors would belong in a log, where developers can read them, not in the user-facing message. When you write error messages, decide what the user needs to know to act, and put only that in the message. Put the rest, the internal details, in a log entry at an appropriate level, where it is available to developers but not to users. That separation protects the program's internals while still helping users, and it is a habit that should be applied to every error message a program shows. Secure messages are not less helpful; they are helpfully general, with details reserved for the right audience.

Secure messages should also avoid revealing whether an item exists when the user is not authorised to know. A message that distinguishes between not found and access denied tells an unauthorised user that the item exists, which is information they should not have, so a single generic message is safer in that case.

Section 17: Rate Limiting and Abuse Prevention

Rate limiting, introduced in the actors chapter as a technical pattern, is also a security measure, because it prevents abuse by limiting how often an action can be performed. Without rate limiting, an attacker can try many passwords quickly, send many requests to overwhelm a program, or scrape data at high speed, all of which are harder when each attempt is limited and slowed. Rate limiting works by counting attempts within a time window and refusing further attempts once a limit is reached, with the limit and window chosen to allow legitimate use while blocking abuse. For logins, a common limit is a small number of attempts, such as five, before a delay or a lockout, because legitimate users rarely need more, while attackers need many. For general requests, the limit is higher, because legitimate use involves many requests, but still bounded, to prevent overwhelming the program. Rate limiting should be combined with other measures, such as strong passwords and account lockout policies, because it slows abuse but does not eliminate it. It should also be designed to avoid harming legitimate users: a limit that is too strict will lock out real users who mistype, while a limit that is too loose will not deter attackers. The balance depends on the action's sensitivity and on normal usage patterns. Rate limiting is a defensive measure that assumes abuse will be attempted, and it limits the damage from each attempt, which is a realistic and practical approach to security. It does not require identifying attackers in advance; it simply enforces a fair-use rule that applies to everyone, which makes abuse expensive and slow, while leaving legitimate use unaffected.

actor LoginAttempts {
    private var attempts = 0
    let limit = 5

    func recordAttempt() -> Bool {
        if attempts < limit {
            attempts += 1
            return true
        }
        return false
    }

    func reset() {
        attempts = 0
    }
}

The login attempts actor counts attempts and refuses further ones once the limit is reached, which is the rate limiting pattern applied to logins. A legitimate user who mistypes a few times will stay within the limit, while an attacker trying many passwords will quickly hit it and be blocked. The actor guarantees that the count is accurate even under concurrent attempts, which is why the actor pattern matters here: a plain counter could be bypassed by concurrent attempts that each see a count below the limit. Rate limiting through an actor therefore combines two security ideas, limiting attempts and guarding the count, into one reliable control. When you implement rate limiting, choose limits based on legitimate use, test that legitimate users are not blocked, and make sure the counter itself is protected against races. Those three steps, sensible limits, legitimate-use testing, and a guarded counter, make rate limiting an effective and fair abuse prevention measure.

Rate limiting should also be applied to operations that are expensive, such as generating a large report or processing a big file, because an attacker who can trigger expensive operations repeatedly can exhaust resources even without guessing passwords. Cost-based limiting protects availability as well as accounts.

Section 18: Dependencies and Supply Chain Awareness

A program's dependencies, meaning the libraries, packages, and tools it uses from others, are part of its security, because a vulnerability in a dependency is a vulnerability in the program. Supply chain awareness means knowing what dependencies a program uses, where they come from, whether they are maintained, and whether they have known vulnerabilities. A dependency that is unmaintained, or that comes from an untrusted source, is a risk, because it may contain vulnerabilities that will never be fixed, or it may have been tampered with. The defensive practices are straightforward: use as few dependencies as necessary, prefer well-maintained, widely used ones from trusted sources, keep them updated, and check for known vulnerabilities regularly. For Swift programs, that means reviewing the packages in a manifest, understanding what each one does, and removing ones that are no longer needed, because every dependency is additional code that must be trusted. It also means being cautious about adding a new dependency for a small feature that could be implemented directly, because the dependency's risk may outweigh its convenience. Supply chain attacks, where a dependency is compromised to affect all programs that use it, are a real concern, and they are hard to detect, which is why minimising and vetting dependencies matters. You do not need to audit every line of a dependency's code, but you should know what it does, who maintains it, and whether it is actively updated. That awareness, combined with updating and minimising, is a proportionate response to supply chain risk for most programs, and it is far better than adding dependencies casually without considering their trust implications.

struct Dependency {
    let name: String
    let isMaintained: Bool
    let version: String
}

func isAcceptable(_ dependency: Dependency) -> Bool {
    return dependency.isMaintained
}

let library = Dependency(name: "ExampleKit", isMaintained: true, version: "2.1.0")
print(isAcceptable(library))

The dependency example models a simple acceptability check: a dependency is acceptable if it is maintained, which is a proxy for whether vulnerabilities in it will be fixed. In a real project, that check would be part of a review process, not code, but the principle is the same: maintained, trusted dependencies are preferred, and unmaintained ones should be replaced or removed. When you add a dependency, ask whether it is maintained, how widely it is used, what it does, and whether you truly need it. If any answer is unsatisfactory, reconsider the dependency. That questioning habit, applied to every dependency, keeps a program's supply chain lean and trustworthy. It also makes updating easier, because fewer dependencies mean fewer updates to track. Supply chain awareness is not about distrusting all external code; it is about trusting deliberately, with knowledge, rather than by default, which is the same cautious approach that underlies all security practice.

Supply chain awareness should also include checking that a dependency's source has not changed unexpectedly, such as a package that suddenly comes from a different publisher. An unexpected publisher change is a warning sign that deserves investigation before the dependency is updated or trusted.

Section 19: Security Testing in Plain Words

Security testing means testing a program's protections, not just its features, to check that they actually work under misuse as well as under normal use. It includes testing that unauthenticated users cannot access protected functions, that regular users cannot perform admin actions, that invalid input is rejected, that error paths fail safely, and that sensitive data is not exposed in messages, logs, or outputs. Those tests are written like ordinary tests, with Arrange, Act, Assert, but their assertions check denials and rejections rather than successes. For example, a security test might assert that a regular user attempting an admin action is denied, or that a login with a wrong password fails, or that an input containing special characters is rejected or safely escaped. Security tests should also cover boundary cases, such as empty inputs, very long inputs, and inputs at permission boundaries, because those are where protections often fail. Another form of security testing is review, where code is read specifically for security issues, such as missing checks, unsafe handling of secrets, or unvalidated input, by someone other than the original author if possible. Review catches issues that tests miss, because tests only check the cases the author thought of, while a reviewer may think of cases the author missed. Security testing is not a separate, exotic activity; it is ordinary testing applied to protections, plus careful review, and it should be part of every program's test suite. A program whose protections are untested is a program whose protections are unverified, and unverified protections should not be trusted. Write security tests alongside feature tests, and run them with the same regularity, so that protections are guarded as carefully as features.

import XCTest

struct Account {
    let role: String
}

func canDelete(_ account: Account) -> Bool {
    return account.role == "admin"
}

final class SecurityTests: XCTestCase {
    func testRegularUserCannotDelete() {
        let user = Account(role: "user")
        XCTAssertFalse(canDelete(user))
    }

    func testAdminUserCanDelete() {
        let admin = Account(role: "admin")
        XCTAssertTrue(canDelete(admin))
    }
}

The security tests check both sides of a permission rule: a regular user is denied, and an admin is allowed. Both checks matter, because a test that only checks the admin case would miss a bug that allowed everyone, and a test that only checks the regular case would miss a bug that denied everyone. That two-sided testing, allowed and denied, is the pattern for permission tests generally. Apply it to every permission rule in a program, and to every validation rule, checking both accepted and rejected inputs, and the program's protections will be verified, not just assumed. Security tests are ordinary tests with a security focus, and they are among the most valuable tests a program can have, because they guard the boundaries that protect users and their data. Write them early, run them often, and treat a failing security test as a serious issue, because it indicates a protection that is not working.

Security testing should also include testing that old, revoked, or expired credentials are rejected, not just that wrong credentials are rejected. A credential that was once valid but has since been revoked should no longer grant access, and a test for that case guards the revocation mechanism itself.

Section 20: Security Checklist for a Small Program

A security checklist helps you review a small program systematically, without needing to remember every security concern from this chapter. The checklist starts with data: what sensitive data does the program handle, where is it stored, who can access it, and how long is it kept? Next, inputs: is every input validated at the boundary, with an allow-list, and are file contents treated as untrusted? Next, access: are authentication and authorisation checked at each sensitive action, with least privilege, and do error paths fail safely? Next, secrets: are secrets kept out of code and logs, obtained from secure storage, and never displayed? Next, output: are error messages general for users and detailed only in logs, and is user input escaped before being included in output? Next, dependencies: are they minimal, maintained, and updated? Next, logging: does the log record important events without sensitive data, at appropriate levels? Next, loss: are destructive actions confirmed or reversible, and are saves atomic? Next, defaults: are sensitive features off by default, requiring explicit opt-in? Finally, tests: are protections tested, with both allowed and denied cases, and are error paths tested for safe failure? Working through that checklist for a small program takes only a short time, but it catches the most common security gaps, because those gaps are usually omissions, things that were never considered, rather than complex flaws. Keep the checklist with the project, use it before finishing a feature, and update it as the program grows. That routine turns security from a vague worry into a concrete review, which is the most practical way to make small programs secure.

struct SecurityReview {
    var inputsValidated = false
    var secretsProtected = false
    var permissionsChecked = false

    var isReady: Bool {
        return inputsValidated && secretsProtected && permissionsChecked
    }
}

var review = SecurityReview(inputsValidated: true, secretsProtected: true, permissionsChecked: true)

The security review struct models a checklist in code: a program is ready only when inputs are validated, secrets are protected, and permissions are checked. That all-or-nothing readiness is the right attitude for a checklist: a program with validated inputs but unprotected secrets is not ready, because its weakest protection determines its overall security. A checklist is not a guarantee, but it is a systematic way to avoid omissions, and omissions are the most common security failure in small programs. Use the checklist in this section as a starting point, adapt it to your program's specific features, and work through it before considering a program finished. That discipline, applied consistently, will make your programs noticeably more secure, without requiring advanced security knowledge. Security for small programs is mostly about care, consistency, and checklists, and those are habits any programmer can build.

A checklist should also be revisited after a security incident or a near miss, because each incident reveals a gap that the checklist should cover in future. A checklist that never changes will miss the lessons of experience, while one that grows with incidents becomes steadily more effective.

Section 21: Session Handling in Plain Words

A session is the period during which a program remembers that a user has already proven their identity, so that they do not have to prove it again for every action. Sessions are convenient, but they are also a security concern, because a session that lasts too long, or that is not properly ended, can be misused by someone else who gains access to the device or the program. Good session handling involves several practices. First, a session should expire after a period of inactivity, so that a forgotten session does not remain usable indefinitely. Second, a session should end explicitly when a user signs out, with all session data cleared, so that signing out actually ends access. Third, a session should be tied to the context in which it was created where possible, so that a session token copied to a different context is less useful, though the details of that tying depend on the platform. Fourth, session data should be stored securely, not in plain text in an easily read file, and session tokens, which are the keys that represent a session, should be treated as secrets, never logged or displayed. For a small local program, sessions may be as simple as remembering that a user is signed in until they sign out or the program closes, which is often sufficient. For a program that handles sensitive data, stricter session handling, with timeouts and explicit sign-out, is warranted. The key idea is that a session is a convenience that trades some security for usability, and that trade should be deliberate, with an expiry and a clear ending, rather than open-ended. When you design sign-in for a program, decide how long a session should last, what ends it, and how its data is protected, and document those decisions, because they are security decisions, not just usability ones.

struct Session {
    let username: String
    var isActive = true

    mutating func signOut() {
        isActive = false
    }
}

var session = Session(username: "Ada")
print(session.isActive)
session.signOut()
print(session.isActive)

The session example shows the essential operations: a session is active after sign-in, and signing out sets it inactive, ending access. A program that checks isActive before sensitive actions will deny them after sign-out, which is the correct behaviour. If signing out merely hid the interface but left the session active, a user who found another path to the sensitive action could still perform it, which is a failure of session handling. That is why sign-out must clear or deactivate the session itself, not just the display. For a fuller implementation, you would add an expiry time, checked on each use, so that an old session is treated as inactive even if sign-out was never called. That expiry, combined with explicit sign-out, gives sessions a bounded lifetime, which limits the window during which a forgotten or stolen session can be misused. Session handling is a small part of a program, but it is a security-critical part, because it determines how long authenticated access lasts, and under what conditions it ends.

Section 22: Protecting Against Social Engineering in Code

Social engineering means tricking a person into doing something harmful, such as revealing a password, clicking a malicious link, or granting access, by deception rather than by technical attack. Programs can help protect users against social engineering, or they can inadvertently make it easier, depending on their design. A program that asks for a password in an unexpected context, or that displays alarming messages urging immediate action, trains users to comply with urgent requests, which is exactly what social engineering exploits. A program that clearly identifies itself, that asks for sensitive actions only in expected contexts, and that explains what is happening in plain language, helps users distinguish legitimate requests from deceptive ones. For example, a program should never ask for a password in a pop-up that appears without context, and it should clearly state why it needs a credential and what it will do with it. It should also avoid alarming language that pressures users to act quickly without thinking, because urgency is a classic social engineering tactic. Another protective design is to show users what action they are about to take, in clear terms, before they confirm it, especially for destructive or sharing actions, so that a tricked user has a chance to notice that the action is not what they intended. Programs cannot prevent social engineering entirely, because it targets human judgement, but they can avoid training users into risky habits, and they can provide clear, calm information that helps users make good decisions. When you design prompts, confirmations, and requests for sensitive information, ask whether a deceptive version of your prompt would be hard to distinguish from the real one, and if so, make the real one more distinctive and more informative, so that users have a basis for telling them apart.

func confirmDelete(itemName: String) -> String {
    return "Are you sure you want to delete '\(itemName)'? This cannot be undone."
}

print(confirmDelete(itemName: "My Notes"))

The delete confirmation states clearly what will happen, which item is involved, and that the action cannot be undone, giving the user a chance to reconsider. That clarity is a defence against social engineering in miniature: a user who was tricked into deleting something would see the item's name and the warning, and might stop. A vague confirmation, such as are you sure, without naming the item or the consequence, would not give that chance. The same principle applies to sharing, signing in, and granting permissions: state what, why, and with what consequence, in plain language, before asking for confirmation. That transparency slows users down just enough to think, which is the opposite of what social engineering wants, which is hurried compliance. Design prompts to inform, not to pressure, and your program will help users resist deception, rather than training them to comply with it.

Programs should also avoid mimicking system prompts or security warnings, because a fake system prompt is a classic social engineering tool. If your program must show a security-related message, make it clearly part of your program, with your program's name and context, rather than imitating the operating system.

Section 23: Secure Coding Habits Summary

Secure coding is a set of habits, and summarising them helps you carry them into every program you write. The habits are: validate all input at the boundary, with an allow-list; check permissions at each sensitive action, with least privilege; keep secrets out of code and logs, and obtain them from secure storage; fail safely, denying access when a check errors; use safe defaults, with sensitive features off until explicitly enabled; escape or parameterise user input before including it in structured output; protect data at rest with permissions and, where warranted, encryption; protect data in transit with secure protocols; log important events without sensitive data, at appropriate levels; keep software and dependencies updated and minimal; test protections, with both allowed and denied cases; and record security decisions in a threat model and a checklist. No single habit makes a program secure; security comes from applying them consistently, so that a failure in one habit is caught by another. That layering, called defence in depth, is why checklists and reviews matter: they ensure that habits are not forgotten under pressure or in a hurry. Secure coding habits also require humility: assume your code has bugs, assume inputs are hostile until validated, and assume protections will be tested, because those assumptions lead to defensive code. The habits in this summary are not advanced; they are basic, and they are within reach of any programmer who applies them deliberately. Make them part of your routine, review them with the checklist, and your programs will be noticeably more secure, not because you have mastered exotic techniques, but because you have consistently applied the basics, which is where most security is won or lost.

Section 24: Handling Sensitive User Data Responsibly

Sensitive user data includes anything that could harm a user if exposed, such as personal notes, health information, financial details, location, contacts, or private messages, and handling it responsibly involves more than just storing it securely. It starts with asking whether the data is needed at all, as in privacy by design, and collecting only what is necessary. It continues with limiting access: only the parts of a program that need the data should be able to reach it, and only the user who owns it should be able to view it, unless they have explicitly shared it. It includes protecting the data in storage and in transit, as covered earlier, and it includes handling the data carefully in code, such as not copying it into logs, error messages, or temporary files that might be less protected than the main storage. It also includes giving users control: the ability to see what data is held, to correct it, and to delete it, because users should not be trapped with data held about them that they cannot manage. Responsible handling also means thinking about retention: how long is the data kept, and is it deleted when it is no longer needed? Data kept indefinitely accumulates risk, because every copy is a potential exposure, and old data that is no longer useful should be deleted, not hoarded. Finally, responsible handling means being honest with users about what is held and why, in plain language, so that they can make informed decisions about using the program. Those practices together, minimisation, limited access, protection, control, retention limits, and honesty, constitute responsible handling, and they apply to any program that touches personal data, however small.

Section 25: Avoiding Information Leaks in Outputs

Information leaks happen when a program's output reveals more than it should, such as internal details, other users' data, or sensitive values, through messages, listings, exports, or error reports. A common leak is including too much in a listing: a list of notes that shows private titles, a list of users that shows email addresses, or a search result that includes content the searcher should not see. Another leak is verbose error output that reveals file paths, database details, or internal state, which helps an attacker understand the program's structure. A third leak is in exports or shared data, where a file intended for one purpose contains extra fields that were not meant to be shared, such as internal identifiers or private notes included in a public export. Preventing leaks requires thinking about each output from the reader's perspective: who will see this output, and what should they be allowed to see? Then filter the output to exactly that, removing anything else, even if it is convenient to include it. That filtering should happen at the point where output is produced, not by hoping that readers will ignore extra data, because readers, including attackers, will not ignore it. It also requires testing outputs with different users and roles, to check that each sees only what they should, which is a form of security testing. Information leaks are often not dramatic; they are small, incremental exposures that together reveal a lot. A single leaked email address seems minor, but a list of leaked addresses is a privacy breach. Treat every output as a potential leak, filter it deliberately, and test it from the reader's perspective, and your program will reveal only what it intends to reveal.

Section 26: Secure Defaults for Network Features

Network features, such as downloading, sharing, or syncing, deserve secure defaults, because their risks are higher than local features: data leaves the device, and it may be observed, altered, or misdirected. The secure defaults for network features are: do not send data until the user explicitly enables the feature; use secure protocols, such as HTTPS, by default, and refuse insecure ones for sensitive data; verify the identity of the server or peer before sending sensitive data; send only the minimum data needed for the feature; and show the user what is being sent, or at least that sending is happening, so that network activity is not hidden. A program that syncs in the background without telling the user, over an insecure connection, sending more data than needed, violates all of those defaults, and exposes the user without their knowledge. A program that asks before syncing, uses HTTPS, verifies the server, sends only the changed items, and shows a sync status, respects the user and protects their data. Network defaults matter especially because users often do not realise when a program is communicating, unlike a visible action such as saving a file. That invisibility makes explicit consent and visible status important: users should know when their data leaves the device, and they should have agreed to it. When you add a network feature, start with it disabled, require explicit enablement, use secure protocols, minimise data, and show status. Those defaults, applied consistently, make network features trustworthy, which is essential, because a network feature that cannot be trusted will, rightly, not be used.

Section 27: Code Review for Security

Code review, where another programmer reads your code before it is accepted, is a powerful security practice, because a fresh reader often spots issues the author missed, such as a missing permission check, an unvalidated input, or a secret in code. Security-focused review involves reading code with specific questions in mind: where does input enter, is it validated, where are sensitive actions performed, are they authorised, where are secrets handled, are they protected, and where does output go, is it filtered? Those questions, applied systematically to a change, catch many security issues that tests miss, because tests only check cases the author thought of, while a reviewer may think of cases the author did not. Review is most effective when it is focused and timely: a small change reviewed promptly receives more attention than a large change reviewed weeks later, because the reviewer can understand a small change fully. It is also more effective when reviewers are respectful and specific, pointing at the code and explaining the concern, rather than making vague criticisms, because specific feedback is actionable and educational. Even solo developers can benefit from self-review, by reading their own code after a break, with security questions in mind, as if they were reviewing someone else's work. That distance, in time or in perspective, reveals issues that were invisible while writing. Code review is not a guarantee, but it is one of the highest-value security practices, because it brings a second mind to bear on code that a single mind may have overlooked. Make review, by others or by your future self, a routine part of finishing a change, especially for security-sensitive code.

Section 28: Incident Response in Plain Words

Incident response means what to do when a security problem is discovered, such as a leaked secret, unauthorised access, or data exposure, and having a plan in advance makes the response faster and calmer. The basic steps are: contain, meaning stop the harm from spreading, such as by revoking a leaked secret, disabling an affected account, or taking a vulnerable feature offline; assess, meaning find out what happened, what was affected, and how it happened, using logs and diagnostics; fix, meaning address the cause, not just the symptom, so that the problem cannot recur the same way; notify, meaning tell affected users what happened, what data was involved, and what they should do, in plain language, without delay; and learn, meaning record the incident and update practices, checklists, and tests to prevent recurrence. Those steps, in that order, prioritise stopping harm and informing users over assigning blame or hiding the problem. Hiding a security incident is both unethical and counterproductive, because affected users cannot protect themselves without knowing, and the problem may continue unnoticed. Notifying promptly, even when the full picture is not yet known, with a commitment to update as more is learned, is the responsible approach. Incident response is not a topic most small programs will need often, but having a simple plan, even a few sentences stating who to contact, how to revoke secrets, and how to notify users, is far better than improvising during a crisis. Write that plan down before you need it, keep it accessible, and review it occasionally, so that if an incident occurs, you can act rather than panic. That preparedness is part of professional responsibility for any program that handles user data.

Section 30: Common Security Mistakes to Avoid

Several security mistakes recur so often that they deserve explicit warning, because recognising them in advance prevents them. The first is hardcoding secrets in code, which has been covered, but bears repeating, because it remains one of the most common and most damaging mistakes. The second is trusting input, whether from users, files, or networks, without validation, which leads to crashes, corruption, and injection problems. The third is checking permissions only at login, rather than at each sensitive action, which allows authenticated users to perform actions they should not. The fourth is logging sensitive data, which turns a diagnostic aid into a leak. The fifth is using insecure defaults, such as sharing enabled by default, or an insecure protocol by default, which exposes users who never change settings. The sixth is ignoring error paths, which fail openly and grant access or discard data when a check errors. The seventh is adding unnecessary dependencies, which expands the program's attack surface for little benefit. The eighth is never updating, which leaves known vulnerabilities open. Each of these mistakes is easy to make, usually for convenience, and each is easy to avoid with the habits in this chapter, if those habits are applied consistently. The common thread is convenience versus care: the mistake is the convenient choice, and the secure choice requires a little extra thought. That extra thought, applied at each decision, is the difference between a program that is secure by habit and one that is insecure by default. When you review your own code, check specifically for these eight mistakes, because they are the ones you are most likely to have made, and catching them in review is far cheaper than discovering them after users are affected.

Section 31: Defence in Depth Explained

Defence in depth means protecting a program with several layers, so that if one layer fails, another still provides protection. The idea comes from physical security, where a building might have a fence, a locked door, and an alarm, so that breaching one does not grant full access. In software, layers might include input validation at the boundary, permission checks at each action, safe defaults, secure storage, and logging that reveals misuse. Each layer addresses a different kind of failure, and together they make a program resilient, because an attacker or a mistake must defeat several protections, not just one, to cause harm. Defence in depth also protects against unknown vulnerabilities, because a layer that was designed for one threat may block another that was not anticipated. For example, input validation designed to prevent crashes may also block an injection attempt, and least privilege designed to limit user damage may also limit the damage from a compromised component. Layers should be independent where possible, meaning they do not all depend on the same check or the same assumption, because dependent layers fail together. A program that checks permission at login and nowhere else has only one layer, however strong, and a bypass of that check grants full access. A program that checks at login and again at each action has two layers, and a bypass of one still leaves the other. Defence in depth is not about adding complexity for its own sake; it is about ensuring that no single failure is catastrophic, which is a realistic goal, because single failures are inevitable. Design layers deliberately, test each layer independently, and your program will be robust in a way that a single strong protection cannot achieve.

That second layer is often the difference between a minor incident and a major one, because it catches the failures the first layer misses.

Defence in depth also applies to data: a sensitive value might be protected by encryption, by file permissions, and by limited access in code, so that defeating one protection still leaves the others. Layered data protection is especially important for the most sensitive values, where a single failure would be serious.

Section 32: Threats from Malicious Files

Files supplied by others, such as documents, images, or data files downloaded from the internet, can be malicious in the sense that they are crafted to exploit a program that reads them. A malicious file might contain values that cause a crash, excessive memory use, or unexpected behaviour in a parser that assumes well-formed input. The defensive approach to untrusted files is the same as for untrusted input generally, but with file-specific emphasis: parse with a well-tested parser, validate the parsed values, limit the file's size before loading, and handle parsing errors gracefully rather than crashing. It is also important not to execute anything from a file unless that is the file's explicit purpose and the execution is sandboxed, meaning isolated from the rest of the system, because executing untrusted content is one of the most dangerous things a program can do. For the programs in this book, which read text and JSON files, the main risks are malformed content and excessive size, both of which are handled by validation and size limits. A program that reads a file should never assume the file was created by itself, even if it usually is, because files can be edited, replaced, or supplied by others, and the program cannot tell the difference. Treating every file as potentially hostile, in the sense of being malformed or oversized, leads to code that is robust against both accidents and malice, which is the goal. That robustness is not paranoia; it is the recognition that files, like all inputs, cross a trust boundary when they enter a program, and trust boundaries require checks.

import Foundation

func loadFileSafely(path: String, maxSize: Int) -> String? {

          let size = attributes[.size] as? Int,
          size <= maxSize else {
        return nil
    }
    return try? String(contentsOfFile: path, encoding: .utf8)
}

Size limits are a simple, effective defence against that class of problem, and they should be set based on the largest legitimate file the program is expected to handle, with a generous margin. When you write file-loading code, always consider size, format, and content validation together, because those three checks cover the main file risks. A file that passes all three is still not guaranteed safe, but it is far safer than one that was loaded without any check, and that improvement is the practical goal of defensive file handling.

Malicious files can also exploit parsers that assume a particular structure, such as a file that claims to contain a small number of items but actually contains many, causing the parser to allocate excessive memory. Validating claimed sizes against actual file size before allocating is a defence against that trick.

Section 33: Secure Randomness in Plain Words

Randomness is used in security for generating tokens, keys, passwords, and other values that must be unpredictable, and the quality of that randomness matters enormously. A predictable token, such as one generated from the current time or from a simple counter, can be guessed by an attacker who knows the generation method, which defeats its purpose. Secure randomness comes from a cryptographically secure random number generator, which is a generator designed and tested to produce values that cannot be predicted, even by someone who has seen previous values. Platforms provide such generators, and secure code should use them for security-sensitive values, rather than using a general-purpose random function, which may be predictable or may repeat its sequence. The distinction matters only for security values; for non-security purposes, such as shuffling a display order or picking a random example, a general random function is fine, because predictability does not cause harm. But for tokens, keys, and anything that guards access, only a secure generator is acceptable. Another aspect of secure randomness is ensuring that generated values are long enough: a short token, even if randomly generated, can be guessed by trying all possibilities, which is called brute force. A token of sufficient length, generated securely, makes brute force infeasible, because the number of possibilities is astronomically large. When you need a random value for security, use the platform's secure generator, generate enough bits, and never derive a security value from predictable inputs such as time, usernames, or counters alone. Those three rules, secure generator, sufficient length, and no predictable inputs, are the core of secure randomness, and they are easy to follow if you use platform APIs designed for the purpose, rather than inventing your own generation method.

import Foundation

func secureToken() -> String {
    var bytes = [UInt8](repeating: 0, count: 32)
    let result = SecRandomCopyBytes(kSecRandomDefault, bytes.count, &bytes)
    if result == errSecSuccess {
        return bytes.map { String(format: "%02x", $0) }.joined()
    }
    return ""
}

let token = secureToken()
print("Token length: \(token.count)")

The secure token function uses the platform's secure random generator to produce thirty-two random bytes, encoded as a hexadecimal string, and it prints only the token's length, not the token itself, which is safe handling. Thirty-two bytes is a generous length, making brute-force guessing infeasible. The function also handles failure gracefully, returning an empty string if generation fails, rather than falling back to a predictable value, which is the fail-safe behaviour for randomness: if secure randomness is unavailable, do not substitute insecure randomness, but report the failure. When you need tokens or keys, follow this pattern: use the platform's secure generator, use a sufficient length, handle failure safely, and never display or log the generated value. Those habits ensure that security values are genuinely unpredictable, which is their entire purpose. Predictable security values are worse than useless, because they create a false sense of protection while remaining guessable.

Secure randomness should also be used for values that are not obviously security-related but could become so, such as temporary file names or session identifiers that an attacker could guess to access another user's data. When in doubt about whether a value needs secure randomness, use it, because the cost is small.

Section 34: Protecting Backups

Backups are copies of data made for recovery, and they need the same protection as the original data, because a backup is, in security terms, just another copy that can be stolen, read, or altered. A program that protects its main data with permissions and encryption, but stores backups unprotected, has a gap that undermines the main protection, because an attacker who cannot access the original can access the backup instead. Backup protection involves the same measures as main data protection: appropriate file permissions, encryption for sensitive data, and access limited to those who need it. It also involves thinking about where backups are stored: a backup on the same device protects against accidental deletion but not against device loss or theft, while a backup elsewhere protects against device loss but introduces a new storage location that must itself be protected. Backup retention matters too: old backups containing data that has since been deleted by the user should themselves be deleted after a reasonable period, because retaining them defeats the user's deletion. A user who deletes a private note expects it to be gone, not to linger in a backup indefinitely. Backup design therefore balances recovery value against exposure and retention: keep enough backups to recover from likely failures, protect them as carefully as the original, and delete them when they are no longer needed. When you add backup functionality to a program, apply the same checklist as for main storage, permissions, encryption where warranted, limited access, and retention limits, and test that restoring from a backup works, because an untested backup may fail when it is needed most. A backup that cannot be restored is not a backup; it is a false sense of security.

import Foundation

func backupNote(_ text: String, to path: String) -> Bool {
    do {
        try text.write(toFile: path, atomically: true, encoding: .utf8)
        return true
    } catch {
        return false
    }
}

print(backupNote("Important tasks", to: "/tmp/tasks-backup.txt"))

The backup function saves a copy atomically, so that a failure during backup does not corrupt the backup file, which is a basic reliability measure. In a fuller implementation, the backup would also be stored with appropriate permissions, and, for sensitive data, encrypted, and old backups would be cleaned up after a retention period. Those additional measures are the security part of backup design, beyond the simple act of copying. When you implement backups, think of them as additional copies of the data, subject to all the same protections, and design their storage, permissions, and retention accordingly. Also test restoration, by restoring from a backup and checking that the data is complete and correct, because a backup's value is only proven by a successful restore. Backup testing is often neglected, because backups are made in hope and used in crisis, but a backup that has never been tested is a gamble. Test it in calm conditions, so that it can be trusted in a crisis.

Section 35: Security and Usability Balance

Security and usability are often presented as opposites, where more security means less convenience, but a good design balances them, because security that users circumvent is not security at all. If a security measure is too inconvenient, users will find workarounds, such as writing passwords on paper, disabling protections, or sharing accounts, which create larger risks than the measure was meant to prevent. The goal is therefore to make the secure path the easy path, so that users do not need workarounds. Examples of that balance include safe defaults, which protect users without requiring action; clear, calm prompts, which inform without alarming; and single sign-on or device-based authentication, which reduce password burden while maintaining protection. Another aspect of balance is proportionality: a low-risk action, such as viewing a public list, should not require the same protection as a high-risk action, such as deleting all data or changing permissions. Requiring strong authentication for trivial actions annoys users and trains them to treat all security prompts as obstacles, which weakens their attention for the important ones. Conversely, a high-risk action should require explicit confirmation and, where appropriate, re-authentication, because its consequences justify the inconvenience. Balancing security and usability requires understanding users' real workflows and risks, not just applying maximum protection everywhere. Maximum protection everywhere is not the most secure design; it is the design most likely to be bypassed. Thoughtful, proportionate protection, where the secure path is easy and the risky path requires deliberate effort, is both more usable and more secure, because it is protection that users will actually follow.

func requiresConfirmation(action: String) -> Bool {
    let destructiveActions = ["deleteAll", "shareAll", "resetAccount"]
    return destructiveActions.contains(action)
}

print(requiresConfirmation(action: "viewTasks"))
print(requiresConfirmation(action: "deleteAll"))

The confirmation function requires explicit confirmation only for destructive actions, such as deleting everything, while ordinary actions, such as viewing tasks, proceed without friction. That proportionality is the balance in code form: low-risk actions are easy, high-risk actions require a deliberate step. If every action required confirmation, users would start confirming without reading, which defeats the purpose. If no action required confirmation, a mistaken destructive action would be irreversible. The middle path, confirmation for destructive actions only, protects against mistakes while preserving ease for routine use. When you design security measures, ask whether the measure's burden matches the action's risk, and whether the secure path is the easy path. If users must work around your security to get their work done, your security is misdesigned, and it will fail in practice, however strong it looks on paper. Usable security is real security, because it is security that is actually used.

Usability balance should also consider users with different abilities and experience levels, because a security measure that is easy for an experienced user may be confusing for a beginner. Clear instructions and forgiving design, such as allowing a user to undo a security action, help all users follow the secure path.

Section 36: Auditing and Reviewing Access

Auditing means recording who did what, when, so that actions can be reviewed afterwards, which is a security measure that deters misuse and aids investigation. An audit log records important actions, such as sign-ins, permission changes, deletions, and exports, with the user, the action, the time, and the affected item, but without sensitive values themselves. That record allows a reviewer to answer questions such as who deleted this item, who changed this permission, and who exported this data, which are essential after a suspected misuse. Auditing differs from ordinary logging in its purpose: ordinary logs record what a program did, for debugging, while audit logs record who did what, for accountability. Both are useful, and they can share infrastructure, but audit entries should be protected against tampering, because an attacker who can alter the audit log can hide their actions. For small programs, auditing may be as simple as logging important actions with usernames and timestamps to a protected file. For larger systems, audit logs may be stored separately and monitored automatically. Auditing also has privacy implications: an audit log is itself sensitive data, because it reveals who did what, and it should be protected and retained only as long as needed, like other sensitive data. Reviewing audit logs regularly, not just after an incident, is part of the practice, because regular review catches misuse early, while a log that is never read is merely a record, not a protection. When you add auditing to a program, decide which actions are important enough to audit, record them consistently, protect the log, and review it periodically. Those steps turn auditing from a passive record into an active security control.

import Foundation

func auditLog(user: String, action: String, item: String) {
    let timestamp = Date()
    print("[AUDIT] \(timestamp) user=\(user) action=\(action) item=\(item)")
}

auditLog(user: "Ada", action: "delete", item: "Old Notes")
auditLog(user: "Ben", action: "export", item: "Task List")

The audit log entries record who performed an action, what the action was, which item was affected, and when, without including sensitive contents. That information is enough to reconstruct important events afterwards, without exposing the data itself. A reviewer reading these entries could see that Ada deleted old notes and Ben exported a task list, which is the accountability that auditing provides. If a deletion were disputed, the audit log would show who performed it and when, resolving the question. When you implement auditing, keep entries consistent, with the same fields in the same order, protect the log file, and review it regularly. Consistency makes the log searchable and trustworthy, protection prevents tampering, and review makes it useful. Auditing is a quiet security measure, invisible during normal use, but invaluable when accountability matters, which is exactly when a program's protections are tested.

Audit logs should also be reviewed for patterns, not just for individual events, because a pattern of small, individually harmless actions can indicate misuse when viewed together. Regular pattern review turns auditing from a record of past events into an early warning system.

Section 37: Secure Communication Between Components

When a program is made of several components, such as a main program and a helper, or a program and a service it talks to, the communication between those components needs protection, just as communication over a network does. A component should not trust data from another component blindly, because components can be compromised, misconfigured, or replaced, and data crossing a component boundary is, in security terms, crossing a trust boundary. The defensive practices are familiar: validate data received from another component, check permissions for actions requested by another component, use secure channels where the communication could be observed, and limit what each component can request. For example, a helper that processes files should not be able to delete arbitrary files merely because the main program asked it to, unless deletion is part of its legitimate job, and its requests should be checked. That limitation is least privilege applied between components. Another practice is to authenticate components to each other, where possible, so that a program does not accept instructions from an impostor component. For local programs, that authentication may be provided by the operating system, such as by restricting which programs can communicate, but the principle remains: do not accept instructions from an unverified source, even a local one. Secure inter-component communication is an advanced topic in full, but its core is the same as all security practice: validate at boundaries, check permissions, limit privilege, and do not trust merely because the source is nearby. Proximity is not trust, and a local component is not automatically safe. Apply boundary thinking to every interface, internal as well as external, and your program's components will be protected from each other as well as from the outside.

struct ComponentRequest {
    let source: String
    let action: String
    let isTrustedSource: Bool
}

func handleRequest(_ request: ComponentRequest) -> String {
    if !request.isTrustedSource {
        return "Request denied: untrusted source"
    }
    return "Handling \(request.action) from \(request.source)"
}

let trusted = ComponentRequest(source: "MainApp", action: "read", isTrustedSource: true)
let untrusted = ComponentRequest(source: "Unknown", action: "delete", isTrustedSource: false)
print(handleRequest(trusted))
print(handleRequest(untrusted))

The component request handler checks the source's trustworthiness before acting, denying requests from untrusted sources regardless of the action requested. That check is the boundary protection for inter-component communication in miniature. In a real system, trust would be established by a stronger mechanism than a boolean flag, such as a credential or an operating system check, but the pattern, check trust before acting, is the same. A program that accepts requests from any component without checking is vulnerable to any other program on the system that chooses to send it a request, which is a real risk on shared systems. When you design components that communicate, define which sources are trusted, how trust is verified, and what each trusted source is allowed to request, and enforce those rules at the boundary. That enforcement turns component communication from an open door into a guarded gate, which is the secure design for any interface, internal or external.

Component communication should also be limited in scope, so that a component can only request the specific actions it needs, rather than having broad access to all functions. Narrow interfaces between components reduce the damage if one component is compromised or misbehaves.

Section 38: Protecting Children and Vulnerable Users

Programs used by children or vulnerable users deserve extra care, because those users may be less able to recognise risks, understand consequences, or protect themselves. Design for such users involves simpler, clearer language, explicit confirmations for sharing or spending, safe defaults that are even more conservative, and avoidance of features that could expose them to harm, such as unrestricted contact with strangers or sharing of personal information. It also involves giving guardians or trusted adults appropriate controls, where relevant, without giving them excessive access to a child's private data. Privacy protections are especially important for vulnerable users, because the consequences of exposure can be more serious, and the users may be less able to manage their own privacy settings. Programs should therefore collect minimal data from such users, explain data practices in age-appropriate language, and avoid dark patterns, meaning design tricks that manipulate users into sharing more or spending more than they intend. Dark patterns are unethical for all users, but they are particularly harmful for vulnerable ones, who may be less able to resist them. While the programs in this book are general tools, not specifically for children, the principle of designing for the most vulnerable user is a good general discipline: if a program is safe and clear for a vulnerable user, it is likely safe and clear for everyone. That discipline involves asking, for each feature, whether a user who does not understand security, who trusts too easily, or who acts impulsively, could be harmed by it, and if so, adding protections, such as confirmations, limits, and clear explanations. Designing for vulnerability is designing with empathy, and it produces programs that are safer for all users, not just the vulnerable ones.

func canShare(isChildAccount: Bool, guardianApproved: Bool) -> Bool {
    if isChildAccount {
        return guardianApproved
    }
    return true
}

print(canShare(isChildAccount: true, guardianApproved: false))
print(canShare(isChildAccount: true, guardianApproved: true))

The sharing check requires guardian approval for child accounts, which is a protective measure for vulnerable users in code form. An adult account can share freely, while a child account requires an additional approval, reflecting the extra care owed to younger users. That kind of age-appropriate protection, applied where relevant, is part of responsible design for programs that may be used by children. More generally, the pattern, an extra check or confirmation for sensitive actions by vulnerable users, applies to any user who might need additional protection, whether due to age, disability, or unfamiliarity with technology. When you design features that involve sharing, spending, or exposing personal data, consider whether some users need extra protection, and provide it through clear language, confirmations, and approvals, rather than assuming all users are equally able to protect themselves. That consideration is not just ethical; it is practical, because a program that harms a vulnerable user has failed in a serious way, regardless of its other qualities.

Vulnerable users also benefit from programs that avoid collecting data that could be used to identify or locate them, such as precise location, unless that data is essential to the program's purpose. Minimising identifying data is a strong protection for users who are at greater risk from exposure.

Section 39: Security Documentation for Users

Security documentation for users means explaining, in plain language, how a program protects their data, what they need to do to stay safe, and what to do if something goes wrong. It is part of a program's security, because users who understand protections are more likely to use them correctly, and users who do not understand them may bypass them or misuse them. Good security documentation covers: what data the program collects and why, how it is protected, how users can control it, including how to delete it, what the program will never ask for, such as passwords by email, so that users can recognise phishing attempts, and how to report a security problem, with a contact or a process. That documentation should be short, clear, and accessible, not buried in legal language, because users will not read what they cannot understand. It should also be honest about limitations: if a program's protection depends on the device's security, or if a feature has known risks, saying so helps users make informed choices. Security documentation is not a substitute for secure design, but it complements it, by aligning user behaviour with the program's protections. A program that is secure by design but whose users do not understand its protections may still be misused, because users may disable protections they do not understand, or share data they think is protected when it is not. Documentation bridges that gap, by making protections visible and understandable. When you finish a program, write a short security note for its users, covering data, protection, control, and reporting, in plain language, and keep it updated as the program changes. That note is a small effort with a large trust benefit, because it shows users that their safety was considered, not just their features.

func securityNote() -> String {
    return "This program stores your tasks on your device only. It never sends them elsewhere. You can delete all data at any time from Settings."
}

print(securityNote())

The security note states, in one clear sentence each, where data is stored, that it is not sent elsewhere, and that users can delete it. That clarity is the goal of user security documentation: short, specific, and actionable. A user reading that note understands the program's data practices immediately, without needing to read a long policy. Longer documentation would expand on each point, with details about protection measures and how to report problems, but the principle remains: plain language, specific claims, and user control. When you write security documentation, avoid vague reassurances, such as your data is safe, without explaining how, because vague claims do not help users judge risk. Instead, state concretely what is collected, where it is stored, how it is protected, and how it can be deleted. Those specifics allow users to verify the claims, at least in principle, and they demonstrate that the program's security was thought through, not just asserted. Clear security documentation builds trust, and trust is essential for any program that handles personal data.

Section 40: Security Review of a Whole Program

A whole-program security review is a systematic examination of a program's security, from its data and features to its dependencies and defaults, using the checklist and habits from this chapter. It starts by listing the program's features and the data each one handles, then by examining each feature's inputs, permissions, outputs, and error paths, asking the security questions for each. It continues by reviewing dependencies, logging, defaults, and backups, and by testing protections with both allowed and denied cases. The review should be documented, with findings, severity, and fixes, so that it can be revisited and so that fixes can be verified. A whole-program review is best done periodically, such as before a release, and after major changes, because security degrades over time as features are added without corresponding protections. It is also best done by someone other than the original author when possible, because fresh eyes catch what familiarity hides, but a self-review, done carefully with a checklist, is far better than no review. The review's goal is not to prove a program is perfectly secure, which is impossible, but to find and fix the most important gaps, proportionate to the program's risks. A small local tool does not need the same review depth as a large service handling sensitive data for many users, but it does need a review proportionate to its data and its users. That proportionality is the theme of this chapter: security effort should match risk, applied consistently through habits, checklists, and reviews. A whole-program review, done honestly, will almost always find something to improve, and that improvement is the review's value. It turns security from a one-time concern into an ongoing practice, which is the only kind that keeps pace with a changing program.

struct ReviewFinding {
    let area: String
    let severity: String
    var fixed = false
}

var findings = [
    ReviewFinding(area: "Input validation", severity: "High"),
    ReviewFinding(area: "Logging", severity: "Low"),
]

findings[0].fixed = true
let allFixed = findings.allSatisfy { $0.fixed }
print("All findings fixed: \(allFixed)")

The review findings example tracks security issues by area and severity, with a fixed flag, and checks whether all findings are fixed. That tracking is the practical side of a review: findings without tracking are easily forgotten, while tracked findings are fixed and verified. A real review would include descriptions, evidence, and fix details for each finding, but the structure, list, severity, fix, verify, is the same. When you conduct a whole-program review, record your findings in that structured way, prioritise by severity, fix the highest first, and verify each fix with a test. That disciplined follow-through is what makes a review effective, rather than merely a document that is filed and forgotten. Security review is not a one-time event; it is a cycle of review, fix, verify, and repeat, applied as a program evolves. Adopt that cycle, and your programs' security will improve steadily, keeping pace with their growth and with the changing risks they face.

A whole-program review should also include a check that security documentation for users is accurate and up to date, because documentation that describes protections the program no longer has, or omits new data collection, misleads users and undermines trust.

Section 41: Security for Command-Line Tools

Command-line tools have specific security considerations, because they often run with the user's full permissions, accept arguments and files from the command line, and are used in scripts where their behaviour may be automated. A command-line tool should validate its arguments just as carefully as a program validates interactive input, because arguments can be supplied by scripts, by other programs, or by users who mistype. It should handle file paths safely, ensuring that paths built from arguments stay within intended folders, and that it does not overwrite or delete files outside those folders without explicit confirmation. It should be careful with its output, avoiding sensitive data in printed results, and it should use exit codes to indicate success or failure clearly, so that scripts can detect failures rather than proceeding as if an operation succeeded. A command-line tool that runs with elevated permissions, which should be avoided where possible, must be especially careful, because its permissions amplify any bug into a larger harm. The principle of least privilege applies here too: a tool should request only the permissions it needs, and it should drop elevated permissions as soon as it no longer needs them, if it ever had them. Command-line tools are also often used by other programs, which means their behaviour becomes part of a larger system's security, and a tool that is unsafe when called programmatically can undermine the system that calls it. Designing command-line tools with the same security habits as other programs, validation, least privilege, safe defaults, and clear outputs, ensures that they are safe building blocks, not weak links. That care is especially important because command-line tools are frequently written quickly, for a specific task, and their security is overlooked in the rush to make them work.

func runTool(arguments: [String]) -> Int {
    if arguments.isEmpty {
        print("Usage: tool <input-file>")
        return 1
    }
    let inputPath = arguments[0]
    if inputPath.isEmpty {
        print("Error: input path is empty")
        return 1
    }
    print("Processing \(inputPath)")
    return 0
}

print("Exit code: \(runTool(arguments: []))")

The tool example validates its arguments, prints usage when they are missing, and returns a non-zero exit code for failure, which are basic command-line security and usability practices. A tool without argument validation might crash on missing arguments, or proceed with an empty path and damage an unintended file, while a tool without clear exit codes would leave scripts unable to tell success from failure. Those small practices, validation, usage messages, and exit codes, make a command-line tool safe to use both interactively and in scripts. When you build command-line tools, apply the security checklist to them as well: validate arguments, check paths, avoid sensitive output, use exit codes, and run with minimal permissions. That checklist, applied to tools as well as to apps, ensures that the small, quick programs that often do important work are as safe as the larger programs they support.

Command-line tools should also avoid printing sensitive data in their normal output, because output is often captured to files or shared in bug reports. A tool that prints a token or a private path in its output creates a leak every time it runs, not just when it is debugged.

Section 42: Avoiding Dangerous Functions and Patterns

Some functions and patterns are dangerous because they are easy to misuse in ways that create security problems, and avoiding them, or using their safe alternatives, is a practical security habit. Examples include force-unwrapping optionals, which crashes on nil and can be triggered by unexpected input; building structured text, queries, or commands by string concatenation with user input, which enables injection; using predictable random values for security purposes, which enables guessing; and disabling security checks, such as certificate verification, to make development easier, which, if forgotten, leaves production code unprotected. Each of these patterns has a safe alternative: safe unwrapping with guard or if let, parameterised queries and escaping, secure random generators, and proper certificate handling with development-only workarounds that are clearly marked and removed before release. The habit is to recognise dangerous patterns when you see them, whether in your own code or in examples you copy, and to replace them with safe alternatives before the code is finished. Copying code from examples is a particular risk, because examples often prioritise brevity over safety, and they may use dangerous patterns for simplicity. When you copy an example, review it for dangerous patterns and fix them, rather than assuming the example is safe because it works. Dangerous patterns are not always obvious, which is why checklists and reviews help: a reviewer looking specifically for force unwraps, concatenation, predictable randomness, and disabled checks will catch them reliably. Avoiding dangerous patterns is not about memorising a long list; it is about developing a sensitivity to code that bypasses a protection, and replacing it with code that respects the protection. That sensitivity grows with practice and with review, and it is one of the marks of a security-conscious programmer.

func safeGreeting(name: String?) -> String {
    guard let name = name, !name.isEmpty else {
        return "Hello, guest!"
    }
    return "Hello, \(name)!"
}

print(safeGreeting(name: nil))
print(safeGreeting(name: "Ada"))

The safe greeting uses guard to handle nil and empty names gracefully, rather than force-unwrapping, which would crash on nil. That safe pattern is the alternative to a dangerous one, and it is barely longer, which shows that safe code is often not much more effort than dangerous code. The difference is in the habit: reaching for guard by default, rather than for force unwrap by default, prevents a whole class of crashes. Similarly, reaching for parameterised methods by default, rather than string concatenation, prevents injection, and reaching for secure generators by default prevents predictable tokens. Those defaults, safe patterns as the first choice, are what secure coding habits amount to in practice. When you write code, pause at each potentially dangerous pattern and ask whether a safe alternative exists. Usually it does, and usually it is nearly as easy. Choosing it consistently is how dangerous patterns disappear from a codebase, replaced by safe ones that become the new default.

Dangerous patterns also include using a weak or outdated method for a security purpose, such as an old hashing method for passwords, which is covered in the next chapter. When a platform marks a method as deprecated for security reasons, treat that as a warning to find the recommended replacement promptly.

Section 43: Security in Error Handling

Error handling is a security concern, because errors are moments when a program is in an unusual state, and unusual states are where protections often fail. Secure error handling follows several principles. First, errors should not reveal sensitive information, as discussed for error messages: user-facing errors should be general, with details in logs. Second, errors should fail safely, denying access or preserving data, rather than granting access or discarding data, as discussed for fail-safe design. Third, errors should be handled explicitly, not ignored, because an ignored error can leave a program in an inconsistent state, where a later operation proceeds on the assumption that an earlier one succeeded, when it did not. For example, ignoring a failed permission check and proceeding as if it passed is a security flaw, as is ignoring a failed save and reporting success. Fourth, error handling code itself should be simple and well-tested, because complex error handling is itself a source of bugs, and error paths are less frequently exercised than normal paths, so their bugs are less likely to be caught by ordinary testing. Testing error paths deliberately, by simulating failures, is therefore a security practice, not just a reliability practice. Fifth, errors should be logged at an appropriate level, with enough detail for diagnosis, but without sensitive values, so that failures can be investigated without creating leaks. Secure error handling is therefore a combination of the principles already covered, general messages, fail-safe defaults, explicit handling, simple code, tested paths, and safe logging, applied specifically to the moments when things go wrong. Those moments deserve extra care, because they are when a program is most vulnerable to misuse and to mistakes.

enum LoadResult {
    case success(String)
    case failure
}

func loadData() -> LoadResult {
    return .failure
}

switch loadData() {
case .success(let text):
    print("Loaded: \(text)")
case .failure:
    print("Could not load data. Using safe defaults.")
}

The load example handles failure explicitly, with a safe fallback and a general message, rather than ignoring the failure or crashing. That explicit handling, with a safe default, is the pattern for secure error handling. A version that ignored the failure and proceeded with empty or partial data might misbehave in ways that expose data or corrupt state, while a version that crashed would deny service. The safe fallback, using defaults and informing the user, preserves both security and usability. When you write error handling, make it explicit, make it safe, make it simple, and test it by simulating the failure. Those four qualities, applied to every error path, will make your program's error handling a security strength rather than a weakness, which is important, because error paths are where attackers and accidents both tend to strike.

Error handling should also ensure that a partially completed operation is rolled back safely when an error occurs halfway through, rather than leaving data in a half-updated state. A half-updated state can violate integrity and can expose intermediate values that should never have been visible.

Section 44: Protecting Against Denial of Service

Denial of service means making a program unavailable to legitimate users, by overwhelming it with work, data, or requests, and protecting against it involves limiting the resources any single user or input can consume. The main limits are: size limits, such as refusing files or inputs larger than a reasonable maximum; count limits, such as limiting the number of items, requests, or operations in a given period, which is rate limiting; time limits, such as timeouts for operations that might hang; and complexity limits, such as avoiding algorithms that become extremely slow for certain inputs. Each limit prevents a different form of exhaustion: size limits prevent memory exhaustion, count limits prevent request exhaustion, timeouts prevent hanging, and complexity limits prevent CPU exhaustion. For small programs, denial of service may seem like a large-system problem, but even a local tool can be overwhelmed by a huge file, a long list, or a crafted input that triggers slow processing, and the resulting hang or crash denies service to its user, even if no attacker is involved. The defensive approach is proportionate: set limits based on legitimate use, with generous margins, so that normal use is unaffected, while abusive or accidental extremes are blocked. Limits should fail gracefully, with a clear message, rather than crashing, because a crash is itself a denial of service. Testing limits, by trying inputs at and beyond them, ensures they work as intended. Denial of service protection is therefore another application of the general security principles, limits, validation, and graceful failure, applied to resource use. A program that limits resource consumption is a program that remains available, which is one of the three security goals, alongside confidentiality and integrity.

func processItems(_ items: [String], maxItems: Int) -> String {
    if items.count > maxItems {
        return "Too many items. Maximum is \(maxItems)."
    }
    return "Processed \(items.count) items"
}

print(processItems(["A", "B"], maxItems: 100))
print(processItems(Array(repeating: "X", count: 200), maxItems: 100))

The item processing function refuses inputs larger than a maximum, with a clear message, rather than attempting to process an unlimited number and potentially exhausting resources. That limit, set generously for legitimate use, prevents both accidental and deliberate overload. A program without such a limit might attempt to process a million items, consuming memory and time, and becoming unresponsive, which denies service to its user. The limit's message is also important: it tells the user why their input was refused and what the maximum is, so that they can adjust, rather than leaving them with a mysterious failure. When you design operations that handle variable amounts of data, set a reasonable maximum, enforce it early, before allocating resources, and report it clearly. That early enforcement is key, because a limit checked after resources are allocated does not prevent exhaustion. Check limits at the boundary, before work begins, and your program will remain responsive even when faced with extreme inputs.

Denial of service protection should also consider that a single user might trigger many expensive operations through a script, even if each operation alone is within limits. Combining per-operation limits with overall rate limits addresses that pattern, because it limits both single requests and sustained volume.

Section 45: Security Awareness for Developers

Security awareness for developers means understanding that security is part of your job, not someone else's, and that your daily decisions, about validation, permissions, secrets, and defaults, determine whether a program is secure. It involves staying informed about common vulnerabilities, such as the ones covered in this chapter, and about new ones as they are discovered, through reading, training, or following trusted security sources. It also involves recognising that security is a moving target: new attacks are developed, new vulnerabilities are found, and yesterday's secure practice may become today's weakness, which is why updating and review are ongoing, not one-time. Security awareness also means thinking like a defender, not just like a builder: when you write a feature, ask how it could be misused, what data it exposes, and what happens when it fails, in addition to asking whether it works. That defender's mindset, applied consistently, catches issues that a purely functional mindset misses. It also means being honest about uncertainty: if you are unsure whether a design is secure, ask for review, research the question, or choose the more conservative option, rather than assuming it is fine. Security awareness is not about fear; it is about responsibility. Programs affect real people, and developers owe those people care in how their data is handled. That care, expressed through awareness, habits, and review, is what makes a developer trustworthy, not just technically competent. Cultivate awareness by reading about security regularly, by reviewing your own code with security questions, and by learning from incidents, your own and others', without blame. That ongoing learning is the foundation of secure development, because the field changes, and developers must change with it.

func developerChecklistComplete(validated: Bool, permissionsChecked: Bool, secretsSafe: Bool) -> Bool {
    return validated && permissionsChecked && secretsSafe
}

print(developerChecklistComplete(validated: true, permissionsChecked: true, secretsSafe: true))
print(developerChecklistComplete(validated: true, permissionsChecked: false, secretsSafe: true))

The developer checklist function shows, in code, that security requires all of its parts: validation, permissions, and secret safety together, not just one of them. A program that validates input but does not check permissions is not secure, just as one that checks permissions but leaks secrets is not secure. That all-parts requirement is why awareness matters: a developer who is aware of all the parts will check all of them, while one who knows only one part will miss the others. Awareness is therefore not just knowledge of individual techniques, but knowledge of the whole picture, and of how the parts fit together. Build that picture by studying the whole checklist, by reviewing whole programs rather than single functions, and by asking, for each program, whether every part of the picture has been addressed. That whole-picture thinking is what separates a security-aware developer from one who merely knows a few tricks, and it is a skill that grows with deliberate practice and ongoing learning.

Security awareness should also include recognising that security advice itself can become outdated, so advice should be checked against current sources rather than followed blindly. A practice recommended years ago may have been superseded, and following it without checking can leave a program using weak protection.

Section 46: Security for Data Exports

Data exports, where a program writes data to a file for sharing, backup, or use elsewhere, are a security concern, because an export creates a new copy of data that may be less protected than the original, and may be shared more widely. Before exporting, a program should check that the user is authorised to export the data, and that the export includes only the data they are allowed to share, filtering out private or sensitive fields, as with public views. It should also warn the user, where appropriate, that exported data will be in a file that they are responsible for protecting, because once data leaves the program, the program can no longer control who sees it. That warning is important, because users may not realise that an exported file, emailed or uploaded, is no longer protected by the program's permissions. Export formats matter too: a format that includes extra metadata, such as internal identifiers, timestamps, or hidden fields, may leak information the user did not intend to share, so exports should be reviewed for unintended content. Exported files should also be written with appropriate permissions, not world-readable by default, and sensitive exports should be encrypted where possible, or at least the user should be advised to protect them. Finally, exports should be logged, as audit events, so that there is a record of what was exported, by whom, and when, which aids accountability if exported data is later misused. Data exports are a common feature, and they are often implemented without security thought, because they seem like a simple file write. Treating them as a security boundary, with authorisation, filtering, warning, permissions, and auditing, ensures that sharing data does not become an unintended leak. That boundary thinking, applied to exports as to all outputs, is the key to safe sharing.

struct ExportableTask {
    let title: String
}

struct FullTask {
    let title: String
    let privateNote: String
}

func exportTask(_ task: FullTask) -> ExportableTask {
    return ExportableTask(title: task.title)
}

let full = FullTask(title: "Buy milk", privateNote: "Personal reminder")
print(exportTask(full).title)

The export function converts a full task, which contains a private note, into an exportable task containing only the title, filtering out the private content. That filtering ensures that an export does not leak private notes, even if the export feature is used carelessly. A version that exported the full task would share private data with whoever received the file, which is a leak caused by failing to filter at the export boundary. When you implement exports, define an exportable type that contains only shareable fields, use it consistently, and test that private fields are absent from exported files. That structural filtering, like the public view pattern, makes leaks impossible by construction, rather than relying on display code to omit fields. Combine it with authorisation, a warning to the user, appropriate file permissions, and an audit log entry, and exports become a safe, accountable feature, rather than a hidden leak. Exports deserve the same security attention as any other output, because they are outputs that leave the program's control entirely.

Section 47: Security When Sharing Code

Sharing code, such as publishing a library, posting an example, or contributing to a project, has security implications, because shared code may contain secrets, sensitive examples, or insecure patterns that others will copy. Before sharing code, check it for secrets, such as keys, tokens, or passwords, including in comments, test data, and configuration files, and remove them, rotating any secret that was ever shared, because a shared secret cannot be unshared. Check examples for sensitive data, such as real user names, email addresses, or file paths, and replace them with clearly fake examples, so that sharing code does not leak real information. Check the code itself for insecure patterns, such as the dangerous functions discussed earlier, and fix them, because shared code is often copied verbatim, and an insecure example will propagate insecurity to every program that copies it. Sharing code responsibly also means documenting its security assumptions, such as what inputs it expects to be validated, what permissions it requires, and what it does with sensitive data, so that users of the code can use it safely. That documentation is part of the code's interface, not an optional extra, because a library that is secure when used correctly but insecure when used naively needs its correct use documented clearly. When you share code, treat it as a publication: review it as a stranger would read it, remove secrets and sensitive examples, fix insecure patterns, and document its security assumptions. That care protects both you and the people who will use your code, and it contributes to a healthier ecosystem, where shared code is a source of good practice rather than a vector for insecurity.

func exampleGreeting(name: String) -> String {
    return "Hello, \(name)!"
}

print(exampleGreeting(name: "Example User"))

The example greeting uses a clearly fake name, Example User, rather than a real person's name, which is the practice for shared examples. That fake name signals to readers that the example is illustrative, not real data, and it prevents any accidental leak of a real user's information. Similarly, example passwords, keys, and tokens in shared code should be obviously fake, such as example-password, and should never be real values, even if they seem harmless. A real value in an example, once shared, is compromised, and it may be difficult to rotate if it is embedded in many copies. When you write examples for sharing, use fake data that is clearly fake, review the example for secrets, and document any security assumptions. Those habits, applied to every shared snippet, protect you and your readers, and they set a good example, in both senses, for the wider community. Shared code is a responsibility, and handling it securely is part of being a responsible developer.

Sharing code should also include removing any credentials from test fixtures and sample configuration files, because those files are often overlooked during a secrets check. A sample configuration that contains a real key is just as much a leak as a key in source code.

Section 48: Staying Current with Security Knowledge

Security knowledge changes constantly, as new vulnerabilities are discovered, new attacks are developed, and new defences are created, so staying current is part of a developer's ongoing responsibility. Staying current does not require reading everything; it requires following a few trusted sources, such as official security advisories for the platforms and libraries you use, and reputable security publications, and paying attention when a vulnerability affects something you use. It also requires periodic review of your own programs against current best practice, because a practice that was secure when a program was written may become insecure as new attacks emerge. For example, a password policy or an encryption method that was recommended years ago may now be considered weak, and a program that has not been updated will be using outdated protection. Staying current therefore involves both external awareness, following sources, and internal review, checking your programs against what you have learned. It also involves learning from incidents, both your own and others', by reading incident reports and understanding what went wrong and how it could have been prevented. That learning, applied to your own programs, is more valuable than abstract knowledge, because it is grounded in real failures. Make staying current a routine, such as setting aside time regularly to read advisories and to review a program's security, rather than a reaction to a crisis. That routine keeps your knowledge fresh and your programs protected, without requiring constant attention. Security is a field where standing still means falling behind, so a small, regular investment in learning is essential to maintaining protection over time.

func isKnowledgeCurrent(lastReviewedDaysAgo: Int) -> Bool {
    return lastReviewedDaysAgo <= 90
}

print(isKnowledgeCurrent(lastReviewedDaysAgo: 30))
print(isKnowledgeCurrent(lastReviewedDaysAgo: 200))

The knowledge currency check uses ninety days as a threshold for recent review, which is an arbitrary but illustrative interval: a program whose security was last reviewed two hundred days ago is less likely to reflect current best practice than one reviewed thirty days ago. The exact interval matters less than the habit of regular review, with a defined maximum gap, so that review does not slip indefinitely. When you adopt a review routine, choose an interval that fits your program's risk and your available time, record the last review date, and check it regularly. That simple tracking turns staying current from a vague intention into a measurable practice. It also helps prioritise: a high-risk program deserves more frequent review than a low-risk one, and a program that handles sensitive data deserves more attention than one that handles only public data. Proportionate, regular review is the practical way to stay current, without attempting to follow every development in a fast-moving field. Focus on what affects your programs, review regularly, and learn from incidents, and your security knowledge will remain useful.

Staying current should also include learning from the security practices of the platforms you use, because platform providers update their guidance as threats evolve. Reading platform security documentation periodically is a reliable way to learn about recommended practices for your specific environment.

Section 49: Building a Security Mindset

A security mindset is a way of thinking about programs that consistently asks security questions, not just functional ones, and it is built through practice, not through reading alone. It involves asking, for every feature, what could go wrong, who could be harmed, and how the feature could be misused, in addition to asking whether it works. It involves assuming inputs are untrusted until validated, assuming permissions must be checked, and assuming secrets must be protected, as defaults, rather than as afterthoughts. It involves thinking about failure modes, not just success modes, and about error paths, not just normal paths, because failures are where security often breaks. It involves empathy for users, especially vulnerable ones, and for future maintainers, who will need to understand the program's protections. A security mindset is not about fear or suspicion; it is about care and thoroughness, applied to the question of harm. It is developed by practising the habits in this chapter, by reviewing code with security questions, by learning from bugs and incidents, and by discussing security with peers, who may see risks you miss. It is also developed by studying real incidents, not to blame those involved, but to understand how a seemingly small oversight led to harm, and how it could have been prevented. That study builds pattern recognition, so that similar oversights become visible in your own code before they cause harm. A security mindset is a professional identity, like a debugging mindset, and it grows with deliberate practice. Cultivate it by asking security questions for every feature, by reviewing with a checklist, and by learning continuously, and it will become part of how you think about programs, not just something you do when reminded.

func mindsetCheck(asksWhatCouldGoWrong: Bool, validatesInput: Bool, checksPermissions: Bool) -> Bool {
    return asksWhatCouldGoWrong && validatesInput && checksPermissions
}

print(mindsetCheck(asksWhatCouldGoWrong: true, validatesInput: true, checksPermissions: true))

The mindset check function, though simplified, illustrates that a security mindset is a combination of habits, asking what could go wrong, validating input, and checking permissions, all together, not just one of them. A programmer with a security mindset does all of those habitually, without needing to be reminded for each feature. That habitual combination is the goal, and it is reached through practice, not through a single insight. When you finish a feature, ask yourself whether you asked what could go wrong, whether you validated inputs, and whether you checked permissions, and if any answer is no, address it before considering the feature done. That self-check, repeated for every feature, builds the mindset over time, until the questions become automatic. A mindset is not a tool you pick up; it is a way of working that you develop, and it is one of the most valuable professional qualities a programmer can cultivate, because it protects users in ways that no single technique can.

A security mindset also involves humility about one's own code, meaning an assumption that it contains flaws that have not yet been found. That humility leads to testing, review, and defence in depth, rather than to confidence based on the absence of known problems.
