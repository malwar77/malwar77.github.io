Chapter 26: Guard, Defer and Clean Code

Section 1: What Clean Code Really Means

Clean code is code that another person can read and understand without a long explanation, and it is also code that you yourself can still understand six months after you wrote it. Many beginners think clean code means short code, but short code can be confusing, and long code can be clear, so length alone is never the test. The real test is whether a reader can follow the idea from the top of a function to the bottom without getting lost, guessing, or rereading the same lines many times. Clean code tells a story in order, one small step at a time, and each step has a name that says what it does. When you write clean code, you are really being kind to your future self and to anyone who will work with your program later.

Clean code is not about clever tricks or showing off how much Swift you know, because clever code often hides its meaning behind shortcuts that only the author understands. A clever one-line solution might feel satisfying, but if a teammate cannot see what it does, then it costs more time than it saves, and it becomes a place where bugs can hide. Simple code, by contrast, uses plain names, small steps, and obvious flow, so a bug stands out quickly when something goes wrong. This chapter will show you two of Swift's best tools for clean code, guard and defer, and it will also teach habits that keep any program readable. Think of clean code as good manners for programmers, because it respects the reader's time and attention.

A useful habit is to read your own code out loud after you finish it, as if you were explaining it to a friend who has never seen it before. If you stumble over a sentence, or if you have to say "well, this part is a bit strange," then that part probably needs a better name or a simpler shape. Another useful habit is to imagine that the reader is tired and in a hurry, because real readers often are, and they will thank you for code that goes straight to the point. Clean code does not happen by accident, but it does not require talent either, since it is mostly a set of small habits repeated often. By the end of this chapter, you will have a practical toolkit for writing code that is easy to read, easy to test, and easy to change.

The rest of this chapter builds that toolkit step by step, starting with guard, which lets you check problems early and leave, and then defer, which guarantees cleanup happens no matter how a piece of code ends. Along the way, you will practise naming, shrinking functions, removing duplication, and reviewing your own work with a simple checklist. Each section ends with a question that helps you check your understanding before you move on, so take a moment to answer it honestly. If an answer feels shaky, reread the section or try the example in a playground, because understanding here will make every later chapter easier. Clean code is a skill that pays you back every single day you program, so it is well worth learning carefully now.

let score = 85
if score >= 50 {
    print("Passed with \(score)")
}

Section 2: Why Early Exits Beat Deep Nesting

Deep nesting happens when one if sits inside another if, which sits inside another, so the code drifts further and further to the right, and the reader has to remember many conditions at once. A function with five levels of nesting is hard to follow because the important work hides at the very bottom, buried under a staircase of conditions, and a small change near the top can break the meaning of everything below it. Beginners often write this shape without noticing, because each if feels reasonable on its own, but the whole shape becomes a maze. Early exits solve this problem by turning the shape upside down, so problems are handled first and the main work stays at the left edge. When a condition fails, the function leaves at once, and the reader knows that everything below that point has already passed its checks.

Think of a bouncer at the door of a party who checks invitations before anyone enters, because once you are inside, you can enjoy the party without being checked again. Early exits work the same way, since they check each requirement at the door and send invalid input away immediately, leaving the rest of the function free to do its real job. This shape is easier to read because each check stands alone, the reason for leaving is written next to the check, and there is no need to remember a pile of earlier conditions. It is also easier to test, because you can try each invalid input on its own and see that the function leaves promptly. Deep nesting, by contrast, forces a tester to build a perfect set of inputs that reaches the bottom, which is slower and more error-prone.

Early exits also make bugs easier to find, because when a function fails, you can look at the first check that sent it away and see exactly which requirement was not met. In a deeply nested function, a failure might mean that any one of several conditions was false, and you have to work out which one by tracing backwards through the staircase. Early exits give each failure its own clear exit point, almost like labelled doors, so debugging becomes a short walk instead of a maze search. They also make it safer to add a new check later, since you can add it at the top without disturbing the main work below, whereas adding a condition inside deep nesting risks breaking the balance of braces. Over time, this habit keeps functions flat, calm, and welcoming to new readers.

Some beginners worry that leaving a function early is untidy, as if a function should have only one exit at the very end, but Swift programmers generally prefer clarity over that old rule. A single exit at the end sounds neat in theory, yet in practice it forces you to wrap the whole function in conditions and track a result variable through every branch. Early exits are honest, because they say "this cannot continue, so we stop here" at the exact place where the problem is discovered. The rest of this chapter will show you guard, which is Swift's purpose-built tool for early exits, and you will see how it turns nested staircases into flat, readable code.

func greet(name: String?) {
    if let realName = name {
        if !realName.isEmpty {
            print("Hello, \(realName)")
        }
    }
}

Section 3: Introducing guard in Plain Words

A guard statement is Swift's way of saying "this must be true, or we cannot continue, so leave now," and it is written at the top of a function, loop, or other block where a requirement matters. The shape is simple: you write guard, then a condition, then else, then the code that runs when the condition fails, and that failure code must leave the current scope by returning, breaking, continuing, or throwing an error. If the condition is true, the program simply carries on past the guard as if it were not there, which is why guard feels so light to read. The key idea is that guard protects the code below it, like a gate that only lets good data through, and everything after the gate can trust that the requirement holds. This is the opposite of an if, which wraps the good path inside braces, because guard puts the failure path in braces and leaves the good path free.

Guard is most often used with optionals, but it works with any condition that produces a true or false answer, such as checking that a number is positive, that a string is not empty, or that a user is logged in. When you read guard, you can translate it into plain English as "make sure this is true, otherwise stop," and that translation is usually all you need to understand a function at a glance. Because the failure block must exit, the Swift compiler enforces the rule for you, so you cannot accidentally forget to leave and then carry on with bad data. This enforcement is a gift, because it removes a whole class of mistakes where a programmer checks a problem, prints a message, and then forgets to stop. With guard, the check and the exit are tied together in one statement, so they cannot drift apart.

You will meet guard again and again in real Swift programs, and experienced programmers reach for it whenever a function has requirements that must hold before the real work begins. It is especially common at the start of functions that take user input, read files, or talk to other parts of a program, because those are the places where bad data first appears. Learning guard well now will make your code look professional, and it will also make your own debugging faster, since failures will happen loudly and early. In the next sections, you will practise guard with optionals, with plain conditions, and with several conditions at once, and you will compare it directly with if let so you can choose the right tool each time. For now, practise saying the guard sentence out loud: "guard this is true, else leave," and notice how naturally it describes a requirement.

One more thing to notice is that guard does not change what your program does, it only changes how clearly the program says it, because any guard can be rewritten as an if with the branches swapped. The value of guard is therefore a human value, not a machine value, since the computer runs both shapes equally well, but people read the guard shape much faster.

func printScore(score: Int) {
    guard score >= 0 else {
        print("Score cannot be negative")
        return
    }
    print("Score is \(score)")
}

Section 4: guard let for Optionals

Optionals are values that may or may not exist, and guard let is the cleanest way to unwrap one when the rest of your code needs the real value. You write guard let, then a new name, then equals, then the optional, then else, then the exit code, and if the optional contains a value, that value becomes available under the new name for the rest of the block. This is different from if let, because the unwrapped value from if let only lives inside the if braces, while the value from guard let lives on after the guard, exactly where the main work happens. That difference matters a lot, because most of the time you unwrap an optional precisely so you can use it in the main work, not just inside a small side branch. Guard let therefore keeps the unwrapped value where you need it, at the top level of the function, without extra nesting.

Consider a function that greets a user whose name might be missing, since the name arrives as an optional string from somewhere else in the program. With if let, the greeting has to live inside the braces, and any further code that needs the name must also squeeze inside, which quickly builds a staircase. With guard let, you unwrap the name at the door, leave if it is missing, and then greet the user in flat, open code that anyone can follow. The pattern also scales beautifully, because you can unwrap two or three optionals with separate guard statements, one after another, and each one either succeeds or sends the function home. Readers can see the list of requirements in order, like a checklist, and they know that after the last guard, every value is real and ready to use.

There is a small detail worth learning early, which is that you can reuse the same name when unwrapping, by writing guard let name = name, and Swift understands that the new name shadows the old optional for the rest of the block. This is common in real code, and it keeps names short and natural, since you do not have to invent names like realName or unwrappedName for every value. Some beginners find shadowing confusing at first, but it soon feels normal, because after the guard, the name simply means the real value, and the optional version is no longer needed. If shadowing still feels strange, you may use a different name while you are learning, and switch later when you feel comfortable, since both styles are correct. The important thing is that the code reads clearly, not that you follow one naming trick.

Guard let also pairs well with clear failure messages, because the else block is the perfect place to explain what was missing before leaving. A message like "No name provided, so we cannot greet anyone" tells the reader and the user exactly what went wrong, which is far better than silently returning. In larger programs, the else block might log the problem, show an alert, or throw an error, but the shape stays the same: explain, then exit. Practise this pattern until it feels automatic, because unwrapping optionals safely is something you will do hundreds of times in Swift.

func greet(name: String?) {
    guard let name = name else {
        print("No name provided")
        return
    }
    print("Hello, \(name)")
}

Section 5: guard with Boolean Conditions

Guard is not only for optionals, because it works just as well with any condition that must be true before a function can continue, such as a number being in range, a string not being empty, or a user having permission. The shape is the same: guard, then the condition, then else, then the exit, and the code below can safely assume the condition held. This makes guard a general tool for stating requirements, not just a tool for unwrapping, and it helps readers see all of a function's rules in one place near the top. For example, a function that awards a prize might guard that the score is at least fifty, that the player has finished the game, and that the prize has not already been claimed, with each rule on its own clear line. If any rule fails, the function explains why and leaves, and the prize code below stays simple and trusting.

Boolean guards are especially helpful for input validation, which is the job of checking that data is sensible before you use it, because invalid input is one of the most common sources of bugs. A function that divides by a number should guard that the number is not zero, a function that sets a volume should guard that the value is between zero and one hundred, and a function that sends a message should guard that the message is not empty. Writing these checks as guards keeps the validation visible and separate from the main logic, so a reader can check the rules without wading through the work itself. It also means that when a rule changes, there is exactly one place to change it, which reduces the chance of updating one copy and forgetting another. Good validation is like a good fence, since it keeps bad data out before it can cause trouble inside.

You can also use guard with comparisons, logical combinations, and calls to helper functions that return true or false, as long as the whole condition reads clearly. A guard like "guard age >= 18 else" is instantly clear, while a guard with a long tangled condition might be better split into two guards with helpful messages. When you write boolean guards, choose messages that say what was wrong and what was expected, because a message like "Invalid input" helps nobody, while "Age must be 18 or older" tells the reader exactly how to fix the problem. This habit matters even in small learning programs, because it trains you to think about the person who will see the message, whether that person is a user, a teammate, or your future self reading a log file.

A common question is whether to use guard or if for a boolean check, and the answer depends on what happens when the check fails. If failure means the function cannot continue, then guard is the natural choice, because its else block must exit, and the code below can trust the condition. If failure means the function should do something different but still continue, then if is the natural choice, because both branches are real work rather than an exit.

func setVolume(level: Int) {
    guard level >= 0 && level <= 100 else {
        print("Volume must be between 0 and 100")
        return
    }
    print("Volume set to \(level)")
}

Section 6: guard else and What Must Happen

The else block of a guard is not optional decoration, because it is the place where you decide what happens when a requirement fails, and Swift insists that this block must leave the current scope. Leaving can mean returning from a function, breaking out of a loop, continuing to the next loop item, or throwing an error, and the compiler will complain if your else block simply prints a message and then falls through. This rule might feel strict at first, but it is actually what makes guard trustworthy, since a reader knows for certain that code below a guard only runs when the requirement held. Without this rule, guard would be no safer than an ordinary if, and programmers could forget the exit and carry on with bad data. The compiler acts like a careful friend here, refusing to let you write a guard that does not really guard anything.

Choosing the right exit matters, and it depends on where the guard sits and what the program should do next. In a function that returns a value, you usually return a sensible fallback or nil, while in a function that returns nothing, a plain return is enough. Inside a loop, continue skips to the next item, which is perfect when one bad item should not stop the whole loop, while break stops the loop entirely, which fits when a failure means there is no point carrying on. In a throwing function, you can throw an error that describes the problem, which lets the caller decide how to respond. Each of these exits tells a different story, so pick the one that matches your intention, and write a message or error that explains the failure clearly. A guard whose else block does the wrong kind of exit can confuse readers just as much as no guard at all.

It is also worth knowing that the else block runs only when the condition is false, which sounds obvious but has a practical consequence: any code in the else block should assume the requirement failed, and should not try to use the value that guard was checking. For example, after a failed guard let, there is no unwrapped value to use, so the else block must work without it, perhaps by returning a default or reporting the missing value. This is why the else block must exit, because there is nothing sensible for the main code to do without the missing value. Once you accept this logic, guard stops feeling like a rule imposed by the compiler and starts feeling like common sense, since you would not carry on cooking if a key ingredient were missing. You would stop, explain the problem, and decide what to do instead, which is exactly what the else block does.

Practise writing else blocks that are honest and specific, because vague failure handling is a common weakness even in otherwise tidy programs. Compare "return" with no message, which leaves the user guessing, against a short print or log line that names the failed requirement before returning, which helps everyone. In real applications, the message might go to a log file or become an error shown to the user, but the principle stays the same: say what failed, then leave cleanly.

func divide(top: Int, bottom: Int) -> Int? {
    guard bottom != 0 else {
        print("Cannot divide by zero")
        return nil
    }
    return top / bottom
}

Section 7: Multiple Conditions in One guard

A single guard can check several conditions at once by joining them with commas, and the guard only passes when every condition in the list is true. This is a compact way to state a group of related requirements, such as checking that a name is present, that it is not empty, and that an age is within range, all before the main work begins. The comma-separated list reads like a checklist, and if any item on the checklist fails, the else block runs and the function leaves. This shape is often cleaner than writing three separate guard statements, especially when the conditions belong together and share one failure message, because the reader sees the whole requirement in one place. However, it is not always the best choice, and learning when to combine and when to separate is part of writing clean code.

The main advantage of combining conditions is brevity, since one guard with three conditions replaces three guards with three else blocks, and the function stays short and flat. This works well when the conditions are closely related, like the parts of a single validation rule, and when a single message can explain any failure, such as "Invalid player details." It also works well when the conditions are cheap to check and do not need separate handling, because no special recovery is needed for one failing condition versus another. In such cases, combining keeps the top of the function tidy and lets the reader grasp the full requirement quickly. Think of it as writing one sentence with several clauses, which is clear when the clauses are short and connected, but confusing when they are long and unrelated.

There is one more detail that matters when you combine conditions, which is that Swift checks them from left to right, and later conditions can use values unwrapped by earlier ones in the same guard. For example, you can write guard let name = name, !name.isEmpty, and the second condition safely uses the unwrapped name, because the first condition has already succeeded by the time the second is checked. This left-to-right order makes combined guards powerful, since you can unwrap and then immediately validate the unwrapped value in one statement. It also means order matters, so put unwrapping first and checks that depend on it afterwards, or the compiler will complain that the value is not available yet. Reading a combined guard from left to right should feel like following a short story: first we get the value, then we check it, then we carry on.

As you practise, try both shapes on the same function and compare how they read, because personal taste matters less than clarity, and seeing the difference will sharpen your judgement. Write a version with one combined guard, then a version with separate guards, and ask a simple question: which version would a tired reader understand faster? Often the answer will be the combined guard for a small set of related checks, and the separate guards for a longer or more varied set. Either way, you are making a deliberate choice instead of copying a habit blindly, and deliberate choices are the heart of clean code.

func register(name: String?, age: Int) {
    guard let name = name, !name.isEmpty, age >= 13 else {
        print("Need a name and age 13 or older")
        return
    }
    print("Registered \(name), age \(age)")
}

Section 8: guard Versus if let, Side by Side

Guard let and if let both unwrap optionals safely, but they serve different purposes, and choosing between them is one of the most useful decisions a Swift beginner can learn. If let says "if this value exists, do this extra work inside these braces," which makes it perfect for optional side work, such as showing a nickname only when one is provided, while the rest of the program carries on regardless. Guard let says "this value must exist, or we cannot continue," which makes it perfect for requirements, where the rest of the function genuinely needs the value. The difference is not about which one is better in general, but about what your program means: is the value a nice bonus, or is it essential? Answering that question honestly will usually point you to the right tool.

The practical difference is scope, which is a fancy word for where a value can be used, because an if let value only lives inside its braces, while a guard let value lives on for the rest of the block. This means that if you need the unwrapped value in the main flow of a function, guard let keeps your code flat, while if let forces you to nest the main flow inside braces. On the other hand, if you only need the value briefly, such as printing an optional message when it exists, then if let is simpler, because it does not force the function to exit when the value is missing. A good mental test is to ask what should happen when the optional is empty: if the answer is "carry on without it," use if let, and if the answer is "stop, because we cannot proceed," use guard let. That single question resolves most cases cleanly.

It also helps to compare how the two shapes read to another person, because readability is the reason both exist. A function full of if let blocks around its main work reads like a set of nested boxes, where the reader must track which box they are inside, while a function that starts with guard let statements reads like a checklist followed by open, flat work. The guard version states its requirements up front, so the reader knows immediately what the function needs, whereas the if let version reveals its requirements gradually as the boxes open. Neither shape is wrong, but the guard shape usually communicates requirements more directly, which is why experienced Swift programmers prefer it for the top of functions. When you review your own code, look for if let blocks that wrap most of a function, since those are strong candidates for guard let.

Finally, remember that both tools protect you from force unwrapping, which is the risky habit of using an exclamation mark to demand a value that might not exist. If let and guard let both check safely, so neither will crash when the optional is empty, and choosing between them never means giving up safety. The choice is purely about structure and meaning, which is a good thing, because it means you can focus on clarity without worrying about correctness.

func describe(nickname: String?) {
    if let nickname = nickname {
        print("Nickname: \(nickname)")
    }
    print("Profile shown")
}

Section 9: Flattening Nested Code with guard

Flattening means taking code that drifts to the right through layers of nesting and reshaping it so the main work sits near the left edge, and guard is the best tool for this job. The process is simple to describe, even though it takes practise to do smoothly: find the innermost important work, list every condition that must be true for that work to run, and turn each condition into a guard at the top, with the failure case exiting early. What was once a staircase becomes a short checklist followed by flat work, and the reader no longer needs to remember a pile of conditions while reading the main logic. The flattened version also tends to be shorter, because it removes layers of braces and the indentation that went with them, which leaves more room for the ideas themselves.

Let us walk through a small example in words, since seeing the transformation matters more than memorising a rule. Imagine a function that prints a discount for a member: it first checks that a user exists, then that the user is a member, then that the user has enough points, and only then prints the discount. In nested form, the print statement sits three levels deep, and a reader must hold all three conditions in mind to understand it. In flattened form, three guards stand at the top, one for each condition, each with a clear message and an exit, and the print statement sits at the left edge, free of conditions. The two versions do exactly the same thing, but the flattened version explains itself faster, because the requirements are listed before the work instead of wrapped around it. This is the same idea as the bouncer at the door, applied to a whole function.

A word of caution is still needed, because flattening is a tool, not a rule that every function must obey at all costs. Some nesting is natural, such as a loop that contains an if, or a choice between two genuinely different paths, and trying to flatten those with guards can make code stranger, not clearer. The goal is to flatten requirement checks at the start of a block, not to remove every if from your program, since if remains the right tool for choices in the middle of work. A good test is to ask whether a condition is a requirement for everything below it, and if the answer is yes, then guard is probably the right flattening tool, while if the answer is no, then an if is probably fine where it is. Keep that test in mind, and your flattening will improve code instead of merely rearranging it.

Practise flattening on your own old programs, because they are full of staircases you wrote before you knew guard. Pick a nested function, rewrite it with guards, run both versions with the same inputs, and check that the outputs match, since flattening should never change behaviour. If the outputs differ, you have found a mistake in the rewrite, which is itself a useful lesson, because it shows that refactoring needs testing.

func discount(user: String?, isMember: Bool, points: Int) {
    guard let user = user else { print("No user"); return }
    guard isMember else { print("Not a member"); return }
    guard points >= 100 else { print("Not enough points"); return }
    print("\(user) gets a discount")
}

Section 10: Validating Function Inputs Early

Validating inputs means checking that the values passed into a function are sensible before the function uses them, and doing this early is one of the most valuable habits in programming. Functions are the doors of a program, since data from users, files, and other parts of the code all arrive through them, and if bad data slips through a door, it can cause wrong results, crashes, or confusing behaviour far away from where it entered. Early validation catches problems at the door, where the cause is still obvious and the fix is still simple, instead of letting them travel deep into the program. Guard is the natural tool for this, because it lets you list the rules at the top of the function and leave with a clear message when a rule fails. A function that validates early is like a careful shopkeeper who checks goods on delivery, rather than discovering a fault after the goods are already on the shelves.

Good validation checks the things that matter for that particular function, and no more, because over-checking can make a function rigid and hard to use. A function that calculates an average should check that the list is not empty, since dividing by zero would fail, but it probably does not need to check that every number is positive, unless the problem genuinely requires it. A function that sets a password should check length and emptiness, but it should not guess at rules the caller never promised. The art is to check exactly the conditions that the rest of the function assumes, so that the code below the guards can trust its inputs completely. When you write a function, ask yourself what the main code assumes, and turn each assumption into a guard, because assumptions that are never checked are the places where bugs breed.

Early validation also makes testing much easier, because each rule can be tested on its own with a single bad input, and the expected result is a prompt, clear exit. Testers do not need to construct elaborate inputs that reach deep into the function, since the guards are right at the top, and each one can be triggered independently. This is another reason why flat, guard-based functions are popular in teams, because they are cheap to test and quick to understand when a test fails. When you write tests for your own functions later in this book, you will appreciate having validation at the door, since it gives you obvious test cases for free. For now, practise by adding guards to functions you have already written, and then trying each bad input to see the clear message.

One last point is that validation should happen once, at the boundary where data enters, rather than being repeated in every helper the data passes through. If a public function validates its inputs and then calls private helpers, those helpers can usually trust the data, because it has already been checked, and repeating the checks everywhere would clutter the code. This idea is sometimes called trusting the inside after guarding the outside, and it keeps programs both safe and readable.

func average(numbers: [Int]) -> Double? {
    guard !numbers.isEmpty else {
        print("List must not be empty")
        return nil
    }
    let total = numbers.reduce(0, +)
    return Double(total) / Double(numbers.count)
}

Section 11: guard in Loops

Guard works inside loops as well as inside functions, and there its exit options take on a special meaning, because continue and break become the natural ways to leave. When a guard inside a loop fails, continue skips the rest of the current item and moves on to the next one, which is perfect when one bad item should not spoil the whole loop. For example, a loop that prints scores might skip any score that is missing or out of range, while still printing every good score, and guard with continue expresses that idea in one clear line. Without guard, the same loop would need an if that wraps the printing code, and the loop body would drift to the right, especially if several checks are needed. Guard keeps loop bodies flat, which matters a lot, because loops already add a layer of structure, and extra nesting inside them quickly becomes hard to follow.

The choice between continue and break inside a loop guard deserves careful thought, because the two exits tell very different stories. Continue says "this item is bad, try the next one," while break says "something is so wrong that the whole loop should stop now." A loop reading a list of names might continue past an empty name, since the other names are still worth printing, but it might break when it meets a special stop marker, since that marker means the list has ended. Choosing the wrong one can cause real bugs, such as skipping good data or stopping too early, so always ask which story matches your intention before you write the else block. Writing a short message before the exit, like "Skipping empty name," also helps readers and helps you debug, because it shows which items were skipped and why.

There is one trap to watch for, which is using return inside a loop guard when you meant continue, because return leaves the whole function, not just the current loop item. This mistake is easy to make, especially when you copy a guard from a function top into a loop body without adjusting its exit, and the result is a loop that stops after the first bad item instead of skipping it. Swift will not warn you, because return is a legal exit from the function, so the bug hides until a test with a bad item in the middle reveals it. The defence is simple: every time you write a guard inside a loop, pause and ask whether the exit should be continue, break, or return, and choose deliberately. That pause takes two seconds and prevents a bug that could take much longer to find.

Finally, remember that guard in a loop still follows the same rule as everywhere else, which is that the else block must exit the current scope, and inside a loop, continue and break count as exits from the loop item or the loop itself. This rule keeps loop guards honest, since you cannot write a guard that checks a problem and then carries on with the bad item anyway.

let scores: [Int?] = [80, nil, 95, nil, 70]
for score in scores {
    guard let score = score else { continue }
    print("Score: \(score)")
}

Section 12: guard in Initializers and Failable init

Initializers are special functions that set up a new instance of a struct or class, and guard fits them particularly well, because an initializer often needs to check its inputs before it can build a valid object. In a normal initializer, a failed guard can return early only after all properties have values, which limits its use, but Swift provides a special kind called a failable initializer, written with init? instead of init, which is allowed to return nil when the inputs cannot make a valid object. Inside a failable initializer, a guard that fails can simply return nil, which tells the caller that no object could be created, and the caller receives an optional that it must handle safely. This pattern keeps invalid objects from ever existing, which is a powerful idea, because much of the rest of the program can then trust that every object it meets is valid.

Consider a struct for a person that requires a non-empty name and an age between zero and one hundred and twenty, since those are sensible rules for the problem. A failable initializer can guard both rules at the top, returning nil when either fails, and only then assign the properties and finish building the person. Callers who try to create a person with an empty name will get nil, which they can check with if let or guard let, and they will never receive a person with a broken name. This is much cleaner than creating the person anyway and hoping that every later piece of code remembers to check the name, because the check happens once, at creation, and the guarantee lasts for the object's whole life. The object itself becomes a proof that its data passed the rules, which is a lovely property for clean programs.

Failable initializers also make failure obvious to callers, because the optional return type is visible in the code, and Swift forces callers to handle the nil case instead of ignoring it. This is better than an initializer that prints a warning but builds a broken object anyway, since a warning is easy to miss, while an optional cannot be used without unwrapping. When you design a type, ask which inputs would make the object meaningless, and turn those into guard checks in a failable initializer, so that meaningless objects simply cannot be born. Not every type needs this, since some types are valid for any input, but for types with real rules, such as dates, scores, or account details, it is an excellent design choice. The rules live with the type, where they belong, instead of being scattered across every place that creates it.

Practise by writing a small struct with a failable initializer, such as a rectangle that requires positive width and height, or a score that requires a value between zero and one hundred. Try creating valid and invalid instances, and notice how the invalid ones become nil without any crash or broken object. Then use the valid instances in the rest of a program, and notice how much simpler the rest becomes when it can trust its objects.

struct Player {
    let name: String
    let age: Int
    init?(name: String, age: Int) {
        guard !name.isEmpty, age >= 0 else { return nil }
        self.name = name
        self.age = age
    }
}

Section 13: Naming Things So Code Reads Like Sentences

Good names are one of the cheapest and most powerful tools in clean code, because a well-chosen name explains a value, a function, or a type without any comment at all. When you read code with good names, it feels almost like reading sentences, since a line like "if user.isLoggedIn" or "total = prices.reduce" tells you what is happening in plain language. Poor names, by contrast, force the reader to stop, look elsewhere, and work out what a value means, which breaks the flow of reading and invites mistakes. Names like x, temp, data, and stuff might save a few seconds while typing, but they cost minutes every time the code is read later, and code is read far more often than it is written. Choosing names well is therefore not fussiness, but a practical investment in every future reading.

Swift has conventions that help names read naturally, and following them makes your code feel at home among other Swift programs. Variables and functions usually start with a lowercase letter and use camel case, where each new word starts with a capital, such as totalScore or sendMessage, while types start with an uppercase letter, such as Player or TaskManager. Functions often read like verbs or verb phrases, such as calculateTotal or saveNote, because functions do things, while boolean values often read like questions, such as isEmpty, isLoggedIn, or hasDiscount, because they answer yes or no. Following these conventions means that readers can guess the kind of thing a name refers to before they even look it up, which speeds up reading enormously. Consistency matters more than cleverness, so pick a style and use it everywhere.

Length is another question that beginners often worry about, and the answer is that a name should be as long as it needs to be to be clear, and no longer. A loop counter can be i when its meaning is obvious from a tiny loop, but a value that lives across a whole function deserves a full name like customerCount, because the reader may meet it far from where it was created. Single-letter names are fine for tiny, obvious scopes, and long names are fine for important, long-lived values, but the worst choice is a short name for an important value, since that hides meaning where it matters most. If you find yourself writing a comment to explain a name, consider whether a better name would remove the need for the comment, because a good name is a comment that never goes out of date.

A practical habit for improving names is to read a line of your code aloud and ask whether it sounds like a sentence a person would say. If you have to translate it, such as turning "d.process" into "the data is processed," then the names need work, but if it already sounds like "user.hasDiscount" meaning "the user has a discount," then you are on the right track. Another habit is to rename fearlessly when you learn a better name, because modern editors make renaming safe, and a better name is worth the small effort.

Section 14: Short Functions, One Job Each

A function should do one job, and do it well, because a function that tries to do five jobs becomes hard to read, hard to test, and hard to reuse. When a function does one job, its name can describe it exactly, its body stays short, and a reader can understand it in one pass without holding many ideas in mind at once. When a function does many jobs, its name becomes vague, its body grows long, and a change to one job risks breaking the others, since they are tangled together. A useful test is to try describing a function in one short sentence without using the word "and," because if you need "and" several times, the function is probably doing several jobs. Splitting it into smaller functions, each with one job, is usually the fix, and the original function then becomes a short coordinator that calls the smaller ones in order.

Short functions are easier to test, because each one can be tried on its own with a few inputs, and when a test fails, the faulty job is immediately obvious. A long function that mixes reading a file, cleaning the data, calculating a result, and printing a report needs a complicated test that covers all four jobs at once, and a failure could come from any of them. Small functions, by contrast, give you small, precise tests, and they also give you reusable pieces, since a function that only calculates an average can be used anywhere an average is needed, while a function that calculates an average and prints a report can only be used where a report is wanted. Reuse is one of the main reasons to write functions at all, and single-job functions reuse far better than multi-job ones. Keep this in mind whenever a function starts to grow, and ask whether a piece of it deserves its own name and function.

There is no strict rule for how many lines a function should have, and chasing a number can do more harm than good, but as a guide, many programmers aim for functions that fit on one screen, roughly twenty lines or fewer, with the main idea visible at a glance. If a function grows beyond that, it is worth asking whether it contains a step that could be named and extracted, such as validating input, transforming data, or formatting output. Extraction is simple: select the step, move it into a new function with a clear name, and call it from the original place, then check that the program still behaves the same. This process, called refactoring, is safe when it is done one step at a time with testing after each step, and it is a skill you will use throughout your programming life. The goal is not shortness for its own sake, but clarity, and shortness usually follows clarity naturally.

Practise by looking at a long function you have written and splitting it into two or three smaller functions, each with a clear name and one job. Run the program before and after, and confirm that the behaviour is unchanged, because a good split changes structure, not results.

func average(scores: [Int]) -> Double {
    guard !scores.isEmpty else { return 0 }
    return Double(scores.reduce(0, +)) / Double(scores.count)
}

Section 15: Removing Duplicated Code

Duplicated code means the same logic written in two or more places, and it is one of the most common sources of bugs, because when the logic needs to change, every copy must be changed, and it is easy to miss one. Imagine a program that calculates a discount in three places with the same five lines, and then the discount rule changes: if you update two copies and forget the third, the program will give different answers in different places, and the bug may be hard to notice. The fix is to write the logic once, in a function with a clear name, and call that function from every place that needs it, so that a change happens in exactly one place. This principle is often called "do not repeat yourself," and it is one of the most practical rules in clean code, because it directly prevents a whole class of mistakes.

Spotting duplication takes practise, because it is not always word-for-word identical, and sometimes two pieces of code look different but do the same job with different variable names. A good habit is to notice when you are about to copy and paste a block of code, and to pause before pasting, because that pause is the moment when a helper function should be born instead. Ask what the block does in one sentence, give that job a name, and turn the block into a function that takes the varying parts as parameters and returns the result. The places that used the block then become short calls to the function, which are easier to read than the original block, and the logic itself lives in one well-named place. Copy and paste feels fast in the moment, but it borrows time from the future, when every copy must be maintained.

There are times when a small amount of duplication is acceptable, and recognising those times is part of good judgement. If two pieces of code look similar today but are likely to change in different directions tomorrow, then forcing them into one function can create awkward parameters and confusing branches, and keeping them separate may be clearer. The classic example is two screens that look alike now but will diverge as features are added, where sharing too early causes more pain than it saves. A sensible rule is to remove duplication when the copies must always stay the same, and to leave it when they merely happen to look alike for now. If you are unsure, wait until you see the third copy, because three copies are a strong signal that a shared helper is needed, while two copies may still be a coincidence.

Practise by searching your own programs for repeated blocks, even short ones of three or four lines, and turning the clearest repeat into a function. Run the program before and after to confirm that nothing changed, and notice how much shorter and clearer the calling code becomes. This exercise also improves your function-naming skills, since the helper's name must capture the shared job exactly. Over time, you will develop an eye for duplication, and you will start writing helpers before the second copy ever appears, which is the habit that keeps large programs manageable.

}

Section 16: Comments That Explain Why, Not What

Comments are notes written for human readers that the computer ignores, and good comments explain why code exists, not what it already says, because the code itself shows what it does. A comment like "add one to count" above the line count += 1 adds nothing, since any reader can see the addition, and such comments clutter the program without helping anyone. A comment like "we add one here because the list includes a header row" is genuinely useful, because it explains a reason that is invisible in the code, and it saves the next reader from wondering whether the plus one is a mistake. The test for a comment is simple: if removing it would lose information that the code cannot show, then it earns its place, but if the code already says the same thing, then the comment is just noise. Clean code aims for few, valuable comments rather than many obvious ones.

The best comments often explain decisions, constraints, and surprises, such as why a particular approach was chosen, why a simpler approach would fail, or why a strange-looking value is correct. For example, a comment might explain that a date is stored in a certain format because an older system expects it, or that a loop starts at one instead of zero because the first item is a title, not data. These are the details that a future reader cannot guess, and they are also the details that are most likely to be "fixed" by mistake if they are not explained. When you write a tricky piece of code, pause and ask what a reader would wrongly assume, and write a comment that corrects that assumption before it causes trouble. A short, honest comment at a tricky spot is worth far more than a long comment at an obvious one.

Beginners sometimes write comments as a diary of their own learning, such as "this is a loop" or "I struggled with this part," and while those notes may help while learning, they are not the kind of comments that belong in finished programs. A better learning habit is to keep such notes in a separate journal or notebook, and to put only reader-focused comments in the code itself. Similarly, commented-out old code, where dead lines are left in the program with comment markers, should be deleted rather than kept, because it confuses readers who cannot tell whether it is important or forgotten. Version control and backups exist to preserve old code, so there is no need to keep it in the file. A clean file contains only code that runs and comments that help, nothing else.

As you practise, try writing a program first with no comments at all, using only clear names and small functions, and then add comments only where a reader would still be puzzled. You will often find that very few comments are needed, which is a sign that the code itself is clean, and the comments you do add will be the valuable kind that explain why. This exercise reverses the beginner habit of commenting everything, and it teaches the more professional habit of making code self-explanatory first and commenting second.

Section 17: Constants Instead of Magic Numbers

A magic number is a raw number written directly in code without any explanation, such as 100, 0.9, or 60, and it is called magic because its meaning is mysterious to anyone who did not write it. When a reader meets a line like price * 0.9, they must guess whether 0.9 is a discount, a tax, a conversion rate, or something else entirely, and guessing is a poor way to read code. The fix is simple: give the number a name by storing it in a constant, such as let discountRate = 0.9, and then use the constant in place of the raw number, so the code reads as price * discountRate and explains itself. This small change costs one line and saves every future reader from guessing, which is an excellent trade, and it also makes the number easy to find and change later.

Constants also solve the maintenance problem that magic numbers create, because a magic number that appears in several places must be changed in every place when the value changes, and missing one place creates an inconsistency. A discount rate written as 0.9 in four functions becomes a bug waiting to happen, while a single constant called discountRate can be changed once, at its definition, and every use updates automatically. This is the same single-home principle you met when removing duplicated code, applied to values instead of logic, and it is just as important. Constants turn scattered, anonymous values into named, managed facts, and a program whose facts have names is much easier to keep correct as it grows.

Choosing good constant names matters, because a constant called value or number is barely better than the raw number itself, while a name like maxAttempts, passingScore, or secondsPerMinute tells the reader exactly what the number means. Constants in Swift are usually written with let, since their values do not change, and they are often placed near the top of a file or function where they are easy to find, or grouped together when several belong to the same feature. For values that are truly universal, such as the number of minutes in an hour, a well-known name makes the code read like a sentence, and a reader can trust it without checking. Avoid the temptation to name a constant after its value, such as let ninety = 0.9, since that name explains nothing and breaks the moment the value changes.

Practise by hunting for magic numbers and strings in your own programs, especially numbers that appear more than once or that would puzzle a stranger, and replace them with named constants. You do not need to replace every number, since small, obvious numbers like 0, 1, or 2 in a simple loop are usually clear from context, and over-naming those can clutter code. The numbers worth naming are the ones with business meaning, such as limits, rates, thresholds, and sizes, where the reader needs to know why that particular value was chosen. When in doubt, ask whether a stranger would ask "why this number?" and if the answer is yes, then the number deserves a name. That question alone will remove most magic from your code.

let discountRate = 0.9

    print(score)

Section 18: Organising Code into Logical Groups

As programs grow, organising code into logical groups becomes just as important as writing each piece correctly, because a reader must be able to find the piece they need without searching through a single long file. Logical grouping means putting related functions, types, and constants together, with the most important or most used pieces easy to find, and with clear separations between different jobs. In a small program, this might mean grouping all task-related functions together and all note-related functions together, with a blank line and a short comment marking each group. In a larger program, it might mean splitting code into separate files, one per feature, so that each file has a single clear purpose. Either way, the principle is the same: related things live together, and unrelated things live apart, so that finding and changing code is quick.

A useful way to think about grouping is to imagine your program as a small shop, where cooking tools belong in the kitchen, books belong on shelves, and cleaning supplies belong in a cupboard, because mixing them all in one pile would make every task slower. Code works the same way, since a programmer looking for the saving logic should not have to wade through printing logic, and a programmer fixing a calculation should not have to read file handling code to reach it. Grouping by feature or job, rather than by accident of writing order, makes the program's structure match its ideas, and that match is what makes large programs navigable. When you add a new function, pause and ask where a reader would look for it, and put it there, even if that means moving it away from where you happened to write it first.

Grouping also helps you notice when a piece of code belongs somewhere else, or when a group has grown so large that it should split into two. If a file or section contains two unrelated jobs, such as handling both tasks and user accounts, then it is probably doing too much, and splitting it will make both jobs clearer. Similarly, if a helper function is used by many groups, it may belong in a shared place of its own, rather than being copied or hidden inside one group. These decisions are part of design, and they get easier with practise, because you will start to feel when a group is tidy and when it is crowded. Do not be afraid to reorganise, since moving code without changing its behaviour is safe when you test after each move, and a tidy structure pays for itself quickly.

For the programs in this book, practise grouping by keeping each chapter's ideas in their natural places: model types together, file handling together, display together, and input handling together, with short comments marking each group. Even in a single-file program, a few group comments and blank lines can transform a wall of code into a readable map, and that map will help you enormously when you return to the program later. As your programs grow into multiple files in later chapters, the same habit will guide you to choose file names and contents that match the program's ideas.

Section 19: Introducing defer in Plain Words

Defer is Swift's way of saying "no matter how this block ends, run this cleanup code before leaving," and it is written as defer followed by a block of code that is saved and run later. When the program reaches a defer statement, it does not run the block immediately, but instead remembers it, and then carries on with the rest of the code, running the saved block only when the current scope exits. Scope here means the current pair of braces, such as a function body or a loop body, and exiting can happen through a normal return, an early guard exit, an error being thrown, or simply reaching the end. This guarantee is what makes defer so valuable, because cleanup that must always happen, like closing a file or restoring a setting, will happen even on paths that a programmer might forget. Defer turns "remember to clean up" from a hope into a promise.

A simple picture helps: imagine you borrow a book from a library and you write yourself a note that says "return the book before leaving the building," and you stick that note where you will see it on your way out, no matter which door you use. Defer is that note, because you write the cleanup right where you acquire the resource, and Swift makes sure it runs on every exit, including exits you did not plan for. Without defer, you would have to remember to write the cleanup before every return, every break, and every error path, and missing even one would leave the resource open or the state unrestored. With defer, you write the cleanup once, next to the acquisition, and the language handles all the exits for you. This closeness matters, because when acquisition and cleanup sit side by side, readers can see the pair and trust that they belong together.

Beginners sometimes wonder why defer is needed when they could simply write the cleanup at the end of a function, and the answer is that the end of a function is only one of many exits. A function with three guard statements has four exits: the three early exits plus the normal end, and cleanup written only at the end would be skipped on all three early exits. You could copy the cleanup before each exit, but that repeats code and invites the mistake of missing one copy, which is exactly the duplication problem from earlier in this chapter. Defer solves this cleanly by letting you write the cleanup once and trust it on every exit, which is both shorter and safer. It is a small piece of Swift syntax with a large effect on reliability, and it pairs naturally with guard, as you will see soon.

Try defer in a tiny example first, such as a function that prints a starting message, defers a finishing message, and then returns early on a condition, and watch the finishing message print even on the early return. That small experiment proves the guarantee better than any explanation, because you will see cleanup happen on a path where no explicit cleanup was written. Once you trust the guarantee, you will start using defer wherever cleanup matters, and your code will become more reliable without becoming longer.

func example() {
    defer { print("Cleaning up") }
    print("Doing work")
}

Section 20: defer Runs When Scope Exits

The most important detail about defer is exactly when its code runs, which is when the current scope exits, and scope means the block of braces that contains the defer statement. For a defer written directly in a function body, the scope is the whole function, so the deferred code runs just before the function returns, no matter which return it is. For a defer written inside a loop body, the scope is that single pass through the loop, so the deferred code runs at the end of each pass, not at the end of the whole loop, which is a detail that surprises many beginners. For a defer written inside an if block, the scope is that if block, so the code runs when the if block ends, even if the function continues afterwards. Understanding scope is therefore essential, because it tells you exactly when your cleanup will happen, and placing a defer in the wrong scope can make cleanup happen too early or too late.

Normal exits are easy to picture, since a function that reaches its last line runs its deferred blocks in order and then returns, which is the case most programmers think of first. Early exits are where defer proves its worth, because a guard that returns early still triggers the deferred blocks of the scope it leaves, so cleanup is not skipped on the failure path. Error exits work the same way, since a throwing function that throws an error still runs its deferred blocks before the error travels to the caller, which means resources are cleaned up even when something goes wrong. This consistency across all exit types is what makes defer trustworthy, because you do not need to think separately about normal, early, and error exits, since defer handles all of them with one mechanism. The guarantee is uniform, and uniform guarantees are easy to reason about.

Loop scopes deserve special attention, because they are the place where defer timing most often confuses beginners. Imagine a loop that opens a file, defers closing it, and processes one item per pass: the deferred close runs at the end of each pass, which is correct, since each pass opens its own file and should close it before the next pass begins. If you mistakenly believed that defer runs only at the end of the function, you might think all the files stay open until the loop finishes, which would be wrong and could cause resource problems. The correct mental model is that defer belongs to its braces, not to its function, and each pass through a loop creates a fresh scope with fresh deferred blocks. When you write defer inside a loop, always ask whether per-pass cleanup is what you want, and in most cases it is, since each pass usually acquires its own resource.

Practise the timing by writing small functions with prints in the main code and in defer blocks, placed in different scopes, and then tracing the order of the printed lines. Try a function with an early return, a loop with a defer inside it, and an if block with a defer inside it, and predict the output before running each one.

func work(shouldStop: Bool) {
    defer { print("Function ending") }
    if shouldStop {
        print("Stopping early")
        return
    }
    print("Finishing normally")
}

Section 21: defer Order: Last In, First Out

When a single scope contains several defer statements, they do not run in the order you wrote them, but in reverse order, so the last defer written runs first and the first defer written runs last. This rule is called last in, first out, and it matches the way nested resources are usually acquired, since the most recently acquired resource is often the one that should be released first. Imagine opening a box, then opening a smaller box inside it: you should close the smaller box before closing the larger one, and reverse-order defer does exactly that without you having to think about it. If defer ran in written order, you would have to write your cleanups backwards to get the same effect, which would be confusing and error-prone, so Swift's reverse order is a thoughtful design choice. Learning this order now will prevent surprises when you first use several defers together.

A concrete example makes the order clear, so consider a function that defers three messages, one after another, and then finishes normally. The output will show the third message first, then the second, then the first, which looks backwards if you expected written order, but makes perfect sense once you think of defer as a stack of notes. Each new defer is placed on top of the stack, and when the scope exits, notes are taken off the top, one by one, so the top note, which was written last, is handled first. This stack picture is worth remembering, because it also explains why defer pairs so well with acquisition order: resources acquired first sit at the bottom of the stack and are released last, which is usually the safe order for nested resources. Try this example yourself and watch the reversed output, since seeing it once will fix the rule in your mind better than reading about it several times.

Reverse order also matters when cleanups depend on each other, because a later cleanup may need an earlier resource to still be available. For example, suppose a function opens a file and then starts a log entry about that file: the log entry should be finished before the file is closed, so the defer that finishes the log should run first, which means it should be written last. If you write the defers in acquisition order, with the file defer first and the log defer second, then reverse execution gives you exactly the right release order, which is log first and file second. This is a happy coincidence that comes from writing acquisition and cleanup in the same order, and it is one of the reasons experienced programmers write a defer immediately after acquiring each resource, rather than collecting all cleanups at the end. The pattern of acquire-then-defer, repeated for each resource, naturally produces the correct release order.

Practise reverse order with a small function that defers three print statements and also returns early on a condition, and check that the reversed order holds on both the normal and the early path. Then try a more realistic pair, such as deferring a "closing file" message after a "starting work" message, and notice how the closing message still runs first when the function exits.

func orderExample() {
    defer { print("First written, runs last") }
    defer { print("Second written, runs second") }
    defer { print("Third written, runs first") }
    print("Doing work")
}

Section 22: defer for Closing Files and Releasing Resources

Files are the classic example of a resource that must be released, because a file that is opened and never closed can lock other programs out, lose buffered data, or exhaust the system's supply of open files. In Swift's standard library, many file operations handle opening and closing for you, but whenever you work with a resource that you open yourself, or with a type that requires an explicit close, defer is the safest way to guarantee that close happens. The pattern is simple: open the resource, immediately write a defer block that closes it, and then do your work, knowing that every exit path, including early returns and errors, will run the close. This pattern is so common that experienced programmers treat an open without a nearby defer as a warning sign, and you should develop the same instinct. A resource and its cleanup belong together in the code, just as they belong together in real life.

The same pattern applies to many other resources beyond files, such as network connections that must be disconnected, locks that must be released, or temporary folders that must be deleted when work is done. In each case, the danger is the same: a forgotten release on an unusual path, such as an error or an early return, leaves the system in a messy state that can affect later work. Defer removes that danger by centralising the release in one place that all paths share, so you no longer need to remember every exit. This is especially valuable in functions with several guards, because each guard is an exit that could otherwise skip cleanup, and defer makes all of those exits safe at once. When you review code, look for resources that are acquired but have no nearby defer, since those are the places where leaks hide.

It is important to keep defer cleanup code simple and safe, because it runs at exit time, when the program may already be handling an error, and a failing cleanup could make the situation worse. A close operation that can fail should usually have its failure ignored or logged, rather than thrown, since there is often nothing sensible to do about a close failure at exit time. Similarly, a defer block should not do long or complicated work, such as starting a new network request, because exit-time code should finish quickly and predictably. Think of defer as a tidy-up step, like putting tools away after a job, not as a new job in itself, and keep it short. If cleanup genuinely needs complex logic, put that logic in a helper function and call it from the defer block, so the defer itself stays readable.

A final note is that defer does not replace careful design of your resource types, since the best resources clean themselves up automatically when they go out of scope, through mechanisms you will meet later. Defer is the tool for cases where automatic cleanup is not available, or where you need an explicit step at a specific time, and it is a perfectly respectable tool for those cases. Do not feel that using defer is a failure of design, because even well-designed programs use it for temporary state changes and simple releases.

    print("Resource opened")
    defer { print("Resource closed") }
    print("Using resource")
}

Section 23: defer for Unlocking and Restoring State

Not all cleanup involves files or external resources, because programs also change their own internal state temporarily, and that state often needs to be restored before a function returns. A common example is a function that turns on a "busy" flag while it works, so that other parts of the program know not to start conflicting work, and that flag must be turned off again when the work finishes, even if the work fails early. Another example is a function that temporarily changes a setting, such as a display mode or a sorting order, and must restore the old setting before returning, so that callers are not surprised by a changed world. Defer is perfect for both cases, because you can save the old value, set the new value, defer the restoration, and then work freely, knowing that every exit restores the state. This pattern keeps functions polite, since they leave the world as they found it.

Restoring state with defer also makes code easier to reason about, because callers can trust that a function will not leave unexpected changes behind, which is a property sometimes called leaving no trace. When functions leave traces, such as a flag still set or a setting still changed, the next function to run may behave strangely, and the bug can be far from its cause, which makes debugging painful. Defer prevents this class of bug by tying restoration to scope exit, so that no path, however unusual, can forget it. This is the same guarantee you met for files, applied to internal state, and it shows how general the defer idea really is. Whenever a function says "temporarily," that word is a strong hint that a defer should follow, since temporary changes need guaranteed restoration.

A practical example helps to fix the pattern, so imagine a simple counter that tracks whether a task is running, with a function that sets it to true, does some work, and must set it back to false. Without defer, the function would need to set the flag back before every return, and a new early return added later might forget it, leaving the program stuck thinking a task is still running. With defer, the restoration is written once, right after the flag is set, and every return, including future ones added by other programmers, will restore it automatically. This robustness against future edits is a major benefit, because code is changed far more often than it is written, and a pattern that survives edits is worth more than one that works only on the day it is written. Defer makes restoration edit-proof in exactly this way.

Practise this pattern with a tiny program that has a global or shared setting, a function that temporarily changes it, and prints before, during, and after, including on an early return path. Watch the setting return to its old value on every path, and then try removing the defer to see how the early return leaves the wrong value behind. That contrast is the lesson in miniature, and it will help you recognise temporary state changes in larger programs. Remember the rule: if a change is temporary, then its restoration belongs in a defer, written immediately, with the old value saved first.

var isBusy = false
func doWork() {
    let wasBusy = isBusy
    isBusy = true
    defer { isBusy = wasBusy }
    print("Working, busy is \(isBusy)")
}

Section 24: defer Is Not a Replacement for Error Handling

Defer and error handling are related, because both deal with things going wrong, but they solve different problems, and confusing them leads to code that cleans up nicely while still failing to report or handle the actual error. Defer answers the question "what cleanup must happen no matter what?" while error handling answers the question "what went wrong, and what should the program do about it?" A defer block can close a file after an error, but it cannot decide whether the caller should retry, show a message, or use a fallback, because that decision belongs to do, try, and catch, which you learned in earlier chapters. Keeping these roles separate makes programs clearer, since each mechanism does one job well, and readers can tell at a glance which job each piece of code is doing.

A common beginner mistake is to put error reporting inside a defer block, such as printing an error message or trying to fix the problem, when the defer runs on every exit, including successful ones. A defer that prints "something went wrong" will print even when nothing went wrong, because defer cannot tell a successful exit from a failed one, since it runs on both. This makes defer the wrong place for error-specific logic, which should live in the catch block or in the guard's else block, where the program knows that a failure actually happened. Defer should be reserved for unconditional cleanup, such as closing, unlocking, or restoring, which is needed on success and failure alike, and it should not try to guess whether the exit was good or bad. If a cleanup step genuinely differs between success and failure, then it belongs in the main code or the error path, not in a defer.

Another mistake is to assume that defer somehow handles an error, as if writing a defer that closes a file means the error itself has been dealt with, when in fact the error still travels to the caller unless it is caught. Defer does not catch, swallow, or transform errors, and it does not stop an error from propagating, since it runs as part of leaving, not instead of leaving. A throwing function with a defer will still throw after the defer runs, and the caller must still handle the error with do and catch, or propagate it further. This is correct behaviour, because cleanup and error handling are separate concerns, but beginners sometimes feel surprised when a program with a defer still reports an error, as if the defer should have fixed it. Think of defer as the cleaning crew that tidies a room after an event, not as the event organiser who decides whether the event succeeded.

Finally, remember that defer blocks themselves should not throw errors or cause new failures, because they run during exit, when the program is already in the process of leaving or propagating an error. A defer that throws would complicate the exit and could hide the original error, which is the opposite of helpful, so keep defer code simple and failure-proof. If a cleanup operation can fail, handle that failure inside the defer, for example by ignoring it or logging it, rather than letting it escape.

func readValue() throws -> Int {
    defer { print("Cleanup done") }
    return 42
}

Section 25: Combining guard and defer

Guard and defer are natural partners, because guard creates early exits and defer guarantees cleanup on those exits, so together they make functions that are both flat and safe. The typical shape is easy to describe: acquire a resource, defer its cleanup, then use guards to validate inputs and check conditions, knowing that any guard failure will still run the deferred cleanup on its way out. Without defer, each guard's early exit would need its own cleanup code, which would repeat the cleanup many times and invite mistakes, but with defer, the cleanup is written once and shared by all exits. This combination is one of the most common patterns in professional Swift code, and recognising it will help you read real programs, where guard and defer often appear within a few lines of each other. The two tools were designed to work together, and using them together is a sign of growing fluency.

Order matters when combining them, because the defer must be written before the guards that might exit, if the cleanup is to run on those exits. A defer written after a guard cannot clean up after that guard's early exit, since the program leaves before reaching the defer statement, and the deferred block is never even registered. This is a subtle point that causes real bugs, so the rule is to acquire and defer first, then guard, which ensures that every later exit is covered. Think of it as putting on a safety harness before walking onto a narrow path, rather than after you have already started, because the harness only helps if it is on before the risky steps. When you write a function, check the order: acquisition, defer, guards, then work, and if you find a guard before its defer, move the defer earlier.

A worked example in words will make the combination concrete, so imagine a function that opens a log, defers closing it, guards that the message is not empty, guards that the user is allowed to log, and then writes the message. On the success path, the message is written and the log is closed by the defer at the end, while on either guard failure, the function prints a reason, returns early, and the defer still closes the log on the way out. Without defer, the two guard exits would each need to close the log, and a third guard added later would need a third close, but with defer, all exits share one close. The code is shorter, safer, and easier to change, which is the triple benefit that clean code aims for. This example is small, but the pattern scales to functions with many guards and several resources, where the savings grow with each exit.

Practise the combination by writing a function that simulates a resource with prints, defers its close, and then has two guards that can fail, and run it with inputs that trigger each guard and with inputs that succeed. Watch the close message appear on every path, and notice how the guards stay simple because they do not need to clean up themselves. Then try moving the defer below a guard and watch the close disappear on that guard's path, which proves why order matters.

func logMessage(_ message: String) {
    print("Log opened")
    defer { print("Log closed") }
    guard !message.isEmpty else {
        print("Empty message")
        return
    }
    print("Logged: \(message)")
}

Check: Why must a defer be written before the guard statements it is meant to protect?

Section 26: Cleaning Up After an Early Return

Early returns are a gift for readability, but they create a cleanup question, because a function that returns early skips all the code after the return point, including any cleanup written at the end. If a function opens a resource, does some work, and then returns early on a bad input, a cleanup step written only at the normal end will never run on that early path, and the resource will be left open. This is the exact problem that defer solves, and it is worth understanding deeply, because it is the reason defer exists in the first place. The rule to remember is that any cleanup written as ordinary code at the end of a function is only safe if the function has exactly one exit, and as soon as you add guards and early returns, end-of-function cleanup becomes unreliable. Defer replaces that fragile pattern with a guarantee that covers every exit.

A useful way to audit a function for this problem is to count its exits, including the normal end, every guard return, every loop break that leaves a resource scope, and every throw, and then to ask, for each exit, whether cleanup happens. If cleanup is written as ordinary code, you will usually find that some exits skip it, unless the programmer carefully repeated the cleanup before each exit, which is tedious and easy to get wrong. If cleanup is written as a defer, the audit becomes trivial, because the defer runs on every exit by definition, and you only need to check that the defer was registered before the exits, not that each exit repeats it. This audit habit is a practical debugging skill, and it will help you spot resource leaks in code written by others, where cleanup is often written only at the end and early returns were added later without updating it. Code changes over time, and defer is what makes cleanup survive those changes.

There is a related case where early returns happen inside nested scopes, such as a loop or an if block, and the cleanup belongs to that inner scope rather than to the whole function. In that case, a defer inside the inner scope runs when that scope exits, including on an early return from within it, which is exactly right, while a defer at function level would delay cleanup until the whole function ends. Choosing the right scope for the defer is therefore part of the audit, since cleanup should happen as soon as the resource is no longer needed, not merely eventually. A file opened inside a loop pass should be closed at the end of that pass, not at the end of the function, and a defer inside the loop body achieves that, while a defer outside the loop would not. Scope-aware cleanup is a sign of careful programming, and it prevents resources from being held longer than necessary.

Practise by taking a function with an early return and a cleanup step at the end, and converting the cleanup to a defer, then testing every exit path to confirm that cleanup now happens on all of them.

func process(value: Int?) {
    print("Started")
    defer { print("Tidied up") }
    guard let value = value else {
        print("No value")
        return
    }
    print("Value is \(value)")
}

Check: Why does cleanup written only at the end of a function fail when early returns are added?

Section 27: Refactoring a Messy Function Step by Step

Refactoring means improving the structure of code without changing what it does, and it is best done step by step, with testing after each step, rather than in one large rewrite. A large rewrite is risky, because if the behaviour changes, you will not know which part of the rewrite caused it, while small steps let you catch mistakes immediately, since each step is easy to check. The process usually starts by understanding the messy function, which means reading it, running it with several inputs, and noting its outputs, so that you have a baseline to compare against. Then you make one small improvement, such as extracting a helper, replacing a nested if with a guard, or naming a magic number, and you run the same inputs again to confirm that the outputs are unchanged. Repeating this cycle gradually transforms the function, and at each point the program still works, which keeps the work safe and confidence high.

A good first step in refactoring a messy function is to add guards for its requirements, because guards flatten the structure and make the rest of the work visible. Look for if blocks that wrap large parts of the function, and ask whether they are really requirements, in which case a guard at the top can replace them, with the failure case exiting early. A second step is to extract repeated or distinct jobs into helper functions, giving each helper a clear name, which shortens the original function and reveals its overall shape. A third step is to replace magic numbers and vague names with named constants and clear names, which makes the code explain itself without comments. Each of these steps is small on its own, but together they can transform a tangled function into a short coordinator that reads like a list of steps, and the transformation is safe because each step is checked separately.

Testing during refactoring does not need to be formal, especially in small learning programs, but it does need to be deliberate, because "it looks right" is not the same as "it behaves the same." Keep a small set of example inputs that cover the normal case, the edge cases, and the failure cases, and run them before refactoring and after each step, comparing the outputs. If an output changes, you have either found a refactoring mistake, which you should fix by undoing the last step, or you have discovered that the original behaviour was itself a bug, which is useful information that deserves a conscious decision. Writing down the test inputs and outputs, even briefly, makes this comparison easy, and it is a habit that professional programmers rely on. Refactoring without tests is like tidying a room in the dark, since you cannot tell whether you have broken something until much later.

Practise refactoring on a deliberately messy function that you write yourself, with deep nesting, duplicated logic, and vague names, and then improve it step by step, testing after each step. Keep the original version saved separately, so you can compare the start and finish, and notice how much clearer the final version is, even though it does exactly the same thing.

func messy(score: Int?) -> String {
    guard let score = score else { return "No score" }
    guard score >= 0 else { return "Invalid score" }
    return score >= 50 ? "Pass" : "Fail"
}

Check: Why is refactoring safer when it is done in small steps with testing after each step?

Section 28: Reading Code Aloud as a Test

Reading code aloud is a surprisingly powerful test for clarity, because spoken language reveals awkwardness that silent reading often hides. When you read a function aloud, you are forced to turn each name and each structure into words, and if a name is vague or a structure is tangled, you will stumble, hesitate, or need to add explanations that are not in the code. That stumble is valuable information, because it marks exactly the place where a reader will also struggle, and it tells you what needs a better name, a simpler shape, or a short comment. Programmers who read their code aloud regularly catch unclear code before anyone else has to suffer it, and the habit costs nothing but a few minutes. Try it with your next function, and notice how different it feels from merely looking at the code.

The technique works best when you pretend you are explaining the code to a friend who cannot see it, because that forces you to say what each part means, not just what it is spelled. For example, reading "guard let name = name else return" aloud as "make sure we have a name, otherwise stop" shows that the code already reads well, while reading a vague line aloud as "do the thing with the stuff" shows that the names have failed. If you find yourself saying "well, this part is a bit complicated" or "ignore this for now," then that part needs work, since a reader will have the same reaction. The aloud test is therefore a kind of honesty check, because it prevents you from glossing over parts that you understand only because you wrote them, rather than because they are clear. Code that passes the aloud test is code that a stranger can follow, which is the real goal.

Reading aloud also helps with structure, not just naming, because a flat function reads as a short, ordered story, while a deeply nested function reads as a story full of interruptions and side conditions. When you read a nested function aloud, you will hear yourself saying "if this, then if that, then if the other, then finally," which sounds tiring, and that tiredness is a signal to flatten with guards. A function that has been refactored with guards reads as "first check this, then check that, then do the work," which sounds calm and confident, and that calmness is what readers experience too. Listening to your code is therefore a shortcut to feeling what readers will feel, and it can guide refactoring decisions without any formal rules. If it sounds tangled, it is tangled, and if it sounds clear, it probably is.

Make the aloud test a regular part of finishing a function, alongside running it and checking its outputs, so that clarity becomes a checked property rather than a vague hope. You do not need to read every line aloud for every tiny program, but for functions that others will read, or that you will return to later, the few minutes are well spent. Over time, you will internalise the test, and you will start hearing the awkwardness in your head as you write, which means you will write clearer code from the start.

func welcome(name: String?) {
    guard let name = name else { return }
    print("Welcome, \(name)")
}

Check: What does it mean when you stumble while reading your own code aloud?

Section 29: Handling Edge Cases First

Edge cases are the unusual inputs that sit at the edges of a problem, such as an empty list, a zero value, a missing name, or a maximum limit, and they are where many bugs hide, because programmers naturally think about normal inputs first. Handling edge cases first, with guards at the top of a function, is a clean code habit that makes these unusual inputs visible instead of letting them slip through to code that assumes normal data. For example, a function that averages a list should guard against an empty list before dividing, a function that greets a user should guard against a missing name before greeting, and a function that sets a volume should guard against out-of-range values before applying them. When edge cases are handled first, the main code can assume normal data, which simplifies it and removes defensive checks scattered throughout. The function becomes two clear parts: edge cases at the door, and normal work inside.

Thinking about edge cases also improves your understanding of the problem itself, because it forces you to ask what the function should do when the input is strange, rather than discovering the question later through a crash. Should an empty list average to zero, to nil, or to an error, and who decides? Should a missing name mean a silent return, a default greeting, or an error message, and which choice fits the program? These are design questions, not just coding questions, and answering them early, with guards and clear messages, makes the function's behaviour deliberate instead of accidental. Beginners often leave edge cases unhandled, which means the program's behaviour on strange inputs is whatever happens by accident, such as a crash or a wrong answer, while experienced programmers decide the behaviour on purpose. Guard statements are the visible record of those decisions, which is another reason they aid readability.

A practical way to find edge cases is to list the boundaries of each input, such as zero, one, empty, maximum, and missing, and to test each boundary deliberately. For a number, test zero, negative, one, and a very large value, and for a string, test empty, one character, and a very long value, and for a list, test empty, one item, and many items. This boundary testing is quick, and it often reveals surprises, such as a function that works for many items but fails for one, or that works for positive numbers but not for zero. When you find a surprise, add a guard that handles it explicitly, with a message or result that makes sense, and add the boundary case to your mental test set. Over time, boundary thinking becomes automatic, and you will start writing guards for edge cases before you even run the program, which prevents bugs instead of merely catching them.

Practise edge-case-first thinking by taking a function you have already written and listing its edge cases, then adding guards for each one and testing them. Notice how the main code becomes simpler once the edges are handled, and how the function as a whole becomes more trustworthy.

func firstItem(items: [String]) -> String? {
    guard !items.isEmpty else { return nil }
    return items[0]
}

Section 30: Avoiding Force Unwrapping in Clean Code

Force unwrapping means using an exclamation mark to demand the value inside an optional, with the program crashing if the optional is empty, and it is one of the riskiest habits in Swift. A force unwrap says "I am certain this value exists," but certainty in programming is often misplaced, because data from users, files, and other systems can surprise you, and a crash is a harsh punishment for a wrong guess. Clean code avoids force unwrapping except in the rare cases where the value truly cannot be missing, such as a value set up in the same function just before, and even then, many programmers prefer a safe unwrap for clarity. The safe alternatives you already know, if let and guard let, check the optional and handle the missing case gracefully, which turns a potential crash into a controlled message or fallback. Choosing safety over brevity is a hallmark of professional code, because a program that handles missing data politely is far better than one that crashes.

Force unwrapping is tempting because it is short, since writing name! is shorter than writing a guard let, and in a small example where the value is obviously present, it can feel harmless. The danger grows as programs grow, because a force unwrap written when the value was obviously present may later be used in a new context where it is not, and the crash will appear far from the change that caused it. A value that comes from a dictionary lookup, a file read, or a user input is never obviously present, no matter how confident you feel, and those are exactly the places where force unwrapping causes real-world crashes. A good rule is to treat every force unwrap as a small bet that the program will crash if you are wrong, and to ask whether that bet is worth the few characters saved. Almost always, the answer is no, and a safe unwrap is the better choice.

There are a few legitimate uses of force unwrapping, and recognising them helps you avoid both reckless use and fearful avoidance. A common legitimate case is in tests, where a crash on missing test data is acceptable because it signals a broken test immediately, and another is for values that the program itself just created and therefore knows exist, such as an image loaded from the app's own bundle. Even in those cases, many programmers add a comment explaining why the unwrap is safe, so that a future reader does not mistake it for carelessness. If you cannot write a convincing comment explaining why the value cannot be missing, then the unwrap is probably not safe, and you should use guard let or if let instead. This comment test is a practical filter that catches most unsafe unwraps before they cause trouble.

Finally, remember that the compiler and the tools around Swift can help you find force unwraps, since searching for exclamation marks in your code is a quick audit, and many teams treat new force unwraps as something that needs justification in review. Make this audit part of your own review checklist, and treat each force unwrap as a question: is this safe, and can I prove it?

func greet(name: String?) {
    guard let name = name else {
        print("No name to greet")
        return
    }
    print("Hello, \(name)")
}

Section 31: Small Helpers and Helper Functions

Helper functions are small functions that do one supporting job for a larger function, such as validating an input, formatting a value, or calculating a piece of a result, and they are one of the best tools for keeping main functions short and readable. When a main function contains a chunk of code that can be described in one sentence, that chunk is a candidate for a helper, because giving it a name and moving it out makes the main function read like a list of steps, each step named by its helper. For example, a function that processes an order might call helpers to check stock, calculate tax, and format a receipt, and a reader can understand the order process without reading the details of tax calculation. Helpers let readers choose their level of detail, since they can grasp the big picture from the main function and dive into a helper only when they need its specifics. This layered reading is much easier than facing a single long function all at once.

Helpers also improve reuse, because a helper written for one function can often be called from others that need the same job, which removes duplication and keeps the logic in one place. A helper that formats a price, for instance, can be used by a shopping cart, a receipt printer, and a report generator, and a change to the format happens once, in the helper, rather than in three places. Even when a helper is used only once, it still earns its place if it gives a name to a chunk of logic, because naming is itself a form of documentation, and a well-named helper explains its chunk better than a comment could. Do not worry that creating a helper for a single use is wasteful, since the cost of a function call is tiny, and the clarity gained is large. Small helpers are a sign of thoughtful design, not of over-engineering, as long as each helper does a real, nameable job.

There is a balance to strike, because too many tiny helpers can fragment code, forcing readers to jump between many small functions to follow a simple idea. If a helper is only two lines long and its job is obvious from the surrounding code, then inlining it, which means keeping it in place, may be clearer than extracting it, since extraction adds a jump without adding meaning. The judgement comes from asking whether the extraction helps a reader: does it name a non-obvious job, hide a messy detail, or enable reuse? If the answer is yes, extract, and if the answer is no, leave the code where it is. This judgement improves with practise, and it is better to extract slightly too often while learning, since the cost of an extra helper is low, while the cost of a tangled function is high. Over time, you will develop a feel for the right size.

Practise by taking a medium-length function and extracting two helpers from it, giving each a clear name, and then reading the main function aloud to hear how much clearer it sounds.

func isValidScore(_ score: Int) -> Bool {
    return score >= 0 && score <= 100
}
print(isValidScore(75))

Section 32: Consistent Style and Formatting

Consistent style means writing code in the same way throughout a program, with the same indentation, spacing, naming patterns, and ordering, so that readers can focus on ideas instead of adjusting to a new look on every page. Inconsistency is tiring, because a reader who meets three different ways of writing the same thing must wonder whether the differences mean something, when they usually mean nothing at all. For example, if one function uses guard for validation and another uses nested if for the same job, a reader may wonder whether the second function has a special reason, when it is simply written differently. Consistency removes that false puzzle, since readers learn one pattern and can then recognise it instantly everywhere. Teams care deeply about style for this reason, and many use automatic formatters to enforce it, but even alone, you can develop a consistent personal style that makes your code feel professional.

Indentation is the most visible part of style, because it shows structure, and Swift code is conventionally indented with four spaces per level, with matching braces aligned so that the start and end of each block are clear. Consistent indentation lets a reader see nesting at a glance, while inconsistent indentation can hide a bug, such as a line that looks inside an if block but is actually outside it. Spacing matters too, since spaces around operators and after commas, and blank lines between logical groups, give code room to breathe, while cramped code feels rushed and is harder to scan. These details may seem small, but they affect reading speed every time, and reading speed affects how quickly bugs are found. Treat formatting as part of writing, not as decoration to be added later, and tidy as you go.

Naming consistency is another part of style, because using the same kind of name for the same kind of thing helps readers predict meaning. If one function calls a count total and another calls it number and a third calls it amount, then readers must learn three names for one idea, while a single consistent name would let them transfer understanding instantly. Similarly, if boolean values sometimes start with is and sometimes do not, readers cannot guess which names are booleans, and they must check each one. Pick conventions for your names, such as verbs for functions and is or has for booleans, and apply them everywhere, even when a different name might feel slightly better in one place. Consistency beats local cleverness, because the benefit of a predictable pattern across a whole program outweighs the benefit of a perfect name in one spot.

A practical way to build consistency is to review your own code for style before you consider it finished, looking for variations in indentation, spacing, naming, and ordering, and fixing them while the code is still fresh. Automatic tools can help with indentation and spacing, but naming and ordering consistency require human judgement, so a short self-review is still valuable. Over time, consistency becomes a habit, and you will write in your style without thinking, which leaves more attention for the ideas themselves.

func add(a: Int, b: Int) -> Int {
    return a + b
}

Section 33: Meaningful Error Messages

Error messages are the words a program uses when something goes wrong, and meaningful messages are one of the most user-friendly parts of clean code, because they turn confusion into a clear next step. A vague message like "Error" or "Invalid input" tells nobody what happened or how to fix it, while a specific message like "Score must be between 0 and 100, but got 150" tells the reader exactly what was wrong and what range was expected. The difference matters for users, who need to know how to correct their input, and for programmers, who need to know which check failed when reading a log. Writing meaningful messages costs only a few extra words, but it saves minutes of guessing every time an error occurs, and errors occur often, especially during learning and testing. Treat every error message as a small act of communication, and ask whether it would help a stranger fix the problem.

Good error messages usually contain three pieces of information: what went wrong, what value or input caused it, and what was expected instead. For example, "Cannot divide by zero" says what went wrong, while "File tasks.txt not found" names the missing file, and "Age must be 18 or older" states the expectation, and a message that combines these, such as "File tasks.txt not found in the current folder," is even better. Including the offending value is especially helpful, because it lets the reader see whether the value was a typing mistake, a wrong file, or a program bug, without needing to reproduce the problem. Avoid messages that blame the user, such as "You did it wrong," since errors are often caused by unclear instructions or program bugs, and a neutral, factual tone helps everyone focus on fixing the issue. Kindness in error messages is part of clean code, because it respects the person on the other side.

Error messages also matter inside guard else blocks and catch blocks, where they are often the only record of a failure, especially in programs without a visible interface. A guard that silently returns on bad input leaves no trace, so when the program behaves unexpectedly, there is no clue about which guard fired, while a guard that logs a specific message leaves a trail that makes debugging straightforward. In small learning programs, printing the message is enough, while in larger programs, the message might go to a log file or become an error value returned to the caller, but the principle is the same: do not fail silently. Silent failures are among the hardest bugs to find, because the program looks as if it simply did nothing, and the programmer must guess which of many possible causes is responsible. A short message eliminates that guessing.

Practise by reviewing the error messages in your own programs and rewriting any vague ones to include what went wrong, the offending value, and the expectation. Then trigger each error deliberately and read the message as if you were a stranger, asking whether you would know how to fix the problem from the message alone. If the answer is no, improve the message until it is yes, and notice how much easier debugging becomes when messages are specific.

func setAge(_ age: Int) {
    guard age >= 0 && age <= 120 else {
        print("Age must be between 0 and 120, but got \(age)")
        return
    }
    print("Age set to \(age)")
}

Section 34: When to Break a Function Apart

Knowing when to break a function apart is a judgement skill that grows with experience, and there are several reliable signals that tell you the time has come. One signal is length, since a function that scrolls beyond one screen is hard to hold in mind, and it probably contains steps that could be named and extracted. Another signal is the need for the word "and" when describing the function, since a description like "this function reads a file and cleans the data and calculates the total and prints a report" is really four jobs wearing one name. A third signal is difficulty in testing, since a function that needs many different test cases to cover its branches is probably doing too much, while smaller functions need fewer, simpler tests each. When you notice any of these signals, pause and consider a split, because the function is telling you it has outgrown its shape.

Another signal is repetition within the function, such as the same check or calculation appearing twice, which suggests that a helper could serve both places and remove the duplication. A related signal is a chunk of code that is indented deeply, since deep indentation often marks a step that could be lifted out into its own function with a clear name, flattening the original in the process. A further signal is a comment that explains a chunk, because a chunk that needs a comment to explain it may be better served by a helper whose name is the explanation, which is a point you met in the comments section. These signals often appear together, since a long function is usually also a multi-job function with repeated chunks, and recognising one signal should prompt you to look for the others. Together, they form a practical checklist for deciding when to split.

The mechanics of splitting are straightforward, and they follow the refactoring discipline from earlier in this chapter: choose a chunk, give it a name, move it into a new function with the values it needs as parameters and its result as a return value, and call it from the original place. Test after the split to confirm that behaviour is unchanged, and then repeat for the next chunk if needed, one split at a time. The new function should be placed near the original, or in the same logical group, so that readers can find it easily, and its name should be clear enough that callers can use it without reading its body. If the split requires passing many parameters, that may be a sign that the chunk belongs with some data as a method on a type, which is an idea you will explore more in later chapters, but for now, a few parameters are fine. Splitting is safe when it is done gradually and tested, and it is one of the most reliable ways to improve code.

Practise by taking a function that shows at least two of the split signals and breaking it into two or three functions, testing after each split, and then reading the result aloud to judge whether it is clearer. Save the original for comparison, and ask a simple question: would a stranger understand the split version faster?

func total(prices: [Double]) -> Double {
    return prices.reduce(0, +)
}

Section 35: Avoiding Deep Indentation

Deep indentation is the staircase shape where code drifts to the right through many levels of nesting, and it is worth treating as a warning sign, because each level adds mental load for the reader. A reader following deeply indented code must remember every enclosing condition, loop, and block to understand a single line, and that memory burden grows with each level, until the line itself becomes almost unreadable. Deep indentation also squeezes the available width for the actual code, forcing long lines to wrap or be shortened awkwardly, which further hurts readability. Most programmers find that code beyond three or four levels of indentation is hard to follow, and they treat deeper nesting as a signal to restructure, usually with guards, helpers, or early exits. The goal is not to ban nesting, since loops and choices naturally nest, but to keep nesting shallow enough that a reader can follow it without strain.

Guard is the main tool for avoiding deep indentation, because it turns requirement checks at the top of a block into early exits, removing a level of nesting for each check. A function that nested three checks to reach its main work can be flattened to a checklist plus flat work, which removes three levels at once, and the improvement is dramatic. Helper functions are the second tool, because a chunk of nested code can be extracted into a helper, where it starts at the left edge again, and the original function simply calls the helper. Loops with complex bodies benefit especially from helpers, since a loop body that contains several nested ifs can be replaced by a call to a helper that handles one item, and the helper's own nesting starts fresh. Together, guard and helpers can flatten almost any staircase into a set of shallow, readable pieces.

It is also helpful to think about indentation as a budget, where each function has a limited amount of depth it can spend before becoming confusing, and spending that budget on requirements is wasteful when guards could handle them flatly. Save your indentation budget for the genuinely nested parts of a problem, such as a loop over a list of groups where each group contains items, since that nesting reflects the data itself and cannot be flattened without hiding the structure. Requirements, validations, and edge cases, by contrast, do not reflect the data's structure, but only the conditions for proceeding, so they should not consume indentation budget. This distinction helps you decide which nesting is meaningful and which is merely accidental, and accidental nesting is the kind to remove. Meaningful nesting tells a story about the data, while accidental nesting tells a story about the programmer's order of checks, and readers care far more about the data.

Practise by finding a deeply indented piece of your own code, counting its levels, and then flattening it with guards and helpers until no line sits beyond three levels. Compare the before and after, and notice how much easier the flattened version is to read aloud, since it no longer requires a long chain of conditions to reach the main idea.

func check(score: Int) {
    guard score >= 0 else { return }
    guard score <= 100 else { return }
    print("Valid score: \(score)")
}

Section 36: Writing Code for the Next Reader

Writing code for the next reader means remembering that programs are read by people, not just run by computers, and that the next reader may be a teammate, a stranger, or yourself in six months, when the details have faded. This shift in audience changes many small decisions, because code written only for the computer can be terse and clever, while code written for a reader must be clear, explicit, and kind. A reader-friendly program uses names that explain themselves, functions that do one job, guards that state requirements up front, and comments that explain only the surprising whys, all of which you have practised in this chapter. The unifying idea is empathy, since a programmer who imagines a tired reader at midnight will write differently from one who imagines only a compiler. Empathy is not softness in programming, but a practical skill, because readable code is cheaper to maintain, test, and extend.

One way to practise reader empathy is to imagine specific readers and their questions, such as a new teammate asking "what does this function need?" or a future you asking "why did I write it this way?" A function that starts with guards answers the first question immediately, while a comment explaining a surprising choice answers the second, and both are small kindnesses that save real time. Another reader question is "where do I change this behaviour?" and code that keeps each idea in one place, with no duplication, answers it by giving a single obvious location. A further question is "is this safe to change?" and code with small, tested, single-job functions answers it by limiting the blast radius of any change. Designing for these questions, rather than merely for the computer's execution, is what turns working code into professional code, and it is a habit worth building early.

It is tempting to think that reader-friendly code takes longer to write, and in the moment it does, since choosing a good name or splitting a function takes a few extra minutes. Over the whole life of a program, however, reader-friendly code saves far more time than it costs, because programs are read many more times than they are written, and each reading is faster when the code is clear. A program that is read ten times and saves five minutes per reading has saved nearly an hour, which dwarfs the few minutes spent on clarity, and real programs are read far more than ten times. This arithmetic is why teams invest in style guides, reviews, and refactoring, since they know that clarity pays compound interest. As a learner, you can trust the same arithmetic, and invest in clarity even when nobody is watching, because your future self is a reader who will thank you.

A final habit for reader-friendly code is to review your work as if you were the next reader, before you consider it finished, by reading it fresh, checking its names, its guards, its helpers, and its messages, and fixing anything that would puzzle you. This self-review is quick, but it catches many small unclear spots, and it trains the empathy that makes the next program clearer from the start.

func greetUser(name: String?) {
    guard let name = name, !name.isEmpty else {
        print("A name is needed to greet someone")
        return
    }
    print("Hello, \(name)")
}

Section 37: Testing Clean Code Is Easier

Clean code is easier to test, and this is not a coincidence, because the same qualities that make code readable, such as small functions, single jobs, and clear inputs and outputs, also make it testable. A small function that takes values and returns a result can be tested by calling it with a few inputs and checking the outputs, without setting up a whole program or simulating user interaction. A large, tangled function that mixes reading, calculating, and printing, by contrast, needs a complicated test that covers all its jobs at once, and a failure could come from any of them, which makes the test less useful. When you write clean code, you are therefore also writing testable code, even if you do not write formal tests yet, because the structure itself invites testing. This connection is one reason professionals care so much about cleanliness, since tested code is trusted code.

Guard statements help testing in a specific way, because each guard defines a clear test case: one test for each requirement failing, and one test for all requirements passing. A function with three guards has at least four natural tests, one per guard plus the success case, and each test is simple to write and easy to understand when it fails. This is far better than a deeply nested function, where reaching a particular failure may require a combination of inputs that satisfy all outer conditions but fail an inner one, which is harder to construct and harder to explain. Clean structure turns testing into a checklist, where each requirement gets its own test, and the checklist itself documents the function's contract. When you later learn formal testing in this book, you will find that guard-based functions almost test themselves, because their structure already suggests the tests.

Single-job helpers help testing for a similar reason, since each helper can be tested in isolation, with inputs that focus on its one job, and a failing helper test points directly at the faulty job. If a helper calculates tax, a test can check tax alone, without involving file reading or printing, and if the tax test fails, the problem is in the tax logic, not elsewhere. This isolation is powerful, because it turns debugging from a search through a whole program into a check of one small piece, and it gives programmers confidence when they change code, since they can run the helper's tests and see immediately whether the change broke anything. Programs built from tested helpers feel solid, because each piece has been proven on its own, and the whole is only as strong as its pieces. Clean code and tested code grow together, each supporting the other.

Finally, remember that testing is not a separate phase that happens after clean code, but a partner to it, since writing testable code and writing tests reinforce each other. As you continue through this book, you will learn formal testing tools, and you will appreciate the clean structures you are building now, because they will make those tools easy to apply. For now, practise by writing small functions, listing their guard cases and edge cases, and trying each one by hand, noting whether the results match your predictions.

func isPassing(score: Int) -> Bool {
    return score >= 50
}
print(isPassing(75))
print(isPassing(30))

Section 38: Common guard Mistakes

Even a useful tool like guard can be misused, and learning its common mistakes will help you avoid them in your own code. One common mistake is writing a guard whose else block does not really handle the failure, such as printing a message but forgetting that the else block must exit, which the compiler will catch, or exiting with the wrong kind of exit, such as returning from a loop when you meant to continue. The compiler catches the missing exit, but it cannot catch the wrong exit, so you must choose continue, break, return, or throw deliberately, based on what the program should do next. Another common mistake is placing a guard after the code that needs it, such as checking an input after it has already been used, which defeats the purpose of guarding, since the bad data has already caused trouble. Guards belong at the top, before the code they protect, and a guard that arrives late is a sign that the function needs reordering.

A second group of mistakes involves combining conditions badly, such as writing a very long combined guard that mixes unrelated checks, or combining conditions that need different failure messages into one guard with a vague message. Long combined guards are hard to read, because the reader must parse a complex condition to understand a single requirement, and vague messages hide which condition failed, which makes debugging harder. The fix is to split unrelated or long conditions into separate guards, each with its own clear message, even if that means a few more lines, since clarity is worth more than brevity. A related mistake is ordering combined conditions wrongly, such as checking a value before unwrapping it, which the compiler will catch, but which still wastes time and confuses readers. Remember the left-to-right rule: unwrap first, then check the unwrapped value, and keep each guard focused.

A third mistake is using guard where if is more appropriate, such as guarding a value that is merely optional bonus information, where missing data should not stop the function. Forcing a guard in that case makes the function exit unnecessarily, and callers may be surprised when a function that should carry on instead returns early. The test from earlier in this chapter helps here: if missing data means "carry on without it," use if let, and if it means "cannot continue," use guard let, and applying that test honestly will prevent most misuses. A related mistake is the opposite, using if let where guard let is better, which wraps the main work in nesting and hides requirements, but that mistake is less harmful, since the code still works, only less clearly. Both directions matter, because choosing the right tool communicates intention, and intention is part of clean code.

Finally, a subtle mistake is relying on guard to validate data that should have been validated earlier, or duplicating the same guard in many functions instead of validating once at the boundary. Guard is best used at the doors of a program, where data enters, and helpers inside can then trust the data, while guarding everywhere clutters code with repeated checks.

func showAge(age: Int?) {
    guard let age = age else {
        print("Age is missing")
        return
    }
    print("Age: \(age)")
}

Section 39: Common defer Mistakes

Defer has its own common mistakes, and the most frequent is placing a defer after the code that might exit, so that the deferred cleanup is never registered on the early path that needs it. A defer written at the end of a function, after guards that can return early, will not run on those early returns, because the program leaves before reaching the defer statement, and the cleanup is skipped exactly when it matters most. The fix is the rule from earlier: acquire, then defer immediately, then guard and work, so that every later exit is covered. A related mistake is placing a defer in the wrong scope, such as at function level for a resource used only inside a loop pass, which delays cleanup until the function ends, instead of running it at the end of each pass. Scope mistakes do not always cause visible bugs, but they hold resources longer than necessary, and they confuse readers who expect cleanup near use.

A second mistake is misunderstanding defer order, by writing several defers and expecting them to run in written order, when they actually run in reverse. This causes log output that looks backwards and, worse, cleanups that happen in the wrong sequence when they depend on each other, such as closing a resource before finishing work that needs it. The fix is to remember the stack picture and to write defers in acquisition order, letting reverse execution produce the correct release order, or to combine dependent steps into a single defer block where order is explicit. If you ever find yourself writing defers in reverse order to compensate, stop, because that is a sign that the order has been misunderstood, and the code will confuse the next reader. Write acquisition order, trust reverse release, and test with prints if you are unsure.

A third mistake is putting too much work in a defer block, such as long calculations, new network calls, or error handling that belongs elsewhere, which makes exit-time behaviour complicated and hard to predict. Defer blocks should be short, safe, and focused on cleanup, since they run when the program is already leaving, and a failing or slow defer can cause new problems at the worst moment. If cleanup needs complex logic, put that logic in a helper function and call it from a short defer, so that the defer itself stays readable and the helper can be tested on its own. A related mistake is writing a defer that can throw or that depends on values that may have changed, which makes the cleanup itself fragile. Keep defer code simple, avoid throwing, and capture the values it needs at the time the defer is written, so that it does not depend on later state.

Finally, a mistake that is easy to overlook is forgetting defer entirely, by writing cleanup as ordinary code at the end of a function and then adding early returns later without updating it, which leaves some exits without cleanup. This is not a mistake in using defer, but a mistake in not using it, and it is common because functions often start simple, with one exit, and grow more exits over time.

func safeWork() {
    print("Opened")
    defer { print("Closed") }
    print("Working")
}

Section 40: guard with Enums and Pattern Matching

Guard can also check enum values and patterns, which makes it useful for functions that must handle one specific case before continuing, while other cases should exit early. An enum in Swift is a type with a fixed set of cases, such as a traffic light with red, yellow, and green, or a result that is either success or failure, and guard can test which case a value holds. The shape uses guard case, followed by a pattern, then equals, then the value, then else, then the exit, which reads as "make sure this value matches this pattern, otherwise leave." This is a powerful pattern, because it combines a check and an extraction in one statement, similar to how guard let combines a check and an unwrap, and the extracted values from the pattern are available below the guard. Pattern guards keep functions flat in the same way as other guards, by handling unwanted cases at the door.

A concrete example helps, so imagine a function that processes a successful result, where the result enum has a success case carrying a value and a failure case carrying an error message. A guard case for success extracts the value and leaves on failure, with a message explaining the failure, and the rest of the function works with the success value in flat code. Without guard case, the same function would need a switch or an if case that wraps the success handling in braces, adding nesting and hiding the main work. Guard case is therefore the flat alternative for enums, just as guard let is the flat alternative for optionals, and learning both gives you a complete toolkit for early exits. The pattern syntax may look unfamiliar at first, but it follows the same logic: check, extract, or leave.

Guard case also works with associated values, which are values carried by enum cases, such as a success case carrying a number or a failure case carrying a message, and the guard can bind those values to names for use below. For example, guard case .success(let value) = result extracts the value when the result is success, and leaves otherwise, which is concise and clear once the syntax is familiar. Beginners sometimes find the dot syntax and the let inside the pattern confusing, but it helps to read it aloud as "make sure the result is a success, and call its value by this name, otherwise leave." Practising with a small enum, such as a simple success or failure type, will make the syntax feel natural quickly, and you will then recognise it in real code, where it appears often. Pattern matching is a deep topic in Swift, and guard case is a gentle introduction to it.

Practise guard case by writing a small enum with two or three cases, one carrying a value, and a function that guards for the carrying case, extracts its value, and uses it in flat code below. Try all cases, including the ones that exit early, and notice how the function's requirements are visible at the top, just as with other guards. Then rewrite the same function with a switch, and compare the two shapes, asking which one communicates the intention better for this particular problem.

enum Result {
    case success(Int)
    case failure(String)
}
func handle(_ result: Result) {
    guard case .success(let value) = result else {
        print("Not a success")
        return
    }
    print("Value: \(value)")
}

Section 41: defer in Loops and Nested Scopes

Defer inside loops and nested scopes follows the same scope rule you learned earlier, but it deserves a closer look, because loops and nesting are where timing mistakes most often happen. Inside a loop body, a defer runs at the end of each pass, which means that a resource acquired in one pass is cleaned up before the next pass begins, and this per-pass behaviour is usually exactly what you want. For example, a loop that processes files one by one might open a file, defer its close, process it, and then move on, with the close happening automatically at the end of each pass, so no file stays open into the next pass. If the defer were instead at function level, all files would stay open until the loop finished, which could exhaust resources and confuse readers. Placing defer in the loop body, close to the acquisition, gives the correct per-pass timing, and it is the pattern to use whenever a loop acquires its own resource each time.

Nested scopes work similarly, because a defer inside an if block or a do block runs when that block ends, not when the function ends, which lets you clean up short-lived resources promptly. Imagine a function that temporarily changes a setting inside an if block, defers restoring it, and then continues with other work after the block: the restoration happens at the end of the if block, which is correct, since the temporary change was only meant for that block. If the defer had been at function level, the setting would stay changed for the rest of the function, which would be wrong and surprising. The lesson is to place defer in the smallest scope that contains the resource's full use, so that cleanup happens as soon as the resource is no longer needed. Small scopes give precise timing, while large scopes give delayed timing, and precise timing is usually better for resources.

There is a subtle case where a loop contains a guard with continue, and a defer in the same loop body, which is worth tracing carefully, because it shows how defer and guard interact in loops. When the guard fails and continues to the next pass, the loop body scope exits, so the defer runs, cleaning up anything acquired earlier in that pass, before the next pass begins. This is correct and desirable, since the failed pass should not leave a mess for the next pass, and defer guarantees that tidiness even on the skip path. Without defer, the continue path would need its own cleanup code, which is easy to forget, and the next pass might inherit a dirty state. The combination of guard with continue and defer in a loop body is therefore a robust pattern for processing lists where some items are skipped, and it is worth practising until its timing feels obvious.

Practise by writing a loop with a defer inside it and a print in each pass, and watch the defer print after each pass, not just at the end, which proves the per-pass timing. Then add a guard with continue and a resource print, and watch the defer still run on skipped passes, which proves the guard interaction.

for i in 1...3 {
    defer { print("Pass \(i) cleaned up") }
    print("Pass \(i) working")
}

Section 42: Cleaning Up a Real Example: A Login Check

Real examples show how clean code habits work together, so let us clean up a login check, which is a function that decides whether a user may enter a program. A messy version might nest several ifs: first check that a username exists, then that a password exists, then that the username is not empty, then that the password is long enough, and only then print a welcome message, with the welcome buried four levels deep. Each check is reasonable on its own, but the whole shape is a staircase, and a reader must hold all four conditions to understand the welcome, while a tester must construct inputs that pass all four to reach it. The messy version also tends to have vague failure handling, such as a single else at the bottom that says "login failed" without saying which check failed, which makes debugging harder. This is a typical messy function, and it is a perfect candidate for guard-based cleanup.

The cleaned version starts with a checklist of guards, one for each requirement, in a sensible order: first guard that the username exists, then that the password exists, then that the username is not empty, and then that the password meets the length rule, each with a specific message and a return. After the checklist, the welcome message sits at the left edge, in flat code, and a reader can see immediately what the function needs and what it does when those needs are met. The messages also improve debugging, because a failed login now reports exactly which requirement failed, such as "password too short" instead of a generic failure, which helps both users and programmers. The cleaned version is not shorter by much, but it is far clearer, because its structure matches its meaning: requirements first, work second, with each requirement named and explained. This is the guard pattern in its most natural setting, since login checks are pure requirements.

There is also a security note worth learning from this example, which is that real login systems must be careful about how much failure information they reveal, since telling an attacker exactly which part failed can help them guess credentials. In a real system, the messages shown to users might be generic, such as "invalid username or password," while detailed messages go only to logs for programmers, and this distinction matters when you build real authentication later in this book. For learning purposes, specific messages are better, because they teach you which guard fired, but you should remember that production messages balance helpfulness with safety, and the balance depends on the audience. The structure of the cleaned function stays the same either way, since guards still check each requirement, and only the wording of the messages changes. Clean structure and careful wording are separate skills, and both matter in real programs.

Try cleaning up a login check yourself, starting from a nested version and ending with a guard version, and then try the helper version, testing each with valid and invalid inputs.

func login(username: String?, password: String?) {
    guard let username = username, !username.isEmpty else {
        print("Username needed"); return
    }
    guard let password = password, password.count >= 8 else {
        print("Password must be 8 or more characters"); return
    }
    print("Welcome, \(username)")
}

Section 43: Cleaning Up a Real Example: A File Reader

A file reader is another realistic example, because it combines several clean code concerns: checking inputs, handling missing data, cleaning up resources, and reporting errors clearly. A messy file reader might open a file, nest checks for whether the file exists, whether it has content, and whether the content is valid, and then process it deep inside the nesting, with cleanup written only at the end, so that early failures skip cleanup. The cleaned version reverses this shape, by guarding inputs first, opening the resource, deferring its cleanup immediately, and then processing in flat code, with each failure reporting a specific message. Even without the full file API, which you will learn in the next chapter, the shape of the cleaned version is instructive, because it shows guard and defer working together in a realistic order. The shape is the lesson, and the file details will fill it in soon.

The order of steps in the cleaned reader deserves attention, because it follows the pattern from earlier: cheap checks first, acquisition second, defer third, and work last, with guards for any checks that depend on the resource placed after the defer. For example, the function might first guard that the file name is not empty, which needs no resource, then open the file, defer closing it, and then guard that the content is not empty, which depends on the opened file, with the defer covering that guard's exit. This ordering ensures that every exit after acquisition is cleaned up, while exits before acquisition need no cleanup, which is the tidiest possible arrangement. If the order were reversed, with acquisition before cheap checks, then cheap failures would needlessly open and close a resource, and if the defer were placed after the content guard, then that guard's exit would skip cleanup. Order is therefore not a minor detail, but a central part of correctness, and the cleaned reader makes its order explicit.

Helpers can further clean the reader, by extracting steps such as checking the file name, validating content, and processing lines into named helpers, so that the main reader function becomes a short list of steps. A reader that calls helpers for validation and processing reads like a summary of file reading, while the details live in helpers that can be tested independently, such as a helper that checks whether content is valid. This layering also makes the reader easier to extend, since a new processing step can be added as a new helper call, without disturbing the existing steps. The combination of guards for requirements, defer for cleanup, and helpers for steps is the full clean code toolkit applied to one realistic function, and it is worth studying as a model. When you write your own file code in the next chapter, try to follow this model from the start, rather than writing a messy version and cleaning it later.

Practise by sketching a file reader function in pseudocode or with prints standing in for real file operations, following the cleaned shape, and testing it with an empty name, a missing file, an empty file, and a valid file. Notice how each case produces a clear message and, where appropriate, a cleanup message, and how the valid case flows flatly to processing.

func readFile(named name: String) {
    guard !name.isEmpty else {
        print("File name is empty"); return
    }
    print("Opened \(name)")
    defer { print("Closed \(name)") }
    print("Processing \(name)")
}

Section 44: Cleaning Up a Real Example: A Score Calculator

A score calculator is a small but realistic example that shows how clean code habits help even when no files or logins are involved, because it mixes validation, calculation, and formatting in a way that easily becomes tangled. A messy calculator might take a list of scores, nest a check for emptiness, then a loop that adds scores while also checking each one for validity inside the loop, then a division, then a grading chain, all in one long function with vague names like s and t. The result is hard to test, because the calculation, validation, and grading are mixed, and a failure in one part is hard to isolate from the others. The cleaned version separates these jobs, guards the edge cases first, uses helpers for calculation and grading, and names every value clearly, so that each part can be understood and tested on its own. Even a tiny program benefits from this separation, and the benefit grows with size.

The cleaned calculator starts with guards for its requirements, such as the list not being empty and, if the problem requires it, scores being within range, each with a clear message and an early exit or fallback. After the guards, the main code calls a helper to calculate the average, which is a single-job function that takes scores and returns a number, and then calls another helper to turn the average into a grade, such as "Pass" or "Fail," or a letter grade. The main function itself becomes a short coordinator: guard, calculate, grade, and report, which reads like a summary of the whole job. This coordinator shape is easy to follow, because a reader can understand the overall flow without reading the details of averaging or grading, and can dive into a helper only when they need its specifics. The messy version, by contrast, forces readers to understand everything at once, which is tiring and error-prone.

Naming plays a large role in the cleaned calculator, because names like scores, average, and grade explain themselves, while names like s, t, and x force readers to guess. Constants also help, since a passing threshold written as passingScore = 50 is clearer than a bare 50 in a comparison, and it makes the threshold easy to change in one place. Formatting the result is another job that deserves its own helper or at least a clear step, since mixing formatting with calculation makes both harder to test, while separating them lets you test the calculation with numbers and the formatting with strings. These small separations add up, and the cleaned calculator ends up with several short, trustworthy pieces instead of one long, doubtful one. The total amount of code is similar, but its organisation is entirely different, and organisation is what readers experience.

Finally, the calculator example shows that clean code is not only for large programs, but for small ones too, since small programs grow into large ones, and habits formed on small programs carry over. A calculator written cleanly today becomes a module that can be reused tomorrow, while a calculator written messily becomes a piece that must be rewritten when it is needed again.

func averageGrade(scores: [Int]) -> String {
    guard !scores.isEmpty else { return "No scores" }
    let average = Double(scores.reduce(0, +)) / Double(scores.count)
    return average >= 50 ? "Pass" : "Fail"
}

Section 45: Refactoring Without Changing Behaviour

The golden rule of refactoring is that it must not change behaviour, because refactoring is about improving structure, not about adding features or fixing bugs, and mixing those goals makes it hard to tell what caused a change. When you refactor, the program's outputs for every input should stay exactly the same, so that you can be confident the improvement is safe, and any behaviour change should be a separate, deliberate step with its own testing. This separation is important in teams, where a refactoring change that secretly alters behaviour can break other parts of a program in ways that are hard to trace, while a pure refactoring can be reviewed quickly, since reviewers only need to check structure, not behaviour. Keeping refactoring pure is therefore a professional discipline, not just a neat idea, and it requires testing before and after to prove that nothing changed.

Proving that nothing changed requires a baseline, which is a set of inputs and their expected outputs recorded before refactoring begins, so that the same inputs can be run after and compared. For small programs, the baseline can be as simple as running the program with a few representative inputs and noting the outputs, while for larger programs, it may involve automated tests that cover the main cases and edge cases. The key is to cover not just the normal case, but also the edges and failures, since refactoring mistakes often show up on unusual inputs that the normal case does not exercise. A refactoring that passes only the normal case is not proven safe, while one that passes a broad baseline is much more trustworthy. Building a baseline before refactoring is a small investment that pays off immediately, because it turns "I think it still works" into "I checked, and it still works."

Small steps are the other half of safe refactoring, because each step changes only one aspect, such as extracting a helper or replacing a nested if with a guard, and each step is checked against the baseline before the next begins. If a step breaks the baseline, you know exactly which step caused it, and you can undo that one step without losing the earlier improvements, which keeps the work manageable. Large steps, by contrast, change many aspects at once, and a failure could come from any of them, which makes debugging slow and discourages refactoring altogether. The discipline of small steps feels slower in the moment, but it is faster overall, because it avoids long debugging sessions and builds confidence that encourages more refactoring. Professional programmers refactor in small steps precisely because they have learned how costly large, unchecked changes can be.

Practise pure refactoring by taking a working function, recording its outputs for five inputs, including edges and failures, and then refactoring it with guards and helpers, checking the outputs after each step. Notice how the discipline of recording and checking gives you confidence, and how the final function, while behaving identically, reads much better than the original. Then try a second exercise where you deliberately change behaviour during refactoring, such as changing a threshold, and notice how the baseline comparison catches it, which proves the value of the baseline.

func describe(score: Int) -> String {
    guard score >= 50 else { return "Fail" }
    return "Pass"

Section 46: Checklists for Reviewing Your Own Code

A review checklist is a short list of questions you ask yourself before considering code finished, and it is one of the most effective tools for catching problems early, because it turns vague worry into specific checks. A good checklist for this chapter might include: does every function start with guards for its requirements, does every resource have a nearby defer, are names clear and consistent, is any logic duplicated, are magic numbers named, are error messages specific, and is any code deeply nested? Running through such a list takes only a few minutes, but it catches many of the mistakes that otherwise survive until testing or review by others. Checklists are used by pilots, surgeons, and engineers for exactly this reason, because human memory is unreliable under pressure, while a written list is not. Adopting a checklist for your own code is a professional habit that will improve every program you write.

Building your own checklist is better than copying someone else's, because your checklist should reflect the mistakes you actually make, and it should grow as you learn new habits. Start with the habits from this chapter, since they are fresh, and add a question for each one, phrased so that it can be answered yes or no for a given function. For example, "does this function guard its inputs?" and "does every defer sit immediately after its acquisition?" are good checklist questions, because they are specific and checkable, while "is this code clean?" is too vague to be useful. Keep the checklist short, perhaps eight to ten questions, so that using it stays quick, and revise it occasionally, removing questions that have become automatic and adding new ones for new habits. A checklist that is too long will be skipped, while a short, relevant one will be used, so brevity is a virtue.

Using a checklist effectively means applying it at the right time, which is after the code works, but before you move on, when the code is still fresh and easy to fix. Run the program first, to confirm behaviour, and then run the checklist, fixing any issues it reveals, and running the program again after fixes, since fixes can introduce new mistakes. This order matters, because checking code that does not yet work wastes time on style when behaviour is still broken, while checking after behaviour is confirmed lets you focus on clarity. It also helps to apply the checklist function by function, rather than to a whole program at once, since small, focused reviews are more thorough than large, rushed ones. A few minutes per function is enough, and the time is repaid by fewer bugs and faster future reading.

Practise by writing your own checklist now, based on this chapter, and using it to review a function you wrote earlier, noting how many issues it catches that you had missed. Then revise the checklist based on what you found, adding questions for the issues you missed and removing any that felt irrelevant, so that the list fits your actual work. Keep the checklist somewhere visible, such as at the top of your notes or in a file you open often, so that using it becomes a habit rather than a chore.

func reviewed(score: Int) -> String {
    guard score >= 0 && score <= 100 else { return "Invalid" }
    return score >= 50 ? "Pass" : "Fail"
}

Section 47: Clean Code in a Team

Clean code matters even more in a team than it does alone, because team code is read by many people with different backgrounds, and it must survive many hands changing it over time. When you work alone, you can remember your own shortcuts and intentions, but in a team, no single person holds the whole program in mind, so the code itself must communicate clearly, through names, guards, helpers, and structure. A team member who picks up your function should be able to understand its requirements from its guards, its jobs from its helpers, and its behaviour from its messages, without needing to ask you, since asking takes time and interrupts both people. Clean code is therefore a form of teamwork, because it reduces the need for explanations and lets team members work independently with confidence. Teams that value clean code move faster, not slower, because they spend less time deciphering and more time building.

Shared conventions are the team's version of personal style, and they matter because consistency across a codebase lets any member read any part quickly, as you learned in the style section. Teams often agree on naming patterns, guard usage, file organisation, and formatting, and they write these agreements down in a style guide, so that new members can learn them and existing members can follow them. Following a team's conventions, even when they differ slightly from your personal preferences, is part of being a good teammate, because the benefit of consistency outweighs the benefit of individual taste. If you disagree with a convention, the right time to discuss it is in a team conversation, not by silently writing differently, since silent deviation creates inconsistency that harms readers. Good teams welcome discussion about conventions, but they also expect everyone to follow the agreed ones until they change.

Code review is another team practice that depends on clean code, because reviewers can only give useful feedback on code they can understand, and clean code makes review faster and more thorough. A reviewer who faces a tangled function must spend most of their time deciphering it, leaving little time to check its logic, while a reviewer who faces a clean function can focus on whether the logic is correct and complete. Clean code therefore improves the quality of reviews, which improves the quality of the program, in a virtuous cycle, while messy code degrades reviews, since reviewers may miss bugs hidden in the tangle. When you submit code for review, treat clarity as part of the work, not as polish to be added later, because reviewers are your first readers, and their experience predicts the experience of future maintainers. Welcoming review feedback about clarity, rather than defending messy code, is a sign of professional maturity.

As a learner, you can practise team habits even before joining a team, by writing code as if a teammate will read it tomorrow, by following consistent conventions, and by reviewing your own code with a checklist. You can also practise by reading others' code, such as examples in this book or open-source programs, and noticing which ones are easy to follow and why, since that observation trains your eye for clean team code.

    print("Hello, \(name)")
}

Section 48: When Clever Code Hurts

Clever code is code that uses a tricky shortcut, an obscure feature, or a dense expression to solve a problem in fewer lines, and it hurts when the trick hides meaning from readers, even if it works correctly. A clever one-liner that combines several operations, nested ternaries, or obscure operators may impress at first, but it forces every reader to decode it, and decoding takes time and invites misunderstanding, especially for beginners or tired readers. Clever code also tends to be fragile, because a small change to a dense expression can have surprising effects, while a clear, step-by-step version can be changed one step at a time with confidence. The harm of clever code is therefore not that it is wrong, but that it is expensive to read, test, and change, and those costs recur every time the code is touched. Professional programmers prefer boring, obvious code, because boring code is reliable, and reliability beats impressiveness in real programs.

A useful test for cleverness is to ask whether a reader can understand the code without a comment explaining the trick, and if the answer is no, then the trick should probably be replaced with clearer steps, even if that means more lines. For example, a chain of transformations that fits on one long line might be clearer as three separate steps with named intermediate values, where each step can be checked and understood on its own. Named intermediates cost a few lines, but they give readers places to pause, check values, and understand the flow, which is exactly what a dense chain denies them. Similarly, a nested ternary that chooses among three results might be clearer as an if-else chain or a switch, where each case is visible and labelled. Clarity is not about avoiding advanced features, but about using them in a way that readers can follow, and sometimes that means writing the obvious version instead of the clever one.

Cleverness also hurts when it relies on subtle language details that many readers do not know, such as obscure operator precedence, implicit conversions, or edge-case behaviour of a function. A reader who does not know the subtle detail will misunderstand the code, while a reader who does know it must still pause to confirm that the detail applies here, which slows reading either way. Clear code, by contrast, uses only well-known features in straightforward ways, so that readers can focus on the problem, not on the language trivia. This is especially important in teams and in teaching code, where readers have varied experience, and where a trick that is obvious to the author may be opaque to everyone else. When you are tempted by a clever trick, ask who will read the code and whether they will know the trick, and if you are unsure, choose the clearer version.

Practise spotting clever code by reviewing your own programs for dense lines, nested ternaries, and obscure shortcuts, and rewriting the worst offenders as clear, step-by-step code, then comparing the two versions for readability. Notice how the clear version is easier to read aloud, easier to test, and easier to change, even though it is longer, and notice how the clever version's brevity was an illusion, since it saved typing time but cost reading time.

Section 49: Building a Clean Code Habit

Habits are behaviours that happen automatically, without needing a decision each time, and building clean code habits is what turns the lessons of this chapter from knowledge into everyday practice. Knowledge alone is fragile, because under time pressure, programmers fall back on old habits, such as nesting, vague names, and missing guards, unless new habits have been practised enough to replace them. Building a habit requires repetition in small, manageable steps, such as choosing one habit at a time, practising it deliberately for a week, and then adding the next, rather than trying to adopt every habit at once and becoming overwhelmed. For example, you might start with guard for validation, practising it in every function until it feels natural, and then add defer for cleanup, and then naming, and so on, layering habits gradually. Small, steady practise beats intense, short-lived effort, because habits are built by frequency, not by intensity.

A practical way to build habits is to attach them to existing routines, such as reviewing your code with a checklist before you run it, or reading your function aloud after you finish it, so that the new habit rides on an old routine and is less likely to be forgotten. Another way is to set small, visible reminders, such as a note at the top of your notes listing the habit you are currently practising, which keeps it in mind while you work. It also helps to practise habits on small programs first, where the stakes are low and the feedback is quick, before applying them to larger projects, since small successes build confidence and make the habit feel rewarding. Reward matters, because habits that feel good are repeated, and clean code feels good when you return to it later and find it easy to read, which is a reward that grows over time. Notice and celebrate those moments, since they reinforce the habit.

Feedback is essential for habit building, because practising a habit incorrectly can entrench a mistake, while feedback corrects it early. Seek feedback by reviewing your own code against the checklist, by comparing your code with examples in this book, and, when possible, by asking a peer or mentor to read your code and say where they stumbled. A stumble in a reader is precise feedback about a habit that needs work, whether it is naming, guard placement, or structure, and it is far more useful than general praise. If you have no peer available, you can simulate feedback by reading your code aloud a day later, when it is less familiar, and noting where you stumble, since a day's distance reveals unclear spots that fresh writing hides. Use feedback to adjust, not to judge yourself, since every programmer's code improves through feedback, and seeking it is a strength.

Finally, remember that habits are sustained by environment as much as by willpower, so arrange your environment to support clean code, by keeping your checklist visible, by using an editor that formats consistently, and by saving examples of clean code that you admire for reference. When you meet a beautifully clear function, save it and study what makes it clear, since good examples teach habits faster than rules alone.

    print("Hello, \(name)")

Section 50: Putting It All Together

This final section brings together everything from this chapter into one picture, so that you can see guard, defer, and clean code habits as a single toolkit rather than as separate tricks. The toolkit starts with guard, which states requirements at the top of a function, flattens nesting, and gives each failure a clear exit and message, making functions readable and testable. It continues with defer, which guarantees cleanup on every exit, in reverse order, and which pairs with guard to make early exits safe, so that flat code is also reliable code. Around these two tools sit the broader habits: clear names, single-job functions, helpers, constants instead of magic numbers, comments that explain why, specific messages, shallow nesting, and regular review with a checklist. Together, these habits turn working code into code that is easy to read, easy to test, easy to change, and easy to trust, which is the definition of clean code you met at the start.

A good way to remember the toolkit is to picture a function as a small, well-run shop, where guard is the bouncer at the door checking requirements, defer is the cleaner who tidies up no matter how the day ends, helpers are the skilled staff who each do one job well, names are the labels that tell everyone what everything is, and the checklist is the closing routine that checks everything before the shop shuts. Each part has a clear role, and together they make the shop run smoothly, even when visitors arrive with strange requests or when the day ends unexpectedly. This picture may seem playful, but it captures the structure accurately, and it gives you a mental model to recall when you face a messy function. Ask which part of the shop is missing or broken, and you will usually know what to fix: a missing bouncer means missing guards, a missing cleaner means missing defer, and confusing labels mean poor names.

The next chapters will give you many chances to use this toolkit, starting with files in the next chapter, where guard will validate file names and defer will close resources, and continuing through JSON, dates, and concurrency, where clean structure will keep complex topics manageable. Each new topic will be easier if you apply the toolkit from the start, rather than writing messy code and cleaning it later, so make a conscious effort to start each new program with guards, defers, and clear names. You will find that new ideas feel less overwhelming when they are expressed in clean code, because the structure is familiar even when the topic is new, and familiarity frees attention for the new idea itself. Clean code is therefore not just a topic of this chapter, but a foundation for the rest of the book, and the time you spent here will pay off repeatedly.

Finally, carry one idea from this chapter into every program you write from now on, which is to write for the reader, not just for the computer, because that single idea motivates every other habit.

func cleanExample(name: String?) {
    defer { print("Done") }
    guard let name = name, !name.isEmpty else {
        print("Name needed")
        return
    }
    print("Hello, \(name)")
}
