Section 2: Recoverable Versus Unrecoverable Errors

A recoverable error is one the program or the user can work around, such as a missing optional file that can be replaced with defaults, while an unrecoverable error leaves no useful path forward, such as a corrupted password store that cannot be read. The distinction matters because it decides the response: recover quietly or with a small note for the first, and report honestly and stop safely for the second. Trying to recover from an unrecoverable error can invent data or hide damage, which is worse than stopping. Classifying each error case this way, at design time, prevents panicked decisions during a failure.

Section 3: The Result Type in Depth

Result is a Swift type that holds either a success value or a failure error, written as Result<Success, Failure>, where Failure must be an Error. Unlike throwing, which interrupts control flow, Result lets an error travel as an ordinary value that can be stored, returned, and examined later. This is useful when a function cannot throw, such as a completion handler, or when you want to collect several results before deciding what to do. Result does not replace do-catch; it gives you a second shape for the same idea, and choosing between them is a design decision you will practise in this chapter.

Section 5: Switching Over a Result

Switching over a Result is the most explicit way to handle it, because you write one branch for success and one for failure, and Swift checks that both are covered. In the success branch you bind the value and use it; in the failure branch you bind the error and decide the response. This completeness is valuable in important code, where silently ignoring a failure would be dangerous. A switch also reads well in code review, because the two outcomes sit side by side and a reviewer can check that both were considered.

Section 7: Converting Result to Throws with get

The get method on a Result does the reverse conversion: it returns the success value, or throws the failure error if the result is a failure. This is useful when a value-style result reaches code that prefers throwing, such as a function already written with do-catch. Calling get inside a do block is therefore a clean bridge between the two styles, and it keeps the error itself unchanged, so no information is lost in translation. Bridges like get mean you rarely have to choose one style for an entire program; you can use each where it fits and convert at the boundary.

This avoids nested switches for simple transformations and keeps the pipeline readable: each map is one clear step. Section 10: FlatMap and Chaining Results

FlatMap chains two Result-producing steps together: it runs the second step only if the first succeeded, and passes any failure straight through. Without flatMap, chaining would produce a Result inside a Result, which is awkward to use. With it, a sequence of dependent steps reads as a flat pipeline, where each step depends on the previous success. This pattern appears constantly in real code, such as reading a file and then parsing its contents, where the second step cannot run until the first has succeeded. Learning flatMap is therefore learning how to compose fallible steps cleanly.

Section 11: Fallback Values with a Default

Sometimes the kindest response to a failure is a sensible default, such as empty settings when a configuration file is missing, or zero when an optional count cannot be read. With Result, you can express this as try? result.get() ?? default, or by switching and choosing the default in the failure branch. The key discipline is to choose defaults deliberately and to document them, because a silent default can hide a real problem if it is used for a critical value. Defaults suit optional, low-stakes data; they do not suit passwords, payments, or medical records, where inventing a value would be dangerous.

Section 45: Error Handling in Libraries Versus Apps
