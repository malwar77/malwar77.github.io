Chapter 24: Generics: Writing Flexible Code

Section 1: What Generics Are

Generics let you write code that works with many types, while still keeping Swift's type safety. Instead of writing one function for integers, one for strings, and one for doubles, you write a single function with a placeholder type, and Swift fills in the real type each time the function is used. The placeholder is not a vague Any that loses information; it is a promise that the same type will be used consistently within one call. Generics therefore give you the flexibility of reused code without giving up the compiler checks that catch mistakes early.

Section 2: Why Duplicate Code Is a Problem

Duplicated code is a problem because every copy must be fixed when a bug is found, and it is easy to fix three copies and forget the fourth. Duplication also hides the idea that the copies share: a reader must compare them line by line to see that they differ only in type. Generics remove that duplication by expressing the shared logic once, with the type as a parameter. The result is less code to maintain, fewer places for bugs to hide, and a clearer statement of what the logic actually does, independent of any one type.

Section 12: Associated Types in Protocols

An associated type is a placeholder inside a protocol, written as associatedtype Element, that each conforming type fills in with a concrete type. A Container protocol, for example, might declare an associated Element, so an array of integers conforms with Element as Int, while an array of strings conforms with Element as String. Associated types let a protocol describe a family of related types without fixing them in advance, which is far more flexible than writing a separate protocol for each element type. They are the protocol counterpart of generic type parameters.

Section 49: Generics Pitfalls to Avoid

Generics pitfalls include over-genericising a function that only ever handles one type, which adds complexity without benefit; constraining too tightly, which blocks legitimate uses; and hiding type information behind Any when a parameter would preserve it. Another pitfall is writing a generic function whose body secretly assumes a concrete type, such as using arithmetic on a parameter that lacks a Numeric constraint, which the compiler will rightly reject. Avoiding these pitfalls is a matter of asking, for each generic, whether the flexibility is real, whether the constraint matches the body, and whether a simpler design would serve better.
