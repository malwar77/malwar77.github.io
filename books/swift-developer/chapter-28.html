Chapter 28: JSON and Working with Data

Section 1: What JSON Looks Like

JSON stands for JavaScript Object Notation, but despite its name, it is used by almost every programming language today, including Swift, because it is a simple, human-readable way to represent structured data as text. A JSON document is built from a small set of values: objects, which are collections of named fields inside curly braces, arrays, which are ordered lists inside square brackets, strings in double quotes, numbers, true and false, and null, which means no value. A simple example is a person object with a name field, an age field, and a list of hobbies, all written in plain text that a human can read and a program can parse. This combination of readability and structure is JSON's great strength, since it lets people inspect data by eye, while programs can still process it reliably. JSON is the common language that programs use to exchange data, and learning it opens the door to files, settings, and network data.

Objects are the heart of JSON, because they group related fields under names, much like a Swift struct groups properties, and each field is written as a name in quotes, followed by a colon, followed by a value. An object for a task might have a title field with a string, a done field with a boolean, and a priority field with a number, which together describe one task completely, in a form that is both readable and structured. Arrays hold ordered collections, such as a list of tasks, where each element is an object, so that a whole task list becomes an array of task objects, nested inside a single document. Nesting, which means putting objects inside objects and arrays inside objects, lets JSON represent complex, real-world data, such as a user with an address object and a list of orders, each with its own list of items. This nesting mirrors how data naturally fits together, which is why JSON feels intuitive once you see a few examples.

JSON has strict rules that must be followed, or a parser will reject the document, and learning those rules early prevents frustrating errors. Field names and strings must use double quotes, not single quotes, numbers must not have trailing commas, and the last item in an object or array must not be followed by a comma, which are rules that differ from some other formats and from Swift's own syntax. Commas separate items, colons separate names from values, and braces and brackets must balance, with every opening matched by a closing, or the document is invalid. These rules are simple, but they are strict, and a single missing quote or extra comma can make a whole document unreadable, which is why JSON tools and validators are useful for checking documents during development. Strictness is actually a virtue here, since it means that a valid JSON document can be parsed confidently, without guessing about its meaning.

JSON's popularity comes from its balance: it is simpler than older formats like XML, which required verbose tags, yet expressive enough for most data, from settings to API responses to saved application state.

let json = "{\"name\": \"Ana\", \"age\": 28}"
print(json)

Section 2: JSON Values: Objects, Arrays, Strings, Numbers

JSON values come in six kinds, and understanding each one, and how they combine, is the foundation for reading and writing JSON correctly. Objects, written with curly braces, hold named fields, where each name is a string and each value can be any JSON value, including another object, which allows nesting. Arrays, written with square brackets, hold ordered lists of values, where each value can be any JSON kind, and where order matters, unlike objects, where field order is not semantically important, although it is usually kept consistent for readability. Strings, written in double quotes, hold text, and they can contain escaped characters for quotes, backslashes, and control characters, following rules that parsers handle automatically. Numbers hold integers and decimals without quotes, booleans are the bare words true and false, and null is the bare word null, meaning an explicitly missing value, which is different from a missing field. Together, these six kinds can represent almost any structured data, from a simple setting to a complex document.

Strings in JSON deserve attention, because their escaping rules affect how text with special characters is stored, and because Swift strings and JSON strings, while similar, are not identical. A JSON string containing a double quote must escape it as a backslash followed by a quote, so that the parser knows the quote is data, not the end of the string, and similarly, backslashes themselves must be escaped, along with line breaks, which are written as a backslash followed by n, rather than as an actual line break inside the string. When Swift encodes a string to JSON, it handles these escapes automatically, and when it decodes, it reverses them, so you rarely need to escape by hand, but understanding the rules helps you read raw JSON files and diagnose problems when a hand-written document fails to parse. A JSON string that contains an unescaped quote or a raw line break is invalid, and a parser will reject it, which is a common error in hand-written JSON. Let Swift's tools handle escaping, and your JSON strings will always be valid.

Numbers in JSON are simpler, since they are written without quotes, as integers like 42 or decimals like 3.14, and they can also use exponent notation for very large or small values, although that is rare in everyday data. JSON does not distinguish integers from decimals at the syntax level, since both are just numbers, and the distinction is made by the receiving program, which interprets a number as an integer or a decimal depending on its Swift type. This means that a JSON number like 85 can decode into a Swift Int, while 85.5 requires a Double, and attempting to decode a decimal into an Int will fail, which is a type mismatch to watch for. Booleans are similarly straightforward, since true and false decode into Swift Bool values, while null requires special handling, since it represents the absence of a value, which in Swift usually maps to an optional that is nil. Type matching between JSON and Swift is a central theme of this chapter, since most JSON errors are type mismatches in disguise.

let values = ["name": "Ana", "age": 28, "active": true] as [String: Any]
print(values["name"] as? String ?? "")

Section 3: JSON in Swift: The Big Picture

JSON in Swift is handled primarily through a protocol called Codable, which is actually two protocols combined, Encodable for turning Swift values into JSON, and Decodable for turning JSON back into Swift values, and which lets Swift convert structured data almost automatically. The big picture is simple: you define a Swift struct that describes your data, with properties matching the JSON fields, you make that struct conform to Codable, and then you use JSONEncoder to encode it into JSON data, and JSONDecoder to decode JSON data back into the struct. This automatic conversion is powerful, because it means you work with Swift types, with their safety and clarity, while JSON handles the storage and exchange, without you needing to parse text by hand. Codable is the bridge between Swift's type system and JSON's text format, and it is one of the most useful tools in modern Swift, used for files, settings, and network data alike.

The workflow for using Codable has three stages, which are worth naming clearly, since they recur in every JSON task in this chapter. First, you model the data, by defining a struct whose properties correspond to the JSON fields, choosing Swift types that match the JSON values, such as String for JSON strings, Int for JSON integers, Bool for JSON booleans, and arrays or nested structs for JSON arrays and objects. Second, you encode or decode, by creating an encoder or decoder, and calling its encode or decode method with your struct type and your data, handling errors with do-catch, since encoding and decoding can fail for type mismatches or malformed JSON. Third, you use the result, which is either JSON data to write to a file or to send elsewhere, or a Swift value to work with in your program, using all the Swift tools you already know. Modelling, converting, and using, in that order, is the Codable workflow, and keeping the stages distinct helps you debug, since a problem in modelling looks different from a problem in converting.

Codable's automatic behaviour covers the common cases, where JSON field names match Swift property names exactly, and where types correspond straightforwardly, which is true for well-designed JSON that follows Swift naming conventions. When field names differ, such as JSON using snake_case while Swift uses camelCase, or when a JSON field needs a different Swift name, Codable provides CodingKeys, which you will learn later, to map between the two without changing your struct's design. When types differ, or when JSON has an unusual shape, Codable allows custom encoding and decoding, where you write code to handle the special case, while still using automatic behaviour for the rest, which is a flexible middle ground. This layered design, automatic by default, customisable when needed, is why Codable is so popular, since it handles simple cases simply and complex cases without forcing you to abandon it entirely. You will start with automatic cases, and add customisation only as needed.

Errors in Codable work are usually informative, since the decoder reports which field failed, what type it expected, and what it found, which helps you diagnose mismatches between your model and your JSON.

import Foundation
struct Person: Codable {
    let name: String
    let age: Int
}

Section 4: Codable in Plain Words

Codable is a Swift protocol, which means it is a promise that a type can be converted to and from an external format, and in practice, for this chapter, that format is JSON. When a struct conforms to Codable, Swift automatically generates the code to encode its properties into JSON fields and to decode JSON fields back into its properties, without you needing to write that conversion code by hand. This automatic generation works when the struct's properties are themselves Codable, which is true for Swift's basic types, such as String, Int, Double, Bool, arrays, dictionaries, and other Codable structs, which covers almost all data you will model. The word Codable itself is a combination of Encodable and Decodable, and a type can conform to just one if it only needs to encode or only needs to decode, although conforming to both is common and convenient. Think of Codable as a label that tells Swift "this type knows how to become JSON and how to come back from JSON," and Swift does the rest.

Conforming to Codable is as simple as adding it to a struct's declaration, such as struct Task: Codable, provided that all of its properties are Codable and that their names match the JSON field names, which is the automatic case. Swift then synthesises, which is a fancy word for automatically creates, the encoding and decoding code at compile time, so there is no runtime cost for hand-written conversion, and no chance of a typo in conversion code, since the compiler generates it from the struct itself. If you later add a property to the struct, the synthesised code updates automatically, which means your JSON format evolves with your model, without needing to update separate conversion code, although it also means that old JSON files may lack the new field, which is a versioning question covered later. This synthesis is a major reason Codable is preferred over hand-written parsing, since it keeps the model and the conversion in sync by construction, rather than by programmer discipline.

Codable also works with classes, although structs are preferred for data models in Swift, since they are value types with clear copying behaviour, which suits data that is loaded, modified, and saved. Enums can also be Codable, particularly simple enums without associated values, which encode as their case names, while enums with associated values require more care, as you will see later. Optionals are Codable too, with a nil optional encoding as null or being omitted, depending on the encoder's settings, and decoding as nil when the JSON field is null or missing, which makes optional properties a natural way to represent optional JSON fields. Arrays and dictionaries of Codable values are Codable themselves, which means a struct containing an array of other Codable structs is still automatically Codable, allowing nested models to work without extra code. This composability, where Codable types build from other Codable types, is what makes complex models manageable.

The limits of automatic Codable are worth knowing, since they tell you when customisation is needed, rather than causing surprise later.

import Foundation
struct Task: Codable {
    let title: String
    let done: Bool
}
let task = Task(title: "Buy milk", done: false)

Section 5: Encoding a Struct to JSON

Encoding means converting a Swift value into JSON data, which is a sequence of bytes representing the JSON text, and Swift's JSONEncoder performs this conversion with a single method call. You create an encoder, such as let encoder = JSONEncoder(), and then call try encoder.encode(value), where value is your Codable struct, and the result is Data, which you can convert to a String for inspection, write to a file, or send elsewhere. Because encoding can fail, for example if a value contains data that cannot be represented in JSON, you call it with try inside a do block, although for simple structs with basic types, encoding rarely fails, and failures usually indicate a modelling problem. The resulting JSON, by default, is compact, with no extra spaces or line breaks, which is efficient for storage and transfer, but less readable for humans, and later sections will show how to make it pretty for inspection. Encoding is the first half of the Codable workflow, and it turns Swift data into portable text.

The shape of the encoded JSON mirrors the shape of your struct, with each property becoming a field of the same name, and each property's value encoded according to its type, so that a Task struct with title and done properties becomes a JSON object with title and done fields. Nested structs become nested objects, arrays become JSON arrays, and optionals become either a value or null, depending on whether they contain a value, which means the JSON structure is a direct reflection of the Swift structure. This mirroring is intuitive, since you can predict the JSON from the struct, and you can design the struct to produce the JSON you want, which is a useful way to think about modelling: design the Swift type for clarity, and the JSON will follow. If the JSON produced does not match what another system expects, the fix is usually to adjust the struct, its property names, or its CodingKeys, rather than to manipulate the JSON text directly, since the struct is the source of truth. Model first, encode second, and the JSON will be correct by construction.

Encoding options let you customise the output, such as pretty printing, which adds line breaks and indentation for readability, sorting keys alphabetically, which makes output deterministic and easier to compare, and choosing date formats, which you will learn in the dates chapter. These options are set as properties on the encoder before encoding, such as encoder.outputFormatting = .prettyPrinted, and they affect all values encoded by that encoder, which is convenient for consistent output. For files meant for humans to read, pretty printing is a kindness, since it turns a single long line into a structured document, while for files meant only for programs, compact output is smaller and faster, so the choice depends on the file's audience. Encoder options are a small detail with a visible effect, and learning them early lets you produce JSON that suits its purpose, rather than accepting the default for every case. Options are set once per encoder, and they apply uniformly, which keeps output consistent.

import Foundation
struct Task: Codable {
    let title: String
    let done: Bool
}
let encoder = JSONEncoder()
if let data = try? encoder.encode(Task(title: "Buy milk", done: false)) {
    print(String(data: data, encoding: .utf8) ?? "")
}

Section 6: Decoding JSON into a Struct

Decoding is the reverse of encoding: it turns JSON data back into a Swift value, and Swift's JSONDecoder performs this with a single method call that takes the expected Swift type and the JSON data. You create a decoder, such as let decoder = JSONDecoder(), and then call try decoder.decode(Task.self, from: data), where Task.self names the type to decode into, and data is the JSON bytes, and the result is a Task value whose properties hold the JSON fields' values. Because decoding can fail, for type mismatches, missing fields, or malformed JSON, you call it with try inside a do block, and you handle errors with a catch that reports what went wrong, including the field and the expected type when available. Decoding is the second half of the Codable workflow, and it turns portable text back into safe, typed Swift data, which you can then use with all of Swift's tools.

The type argument to decode is crucial, because it tells the decoder what shape to expect, and the decoder will check the JSON against that shape, field by field, reporting mismatches as errors. If the JSON contains a title field with a string and a done field with a boolean, and the Task struct expects exactly those, decoding succeeds, but if the JSON's done field contains a string instead, or if the title field is missing, decoding fails, which is correct, since the JSON does not match the model. This strictness is a feature, not a flaw, because it prevents a program from working with data that does not fit its expectations, which could cause wrong behaviour later, and it forces mismatches to be fixed at the boundary, where data enters the program. A decoder that silently accepted mismatched data would be dangerous, since it would hide problems, while Swift's strict decoder surfaces them immediately. Trust the strictness, and fix mismatches at their source, whether that source is the model or the JSON.

Decoding from a String requires converting the string to Data first, using the string's utf8 encoding, since the decoder works with Data, not with String directly, which is a small step that is easy to forget. A common pattern is to read JSON from a file as Data, or to convert a JSON string literal to Data with jsonString.data(using: .utf8), and then to decode that Data, handling the optional conversion with a guard, since a string that cannot convert to UTF-8 data is itself an error. For file-based JSON, reading the file as Data directly, rather than as a String, avoids an unnecessary conversion, and it is the pattern you will use most often in this chapter, when JSON lives in files. Whether the JSON comes from a string or a file, the decoding step itself is the same, which shows how Codable separates the source of JSON from its interpretation: any Data containing valid JSON for the expected type will decode, regardless of where it came from. That separation makes Codable reusable across files, settings, and network data.

import Foundation
struct Task: Codable {
    let title: String
    let done: Bool
}
let json = "{\"title\": \"Buy milk\", \"done\": false}"
if let data = json.data(using: .utf8) {
    if let task = try? JSONDecoder().decode(Task.self, from: data) {
        print(task.title)
    }
}

Section 7: JSONEncoder and JSONDecoder

JSONEncoder and JSONDecoder are the two tools that perform Codable conversion, and understanding their roles, options, and symmetry will make JSON work feel straightforward. JSONEncoder takes a Codable value and produces Data containing JSON, while JSONDecoder takes Data containing JSON and a Codable type, and produces a value of that type, so the two are mirror images, with Data as the common middle ground. Both are created as instances, such as JSONEncoder() and JSONDecoder(), and both have properties for customising behaviour, such as output formatting for the encoder, and key and date strategies for both, which you will learn in later sections. Creating a new encoder or decoder for each operation is fine for small programs, while reusing one instance with consistent settings is better for larger programs, since it ensures uniform output and decoding across the program. The tools are simple to use, but their options give them depth, which you will explore gradually.

Encoder options include output formatting, which controls pretty printing and key sorting, and date encoding strategies, which control how Swift Date values are represented in JSON, since JSON has no native date type and dates must be encoded as strings or numbers. Decoder options mirror these, with key decoding strategies for handling naming differences, and date decoding strategies that must match the encoder's choices, or decoding will fail, since the decoder must interpret dates in the same way the encoder wrote them. Matching encoder and decoder strategies is essential when the same program both writes and reads JSON, since a mismatch, such as encoding dates as seconds but decoding them as ISO strings, will cause failures that seem mysterious until the strategies are compared. When JSON comes from another system, the decoder's strategies must match that system's choices, which may require reading its documentation or inspecting its JSON to infer the format. Strategies are a contract between writer and reader, and both sides must honour it.

Error handling differs slightly between encoding and decoding, since encoding failures are rarer and usually indicate a modelling problem, such as a value that cannot be represented, while decoding failures are common and usually indicate a mismatch between model and JSON, or malformed JSON text. For encoding, a simple do-catch that reports the error is usually sufficient, while for decoding, a more detailed catch that inspects the error can help diagnose which field failed, since Swift's DecodingError provides cases for type mismatches, missing keys, and data corruption, each with context about the coding path. Learning to read these error cases, even briefly, will make decoding failures much easier to fix, since the error often names the exact field and the expected type, which is precisely the information needed to correct the model or the JSON. Do not treat decoding errors as generic failures, but as diagnostic messages, and read them carefully before changing code. The decoder is trying to help you, in its precise, technical way.

A practical pattern for using encoders and decoders is to create helper functions, such as encodeToFile and decodeFromFile, that encapsulate the encoder or decoder settings, the file operations, and the error handling, so that callers work with Swift values and file paths, not with Data and strategies.

import Foundation
let encoder = JSONEncoder()
encoder.outputFormatting = .prettyPrinted
print("Encoder ready")

Section 8: Pretty Printed JSON

Pretty printed JSON is JSON formatted with line breaks and indentation, so that its structure is visible to human readers, as opposed to compact JSON, which puts everything on as few lines as possible. By default, JSONEncoder produces compact JSON, which is efficient for machines but hard for humans to read, especially for nested objects and long arrays, where a single line can stretch for hundreds of characters. Setting the encoder's output formatting to prettyPrinted, or combining it with sorted keys, produces JSON where each field appears on its own line, indented according to its nesting level, which makes the document's structure immediately obvious. Pretty printing is a kindness to anyone who will open the file, including yourself during debugging, since it turns an opaque line into a readable document, and it costs only a little extra file size, which is negligible for small files. For files meant for humans, pretty print; for files meant only for programs, compact is fine, and the choice should follow the audience.

Pretty printing also aids debugging, because a pretty printed file can be inspected by eye to spot missing fields, wrong values, or structural problems, while a compact file must be reformatted by a tool before it can be read comfortably. When a decoding failure occurs, opening the pretty printed JSON file and checking the field named in the error is a quick diagnostic step, since the field is easy to find in an indented document. Similarly, when comparing two JSON files, pretty printed and key-sorted output makes differences stand out, since corresponding fields appear on corresponding lines, while compact output hides differences inside long lines. These practical benefits mean that pretty printing is often used even for program-only files during development, with compact output reserved for production or for large files where size matters. Development readability is worth a few extra bytes, and pretty printing provides it with a single setting.

Sorted keys are a companion to pretty printing, since they order an object's fields alphabetically, rather than in the struct's property order, which makes output deterministic and comparable across runs and across programs. Without sorted keys, the field order follows the struct's definition, which is stable for a given struct, but which may differ from another program's order for the same data, making file comparison harder. With sorted keys, two JSON documents containing the same data will have the same field order, regardless of struct definition order, which is useful for testing, for version control, and for any workflow that compares files. Combining pretty printing with sorted keys, by setting outputFormatting to [.prettyPrinted, .sortedKeys], produces JSON that is both readable and comparable, which is an excellent default for files that humans will inspect or that will be stored in version control. Deterministic output is a small discipline with large benefits for debugging and collaboration.

There is a trade-off to pretty printing, which is file size and, for very large files, processing time, since indentation and line breaks add bytes, and formatting takes a little extra work. For files of thousands of records, the size increase is noticeable, although still modest compared with the data itself, and for files of millions of records, compact output may be preferable, with pretty printing reserved for samples or for debugging.

import Foundation
struct Task: Codable {
    let title: String
    let done: Bool
}
let encoder = JSONEncoder()
encoder.outputFormatting = [.prettyPrinted, .sortedKeys]
if let data = try? encoder.encode(Task(title: "Buy milk", done: false)) {
    print(String(data: data, encoding: .utf8) ?? "")
}

Section 9: Keys and CodingKeys

CodingKeys is Swift's mechanism for mapping between JSON field names and Swift property names when they differ, and it is implemented as a nested enum inside a Codable struct, where each case names a property and its raw value names the JSON field. For example, if JSON uses a field called "task_title" but your Swift struct uses a property called title, then a CodingKeys enum with a case title = "task_title" tells the decoder and encoder how to translate, so that the Swift code uses the clean name title while the JSON uses task_title. Without CodingKeys, Codable assumes that property names and JSON names match exactly, which works for well-designed JSON but fails for JSON from other systems that use different naming conventions. CodingKeys therefore bridges the gap between Swift naming and external naming, allowing your Swift code to follow Swift conventions while still working with JSON that follows other conventions. It is a small, explicit mapping that keeps both sides clean.

Writing a CodingKeys enum requires listing every property that needs mapping, or, if you list any, listing every property, since a custom CodingKeys replaces the automatic mapping entirely, and properties without a case will be ignored by Codable. This is a common beginner mistake: adding a CodingKeys enum for one renamed field, and forgetting to include the other properties, which then silently fail to encode or decode, producing missing data that is hard to diagnose. The fix is to include a case for every property, even those whose names match, where the case name and the raw value are the same, so that the mapping is complete and explicit. A complete CodingKeys enum is longer, but it is also self-documenting, since it shows the full translation between Swift and JSON in one place, which helps future readers understand the format. Completeness is essential for CodingKeys, and checking it should be part of your review whenever you write one.

CodingKeys also allows you to exclude properties from JSON, by omitting them from the enum, although this should be done deliberately, since an excluded property will not be encoded, and decoding will require it to have a default value or to be optional, or decoding will fail. Excluding a property is useful for computed or transient data that should not be stored, such as a property derived from other properties, or a cache that can be rebuilt, and it is a cleaner way to handle such data than custom encoding. However, excluding by accident, through an incomplete CodingKeys enum, is a bug, so the distinction between deliberate exclusion and accidental omission must be clear in your code, ideally with a comment explaining why a property is excluded. When in doubt, include every property, and exclude only with a reason, since a missing field in JSON is harder to notice than an extra field. Explicitness in CodingKeys prevents silent data loss.

Key strategies offer an alternative to CodingKeys for systematic naming differences, such as converting between snake_case JSON and camelCase Swift for all fields, without writing a mapping for each property. The encoder and decoder each have a key strategy property, and setting it to convertFromSnakeCase or convertToSnakeCase handles the common case where JSON uses snake_case and Swift uses camelCase, automatically, for every field.

import Foundation
struct Task: Codable {
    let title: String
    let done: Bool
    enum CodingKeys: String, CodingKey {
        case title = "task_title"
        case done
    }
}

Section 10: When JSON Keys Differ from Swift Names

JSON keys often differ from Swift property names, because JSON comes from other systems, other languages, or older designs, where naming conventions differ from Swift's camelCase. A common difference is snake_case, where words are separated by underscores, such as task_title, versus Swift's camelCase, taskTitle, and another is abbreviated or legacy names, such as usr for user, or short codes that made sense in an older system but are unclear in Swift. When you encounter such JSON, you have two choices: rename your Swift properties to match the JSON, which makes Swift code follow foreign conventions and look unidiomatic, or keep Swift names clean and map them with CodingKeys or key strategies, which keeps Swift code idiomatic while still working with the JSON. The second choice is almost always better, since Swift code is read by Swift programmers who expect Swift conventions, while JSON is read by parsers that do not care about naming style, as long as the mapping is correct. Clean Swift names with explicit mapping is the professional approach to foreign JSON.

Key strategies handle the systematic case, where every JSON key follows one convention and every Swift property follows another, such as snake_case to camelCase, by converting automatically during encoding and decoding. To use a strategy, you set the decoder's keyDecodingStrategy to convertFromSnakeCase, and the encoder's keyEncodingStrategy to convertToSnakeCase, and Codable will translate task_title to taskTitle and back, without any CodingKeys needed. This is elegant for consistent JSON, but it has limits, since it only handles case conversion, not arbitrary renames, such as usr to user, or task_title to title, where the words themselves differ, not just their case. For arbitrary renames, CodingKeys is required, since only an explicit mapping can express that usr means user, which no automatic strategy can guess. Strategies for patterns, CodingKeys for exceptions, is a useful rule, and combining them, with strategies as the default and CodingKeys for the odd fields, handles most real JSON.

Testing name mapping is essential, since a mapping error produces missing or wrong data that may not cause a decoding failure, but may silently produce default or nil values, depending on whether the property is optional. A round-trip test, where you encode a known Swift value, inspect the JSON keys to confirm they match the expected external format, and then decode the JSON back and confirm the Swift value matches the original, catches mapping errors in both directions. Testing with real JSON from the external system, rather than only with JSON you generated yourself, is even better, since it confirms that your mapping matches the actual external format, not just your assumption about it. When JSON comes from an API or another team, obtain a sample document, decode it with your model, and verify that every field lands in the right property, which is a quick check that prevents integration bugs. Name mapping is a contract with an external system, and contracts should be tested against real samples.

A further consideration is that JSON keys, unlike Swift property names, can contain characters that are not valid in Swift identifiers, such as spaces, hyphens, or leading digits, which cannot be used as property names at all, and which therefore require CodingKeys by necessity.

import Foundation
let decoder = JSONDecoder()
decoder.keyDecodingStrategy = .convertFromSnakeCase
print("Decoder ready for snake_case JSON")

Section 11: Optional Fields in JSON

Optional fields in JSON are fields that may or may not be present, or that may be present with a null value, and Swift represents them with optional properties, which decode as nil when the field is missing or null, and as a value when the field is present with data. This mapping is natural, since optionals in Swift mean "may be absent," which is exactly what optional JSON fields mean, and it makes Codable models tolerant of variation in JSON, where some records have extra information and others do not. For example, a task with an optional notes field will decode correctly whether the JSON includes notes, includes notes as null, or omits notes entirely, producing a task with notes set or nil accordingly, without requiring the JSON to be uniform. Optional properties are therefore the right tool for fields that are not guaranteed, and they should be used whenever a JSON field's presence is uncertain, rather than making the property required and hoping the field always appears. Hope is not a decoding strategy, but optionals are.

Required fields, by contrast, are properties that are not optional, and decoding will fail if the JSON lacks them, which is correct when the field is essential to the model's meaning, such as a task's title, without which the task is meaningless. The distinction between required and optional should reflect the data's semantics, not just convenience, since making everything optional hides real problems, while making everything required makes decoding brittle. A good model asks, for each field, whether a record without that field is still a valid record, and if the answer is yes, the property should be optional, while if the answer is no, it should be required, with decoding failure signalling corrupt or incomplete data. This semantic modelling is a design skill, since it requires understanding the data, not just its syntax, and it produces models that fail loudly on genuinely bad data while tolerating harmless variation. Model the meaning, not just the shape, and your JSON handling will be both robust and honest.

Encoding optional properties has a subtlety, since an optional that is nil can either be encoded as a JSON null field, or omitted from the JSON entirely, depending on the encoder and on how the property is defined, although Swift's default JSONEncoder encodes nil optionals as null when the property is present in the CodingKeys, which is the usual behaviour for simple models. In practice, this means that encoding a task with no notes will produce JSON with a notes field set to null, which decodes back to nil correctly, so round-tripping works, even though the JSON contains an explicit null. Some systems prefer omitted fields over null fields, and custom encoding can achieve omission, but for most Swift-to-Swift JSON, null fields are fine, since Swift decodes both forms to nil. When JSON goes to an external system, check whether it prefers null or omitted for absent values, since some systems distinguish them, as discussed with null earlier, and adjust encoding if needed. For internal JSON, either form works, as long as decoding handles both, which Swift does.

Section 12: Nested Objects in JSON

Nested objects are JSON objects inside other JSON objects, and they represent data that itself has structure, such as a user with an address, where the address is an object with street, city, and postcode fields, nested inside the user object. In Swift, nested JSON objects map to nested structs, where the outer struct has a property whose type is another Codable struct, and Codable handles the nesting automatically, encoding the inner struct as a nested object and decoding it back. For example, a User struct with a name property and an address property of type Address, where Address is a Codable struct with street and city, will encode to JSON with an address object containing street and city, and decode from such JSON without any extra code. This direct mapping between nesting in JSON and nesting in Swift is intuitive, since the Swift model mirrors the JSON structure, and it scales to multiple levels, such as a company with departments, each with employees, each with addresses. Nesting is how JSON represents real-world hierarchies, and Swift structs represent them the same way.

Designing nested models requires thinking about the data's natural hierarchy, since the nesting should reflect how the data fits together, not just how it happens to appear in a sample document. A task with a due date object, containing day, month, and year, might be better modelled as a task with a Date property, using Swift's date handling, rather than as a nested struct, depending on how the date is used, which is a modelling decision that balances JSON fidelity with Swift convenience. Similarly, an address that is always used as a whole might deserve its own struct, while an address that is only ever displayed as a single string might be better as a single String property, even if the JSON nests it, which would require custom decoding to flatten it. These decisions are part of modelling, and they should be made based on how the program uses the data, not solely on the JSON's shape, since the program's needs are what the model serves. Model for use, not just for mirroring, and your structs will be both faithful and convenient.

Decoding nested objects can fail at any level, and the error messages will indicate the coding path, which is the sequence of fields leading to the failure, such as user, then address, then postcode, which helps you locate the problem in a large document. A missing required field inside a nested object will fail the whole decode, even if the outer object is otherwise fine, which is correct, since the nested object is incomplete, but it means that nested required fields make decoding stricter, since a failure deep inside fails the whole document. To make nested decoding more tolerant, inner fields that may be missing should be optional, or inner objects themselves should be optional, so that a missing address does not fail a user decode, but instead produces a user with a nil address, which the program can handle. Tolerance should be applied at the level where variation actually occurs, which requires understanding which parts of the data are reliable and which are variable. Nested optionals are a precise tool for tolerant decoding of hierarchical data.

Section 13: Arrays of Objects

Arrays of objects are JSON arrays where each element is an object, and they represent collections of structured records, such as a list of tasks, a list of users, or a list of products, which are among the most common JSON shapes in real programs. In Swift, an array of objects maps to an array of Codable structs, such as [Task], and Codable handles the whole array automatically, encoding each struct as an object in the array, and decoding each object back into a struct, in order. Decoding an array requires that every element matches the expected struct type, since a single malformed element will fail the whole array decode, which is strict but correct, since a list with a corrupt element cannot be trusted as a whole without handling that element specially. For tolerant loading, where one bad element should not destroy the whole list, custom decoding that skips bad elements is needed, which is an advanced technique covered later, but for well-formed data, automatic array decoding is simple and reliable. Arrays of objects are the workhorse of JSON data, and mastering them is essential.

Top-level arrays, where the entire JSON document is an array rather than an object, are common for simple lists, such as a file containing only a list of tasks, with no wrapping object, and Swift decodes them by specifying the array type, such as [Task].self, as the decode target, which is straightforward once you know that the top level can be any JSON value, not just an object. Wrapped arrays, where the array is a field inside an object, such as an object with a tasks field containing the array, are also common, especially for documents that include metadata alongside the list, such as a count or a timestamp, and Swift handles them by modelling the wrapper object as a struct with an array property. Choosing between top-level and wrapped arrays is a format design decision, since a wrapper allows metadata and future extension, while a top-level array is simpler for a pure list, and the choice should reflect whether metadata is likely to be needed. For a task file that may later need a version or a last-updated field, a wrapper is a wise choice, while for a simple export, a top-level array is fine.

Ordering in arrays matters, since arrays preserve the order of their elements, unlike objects, where field order is not significant, and Swift arrays preserve JSON array order on decoding, so the first task in JSON becomes the first task in the Swift array. This order preservation means that sorting, filtering, and displaying can rely on array order, and that saving an array back to JSON preserves the program's order, which is important for lists where order means priority, chronology, or user arrangement. When a program sorts its tasks, it changes the array order, and saving will persist that new order, which is correct, since the array is the order, not just a collection. Understanding that arrays are ordered, while sets and dictionaries are not, is a fundamental distinction that affects how you model collections in JSON, and it should guide you to arrays whenever order matters, which is most of the time for user-facing lists. Order is data, and arrays preserve it.

Section 14: Decoding Dates in JSON

JSON has no native date type, which means dates must be represented as strings or numbers, and Swift's JSONDecoder must be told how to interpret those representations, through a date decoding strategy. The most common representation is an ISO8601 string, such as "2026-10-30T09:00:00Z," which is a standard, sortable, human-readable format that includes date, time, and timezone, and which Swift can decode with the iso8601 strategy. Another common representation is seconds since a reference date, as a number, which is compact and precise, but less readable, and which Swift decodes with a seconds-since-1970 strategy, while a third is a custom string format, which requires a custom formatter, as you will learn in the dates chapter. Choosing a date representation is a format decision that must be shared between writer and reader, since a decoder using the wrong strategy will fail or produce wrong dates, which is why date strategies must match on both sides. Dates in JSON are a convention, not a type, and conventions must be agreed.

The ISO8601 strategy is the recommended default for new JSON, since it is standard, readable, and widely supported by other languages and tools, which makes it ideal for data shared between systems. To use it, you set the decoder's dateDecodingStrategy to .iso8601, and the encoder's dateEncodingStrategy to .iso8601, and Swift Date values will then encode as ISO8601 strings and decode back correctly, without any custom code. This symmetry, where encoder and decoder use the same strategy, is essential, and it should be encapsulated in helpers, so that every part of a program uses the same date handling, preventing mismatches. For JSON from an external system, you must discover its date format, by inspecting a sample or reading its documentation, and set the decoder's strategy to match, rather than assuming ISO8601, since external systems vary. Date strategy mismatches are a common source of decoding failures, and they are fixed by matching strategies, not by changing the model.

Custom date formats, where dates are written as strings like "30/10/2026" or "October 30, 2026," require a DateFormatter configured with the exact format, and set as a custom date strategy, which is more work and more fragile, since the formatter must match the string exactly, including separators and order. Custom formats are sometimes necessary for compatibility with older systems or for human-friendly display, but they should be avoided for new JSON, since they are locale-dependent and error-prone, while ISO8601 is locale-independent and standard. If you must handle a custom format, test it with several dates, including edge cases like single-digit days and different months, to ensure the formatter parses them correctly, and document the format clearly, since future readers will need to know it. Dates are deceptively tricky, as the next chapter will show in depth, and JSON dates inherit that trickiness, so prefer standard formats whenever you have a choice. Standard dates save debugging time.

Decoding failures involving dates often appear as type mismatches, where the decoder expected a Date but found a string it could not parse, or a number it did not expect, and the error message will name the field and the strategy problem, which points to the fix.

Section 15: Numbers, Booleans and Null

Numbers, booleans, and null in JSON map to Swift's numeric, Bool, and optional types, but the mapping has details that cause common decoding errors, which are worth learning explicitly. JSON numbers decode into Swift Int when they are whole numbers and the property is Int, into Double when they have decimals or when the property is Double, and into other numeric types as appropriate, but a JSON decimal will fail to decode into an Int, since Swift will not silently truncate a decimal to an integer, which is a safety feature. A JSON number that is too large for its Swift type, such as a huge integer into an Int32, will also fail, which protects against overflow, although it can surprise programmers who assume all numbers are interchangeable. When JSON numbers may vary in shape, such as sometimes whole and sometimes decimal, modelling the property as Double is safer than Int, since Double accepts both, while Int accepts only whole numbers, although Double loses integer precision for very large values. Choose numeric types based on the data's actual range and shape, not just on convenience.

Booleans in JSON are the bare words true and false, without quotes, and they decode into Swift Bool directly, while a JSON string "true" with quotes will not decode into a Bool, since it is a string, not a boolean, which is a common mismatch when JSON is hand-written or comes from a system that represents booleans as strings. Similarly, a JSON number 1 will not decode into a Bool, even though some languages treat 1 as true, since Swift's decoder is strict about types, and it requires an actual JSON boolean for a Bool property. This strictness prevents subtle bugs, where a string or number is mistaken for a boolean, but it requires JSON producers to use real booleans, and it requires decoders to handle string booleans with custom decoding if they must accept them. When you encounter a boolean mismatch, check whether the JSON uses true/false, "true"/"false", or 1/0, and adjust either the JSON or the decoding to match, rather than changing the Swift type to String, which would lose boolean semantics. Booleans should stay booleans, and JSON should use real booleans for them.

Null, as discussed earlier, decodes into nil for optional properties, and it fails for required properties, since a required property cannot be nil, which is correct, since null means "no value" and a required property promises a value. A JSON field with null for a required String property is therefore a decoding error, signalling that the data is incomplete, while the same field for an optional String property decodes to nil, signalling an absent value that the program can handle. This distinction makes optionals essential for fields that may be null, and it means that modelling a field as required is a promise that the JSON will never contain null for it, which should only be made when that promise is true. For fields where null is possible, even rarely, optional is the safe model, since it handles both present values and nulls gracefully, without failing the whole decode. Null handling is a modelling decision, not just a syntax detail, and it should reflect the data's reality.

Section 16: Handling Missing or Extra Fields

JSON documents in the real world rarely match a Swift model exactly, since they may lack fields the model expects, or contain extra fields the model does not know about, and Codable handles these two cases differently, which is important to understand. Missing fields cause decoding to fail if the corresponding Swift property is required, since the decoder cannot invent a value, but they decode as nil if the property is optional, which is the tolerant behaviour for optional data. Extra fields, by contrast, are simply ignored by the decoder, which reads the fields it knows about and skips the rest, without error, which is tolerant behaviour that allows JSON to evolve by adding new fields without breaking older programs. This asymmetry, strict on missing required fields, tolerant on extra fields, is deliberate, since missing required data means the record is incomplete, while extra data means the record has more information than the program needs, which is harmless. Understanding this asymmetry helps you design models that are robust to JSON evolution.

Extra-field tolerance is a key reason Codable programs can handle JSON from evolving systems, since a server can add a new field to its responses, and older Swift programs will continue to work, simply ignoring the new field until they are updated to use it. This forward compatibility is valuable, since it means JSON producers and consumers can evolve independently, as long as producers only add fields, rather than removing or renaming existing ones, which would break consumers. For consumers, extra-field tolerance means that decoding does not need to be updated for every producer change, which reduces maintenance, although it also means that a misspelled field in JSON, which the decoder treats as extra, will be silently ignored, potentially hiding a bug. To catch such bugs, it is worth validating important JSON against its expected schema during development, even though production decoding will ignore extras, since development validation can reveal typos that tolerance would hide. Tolerance is for evolution, not for hiding mistakes, and development checks should compensate for its blindness.

Missing-field handling, as with optionals, should reflect the data's semantics, since a missing field that is essential should fail, while a missing field that is merely additional should be optional. When a model evolves by adding a new required field, old JSON files lacking that field will fail to decode, which is a versioning problem that requires a migration strategy, covered later, such as making the new field optional initially, or providing a default through custom decoding. For new models, it is wise to make fields optional unless they are truly essential, since that choice preserves compatibility with older JSON that may lack them, and it lets the program handle absence gracefully in its logic. Overly strict models, where every field is required, are brittle, since any variation in JSON, even a harmless omission, will fail the whole decode, while thoughtfully optional models are resilient. Strictness should be reserved for fields whose absence makes the record meaningless.

Section 17: Decoding Errors and What They Mean

Decoding errors are Swift's way of telling you that JSON does not match your model, and learning to read them turns failures from frustrations into precise diagnoses. The main error type is DecodingError, which has cases for type mismatches, where a field's JSON type differs from the expected Swift type, for missing keys, where a required field is absent, for value-not-found, where a field is null but the property is required, and for data corruption, where the JSON text itself is malformed. Each case carries context, including the coding path, which is the sequence of field names leading to the problem, and a description of what was expected versus what was found, which together pinpoint the exact field and the exact mismatch. Reading the full error, rather than just noting that decoding failed, is the key skill, since the error usually contains everything needed to fix the problem, whether that fix is in the model, in the JSON, or in the decoding strategy. Errors are diagnostic messages, not just failures, and they deserve careful reading.

Type mismatch errors are the most common, and they occur when JSON contains a string where Swift expects a number, a number where Swift expects a boolean, an object where Swift expects an array, or any similar type disagreement. The error will name the field, the expected type, and the actual value or type found, which lets you compare the JSON field with the Swift property and decide which is wrong. If the JSON is from an external system and cannot be changed, then the model must be adjusted, perhaps by changing the property type, by making it optional, or by adding custom decoding to handle the external type, while if the JSON is produced by your own program, then the producer's model or encoding may be wrong, and fixing it there is cleaner. Type mismatches are contracts disputes between model and JSON, and resolving them requires deciding which side should change, which is a design decision, not just a code fix. Read the error, inspect the JSON, and decide deliberately which side is correct.

Missing key errors occur when JSON lacks a required field, and they name the missing key and its coding path, which tells you exactly which field to add to the JSON or to make optional in the model. Value-not-found errors are similar, but occur when the field is present as null while the property is required, which is a subtler case, since the field exists but has no value, and the fix is either to ensure the JSON provides a value, or to make the property optional so that null decodes to nil. Data corruption errors occur when the JSON text itself is invalid, such as a missing quote, an extra comma, or a truncated file, and they often lack a specific field, since the problem is with the text as a whole, rather than with one field's type. For corruption errors, the fix is to validate the JSON text with a JSON validator, or to inspect the raw text around the reported position, since the text itself must be repaired before decoding can succeed. Different error cases point to different fixes, which is why distinguishing them matters.

Section 18: Encoding Errors

Encoding errors are less common than decoding errors, since encoding starts from Swift values that are already typed and valid, rather than from external text that may mismatch, but they still occur and deserve understanding. Encoding can fail when a value contains data that cannot be represented in JSON, such as a floating-point value that is not a number, like infinity or not-a-number, which JSON has no syntax for, and which Swift's encoder will reject rather than writing invalid JSON. Encoding can also fail when a custom encoding implementation throws, or when a value's structure is invalid, although for simple Codable structs with basic types, encoding almost always succeeds, which is why many programs use try? for encoding and treat failure as unlikely. Even when failure is unlikely, it should not be ignored silently, since a failed encoding that is treated as empty data could cause a program to save an empty file, losing data, which is worse than reporting the failure. Handle encoding errors explicitly, even if briefly, so that failures are visible.

Invalid floating-point values are the classic encoding failure, since Swift Double can hold infinity and NaN, which arise from operations like dividing by zero in floating-point arithmetic, or from calculations that overflow, and which JSON cannot represent. Swift's JSONEncoder, by default, throws an error for such values, rather than writing them as strings or nulls, which would be misleading, and the correct fix is usually to validate or clamp the values before encoding, ensuring they are finite numbers that JSON can hold. A program that encodes user-entered or calculated numbers should check for finiteness, with a guard or a validation step, before encoding, so that encoding failures are prevented at their source, rather than caught after the fact. This validation is part of modelling, since it ensures that Swift values are JSON-representable before they reach the encoder, which is a cleaner design than relying on the encoder to catch invalid values. Validate before encoding, and encoding will rarely fail.

Custom encoding errors occur when a type implements its own encode method and that method throws, for example because a value is in an invalid state for JSON, or because a required transformation fails, and these errors propagate through the encoder to the caller, where they should be caught and reported. Custom encoding is an advanced topic, covered later, but the principle is that encoding code, like any code, can fail, and its failures should be handled, not ignored, since they signal that the data cannot be represented as intended. For automatic encoding, custom errors do not arise, which is another benefit of automatic Codable, since it removes a source of failure, but for custom cases, error handling is part of the implementation. When you write custom encoding, think about what can fail, and throw informative errors, so that callers can diagnose problems, just as decoding errors inform about mismatches. Encoding errors, like decoding errors, should be informative, not silent.

A practical habit for encoding is to verify the result, especially for important data, by decoding it back and comparing it with the original, which is the round-trip test, since a successful encode that produces JSON which fails to decode indicates a modelling or strategy mismatch that needs fixing.

Section 19: Reading JSON from a File

Reading JSON from a file combines the file operations from the previous chapter with Codable decoding, in a pattern that is the standard way to load structured data in Swift programs. The steps are: locate the file, read its contents as Data, decode that Data into the expected Swift type with JSONDecoder, and handle errors at each stage, distinguishing file errors, such as a missing file, from decoding errors, such as a type mismatch. A helper function that encapsulates these steps, taking a file path and a type, and returning a decoded value or throwing an error, makes file-based JSON loading clean and reusable, since callers work with Swift values and paths, not with Data and decoders. The helper should report errors with the file path included, so that a failure can be traced to its file, and it should handle a missing file according to the data's importance, using defaults for optional data or reporting failure for essential data. File JSON loading is a boundary operation, and its error handling should be as thoughtful as its decoding.

The choice between reading a file as Data versus as a String matters for JSON, since JSONDecoder works with Data, so reading as Data directly is more efficient and avoids an extra conversion, while reading as a String is useful only when you need to inspect the text, such as for debugging or for logging the raw JSON on failure. For production loading, read as Data, decode, and on failure, optionally read as a String for diagnostic printing, which gives you both efficiency and debuggability, since the diagnostic read happens only when needed. FileManager and Data's file-reading methods provide the Data, with throwing operations that fit naturally into do-catch blocks, alongside the decoder's throwing decode, so that a single do block can cover both reading and decoding, with catch blocks distinguishing file errors from decoding errors by their types. This combined do block is concise, but it should still distinguish error kinds in its messages, since a file error and a decoding error require different fixes, and lumping them together hides that distinction. Distinguish errors, even when handling them together, so that fixes are clear.

A missing JSON file, like a missing text file, may be normal on first run, in which case the loader should return defaults or an empty collection, rather than failing, while a present but corrupt JSON file is a genuine problem, which should be reported with the path and the decoding error, so that the user can fix or replace the file. This distinction between missing and corrupt is important, since missing means "no data yet," while corrupt means "data exists but is broken," and the program's response should differ accordingly, as with text files earlier. A loader that treats corrupt JSON as missing, by returning defaults, would silently discard the user's data, which is dangerous, while a loader that treats missing JSON as corrupt, by failing on first run, would frustrate new users. Handle missing and corrupt differently, with messages that reflect the difference, and your JSON loading will be both welcoming and safe. The file's state, not just the operation's success, should guide the response.

Section 20: Writing JSON to a File

Writing JSON to a file is the counterpart to reading, and it combines Codable encoding with file writing, in a pattern that mirrors the loading pattern in reverse. The steps are: encode the Swift value to Data with JSONEncoder, configured with the desired formatting, such as pretty printing for human-readable files, and then write that Data to a file, using atomic writing for safety, and handling errors at each stage. A helper function that encapsulates encoding and writing, taking a Swift value and a file path, makes JSON saving clean and reusable, since callers work with values and paths, not with encoders and Data. The helper should report errors with the path included, and it should back up the existing file before overwriting, for important data, following the backup habit from the file chapter, so that a failed or mistaken save does not destroy the previous version. JSON saving is a boundary operation, and its safety habits should match its importance.

Formatting choices for JSON files should follow the file's audience, as with pretty printing earlier, since a settings file or a task file that users may inspect should be pretty printed and key-sorted, while a large data export meant only for programs may be compact. The encoder's output formatting should be set consistently in the helper, so that every file written by the program follows the same presentation, which aids comparison and debugging, and which prevents one part of the program from writing pretty JSON while another writes compact JSON for the same data. Consistency in formatting is a small discipline, but it makes files predictable, which users and programmers appreciate, especially when files are version-controlled, since consistent formatting produces clean diffs. A helper that centralises formatting ensures consistency, while scattered encoding code risks divergence, which is another reason to encapsulate JSON file operations. Centralise formatting, and files will be uniform.

Atomic writing for JSON files is especially important, since JSON files are often the sole store for structured data, and a half-written JSON file is not just incomplete, but invalid, since JSON parsers reject truncated documents, which means a failed non-atomic write could destroy the entire dataset, not just the latest changes. Atomic writing, by writing to a temporary file and swapping it in only on success, ensures that readers always see either the complete old JSON or the complete new JSON, never a fragment, which is essential for data integrity. Combined with backups, atomic writing gives two layers of protection: atomicity protects against failures during the write, while backups protect against logic errors in the data itself, since a backup preserves a previous good version even when the new version is logically wrong. For JSON files, both layers are worth their small costs, and they should be standard practice, not optional extras, for any data that matters. Protect JSON writes doubly, since JSON corruption loses whole datasets, not just lines.

After writing JSON, verification by reading it back and decoding it, the round-trip test, confirms that the file is valid and that the data survived the write, which is a strong check that catches encoding, formatting, and file errors in one step.

    try data.write(to: URL(fileURLWithPath: "tasks.json"), options: .atomic)
    print("Saved tasks.json")
} catch {
    print("Save failed: \(error)")
}

Section 21: JSON Strings in Code

JSON strings in code are Swift string literals that contain JSON text, and they are useful for testing, for examples, and for small, fixed JSON documents, although they require care with escaping, since JSON itself uses double quotes. A Swift string containing JSON must escape its inner double quotes, or use Swift's multi-line string literals, which allow double quotes without escaping, making JSON literals much more readable. For example, a multi-line string delimited by three double quotes can contain JSON with its own double quotes, line breaks, and indentation, exactly as it would appear in a file, which is ideal for test data and for examples in this chapter. Single-line JSON strings, with escaped quotes, are harder to read and easier to get wrong, since a missing backslash can break the Swift string or the JSON, so multi-line literals are preferred for any JSON longer than a few fields. Readable test JSON makes testing easier, since you can see the data's structure at a glance, rather than decoding a tangle of escapes.

For tests, embedded JSON is ideal, since the test data travels with the test, is visible in the test itself, and does not depend on external files that might change or go missing, which makes tests self-contained and reliable. For defaults, such as a starter task list or a sample configuration, embedded JSON can provide initial data when no file exists, which the program can then save to a file for future runs, combining the convenience of embedding with the persistence of files. Section 22: Validating JSON Before Decoding

Validating JSON before decoding means checking that the JSON text is well-formed and that it matches expectations, before attempting to decode it into a Swift model, which can catch problems early and give clearer errors. The simplest validation is to check that the JSON data can be parsed as generic JSON, using JSONSerialization, which will throw an error for malformed text, such as missing quotes or commas, without requiring a specific model, so that text errors are distinguished from model errors. A more thorough validation checks the JSON's structure against an expected schema, such as confirming that required fields exist and have the right types, although Swift's Codable decoding itself performs much of this validation, since it fails on type mismatches and missing required fields. Pre-validation is therefore most useful when you need to distinguish text errors from model errors, or when you need to validate JSON before choosing which model to decode into, such as when a document's type field determines its model. For straightforward decoding, Codable's own errors are often validation enough, and extra pre-validation may be redundant.

A practical validation step is to check that JSON data is not empty before decoding, since an empty file or an empty string will fail decoding with a data corruption error that is less clear than a specific message like "JSON file is empty." A guard for empty data, with a message naming the file, turns a cryptic decoding failure into a clear diagnosis, which is a small but valuable improvement, especially for files that may be empty due to a failed save or a truncated write. Similarly, checking that JSON data starts with the expected character, such as { for an object or [ for an array, can catch cases where a file contains the wrong kind of document, such as a text file mistaken for JSON, before decoding attempts a confusing type mismatch. These lightweight checks, empty and first-character, are cheap and informative, and they complement Codable's detailed errors by handling the gross cases clearly. Validate the obvious, decode the rest, is a pragmatic approach that improves error messages without duplicating Codable's work.

Schema validation, where JSON is checked against a formal description of its expected shape, is a more advanced technique, used when JSON comes from untrusted or external sources, and where security or correctness requires strict checking beyond Codable's type and presence checks. A schema might specify that a score must be between 0 and 100, that a name must match a pattern, or that an array must have at most ten elements, which are semantic constraints that Codable alone does not enforce, since it checks types, not ranges or patterns. For such constraints, post-decoding validation, where the decoded Swift value is checked with guards, is often simpler than schema validation, since Swift code can express ranges and patterns naturally, and it benefits from Swift's type safety. Schema validation is therefore most useful when JSON must be validated before decoding, such as for security filtering, or when the schema is shared with other languages that also validate against it, which is beyond this chapter's scope. For Swift programs, decode then validate in Swift is usually the cleaner path.

Section 23: Custom Decoding for Tricky JSON

Custom decoding means writing your own decoding code for a type, instead of relying on Codable's automatic synthesis, and it is needed when JSON has a shape that automatic decoding cannot handle, such as fields whose types vary, fields that need transformation, or structures that do not map directly to Swift properties. To implement custom decoding, you write an init(from decoder:) method in your struct, which uses a container to read fields by their CodingKeys, applying custom logic for each field, such as converting a string to a number, handling multiple possible types for one field, or deriving a property from several JSON fields. Custom decoding is more code than automatic decoding, but it is still Codable, since it uses the decoder's containers and keys, which means it benefits from Codable's error reporting and structure, while giving you full control over tricky cases. It is the escape hatch that makes Codable flexible enough for real-world JSON, where automatic mapping is not always sufficient.

A common tricky case is a field that can be either a string or a number in JSON, such as a score that is sometimes "85" and sometimes 85, depending on the producer, which automatic decoding cannot handle, since it expects one type. Custom decoding can try to decode the field as an Int first, and if that fails, try as a String and convert it to an Int, handling both forms gracefully, with a clear error if neither works. Another tricky case is a field that needs transformation, such as a date string in a custom format that requires a formatter, or a comma-separated string that should become an array, where custom decoding performs the transformation during decoding, so that the Swift model holds the transformed value, not the raw string. A third case is a property derived from multiple fields, such as a full name derived from first and last name fields, where custom decoding reads both fields and combines them, so that the Swift model has a single property for a concept that JSON splits. These cases share a pattern: JSON shape and Swift shape differ, and custom decoding bridges the gap.

Writing custom decoding requires care, since you must handle each field explicitly, including optionals, which need decodeIfPresent rather than decode, to avoid failing on missing fields, and you must call the container correctly, or decoding will fail in confusing ways. A common mistake is to forget a field in custom decoding, which silently produces a default or missing value, similar to the incomplete CodingKeys mistake, so a checklist of fields, compared against the JSON sample, is essential when writing custom decoding. Another mistake is to make custom decoding too complex, handling every possible variation, when a simpler approach, such as fixing the JSON producer or using a more tolerant model, would suffice, since complexity in decoding is hard to maintain and test. Custom decoding should be used sparingly, for genuinely tricky JSON, and it should be tested thoroughly, with samples covering each variation it handles, so that its behaviour is proven, not just assumed. Custom code deserves custom tests, and tricky JSON deserves both.

        let container = try decoder.container(keyedBy: CodingKeys.self)

    }
    enum CodingKeys: String, CodingKey { case points }

Section 24: Encoding Only Some Properties

Encoding only some properties means producing JSON that includes a subset of a struct's properties, omitting others that are internal, sensitive, or derivable, and Codable provides several ways to achieve this. The simplest way is CodingKeys, by omitting the unwanted properties from the CodingKeys enum, which excludes them from both encoding and decoding, although decoding then requires those properties to be optional or to have defaults, or it will fail, since the JSON will lack them. This approach is clean for properties that should never appear in JSON, such as a cached value or a password that should not be stored, since it makes the exclusion explicit in the mapping. However, it excludes the property from decoding as well, which may not be desired if the property should be decoded when present but not encoded when saving, which is a rarer case that requires custom encoding. For most cases, where a property should simply not be in JSON at all, CodingKeys exclusion is the right tool, with a comment explaining why the property is excluded, so that future readers do not mistake omission for an accident.

Custom encoding, through an encode(to:) method, provides finer control, allowing a type to encode a subset of its properties, or to encode them differently, while still decoding all properties automatically, or vice versa, although mixing custom encoding with automatic decoding requires care to keep the two consistent. Custom encoding is useful when the JSON representation differs from the Swift model in a way that CodingKeys cannot express, such as encoding a property under different conditions, or encoding a derived value instead of a stored one, which are advanced cases beyond simple exclusion. For simple exclusion, CodingKeys is preferable, since it is less code and less error-prone, while custom encoding should be reserved for cases where CodingKeys is insufficient, following the principle of using the simplest tool that solves the problem. Overusing custom encoding for simple cases adds maintenance burden, since custom code must be updated whenever the model changes, while CodingKeys, although also manual, is more declarative and easier to review. Choose the simplest exclusion mechanism that meets the need, and document the reason for exclusion.

A related case is encoding a struct for different audiences, such as a public JSON representation that omits private fields, and a private JSON representation that includes them, which cannot be achieved with a single CodingKeys, since CodingKeys is fixed per type. For different audiences, separate model types, such as a public view struct and a private storage struct, with conversion between them, is a cleaner design than custom encoding with conditions, since it makes each representation explicit and testable. For example, a User struct for storage might include an email and a password hash, while a UserPublic struct for sharing might include only a name and a public identifier, with a conversion method that builds the public view from the stored user. This separation follows the single-responsibility principle, since each type serves one audience, and it prevents accidental leakage of private fields through a shared encoding. Different audiences deserve different types, not conditional encoding, which is a security and clarity principle worth learning early.

Section 25: Snake Case and Key Strategies

Snake case and camel case are the two most common naming conventions in JSON and Swift respectively, and key strategies are Codable's automatic tool for translating between them, without writing CodingKeys for every property. Snake case separates words with underscores, such as task_title and due_date, and it is common in JSON from Python, Ruby, and many APIs, while camel case capitalises each new word except the first, such as taskTitle and dueDate, and it is Swift's convention for properties. The decoder's convertFromSnakeCase strategy converts snake_case JSON keys to camelCase Swift properties automatically, by splitting on underscores and capitalising, while the encoder's convertToSnakeCase strategy does the reverse, converting camelCase properties to snake_case keys. Setting these strategies on your encoder and decoder, as in an earlier section, handles the systematic case conversion for an entire document, with no per-property code, which is elegant and maintainable for consistent JSON. Strategies are the right tool when naming differs only by case convention, not by words themselves.

Key strategies have edge cases that are worth knowing, since automatic conversion is not always perfect, particularly for acronyms, initialisms, and words with numbers, where the conversion rules may produce unexpected results. For example, a JSON key like "user_id" converts to userId, which is correct, but a key like "url_value" may convert to urlValue or uRLValue depending on the strategy's handling of acronyms, which can cause a mismatch if the Swift property uses a different capitalisation. Similarly, a Swift property like "userID" may encode to "user_id" or "user_i_d" depending on how the strategy splits capitals, which is a subtlety that can break round-tripping if encoder and decoder strategies do not agree. Testing key strategies with real property names, including acronyms, is therefore essential, since the conversion is automatic but not magical, and its rules must be verified against your actual names. When a strategy produces a wrong name for a particular field, a CodingKeys entry for that field overrides the strategy, which is the combination pattern mentioned earlier: strategy for the general rule, CodingKeys for exceptions.

Choosing between key strategies and CodingKeys should follow the shape of the naming difference, as with earlier sections, but it is worth emphasising that strategies are for conventions, while CodingKeys are for mappings, and that mixing them requires understanding their interaction. When both a strategy and a CodingKeys are present, the CodingKeys raw values are used as the JSON keys, and the strategy is applied to the CodingKeys cases in some configurations, depending on Swift version and settings, which is a detail that can confuse, and which should be tested rather than assumed. A safer approach, when both are needed, is to use CodingKeys with explicit raw values for all fields, so that the mapping is fully explicit and does not depend on strategy interaction, even though it is more verbose. Explicitness beats clever interaction, especially for naming, where a wrong key causes silent data loss or decoding failure, and where debugging the interaction can waste time. When in doubt, be explicit with CodingKeys, and use strategies only when the conversion is uniform and tested.

Section 26: Working with JSON Dictionaries

JSON dictionaries, in Swift terms, are dictionaries whose keys are strings and whose values are JSON values, and they are useful when JSON has a dynamic shape, where field names are not known in advance, such as a settings object with arbitrary keys, or a response where field names are user-defined. Swift represents such JSON as [String: Any] when using JSONSerialization, or as [String: String] or other typed dictionaries when using Codable with a known value type, although Codable dictionaries require a single value type, which limits them for mixed-type JSON. JSONSerialization, the older JSON tool, works with Any, allowing mixed types, but losing type safety, since values must be cast to their expected types with optional casting, which can fail at runtime. Codable, by contrast, provides type safety for known shapes, but is less flexible for dynamic shapes, which is a trade-off between safety and flexibility that should guide your choice. For known shapes, use Codable; for dynamic shapes, use dictionaries with careful casting, or a custom Codable type that handles dynamic keys.

Dynamic keys are a specific challenge, where JSON object field names vary by record, such as a translations object where keys are language codes, like "en" and "fr," and values are translated strings, which cannot be modelled as fixed Swift properties, since the languages are not known in advance. Codable can handle dynamic keys with a custom CodingKey type that accepts any string, and with custom decoding that reads all keys from the container, building a dictionary from them, which is an advanced but powerful technique. JSONSerialization handles dynamic keys more simply, since it produces a dictionary directly, without needing custom keys, although it loses the type safety of a struct model. The choice depends on whether the dynamic data needs the safety and clarity of a model, or whether a dictionary is sufficient for its use, such as simply looking up a translation by language code. For lookup-style dynamic data, a dictionary is often the right model, since the program's use is itself dictionary-like, looking up by key, rather than accessing fixed properties. Model dynamic data as dictionaries when its use is dynamic, and as structs when its shape is fixed.

Working with [String: Any] dictionaries requires careful casting, since every value retrieved from the dictionary is of type Any, and must be cast to String, Int, Bool, array, or dictionary before it can be used, with as? providing safe optional casting that yields nil on failure. A chain of optional casts and guards, such as guard let name = dict["name"] as? String, is the safe pattern, since it handles missing keys and wrong types gracefully, with a clear failure path, rather than force casting with as!, which would crash on a mismatch. This casting code is verbose compared with Codable, which is why dictionaries are less pleasant for known shapes, but it is necessary for dynamic shapes, where Codable's fixed properties cannot express the variation. When you work with dictionaries, write helpers for common casts, such as a function that extracts a string for a key with a default, to reduce repetition and to centralise error handling, which makes dictionary code cleaner and safer. Helpers tame the verbosity of Any, and they should be used whenever dictionary code repeats.

Section 27: JSONSerialization in Plain Words

JSONSerialization is Swift's older, lower-level JSON tool, which converts between JSON data and Foundation objects, such as dictionaries, arrays, strings, and numbers, without requiring Codable models. It has two main operations: jsonObject, which parses JSON data into an object, usually a dictionary or array containing Any values, and data, which converts such an object back into JSON data, with options for pretty printing. Unlike Codable, JSONSerialization does not use Swift types or type safety, since its results are untyped Any values that must be cast, which makes it more flexible for dynamic or unknown JSON, but less safe and less clear for known shapes. It is still useful for quick inspection, for working with JSON whose shape is not known in advance, and for compatibility with older code, which is why it remains part of Foundation alongside Codable. Think of JSONSerialization as a generic JSON parser, while Codable is a typed JSON mapper, and choose based on whether you need generic parsing or typed mapping.

Using JSONSerialization to parse involves calling try JSONSerialization.jsonObject(with: data), which returns Any, and then casting that Any to the expected top-level type, such as [String: Any] for an object or [[String: Any]] for an array of objects, with as? providing safe casting. Each nested value must then be cast similarly, which produces verbose code for deep structures, but which also makes the parsing steps explicit, so that a reader can see exactly how each field is extracted and what type is expected. For shallow, dynamic JSON, this verbosity is manageable, while for deep, fixed JSON, it becomes tedious compared with Codable's automatic mapping, which is why Codable is preferred for fixed shapes. JSONSerialization also has options, such as allowing fragments, which are top-level values that are not objects or arrays, such as a bare string or number, which Codable can also handle but which JSONSerialization handles with an explicit flag. Options should be used deliberately, since allowing fragments can mask malformed documents that should be objects or arrays.

Writing JSON with JSONSerialization involves calling try JSONSerialization.data(withJSONObject: object, options:), where object is a dictionary, array, or other Foundation type containing only JSON-compatible values, and where the result is Data that can be written to a file. The input object must contain only strings, numbers, booleans, nulls, arrays, and dictionaries, since other types, such as Swift structs or dates, will cause an error, which is a limitation compared with Codable, which handles structs and dates automatically. JSONSerialization writing also requires that dictionary keys be strings, which is true for JSON, but which must be ensured when building the object from Swift data, since a dictionary with non-string keys cannot become JSON. These constraints make JSONSerialization writing best suited for data that is already in dictionary and array form, such as data parsed from JSON or built as generic collections, rather than for Swift models, which Codable handles more naturally. Use JSONSerialization for generic collections, Codable for models, is a clean division.

Validating JSON with JSONSerialization, as in an earlier section, is one of its most useful roles, since jsonObject will throw for malformed JSON, providing a quick validity check without needing a model, which is handy for inspecting unfamiliar files or for pre-validation before Codable decoding.

Section 28: Comparing Codable and JSONSerialization

Comparing Codable and JSONSerialization helps you choose the right tool for each JSON task, since they overlap in purpose but differ in safety, clarity, and flexibility, and the choice affects how your code reads and how it fails. Codable provides type safety, since decoding produces a Swift value of a known type, with compiler-checked properties, which means type errors are caught at decoding time with clear messages, and the rest of the program works with typed values, not with Any casts. JSONSerialization provides flexibility, since it handles any JSON shape without a predefined model, which is useful for dynamic, unknown, or exploratory JSON, but it sacrifices type safety, since every value is Any and must be cast, with casting failures possible at runtime. Safety versus flexibility is the core trade-off, and it should guide your choice: use Codable when the shape is known, and JSONSerialization when it is not, or when you need generic inspection without a model. Most JSON in real programs has a known shape, which is why Codable is the default choice in modern Swift.

Clarity also differs, since Codable code reads as modelling, with structs that name the data and its fields, while JSONSerialization code reads as casting, with dictionaries and as? chains that obscure the data's meaning. A Codable model documents the JSON shape in Swift code, so that a reader can understand the data by reading the struct, while a JSONSerialization parser documents the shape only implicitly, through its casting code, which is harder to read and easier to get wrong. Maintenance differs similarly, since adding a field to a Codable model means adding a property, with compiler help to update related code, while adding a field to JSONSerialization code means adding a cast in the right place, with no compiler help to find all uses. For long-lived programs, Codable's clarity and maintainability outweigh JSONSerialization's flexibility, which is why modern Swift style prefers Codable, reserving JSONSerialization for the cases where a model is impractical. Clarity is a long-term asset, and Codable provides it for JSON.

Performance differences between the two are usually negligible for small and medium JSON, since both parse efficiently, and the choice should not be driven by micro-optimisation unless measurement shows a bottleneck, which is rare for JSON handling. Codable may be slightly slower for very large documents due to its type machinery, while JSONSerialization may be slightly faster for generic parsing, but the difference is small compared with file I/O and program logic, and it should not override safety and clarity considerations. For very large JSON, the bigger performance question is whether to load the whole document at once or to stream it, which neither tool handles directly, and which requires specialised parsing beyond this chapter. Do not choose JSON tools by imagined performance, but by shape, safety, and clarity, and measure only if JSON handling becomes a proven bottleneck, which it rarely does for the programs in this book. Performance follows measurement, not assumption, as with other optimisations.

Section 32: Sending JSON Concepts

Sending JSON means transmitting JSON data from one program to another, usually over a network, although the concepts in this section apply to any transfer, including files shared between programs, and they preview the HTTP client chapter later in this book. The basic idea is that a program encodes its Swift value to JSON data, as you have learned, and then sends that data as the body of a request, with a header indicating that the content type is JSON, so that the receiver knows how to interpret it. The receiver then decodes the JSON data into its own model, which may be in a different language, but which shares the JSON field names and types, since JSON is language-neutral. This encode-send-decode cycle is the foundation of modern APIs, where programs communicate by exchanging JSON documents, rather than by sharing memory or databases, which would couple them too tightly. Sending JSON is therefore encoding plus transport, with the transport details, such as HTTP methods and URLs, covered later, while the JSON details are exactly what this chapter teaches.

Content types and headers are part of sending JSON correctly, since a receiver needs to know that the data it receives is JSON, not plain text or another format, and the standard header for this is Content-Type: application/json, which is sent alongside the JSON body. Without this header, a receiver might try to parse the body as the wrong format, or reject it, even though the JSON itself is valid, which is a common integration bug that is fixed by setting the header explicitly. Similarly, a sender that expects a JSON response should indicate that it accepts JSON, with an Accept header, although many receivers return JSON by default for API requests, regardless of the header. Headers are metadata about the data, separate from the data itself, and they are essential for correct interpretation, just as file extensions hint at a file's format, but more formally, since receivers rely on them. When you build an HTTP client later, setting JSON headers will be a required step, not an optional nicety, and learning the concept now prepares you for that chapter.

Errors when sending JSON can occur at several stages, including encoding failures, transport failures, such as a network error or a server error, and decoding failures on the response, each requiring different handling, and each deserving a clear message. Encoding failures, as discussed earlier, are rare for simple models, but they should still be handled, since a failed encode means nothing was sent, and the program should report that it could not prepare the data, rather than pretending the send succeeded. Transport failures, such as a lost connection, mean the data may or may not have arrived, which is an ambiguity that requires careful handling, such as retrying with idempotency, which is an advanced topic for the HTTP chapter. Response decoding failures mean the server returned something unexpected, such as an error page instead of JSON, and the program should report the unexpected response, rather than crashing on a decode error, since the server's error may contain useful information. Sending JSON involves a chain of steps, and each step's failure should be handled at its own level, with messages that distinguish encoding, transport, and response problems.

Section 33: Receiving JSON Concepts

Receiving JSON means accepting JSON data from another program, usually as a response to a request, and decoding it into Swift values, with validation and error handling that reflect the fact that the data comes from outside your control. The basic cycle mirrors sending: receive Data, decode it with JSONDecoder into the expected Swift type, validate the decoded value's semantics, and then use it, handling failures at each stage with messages that distinguish transport errors, decoding errors, and validation errors. Receiving is riskier than reading your own files, since external JSON may be malformed, may use unexpected types, may contain extra or missing fields, or may be maliciously crafted to exploit a program, which is why validation and tolerant decoding matter more for received JSON than for your own files. A program that trusts received JSON blindly is vulnerable, while a program that decodes strictly, validates semantically, and handles failures gracefully is robust, which is the standard for API clients. Receiving concepts in this section prepare you for the HTTP chapter, where you will implement them.

Decoding received JSON should use the same Codable models as sending, but with an awareness that the external system's JSON may evolve, adding fields that your model ignores, or changing types in ways that break decoding, which requires version handling and monitoring. Extra fields are ignored, as you learned, which gives forward compatibility for additions, but type changes, such as a field changing from a number to a string, will break decoding, and such breaking changes should be communicated by the producer, with a version bump, so that consumers can update their models. When a breaking change occurs, your program should fail clearly, with a message naming the field and the mismatch, rather than silently using wrong data, since a clear failure alerts you to update the model, while silent wrong data causes bugs downstream. Monitoring decoding failures in production, through logs, helps you detect producer changes quickly, which is a maintenance habit for API clients, since external systems change without warning. Receiving JSON is an ongoing relationship with a producer, not a one-time integration, and it requires attention to change.

Validation of received JSON goes beyond decoding, since a document that decodes correctly may still contain semantically invalid values, such as a task with an empty title, a score outside its range, or a date in the past for a future event, which the program should check with guards before using. Semantic validation uses the same guard patterns as other inputs, applied to the decoded Swift value, with clear messages or fallbacks for invalid values, depending on whether the data is critical or can be filtered. For a list of received tasks, invalid items might be skipped with a warning, preserving the good items, while for a single received configuration, an invalid value might cause the whole response to be rejected, since a partial configuration is worse than none. The choice between skipping and rejecting depends on the data's use, and it should be made deliberately, with the same reasoning as for file loading, since received JSON and file JSON share the boundary-validation principle. Validate semantics, not just syntax, for received data, since syntax alone does not guarantee usefulness.

Section 34: Versioning JSON Data

Versioning JSON data means managing how JSON formats change over time, so that old files and old programs continue to work, or fail clearly, when new fields are added, fields are renamed, or structures change. The simplest versioning strategy is additive change, where new fields are added as optionals, so that old JSON without them still decodes, with nil interpreted as a default, while new JSON with them decodes fully, which is backward compatible, since old data works with new code. Additive changes are the safest kind, and they should be the default for evolving JSON, since they preserve compatibility without migration, although they require the program to handle nils for new fields sensibly, which is a design responsibility. Renaming a field, by contrast, is a breaking change, since old JSON uses the old name and new code expects the new name, unless custom decoding handles both names, by trying the new name first and falling back to the old, which is a migration technique for renames. Breaking changes should be avoided when possible, and when necessary, they should be accompanied by a version field and a migration path, so that old data can be upgraded, rather than simply failing.

A version field in JSON, such as a top-level "version" number, makes versioning explicit, since a program can read the version first, decide whether it understands that version, and either decode with the appropriate model, migrate the data to the current version, or report that the version is unsupported. Without a version field, a program must infer the version from the data's shape, such as the presence of a new field, which is fragile and ambiguous, while a version field gives a clear, unambiguous signal. For files that will evolve, adding a version field from the start, even when the version is 1, is wise, since it costs one field and saves future ambiguity, and it allows the program to handle future versions deliberately, rather than guessing. Version fields are a small investment with large future benefits, and they should be part of any JSON format that is expected to persist and evolve, such as task files, settings, or notes, which will all gain features over time. Version early, and evolution will be manageable.

Migration means converting old JSON data to the current format, either on load, by decoding with an old model and converting to the new model, or in a separate migration step that rewrites files, and it is the process that makes breaking changes survivable. On-load migration is convenient, since it happens transparently when old data is read, and it can be implemented with custom decoding that handles both old and new shapes, or with a two-stage decode that tries the new model first and falls back to the old model and conversion. Separate migration, where a program upgrades all files at once, is more explicit and testable, but it requires a migration tool and a backup, since rewriting files is destructive if the migration has a bug. Whichever approach is chosen, migration should be tested with real old files, backed up before migration, and reversible where possible, since a failed migration that destroys old data is worse than a failed decode that leaves it intact.

Section 35: Migrating Old JSON Formats

Migrating old JSON formats means transforming data stored in an older format into the current format, so that it can be used by the current program, without losing information or requiring users to re-enter data. Migration is needed when a breaking change occurs, such as a field rename, a type change, or a structural change, where old JSON cannot decode directly into the new model, and it is implemented as a conversion step that reads old data, transforms it, and produces new data. The conversion can happen on load, transparently, where the loader tries the new model, falls back to the old model on failure, converts the old value to the new value, and optionally saves the migrated data back, so that future loads use the new format directly. Or it can happen as a separate migration run, where a tool loads all old files, converts them, backs up the originals, and writes the new versions, which is more explicit and easier to test in bulk. Both approaches share the same core: understand the old shape, understand the new shape, write a conversion that preserves meaning, and test it with real old data.

A concrete migration example helps, so consider a task format that originally stored a task as a plain string title, and now stores it as an object with title and done fields, which is a structural change from a string to an object. A migration for this change would read the old JSON, which is an array of strings, convert each string into a Task object with that title and done set to false, since old tasks have no done information, and then save the new array of objects, which the current program can decode. This migration preserves the titles, which are the essential data, while supplying a sensible default for the new done field, which is the best that can be done when old data lacks new information. Defaults for new fields during migration should be chosen carefully, since they affect all migrated records, and they should be documented, so that users understand why their old tasks appear as not done, for example, rather than wondering whether data was lost. Migration defaults are design decisions, and they should be sensible and explained.

Testing migration is critical, since a migration bug can corrupt data for all users at once, which is far worse than a bug affecting a single operation, and migration tests should cover representative old files, edge cases, and the full range of old shapes, including files with missing fields, extra fields, and unusual values. A migration test loads an old sample, runs the migration, and compares the result with an expected new sample, field by field, confirming that titles, dates, and other essential data survived, and that new fields received their intended defaults. Migration tests should also verify that the migrated data round-trips, by decoding it with the new model and re-encoding it, confirming that the migration produced valid current-format data, not just data that looks plausible. Backups before migration are essential, since a failed migration can be undone by restoring the backup, while a migration without a backup risks permanent loss, which is unacceptable for user data.

Section 36: Pretty Versus Compact JSON

Pretty versus compact JSON is a presentation choice that affects readability, file size, and diff-friendliness, but not the data itself, since both forms decode to identical Swift values, which means the choice can be made per file, per audience, or even changed later without affecting correctness. Pretty JSON, with indentation and line breaks, is readable by humans, easy to inspect during debugging, and produces clean diffs in version control, since each field appears on its own line, so a change to one field affects only its line. Compact JSON, with no unnecessary whitespace, is smaller, faster to transmit, and more efficient to store, which matters for large files, for network transfer, and for systems where bandwidth or storage is limited. The trade-off is therefore between human readability and machine efficiency, and the right choice depends on the file's size, its audience, and its lifecycle, with small, human-inspected files favouring pretty, and large, machine-only files favouring compact. Presentation follows purpose, and purpose varies by file.

For files that users or programmers will open, such as settings, task lists, and notes, pretty JSON is almost always the right choice, since the size cost is negligible for small files, while the readability benefit is large, especially when debugging or hand-editing. A pretty settings file invites inspection and editing, while a compact settings file discourages both, since it appears as an intimidating wall of text, even though its data is identical. For files that are generated and consumed only by programs, such as large data exports or cached API responses, compact JSON is reasonable, since no human will read them, and the size savings, while modest per file, can add up across many files or frequent transfers. A hybrid approach is also common, where files are stored compactly but pretty printed on demand, using a formatting tool, for inspection, which gives efficiency in storage and readability when needed, without committing to one form permanently. Since the data is identical, the choice is reversible, and it should be revisited as a file's audience changes, rather than fixed forever.

Diff-friendliness is a specific benefit of pretty JSON that deserves emphasis, since version-controlled JSON files, such as settings or data checked into a repository, are compared line by line, and pretty printing with sorted keys ensures that a small data change produces a small, readable diff. Compact JSON, by contrast, puts an entire object on one line, so a change to one field appears as a change to the whole line, which is hard to review and can hide the actual change among unchanged fields. Sorted keys further improve diffs, since they ensure that field order is consistent across runs, so that a diff reflects data changes, not ordering changes, which is important when struct property order or dictionary order might otherwise vary. For any JSON file that will be version-controlled, pretty printed and sorted is the strongly recommended default, since it makes collaboration and review practical, which is a benefit that outweighs its small size cost. Version control rewards readable, deterministic output, and pretty sorted JSON provides both.

Section 37: Sorting and Filtering Decoded Data

Sorting and filtering decoded data means working with Swift values after decoding, using collection operations to order, select, and transform them, which is where JSON data becomes useful in a program, beyond merely being loaded. Once JSON is decoded into an array of structs, such as tasks, you can sort it by any property, such as title alphabetically, due date chronologically, or priority numerically, using Swift's sorted methods with closures that compare the relevant properties. Filtering means keeping only elements that meet a condition, such as tasks that are not done, notes with a particular tag, or scores above a threshold, using the filter method, which you learned in the collections chapters. These operations are performed on Swift values, not on JSON text, which is the benefit of decoding: the program works with typed, structured data, where sorting and filtering are natural collection operations, rather than with raw text, where they would require string manipulation. Decode first, then process with Swift collections, is the rhythm for JSON data work.

Sorting decoded data requires attention to the property's type, since sorting strings, numbers, and dates each have their own comparison rules, and Swift's comparison operators handle them correctly when the properties are properly typed. Sorting tasks by title uses string comparison, which is case-sensitive by default, so lowercasing for comparison, as with file sorting earlier, produces user-expected order, while sorting by date uses Date comparison, which is chronological, and sorting by a numeric priority uses numeric comparison, which is intuitive. Sorting by multiple criteria, such as done status first and then title, can be achieved with a closure that compares the primary criterion, and falls back to the secondary when the primary ties, which is a common pattern for user-facing lists that need a sensible order. These sorting operations are the same as for any Swift collection, which shows how Codable integrates with the rest of Swift: decoding gives you collections, and collections give you sorting, filtering, and mapping, without any JSON-specific tools. JSON is just a way to get collections into and out of a program.

Filtering decoded data is similarly a collection operation, where a closure tests each element and keeps those that pass, producing a new array that can be displayed, counted, or saved, depending on the program's needs. Filtering tasks by done status, notes by tag, or users by age range are all examples of the same pattern, with different closures, and the filtered result is itself a collection that can be further sorted or processed, chaining operations in a readable pipeline. Combining filtering and sorting, such as filtering to open tasks and then sorting by due date, produces a focused, ordered view of the data, which is how real applications present lists to users, with views that are derived from the full data rather than stored separately. Derived views should not be saved back as if they were the full data, since they are subsets, and saving a filtered view over the full file would lose the filtered-out items, which is a data-loss mistake to avoid. Filter for display, save the full data, is a rule that prevents view-related data loss, and it applies to JSON lists as to other collections.

Section 38: Searching Decoded Data

Searching decoded data means finding Swift values that match a query, such as tasks containing a word, notes with a tag, or users with a name, using collection operations on decoded arrays, which is more powerful and type-safe than searching raw JSON text. The simplest search filters an array by a condition, such as a title containing a search term, using contains on lowercased strings for case-insensitive matching, which is the same pattern as file searching, but applied to typed properties rather than to lines. More advanced search might check multiple properties, such as title or body, combining conditions with logical or, so that a note matches if either its title or its body contains the term, which is a natural extension of the filter pattern. Searching decoded data benefits from types, since a search can target specific fields, such as only titles, or only tags, without false matches from other fields, which raw text search cannot distinguish. Typed search is precise search, and precision is valuable when data has many fields.

Search results should be presented with context, such as the matching task's title, its done status, and its position in the list, so that users can identify and act on matches, rather than just seeing a count or a bare title. For a task search, printing each match with its number, title, and status lets the user complete or delete it by number, which connects search to other operations, while for a notes search, printing the title and a snippet of the body helps the user recognise the right note among several matches. If no matches are found, a clear message, such as "No tasks matching 'milk' found," is better than silence, since it distinguishes a failed search from a failed load, which is the reporting habit from earlier chapters applied to search. Search is a user-facing operation, and its output should be helpful, not just correct, with context, counts, and clear no-match messages, so that users trust and understand the results. Helpful search output turns a filter into a tool.

Searching large decoded collections raises performance considerations, since a linear filter that checks every element is fine for hundreds of items, but may become slow for millions, where indexing or a database would be more appropriate, which is a scaling question that connects to the storage choices in the file chapter. For the programs in this book, with small collections, linear search is sufficient, and it should be used without premature optimisation, since its simplicity outweighs its theoretical slowness for small data. If search becomes slow in a real program, the first step is to measure, to confirm that search is indeed the bottleneck, rather than loading or display, and then to consider indexing, such as building a dictionary from tags to notes, which trades memory for speed. Indexing is an optimisation that should follow measurement, not precede it, and for most JSON programs, it will never be needed, since collections are small and linear search is fast enough. Search simply for small data, optimise only when measured slowness demands it, is a pragmatic rule.

Section 40: Common JSON Mistakes

Common JSON mistakes fall into patterns that are worth learning to recognise, since they cause most JSON failures, and since recognising them in advance prevents debugging time. One pattern is type mismatches, such as a JSON string where Swift expects a number, or a JSON number where Swift expects a boolean, which cause decoding failures that name the field and the expected type, and which are fixed by correcting the model or the JSON, depending on which is wrong. Another pattern is missing required fields, where JSON lacks a field that the model requires, which causes a missing-key error, and which is fixed by adding the field to the JSON or by making the property optional, depending on whether the field is truly essential. A third pattern is malformed JSON text, such as a missing quote, an extra comma, or single quotes instead of double quotes, which causes a data corruption error, and which is fixed by validating the text with a JSON validator and correcting its syntax. These three patterns, type, missing, and malformed, cover most decoding failures, and checking for them in order, text first, then presence, then types, is an efficient debugging sequence.

A fourth pattern is naming mismatches, where JSON keys differ from Swift property names, without a CodingKeys mapping or a key strategy to translate them, which causes fields to decode as missing or as nil, since the decoder looks for the Swift name and does not find it, while the JSON name is ignored as an extra field. This pattern is insidious, because it may not cause a decoding failure if the property is optional, but instead produces nil values that look like missing data, which is harder to diagnose than a clear error. The fix is to compare JSON keys with Swift property names, add CodingKeys or strategies for differences, and test with real JSON samples, which reveals naming mismatches quickly. A fifth pattern is date strategy mismatches, where the encoder and decoder use different date formats, or where the decoder's strategy does not match the external JSON's format, which causes date fields to fail decoding, and which is fixed by matching strategies on both sides, as covered in the dates section. Naming and date mismatches are mapping errors, and they are fixed by aligning the mapping, not by changing the data's meaning.

A sixth pattern is incomplete CodingKeys, where a custom CodingKeys enum lists only renamed fields and omits others, causing those properties to be silently excluded from encoding and decoding, which produces missing data that is hard to trace, since no error is thrown. The fix is to list every property in CodingKeys, as emphasised earlier, and to review CodingKeys completeness whenever a model changes, since adding a property without adding its CodingKeys case will silently exclude it. A seventh pattern is force unwrapping decoded optionals, or assuming that decoded data is valid without validation, which causes crashes or wrong behaviour when JSON contains unexpected values, such as an empty title or an out-of-range score, that decoding alone does not catch. The fix is to validate decoded values with guards, as with other inputs, before using them, since decoding checks types, not semantics, and semantic validation is the program's responsibility.

Section 41: Debugging JSON Problems

Debugging JSON problems is a systematic process that starts with isolating the failure's stage, whether it is in the JSON text, in the decoding model, in the file operation, or in the program's use of decoded data, since each stage has different causes and fixes. The first step is to reproduce the failure reliably, with a specific JSON sample and a specific model, so that you can test fixes against the same case, rather than chasing intermittent failures that may have multiple causes. The second step is to read the error message fully, including the coding path and the expected versus found types, since the error often names the exact field and mismatch, which narrows the search dramatically. The third step is to inspect the JSON text for that field, by printing it or by opening the file, and to compare its actual value and type with the model's expectation, which usually reveals the mismatch, whether it is a type, a name, a missing field, or a malformed syntax. This reproduce, read, inspect sequence is the core debugging workflow for JSON, and it resolves most problems without guesswork.

Isolating the problem further can involve simplifying the model or the JSON, such as decoding into a model with only the failing field, or decoding the JSON as a generic dictionary to see its actual structure without model constraints, which helps when the error is confusing or when the JSON's shape is unclear. Simplifying is a powerful technique, since it removes variables and lets you test one hypothesis at a time, such as whether a particular field's type is the problem, or whether the whole document is malformed. For malformed JSON, a JSON validator tool, which checks syntax and highlights the exact position of an error, is invaluable, since it finds missing quotes, extra commas, and unbalanced braces faster than eye inspection, especially for large documents. For model mismatches, comparing the model's properties, including CodingKeys and optionals, against the JSON's fields, in a checklist, catches naming and presence errors that the error message may only hint at. Isolation and simplification turn large JSON problems into small, testable ones, which is the essence of debugging.

Logging and printing are also valuable for JSON debugging, since printing the raw JSON data as a string, before decoding, shows exactly what the decoder sees, which may differ from what you assumed, such as when a file contains unexpected content or when a network response returns an error page instead of JSON. Printing the decoded value after successful decoding, or printing the error on failure, gives you a record of what happened, which helps when a failure occurs only in certain conditions, such as with specific user data or at specific times. During development, verbose JSON logging is helpful, while in production, logging should be more selective, to avoid leaking sensitive data or filling logs with large documents, but the principle remains: make JSON visible during debugging, so that assumptions can be checked against reality. A program that hides its JSON, by decoding without ever printing it on failure, is harder to debug than one that reveals it, so add diagnostic prints during development, and remove or guard them for production. Visibility is a debugging asset, and JSON visibility is no exception.

Section 42: Testing JSON Encoding and Decoding

Testing JSON encoding and decoding means verifying that Swift values convert to JSON and back correctly, that files persist and load correctly, and that edge cases, such as missing fields, extra fields, and invalid types, are handled as intended. The core test is the round-trip test, where a known Swift value is encoded to JSON, decoded back, and compared with the original, field by field, confirming that no data is lost or altered in the cycle. Round-trip tests should cover representative values, including empty strings, zero numbers, false booleans, empty arrays, and nil optionals, since these edge values are where encoding and decoding most often diverge, such as an empty array becoming nil, or a false boolean becoming missing. A round-trip test that passes for typical values but fails for edge values reveals a modelling problem, such as an optional that should be required, or a default that should be explicit, which is valuable information. Test round-trips with edges, not just with typical values, to prove that encoding is faithful for all data, not just for convenient data.

File-based JSON tests extend round-trip tests to persistence, by encoding a value, writing it to a temporary file, reading it back, decoding it, and comparing, which proves that the file operations and the JSON operations work together, as in the file testing section. These tests should use temporary folders for isolation, so that they do not interfere with real data or with each other, and they should clean up afterwards, with defer or cleanup steps, so that test files do not accumulate. Edge file tests, for missing files, empty files, and corrupt files, prove that loading handles real-world file states gracefully, with defaults for missing, clear errors for corrupt, and no crashes for empty, which are the robustness standards for JSON persistence. Testing files and JSON together is essential, since a program that encodes correctly but writes incorrectly, or that reads correctly but decodes incorrectly, will fail in production, even though its JSON logic alone is correct. Integration tests, covering the full cycle, catch failures that unit tests for encoding alone would miss.

Error-case tests are equally important, since they prove that decoding failures are handled, not just that successes work, and they should include JSON with a wrong type for a field, JSON missing a required field, JSON with an extra field, and malformed JSON text, each with an expected outcome, such as failure, nil, or ignored extra. For each error case, the test should confirm not only that decoding fails or succeeds as expected, but also that the program's response is sensible, such as a clear message, a default, or a skipped record, rather than a crash or silent data loss. Error tests document the model's contract with JSON, showing which variations are tolerated and which are rejected, which is valuable documentation for future maintainers, who can read the tests to understand the contract. Writing error tests also forces you to decide, for each variation, what the correct response should be, which is a design decision that is easy to postpone but important to make deliberately. Test errors deliberately, and your JSON handling will be robust by design, not by accident.

Section 43: JSON and Security Basics

JSON and security intersect in several ways, since JSON data often comes from external, untrusted sources, may contain sensitive information, and may be used in ways that expose programs to attacks if handled carelessly. One risk is injection, where JSON data containing malicious content, such as a string with code or markup, is used in a context where it is interpreted as code, such as being inserted into a web page or a database query without escaping, which can lead to attacks that the JSON format itself does not prevent. The defence is to treat JSON data as data, not as code, and to escape it appropriately for each context where it is used, such as HTML-escaping when displaying in a web page, or parameterising when using in a database, which are context-specific defences that go beyond JSON parsing. JSON parsing itself does not execute code, which is a safety advantage over formats that do, but the data it produces must still be handled safely in its destination context, which is a general security principle: parse safely, use safely, with escaping for each destination. Data is not code, and it should never be treated as code without explicit, safe handling.

Another risk is denial of service through malicious JSON, such as a document with deeply nested arrays or objects that exhaust memory or stack during parsing, or with enormous arrays that consume resources, which can crash or slow a program that parses untrusted JSON without limits. The defence is to limit the size and depth of JSON accepted from untrusted sources, rejecting documents that exceed sensible limits, and to parse with tools that handle nesting safely, although Swift's JSONDecoder does not provide built-in depth limits, so application-level checks, such as file size limits before parsing, are needed for untrusted input. For JSON from trusted files, such as your own program's data, these limits are less critical, but for JSON from networks or users, they are essential, since an attacker can craft a small JSON document that expands into a huge structure, a technique known as a billion-laughs attack in other formats, which JSON is less vulnerable to but not immune from. Limit untrusted JSON by size and depth, and your programs will resist resource-exhaustion attacks.

Sensitive data in JSON is a third risk, since JSON files and transmissions may contain passwords, tokens, personal information, or private notes, which should be protected by encryption in transit and at rest, by access controls on files, and by exclusion from logs and error messages, which might otherwise leak them. A program should never log full JSON documents containing sensitive fields, since logs are often shared or stored insecurely, and it should never include sensitive fields in error messages, which might be displayed to users or stored in crash reports. When JSON contains sensitive data, it should be handled with the same care as other sensitive data, which later security chapters will cover in depth, including secure storage, encryption, and access control, but the basic habit starts here: ask whether each JSON field is sensitive, and if so, protect it, exclude it from logs, and store it securely. Sensitive JSON deserves secure handling, and that handling should be designed, not improvised, when a leak occurs.

Section 44: When JSON Is the Wrong Tool

JSON is a versatile format, but it is not the right tool for every data problem, and recognising its limits helps you choose better tools when they fit, rather than forcing JSON into roles it handles poorly. One limit is binary data, such as images, audio, or video, which JSON cannot represent directly, since it is a text format, and which must be encoded as text, such as base64, if stored in JSON, which inflates size by about a third and makes the JSON unreadable, which is inefficient and awkward. For binary data, dedicated binary formats or file references, where JSON stores a file path and the binary data lives in a separate file, are better, since they keep JSON text-readable and binary data efficient. Another limit is very large data, such as millions of records, where JSON's text overhead and whole-document parsing become slow and memory-heavy, compared with binary formats or databases that support streaming and indexing. For large data, JSON is a poor choice, and a database or a binary format should be considered, even though JSON is simpler for small data.

Another limit is data that requires comments, since JSON has no comment syntax, and any attempt to add comments, such as extra fields for notes, pollutes the data model and may confuse parsers, while formats designed for configuration, such as YAML or TOML, support comments natively, which is valuable for human-edited configuration. For user-edited settings where comments would help explain options, a comment-supporting format may be better than JSON, even though JSON is more standard for program-managed settings, which is a trade-off between human-friendliness and standardisation. A further limit is data with complex relationships, such as a graph with many-to-many links, where JSON's tree structure, with nesting and duplication, becomes awkward, since a tree cannot represent a graph without duplicating nodes or using references, which JSON does not natively support. For graph data, a database with relationships, or a format with references, is more natural, since it models links directly, rather than through duplication or indirection. JSON's tree shape suits hierarchical data, but not graph data, and recognising that distinction guides storage choice.

JSON also lacks some features that other formats provide, such as dates, which it represents only by convention, as you learned, and precise numeric types, since it does not distinguish integers from decimals syntactically, which can cause precision loss for very large integers when parsed by languages that use floating-point numbers for all JSON numbers. For financial data requiring exact decimal precision, or for scientific data requiring exact large integers, JSON's number handling may be insufficient, and a format with explicit decimal or big-integer types, or a database with precise numeric columns, may be needed. These limits do not make JSON bad, since it handles most everyday data well, but they mean that JSON should not be assumed to handle every data type perfectly, and that critical data should be checked for precision and representation issues before choosing JSON. Know JSON's limits, and you will choose it when it fits, and choose alternatives when it does not, which is the mark of thoughtful data design.

Section 45: Building a Small JSON Store Type

A small JSON store type is a struct or class that encapsulates JSON file persistence for a particular data kind, with methods to load, save, add, and list, hiding Codable, file, and error details behind a clean interface, similar to the file helper from the previous chapter but for JSON data. For example, a TaskStore type might hold a file path, a JSONEncoder and decoder configured consistently, and methods such as load() returning [Task], save(_ tasks:) writing them, and add(_ task:) loading, appending, and saving, so that callers work with tasks, not with JSON data or file paths. This encapsulation centralises JSON decisions, such as pretty printing, date strategies, and key strategies, so that every operation uses the same settings, preventing mismatches that arise from scattered encoder and decoder creation. It also centralises error handling, with a consistent policy for missing files, corrupt files, and write failures, so that callers receive predictable results, rather than needing to handle JSON and file errors in every place. A JSON store is a reusable component that turns JSON persistence into a service, which is a maturing design pattern.

Designing a JSON store starts with choosing its interface: what data it manages, what file it uses, what its methods do, and how it reports errors, whether by throwing, by returning optionals, or by printing messages, with the choice documented so that callers know what to expect. A good store has a small interface, with methods named for data operations, such as load, save, add, and remove, and with parameters that are data values, not JSON details, so that callers do not need to know about encoders, decoders, or file formats. Internally, the store should handle its own edge cases, such as a missing file on load returning an empty list, a corrupt file reporting an error with the path, and a save using atomic writing and backups for important data, so that callers receive sensible results without handling file minutiae. The store's file path should be configurable, with a sensible default, so that tests can point it at temporary files, which is essential for isolated testing, as with file helpers earlier. Configurable paths and clean interfaces make stores testable and reusable, which are the qualities that justify encapsulation.

Testing a JSON store involves round-trip tests, where data is saved and loaded back and compared, operation tests, where adding, removing, and listing are verified through the store, and edge tests, where missing, empty, and corrupt files are handled, all in temporary folders for isolation. These tests prove that the store's load, save, and operations work together, and they protect all callers of the store, since a tested store is a trusted component, while an untested store's bugs would affect every caller. A store's tests also document its contract, showing what happens on missing files, what format it writes, and how it handles errors, which helps future maintainers understand and extend it. When a store is used by several parts of a program, its tests are more valuable than tests scattered across callers, since they cover the shared persistence logic once, rather than repeatedly, which is efficient and thorough. Test stores thoroughly, in isolation, and programs built on them will be more reliable.

Section 46: Encoding Enums in JSON

Encoding enums in JSON depends on the enum's kind, since simple enums without associated values encode as their case names, which are strings, while enums with associated values require more complex encoding, which Codable handles with custom logic or with specific strategies. A simple enum, such as a Priority enum with cases low, medium, and high, conforms to Codable automatically, and encodes as the strings "low," "medium," and "high," which are readable and stable, as long as case names do not change, since renaming a case would change the JSON and break old files, which is a versioning consideration. Decoding such an enum from JSON requires an exact match with a case name, and an unknown string, such as a new case added by another system, will cause decoding to fail, which is strict but correct, since an unknown case cannot be mapped to a known value, although tolerant handling, such as defaulting to a known case, requires custom decoding. Simple enums are a natural fit for JSON string fields, such as status, priority, or category, where the set of values is fixed and meaningful, and they should be used for such fields, rather than raw strings, since enums provide type safety that strings do not.

Enums with associated values, such as a Result enum with success carrying a value and failure carrying a message, encode in a more complex way, since Codable must represent both the case and its associated data, which it does by encoding as an object with a case key and associated values, although the exact format depends on the Codable implementation and may be verbose or surprising. For such enums, custom encoding and decoding are often needed to produce a clean, stable JSON format, such as a single object with a type field and a value field, which is more readable and more compatible with other languages than Codable's default associated-value encoding. Designing a JSON format for associated-value enums should be done deliberately, with a documented shape, such as {"type": "success", "value": 42}, and with custom Codable code to implement it, rather than relying on defaults that may change or that other systems cannot parse. Associated-value enums are powerful in Swift, but their JSON representation requires design, not just automatic conformance, which is an advanced topic that rewards careful thought.

Raw-value enums, where each case has an associated raw value, such as an Int or String, encode as their raw values, which is convenient when JSON uses codes, such as 1, 2, 3 for priorities, or short strings, such as "L," "M," "H," which differ from Swift case names. A raw-value enum conforming to Codable will encode as its raw value, and decode from that raw value, failing on unknown raw values, which is similar to simple enums but with a layer of indirection between case names and JSON values. Raw values are useful for compatibility with external systems that use codes, since they allow Swift case names to be clear, such as low, medium, high, while JSON uses the external codes, with the mapping handled automatically by Codable. When raw values change, old JSON breaks, just as with case names, so raw values should be treated as part of the JSON contract, stable and documented, not changed casually.

Section 47: Decoding with Default Values

Decoding with default values means supplying a sensible value when JSON lacks a field, or when a field's value is invalid, so that decoding succeeds with a complete Swift value, rather than failing or producing nil, which is useful for evolving data and for tolerant loading. Swift's automatic Codable decoding does not supply defaults for missing required fields, since it fails on missing keys, which means defaults require either optional properties, where nil is interpreted as a default in program logic, or custom decoding, where decodeIfPresent is used with a nil-coalescing default, such as try container.decodeIfPresent(Int.self, forKey: .priority) ?? 0. Custom decoding with defaults is explicit and flexible, since it allows any default, including computed defaults, and it makes the default visible in the decoding code, which helps future readers understand what happens when a field is missing. For evolving models, where a new field should default for old data, custom decoding with defaults is a clean migration strategy, since it upgrades old data on load, without requiring a separate migration step. Defaults in decoding are a form of migration, applied transparently at the boundary.

Choosing defaults requires care, since a default should be a sensible, safe value that does not misrepresent the data, such as 0 for a count, false for a flag, or an empty array for a list, while a default that hides a real problem, such as a default title of "Untitled" for a missing title, might mask corrupt data that should instead fail loudly. The distinction is between fields where absence is harmless and a default is meaningful, such as a new optional feature flag defaulting to off, and fields where absence indicates corruption, such as a missing title for a task, which should fail rather than default, since a task without a title is not a valid task. Defaults should be chosen per field, based on its semantics, not applied uniformly, and they should be documented, so that readers know what value old data will receive and why that value is safe. A default that is safe for one field may be dangerous for another, so default selection is a modelling decision, not a mechanical one, and it should be made thoughtfully for each field.

An alternative to custom decoding defaults is to use optional properties and to interpret nil as a default in program logic, such as treating a nil priority as medium priority when displaying, which keeps decoding automatic and moves default logic into the program, where it can be tested as ordinary logic. This approach is simpler to implement, since it requires no custom decoding, but it spreads default handling through the program, since every use of the property must handle nil, which can become tedious if the property is used in many places. A computed property that returns the optional's value or a default, such as var effectivePriority: Int { priority ? 1 }, centralises the default in one place, giving the benefits of both approaches: automatic decoding with optionals, and a single default definition. Computed defaults are a neat pattern for evolving models, since they keep the stored model faithful to the JSON, with nil for missing, while providing a convenient, defaulted view for program logic.

Section 48: Handling Large JSON Files

Handling large JSON files poses challenges similar to large text files, since loading an entire JSON document into memory at once can use a great deal of memory, slow parsing, and fail for very large documents, such as datasets with millions of records. Swift's JSONDecoder loads and parses the whole document, producing a complete Swift value, which is simple and correct for small and medium files, but which becomes impractical for large files, where a streaming parser that processes records one by one, without holding the whole document, is needed. Streaming JSON parsing is an advanced technique, requiring a parser that reads JSON incrementally, yielding each object as it is completed, which Swift's standard library does not provide directly, although third-party libraries and manual parsing with JSONSerialization on chunks can approximate it. For most programs in this book, with files of hundreds or thousands of records, whole-document decoding is fine, and streaming should be considered only when measurement shows that whole-document handling is genuinely too slow or memory-heavy. Measure before streaming, since streaming adds complexity that is only justified by large data.

A practical middle ground for moderately large JSON files is to split the data into multiple smaller files, such as one file per category, per date, or per thousand records, so that each file can be decoded whole, while the program loads only the files it needs, rather than the entire dataset at once. Splitting by a natural partition, such as tasks by month, or products by category, is a design decision that should reflect how the data is used, since loading by partition matches access patterns, such as viewing one month's tasks, which needs only that month's file. This partitioning also improves other operations, such as backups, since only changed partitions need backing up, and it makes files more manageable for humans, who can inspect one partition without opening a huge document. Partitioning is a simple, effective scaling strategy that uses whole-document decoding, without streaming complexity, and it should be considered before streaming, since it solves many large-file problems with ordinary tools. Partition data by use, and large files become collections of small files, each easy to handle.

Another middle ground is to store large JSON data in a more efficient form, such as a compact JSON file without pretty printing, which reduces size, or a binary format, or a database, which supports indexing and querying without loading everything, as discussed with storage choices earlier. Compact JSON saves space, but does not solve memory issues during parsing, since the whole document is still parsed, while a database solves both size and memory, by loading only queried records, at the cost of added complexity. The choice between partitioning, compacting, and moving to a database depends on the data's size, its access patterns, and its growth, and it should be made based on measurement and on how the data is actually used, not on speculation about future size. For data that grows unpredictably, a database is often the right long-term choice, since it scales beyond what files can handle comfortably, while for data that is large but stable and accessed whole, partitioned JSON may suffice. Scale storage with data, and measure to decide when to move.

Section 49: JSON in Real Apps: A Tour

JSON in real apps appears in many places, from settings and saved data to network APIs and configuration, and a tour of these uses shows how the skills in this chapter combine into real-world patterns. In mobile apps, JSON often stores user preferences, cached API responses, and offline data, where Codable models define the data, JSON files provide persistence, and encoders and decoders with consistent strategies handle conversion, often encapsulated in stores, as in the store section. In server programs, JSON is the language of APIs, where requests and responses are JSON documents, decoded into models, validated, processed, and encoded back into responses, with error handling for malformed or unexpected JSON at each boundary. In command-line tools, JSON is used for configuration, for data exchange with other tools, and for output that other programs can parse, since JSON output is machine-readable in a way that human-formatted text is not. Across these contexts, the same Codable workflow applies, with models, encoding, decoding, validation, and error handling, adapted to each context's transport and storage. JSON is a universal data language, and its patterns repeat across app types.

A tour of real JSON also reveals common conventions, such as APIs that wrap responses in an object with data and error fields, rather than returning raw arrays, so that errors can be communicated alongside data, and such as pagination, where large lists are returned in pages, with metadata about total count and next page, rather than all at once, which handles large data efficiently. These conventions are not part of JSON itself, but patterns built on top of it, and recognising them helps you integrate with real APIs, since you will need to model wrapper objects and pagination metadata, not just the core data. Another convention is versioned APIs, where the URL or a header indicates the API version, so that breaking changes can be introduced without breaking existing clients, which mirrors the versioning discipline for JSON files, applied to network data. Real JSON work involves these conventions, which are learned through experience with real systems, and which build on the foundational skills in this chapter, rather than replacing them. Foundations first, conventions next, is the learning path for real JSON work.

Real apps also teach lessons about JSON robustness, since real JSON from external systems is messier than textbook examples, with inconsistent types, missing fields, extra fields, and evolving shapes, all of which require the tolerant decoding, custom handling, and validation strategies covered in this chapter. A real app that crashes on unexpected JSON will fail in production, while one that handles variation gracefully, with defaults, skips, or clear errors, will survive, which is why robustness is emphasised throughout this chapter, not just correctness for ideal data. Monitoring real JSON failures, through logs that record decoding errors with samples, helps teams detect producer changes quickly and update models before users are affected, which is a maintenance practice for production JSON integrations. Robustness is not a one-time design choice, but an ongoing practice of monitoring, testing with real samples, and updating models as producers evolve, which is the reality of working with external data. Real JSON is messy, and robust handling is what makes programs survive it.
