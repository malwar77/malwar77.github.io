Chapter 27: Files: Reading and Writing Text

Section 1: Why Programs Need Files

Programs that only work while they are running forget everything when they close, which means a task list, a score, or a note would vanish the moment the program ends. Files solve this problem by giving a program a place to store information on disk, where it stays until the program, or another program, reads it again. This kind of storage is called persistence, which is simply the ability of data to outlive the program that created it, and it is what turns a toy program into a useful tool. When you save a document, keep a high score, or store settings, you are using files, even if the program hides the details from you. Learning to read and write files therefore opens the door to programs that remember, which are the programs people actually rely on every day.

Files also let programs share information with each other, since one program can write a file and another can read it, even if they were written by different people at different times. A text file containing a list of names, for example, can be created by a Swift program, edited by hand in a text editor, and then read back by the same program, which makes text files wonderfully flexible. They are also easy to inspect, because you can open them and see exactly what the program stored, which makes debugging much simpler than with hidden or binary formats. When something goes wrong, you can look at the file and see whether the data was saved incorrectly, read incorrectly, or never saved at all, which narrows the search quickly. This visibility is a major reason this chapter starts with plain text files, before moving to structured formats like JSON in the next chapter.

Working with files introduces a new kind of problem that in-memory programs rarely face, which is that the outside world can fail in ways that variables never do. A file might not exist, a folder might be missing, a disk might be full, or the program might not have permission to write, and each of these failures must be handled politely, rather than crashing. Swift helps here with its error handling, which you learned earlier, since file operations are throwing operations that you call with try inside a do block, catching errors and responding sensibly. You will also use guard to check file names and inputs before attempting work, and defer where cleanup is needed, so this chapter builds directly on the clean code habits of the previous chapter. Files are not a separate world, but the same Swift you know, applied to storage that lives outside the program.

By the end of this chapter, you will be able to write text to a file, read it back, add to it, list folders, and store simple records such as tasks and notes, all using only Swift's standard library. You will also learn the habits that keep file code safe, such as checking before reading, handling missing files gracefully, backing up before overwriting, and writing in a way that does not lose data if something fails halfway. These habits matter, because file mistakes can lose a user's data, which is far worse than a wrong answer on screen, so file code deserves extra care.

Section 2: Paths in Plain Words

A path is simply the address of a file or folder on a computer, written as a sequence of folder names separated by slashes, ending with the file's name. On a Mac or Linux system, a path like /Users/kel/notes/tasks.txt means: start at the root of the disk, go into the Users folder, then into kel, then into notes, and there you will find tasks.txt, and each slash marks one step deeper into the folder tree. Paths can be absolute, meaning they start at the root and describe the full journey, or relative, meaning they start from wherever the program is currently working and describe only the remaining steps. Relative paths are shorter and more portable, since they do not mention a particular user's name, but they depend on the program's current folder, which can change, so absolute paths are more explicit. Understanding both kinds, and knowing which one you are using, prevents a large class of "file not found" confusion.

Folders, which are also called directories, organise files the way drawers organise a desk, and a path is the route through those drawers to one particular item. The current working directory is the folder a program starts in, and relative paths are measured from there, so a relative path of notes/tasks.txt means the notes folder inside the current folder. Swift programs run from different working folders depending on how they are launched, which is why a relative path that works in a playground may fail in a command-line tool, and why it is worth checking where your program is working when a file cannot be found. You can ask Swift for the current directory and for the user's home directory, and those helpers give you reliable starting points for building paths. Building paths from known starting points, rather than guessing, is a habit that saves much frustration.

Swift represents paths as ordinary strings in simple code, and as URL values in more careful code, because a URL can distinguish a file path from a web address and can handle special characters safely. For this chapter, you will mostly see paths as strings when the idea is simple, and as file URLs when the code needs to be precise, and you will learn to move between the two. A file URL looks like a path with file:// at the front, and Swift provides ways to build one from a path string or from a folder plus a file name. Joining a folder and a file name correctly matters, because simply gluing strings together can produce double slashes or missing slashes, while URL helpers handle the joining properly. When you write file code, prefer the helpers for joining, and treat raw string gluing as a shortcut that can bite later.

A common beginner mistake is to assume that a file is in the same folder as the code, when in fact the program's working folder is elsewhere, such as a build folder or a system folder. The fix is to print the path your program is actually using, and to check whether that file exists, before assuming the path is wrong in some mysterious way.

let fileName = "tasks.txt"
let folder = "notes"
let path = folder + "/" + fileName
print(path)

Section 3: The FileManager in Plain Words

FileManager is Swift's built-in helper for working with the file system, and you can think of it as a librarian who knows where every file lives and can check, create, move, and delete files on your behalf. You usually reach it through the shared instance called FileManager.default, which is a single ready-made librarian that your whole program can use, without needing to create a new one each time. FileManager answers questions such as whether a file exists, what is in a folder, and where the user's home folder is, and it performs actions such as creating folders and removing files. It does not itself read or write the text inside files, since that job belongs to the String and Data types, but it manages the files as objects, which is a useful division of labour. Learning FileManager is therefore learning how to ask the librarian, and the answers it gives will guide the rest of your file code.

Checking whether a file exists is one of FileManager's simplest and most useful jobs, and it is the first thing you should do before reading a file that might not be there. The method fileExists takes a path and returns true or false, which lets you guard against missing files with a clear message, instead of crashing or catching a confusing error. This check is cheap and explicit, and it makes your program's behaviour obvious: if the file is missing, you can create it, use a default, or tell the user, depending on what makes sense for the problem. FileManager can also tell you whether a path is a folder or a file, and whether it is readable or writable, which are useful checks before attempting work that might fail. Asking before acting is a polite and robust pattern, and FileManager makes it easy.

Creating folders is another FileManager job, and it matters because writing a file into a folder that does not exist will fail, so programs often create their folders first. The method for creating a folder takes a path and a flag that says whether to create missing parent folders as well, which is usually what you want, since a path like notes/2026 may need both notes and 2026 created. FileManager can also list the contents of a folder, returning the names of the files inside, which lets a program discover what is available instead of assuming names in advance. Listing is how programs build file browsers, load all saved games, or find every note in a folder, and it turns a folder from a fixed address into a collection you can explore. Together, checking, creating, and listing give you the basic vocabulary for managing files as objects.

Removing, moving, and copying files are also FileManager jobs, and they should be used with care, because deleting a file is usually permanent, and moving a file changes where other code expects to find it. Swift's methods for these actions throw errors, so you call them with try inside a do block, and you handle failures such as a missing source or an existing destination gracefully.

import Foundation
let manager = FileManager.default
let exists = manager.fileExists(atPath: "tasks.txt")
print(exists)

Section 4: Checking Whether a File Exists

Before reading a file, a careful program checks whether the file exists, because reading a missing file throws an error, and handling that error after the fact is less clear than checking first. The check itself is simple: ask FileManager whether a file exists at the path, and use the true or false answer to decide what to do next, often with a guard that leaves early with a helpful message when the file is missing. This pattern is the file version of the guard habits from the previous chapter, since it treats a missing file as a requirement failure at the door, rather than letting it cause trouble deeper inside. For a program that loads saved tasks at startup, a missing file might simply mean "no tasks saved yet," which is not an error at all, but a normal first-run situation, and the check lets you handle it gracefully with an empty list. Checking first therefore turns a potential crash into a calm, expected branch.

There are two broad ways to handle a missing file, and the right one depends on the program's purpose, so think about it before you code. If the file is essential, such as a configuration file the program cannot run without, then a missing file is a genuine problem, and the program should report it clearly and stop, perhaps telling the user which file was expected and where. If the file is optional, such as a saved notes file on first run, then a missing file is a normal situation, and the program should carry on with defaults, perhaps creating the file later when there is something to save. Naming which case applies, in a comment or a message, helps readers understand the check, since the same fileExists call can mean two very different things. A guard with a message like "No saved tasks yet, starting fresh" communicates the optional case beautifully, while "Configuration file missing, cannot continue" communicates the essential case.

A subtle point is that existence is not the same as readability, since a file can exist but be unreadable due to permissions, or it can be a folder rather than a file, and a simple existence check will not catch those cases. FileManager offers additional checks for readability and for whether a path is a directory, and for important files, combining those checks gives a stronger guarantee before reading. In practice, the existence check plus error handling around the actual read covers most cases, because the read will throw a specific error if permissions fail, and that error can be caught and reported. The existence check handles the common, expected case of a missing file, while error handling covers the rarer, unexpected failures, and together they make file reading robust. This layered approach, check the expected, catch the unexpected, is a pattern you will use throughout file and data work.

Practise the check by writing a small program that looks for a file, prints a different message for found and missing cases, and behaves sensibly in both, such as loading an empty list when missing. Then create the file by hand, run again, and watch the found branch run, which proves the check responds to the real world, not just to your imagination.

import Foundation
let manager = FileManager.default
if manager.fileExists(atPath: "notes.txt") {
    print("Found notes.txt")
} else {
    print("No notes file yet")
}

Section 5: Reading a Whole Text File

Reading a whole text file is the simplest way to load saved data, and Swift makes it a short operation: you give a file's location and its text encoding, usually UTF-8, and you receive the entire contents as a single String. The operation is written as String(contentsOf:encoding:), and because it can fail, you call it with try inside a do block, catching errors such as a missing file or an unreadable encoding. When it succeeds, the result is the file's text exactly as saved, including line breaks, which you can then print, split into lines, search, or process in any way you like. This whole-file approach suits small files, such as notes, settings, or task lists, where loading everything at once is simple and fast, and it is the right starting point for file reading. Larger files need a different approach, which you will meet later in this chapter, but most learning programs will use whole-file reading.

Encoding deserves a brief explanation, because it is the system that turns characters into bytes for storage, and UTF-8 is the standard encoding that handles almost every language and symbol. When you read with UTF-8, Swift converts the file's bytes back into characters, and if the file was saved in a different encoding, the conversion may fail or produce strange characters, which is why matching the encoding on reading and writing matters. In this book, you will always use UTF-8 for both reading and writing, which keeps things consistent and avoids encoding puzzles, and you should do the same in your own programs unless you have a specific reason not to. If you ever meet a file that reads as gibberish, encoding mismatch is a likely suspect, and checking that both sides used UTF-8 is a good first step. Encoding is invisible when it matches, and confusing when it does not, so consistency is the whole trick.

Error handling around a whole-file read should be specific enough to help, because a generic "something went wrong" message does not tell the user whether the file was missing, unreadable, or wrongly encoded. Swift's errors carry information, and a catch block can print the error itself, which often names the problem, such as a missing file path, and that detail is valuable during debugging. For user-facing programs, you might translate the technical error into a friendly message, such as "Could not load your notes," while still logging the technical detail for yourself, since users and programmers need different levels of detail. In learning programs, printing the error is perfectly fine, and it teaches you what file errors actually look like, which will help you recognise them later. Do not swallow file errors silently, because a program that fails to load data without saying so will confuse everyone.

Once you have the file's text as a String, you can work with it using all the string tools from earlier chapters, such as splitting it into lines, checking whether it contains a word, or counting its characters. Splitting by line breaks is especially common, since text files usually store one record per line, and the resulting array of lines is easy to loop over and process.

import Foundation
do {
    let text = try String(contentsOfFile: "notes.txt", encoding: .utf8)
    print(text)
} catch {
    print("Could not read notes.txt: \(error)")
}

Section 6: Writing Text to a File

Writing text to a file is the mirror of reading, and Swift makes it similarly short: you take a String, choose a file location and encoding, and ask the string to write itself to that location. The operation is written as write(toFile:atomically:encoding:), and because it can fail, you call it with try inside a do block, catching errors such as a missing folder or a lack of permission. When it succeeds, the file contains exactly the text you wrote, replacing any previous contents, which is an important detail, since writing does not add to an existing file by default, but replaces it entirely. This replacement behaviour is useful when you are saving a complete new version of data, such as a whole task list, but it is dangerous if you meant to add a single line, which is why the next section covers appending separately. Knowing whether an operation replaces or adds is essential in file code, because confusing the two is a classic way to lose data.

The atomically flag in the write operation deserves explanation, because it is a safety feature that protects against losing data if something fails halfway through writing. When atomically is true, Swift first writes the text to a temporary file, and only when that succeeds does it replace the original file with the temporary one, so that a failure during writing leaves the original intact. When atomically is false, Swift writes directly to the original, so a failure halfway could leave a half-written file, which is worse than no change at all. For most programs, atomically true is the safer choice, and it is the default you should use unless you have a specific reason not to, since the small extra cost is worth the protection. This is the same idea as the backup habit later in this chapter, built into a single flag, and it shows how Swift's file tools include safety features that careful programmers use by default.

Before writing, a careful program checks that its inputs are sensible, using guard for an empty file name or empty content when empty content would be a mistake, and it ensures that the destination folder exists, creating it with FileManager if needed. Writing to a folder that does not exist will fail, and the error message may not make the reason obvious, so creating folders first removes a common failure. It is also wise to think about what should happen if the file already exists, since replacing it may destroy previous data, and for important data, a backup step before writing is a kindness to the user. In learning programs, replacing is often fine, but the habit of pausing to ask "what is already in this file, and do I care?" will serve you well when the data matters. File writing is an action with lasting consequences, so it deserves a moment of thought before each write.

After writing, it is good practice to verify, especially while learning, by reading the file back and printing its contents, or by opening it in a text editor and confirming that it contains what you expected.

import Foundation
do {
    try "Buy milk\nCall Ana\n".write(toFile: "tasks.txt", atomically: true, encoding: .utf8)
    print("Saved tasks.txt")
} catch {
    print("Could not save: \(error)")
}

Section 7: Appending to a File

Appending means adding new text to the end of an existing file without disturbing what is already there, and it is the right operation for logs, journals, and lists where new entries arrive over time. Swift's simple String write operation replaces a file, so appending needs a different approach, usually opening the file for updating and seeking to its end, or reading the old contents, adding the new text, and writing the whole thing back. For small files, the read-add-write approach is simple and clear: read the existing text if the file exists, append the new line, and write the combined text back atomically, which is safe and easy to understand. For large files, such as long logs, reading everything just to add one line is wasteful, and a file handle that seeks to the end is more efficient, but that technique is more advanced and can wait until you need it. Start with the simple approach, and move to handles when file size makes it necessary.

A common pattern for appending is to treat a missing file as an empty file, so that appending to a file that does not exist yet simply creates it with the new text. This makes the first append behave sensibly, without requiring the caller to create the file in advance, and it matches how logs work in real programs, where the first log entry creates the log file. The pattern uses a check: if the file exists, read its contents, and if not, start with an empty string, then add the new text with a line break, and write the result back. Care with line breaks matters, because appending without one will glue the new text onto the end of the last line, producing a merged line instead of a new entry, which is a subtle bug that is easy to miss. Always ensure that appended entries end with a line break, and that the existing text ends with one before you add, so that each entry occupies its own line.

Appending is also the natural operation for a program that records events over time, such as a diary, a task log, or a simple audit trail, where each run adds entries rather than replacing the whole history. A program that replaced its log on every run would keep only the latest events, losing the history that makes a log useful, while an appending program preserves the full story. This distinction between replacing and appending is a design decision, not just a technical one, because it determines whether a file holds a snapshot or a history, and choosing wrongly can lose data or bloat a file. Snapshots suit settings and current task lists, where only the latest state matters, while histories suit logs and journals, where the past matters. When you design a file, ask whether it should hold the latest state or the whole history, and choose replacing or appending accordingly.

Concurrency and failure deserve a brief note, because appending by read-add-write can lose entries if two programs append at the same time, since each may read the same old contents and overwrite the other's addition.

import Foundation
func appendLine(_ line: String, to file: String) {
    let old = (try? String(contentsOfFile: file, encoding: .utf8)) ?? ""
    let combined = old + line + "\n"
    try? combined.write(toFile: file, atomically: true, encoding: .utf8)
}

Section 8: Handling File Errors with do try catch

File operations fail for reasons outside a program's control, such as missing files, missing folders, permission problems, and full disks, so handling their errors well is not optional, but a core part of file code. Swift marks file operations as throwing, which means you call them with try inside a do block, and you write catch blocks that decide what to do when each kind of failure occurs. A catch block can print a friendly message, use a default value, create a missing file, or propagate the error to a caller that can handle it better, depending on the program's design. The important thing is that errors are never ignored silently, because a silent file failure can mean lost data or a program that behaves as if it loaded data it never actually read. Error handling turns file failures from crashes into decisions, which is exactly what robust programs need.

Different file errors deserve different responses, and thinking about them in advance makes your catch blocks more useful than a single generic message. A missing file on first run is often normal, and the response may be to start with empty data, while a missing file that should exist is a problem, and the response may be to alert the user with the exact path expected. A permission error suggests that the user or the system needs to change access, and the message should say so, rather than pretending the file is missing, while a disk-full error suggests freeing space, which is a different action again. Swift's errors often carry this information, and printing the error itself during development shows you what details are available, which helps you write better messages later. As you gain experience, you will learn to distinguish errors that are expected, errors that are the user's to fix, and errors that are the program's fault, and to respond appropriately to each.

Guard and error handling work together in file code, with guard handling the checks you can make in advance, such as an empty file name, and do-catch handling the failures you cannot predict, such as a disk error during writing. This division is clean, because guards state requirements that the caller controls, while catches handle world failures that nobody controls, and readers can tell which is which by where the handling lives. A function that guards its file name, then tries to read inside a do block, reads as a clear story: first we check what we can, then we attempt the risky operation, then we handle its failure. Mixing the two, such as using try for a checkable condition or guard for an unpredictable failure, muddies the story, so keep the division in mind. Together, guard and catch cover both kinds of file trouble, which is why they appear together so often in file code.

A practical habit for file error handling is to always include the file path in the error message, because a program that works with several files can fail on any of them, and a message without a path leaves the reader guessing which file caused trouble. A message like "Could not read tasks.

Section 9: Creating Folders

Folders organise files, and programs often need to create them before saving, especially when they store data in a dedicated folder such as notes, tasks, or backups. FileManager's folder creation method takes a path and a flag for creating intermediate folders, and when that flag is true, a path like notes/2026 will create both notes and 2026 if neither exists, which is convenient and safe. The operation throws errors, so you call it with try inside a do block, and you handle failures such as permission problems gracefully. Creating a folder that already exists is not an error when the intermediate flag is used sensibly, but it is still good practice to check existence first if your program's logic depends on whether the folder is new, such as when setting up a fresh workspace. Folder creation is a small step, but it removes a whole class of write failures, since writing into a missing folder is one of the most common file mistakes.

Choosing where to create folders matters, because a program should store its data in a sensible, predictable place, such as a folder inside the user's home directory, a documents folder, or the program's own working folder for learning projects. Hard-coding a path with another user's name will fail on other computers, so building folder paths from the home directory or the current directory, using FileManager helpers, makes the program portable. For learning programs, a folder in the current working directory is fine and easy to inspect, since you can see it appear next to your program, while for real applications, the system's documents or application support folders are more appropriate. The principle is the same in both cases: choose a location that makes sense for the data, build the path with helpers rather than guessing, and create the folder before writing into it. A program that creates its own folders is self-sufficient, which users appreciate.

Folder creation also interacts with the rest of file code, since listing, reading, and writing all assume that folders exist, and a missing folder can cause failures far from the real cause. A program that fails to write because its folder is missing may report a write error, when the real problem is that setup was skipped, which is why creating folders during setup, before any file work, is a good pattern. Setup code that creates needed folders, checks for essential files, and reports problems early gives the rest of the program a solid foundation, and it makes later errors easier to diagnose, since folder problems are ruled out. Think of folder creation as preparing the workspace before starting work, like clearing a desk before writing, since work goes more smoothly when the space is ready. Skipping setup is a false economy that costs time later in confusing errors.

There is also a safety note: creating folders is harmless, but deleting folders is not, since a folder deletion removes everything inside it, so deletion code should always be checked carefully and, for important data, backed up first. This chapter covers folder deletion only briefly, because creation and listing are the everyday operations, while deletion deserves caution and confirmation in real programs.

import Foundation
let manager = FileManager.default
do {
    try manager.createDirectory(atPath: "notes", withIntermediateDirectories: true)
    print("Folder ready")
} catch {
    print("Could not create folder: \(error)")
}

Section 10: Listing Files in a Folder

Listing a folder means asking the file system for the names of everything inside it, which lets a program discover files instead of assuming their names in advance. FileManager's contentsOfDirectory method returns an array of names, or URLs, for the items in a folder, and it throws an error if the folder does not exist or cannot be read, so you call it with try inside a do block. Once you have the list, you can loop over it, print it, filter it for a particular extension such as .txt, or sort it alphabetically, using all the collection tools from earlier chapters. Listing turns a folder into data your program can work with, which is powerful, because it means a program can load every note, every saved game, or every backup, without the user having to name each file. This discovery pattern is how file browsers, media players, and backup tools find their content, and it is a natural next step after reading single files.

Filtering a listing is a common and useful step, since a folder may contain files of several kinds, and a program usually cares about only one, such as text files for a notes program or image files for a gallery. You can filter by checking whether each name ends with a particular extension, or by checking a file's type with FileManager, and the result is a clean list of relevant files. Sorting the list is also common, since the file system's order is not guaranteed to be alphabetical, and users expect alphabetical order when they see a list of files. Combining listing with filtering and sorting, using the collection methods you already know, produces a polished result from a simple operation, and it is a good example of how Swift's pieces combine. A notes program that lists, filters for .txt, and sorts will feel professional, even though each step is simple on its own.

Listing also helps with debugging and with user feedback, because a program can show the user what it found, rather than silently loading files or failing mysteriously. If a program expects to find saved tasks but finds none, printing the folder's contents, or a message that the folder is empty, tells the user and the programmer exactly what happened, which is far better than a silent empty list that could mean many things. Similarly, during development, printing a listing is a quick way to confirm that files were created where you expected, and that their names are spelled as you thought. Visibility, which you met as a theme in file code, applies to listings too, since a program that shows what it found is easier to trust than one that hides its discoveries. Make listing output part of your debugging toolkit for file programs.

There are limits to listing that are worth knowing, because a folder can contain subfolders as well as files, and a simple listing does not recurse into subfolders, but only shows the immediate contents. If you need files from subfolders too, you must list each subfolder in turn, which is a recursive job that can be built from the simple listing operation, but which is beyond the scope of this section.

import Foundation
let manager = FileManager.default
do {
    let items = try manager.contentsOfDirectory(atPath: "notes")
    for item in items.sorted() {
        print(item)
    }
} catch {
    print("Could not list notes: \(error)")
}

Section 11: Deleting Files Safely

Deleting a file removes it from the disk, usually permanently, which makes deletion the most dangerous file operation, and the one that most deserves care and confirmation. FileManager's removeItem method deletes a file or folder at a path, and it throws errors if the path does not exist or cannot be removed, so you call it with try inside a do block. Before deleting, a careful program checks that the file exists, that the path is the intended one, and, for important data, that a backup exists, because a deletion cannot easily be undone, unlike a wrong calculation that can be rerun. In interactive programs, deletion usually requires the user to confirm, since the user is the best judge of whether a file is truly unwanted, while in automatic programs, deletion should be limited to files the program itself created, such as temporary files. Treating deletion as a serious action, not a casual cleanup, prevents the most regretted file mistakes.

A useful safety pattern is to move a file to a trash or backup location instead of deleting it outright, when the program's design allows it, since a moved file can be recovered, while a deleted one usually cannot. For learning programs, this might mean moving an old file into a backup folder with a date in its name, rather than removing it, which preserves the data while still clearing the original location. Another safety pattern is to delete only after a successful replacement has been verified, such as deleting an old backup only after a new backup has been written and checked, so that there is never a moment with no backup at all. These patterns share a principle: never destroy the only copy of something important, and always ensure that a replacement or a backup exists before removing the original. That principle, applied consistently, makes deletion safe even when it is necessary.

Testing deletion code deserves special care, because a bug in a path can delete the wrong file, and test data should therefore be clearly separated from real data. When you practise deletion, create test files in a dedicated test folder with obvious names, delete only those, and verify afterwards that only the intended files are gone and that nothing else changed. Never test deletion with a path built from user input that has not been validated, since a mistyped or malicious path could point somewhere unintended, and guard checks on the path, such as requiring it to be inside an expected folder, add a layer of protection. Path validation for deletion is a security habit as well as a safety habit, because it prevents a program from being tricked into deleting files outside its own area. For the programs in this book, deletion will be limited to test files and temporary files, where the risk is low and the learning value is high.

It is also worth knowing what deletion does not do, since deleting a file's directory entry removes its name from the folder, but the underlying data may remain on disk until overwritten, which is why deleted files can sometimes be recovered with special tools, and why sensitive data needs secure deletion methods beyond this chapter.

import Foundation
let manager = FileManager.default
do {
    try manager.removeItem(atPath: "old-note.txt")
    print("Deleted old-note.txt")
} catch {
    print("Could not delete: \(error)")

Section 12: Moving and Copying Files

Moving a file changes its location, and copying a file creates a duplicate in a new location while keeping the original, and both are common operations for organising data, creating backups, and renaming files. FileManager provides moveItem and copyItem methods, each taking a source path and a destination path, and both throw errors, so you call them with try inside a do block. Moving is effectively a rename when the destination is in the same folder, which is how programs rename files, and a relocation when the destination is in a different folder, which is how programs organise files into folders. Copying is how programs create backups, since the original stays safe while the copy can be changed or moved, and it is also how programs duplicate templates or starter files for new work. Together, moving and copying give a program the ability to organise its files, not just to read and write their contents.

A common failure with moving and copying is that the destination already exists, which causes an error, since FileManager will not silently overwrite a destination file. A careful program checks whether the destination exists first, and decides what to do: replace it after backing up, choose a new name, or report the conflict to the user, depending on the situation. Another common failure is a missing source, which should be checked before attempting the operation, with a clear message naming the expected source path. A third failure is a missing destination folder, which can be fixed by creating the folder first, as you learned earlier, so that the move or copy has somewhere to go. Handling these three cases, existing destination, missing source, and missing folder, covers most move and copy failures, and it makes the operations feel reliable instead of mysterious.

Copying deserves special attention as a backup tool, because a backup is simply a copy stored in a safe place, often with a date or version in its name, so that an older version can be restored if the current one is damaged. A program that copies its data file to a backup folder before overwriting it follows a pattern you will meet again later in this chapter, and that pattern is one of the simplest and most effective data-protection habits. The backup copy should be verified after copying, by checking that it exists and has a sensible size, since a failed copy that is assumed to have succeeded gives false confidence. For important data, keeping more than one backup, such as the last three versions, protects against a backup that itself is damaged, although for learning programs, a single backup is a good start. Copying is cheap, and data loss is expensive, so copy generously.

Moving and copying also interact with paths in a way that deserves care, because a move changes where future code must look for the file, and any code that stored the old path will now fail. When a program moves a file, it should update its own records of that file's location, or it should use a consistent rule for finding files, such as always looking in a known folder, so that moves do not break lookups.

import Foundation
let manager = FileManager.default
do {
    try manager.copyItem(atPath: "tasks.txt", toPath: "tasks-backup.txt")
    print("Backup created")
} catch {
    print("Could not copy: \(error)")
}

Section 13: Reading a File Line by Line

Reading a file line by line means processing its contents one line at a time, rather than loading the whole file into memory at once, and it is the right approach when a file is large or when each line is an independent record. The simplest way to do this in Swift is to read the whole file as a String and then split it into lines, which works well for small and medium files, and which you will use most often in this chapter. Each line can then be processed in a loop, with guard checks for empty lines or malformed records, and with helpers for parsing each line's contents, which keeps the loop body clean. This split-then-loop pattern is easy to understand, easy to test, and sufficient for task lists, notes, logs, and other line-based files, which are the most common text files a beginner will meet. It is the line-by-line pattern in its simplest, most practical form.

True streaming line-by-line reading, where the program reads one line, processes it, and then reads the next, without ever holding the whole file, is more efficient for very large files, but it requires lower-level file handling that is more complex and error-prone. For files of thousands of lines or fewer, the difference in memory is negligible on modern computers, so the simple split approach is the better choice, since its clarity outweighs its small inefficiency. A good rule is to use the simple approach until a file is large enough to cause a real problem, such as slowness or memory pressure, and only then to learn streaming, because premature optimisation for large files can complicate code that would otherwise be clear. This is the same judgement you met with duplication and helpers: choose the simplest tool that handles the actual problem, and upgrade only when the problem demands it. Most files you will work with in this book are small, so the simple approach will serve you well.

Processing lines in a loop brings together several habits from earlier chapters, including guard with continue for skipping bad lines, helpers for parsing, and clear messages for malformed records. A loop that reads tasks, for example, might skip empty lines, since a trailing line break at the end of a file produces an empty final line, and it might skip lines that do not match the expected format, reporting each skip with the line number, so that bad data does not crash the whole load. Skipping bad lines, rather than failing the entire load, is often the right choice for user-edited files, since one mistyped line should not destroy access to all the good lines, although for critical data, failing loudly may be safer. The choice depends on the data's importance, and it should be made deliberately, with a comment explaining it, since readers will wonder why bad lines are skipped or why they cause failure. Line processing is where file code meets data quality, and the decisions there matter.

Line numbers are a useful aid when processing lines, because they let error messages point to the exact line that caused trouble, which makes fixing user-edited files much easier.

import Foundation
let text = "Buy milk\nCall Ana\nRead book"
for line in text.components(separatedBy: "\n") {
    print("Task: \(line)")
}

Section 14: Working with Lines and Splitting Text

Splitting text is the operation that turns a block of text into pieces, and it is the key to working with lines, words, and records stored in files. Swift's components method splits a String by a separator, such as a line break for lines, a comma for CSV fields, or a space for words, returning an array of pieces that you can loop over, filter, or transform. Splitting by "\n" gives lines, which is the most common split for files, while splitting by other separators gives fields or words, depending on the file's format. The pieces returned include everything between separators, so an empty line produces an empty piece, and a trailing separator produces a trailing empty piece, which is why line-processing loops often skip empty pieces with a guard. Understanding these edge cases prevents surprises, such as an extra empty task appearing at the end of a list, which is a common beginner puzzle with a simple explanation.

Trimming is the companion to splitting, because lines and fields often carry extra spaces, especially when a file was edited by hand, and those spaces can cause comparisons to fail. Swift's trimming method removes spaces, tabs, and line breaks from the edges of a string, turning " Buy milk " into "Buy milk," which is usually what you want for user-entered data. Trimming before comparing, storing, or displaying is a good habit, since it makes the program tolerant of harmless extra spaces, while still preserving spaces inside the text, where they matter. A line that is only spaces becomes empty after trimming, which is another reason to trim before checking for emptiness, since a spaces-only line should be treated as empty, not as a task containing spaces. Trim and check, in that order, is a small pattern that improves file loading robustness noticeably.

Joining is the reverse of splitting, since it takes an array of pieces and combines them into a single string with a separator between each pair, which is how you rebuild a file's text after processing its lines. For example, after filtering out completed tasks, you can join the remaining lines with "\n" to produce the new file contents, which you then write back, replacing the old file. Joining and splitting are therefore a pair that supports a complete load-process-save cycle: split the file into lines, process the lines as an array, join them back into text, and write the text. This cycle is the backbone of many file programs, including task managers, note editors, and log cleaners, and it uses only the collection and string tools you already know. Recognising the cycle helps you design file programs, since you can think in terms of lines as data, rather than as raw text.

Splitting also introduces the idea of formats, since the separator you choose defines how records are stored, and different formats suit different data. Line-per-record suits simple lists, comma-separated values suit tables, and key-value pairs suit settings, and each format has its own splitting and joining rules, which later sections will explore. For now, the lesson is that splitting is not just a string trick, but a way of imposing structure on plain text, turning an unstructured block into structured pieces that a program can work with.

let line = "  Buy milk, Call Ana  "
let clean = line.trimmingCharacters(in: .whitespaces)
print(clean)

Section 15: Storing Simple Records in Text

Simple records are pieces of data with a few fields, such as a task with a title and a done flag, or a contact with a name and a phone number, and plain text files can store them if each record follows a consistent pattern. The simplest pattern is one record per line, with fields separated by a character that does not appear in the data, such as a pipe symbol or a tab, so that a line like "Buy milk|no" represents a task titled "Buy milk" that is not done. Loading such a file means splitting the text into lines, then splitting each line into fields, then building a record from those fields, with guards for lines that do not have the expected number of fields. Saving means the reverse: turning each record into a line by joining its fields with the separator, joining the lines with line breaks, and writing the result. This round-trip, records to lines and lines to records, is the foundation of simple file storage, and it works well for small programs.

Choosing a separator is a design decision that deserves thought, because the separator must not appear inside the field values, or the split will produce extra fields and corrupt the record. A comma is a poor separator for free text, since commas appear in ordinary sentences, while a pipe or a tab is less common in everyday text, although still possible, which is why later sections cover escaping for CSV. For learning programs with controlled data, such as task titles you type yourself, a pipe separator is a practical choice, and you can guard against titles containing pipes by rejecting them or by choosing a different separator. Documenting the format, even briefly in a comment, helps future readers understand the file, since a file of pipe-separated lines is meaningless without knowing what each field means. A comment like "Format: title|done, where done is yes or no" turns a mysterious file into a clear one.

Validation during loading is important, because files edited by hand can contain mistakes, such as a missing field, an extra separator, or a done flag that is neither yes nor no, and a program should handle these gracefully. A line with the wrong number of fields can be skipped with a message naming its line number, which preserves the good records while flagging the bad one, while a done flag with an unexpected value might default to no, with a warning, or might cause the line to be skipped, depending on how strict the program should be. The choice between skipping and failing depends on the data's importance, as with line processing earlier, and it should be deliberate and documented. Strict loading, which fails on any bad line, suits critical data where a mistake could cause harm, while tolerant loading, which skips bad lines, suits user-edited lists where one typo should not destroy everything. Either way, the program should report what it did, so that bad data does not disappear silently.

Records in text also have limits that are worth recognising, since they suit small, simple data, but they become awkward for nested data, large collections, or data that changes concurrently.

let record = "Buy milk|no"
let fields = record.components(separatedBy: "|")
print(fields[0])
print(fields[1])

Section 16: CSV in Plain Words

CSV stands for comma-separated values, and it is a simple format for storing tables, where each line is a row, and commas separate the columns within each row. A CSV file for scores might look like a header line "Name,Score" followed by rows like "Ana,85" and "Ben,92," and it can be opened in a spreadsheet, a text editor, or a Swift program, which makes it wonderfully portable. Spreadsheets can export and import CSV, which means a Swift program that writes CSV can share data with tools that have nothing to do with Swift, and that interoperability is CSV's greatest strength. For simple tables, CSV is often the right choice, because it is human-readable, easy to generate, and widely supported, without the complexity of JSON or a database. Learning CSV is therefore learning a practical bridge between your programs and the rest of the world's tools.

The header row is a CSV convention worth following, because it names each column, so that readers and programs know what each value means without guessing. A file without a header, containing only rows like "Ana,85," requires outside knowledge to interpret, while a file with a header "Name,Score" is self-describing, at least for its column meanings. When you write CSV, include a header row unless you have a reason not to, and when you read CSV, check whether the first line is a header and skip it if so, rather than treating it as data. A common beginner bug is to treat the header as a data row, producing a phantom record with a name like "Name" and a score that fails to parse, which is easily avoided by skipping the first line when it matches the header. Documenting whether your CSV has a header, in a comment or in the program's messages, prevents this confusion.

CSV also has no standard way to represent types, since every field is text, and a program reading CSV must convert text to numbers, dates, or booleans itself, with guards for values that fail to convert. A score field of "85" must be converted to an integer, and a field of "eighty-five" or an empty field must be handled as an error or a default, depending on the program's strictness. This type conversion is an extra step compared with JSON, where numbers and booleans have their own syntax, and it is a reason to prefer JSON when types matter and interoperability with spreadsheets does not. CSV's strength is tables of simple values shared with spreadsheets, while JSON's strength is structured data shared with programs, and choosing between them depends on who will consume the data. For a scores table destined for a spreadsheet, CSV is ideal, while for a task object with nested data, JSON is better.

Practise CSV by writing a small table by hand, with a header and three rows, and then writing a Swift program that reads it, skips the header, splits each row, and prints each record's fields. Notice how the header skip and the field split combine into a clean loading pattern, similar to the record pattern from the previous section, but with commas and a header.

let header = "Name,Score"
let row = "Ana,85"
print(header)
print(row)

Section 17: Reading CSV Rows

Reading CSV rows follows the same load-process pattern as other line-based files, with the addition of a header skip and a field split for each row. The steps are: read the whole file as text, split it into lines, skip empty lines, skip the header line if the file has one, and for each remaining line, split it by commas into fields, then build a record from those fields. Each step deserves a guard or a check, since a line with too few fields, a field that fails to convert to a number, or an empty line should be handled gracefully, with a message naming the line number. A loop that processes CSV rows with these checks is robust for simple CSV, where fields contain no commas or quotes, and it is the pattern you should master first, before tackling quoted fields. Simple CSV reading is a complete, useful skill on its own, since much real CSV is simple.

Converting fields to their proper types is a key part of CSV reading, because every field arrives as text, and the program must decide what type each column represents. A score column converts to an integer with Swift's Int initializer, which returns an optional that is nil when conversion fails, and a guard let or an if let handles that optional cleanly, either skipping the row or using a default. A price column might convert to a Double, while a name column stays a String, and each column's conversion should be checked separately, so that one bad field does not silently corrupt the whole row. Messages for failed conversions should name the line and the field, such as "Line 3: score 'eighty' is not a number, skipping," which lets a user fix the exact cell. Type conversion with clear messages turns CSV reading from a fragile split into a trustworthy load, and it is worth practising until it feels routine.

Empty lines and whitespace are common in hand-edited CSV, and handling them gracefully prevents phantom records and conversion failures. A trailing line break at the end of a file produces an empty final line, which should be skipped, and a line containing only spaces should be trimmed and skipped as well, since it carries no data. Fields themselves should often be trimmed, since a space after a comma, as in "Ana, 85," is common in hand-written CSV, and trimming the score field before converting it prevents a failure that would surprise users. These small tolerances, skipping empty lines and trimming fields, make a CSV reader feel polished, because it accepts the minor variations that humans naturally produce, while still rejecting genuine errors. A reader that is too strict will frustrate users, while one that is too lax will accept corrupt data, so the balance is to tolerate formatting variation but not content errors.

A CSV reader should also decide what to do with rows that have the wrong number of fields, since a row with too many or too few commas is malformed, and silently using the wrong fields would produce incorrect records. Skipping such rows with a message is usually the right choice for user-edited tables, while failing the whole load suits critical data where a malformed row suggests a larger problem.

let csv = "Name,Score\nAna,85\nBen,92"
let lines = csv.components(separatedBy: "\n")
for line in lines.dropFirst() {
    let fields = line.components(separatedBy: ",")
    print(fields)
}

Section 18: Writing CSV Rows

Writing CSV rows is the reverse of reading, and it follows a clear pattern: build a header line from the column names, build one line per record by joining its fields with commas, join all lines with line breaks, and write the resulting text to a file. Each field must first be converted to text, since numbers and other types need a string form, and Swift's string interpolation handles this naturally, turning a score of 85 into "85" inside a joined line. The header and the rows must use the same column order, since a reader will interpret fields by position, and a mismatch in order will silently assign values to the wrong columns. Consistency in order is therefore a contract between writer and reader, and documenting the order, in a comment or in the header itself, helps future readers honour it. A writer that follows this pattern produces CSV that spreadsheets and other programs can open correctly, which is the point of the format.

Field conversion during writing deserves care, because a field that contains a comma, a quote, or a line break will corrupt the CSV unless it is quoted and escaped, as the next section explains in detail. For simple data without those characters, a plain join works, and many learning programs will use plain joins, but a writer should at least consider whether its data could contain commas, and if so, it should quote fields or choose a different separator. A defensive writer might quote every text field, which is valid CSV and safe, although it makes the file slightly less tidy to read by hand, while a writer that quotes only when needed produces tidier files but requires a check for special characters. Either approach is correct if implemented consistently, and the choice depends on whether tidiness or simplicity matters more for the file's audience. For files destined for spreadsheets, quoting is handled by the spreadsheet on import, so either style works.

Writing CSV atomically, as with other file writes, protects against losing the old file if the new write fails halfway, so use the atomic flag and handle errors with do-catch, reporting the path and the error on failure. After writing, verifying by reading back and counting rows is a good habit, especially for important tables, since it confirms that the file contains the expected number of records and that no row was lost in joining. A writer that reports how many rows it wrote gives the user a quick confidence check, similar to the reader's summary, and it makes debugging easier when counts do not match expectations. For a scores table, a message like "Wrote 3 scores to scores.csv" is simple, informative, and reassuring, and it costs one line. Small reporting habits like this distinguish polished file programs from silent ones.

Round-tripping, which means writing CSV and then reading it back to confirm that the same records return, is an excellent test for a writer, because it catches ordering mistakes, separator mistakes, and conversion mistakes in one check. Write a few records, read them back with your reader, and compare the returned records with the originals, field by field, and any mismatch points to a bug in either the writer or the reader.

let header = "Name,Score"
let rows = ["Ana,85", "Ben,92"]
let csv = ([header] + rows).joined(separator: "\n")
print(csv)

Section 19: Escaping Commas and Quotes in CSV

Escaping is the set of rules that lets special characters appear inside CSV fields without breaking the format, and it is essential for real-world CSV, where names, addresses, and notes often contain commas. The core rule is that a field containing a comma, a double quote, or a line break must be wrapped in double quotes, so that a parser knows the comma inside the quotes is data, not a separator. For example, the name "Smith, John" becomes the field "\"Smith, John\"" in the file, with quotes around it, and a correct parser will return it as a single field. A second rule handles quotes inside fields: a double quote inside a quoted field is written as two double quotes, so that the field for the text Say "hi" becomes "\"Say \"\"hi\"\"\"", which looks strange but is unambiguous to a parser that follows the rules. These two rules together make CSV capable of holding almost any text, at the cost of more complex parsing.

Writing escaped CSV requires a helper function that checks each field for special characters, and if any are present, wraps the field in quotes and doubles any quotes inside it. This helper should be used for every text field, so that escaping is consistent, and it should be tested with fields containing commas, quotes, and line breaks, to confirm that the output follows the rules. A writer that forgets to escape will produce files that look correct to the eye but corrupt on reading, which is a particularly nasty bug, since the corruption appears only when the data contains special characters, which may be rare in testing but common in real use. Testing with tricky data, such as a name with a comma and a note with quotes, is therefore essential for a CSV writer, and it should be part of your practise. Escaping is not an optional extra for real CSV, but a requirement for correctness.

Reading escaped CSV is harder than writing it, because a simple comma split will break quoted fields, splitting them at their internal commas and producing extra fields. A correct reader must scan the line character by character, tracking whether it is inside quotes, and only splitting on commas that are outside quotes, while also converting doubled quotes back to single quotes. This scanning logic is a good exercise in loops and state, since it requires remembering whether quotes are open, but it is also easy to get wrong on edge cases, such as a quote at the end of a field or an unmatched quote. For learning programs, you may use a simple reader for simple CSV and note its limits, while for real programs with tricky data, you should use a well-tested CSV library or JSON instead, rather than writing your own parser. Knowing when to use a library, rather than hand-rolling a parser, is a professional judgement, and CSV parsing is a classic case where libraries earn their place.

The broader lesson of escaping is that formats have rules for special characters, and those rules must be honoured on both sides, writer and reader, or data will corrupt in ways that are hard to detect.

func escapeCSV(_ field: String) -> String {
    if field.contains(",") || field.contains("\"") {
        let doubled = field.replacingOccurrences(of: "\"", with: "\"\"")
        return "\"\(doubled)\""
    }
    return field
}

Section 20: Temporary Files and Working Folders

Temporary files are files created for short-term use during a program's run, such as intermediate results, downloads in progress, or data being prepared before a final save, and they are meant to be deleted when no longer needed. Swift's FileManager provides a temporary directory, which is a folder set aside by the system for such files, and using it, rather than the user's documents or the current folder, keeps temporary clutter out of places where users keep important data. Temporary files should have distinctive names, often including the program's name and a unique identifier, so that they do not collide with other programs' temporary files, and so that they can be recognised and cleaned up later. A program that creates temporary files should also delete them when done, using defer where appropriate, so that a normal exit, an early return, or an error does not leave clutter behind. Temporary file hygiene is a small courtesy that keeps systems tidy.

The temporary directory itself can be found with FileManager's temporaryDirectory, which returns a URL for the system's temp folder, and files inside it can be created, read, and deleted with the same methods as anywhere else. One important detail is that the system may delete temporary files on its own, such as on restart or when disk space is low, so temporary files must never hold the only copy of important data, since they can vanish without warning. This is a crucial distinction: temporary storage is for data that can be recreated or that is only needed briefly, while important data belongs in a persistent location, such as documents or application support. A program that stores a user's work only in a temporary file risks losing it, which is a serious design mistake, so always ask whether the data is temporary or permanent, and choose the location accordingly. Location is part of a file's meaning, not just its address.

Working folders are the folders a program uses for its current task, such as a project folder, a notes folder, or a download folder, and they differ from temporary folders in that their contents are meant to persist and be visible to the user. A program's working folder is often its current directory, which depends on how it was launched, or a folder chosen by the user, which the program should remember and use consistently. When a program works in a folder, it should create the folder if missing, list its contents to show the user what is there, and use paths relative to that folder for its files, so that moving the folder moves the whole project together. This folder-as-project pattern is common in real programs, from photo editors to code projects, and it makes data portable, since copying the folder copies everything. Designing around a working folder, rather than scattered absolute paths, makes programs more robust and user-friendly.

Cleaning up temporary files is where defer shines again, since a function that creates a temporary file can defer its deletion immediately after creation, guaranteeing cleanup on every exit, including errors. Without defer, each exit path would need its own deletion code, and a new exit added later might forget it, leaving clutter that accumulates over time.

import Foundation
let temp = FileManager.default.temporaryDirectory
print(temp.path)

Section 21: File Paths on Different Computers

File paths differ between computers, because users have different names, systems have different folder layouts, and a path that works on one machine may fail on another. A path like /Users/kel/notes/tasks.txt contains the user name kel, which will not exist on a computer owned by someone else, so a program that hard-codes such a path is not portable, and it will break when shared. The solution is to build paths from system helpers that adapt to each computer, such as the home directory, the documents directory, or the current directory, rather than writing full paths by hand. A program that builds its path as home plus notes plus tasks.txt will work for any user, since home adapts, while a program with a hard-coded user name works only for its author. Portability is not an abstract virtue, but a practical requirement for any program that will run on more than one computer, which is almost every program worth sharing.

Operating systems also differ in their path separators and conventions, although Swift programs in this book target Apple platforms and Linux, where the slash separator and the home folder idea are shared. Even within those systems, details differ, such as where documents live or how temporary folders are named, which is why using FileManager's directory helpers, rather than assuming locations, is the robust approach. The helpers return URLs for standard locations, such as the home directory, the temporary directory, and the documents directory, and building paths from those URLs, by appending file names, produces correct paths on each system. Appending with URL methods also handles slashes correctly, avoiding the double-slash or missing-slash bugs that come from gluing strings by hand. System helpers are the program's way of asking the computer where things belong, rather than guessing, and guessing is a poor strategy for paths.

Relative paths offer another kind of portability, since a path like notes/tasks.txt works wherever the program's working folder contains a notes folder, without mentioning any user or system location. Relative paths are ideal for project folders that move together, such as a folder containing a program and its data, since copying the folder preserves all relative relationships. Their weakness is dependence on the working folder, which can change depending on how the program is launched, so a relative path that works when run from a terminal may fail when run from an editor or a script. To use relative paths safely, a program should know its working folder, print it during debugging, and, when necessary, set it explicitly or resolve relative paths against a known folder. Relative and absolute paths each have strengths, and choosing between them depends on whether the data moves with the program or lives in a fixed system location.

Testing portability is straightforward, even with one computer, by checking that your program builds paths from helpers and does not contain hard-coded user names or system-specific locations. Search your code for absolute paths containing a user name, and replace each with a helper-built path, then run the program from a different working folder to confirm that it still finds its files, or fails with a clear message about the working folder.

import Foundation
let home = FileManager.default.homeDirectoryForCurrentUser

Section 22: Home Directory and Current Directory

The home directory is the personal folder belonging to the current user, where their documents, settings, and personal files live, and it is the most reliable starting point for user data on a computer. Swift's FileManager provides it through homeDirectoryForCurrentUser, which returns a URL that adapts to whoever is running the program, so code built from it works for any user without hard-coding names. Inside the home directory, conventional subfolders such as Documents, Desktop, and Library organise different kinds of data, although the exact conventions vary by system, and a program should use system helpers for standard subfolders rather than assuming their names. For learning programs, a simple folder inside the home directory, such as a notes folder, is a sensible and portable place for data, and it is easy to find and inspect. Home is the anchor for personal data, and building from it is a habit that makes programs work for everyone.

The current directory, also called the working directory, is the folder a program starts in, and it is the reference point for relative paths, as you learned earlier. Swift's FileManager provides it through currentDirectoryPath, which returns a string that you can print during debugging to discover where your program is actually working, which often surprises beginners. Programs launched from a terminal work in the terminal's folder, while programs launched from an editor, a script, or a double-click may work elsewhere, such as a build folder or a system folder, which is why relative paths behave differently in different launches. Knowing the current directory is therefore essential for debugging file-not-found errors, since the first question should always be "where is the program working, and is my relative path correct from there?" Printing the current directory at startup, during development, answers that question immediately and saves much guessing.

Changing the current directory is possible, but it should be done carefully, since it affects all relative paths in the program, and a change made in one part can surprise another part that assumed the original folder. A better pattern, in most cases, is to keep the current directory unchanged and to build absolute paths from known anchors, such as the home directory or a user-chosen folder, so that each file operation is explicit about its location. If a program must change directory, it should do so deliberately, document the change, and, where appropriate, restore the original directory with defer when the work is done, which is the temporary-state pattern from the previous chapter. Explicit paths are easier to reason about than a changing reference point, and they make file code more predictable, especially in larger programs where many parts use files. Prefer explicit anchors over changing the shared working folder.

For the programs in this book, a practical approach is to use the current directory for learning and testing, since it makes files easy to find next to your program, and to use the home directory for programs that are meant to persist user data across runs and locations. When you write a learning program, print both directories at startup while you are developing, so that you can see where files will go, and remove those prints when the program is finished, or keep them behind a debug flag.

import Foundation

print("Home: \(manager.homeDirectoryForCurrentUser.path)")
print("Current: \(manager.currentDirectoryPath)")

Section 23: Reading Files Safely with guard

Guard is a natural partner for file reading, because file operations have requirements that must hold before the risky work begins, such as a non-empty file name, an existing file, and a valid encoding. A file-reading function that starts with guards for these requirements reads as a checklist, and each guard's failure produces a clear message and an early exit, which is far cleaner than nesting the read inside several ifs. For example, a function might guard that the file name is not empty, guard that the file exists, and only then attempt the read inside a do block, with the read's own errors caught separately. This division is clean, because guards handle the checkable requirements, while do-catch handles the unpredictable failures, and readers can tell which is which at a glance. Guard-based file functions are therefore both safer and more readable than their nested counterparts.

A common guard pattern for file reading is to validate the file name first, since an empty or malformed name will certainly fail, and failing fast with a message like "File name is empty" is better than attempting a read and catching a confusing error. Another guard pattern is to check existence, as in an earlier section, and to decide whether a missing file means "start fresh" or "cannot continue," with the guard's message reflecting that decision. A third pattern is to guard the loaded content after reading, such as checking that the text is not empty before processing it, since an empty file may mean "no data yet" rather than a valid empty dataset, depending on the program. These guards, placed at the natural points in the function, turn a file reader into a series of explicit decisions, each with a clear outcome, which is exactly the clean code shape from the previous chapter applied to files.

Guard also helps when processing the contents of a file, especially in loops over lines, where each line must meet certain requirements before it can become a record. A loop that guards each line's field count and continues past malformed lines, with a message naming the line number, is robust and readable, since the main processing code below the guard works only with valid lines. Without guard, the same loop would nest the processing inside ifs, adding indentation and hiding the main work, which is the staircase problem you learned to flatten. Guard with continue is therefore the idiomatic way to filter lines during loading, and it pairs beautifully with the line-processing patterns in this chapter. When you write a loader, look for every "if this line is valid, then process it" and consider whether "guard this line is valid, else continue" would flatten it.

There is a limit to guard in file code, which is that guard cannot handle failures that are only discovered by attempting the operation, such as a permission error or a disk error, since those require trying and catching. Guard is for requirements you can check in advance, while do-catch is for failures you can only discover by trying, and using each for its proper role keeps file functions clear.

import Foundation
func loadText(named name: String) -> String? {
    guard !name.isEmpty else {
        print("File name is empty")
        return nil
    }
    return try? String(contentsOfFile: name, encoding: .utf8)
}

Section 24: Cleaning Up with defer When Files Are Open

When a program opens a file for direct handling, rather than using the simple whole-file read and write operations, it must close the file when done, and defer is the safest way to guarantee that close. Whole-file operations in Swift handle opening and closing internally, so they do not need defer, but lower-level file handles, which you will meet when appending efficiently or streaming large files, require explicit closing, and forgetting to close can lock the file or leak resources. The pattern is the one from the previous chapter: open the handle, immediately defer its close, and then work with the file, knowing that every exit, including early returns and errors, will run the close. This pattern should be written as a reflex whenever you open a handle, because the cost of forgetting is a resource leak that may only appear after many runs. Defer turns a fragile manual cleanup into a guarantee, which is exactly what file handles need.

Defer also helps with temporary files and temporary state during file work, such as a function that creates a temporary file, processes it, and then moves it into place as the final file. The temporary file should be deleted if the processing fails, so that a failed run does not leave clutter, and a defer that deletes the temporary file on failure, or that cleans up on all exits after the move is handled, ensures tidiness. A common pattern is to defer deletion of the temporary file, and then, on success, move it and cancel the deletion by tracking success with a flag, although this pattern requires care to avoid deleting the moved file. Simpler patterns, such as deferring deletion and moving only after processing completes, can achieve the same safety with less complexity, and they are preferable while learning. The key idea is that defer manages the temporary file's lifetime, so that no exit path leaves it behind unintentionally.

Another file cleanup case is restoring state that file work temporarily changes, such as the current directory, if a function changes directory to work in a project folder and must restore it afterwards. A defer that restores the original directory, written immediately after the change, guarantees restoration on every exit, which prevents later file operations from accidentally using the wrong folder. This is the temporary-state pattern from the previous chapter, applied to file work, and it shows how defer generalises beyond closing handles to any temporary change that file code makes. When you write file functions that change shared state, even briefly, ask whether a defer should restore it, and write the defer before the work that depends on the change. That habit prevents a class of bugs where one function's temporary change leaks into another function's file operations.

For the simple whole-file operations used most in this chapter, defer may seem unnecessary, since those operations clean up internally, and that observation is correct, but it should not lead you to ignore defer in file code altogether. Defer becomes essential as soon as you use handles, temporary files, or temporary state, which are the next steps beyond whole-file operations, and learning the pattern now prepares you for those steps.

import Foundation
func processFile() {
    print("File opened")
    defer { print("File closed") }
    print("Processing file")
}

Section 25: Text Encoding: UTF-8 in Plain Words

Text encoding is the system that converts characters, such as letters, digits, and symbols, into bytes for storage in a file, and back again when the file is read, and UTF-8 is the encoding that Swift programs should use by default. Characters in a computer are ultimately numbers, and an encoding defines which numbers represent which characters, so that the letter A, the character é, and an emoji each have a byte representation that can be stored and retrieved. UTF-8 is popular because it handles almost every character in every language, it is compatible with older ASCII text for basic English letters, and it is the standard encoding for the web, JSON, and most modern tools. When you read and write files with UTF-8 on both sides, characters round-trip correctly, which means what you write is what you read back, regardless of language or symbols. Consistency in encoding is the whole secret, and UTF-8 is the consistent choice that works almost everywhere.

Problems arise when reading and writing use different encodings, because the bytes are then interpreted with the wrong mapping, producing strange characters, missing symbols, or outright failures. A file written in one encoding and read as UTF-8 may show replacement characters, which look like question marks in diamonds, or it may fail to decode entirely, depending on how incompatible the encodings are. These symptoms are confusing if you do not know about encoding, since the file looks fine in one program and broken in another, but they are easily explained once you understand that the bytes are being read with the wrong map. The fix is to ensure that both sides agree on UTF-8, and when you receive a file from elsewhere, to check its encoding if it reads incorrectly, rather than assuming the file itself is corrupt. Encoding mismatches are a common cause of "my file looks wrong" reports, and UTF-8 consistency prevents most of them.

Swift makes encoding explicit in its file operations, since String reading and writing take an encoding parameter, usually written as .utf8, which forces you to choose and therefore to think about it. This explicitness is helpful, because it prevents the silent default-encoding bugs that occur in languages where encoding is assumed, and it makes the choice visible in code for future readers. When you see .utf8 in file code, you know exactly how the file's bytes should be interpreted, and when you write file code, you should always write .utf8 explicitly, rather than relying on a default, so that the intention is clear. If you ever need to read a file in a different encoding, such as a legacy file in another system, you can pass that encoding instead, but you should do so deliberately, with a comment explaining why, since non-UTF-8 encodings are the exception in modern programs. Explicit encoding is a small habit that prevents a confusing class of bugs.

Beyond files, UTF-8 matters for JSON, network data, and any text that crosses between programs, which is why learning it in the file chapter prepares you for the data chapters that follow. JSON files are UTF-8 by standard, and Swift's JSON tools assume it, so a file program that already uses UTF-8 will integrate smoothly with JSON in the next chapter.

import Foundation
let text = "Hello, world! Bonjour!"
do {
    try text.write(toFile: "greeting.txt", atomically: true, encoding: .utf8)
    print("Saved as UTF-8")
} catch {
    print("Save failed: \(error)")
}

Section 26: What Happens When a File Is Missing

A missing file is one of the most common file situations, and how a program responds depends on whether the file was expected to exist, which is a design decision that should be made deliberately. If a program loads saved tasks at startup and the file is missing, the most sensible response is usually to start with an empty list, since a missing file on first run simply means nothing has been saved yet, and treating it as an error would punish first-time users. If a program loads a configuration file that it needs to run, and that file is missing, the sensible response is to report the missing path clearly and stop, since continuing without configuration would produce wrong behaviour. The same event, a missing file, therefore means two different things in different programs, and the program's code should reflect its own meaning, with a message that explains the decision. A missing file is not automatically an error, nor automatically harmless, but a situation to interpret.

Swift's whole-file read throws an error when a file is missing, which gives you a natural place to make this interpretation, in the catch block, where you can decide whether to use defaults or to report failure. A catch block that checks for a missing file, or that simply treats any read failure as "start fresh" for optional data, implements the tolerant response, while a catch block that prints the error and stops implements the strict response. For optional data, a convenient pattern is to use try? which turns a throwing read into an optional, giving nil on any failure, and then to use nil-coalescing to supply an empty default, such as an empty string or an empty list. This pattern is concise and clear for optional files, although it hides the reason for failure, so for essential files, a full do-catch that prints the error is better, since the reason matters. Choose the pattern that matches the file's importance, and document the choice.

Checking existence before reading, as in an earlier section, is another way to handle missing files, and it has the advantage of making the missing case explicit before any read is attempted, with a guard message that states the interpretation. The existence check and the catch block can also be combined, with the check handling the expected missing case and the catch handling unexpected failures, such as permission errors, which gives the most robust handling. This layered approach is slightly longer, but it is clearer, because readers can see both the expected case and the unexpected case handled separately, rather than lumped together in a single catch. For important programs, layered handling is worth the extra lines, while for small learning programs, either the check or the catch alone is sufficient, as long as the missing case is handled deliberately. Deliberate handling is the key, not the particular mechanism.

A missing file can also be a symptom of a wrong path, rather than a genuinely absent file, and distinguishing those cases matters for debugging, since the fix for a wrong path is to correct the path, while the fix for an absent file is to create it or start fresh.

import Foundation
let text = (try? String(contentsOfFile: "tasks.txt", encoding: .utf8)) ?? ""
print("Loaded \(text.count) characters")

Section 27: Permissions in Plain Words

Permissions are the rules that say who may read, write, or execute a file, and they exist to protect users' data from accidental or malicious changes by other users or programs. On Unix-like systems, including macOS and Linux, each file has an owner, a group, and permissions for owner, group, and others, each of which may allow reading, writing, or executing, and these permissions are checked by the system before a program's file operation is allowed. A program running as one user cannot read another user's private files, and cannot write to system folders it does not own, which is a security feature, not a bug, even though it can frustrate a programmer whose code fails with a permission error. Understanding permissions helps you interpret those errors correctly, as "the system is protecting this file" rather than "my code is wrong," and it guides you to fix the problem by choosing an appropriate location or by requesting access, rather than by forcing the operation. Permissions are the file system's way of enforcing boundaries between users and programs.

Swift's FileManager can check whether a file is readable or writable, through methods that return true or false, and these checks let a program test permissions before attempting an operation, with a clear message when access is denied. For example, a program that needs to write to a folder can check writability first, and if the folder is not writable, it can tell the user to choose a different folder or to change permissions, rather than failing mysteriously during the write. These checks are not guarantees, since permissions can change between the check and the operation, but they handle the common case gracefully and improve messages. As with existence checks, permission checks plus error handling together give robust behaviour, with the check handling the expected denial and the catch handling the unexpected failure. Permission-aware code is polite code, because it respects the system's boundaries and explains denials to users.

Common permission problems for beginners include trying to write to a system folder, trying to read another user's files, and running a program from a folder where it lacks write access, such as a read-only location or a folder owned by someone else. The fix for most of these is to choose a location the program is allowed to use, such as the user's home directory or a temporary folder, rather than to change system permissions, which can weaken security. Changing permissions to make a program work, such as making a system folder writable, is usually the wrong fix, since it opens a security hole for a convenience, and it should be avoided unless you understand the consequences. A better fix is to move the program's data to a place it already owns, which is both safer and more portable, since other users' systems will have the same ownership rules. Respect permissions, work within them, and your programs will be both safer and more reliable.

Permissions also matter for programs that handle sensitive data, since a file containing private information should not be readable by everyone, and a program should set appropriate permissions when it creates such files, or store them in a private folder.

import Foundation
let manager = FileManager.default
print("Readable: \(manager.isReadableFile(atPath: "tasks.txt"))")
print("Writable: \(manager.isWritableFile(atPath: "tasks.txt"))")

Section 28: Large Files: Reading in Chunks

Large files pose a problem for whole-file reading, because loading an entire file into memory at once can use a great deal of memory, slow the program, or even fail if the file is larger than available memory. A file of a few megabytes is fine to load whole, but a file of hundreds of megabytes, such as a long log or a large dataset, deserves a chunked approach, where the program reads a piece, processes it, discards it, and then reads the next piece. Chunking keeps memory usage roughly constant, regardless of file size, since only one piece is held at a time, which makes the program scalable to files far larger than memory. The trade-off is complexity, since chunked reading must handle pieces that split in the middle of a line or record, which requires buffering partial data until the next piece completes it. For most learning programs, whole-file reading is sufficient, but understanding chunking prepares you for real-world large files.

The simplest chunked approach for line-based files is to read the file in blocks of bytes, accumulate the bytes into a buffer, and extract complete lines from the buffer as they become available, carrying any partial line over to the next block. This requires careful handling of line breaks that straddle block boundaries, since a line break may fall exactly at the end of a block, or a multi-byte UTF-8 character may be split across blocks, which complicates decoding. Swift's lower-level file handling, with file handles and data buffers, provides the tools for this, but the code is significantly longer than a whole-file read, and it is easy to introduce bugs in boundary handling. For this reason, chunked reading is an advanced technique that you should learn when you actually need it, rather than using it by default, since its complexity is only justified by large files. The principle, however, is worth understanding now: process a piece, discard it, and repeat, keeping memory flat.

A practical middle ground for moderately large files is to read the whole file but process it line by line without keeping all processed results, such as counting lines or searching for a word, where the program holds the file text but discards each line after processing. This still uses memory for the whole file, but it avoids building a large result collection, which is often the real memory problem, since results can be larger than the input. For counting or searching, you can also process the file's lines as a lazy sequence, which avoids building an intermediate array of all lines, although the file text itself is still loaded. These middle-ground techniques handle many real cases without the full complexity of byte chunking, and they are a good step up from naive whole-file processing. When you meet a file that is slow to process, first ask whether the bottleneck is loading, processing, or storing results, since each has a different fix, and optimising the wrong one wastes effort.

Measuring is the key to deciding whether chunking is needed, because guessing about performance often leads to unnecessary complexity, while measuring reveals the actual bottleneck.

import Foundation
let lines = ["Line 1", "Line 2", "Line 3"]
for line in lines {
    print("Processing: \(line)")
}

Section 29: Saving User Settings in a File

User settings are small pieces of data that customise a program, such as a user's name, a preferred theme, a volume level, or a last-opened file, and saving them in a file lets a program remember a user's preferences across runs. Settings are usually few in number and simple in type, which makes a plain text file with one setting per line, in a key=value format, a natural storage choice for learning programs. A line like "theme=dark" stores a setting named theme with value dark, and loading means splitting each line at the equals sign into a key and a value, storing them in a dictionary, while saving means joining the dictionary's pairs back into lines and writing them. This key-value format is human-readable, easy to edit by hand, and simple to parse, which are exactly the qualities you want for settings, since users and programmers may both need to inspect them. Settings files are a perfect first application of file storage, because they are small, useful, and forgiving.

Loading settings should be tolerant, since a settings file may be missing on first run, may contain unknown settings from a newer version, or may contain a malformed line from hand editing, and none of these should prevent the program from running. A missing file should produce default settings, which are the program's sensible starting values, while unknown settings should be ignored, so that newer settings do not break older programs, and malformed lines should be skipped with a warning, preserving the good settings. This tolerant loading makes settings robust, because it treats the file as a hint about preferences, not as critical data that must be perfect, and it lets a program start even when its settings are damaged. Defaults are therefore an essential part of settings design, since they define what happens when the file is absent or incomplete, and they should be chosen carefully to give a good first-run experience. A program with good defaults feels polished, even on its first run.

Saving settings should be atomic and complete, meaning that the whole settings dictionary is written at once, replacing the old file, so that the file always contains a consistent snapshot, rather than a partial update. Partial updates, such as appending a single changed setting, would duplicate keys and create ambiguity about which value is current, so the snapshot approach is cleaner for settings, even though it rewrites the whole file for a small change. Since settings files are small, rewriting them is cheap, and atomic writing protects against corruption if the program crashes during the save, which is important, because a corrupted settings file should not prevent the program from starting. After saving, a program might reload and verify, or simply trust the atomic write, depending on how critical the settings are, but for learning programs, a simple write with error handling is sufficient. Settings saving is a snapshot operation, not a log, and that distinction guides its design.

Choosing where to store settings matters, since settings should persist for the user but should not clutter their documents, and a dedicated folder, such as a settings folder in the home directory, or the system's application support area for real applications, is appropriate.

let settings = ["theme": "dark", "volume": "80"]
for (key, value) in settings {
    print("\(key)=\(value)")
}

Section 30: A Simple Notes File

A notes file is a practical example that combines many file skills, since it stores a collection of short texts, one per line or one per record, that a user can add to, list, and search. The simplest notes file stores one note per line, which makes adding a note an append operation, listing a read-and-split operation, and searching a read-and-filter operation, all using patterns you have already learned. A note-per-line file is easy to inspect by hand, since each line is a note, and it is easy to edit, since adding or removing a line changes one note, although notes containing line breaks themselves would break the format, which is a limit to note for longer notes. For short, single-line notes, this format is ideal, and it is the basis for many real note-taking tools that store data in plain text, which users value for its portability and simplicity. Plain-text notes are a reminder that simple formats, well used, can be powerful.

Adding a note to a notes file should validate the note first, with guards for an empty note and, if the format requires it, for notes containing line breaks, which would corrupt the one-per-line structure. After validation, appending the note, with a line break, preserves existing notes, which is the correct operation for a growing collection, as opposed to replacing, which would destroy them. A program that adds notes should also report success, such as printing the note and the new total count, so that the user knows the note was saved, rather than wondering whether the append worked. Counting notes after adding, by reading back and counting lines, is a simple verification that also gives the user useful feedback, and it exercises the read-after-write habit from earlier sections. Small feedback messages like this make file programs feel responsive and trustworthy, even when they are simple command-line tools.

Listing notes is a read-and-display operation, where the program reads the file, splits it into lines, skips empty lines, and prints each note with a number, so that users can refer to notes by number for later operations such as deletion. Numbering from one, for human readers, while Swift indexes from zero, is a detail to handle carefully, since an off-by-one error in numbering will confuse users when they try to delete note three and the wrong note disappears. A helper that loads notes into an array, with empty lines filtered out, can be shared by listing, searching, and deleting, which removes duplication and keeps the operations consistent, since they all see the same list. Sharing a loader helper is the helper pattern from the clean code chapter applied to files, and it makes the notes program shorter and more reliable. When several operations need the same data, a shared loader is almost always the right design.

Searching notes is a filter operation, where the program loads the notes, keeps those containing a search word, and prints the matches with their numbers, which lets users find notes without reading the whole file. Searching should usually be case-insensitive, since users do not remember the exact capitalisation of a note they wrote, and Swift's string searching can be made case-insensitive with appropriate options or by comparing lowercased versions.

import Foundation

    guard !note.isEmpty else { print("Note is empty"); return }
    print("Adding note: \(note)")
}

Section 31: Searching Inside a File

Searching inside a file means finding lines or passages that contain a particular word or phrase, without loading the whole file into a complex structure, and it is a fundamental file operation for logs, notes, and documents. The simplest search reads the file as text, splits it into lines, and keeps the lines that contain the search term, using Swift's contains method, which checks whether one string appears inside another. This simple search is case-sensitive by default, which means it distinguishes "Milk" from "milk," and for user-facing search, converting both the line and the term to lowercase before comparing makes the search case-insensitive and more forgiving. Reporting matches with their line numbers, as with line processing earlier, helps users locate the matches in the original file, especially in long files where a matching line alone, without context, may be hard to find. Simple line search is fast enough for small files, and it is the pattern behind many command-line search tools in their basic form.

More advanced search might need to find whole words rather than substrings, since a search for "cat" should not match "category" or "concatenate" if the user meant the whole word cat, and whole-word search requires checking word boundaries, not just containment. Swift's string tools can help here, by splitting lines into words and checking for exact word matches, or by using more advanced pattern matching, which is beyond this section but worth knowing exists. Similarly, searching for a phrase, with spaces, is just containment of the whole phrase, which the simple method handles, while searching with wildcards or patterns requires regular expressions, which are a powerful but complex tool for later learning. For this chapter, substring search with case-insensitivity and line numbers covers the common cases, and it teaches the core idea: load lines, filter by a test, and report matches. More powerful search can be built on this foundation when needed, without changing the basic shape.

Searching large files raises the same memory considerations as reading them, since loading a whole large file to search it may be wasteful, while a chunked or streaming search processes lines as they are read and discards non-matches immediately. For small files, whole-file search is fine, but for log files with millions of lines, streaming search is essential, and it follows the chunked pattern from the large-file section, with the addition of a match test per line. A streaming search also lets a program report matches as they are found, rather than waiting until the whole file is processed, which feels more responsive for long searches. The choice between whole-file and streaming search, like the choice for reading, depends on file size and on whether responsiveness matters, and measuring will tell you when the simple approach is insufficient. Start simple, measure when files grow, and upgrade the search only when the evidence demands it.

Search results should be presented helpfully, with the matching lines, their numbers, and, when useful, a count of total matches, so that users know whether the search succeeded and how many places matched. A search that prints matches without a summary can leave users unsure whether they saw all matches, especially if the output scrolls, while a summary line like "Found 3 matches for 'milk'" gives closure and confidence.

let lines = ["Buy milk", "Call Ana", "Buy bread"]
let term = "buy"
for line in lines {
    if line.lowercased().contains(term) {
        print("Match: \(line)")
    }
}

Section 32: Counting Words and Lines

Counting words, lines, and characters in a file is a classic file task, familiar from tools that report document statistics, and it teaches careful text processing with simple operations. Counting lines is the easiest, since it is the number of pieces produced by splitting the text on line breaks, with care for the trailing empty piece that a final line break produces, which should not count as an extra line. A file ending with a line break has the same number of lines as the same file without a final break, in human terms, even though the split produces one extra empty piece, so a line counter should filter out a trailing empty piece, or count line breaks themselves, depending on the definition it uses. Defining what counts as a line, and handling the trailing break consistently, is a small but important detail, since different definitions give different answers for the same file, and users will notice the discrepancy. State your definition, handle the trailing break, and your line counts will match expectations.

Counting words requires splitting the text into words, which is less straightforward than it sounds, because words are separated by spaces, tabs, and line breaks, and sometimes by punctuation, depending on the definition. A simple word counter splits on whitespace, which is the set of spaces, tabs, and line breaks, and counts the resulting pieces, filtering out empty pieces that arise from multiple consecutive spaces. This definition counts "hello, world" as two words, since the comma stays attached to "hello," but does not create a separate word, which matches most people's intuition for simple text. More precise word counting, which strips punctuation or handles hyphenated words specially, is possible, but it requires decisions about what counts as a word, and those decisions should be documented, since different tools count differently. For learning purposes, whitespace splitting with empty filtering is a clear, defensible definition, and it produces counts that match common tools for ordinary prose.

Counting characters is simpler, since it is the length of the text, although even here there is a subtlety, because Swift counts characters as human-perceived characters, which may differ from byte counts, especially for emoji or accented characters that use multiple bytes in UTF-8. A file's byte size, which you can get from FileManager, will differ from its character count when non-ASCII characters are present, and both numbers are useful for different purposes: character count for document statistics, byte size for storage and transfer. Reporting both, with clear labels, avoids confusion, since a user who sees a character count that differs from a file size may wonder which is wrong, when both are correct under different definitions. Definitions matter in counting, and the best counters state theirs, so that users can interpret the results. This attention to definitions is a general lesson, since many programming tasks hinge on defining terms precisely.

Counting tasks also combine nicely with file operations, since a program can read a file, compute its line, word, and character counts, and report them in a summary, which is a complete small application.

let text = "Buy milk\nCall Ana"
let lines = text.components(separatedBy: "\n")
print("Lines: \(lines.count)")

Section 33: Sorting Lines in a File

Sorting lines in a file means rearranging them into order, usually alphabetical, so that a jumbled list becomes a tidy, searchable one, and it is a common file operation for lists of names, tasks, or words. The pattern is the familiar load-process-save cycle: read the file, split it into lines, sort the lines with Swift's sorted method, join them back with line breaks, and write the result, replacing the original or writing to a new file. Sorting is case-sensitive by default, which means uppercase letters sort before lowercase ones, so a list containing both "banana" and "Apple" will sort with "Apple" first, which may surprise users who expect case-insensitive alphabetical order. For user-facing sorting, comparing lowercased versions, or using a localised comparison, produces the order users expect, where "apple" and "Banana" sort by their letters regardless of case. Choosing the sort order deliberately, and documenting it, is part of sorting well, since different orders suit different audiences.

Sorting also raises the question of stability and of what to do with empty lines, duplicates, and whitespace, since these details affect the result in ways users will notice. Empty lines, if not filtered out, will sort to the top, since an empty string sorts before any non-empty one, which may be undesirable, so filtering empty lines before sorting is usually wise. Duplicates will be preserved by sorting, since sorting rearranges but does not remove, which is correct if duplicates are meaningful, but if duplicates are mistakes, they should be removed as a separate step, which the next sections will not cover in depth but which uses a set or a filter. Whitespace at the edges of lines affects sorting, since a line starting with a space sorts differently from the same line without it, so trimming lines before sorting, or sorting trimmed versions while preserving originals, is a consideration. These details show that sorting is not just calling a method, but preparing the data so that the method's result matches user expectations.

Writing the sorted result back requires care, since replacing the original file destroys the original order, which may be wanted for other reasons, such as chronological order for a log. A safer pattern is to write the sorted lines to a new file, such as a file with "-sorted" in its name, leaving the original intact, so that users can compare and choose, or to back up the original before replacing it, as with other overwrites. For learning programs, replacing is acceptable if the original order is not important, but the habit of considering whether to preserve the original will serve you well when the data matters. Sorting is a transformation, and transformations should be reversible or backed up, unless the original is genuinely disposable, which is a judgement to make deliberately, not by default. When in doubt, write to a new file, since disk space is cheap and lost order is expensive.

Sorting lines also demonstrates how collection operations combine with file operations, since the file provides the lines, the array provides sorting, and the file receives the result, with each stage using tools from different chapters.

let lines = ["banana", "Apple", "cherry"]
let sorted = lines.sorted { $0.lowercased() < $1.lowercased() }
print(sorted)

Section 34: Merging Two Files

Merging two files means combining their contents into a single file, which is useful for joining logs from different days, combining lists from different sources, or assembling a document from parts. The simplest merge reads both files, concatenates their texts or their lines, and writes the combined result to a new file, preserving the order of the sources, such as all of file A followed by all of file B. This simple concatenation works when the files contain independent records, such as log entries or notes, where order within each file matters but the files themselves are simply sequential. A merge should handle missing files gracefully, with a clear message naming the missing file, and it should handle empty files by treating them as contributing nothing, rather than failing, since an empty source is a valid, if uninteresting, merge input. Concatenation is the foundation of merging, and it is sufficient for many real tasks, from combining logs to joining lists.

More complex merges require interleaving or deduplication, such as merging two sorted lists into one sorted list, or merging two task lists while removing duplicates, which are collection operations applied to loaded lines. A sorted merge, for example, loads both files' lines, combines them into one array, sorts the combined array, and writes it, which is a simple extension of the sorting pattern, while a deduplicating merge additionally removes duplicates, using a set or a filter that keeps only the first occurrence of each line. These extensions show how merging is not a single operation, but a family of operations that combine loading, collection processing, and saving in different ways, depending on what the merged result should mean. When you design a merge, first ask what the result should contain and in what order, and then choose the collection operations that produce that result, rather than assuming concatenation is always right. Design the result, then implement it, which is a general principle for file operations.

Merging also raises questions about headers and formats, since files with headers, such as CSV files, should contribute their header only once to the merged file, not once per source, or the merged file will contain header rows in the middle of its data. A CSV merge should therefore read both files, skip the header of the second and later files, and combine only the data rows, with a single header at the top, which requires knowing whether each file has a header and handling it explicitly. Similarly, files with different formats should not be merged blindly, since combining a pipe-separated file with a comma-separated file produces a file that neither format's reader can parse, which is worse than keeping them separate. Merging is only sensible when the sources share a format and a meaning, and checking that compatibility, even informally, is part of merging responsibly. Format-aware merging is a step beyond simple concatenation, and it matters for real data.

A merged file should be verified after writing, by reading it back and checking its line count against the sum of the sources' counts, adjusted for headers or duplicates removed, since a mismatch signals a bug in the merge.

let b = ["Task 3"]

Section 35: Backing Up a File Before Changing It

Backing up a file means copying it to a safe location before changing it, so that if the change goes wrong, the original can be restored, and it is one of the most important data-protection habits in programming. The backup can be a simple copy in the same folder with a name like tasks-backup.txt, or a copy in a dedicated backups folder with a date in its name, such as tasks-2026-10-30.txt, which preserves multiple versions over time. The key steps are: copy the original, verify that the copy exists and has the expected size, and only then proceed with the change, so that there is never a moment when the only copy is being modified without a spare. This order matters, because a change that fails halfway, or that turns out to be a mistake, is recoverable only if the backup was made before the change, not after. Backing up is cheap, while losing data is expensive, so the habit should be automatic for important files.

Naming backups well helps, because a backup folder full of files named backup1, backup2, and backup3 is hard to navigate, while names including the original file's name and a date or version, such as tasks-2026-10-30-0930.txt, tell you immediately which file and when. Dates in backup names should use a sortable format, such as year-month-day, so that listing backups alphabetically also lists them chronologically, which makes finding the latest backup easy. For programs that back up automatically, rotating backups, such as keeping only the last five, prevents the backup folder from growing without limit, although rotation itself must be careful not to delete the only good backup. For learning programs, a single backup with a clear name is a good start, and rotation can be added later when backup accumulation becomes a real issue. Good backup names are a small detail that makes recovery much less stressful.

Backing up before overwriting is especially important for the load-process-save cycle, where a program reads a file, processes its contents, and writes the result back, replacing the original, since a bug in processing could corrupt the data and the original would be lost. A program that backs up before the save step can recover from processing bugs by restoring the backup, while a program that overwrites directly cannot, which is why the backup step belongs in the cycle, not as an afterthought. The backup itself should be written atomically and verified, since a failed backup that is assumed to have succeeded gives false confidence, which is worse than no backup at all, because it encourages risky changes. Verification can be as simple as checking that the backup file exists and that its size matches the original, which takes a few lines but proves the safety net is real. A verified backup is a true safety net, while an assumed backup is a hope.

Restoring from a backup is the other half of the habit, and it should be practised, not just theorised, since a backup that has never been restored may be unusable for reasons that only restoration reveals, such as a wrong path or a corrupted copy.

import Foundation
let manager = FileManager.default
do {
    try manager.copyItem(atPath: "tasks.txt", toPath: "tasks-backup.txt")
    print("Backup ready")
} catch {
    print("Backup failed: \(error)")
}

Section 36: File Extensions and Types

A file extension is the suffix after the last dot in a file name, such as .txt for text, .csv for comma-separated values, or .json for JSON data, and it hints at the file's format, although it does not guarantee it. Extensions help humans and programs guess how to interpret a file, since a .txt file is likely plain text, a .csv file is likely a table, and a .json file is likely structured data, but the actual contents determine the truth, and a file can be misnamed, either by mistake or deliberately. Programs should therefore treat extensions as hints, not as proof, and should validate contents when it matters, rather than trusting the extension blindly. For example, a program that reads a .txt file should still handle lines that do not match its expected format, since the extension does not ensure the format. Extensions are useful labels, but they are not guarantees, and careful programs remember that distinction.

Choosing extensions for files your programs create is a courtesy to users and to other programs, since a clear extension lets a user double-click a file and open it in an appropriate application, and lets other programs recognise it without inspecting its contents. A notes file should use .txt, a table should use .csv, and structured data should use .json, following the conventions that users and tools already understand, rather than inventing new extensions for standard formats. Inventing a new extension for a standard format, such as .notes for plain text, may feel distinctive, but it breaks the user's expectations and prevents other tools from opening the file correctly, which is a cost without a benefit. Follow conventions for standard formats, and reserve custom extensions for genuinely custom formats that no standard covers, documenting them clearly when you do. Convention-following is a form of interoperability, since it lets your files participate in the wider ecosystem.

Swift provides helpers for working with extensions, such as getting a path's extension or checking whether a file name ends with a particular extension, which are useful when filtering listings or validating inputs. A program that lists a folder for notes files can filter for .txt, as in an earlier section, and a program that accepts a file name from a user can check its extension and warn if it seems wrong, such as a .json extension for a plain-text notes file. These checks are hints, not strict validation, since a user may legitimately use an unusual extension, but a warning can catch typos, such as saving a CSV file as .txt by mistake, which would confuse later readers. Extension checks should therefore be gentle, warning rather than refusing, unless the program has a strict reason to require a particular extension. Gentle checks catch mistakes without frustrating legitimate uses.

Extensions also interact with the file system and with user interfaces, since some systems hide extensions by default, or associate extensions with applications, which affects how users perceive files. A file named tasks, without an extension, may be harder for users to open, since the system does not know which application to use, while tasks.txt is immediately recognisable as text.

Section 37: Avoiding Data Loss When Writing

Data loss during writing happens when a program overwrites, truncates, or corrupts a file, leaving the user with less or worse data than before, and avoiding it requires a combination of habits that you have met throughout this chapter. The first habit is to back up before overwriting important files, so that a failed or mistaken write can be undone by restoring the backup, which is the safety net from the previous section. The second habit is to write atomically, so that a failure during writing leaves the original intact, rather than half-written, which is the flag you learned in the writing section. The third habit is to verify after writing, by checking existence, size, or contents, so that a silent failure does not go unnoticed until the data is needed and found missing. Together, backup, atomic writing, and verification form a triple defence against data loss, and each layer covers failures that the others miss. No single habit is enough on its own, but together they make writing robust.

Another data-loss risk is writing to the wrong path, such as a path built from a mistyped name or a wrong folder, which can overwrite an unrelated file or create a file in an unexpected place while leaving the intended file unchanged. Guard checks on file names, printing the path before writing during development, and using helper-built paths from known folders, all reduce this risk, since they make the destination explicit and checkable. A program that writes to a path derived from user input should validate that path, ensuring it is inside an expected folder and has an expected extension, to prevent accidental or malicious overwrites outside its area. Path validation is a security habit as well as a safety habit, since it prevents a program from being tricked into damaging files it should not touch. Explicit, validated paths are a cornerstone of safe writing, and they deserve the same care as the data being written.

A further risk is losing data through logic errors in the load-process-save cycle, such as filtering out records that should have been kept, or joining lines incorrectly, so that the saved file is missing data even though the write itself succeeded. These logic errors are not file-system failures, but program bugs that manifest as data loss, and they are best prevented by testing the cycle with known data, including edge cases, and by comparing the saved result with the expected result before replacing the original. Writing the processed result to a new file first, verifying it, and only then replacing the original, adds a checkpoint where logic errors can be caught before they destroy data, which is a safer variant of the direct replace cycle. For important data, this write-verify-replace pattern is worth its extra steps, since it turns a destructive operation into a reviewed one. When the data matters, slow down the cycle and add checkpoints, rather than overwriting in one bold step.

Finally, data loss can occur when a program crashes or is closed during writing, which is why atomic writing and backups matter, but also why programs should save frequently and incrementally, rather than holding unsaved changes for a long time.

import Foundation
do {
    try "Important data".write(toFile: "data.txt", atomically: true, encoding: .utf8)
    print("Saved safely")
} catch {
    print("Save failed, original untouched: \(error)")
}

Section 38: Atomic Writes in Plain Words

An atomic write is a write operation that either completes fully or leaves the original file completely unchanged, with no in-between state where the file is half-written, and it is one of the most valuable safety features in file programming. The word atomic here means indivisible, as in an operation that cannot be split into a partial result, and Swift provides it through the atomically flag in its write operations, which you met earlier. When atomically is true, Swift writes the new contents to a temporary file first, and only when that temporary write succeeds does it replace the original file with the temporary one, in a single system step that is itself atomic. If the program crashes, loses power, or encounters an error during the temporary write, the original file remains untouched, since the replacement step never happens, which is exactly the guarantee you want for important data. Atomic writes turn a risky overwrite into a safe swap, and they should be your default for file writing.

Understanding why non-atomic writes are risky helps you appreciate the atomic guarantee, since a direct write modifies the original file in place, byte by byte, and a failure halfway leaves a file that is part old and part new, which is often worse than either version alone. A half-written task list, for example, might contain some old tasks and some new ones, with a truncated line in the middle, and a program reading it afterwards cannot tell which parts are trustworthy, so it may load corrupt data or fail entirely. A half-written settings file might contain a setting with a missing value, causing the program to misbehave on its next run, long after the original failure, which makes the bug hard to trace. Atomic writes prevent this entire class of corruption, by ensuring that readers always see either the complete old version or the complete new version, never a mixture. That guarantee simplifies reasoning about files, since you can trust that any file you read is a complete version, not a fragment.

Atomic writes are not magic, and they have limits worth knowing, since they protect against failures during the write itself, but not against logic errors in the data being written, nor against failures after the replacement, such as a later bug corrupting the new version. If your program computes the wrong data and then atomically writes it, the file will contain the wrong data completely, which is still a bug, although it is at least a consistent wrong version that can be restored from a backup. Atomic writes also do not protect against two programs writing the same file simultaneously, since each may atomically replace the file, with the last writer winning and the first writer's changes lost, which is a concurrency problem that requires locking or a database. For single-program use, however, atomic writes are a strong and simple protection, and they combine well with backups, which cover logic errors and provide a history that atomic writes alone do not. Use atomic writes always, backups for history, and stronger tools for shared data.

import Foundation
do {
    try "New version".write(toFile: "notes.txt", atomically: true, encoding: .utf8)
    print("Atomically saved")
} catch {
    print("Save failed, old file intact: \(error)")
}

Section 39: Logging Events to a File

Logging means recording events, such as actions taken, errors encountered, or milestones reached, in a file, so that later you can review what a program did, when, and why. A log file is usually an append-only file, where each event adds a line, preserving history in chronological order, which makes it invaluable for debugging, auditing, and understanding user behaviour. Each log line typically includes a timestamp, a level such as info, warning, or error, and a message describing the event, so that a line like "2026-10-30 09:00 info: Task added: Buy milk" tells you when, how serious, and what happened, in a single glance. Logs are written by programs for programmers and for users who need to diagnose problems, and they are read after the fact, often when something has gone wrong, which is why clarity and completeness in log lines matter. A good log is a diary that helps future investigators reconstruct the past.

Writing log lines uses the append pattern from earlier, since each new event should add to the log, not replace it, and the append should include a line break, so that each event occupies its own line. A helper function for logging, which takes a level and a message, formats them with a timestamp, and appends the result, centralises log formatting and makes logging calls short and consistent throughout a program. Without a helper, each logging site would format its own line, leading to inconsistent timestamps and levels, which makes logs harder to read and search, while a helper ensures every line follows the same pattern. The helper can also handle failures gracefully, such as ignoring a log write failure rather than crashing the program, since logging should never break the main work it is recording, which is an important design principle. Logging is a supporting activity, and it must not become a source of failures itself.

Timestamps in logs deserve attention, because they let you order events and measure intervals, such as how long a task took or when an error first appeared, which are crucial for debugging. Swift's date formatting, which you will learn in depth in a later chapter, can produce timestamps in a sortable format, such as year-month-day hour:minute:second, which sorts chronologically when lines are sorted alphabetically, a useful property for log files. For this chapter, a simple date string is sufficient, and the key point is to include a timestamp on every log line, consistently, so that the log's chronology is explicit. Levels also matter, since they let readers filter logs for errors only, or for warnings and above, which is essential when a log grows large, and a program that logs everything at the same level produces a file that is hard to search. Info, warning, and error are a minimal, useful set of levels, and using them consistently makes logs navigable.

Log files can grow without limit, since a busy program may log many events, so rotation, which means starting a new log file periodically and archiving or deleting old ones, is a practical concern for long-running programs. For learning programs, a single log file is fine, but for real programs, rotation by size or by date prevents a log from filling the disk, which would itself cause failures.

Section 40: Reading a Log Back

Reading a log back means loading a log file and making sense of its lines, usually by filtering, searching, or summarising, to answer questions such as what went wrong, when it first happened, or how often an event occurred. The basic pattern is familiar: read the file, split it into lines, and process each line, but log processing adds the step of parsing each line's structure, such as extracting its timestamp, level, and message, so that filtering by level or by date becomes possible. A simple log reader might filter for lines containing "error," which finds all errors without needing full parsing, while a more advanced reader might split each line into its parts and filter by level exactly, which is more precise. The choice depends on how consistently the log was written, since a consistently formatted log can be parsed precisely, while an inconsistently formatted log requires looser searching. Well-formatted logs reward their writers by being easy to read back, which is another reason to use a logging helper.

Filtering logs by level is a common reading task, since a user investigating a failure wants errors first, without wading through informational lines, and a reader that keeps only lines with a given level, or with a level at or above a threshold, serves that need. Implementing level filtering requires knowing the order of levels, such as info below warning below error, so that a filter for "warning and above" keeps warnings and errors but not info, which is a simple ordering that can be represented with numbers or with a comparison. Filtering by date or by time range is another common task, since a user may want only today's logs, or logs from the hour when a failure occurred, and this requires parsing timestamps, which is covered in the dates chapter, but which can be approximated with string comparison when timestamps use a sortable format. Sortable timestamps, such as year-month-day, allow string comparison to work for date filtering, which is a practical benefit of choosing that format in the first place. Log design and log reading are linked, since design choices made when writing determine what reading can do easily.

Summarising logs is a further reading task, where a program counts events by level, finds the most frequent errors, or lists the first and last occurrences of each event type, turning a long log into a short report. Summarising uses the counting and grouping tools from earlier chapters, such as dictionaries that map an event type to its count, and it transforms raw history into insight, which is the purpose of logs beyond simple debugging. A summary like "Errors: 5, Warnings: 12, Info: 200" gives an immediate sense of a program's health, while a list of the most frequent errors points to the problems worth fixing first. Building a log summariser is an excellent practise project, since it combines file reading, line parsing, dictionary counting, and reporting, all skills from this book, into a tool that is genuinely useful for real programs. Logs are not just for reading line by line, but for analysing in aggregate.

Section 41: A Tiny Task List Stored in a File

A tiny task list stored in a file is a complete, useful application that brings together the file skills of this chapter in a single, coherent design. The design is simple: each task is one line in a text file, with a done marker, such as "[ ] Buy milk" for an open task and "[x] Buy milk" for a completed one, which is human-readable and easy to parse. Adding a task appends a new "[ ]" line, listing reads and prints the lines with numbers, completing a task loads the lines, changes the marker on the chosen line, and writes the lines back, and deleting a task loads, removes the chosen line, and writes back. This design uses every major file operation, appending, reading, writing, and replacing, in a small program that a user can actually use, which makes it an ideal capstone for the chapter's first half. It also previews the SwiftDay capstone at the end of the book, where a fuller task manager will be built, so learning this tiny version now lays groundwork for later.

The task file's format deserves a brief design note, since the "[ ]" and "[x]" markers are visible, meaningful, and easy to parse by checking the start of each line, which is why they are popular in plain-text task systems. A line starting with "[ ]" is open, a line starting with "[x]" is done, and any other line is malformed and should be reported or skipped during loading, with its line number, so that hand-editing mistakes do not silently corrupt the list. The task title itself follows the marker, after a space, and titles should be trimmed of extra spaces, since hand editing may add them, while titles containing line breaks should be rejected on adding, since they would break the one-line-per-task format. These small format rules, documented in a comment, turn a loose text file into a reliable task store, and they show how format design is part of program design, not an afterthought. A format that is easy to read, easy to parse, and tolerant of minor variation is a good format.

Implementing the task list as a set of functions, each with one job, follows the clean code habits: a loader that returns an array of task lines, a saver that writes an array back, an adder that appends, a lister that prints with numbers, and a completer that updates a marker, all sharing the loader and saver helpers. Sharing helpers prevents duplication, since listing, completing, and deleting all need to load, and completing and deleting both need to save, and it ensures consistency, since every operation sees the same loaded data. Guards in each function handle edge cases, such as an empty title on adding, a missing file on listing, or an out-of-range number on completing, each with a clear message, so that the program behaves politely even when misused. This function structure is the same one you will use for larger programs, scaled down to a tiny example, which is why it is worth studying as a model, not just as a task list.

let tasks = ["[ ] Buy milk", "[x] Call Ana"]
for (index, task) in tasks.enumerated() {
    print("\(index + 1). \(task)")
}

Section 42: Loading Tasks at Startup

Loading tasks at startup means reading the task file when a program begins, so that the user's previous tasks are available immediately, without needing to be re-entered. The startup load should be tolerant, since the file may be missing on first run, in which case the program should start with an empty list and a friendly message, rather than an error that alarms a new user. It should also handle a malformed file gracefully, by skipping bad lines with warnings and loading the good ones, so that one typo does not destroy access to all tasks, which is the tolerant-loading principle from earlier sections. After loading, the program should report how many tasks were loaded, and how many lines were skipped if any, so that the user knows the state of their data at a glance. A startup load that is silent, tolerant, and informative sets a welcoming tone for the whole session, and it is the first thing a user experiences, so it deserves care.

The startup load is also a good place to validate the loaded data, such as checking that each task line has a valid marker and a non-empty title, and normalising it, such as trimming extra spaces, so that later operations can assume clean data. Validation at load time, rather than at each use, follows the guard-at-the-door principle, since it checks data once, when it enters the program, and then trusts it thereafter, which simplifies every later function. If validation finds problems, it should report them, but it should not prevent startup, unless the problems are so severe that the data is unusable, in which case a clear error and a suggestion to restore from backup is better than starting with corrupt data. This balance between tolerance and strictness depends on the data's importance, and for a personal task list, tolerance with warnings is usually right, since tasks are important but not critical, and losing access to all of them over one bad line would be worse than skipping that line. Design the startup load for the user's benefit, not for strictness alone.

Startup loading also interacts with the program's structure, since the loaded tasks need to be stored somewhere accessible to the rest of the program, such as a variable in the main flow, or a task manager object that holds the list and provides operations on it. For a simple command-line program, a top-level variable holding the loaded array is sufficient, and functions for adding, listing, and completing can take that array, modify it, and save it, although passing it around explicitly can become tedious as the program grows. For larger programs, a dedicated type that loads on creation and saves on change encapsulates the file handling, so that the rest of the program works with tasks, not with files, which is a cleaner separation. This encapsulation is a preview of the design ideas in later chapters, where types will manage their own persistence, and it shows how file code can be hidden behind a clean interface. Start with a simple variable, and encapsulate when the program grows, which is a natural progression.

import Foundation
let loaded = (try? String(contentsOfFile: "tasks.txt", encoding: .utf8)) ?? ""
let tasks = loaded.components(separatedBy: "\n").filter { !$0.isEmpty }
print("Loaded \(tasks.count) tasks")

Section 43: Saving Tasks on Exit

Saving tasks on exit means writing the current task list to its file when the program finishes, so that changes made during the session are not lost, and it is the counterpart to loading at startup. The simplest exit save writes the whole list, joined by line breaks, to the file atomically, replacing the old version, which is correct for a snapshot-style task list where the file holds the current state. Exit saving should be reliable, which means handling write errors with a clear message, and, for important data, backing up before overwriting, so that a failed save does not destroy the previous version. It should also be complete, meaning that all changes, including additions, completions, and deletions, are included, which is naturally true if the program works on a single in-memory list and saves that list wholesale. A program that saves only some changes, such as additions but not completions, will confuse users when their completions vanish, so the save must cover the whole list.

Relying solely on exit saving has a risk, which is that a crash, a forced quit, or a power loss before exit will lose all changes made during the session, since the save never happens. This is why many programs save after each change, or autosave periodically, in addition to saving on exit, so that the window of unsaved work is small. For a learning task program, saving after each change is simple to implement, since each operation that modifies the list can call the saver immediately, and it makes exit saving almost redundant, although keeping an exit save as a final safety net is still harmless. The combination, save on change plus save on exit, gives the best protection with little extra code, since the saver helper is shared, and it follows the save-early, save-often habit from the data-loss section. Users should not need to remember to save, and a program that saves promptly respects their work.

Exit saving also needs to handle the case where the user made no changes, in which case rewriting the file is unnecessary but harmless, since it produces the same contents, although it does update the file's modification time, which may confuse backup tools that track changes by time. A program can avoid unnecessary writes by tracking whether the list changed, with a simple flag that is set on any modification and checked before saving, which is a small optimisation that also avoids needless disk activity. This dirty flag pattern is common in real programs, where saving is expensive or where modification times matter, and it is easy to implement: set the flag when adding, completing, or deleting, and save on exit only if the flag is set. For learning programs, the flag is optional, but learning it now introduces a pattern you will meet again in editors and other stateful programs. Track changes, save when dirty, and skip when clean, is a tidy rule.

Finally, saving on exit should be tested, by making changes, exiting normally, restarting, and confirming that the changes persisted, which is the round-trip test for the whole task program.

let tasks = ["[ ] Buy milk", "[x] Call Ana"]
let text = tasks.joined(separator: "\n")
print(text)

Section 44: Common File Mistakes

Common file mistakes fall into a few patterns that are worth learning to recognise, since recognising them in advance prevents hours of debugging. One pattern is using the wrong path, such as a relative path from the wrong working folder, a hard-coded user name, or a missing folder in the path, which produces file-not-found errors that seem mysterious until the actual path is printed. The fix is to print the path, check the working folder, and build paths from helpers, as covered earlier, which turns a mystery into a quick check. Another pattern is confusing replacing with appending, such as using a replacing write when an append was intended, which destroys existing data, or appending when a snapshot was intended, which duplicates data. The fix is to ask, for each write, whether the file should hold the latest state or a history, and to choose the operation that matches, which is a design question to answer before coding. Path and operation confusion are the two most frequent file mistakes, and both are prevented by pausing to think before writing.

A third pattern is forgetting error handling, such as using a throwing file operation without do-catch, or using try? everywhere and ignoring failures, which leads to silent data loss or to programs that behave as if they loaded data they never did. The fix is to handle errors deliberately, with messages that include the path and the error, and to decide, for each operation, whether failure means defaults, a warning, or a stop, rather than letting failures pass silently. A fourth pattern is neglecting encoding, such as reading with one encoding and writing with another, or assuming a default encoding, which produces garbled text that is hard to diagnose without encoding knowledge. The fix is to use UTF-8 explicitly on both sides, consistently, which prevents most encoding problems, and to check encoding first when text looks wrong. Error handling and encoding are invisible when correct, but they cause disproportionate trouble when neglected, so they deserve deliberate attention.

A fifth pattern is holding files open or resources unclosed, which matters more for handles than for whole-file operations, but which also appears as temporary files left behind, or as files locked by a program that crashed while holding them. The fix is defer for handles and temporary files, as in the clean code chapter, which guarantees cleanup on every exit, and it is a habit to apply whenever a resource is acquired. A sixth pattern is not backing up before overwriting important files, which turns a logic bug or a mistaken write into permanent data loss, when a backup would have made it recoverable. The fix is the backup habit, applied automatically for important files, with verification, so that recovery is possible. Together, these patterns cover most file bugs, and a checklist that asks about path, operation, errors, encoding, cleanup, and backup will catch them before they cause harm.

A final pattern is testing only the success path, such as testing a file program only with existing, well-formed files, and never with missing files, empty files, malformed lines, or permission failures, which leaves the error handling untested and therefore unreliable.

Section 45: Testing File Code Without Real Files

Testing file code presents a challenge, because tests that use real files can be slow, can leave clutter, and can interfere with each other if they share file names, which makes them unreliable. A better approach for many tests is to use temporary folders, created fresh for each test and deleted afterwards, so that each test works in isolation, with its own files, and no test affects another or the user's real data. Swift's FileManager provides a temporary directory, and a test can create a unique subfolder inside it, using a random name or a test name, run its file operations there, and then delete the subfolder in a defer or cleanup step, guaranteeing tidiness even if the test fails. Temporary-folder testing is a standard professional technique, and it lets file code be tested thoroughly without risking real data, which is essential for deletion and overwrite tests in particular. Isolated tests are trustworthy tests, and temporary folders provide isolation cheaply.

Another testing technique is to separate the logic from the file operations, so that the logic can be tested without files at all, while only a thin layer of file code needs file-based tests. For example, a task parser that turns lines into task records can be tested by passing it strings directly, without reading any file, while the file loader that reads the file and passes its text to the parser needs only a few file tests to prove the reading works. This separation follows the single-job principle, since parsing and reading are different jobs, and it makes most testing fast and file-free, with only the file layer requiring temporary folders. When you design file programs, look for logic that can be extracted from file operations, such as parsing, formatting, filtering, and sorting, and test that logic with plain values, which is faster and more reliable than file-based tests. Separation of logic and I/O is a powerful testing strategy, and it improves design as well as testability.

Mocking, or using fake file operations, is a more advanced technique where a program's file access is replaced, during testing, with an in-memory substitute that behaves like files but stores data in memory, allowing tests to run without any disk access. This requires designing the program to accept a file-access abstraction, rather than calling FileManager directly everywhere, which is a design investment that pays off in large programs with extensive file testing. For learning programs, temporary folders and logic separation are sufficient, and mocking can be learned later, when programs grow large enough to justify the abstraction. The key idea, at any level, is that tests should be isolated, repeatable, and safe, which means they should not depend on the state of the user's real files, should produce the same result every time, and should clean up after themselves. Tests that violate these principles will eventually fail mysteriously, eroding trust in testing itself.

Practising file testing starts with small steps: write a test, by hand if no test framework is yet in use, that creates a temporary folder, writes a known file into it, runs your loader, and checks that the loaded data matches the known data, then deletes the folder.

Section 46: Organising Data Files in a Project

Organising data files in a project means deciding where files live, what they are called, and how they relate to each other, so that the project is easy to navigate, back up, and share. A common organisation is to keep data files in a dedicated folder, such as data or notes, separate from code, so that code and data do not mix, and so that backing up data means copying one folder. Within the data folder, subfolders can separate different kinds of data, such as tasks, notes, and settings, each with its own files, which makes each kind easy to find and manage. File names should be clear and consistent, such as tasks.txt, notes.txt, and settings.txt, with extensions that indicate format, and with dates in backup names where versions matter. A tidy data layout is a form of documentation, since it tells a new reader where each kind of data lives, without needing to search the code for paths.

Data organisation also affects portability, since a project that stores data in absolute paths scattered across the system is hard to move, while a project that stores data in folders relative to the project itself can be copied as a whole and still work. For a learning project, keeping data in a folder next to the code, or in a subfolder of the working directory, makes the project self-contained and easy to share, since copying the project folder copies both code and data. For a real application, data belongs in system-appropriate locations, such as documents or application support, which are not next to the code, but which are still organised consistently, with one folder per application and subfolders per data kind. The principle is the same in both cases: data has a home, that home is consistent, and the program finds its data through that home, not through scattered guesses. Consistent homes make programs portable and maintainable.

Version control and backups interact with data organisation, since code is usually version-controlled, while user data usually is not, and mixing them in one folder can cause data to be accidentally committed or code to be accidentally backed up with data. Keeping data in a separate folder, excluded from version control where appropriate, prevents user data from polluting code history, while still allowing the project's structure to be shared. For learning projects, this distinction matters less, but it is worth learning early, since real projects separate code, generated files, and user data carefully, with different backup and sharing policies for each. A data folder that is clearly marked, with a brief note explaining what lives there, helps future collaborators respect those policies, and it prevents the common mistake of committing a user's private notes to a shared repository. Organisation is not just tidiness, but protection for data and for collaborators.

Naming and documentation complete data organisation, since a folder of files with cryptic names, such as f1.txt and data2.csv, is almost as bad as no organisation, while clear names and a short readme or comment explaining the layout make the project welcoming. A data folder might contain a readme file explaining each file's format, such as "tasks.txt: one task per line, [ ] or [x] marker," which is invaluable for future readers, including yourself, who may forget the formats.

let dataFiles = ["tasks.txt", "notes.txt", "settings.txt"]
for file in dataFiles {
    print("Data file: \(file)")
}

Section 47: Reading Configuration Files

Configuration files are files that store settings and options for a program, such as file paths, feature flags, limits, and credentials for services, although credentials should be handled with extra care, as later security chapters will explain. Configuration files let users and administrators customise a program without changing its code, by editing a text file and restarting the program, which is far easier and safer than recompiling. Common configuration formats include key=value lines for simple settings, JSON for structured settings, and specialised formats for complex systems, and the choice depends on the settings' complexity and on who will edit them. For simple programs, key=value is ideal, since it is human-readable and easy to parse, while for structured settings with nested options, JSON, which you will learn next, is better. Configuration is data that controls behaviour, and storing it in a file separates behaviour from code, which is a powerful design principle.

Reading a configuration file follows the tolerant-loading pattern from settings, since a missing configuration file should usually produce defaults, allowing the program to run with sensible behaviour, rather than failing, unless the configuration is essential. Unknown keys should be ignored, so that newer configurations do not break older programs, and malformed lines should be skipped with warnings, preserving the good settings, since a single typo should not disable a whole program. After loading, the program should validate the configuration values, such as checking that a limit is positive or that a path is non-empty, with guards that fall back to defaults or report errors for invalid values, depending on how critical each setting is. Validation at load time, with clear messages naming the setting and its problem, prevents mysterious behaviour later, when an invalid setting causes a failure far from its source. Configuration loading is therefore a combination of tolerant parsing and strict validation, balanced by each setting's importance.

Configuration files should be located predictably, such as in the program's working folder for learning projects, in the user's home folder for personal programs, or in a system configuration folder for installed programs, with the location documented so that users can find and edit them. A program that looks for configuration in several places, such as a project folder first and then a home folder, can support both per-project and per-user settings, although that flexibility adds complexity and should be documented clearly. For learning programs, a single configuration file in a known location, such as config.txt in the current folder, is sufficient and easy to debug, since you can see and edit it directly. When a program starts, it can print the configuration file it loaded, or a message that defaults were used, which helps users understand why the program behaves as it does, and which aids debugging when behaviour seems wrong. Visibility into configuration is a kindness to users and to future debuggers.

Security is a special concern for configuration files, since they may contain sensitive information, such as passwords, API keys, or private paths, which should not be stored in plain text in a shared or version-controlled file.

let config = ["theme": "dark", "limit": "10"]
print(config["theme"] ?? "default")

Section 48: When Text Files Are Enough, and When Not

Text files are enough when data is small, simple, human-readable, and used by a single program at a time, which covers a large share of learning programs, including task lists, notes, settings, and logs. Their strengths are simplicity, visibility, and portability, since any editor can open them, any program can read them with basic tools, and they can be backed up, emailed, or version-controlled like any document. Their weaknesses appear as data grows more complex, with nested structures, relationships between records, large volumes, concurrent access, or queries such as "find all tasks due this week sorted by priority," which text files handle awkwardly. Recognising when text files are enough, and when they are straining, is a design judgement that prevents both over-engineering, where a database is used for a simple list, and under-engineering, where text files are forced to do a database's job. Use the simplest storage that handles the data comfortably, and upgrade when comfort ends, which is a practical rule for storage choice.

Signs that text files are straining include data that needs nesting, such as a task with subtasks, each with their own due dates and notes, which becomes contorted in a flat line format, and data that needs relationships, such as tasks linked to projects or users, which require lookups that text files do not provide efficiently. Another sign is size, since a text file with millions of lines becomes slow to load whole and awkward to update, requiring chunked reading and careful writing, which add complexity that a database handles internally. Concurrency is a further sign, since multiple programs or users writing to the same text file can overwrite each other's changes, as discussed with appending, while databases provide locking and transactions to handle concurrent access safely. Queries are a final sign, since finding, filtering, and sorting large text data in code is possible but becomes tedious compared with a database query language designed for exactly those operations. When several of these signs appear together, it is time to consider JSON for nesting, or a database for relationships, size, concurrency, and queries.

JSON, which is the next chapter's topic, is a natural step up from text files for nested and structured data, since it represents objects, arrays, and values in a standard, human-readable format, while still being a file that can be read and written with simple operations. JSON handles nesting gracefully, preserves types such as numbers and booleans, and is widely supported, which makes it ideal for settings, task objects, and data shared between programs. Databases, which come later in this book, are a further step up for large, relational, concurrent, or heavily queried data, since they provide indexing, transactions, and query languages that files cannot match. The progression from text to JSON to database is a ladder of storage power, and each rung suits a different scale of problem, so learning to choose the right rung is more valuable than mastering any single one in isolation. Start on the lowest rung that works, and climb only when the problem demands it.

Section 49: Building a File Helper Type

A file helper type is a struct or class that gathers file operations for a particular kind of data into one place, with methods for loading, saving, appending, and listing, so that the rest of a program works with data, not with file paths and encodings. For example, a TaskStore type might have methods to load tasks from a file, save tasks to a file, and add a task, hiding the details of paths, UTF-8, atomic writing, and error handling inside its methods, while presenting a clean interface to callers. This encapsulation follows the single-responsibility principle, since the helper's one job is file persistence for its data kind, and it makes the rest of the program shorter and clearer, since callers write store.load() instead of a block of file code. Helpers also centralise file decisions, such as the file name, the format, and the error policy, so that changing the format or the location requires changing one type, not every caller. Encapsulation is the natural next step after learning file operations, since it turns scattered file code into a reusable component.

Designing a file helper starts with choosing its responsibilities: which file it manages, what format it uses, what its methods do, and how it reports errors, whether by returning optionals, throwing errors, or printing messages. A good helper has a small, clear interface, with methods named for their jobs, such as load, save, and append, and with parameters that are data values, not file details, so that callers do not need to know paths or encodings. Error handling in a helper should be consistent, such as throwing errors for callers to handle, or returning nil for optional data, and the choice should be documented, since callers need to know what happens on failure. The helper should also handle its own edge cases, such as a missing file on load, with the tolerant or strict policy appropriate to its data, so that callers receive sensible results without needing to handle file minutiae. A well-designed helper feels like a service, not like a wrapper around file calls, because it thinks in terms of data, not files.

Testing a file helper is easier than testing scattered file code, since the helper can be tested in isolation, with temporary folders, by calling its methods and checking their results, without involving the rest of the program. A test can create a helper for a temporary file, save known data, load it back, and compare, which is a round-trip test for the helper's format and persistence, and it can test edge cases, such as loading a missing file, by pointing the helper at a non-existent temporary path. This isolation is a benefit of encapsulation, since it turns file testing into helper testing, which is focused and repeatable, and it gives confidence that the helper works before it is used elsewhere. When a helper is used by several parts of a program, its tests protect all of them, which is more efficient than testing file code in each caller separately. Helpers and tests reinforce each other, as with other clean code patterns.

Section 50: Putting It All Together

This final section brings together the file skills of this chapter into one picture, so that you can see reading, writing, appending, listing, and organising as a single toolkit for programs that remember. The toolkit starts with paths and FileManager, which locate and manage files, continues with whole-file reading and writing, which load and save text, and extends to appending, listing, moving, copying, and deleting, which maintain files over time. Around these operations sit the safety habits: guard for requirements, do-catch for failures, atomic writes for safe replacement, backups before overwriting, verification after writing, and defer for cleanup where handles are involved, all of which you learned in this and the previous chapter. Together, these tools and habits let you build programs that store tasks, notes, settings, logs, and tables reliably, which is a major step from programs that forget everything when they close. Files turn programs into tools, and this chapter has given you the tools to build them.

A good way to remember the toolkit is to picture the load-process-save cycle, which is the heartbeat of file programs: load data from a file into memory, process it with collections and helpers, and save the result back, with guards at the start, error handling around the risky steps, and verification at the end. Every file program in this chapter follows this cycle, whether it is a notes list, a CSV table, a settings file, or a log reader, and recognising the cycle helps you design new file programs, since you can start by asking what to load, how to process, and how to save. The cycle also connects to the clean code habits, since loading, processing, and saving are separate jobs that deserve separate helpers, with clear names and single responsibilities, rather than being tangled in one long function. When you face a new file problem, sketch its cycle first, and the implementation will follow naturally, with each stage using the tools from this chapter.

The next chapters will build on file skills in important ways, starting with JSON, which stores structured data in files, using the same reading and writing operations but with a richer format, and continuing with dates, which appear in files as timestamps and deadlines, and concurrency, which affects how files are accessed. File skills are therefore not an isolated topic, but a foundation for data work, since almost every program that handles data must store it somewhere, and files are the simplest and most universal storage. As you learn JSON, notice how its file operations reuse the patterns from this chapter, with encoding and decoding added as processing steps inside the cycle, and as you learn dates, notice how timestamps in logs and tasks use the same file cycle. Foundations compound, and the time spent on files will pay off in every data chapter that follows.
