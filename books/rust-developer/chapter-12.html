The rule that prevents a mutable reference and an immutable reference from coexisting stops data races and surprising changes while another part of the program is reading.

References do not own the data they point to, so when a reference goes out of scope, the underlying value is not dropped and its owner can keep using it. Passing a reference to a function is usually cheaper than moving a large value, because only the reference is copied, not the data behind it. Borrowing is checked at compile time, so a program that borrows incorrectly will not compile, and the error will name the conflicting borrows involved. A reference must never outlive the value it points to, and the compiler enforces this rule, which is why dangling references cannot occur in safe Rust.

You can create a reference with an ampersand and use it with the same operations you would use on the value, because Rust dereferences references automatically in many places. Mutable borrowing requires the original variable to be declared mutable, because borrowing cannot grant permission that the owner itself does not have. When a mutable borrow ends, the owner can use the value again, and the scope of the borrow is determined by its last use, not just by a closing brace. Borrowing makes it possible for several functions to work with the same data in turn, without passing ownership back and forth between every call.

A common beginner mistake is trying to hold a mutable reference while also using the original variable, and the compiler will refuse that pattern for your safety. Reading a borrow error means asking which borrow is still alive, where it was last used, and whether an earlier use can be moved or the borrow can be shortened. Borrowing works with strings, vectors, structs, and other types in the same way, so once you understand references for one type, the pattern transfers widely.
