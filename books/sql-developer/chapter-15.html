Chapter 15: UPDATE: Changing Rows Safely

Section 1: What UPDATE Does

When learners first meet what update does, the idea can seem abstract, so this section grounds it in small fictional examples you can follow by hand. In practice, what update does appears whenever a report, a check, or a correction needs a result that is grouped, renamed, added, or changed in a controlled way. When an update has no filter, every row in the table changes, which is almost never what a correction intends, so treat a filterless update as a warning sign and stop to check.

Updating several columns at once is allowed, but each column change should have a clear reason, and you should be able to explain every new value in plain language. Numbers can be increased, decreased, or replaced, text can be corrected, dates can be moved, and a value can be set to NULL, but each kind of change has its own pitfalls. Transactions provide a safety net for updates, because you can check the changed rows and then either commit the correct change or roll back a mistake.

After an update, verify by selecting the affected rows again and comparing the old and new values, and note how many rows the database reports as changed. A small fictional example makes update safety vivid: correcting one book price should change one row, not every book price, and the row count tells you immediately if something went wrong. Filters using lists, ranges, or patterns need extra care, because a pattern that is too broad can match rows you never intended to change.

Related tables add another layer of care, because changing a key or a referenced value can affect other rows, and the rules of the table will either block or allow that change. Keep a simple safety checklist for every update: preview first, use a precise filter, change only the intended columns, verify afterwards, and keep a note of what changed and why. Practice updates on practice data until previewing feels automatic, because the habit, not just the syntax, is what protects real data from accidental mass changes.

An update does not create a new row and does not delete a row, it rewrites values inside rows that already exist, and understanding that distinction prevents confusion with other statements. When in doubt, ask whether the change should affect one row, a defined group, or all rows, and if you cannot answer clearly, do not run the update yet. Changing existing rows is powerful, and it deserves more caution than adding rows, because an update can alter many rows at once and the change may be hard to undo. The safest habit is to preview with a SELECT using the same filter you plan to use for the update, so you can see exactly which rows will change before anything changes. A filter based on a unique key, such as a single fictional order id or customer id, is the most precise way to target one row, and it should be your default for single-row corrections.

UPDATE books
SET price = 24.50
WHERE book_id = 42;

When in doubt, ask whether the change should affect one row, a defined group, or all rows, and if you cannot answer clearly, do not run the update yet. Changing existing rows is powerful, and it deserves more caution than adding rows, because an update can alter many rows at once and the change may be hard to undo.

The safest habit is to preview with a SELECT using the same filter you plan to use for the update, so you can see exactly which rows will change before anything changes. A filter based on a unique key, such as a single fictional order id or customer id, is the most precise way to target one row, and it should be your default for single-row corrections. When an update has no filter, every row in the table changes, which is almost never what a correction intends, so treat a filterless update as a warning sign and stop to check.

Updating several columns at once is allowed, but each column change should have a clear reason, and you should be able to explain every new value in plain language. Numbers can be increased, decreased, or replaced, text can be corrected, dates can be moved, and a value can be set to NULL, but each kind of change has its own pitfalls. Transactions provide a safety net for updates, because you can check the changed rows and then either commit the correct change or roll back a mistake.

After an update, verify by selecting the affected rows again and comparing the old and new values, and note how many rows the database reports as changed. A small fictional example makes update safety vivid: correcting one book price should change one row, not every book price, and the row count tells you immediately if something went wrong. Filters using lists, ranges, or patterns need extra care, because a pattern that is too broad can match rows you never intended to change. Related tables add another layer of care, because changing a key or a referenced value can affect other rows, and the rules of the table will either block or allow that change. Keep a simple safety checklist for every update: preview first, use a precise filter, change only the intended columns, verify afterwards, and keep a note of what changed and why.
