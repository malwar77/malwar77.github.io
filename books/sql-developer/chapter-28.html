A self join treats one table as if it were two tables by giving it two different aliases in the same query. One alias plays the first role and the other plays the second role, and the ON clause compares a column from the first alias with a column from the second alias. In an employee table, for example, one alias can stand for employees and the other for managers, with the employee manager identifier matched against the manager identifier.

Section 2: One Table, Two Roles

One Table, Two Roles matters because it changes which rows a query returns, and row selection is the heart of almost every SQL question. In plain words, one table, two roles is a tool for stating a question precisely, so that the database returns exactly the rows you meant and no others. Beginners often meet this idea in a confusing result, where rows are missing or duplicated and the reason is not obvious at first glance. Learning it now will save you puzzling later, because the same idea returns in reports, in checks for missing data, and in larger queries built from smaller parts. Keep the chapter idea in view as you read: self joins and hierarchical data is the theme, and this section is one careful step inside it.

Hierarchical data stores a parent link inside each row, so a child row points upward to its parent row in the same table. A self join follows that link for one level: join the table to itself on the parent link and you can show a child beside its parent. To go two levels, you join a third copy of the table and follow the link again. Each extra copy adds one more level, but also adds complexity, so self joins are clearest for one or two levels, while deeper trees usually call for a different technique that the chapter notes in passing.

FROM courses AS child

Another trap is doubling pairs. If Ada and Bola share a course, a naive self join lists Ada with Bola and also Bola with Ada, which doubles the count and confuses a report. Requiring the first identifier to be smaller than the second keeps only one ordering of each pair. A third trap is assuming a self join can walk a whole tree in one step.

Reports that ignore those rows can look complete while quietly hiding gaps, so learning to keep or to find them on purpose is a practical skill, not only an academic one.

Section 48: A Safe Habit for Every Self Join

This section looks closely at a safe habit for every self join, and it does so in plain words before it shows any syntax. The goal is not to memorise a keyword, but to understand the question that keyword answers. Ask yourself, as you read, what would be harder without this idea, and what mistake would be easy to make if you did not know it. That question is a useful guide, because SQL rewards writers who know what they are asking for. A query that looks correct but answers the wrong question is harder to fix than a query with a simple typing error, and this section helps you avoid that first kind of mistake.

Pairs inside one table are another classic self join job. Joining a table to itself on a shared value, such as the same course or the same town, finds pairs of rows that share that value. Care is needed to avoid pairing a row with itself and to avoid listing each pair twice in both orders. A simple comparison between the two aliases, such as requiring the first identifier to be smaller than the second, removes both problems in many cases. That small condition is easy to forget and its absence is a common cause of doubled results.

The example in this section uses only fictional data, with invented names for people, books, orders and courses, so that no real personal information is involved and every row can be checked by hand. That small size is a strength while you learn: you can list the rows you expect, run the query, and compare the two lists row by row. If a row you expected is missing, ask whether the matching rule excluded it or whether a filter removed it. If an extra row appears, ask whether a key matched more than once. Those two questions, missing row and extra row, cover most debugging in this chapter, and they work for every section that follows.

FROM employees AS e
LEFT JOIN employees AS child ON child.manager_id = e.employee_id
GROUP BY e.employee_name;

Ordering by parent first, then by child, lets a reader scan the tree top to bottom instead of hunting through scattered rows. Section 49: Choosing Self Join, Subquery or Lookup

Choosing Self Join, Subquery or Lookup is an important part of learning SQL, and this section takes it one careful step at a time. In plain words, choosing self join, subquery or lookup describes a piece of knowledge you will meet in real queries, not only in textbook examples. When you first meet a new idea like this, it can feel abstract, because the words are unfamiliar and the query looks short but dense. The way through that feeling is to connect the idea to something concrete: a small fictional table you can picture, a result row you can check, or a small change you can make and watch. As you read, keep a practice database in mind, so that every claim in this section can be tested rather than merely believed.

A self join treats one table as if it were two tables by giving it two different aliases in the same query. One alias plays the first role and the other plays the second role, and the ON clause compares a column from the first alias with a column from the second alias. In an employee table, for example, one alias can stand for employees and the other for managers, with the employee manager identifier matched against the manager identifier.

Here is a short example to study, keeping choosing self join, subquery or lookup in mind as you read each line. The example is deliberately small, because a small example lets you follow every row without getting lost in extra details. Type the example yourself rather than only reading it, because typing forces you to notice each keyword and each table alias. As you work through it, say what each line does in your own words, and predict the result before you run it. If the result does not match your prediction, do not simply move on: that mismatch is the most useful moment in the whole exercise, because it points exactly to the part of your understanding that needs adjusting.

SELECT e.employee_name AS employee, m.employee_name AS manager
FROM employees AS e
LEFT JOIN employees AS m ON m.employee_id = e.manager_id
ORDER BY e.employee_name;

The most common self join mistake is forgetting an alias, or reusing the same alias for both copies of the table, which makes the query ambiguous or wrong. Give each copy a role name that a reader can follow, such as employee and manager, or child and parent, and use those names on every column. A second slip is pairing a row with itself, which happens when the ON clause only matches a shared value and does not exclude identical rows.

When you practise choosing self join, subquery or lookup, start with a tiny fictional table and a question you can answer by hand, then write the query and compare the two answers. That loop of predicting, running, and comparing is the core skill of SQL, and this section is a safe place to practise it. Over time, the same loop scales to larger tables and to queries that combine several ideas from this book, including joins, filters, grouping, and subqueries.

Section 50: Review: One Table, Many Relationships

Review: One Table, Many Relationships matters because it changes which rows a query returns, and row selection is the heart of almost every SQL question. In plain words, review: one table, many relationships is a tool for stating a question precisely, so that the database returns exactly the rows you meant and no others. Beginners often meet this idea in a confusing result, where rows are missing or duplicated and the reason is not obvious at first glance. Learning it now will save you puzzling later, because the same idea returns in reports, in checks for missing data, and in larger queries built from smaller parts. Keep the chapter idea in view as you read: self joins and hierarchical data is the theme, and this section is one careful step inside it.

Hierarchical data stores a parent link inside each row, so a child row points upward to its parent row in the same table. A self join follows that link for one level: join the table to itself on the parent link and you can show a child beside its parent. To go two levels, you join a third copy of the table and follow the link again. Each extra copy adds one more level, but also adds complexity, so self joins are clearest for one or two levels, while deeper trees usually call for a different technique that the chapter notes in passing.

Study the example below as a worked answer to a plain question about fictional data, such as customers and orders, members and books, or students and courses. Read the FROM clause first to see which tables are involved, then the matching or filtering clause to see which rows survive, and only then the SELECT list to see which columns are shown. That reading order matches how the database reasons about the query, and it helps you spot a wrong key or a misplaced filter before you worry about column names.

SELECT child.course_name AS course, parent.course_name AS prerequisite
FROM courses AS child
LEFT JOIN courses AS parent ON parent.course_id = child.prerequisite_id;
