Chapter 29: Subqueries: Queries Inside Queries

Section 1: What a Subquery Is

What a Subquery Is is an important part of learning SQL, and this section takes it one careful step at a time. In plain words, what a subquery is describes a piece of knowledge you will meet in real queries, not only in textbook examples. When you first meet a new idea like this, it can feel abstract, because the words are unfamiliar and the query looks short but dense. The way through that feeling is to connect the idea to something concrete: a small fictional table you can picture, a result row you can check, or a small change you can make and watch. As you read, keep a practice database in mind, so that every claim in this section can be tested rather than merely believed.

A subquery is a complete SELECT statement placed inside another statement, usually inside parentheses. The inner query runs first in concept, and its result is used by the outer query as a value, a list, or a table. A scalar subquery returns a single value, such as an average price, which the outer query can compare against. A list subquery returns one column of values for IN or NOT IN.

Here is a short example to study, keeping what a subquery is in mind as you read each line. The example is deliberately small, because a small example lets you follow every row without getting lost in extra details. Type the example yourself rather than only reading it, because typing forces you to notice each keyword and each table alias. As you work through it, say what each line does in your own words, and predict the result before you run it. If the result does not match your prediction, do not simply move on: that mismatch is the most useful moment in the whole exercise, because it points exactly to the part of your understanding that needs adjusting.

SELECT customer_name FROM customers
WHERE customer_id IN (SELECT customer_id FROM orders
WHERE order_total > 50);

The most common subquery mistake is returning the wrong shape: a scalar comparison that receives several rows, or an IN list that receives several columns, will fail or mislead. Before writing the outer query, run the inner query alone and check how many rows and columns it returns. A second slip is forgetting NULL with NOT IN, where a single NULL in the inner list can make the whole NOT IN test return no rows at all.

When you practise what a subquery is, start with a tiny fictional table and a question you can answer by hand, then write the query and compare the two answers. That loop of predicting, running, and comparing is the core skill of SQL, and this section is a safe place to practise it. Over time, the same loop scales to larger tables and to queries that combine several ideas from this book, including joins, filters, grouping, and subqueries. Confidence grows from those small, successful uses, repeated over time, rather than from trying to learn everything at once.

In plain words, queries inside queries in plain words is a tool for stating a question precisely, so that the database returns exactly the rows you meant and no others. Beginners often meet this idea in a confusing result, where rows are missing or duplicated and the reason is not obvious at first glance. Learning it now will save you puzzling later, because the same idea returns in reports, in checks for missing data, and in larger queries built from smaller parts. Keep the chapter idea in view as you read: subqueries: queries inside queries is the theme, and this section is one careful step inside it.

Correlated subqueries are different because they refer to a column from the outer query, so they cannot be run once and forgotten. Conceptually the inner query is evaluated again for each outer row, using that row value in its own filter. That makes correlated subqueries powerful for row-by-row questions, such as whether this particular customer has any order, but it also means they deserve a small test first. Reading a correlated subquery means following the link between the inner and outer aliases, which is why clear alias names matter even more here than in a simple join.

That reading order matches how the database reasons about the query, and it helps you spot a wrong key or a misplaced filter before you worry about column names.

SELECT book_title, book_price FROM books
WHERE book_price > (SELECT AVG(book_price) FROM books);

Another trap is nesting without reading from the inside out. A deeply nested subquery is hard to review when it is read top to bottom, because the innermost query is the one that runs first in concept. Read the innermost SELECT, state its result in one sentence, then move outward one level at a time, replacing each subquery with that sentence.

A useful way to remember queries inside queries in plain words is to picture the tables involved and to ask which rows must survive no matter what. Draw the two tables on paper if it helps, draw lines for the matches, and circle the rows that have no line. Those circled rows are often the interesting ones, because they reveal missing orders, unborrowed books, or unenrolled students. Reports that ignore those rows can look complete while quietly hiding gaps, so learning to keep or to find them on purpose is a practical skill, not only an academic one.

Section 3: A Subquery in the WHERE Clause

This section looks closely at a subquery in the where clause, and it does so in plain words before it shows any syntax. The goal is not to memorise a keyword, but to understand the question that keyword answers. Ask yourself, as you read, what would be harder without this idea, and what mistake would be easy to make if you did not know it. That question is a useful guide, because SQL rewards writers who know what they are asking for. A query that looks correct but answers the wrong question is harder to fix than a query with a simple typing error, and this section helps you avoid that first kind of mistake.

Choosing between a subquery and a join is often a readability choice rather than a right-or-wrong choice. A subquery can state a filter in plain steps, first find the set you care about, then keep rows that belong to it. A join can state the same idea as a combined table. When the question is about existence or about comparing against an aggregate, a subquery often reads most directly. When the question needs columns from both tables in the output, a join often reads more naturally. Either way, testing on small fictional data settles the question faster than debating it in the abstract.

The example in this section uses only fictional data, with invented names for people, books, orders and courses, so that no real personal information is involved and every row can be checked by hand. That small size is a strength while you learn: you can list the rows you expect, run the query, and compare the two lists row by row. If a row you expected is missing, ask whether the matching rule excluded it or whether a filter removed it. If an extra row appears, ask whether a key matched more than once. Those two questions, missing row and extra row, cover most debugging in this chapter, and they work for every section that follows.

SELECT customer_name,
  (SELECT COUNT(*) FROM orders WHERE orders.customer_id = customers.customer_id) AS order_count
FROM customers;

A third habit is to check correlation carefully. In a correlated subquery, the inner query must refer to the outer alias, not to a column that happens to share a name. A missing or wrong outer reference can turn a correlated question into an uncorrelated one, which returns the same set for every outer row and silently changes the answer. Giving the outer and inner tables distinct aliases, and qualifying every column, makes that link visible and checkable.

As you finish this section, try explaining a subquery in the where clause to a friend in plain words, without looking at the example. If you can state the question it answers, the rows it keeps, and the rows it drops, you understand it well enough to use it with confidence. If part of that explanation feels shaky, reread that part of the section and try a second tiny example before moving on. That pause is not wasted time; it is how a fragile first understanding becomes a reliable tool.

This section looks closely at subqueries in a report for every book, and it does so in plain words before it shows any syntax. The goal is not to memorise a keyword, but to understand the question that keyword answers. Ask yourself, as you read, what would be harder without this idea, and what mistake would be easy to make if you did not know it. That question is a useful guide, because SQL rewards writers who know what they are asking for. A query that looks correct but answers the wrong question is harder to fix than a query with a simple typing error, and this section helps you avoid that first kind of mistake.

Choosing between a subquery and a join is often a readability choice rather than a right-or-wrong choice. A subquery can state a filter in plain steps, first find the set you care about, then keep rows that belong to it. A join can state the same idea as a combined table. When the question is about existence or about comparing against an aggregate, a subquery often reads most directly. When the question needs columns from both tables in the output, a join often reads more naturally. Either way, testing on small fictional data settles the question faster than debating it in the abstract.

The example in this section uses only fictional data, with invented names for people, books, orders and courses, so that no real personal information is involved and every row can be checked by hand. That small size is a strength while you learn: you can list the rows you expect, run the query, and compare the two lists row by row. If a row you expected is missing, ask whether the matching rule excluded it or whether a filter removed it. If an extra row appears, ask whether a key matched more than once. Those two questions, missing row and extra row, cover most debugging in this chapter, and they work for every section that follows.

SELECT course_name FROM courses
WHERE course_id IN (SELECT course_id FROM enrolments
GROUP BY course_id HAVING COUNT(*) >= 3);

A third habit is to check correlation carefully. In a correlated subquery, the inner query must refer to the outer alias, not to a column that happens to share a name. A missing or wrong outer reference can turn a correlated question into an uncorrelated one, which returns the same set for every outer row and silently changes the answer. Giving the outer and inner tables distinct aliases, and qualifying every column, makes that link visible and checkable.

That pause is not wasted time; it is how a fragile first understanding becomes a reliable tool.

Section 49: A Safe Habit for Every Subquery You Write

A Safe Habit for Every Subquery You Write is an important part of learning SQL, and this section takes it one careful step at a time. In plain words, a safe habit for every subquery you write describes a piece of knowledge you will meet in real queries, not only in textbook examples. When you first meet a new idea like this, it can feel abstract, because the words are unfamiliar and the query looks short but dense. The way through that feeling is to connect the idea to something concrete: a small fictional table you can picture, a result row you can check, or a small change you can make and watch. As you read, keep a practice database in mind, so that every claim in this section can be tested rather than merely believed.

A subquery is a complete SELECT statement placed inside another statement, usually inside parentheses. The inner query runs first in concept, and its result is used by the outer query as a value, a list, or a table. A scalar subquery returns a single value, such as an average price, which the outer query can compare against. A list subquery returns one column of values for IN or NOT IN.

Here is a short example to study, keeping a safe habit for every subquery you write in mind as you read each line. The example is deliberately small, because a small example lets you follow every row without getting lost in extra details. Type the example yourself rather than only reading it, because typing forces you to notice each keyword and each table alias. As you work through it, say what each line does in your own words, and predict the result before you run it. If the result does not match your prediction, do not simply move on: that mismatch is the most useful moment in the whole exercise, because it points exactly to the part of your understanding that needs adjusting.

SELECT customer_name FROM customers
WHERE customer_id IN (SELECT customer_id FROM orders
WHERE order_total > 50);

The most common subquery mistake is returning the wrong shape: a scalar comparison that receives several rows, or an IN list that receives several columns, will fail or mislead. Before writing the outer query, run the inner query alone and check how many rows and columns it returns. A second slip is forgetting NULL with NOT IN, where a single NULL in the inner list can make the whole NOT IN test return no rows at all.

When you practise a safe habit for every subquery you write, start with a tiny fictional table and a question you can answer by hand, then write the query and compare the two answers. That loop of predicting, running, and comparing is the core skill of SQL, and this section is a safe place to practise it. Over time, the same loop scales to larger tables and to queries that combine several ideas from this book, including joins, filters, grouping, and subqueries.

Section 50: Review: Inner Query First, Outer Query Second

Review: Inner Query First, Outer Query Second matters because it changes which rows a query returns, and row selection is the heart of almost every SQL question. In plain words, review: inner query first, outer query second is a tool for stating a question precisely, so that the database returns exactly the rows you meant and no others. Beginners often meet this idea in a confusing result, where rows are missing or duplicated and the reason is not obvious at first glance. Learning it now will save you puzzling later, because the same idea returns in reports, in checks for missing data, and in larger queries built from smaller parts. Keep the chapter idea in view as you read: subqueries: queries inside queries is the theme, and this section is one careful step inside it.

Correlated subqueries are different because they refer to a column from the outer query, so they cannot be run once and forgotten. Conceptually the inner query is evaluated again for each outer row, using that row value in its own filter. That makes correlated subqueries powerful for row-by-row questions, such as whether this particular customer has any order, but it also means they deserve a small test first. Reading a correlated subquery means following the link between the inner and outer aliases, which is why clear alias names matter even more here than in a simple join.

Study the example below as a worked answer to a plain question about fictional data, such as customers and orders, members and books, or students and courses. Read the FROM clause first to see which tables are involved, then the matching or filtering clause to see which rows survive, and only then the SELECT list to see which columns are shown. That reading order matches how the database reasons about the query, and it helps you spot a wrong key or a misplaced filter before you worry about column names.

SELECT book_title, book_price FROM books
WHERE book_price > (SELECT AVG(book_price) FROM books);

Another trap is nesting without reading from the inside out. A deeply nested subquery is hard to review when it is read top to bottom, because the innermost query is the one that runs first in concept. Read the innermost SELECT, state its result in one sentence, then move outward one level at a time, replacing each subquery with that sentence.

A useful way to remember review: inner query first, outer query second is to picture the tables involved and to ask which rows must survive no matter what. Draw the two tables on paper if it helps, draw lines for the matches, and circle the rows that have no line. Those circled rows are often the interesting ones, because they reveal missing orders, unborrowed books, or unenrolled students. Reports that ignore those rows can look complete while quietly hiding gaps, so learning to keep or to find them on purpose is a practical skill, not only an academic one.
