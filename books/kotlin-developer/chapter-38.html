Chapter 38: Object-Oriented Design in Practice

This chapter teaches object-oriented design in practice in small, friendly steps. Each section explains one idea, shows a short example, and ends with a question you can answer in your own words. Work through the sections in order, try every example, and do not worry about speed. Understanding one section well is better than rushing through five.

Section 1: Designing Before Coding

This section is about designing before coding in the context of object-oriented design in practice. When you build a object-oriented program, you will meet this idea again and again, so it is worth understanding it clearly before you move on. Start by forming a plain picture in your mind: what goes in, what comes out, and who benefits from the result. If that picture is fuzzy, the code that follows will feel fuzzy too, because code only makes a clear idea concrete. Take a moment to say the idea in your own words, without looking at any example, and notice which part you find hardest to explain.

Why does designing before coding matter for someone learning Kotlin? It matters because real programs are judged by how they behave for real users, not by how clever they look to the person who wrote them. A program that handles designing before coding well feels calm and predictable: it gives useful feedback, it does not surprise the user, and it fails in a way that can be understood and fixed. By contrast, a program that ignores this idea may work once in a demonstration and then fail the first time a real person uses it differently. Good habits here therefore protect both the user and the programmer, and they make later changes safer because each part has a clear job.

In Kotlin, working with designing before coding usually means writing a small, focused piece of code and then calling it from a clear place in the program. Read the short example in this section slowly, line by line, and ask what each line contributes and what would change if you removed it. Try changing one value, predicting the output, and then checking your prediction by reasoning through the code again. This habit of prediction turns passive reading into active learning, and a wrong prediction is useful information rather than a failure. Keep the example small: one new idea at a time is easier to test, easier to debug, and easier to remember next week.

Beginners often stumble on the same points with designing before coding. One common mistake is rushing to a complicated case before the simple case is solid. Another is copying an example without understanding it, which works until the first small change is needed. A third is ignoring error messages instead of reading them as guidance about what went wrong. When something goes wrong, slow down, read the message, and check the simplest explanation first: spelling, brackets, types, and the values your variables actually hold at that point. Fix one thing at a time, test again, and write down what you learned.

To practise designing before coding, build a tiny program that uses only this idea and nothing else new. Run it, change one thing, and run it again, so you can watch cause and effect directly. Then connect it to ideas from earlier chapters: ask how it fits with functions, collections, null safety, and error handling that you have already met. That connection is where real understanding forms, because isolated facts fade quickly while linked ideas stay. Before moving on, explain the idea aloud in two or three sentences, as if teaching a friend who has never seen it before.

    fun describe(): String = "Task: $name"
}

    val task = Task("Learn design")
