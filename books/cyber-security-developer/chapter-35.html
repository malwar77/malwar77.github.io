Chapter 35: Input Validation and Safe Defaults

Section 1: What Is Input

This section is about what is input. It matters because it is one of the everyday habits that separate a careful defender from someone who only reacts after trouble arrives. Take it slowly, in plain words, and connect it to systems and files you own and control. The examples in this section use only your own computer, your own accounts, and your own notes. By the end, you should be able to explain what is input to a friend without jargon, and to say what you would check first, what you would do next, and what you would write down.

Input is any data that comes into your program from outside it. That includes text typed into a form, a file chosen for upload, a value in a web address, a setting changed in an app, and data received from another system. Input is not bad by itself; programs exist to accept input. The risk comes from assuming input will always be sensible, complete, and honest. It will not be. People make typos, systems send unexpected formats, and attackers deliberately send odd input to see what breaks. Checking input is how a program stays safe and useful.

An allow list is the strongest and simplest validation idea: decide exactly what is allowed, and reject everything else. If a field should contain only letters and a few safe characters, say so, and refuse the rest. If a choice should come from a short list, accept only items on that list. A deny list works the other way: it tries to list everything bad and block only those items. Deny lists fail because the list of bad things is long, creative, and always growing. Allow lists are stricter, but they are also clearer to users and easier to test.

Validation checks several things, and each check catches a different kind of problem. Type asks whether the value is the kind you expected, such as a number rather than text. Length asks whether it is too short or too long. Range asks whether a number or date falls inside sensible limits. Format asks whether it follows the expected pattern, such as an email shape or a date shape. A value can pass one check and fail another, so a careful program checks each one that matters for that field, in a clear order.

If the result surprises you, do not rush to a conclusion; check one more source, such as a second log, a settings page, or a trusted help page. A careful note, with the date and the result, turns a single exercise into a habit you can repeat. That habit is the real lesson of this section, more than any single fact, because defenders improve by repeating calm checks, not by memorising warnings.

Missing and empty values deserve their own thought. A required field that is empty is a different problem from an optional field left blank on purpose. A program should tell the user plainly which fields are required, accept a blank optional field without error, and never treat a missing value as a valid value by accident. Default values can help here, but only when the default is safe. A missing permission should default to no access, a missing sharing choice should default to private, and a missing setting should default to the safer option.

Server-side validation is the check that matters most, because it runs where the user cannot change it. Choosing a safe default is therefore a security decision, not a small detail. Section 3: Why Input Must Be Checked

This section is about why input must be checked. It matters because it is one of the everyday habits that separate a careful defender from someone who only reacts after trouble arrives. Take it slowly, in plain words, and connect it to systems and files you own and control. The examples in this section use only your own computer, your own accounts, and your own notes. By the end, you should be able to explain why input must be checked to a friend without jargon, and to say what you would check first, what you would do next, and what you would write down.

Validation messages should help, not shame or confuse. Tell the user what was wrong in plain words, and what a correct value looks like. Avoid technical jargon, avoid blaming language, and never repeat a secret or sensitive value back in an error message. A good message sounds like a helpful guide: this field needs a number between one and one hundred, for example, rather than a code. Helpful messages reduce mistakes, and fewer mistakes mean fewer frustrated users trying to work around the checks.

File uploads need extra care because a file is input too, and a file can carry more than its name suggests. Check the size first, so a huge file cannot fill your storage. Check the type by inspecting the content where you can, not only by trusting the file extension, because extensions are easy to rename. Store uploads in a safe place, limit who can access them, and never run an uploaded file as a program. When in doubt, reject the upload with a clear message and offer a safe alternative.

Validating in layers means checking at more than one place, so a single missed check does not leave the program open. The browser checks for fast feedback, the server checks for safety, and the part of the program that uses the data checks again before acting on it. Stored data should also be re-checked when it is read back, because data can change, age, or come from an older version of the program. Layers are not wasteful duplication; they are defence in depth applied to input.

Server-side validation is the check that matters most, because it runs where the user cannot change it. Checks in the browser are helpful for fast feedback and a friendly experience, but anyone can bypass them by changing the page, using a different tool, or sending a request directly. A program that only checks in the browser is like a shop that only locks the front door while the back door stands open. Check in the browser for kindness, and check on the server for safety, every time.

Safe defaults protect people who never change a setting, which is most people. A new account should start private, a new document should start unshared, and a new device should start with protection on. Defaults are powerful because they decide what happens when nobody decides. Choosing a safe default is therefore a security decision, not a small detail. When you change a default, tell users plainly what changed and why, and give them a simple way to choose differently if they wish.

Validation messages should help, not shame or confuse. Tell the user what was wrong in plain words, and what a correct value looks like. Helpful messages reduce mistakes, and fewer mistakes mean fewer frustrated users trying to work around the checks.

File uploads need extra care because a file is input too, and a file can carry more than its name suggests. Check the size first, so a huge file cannot fill your storage. Check the type by inspecting the content where you can, not only by trusting the file extension, because extensions are easy to rename. Store uploads in a safe place, limit who can access them, and never run an uploaded file as a program. When in doubt, reject the upload with a clear message and offer a safe alternative.

Validating in layers means checking at more than one place, so a single missed check does not leave the program open. The browser checks for fast feedback, the server checks for safety, and the part of the program that uses the data checks again before acting on it. Stored data should also be re-checked when it is read back, because data can change, age, or come from an older version of the program. Layers are not wasteful duplication; they are defence in depth applied to input.

Testing validation means trying the edge cases, not only the obvious good values. Try empty input, very long input, numbers at the exact limits and just beyond them, unexpected characters, and values from a different type. Try submitting a form with a required field missing, and try sending a value that is not on the choice list. Record which cases pass and which fail, and fix the failures before users meet them. A validation bug found in testing is a cheap lesson; the same bug found by a stranger is an incident.
